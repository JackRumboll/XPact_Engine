1. Purpose, Scope, and Locked Decisions

1.1 What XCore-4b is

XCore-4b is the C++ runtime that implements XPact's reflection types, including the UE-equivalent replication-metadata source on FProperty that XNetworking's FReplicationStateDescriptorRegistry consumes via reflection to build replication-state descriptors. It is the System 4 deliverable in the plan's Section 4 build order. It depends on XCore-4a (Phase 1a-1g; the no-reflection foundation: allocator, containers, FString, math, hash, CVars, Stat, FText runtime, threading primitives, FName 8-byte forward handle, XGCRootSpan weak-symbol stubs). It depends on XHT's parser (System 2) being already shipped but does NOT depend on XCoreXObject (System 5) which builds on XCore-4b.

The deliverables of XCore-4b are:

  • The FName intern table and full FName API (UTF-8 byte-exact case-sensitive, hot-reload-stable, shared-read fast path, FXxh3-64 hashed) — replaces the 8-byte forward handle declared in XCore-4a §11.8 with a complete implementation.
  • The FField base type — the polymorphism-free anchor of every reflected field-or-property descriptor.
  • The FProperty class and its complete subclass family (28 subclasses: 23 MVP from Rev 1 + 5 MVP additions per FIX-3 + 5 reserved post-MVP). FProperty carries the UE-equivalent pre-Iris replication-metadata set (RepIndex uint16, BlueprintReplicationCondition uint8, RepNotifyFunc FName) that XNetworking's FReplicationStateDescriptorRegistry reads via reflection to build its descriptors. XCore-4b is the SOURCE; the descriptor host lives in XNetworking at Layer 13.
  • The FClass / FStruct / FScriptStruct / FEnum / FInterface metadata descriptors — the reflection-side mirror of UE's UClass / UStruct / UScriptStruct / UEnum / UInterface, restructured per XPact's hot-reload + ABI requirements.
  • The XReflectionRuntime registry with lookup-by-FName, lookup-by-stable-symbol-name, and the per-module registration hooks XHT's .init.gen.cpp calls into. Replaces the XCore-Stub at Engine/Source/Runtime/XCore/Public/XReflectionRuntime.h.
  • The FCustomVersion subsystem + the per-type SchemaHash discipline (hashed over declared shape, not compiled offsets — see FIX-10) that closes UE's silent-serialization-mismatch class of bugs (Master Plan §2 Reflection schema versioning row).
  • The Toolchain Contract addendum that freezes XHT's emitter struct byte-layouts at Contract Rev 13.8 (Master Plan §4 Step 4: "XCore-4b triggers the Stage B addendum that freezes XHT's emitter struct layouts"). The addendum is a separate HTML file (XToolchainContract.html at Rev 13.8) that XCore-4b's implementation ships alongside; the addendum content is enumerated in §11 of this spec.

1.2 What XCore-4b is NOT

XCore-4b is bounded narrowly. It does NOT ship:

  • XObject base class. Deferred to System 5 (XCoreXObject). The XObject root, ClassDefaultObject lifecycle, and the GC-rooted heap are downstream concerns.
  • GC mark-and-sweep collector. Card-table write barriers, conservative root scanning, mark phase, sweep phase, generational scan-reduction, remembered-set saturation handling — all System 5. XCore-4a shipped the weak-symbol stubs XGC_WriteBarrier / XGC_RegisterRootSpan / XGC_UpdateRootSpan / XGC_UnregisterRootSpan at Phase 1g; XCore-4b leaves them as weak-symbol stubs (the XReflectionRuntime registry itself uses no GC).
  • Card-table generational scan-reduction. The remembered-set + card-table data structures live in System 5.
  • Asset serialization (FArchive<FProperty> round-trip on disk). XSerialization (System 9) consumes the FCustomVersion + per-type SchemaHash discipline + the HasSerializer / HasNetSerializer capability bits that XCore-4b ships, but the on-disk binary format itself is XSerialization's responsibility. XCore-4b ships the discipline (the version-bump-trigger registry, the SchemaHash registration API, the capability-bit set), not the format.
  • FReplicationStateDescriptor / FReplicationStateDescriptorRegistry / FNetObjectGroups. Per Master Plan Rev 15 (Iris architectural correction; Rev 15 line 173 amendment acknowledges FProperty 136→104 via FakeVTable), these live entirely in XNetworking (Layer 13) as process-singleton registries keyed by FFieldVariant. XCore-4b is the source: XNetworking's XReplicationStateDescriptorBuilder reads FProperty's UE-equivalent replication metadata (RepIndex + ELifetimeCondition + RepNotifyFunc) via reflection to build its descriptors at session-init; descriptors are cached against XCore-4b's reflection runtime.
  • Push-model replication runtime. The push-model declaration lives as a single bit in EPropertyFlags (CPF_PushModel); the runtime that consumes the flag, elides per-tick property iteration, and tracks dirty-state is XNetworking. No per-FProperty bitfield slot; the flag is enough.
  • FXObjectKey. Per FIX-9: XCore-4b's non-moving GC produces stable XObject pointers for object lifetime, but CDO replace-on-hot-reload moves the CDO pointer. FXObjectKey ({uint32 Index; uint32 SerialNumber}, analogous to FName, surviving hot-reload-replace-of-class) is the System 5 (XCoreXObject) responsibility. XCore-4b's stable-pointer guarantee holds only for object lifetime, not across class replacement.
  • Blueprint VM / blueprint compiler integration. The BlueprintFlags slot on FProperty is reserved; XBlueprintCompiler (Layer 21) consumes it.
  • Editor property-detail customization. The EditFlags slot on FProperty is reserved; XPropertyEditor (Layer 20) consumes it.

4. FName Design

FName is the heart of XCore-4b. Every reflected type name, every reflected property name, every reflected enum-value name, every XHT-emitted symbol name lives in the FName intern table. Every TMap<FName, V> lookup, every FProperty::IsA<T> cast, every XReflectionRuntime::FindClass call begins with an FName equality test. Performance, correctness, and hot-reload stability of FName underwrite every other surface in this spec.

4.1 Public surface

The 8-byte handle layout is locked by XCore-4a §11.8 + Contract Rev 13.7 §6 and CANNOT change in this spec without ABI-breaking every TMap<FName, V> instantiation engine-wide. XCore-4b implements the full API on top of the locked handle.

namespace XCore::Reflect {

// Layout-locked at XCore-4a §11.8 + Contract Rev 13.7 §6 (FName subsystem).
// XCore-4b ships the implementation; the handle layout is immutable.
struct FName {
    uint32_t Index;         // 0  +4   intern-table entry index (0 = NAME_None)
    uint32_t SerialNumber;  // 4  +4   numbered-name suffix (0 = no suffix)

    // Construction (XCore-4b adds these to the XCore-4a forward decl).
    constexpr FName() noexcept : Index(0), SerialNumber(0) {}          // NAME_None
    explicit FName(const char* utf8_name);                              // FromString fast path; never null
    explicit FName(FStringView utf8_view);                              // FromString view-based fast path
    FName(FStringView utf8_view, uint32_t suffix);                      // numbered-name construction

    // Conversion (XCore-4b adds these to the XCore-4a forward decl).
    FString ToString() const;                                           // allocates; "Name_5" form when SerialNumber > 0
    void ToString(FString& out) const noexcept;                         // appends in place; no allocation if room
    FStringView ToStringView() const noexcept;                          // non-allocating view of intern-table bytes

    // Predicates.
    constexpr bool IsNone() const noexcept { return Index == 0; }
    constexpr bool IsNumbered() const noexcept { return SerialNumber != 0; }
    bool IsValid() const noexcept;                                      // index is within current intern-table bounds

    // Equality + hash.
    constexpr bool operator==(FName other) const noexcept {
        return Index == other.Index && SerialNumber == other.SerialNumber;
    }
    constexpr bool operator!=(FName other) const noexcept { return !(*this == other); }
    friend uint64_t GetTypeHash(FName n) noexcept;                      // XXH3 scalar of (Index, SerialNumber)
};

static_assert(sizeof(FName)  == 8, "FName ABI lock");
static_assert(alignof(FName) == 4, "FName alignment lock");

// NAME_None sentinel; constexpr-accessible from any EInitPhase.
inline constexpr FName NAME_None = FName();

} // namespace XCore::Reflect

4.2 Intern-table design (two-pool, sharded)

The intern table is structured as a sharded read-mostly hash table. The shard count is fixed at 256 (8-bit shard index derived from the high bits of the byte-hash). Each shard owns:

  • An open-addressing hash slot table (SwissTable, mirroring XCore-4a §5.3 TMap algorithm) keyed by the UTF-8 byte sequence's FXxh3-64. Slot values hold the entry index into the shard's entry pool.
  • An entry pool — an append-only contiguous buffer of FNameEntry records. The entries are bump-allocated; once written, an entry's bytes are immutable until process exit (or until DLL unload of the engine module).
  • An FRWLock guarding the slot table + entry pool. Reads acquire the lock shared; writes acquire exclusive.

FNameEntry layout (immutable; only written once at intern time). Per Rev 2 FIX-21, the Rev 1 Reserved 2-byte field is DROPPED — FNameEntry header is now 6 bytes (less footprint at scale; no concrete need for the reserve has surfaced):

struct alignas(8) FNameEntry {
    uint32_t Hash;             // 0  +4   FXxh3-64 truncated to 32 bits (full hash kept in slot for collision check)
    uint16_t Length;           // 4  +2   UTF-8 byte length (excludes null terminator)
    char     Bytes[];          // 6  +N   UTF-8 bytes (null-terminated for ToString compatibility)
};

static_assert(offsetof(FNameEntry, Bytes) == 6, "FNameEntry ABI lock: Bytes at offset 6 (Rev 2: Reserved field dropped per FIX-21)");

The Bytes[] trailing array is allocated as part of the same allocation as the header. The entry is null-terminated (so const char* consumers see a C-string) but Length excludes the terminator. Maximum FName length is 1024 bytes (matching UE's NAME_SIZE; NameTypes.h:57) — longer names fail FromString with a diagnostic.

4.3 Shared-read fast path (FromString) (Rev 2 renamed per FIX-22)

Rev 1 called this section "Lock-free fast path"; the rename to "Shared-read fast path" is accurate — the read path acquires the per-shard FRWLock in shared-read mode (wait-free in steady state once the entry exists; not strictly lock-free as the term is used in concurrent-programming literature). The behaviour is unchanged from Rev 1; only the terminology is corrected.

FromString is the hot path. Engine boot generates thousands of FName lookups for class names, property names, function names; every Find* call in XReflectionRuntime is an FName equality test that begins with an FromString-style lookup if the caller passed a string. The fast path is structured to avoid taking any lock on the common case (the name already exists).

FName::FName(FStringView utf8_view) {
    if (utf8_view.IsEmpty()) {
        Index = 0;
        SerialNumber = 0;
        return;
    }

    // 1. Bytewise hash. Determinism contract: XCore-4a §11.9 scalar XXH3 fixed seed = 0.
    const uint64_t Hash = XCore::Hash::XXH3(utf8_view.Data(), utf8_view.Length(), 0);

    // 2. Shard selection (high 8 bits of hash).
    const uint8_t ShardIdx = static_cast(Hash >> 56);
    FNamePoolShard& Shard = g_NamePool.Shards[ShardIdx];

    // 3. Shared-lock read: try to find existing entry.
    {
        FRWScopeLock ReadLock(Shard.Lock, FRWScopeLockType::ReadOnly);
        const uint32_t MaybeIndex = Shard.TryFindEntry(Hash, utf8_view);
        if (MaybeIndex != INVALID_ENTRY_INDEX) {
            Index = (static_cast(ShardIdx) << 24) | MaybeIndex;
            SerialNumber = 0;
            return;
        }
    } // ReadLock released here

    // 4. Exclusive-lock write path: race-checked insert.
    {
        FRWScopeLock WriteLock(Shard.Lock, FRWScopeLockType::ReadWrite);
        const uint32_t MaybeIndex = Shard.TryFindEntry(Hash, utf8_view);  // re-check under write lock
        if (MaybeIndex != INVALID_ENTRY_INDEX) {
            Index = (static_cast(ShardIdx) << 24) | MaybeIndex;
            SerialNumber = 0;
            return;
        }
        const uint32_t NewIndex = Shard.InsertEntry(Hash, utf8_view);
        Index = (static_cast(ShardIdx) << 24) | NewIndex;
        SerialNumber = 0;
    }
}

This design beats UE's FNamePool in three ways (Rev 2 FIX-6: the Rev 1 FRWLock-vs-FCriticalSection claim is RETRACTED — UE 5.4+ uses FRWLock too, verified at UnrealNames.cpp:889 and UnrealNames.cpp:1241):

  • Case-sensitive single-ID design: UE's case-preserving mode requires a ComparisonId + DisplayId pair stored separately (NameTypes.h:632); XPact's case-sensitive MVP eliminates the duality — one ID per name, half the intern-table memory, and closes UE's documented silent-corruption class where two names that "look the same" don't compare equal.
  • No LowercaseProbeHash: UE's FNameEntryHeader is bitfield-packed to embed a lowercase probe hash for case-insensitive acceleration (NameTypes.h:275). XPact's case-sensitive design makes the probe hash unnecessary; explicit fields are cleaner, faster on ARM64 (no bitfield-extraction instructions), and Rev 2's drop of the FNameEntry Reserved field (FIX-21) shrinks the header to 6 bytes.
  • 256-shard high-byte selection + one hash function: UE's shard count is 1024 by default but its hash function varies by UE_FNAME_OUTLINE_NUMBER build flag (UnrealNames.cpp:946-951); XPact uses 256 shards with high-byte selection (matches the smaller XPact name population ≈5-10k vs UE 30k+) and one hash (FXxh3-64 scalar) on every platform/config — one performance profile, one set of test vectors.

4.4 Numbered-name support

Numbered names (e.g., Actor_1, Actor_2) are a Blueprint-VM and editor-instance-naming requirement. XPact mirrors UE's mechanism but with a cleaner integration with the case-sensitive intern table:

  • The base name's bytes (Actor) are stored in the intern table exactly once. Subsequent numbered instances re-use the same Index; only the SerialNumber field of the FName handle differs.
  • SerialNumber == 0 means "no suffix" (the plain FName Actor). SerialNumber == 1 means Actor_1. SerialNumber == 2 means Actor_2. The internal-to-external offset is zero (XPact does NOT inherit UE's "internal numbers are external + 1" hack from NameTypes.h:169; the offset existed in UE to make zero-init produce NAME_None which XPact gets for free because Index == 0 IS NAME_None).
  • FString construction at ToString time: when SerialNumber == 0, ToString returns the byte view directly; when SerialNumber > 0, ToString builds a string of the form {base}_{number} using the FString append API.
  • FromString parses trailing _N automatically (matching UE's behaviour). The pattern matches if and only if the suffix is _ followed by 1-10 digits, no leading zero, no value above MAX_int32 — identical to UE's ParseNumberFromName (NameTypes.h:241). Numbered-name FromString therefore yields a handle with the base's Index and the parsed SerialNumber, NOT a fresh intern-table entry for the full Actor_1 string. This is critical for memory: an instance population of 10000 actors named Actor_1 through Actor_10000 consumes one intern-table entry (the base Actor), not 10000.

4.5 Hash function + equality

The byte-hash is XCore::Hash::XXH3(bytes, len, 0) — the XCore-4a scalar XXH3 with fixed seed zero (XCore-4a §11.9). Bit-exact across Win64 x86_64 / Linux x86_64 / Android ARM64; no SIMD acceleration paths.

The 64-bit byte-hash is the value the intern table's slot search uses for collision checks. The slot table itself stores the (Hash, EntryIndex) pair so a collision check is a 64-bit integer compare before any byte comparison; only when the hash matches does the lookup walk into the entry's Bytes[] for a memcmp confirmation.

FName equality (operator==) compares the 8-byte handle as two 32-bit ints. Bitwise equality is exact because two FNames are equal if and only if their Index and SerialNumber match; the intern table is the single source of truth for what name an Index refers to.

GetTypeHash(FName) is FXxh3-64 of the 8-byte handle. Specifically: hash the two uint32 values as an 8-byte sequence. This is intentionally NOT the same hash as the byte-hash that populated the slot — the byte-hash is for FromString lookup; GetTypeHash is for TMap<FName, V> consumer-side hashing. The two-hash split avoids hash-result leakage between the intern-table key (the bytes) and the FName-as-TMap-key (the 8-byte handle).

4.6 Persistence layout

FName cannot be persisted as the in-memory 8-byte handle because Index is process-local. The on-disk form is the byte sequence + suffix:

  • FArchive (XSerialization) serialises an FName as a string-table reference: index into the archive-local FName string table (a deduped TArray<FString>) + uint32 SerialNumber. The archive header carries the FName string table.
  • On load, each unique string in the archive's FName string table is FromString'd into the running process's intern table, producing a fresh Index. The archive-local table is then a process-local TArray<FName> that maps archive-table-index to running-process Index.
  • FCustomVersion is reflected on FName when XCore-4b's intern-table format changes; bumping the version triggers archive-format migration in XSerialization.

4.7 Hot-reload across DLL patch (CRITICAL DIVERGENCE FROM UE)

Hot-reload requires the intern table to survive a DLL patch. UE's intern table lives in the Core module and depends on Core's static initialisers; when a hot-reload patch swaps a downstream module's DLL, the Core module is untouched, so FNames created in the old DLL continue to resolve correctly. XPact mirrors this: the intern table lives in XCore (the lowest-tier module) and is allocator-backed by the Phase-1g allocator whose lifetime is the whole process. When a downstream DLL is hot-patched:

  • FNames the downstream DLL created before patch are still valid after patch — the Index points to an FNameEntry the intern table still owns.
  • FNames the patched downstream DLL creates after patch may collide with FNames created before patch — the lookup hits the same intern-table entry and returns the same Index. This is the right behaviour: the same string yields the same FName regardless of which DLL revision created it.
  • The intern table is NOT cleared on patch; entries accumulate over the process lifetime. This matches UE's behaviour and is acceptable because the intern table grows logarithmically with unique name count, not with patch count.

The single divergence from UE: XPact's intern table is structured so that the entry pool is never relocated. UE's FNameEntryAllocator grows its pool by appending 1 MB blocks (each block is allocated once and never freed; UnrealNames.cpp around line 1100); XPact uses the same append-block discipline but with 64 KB blocks (each shard's entry pool is a list of fixed-size 64 KB blocks; new entries append to the tail of the latest block; full blocks become read-only). Rationale (FIX-25): the 64 KB block size matches the Quest 3 Snapdragon XR2 Gen 2 L2 cache size (per Cortex-A78 family) for allocator-metadata locality — a single block's per-block metadata (cursor, free count, in-shard-list pointers) fits in one L2 line and the active-block bytes warm up with the same access pattern. UE's 1 MB blocks are tuned for desktop CPUs with much larger L2; on Quest 3 they would thrash L2 on bulk-intern sequences. The append-block discipline means an FName Index encodes (block-id, entry-offset-within-block); the entry pool never relocates; pointer stability across patches is structural.

5. FField + FProperty Design

FField is the polymorphism-free anchor of every reflected field-or-property descriptor. FProperty extends FField with the type-shape information that every reflectable type needs. The FProperty subclass family covers every reflectable type XPact supports in MVP plus the four post-MVP types reserved for ABI compatibility.

5.1 FField base

FField is the smallest possible reflection-runtime anchor. UE's FField (Field.h:602) carries an FFieldClass pointer, an Owner (FFieldVariant), a Next pointer, an FName, and an EObjectFlags-derived flags slot. XPact's FField strips out the EObjectFlags (deprecated in UE 5.8 anyway; see Field.h:655-659) and keeps the four load-bearing fields.

namespace XCore::Reflect {

// 32-byte FField base. Zero virtual methods (hot-reload safety).
struct alignas(8) FField {
    const FFieldClass*  ClassPrivate;    //  0  +8   FFieldClass descriptor pointer
    FFieldVariant       Owner;           //  8  +8   16-bit kind tag + 48-bit raw pointer to FStruct or FField parent
    FField*             Next;            // 16  +8   intra-struct linked-list next
    FName               NamePrivate;     // 24  +8   field name (8-byte handle layout from §4)

    // Function-pointer slots replacing UE's virtual methods (hot-reload safety).
    // Subclasses populate via the FFieldClass.Construct registration; null means "not applicable for this subclass."

    constexpr FField() noexcept = default;
    explicit FField(const FFieldClass* cls, FFieldVariant owner, FName name)
        : ClassPrivate(cls), Owner(owner), Next(nullptr), NamePrivate(name) {}
};

static_assert(sizeof(FField)  == 32, "FField ABI lock: 32 bytes (one cache line / 2)");
static_assert(alignof(FField) ==  8, "FField alignment lock");

} // namespace XCore::Reflect

The 32-byte layout is half a 64-byte cache line on every target platform (Win64 Ryzen, Linux server, Quest 3 Snapdragon XR2 Gen 2). Two FFields fit per line; the FField + the first 32 bytes of an FProperty subclass payload fit in one line.

FFieldVariant (Rev 2 reshaped per FIX-4 to UE's LSB-tag pattern; Field.h:399-595). UE's actual FFieldVariant uses a 1-bit LSB tag on an 8-byte-aligned pointer (verified at Field.h:408 UObjectMask = 0x1, Field.h:454 (uintptr_t)Container.Object | UObjectMask, Field.h:489 (uintptr_t)Container.Object & UObjectMask, Field.h:559 (uintptr_t)Container.Object & ~UObjectMask). Rev 1 used a 16-bit high-tag in the top of a 48-bit pointer; Rev 2 switches to UE's 1-bit LSB tag for two reasons: (a) it's forward-compatible with any future ARM64 VA extension (8-byte alignment is architecture-independent, whereas the 48-bit VA assumption is not), and (b) it's faster (one AND instruction vs shift + AND). XPact's FFieldVariant:

struct alignas(8) FFieldVariant {
    // LSB = 0 -> FField pointer (FField is 8-byte aligned per §5.1 layout)
    // LSB = 1 -> FStruct pointer (FStruct is 8-byte aligned per §7.1 layout)
    uint64_t Storage;

    static constexpr uint64_t kFStructTag = 0x1;
    static constexpr uint64_t kPointerMask = ~uint64_t(0x1);

    bool             IsFStruct() const noexcept { return (Storage & kFStructTag) != 0; }
    bool             IsFField()  const noexcept { return (Storage & kFStructTag) == 0; }

    const FStruct*   AsStruct() const noexcept;  // null if !IsFStruct()
    const FField*    AsField()  const noexcept;  // null if !IsFField()
};

static_assert(sizeof(FFieldVariant) == 8, "FFieldVariant ABI lock");

The LSB-tag pattern requires every FField and FStruct allocation to be at least 8-byte aligned, which is structural per the alignas(8) declarations in §5.1 (FField) and §7.1 (FStruct). Compile-time-constant FField/FStruct descriptors emitted by XHT into .rodata also satisfy this alignment because XHT emits them with explicit alignas(8). The Stage B addendum's XPACT_FPROPERTY_LAYOUT_TAG covers the FFieldVariant scheme; the value moves from "FFieldVariant-v1: 16-bit-high-tag + 48-bit-pointer" (Rev 1) to "FFieldVariant-v2: 1-bit-LSB-tag (0=FField, 1=FStruct) on 8-byte-aligned pointer" (Rev 2).

LSB-tag semantic note (Rev 3 FIX-R2-LOW-6): XPact's LSB-tag semantic is inverted relative to UE. UE encodes LSB=1 → UObject pointer (verified at Field.h:454 (uintptr_t)Container.Object | UObjectMask); XPact encodes LSB=1 → FStruct pointer. Both schemes are equivalent — the choice of which kind gets the tag bit is arbitrary. Documented here for cross-reference: anyone porting code or test vectors between UE and XPact must flip the LSB-test polarity. The XPact choice (FStruct gets the tag) follows from the fact that FField is the more frequent kind in reflection-walk hot paths, so a zero-tag bit on FField shaves one bitwise-NOT-then-AND for the common case.

5.2 FFieldClass

FFieldClass is the runtime descriptor for an FField subclass. UE's FFieldClass (Field.h:66) carries Name, ClassFlags, Id, CastFlags, SuperClass, DefaultObject, ConstructFn, and a UniqueNameIndexCounter. XPact's FFieldClass strips the DefaultObject (XPact does NOT instantiate FField objects at runtime for blueprint-VM cases; the runtime path uses the descriptor directly) and structures the rest:

5.3 FProperty base (Rev 2 reshaped per FIX-1 + FIX-2 + FIX-19; Rev 4 confirms FProperty base unaffected by TArray cascade)

Rev 4 amendment (Round 4 of XCore-4b audit cycle): Rev 3 FIX-R2-CRIT-1 cited sizeof(TArray<T>) == 16 bytes based on a reading of XCore-4a's spec wording ("0 bytes when AllocatorT is empty"). Phase 4b.5 implementation verified by direct sizeof on MSVC 19.44 that XCore-4a's actual DefaultAllocator carries a 2-byte FMemTag for per-container memory attribution (per XCore-4a's DefaultAllocator.h:178-186 static_assert: sizeof(DefaultAllocator) == 2). XPACT_NO_UNIQUE_ADDRESS has no padding hole to fold into. Actual TArray sizeof is 24 bytes (T* m_data @ 0 (8) + int32 m_num @ 8 (4) + int32 m_capacity @ 12 (4) + DefaultAllocator m_alloc @ 16 (2) + pad @ 18 (6) = 24). All descriptor sizes cascade: FStruct 104→112, FScriptStruct 120→128, FClass 200→224, FEnum 64→72, FInterface 56→64. FProperty itself is unchanged at 104 bytes — FProperty contains no TArray members; the cascade only affects descriptors that contain TArray fields.

Per Prime Directive (engineering_principles.md: "Use the thing that is correct not the thing that is easier to implement"), two responses were considered:

  • Option A: Refactor XCore-4a to make DefaultAllocator truly stateless. Move FMemTag attribution to per-allocation callsite. Pros: 16-byte TArray as Rev 3 intended; ~8 bytes saved per TArray instance. Cons: substantial XCore-4a churn (~10k LoC touched; all containers + tests re-verified); API friction (FMemTag becomes an explicit parameter at every allocation callsite); loses the leak-tracker integration shape.
  • Option B (Rev 4 adopts): Acknowledge XCore-4a's design choice and ship accurate sizes. Pros: matches actual implementation; preserves XCore-4a's leak-tracker + memory-budget attribution feature; no XCore-4a churn. Cons: ~8 bytes per TArray vs theoretical optimum.

Rev 4 adopts Option B. The FMemTag-per-allocator design is a load-bearing XCore-4a feature consumed by Phase 1b leak detection + Master Plan §2b memory budget telemetry. The 8-byte cost is acceptable for the attribution capability. The Prime Directive instructs "do it right the first time, not the easy way" — in this case, the right thing is to honour XCore-4a's deliberate design decision (per-container memory attribution) rather than to retrofit XCore-4a for a minor reflection-runtime footprint win.

Rev 2's FakeVTable adoption replaced the 40-byte inlined dispatch with an 8-byte pointer (saves 32 bytes); the dense ObjectRefProperties TArray (FIX-13) lives on FStruct, not FProperty. Total FProperty Rev 1 → Rev 2 footprint change is solely from the dispatch-table relocation: 40 → 8 = -32 bytes.

NetIndex elimination rationale (FIX-19): UE's UClass::ClassReps is TArray<FRepRecord> where FRepRecord = {FProperty* Property; int32 Index}; UE uses the ClassReps array index AS the NetIndex (and the FRepRecord.Index supports XPROPERTY(Replicated) with ArrayDim > 1 by emitting one entry per element). XCore-4b Rev 2 mirrors this exactly (FIX-7) and drops the per-FProperty NetIndex field. The ClassReps index is the NetIndex.

RepNotify function-pointer resolution (Rev 2 reshape): Rev 1 carried a RepNotifyFuncName (FName) + RepNotifyFunc (pre-resolved function pointer) on FProperty itself. Rev 2 drops the function-pointer field; the FName is enough on FProperty (matches UE's UnrealType.h:245 FName RepNotifyFunc). XNetworking resolves the FName to a callable via the owning FClass's NetFields lookup at FClass::Link time and caches the resolved pointer in its FReplicationStateDescriptor. This keeps FProperty's footprint tight and concentrates the replication-engine knowledge in XNetworking (where it belongs).

5.4 FProperty FakeVTable dispatch (Rev 2 reshaped per FIX-2)

UE's FProperty has 25+ virtual methods (UnrealType.h:178); every subclass overrides several. The hot-reload risk is significant: any patch DLL whose FProperty subclass overrides a virtual method must be recompiled against the exact same vtable layout the runtime expects, OR the patch DLL's vtable bytes must be slotted into the runtime's known vtable layout. UE's pattern requires the latter (and frequently breaks); XPact's pattern eliminates the vtable.

Rev 1 carried a 5-slot inlined function-pointer table on every FProperty instance (40 bytes per instance). Rev 2 adopts the TStructOpsFakeVTable mechanism (UE's Class.h:1737-1768 for UScriptStruct::ICppStructOps) but applies it more broadly than UE does — to both FProperty subclass dispatch and FScriptStruct ICppStructOps dispatch. The broader-application part is XPact-novel per Prime Directive (avoids the hot-reload vtable-mismatch class that UE's FProperty virtuals introduce; UE only applies the FakeVTable pattern to UScriptStruct ICppStructOps, not FProperty). Each FProperty subclass has a single shared FFakeVTable in .rodata; every FProperty instance carries an 8-byte DispatchTable pointer to its subclass's table. Per-instance footprint drops from 40 bytes to 8 bytes; the shared per-subclass cost is 128 bytes (Rev 3 corrected per FIX-R2-MAJ-1 + FIX-R2-HIGH-1: 8-byte header + 15 × 8-byte slots); total module-wide cost is 28 subclasses × 128 = 3584 bytes ≈ 3.5 KB. This is the correct shape, not the easier shape (Prime Directive). FIX-R2-MED-2 corrected the Rev 2 narrative claim that UE applies the pattern "broadly across FProperty subclasses" — UE does not; XPact does.

The dispatch surface is 15 slots (Rev 3: Rev 1's 7 baseline + Rev 2's 7 additions = 14, plus Rev 3's ConvertFromType for XSerialization schema-migration per FIX-R2-HIGH-1 = 15 total). Slot table:

5.4.1 Fixed-table dispatch rationale (Rev 3 added per FIX-R2-HIGH-1)

XPact's FFakeVTable uses a fixed 15-slot table (one function-pointer slot per dispatch operation, populated or nullptr depending on whether the subclass supports the operation). UE's analogous FStructOpsFakeVTable (Engine/Source/Runtime/CoreUObject/Public/UObject/Class.h:1655-1721) uses a variable-length form: each ICppStructOps instance emits only the slots for capabilities it advertises, with a popcount-decode at every dispatch site (or a caller-cached slot index) to map slot semantics to physical slot positions. Rev 3 deliberately diverges from UE here. Prime Directive citation (per engineering_principles.md: "Use the thing that is correct not the thing that is easier to implement"):

  • Per-call dispatch speed dominates at our scale. Every replication frame, every GC scan, every serialization round-trip dispatches through these slots tens to hundreds of thousands of times. A popcount-decode at every dispatch site adds one to three cycles per call; cached-slot-index requires the caller to memoize the lookup, complicating call sites. The fixed table is a single indexed load (vtable->Slots[ESlot::Identical]) at every call site — one instruction.
  • The footprint cost is bounded and small. Variable-length form would save approximately 3 KB module-wide (across 28 subclasses each carrying only the slots they implement). The fixed form costs 28 × 128 = 3584 bytes total. The ~3 KB savings does not justify the dispatch-site complexity at any reasonable scale (the engine's .rodata sections measure in megabytes; 3 KB is noise).
  • Compile-time slot enumeration is more readable. The fixed table allows ESlot::Identical-style compile-time slot enumeration, so call sites read as vtable->Slots[ESlot::Identical] rather than SlotPointerForCapability(vtable, CAP_HasIdentical). Code review, debugging, and onboarding all benefit from the readable form.
  • Sparse nulls are explicit and queryable. Unused slots are nullptr; the Capabilities bitmask tells the caller which slots are populated before dispatch. Null-check + bitmask-check are both O(1) and side-effect-free.
  • Deliberate divergence acknowledged. Per Prime Directive's "Don't blindly mirror UE patterns" clause: the variable-length form is one of UE's well-known footguns — popcount-encoding bugs in StructOpsTypeTraits.h have surfaced multiple times in UE's bug tracker. The fixed-table form is structurally immune to that class of bug.

If a future XCore-4b revision (post-MVP) profiles a path where the per-subclass .rodata footprint becomes load-bearing (e.g., game content emitting 100+ FProperty subclasses with sparse capability sets), the variable-length form can be reconsidered. The fixed form is the correct MVP choice.

5.8 C#-specific reflection mappings (Rev 2 added per FIX-18)

XPact's C# surface differs from UE's because UE has no C#. The XPact-only C# reflection surface mappings:

  • Nullable reference types (string?, SomeXObject?): EPropertyFlags adds CPF_NullableReferenceType (1 bit). The reflection runtime carries the bit; XIL2CPP preserves it through the C++ emit boundary so C# consumers can tell which reference properties are declared-nullable vs not.
  • Nullable value types (int?, FVector?): map to a tagged-union pattern. Deferred to FOptionalProperty (post-MVP per FIX-3). In MVP, XIL2CPP transpiles int? to XOptional<int32_t> (a XCore-4a value type) without a reflection-level nullable annotation — users opting into reflectable nullable value types in MVP work with XOptional directly.
  • Generic instantiations (List<int> vs List<XObject>): each generic instantiation is a distinct FClass with a name suffix (e.g., TArray_int, TArray_XObject). FArrayProperty.Inner points at the element FProperty for the specific instantiation. XIL2CPP emits one FClass per instantiation reached by the program; the cost is per-program, not per-engine-build.
  • C# records (record Foo(int X, int Y)): primary-constructor parameters become FProperty entries with auto-property semantics; XIL2CPP emits the init-only setter and value-equality default. Records are FScriptStruct-shaped at the C++ side; FScriptStruct's HasIdentical capability bit (FIX-5) is auto-populated for records because their value-equality is determinate from declared shape.
  • C# required members (public required int X { get; init; }): EPropertyFlags adds CPF_RequiredInit (1 bit). C# compile error if the field is not set in object initialization; XIL2CPP emits a runtime check in the generated constructor for the C++ side.
  • nameof(X) pointer-identity: covered in §4.8 per FIX-18; one UTF-8 byte constant per literal per build, link-time deduplicated.

The new EPropertyFlags bits (CPF_NullableReferenceType, CPF_RequiredInit) consume bits 60-61 in the 64-bit flag word; remaining bits 62-63 are reserved.

6.2 RepNotify FName (Rev 2 reshape per FIX-1)

FProperty carries a single RepNotifyFunc FName at offset 64 (per §5.3 byte layout). This keeps FProperty tight and concentrates replication-engine knowledge in XNetworking.

using FRepNotifyFunc = void (*)(void* Instance, void* OldValue);

// XNetworking dispatches via the descriptor at replication time (not via FProperty directly):
void XNetworking::DispatchRepNotify(XObject* Instance, const FReplicationStateDescriptor* Desc,
                                     int32_t RepIndex, const void* OldValueSlot) {
    const FRepNotifyFunc Fn = Desc->GetCachedRepNotify(RepIndex);  // resolved at session-init
    if (Fn != nullptr) {
        Fn(Instance, const_cast<void*>(OldValueSlot));
    }
}

UE's pattern stores only the FName and looks up the function via UFunction at every replication event (slow); XNetworking's cache-in-descriptor pattern resolves once at session-init (fast). The cache lives in XNetworking, not on FProperty.

6.3 Push-model (Rev 2 reshape per FIX-1)

Push-model replication is declared via a single bit in EPropertyFlags: CPF_PushModel (bit 56). When set, XNetworking's replication path elides the property's per-tick equality check and waits for explicit MarkPropertyDirty() calls from gameplay code. The flag is enough; Rev 1's per-FProperty PushModelBits bitfield with sub-modes (PMB_RequiresMarkBeforeFirstReplicate, PMB_ForceUntilNextTick) is dropped — UE doesn't carry these per-FProperty either, and the sub-modes can be re-introduced as additional EPropertyFlags bits if a concrete need surfaces. The Rev 1 over-reservation is corrected.

MVP rationale (preserved from Rev 1): lockstep input replication is the primary path, but the fallback property-rep path benefits significantly from push-model because UE's per-tick property iteration cost is a well-documented performance pitfall for properties on actors with large component counts. Push-model is the established remediation; XCore-4b declares the flag bit; XNetworking implements the elision.

6.4 Delta compression (Rev 2 reshape per FIX-1)

Delta-compressed properties are declared via CPF_DeltaCompressed (bit 57) in EPropertyFlags. XNetworking's delta-compression engine consults the flag at descriptor-build time to select per-property compression strategy. Rev 1's per-FProperty DeltaHintFlags bitfield with sub-modes (small-value full-send, infrequent-change heavy-delta, array-element-by-delta) is dropped; the flag is enough for MVP. Sub-mode bits can be re-introduced as additional EPropertyFlags if a concrete profiling need surfaces.

6.5 RepIndex + FRepRecord (Rev 2 updated per FIX-7 + FIX-19)

RepIndex (uint16 at FProperty offset 56) is the per-class replication index. Properties in a class are linked into the FClass's ClassReps array (now TArray<FRepRecord> per FIX-7); each property's RepIndex is its position in that array. The RepIndex IS the NetIndex (FIX-19 eliminated the separate NetIndex field on FProperty). The RepIndex is used by the wire-encoding to compact-encode "which property is being sent." Max 65535 properties per class hierarchy — an enormous safety margin (UE's largest classes have ~200 properties).

FRepRecord shape (FIX-7): UE's UClass::ClassReps (Class.h:3984; Rev 3 FIX-R2-MED-3 corrected from Rev 2's :3915 which is FirstOwnedClassRep's line) is TArray<FRepRecord> where FRepRecord is {FProperty* Property; int32 Index}. The Index field supports XPROPERTY(Replicated) float Stamina[4] by emitting four ClassReps entries (Index=0, 1, 2, 3) all pointing at the same FProperty. XPact mirrors UE exactly (see §7.3 FClass.ClassReps).

struct FRepRecord {

6.6 XNetworking as descriptor host (Rev 2 reshape)

Per Master Plan Rev 15 Iris correction: XCore-4b is the source; XNetworking is the host.

  • XNetworking's FReplicationStateDescriptorRegistry is a process-singleton keyed by FFieldVariant; descriptors are TRefCountPtr<const FReplicationStateDescriptor>; stale descriptors pruned on PostGarbageCollect.
  • The builder lives at XReplicationStateDescriptorBuilder::CreateDescriptorsForClass(...); it reads FProperty's RepIndex + ELifetimeCondition + RepNotifyFunc via reflection, plus EPropertyFlags' CPF_PushModel / CPF_DeltaCompressed bits, to build multiple descriptors per class (one per replication-state grouping: init-only states, lifetime-conditional states, fast-path-update states — matching UE 5.4+ Iris).
  • Net-object-groups live in a separate FNetObjectGroups registry inside XNetworking; FNetObjectGroupHandle (8 bytes: 24-bit GroupIndex + 8-bit Epoch + 32-bit UniqueId; mirrors NetObjectGroupHandle.h:21-110) is owned there, NOT inside FReplicationStateDescriptor.

The MVP-fallback rationale (preserved from Rev 1): the fallback property-rep path must be feature-complete per the Year-3 lockstep validation milestone. Push-model + delta-compression are the established UE remediations for per-tick polling cost on actors with large component counts. XCore-4b declares the flags; XNetworking implements the behaviour.

RefLink rework rationale (FIX-13): Rev 1 used UE's intrusive-linked-list RefLink (a chain of FProperty pointers via per-FProperty NextRef field) for GC reference traversal. Linked-list pointer-chasing on the Quest 3 ARM64 cache is slow — Master Plan §11 Step 5.5 criterion (b) demands <50ms full-heap-scan over 100k XObjects with 5-10 ObjectRef properties each. TArray header dependency (FIX-15; Rev 4 corrected per FIX-R3-CRIT-1): FStruct's byte layout depends on XCore-4a's TArray sizeof = 24 bytes per Phase 4b.5 implementation verification. XCore-4a's DefaultAllocator is NOT stateless: it carries a 2-byte FMemTag m_tag field (verified at XCore-4a DefaultAllocator.h:178-186 with static_assert(sizeof(DefaultAllocator) == 2)) for per-container memory attribution. The FMemTag attribution lets the leak tracker + memory-budget telemetry trace allocations to specific containers ("XActor's component list", "FString buffer", etc.) — a deliberate XCore-4a design feature consumed by Phase 1b leak detection + Master Plan §2b memory budget telemetry. Because DefaultAllocator is non-empty, XPACT_NO_UNIQUE_ADDRESS has no padding hole to fold into; the TArray layout is: T* m_data @ 0 (8) + int32 m_num @ 8 (4) + int32 m_capacity @ 12 (4) + DefaultAllocator m_alloc @ 16 (2) + pad @ 18 (6) = 24 bytes total. Rev 3 erroneously cited 16 bytes based on a misreading of XCore-4a's spec wording (which described the theoretical EBO that would apply if the allocator were truly empty); Phase 4b.5 commit d4062e8 verified by direct sizeof on MSVC 19.44 that the actual TArray is 24 bytes. Any future XCore-4a refactor that makes DefaultAllocator truly empty (Option A discussed in §5.3) would shrink TArray to 16 bytes and force an XCore-4b ABI bump + a new Stage B addendum revision. The Stage B addendum's XPACT_FCLASS_LAYOUT_TAG covers this implicitly (FStruct is FClass's base); a future TArray sizeof change requires re-deriving all FStruct/FClass byte offsets. Cascade impact (Rev 4 audit): every TArray field in FStruct, FClass, FScriptStruct, FEnum, FInterface re-computed in Rev 4; every static_assert(sizeof(...) == N) updated; every byte-offset citation in §11 Stage B addendum recomputed.

Cross-reference fix (FIX-27): Rev 1 §3 step 6 mentioned a ScriptAndPropertyObjectReferences field that wasn't shown in the code block. Rev 2 resolves: that field name was Rev 1 placeholder for what is now the dense ObjectRefProperties TArray. The naming is harmonized to ObjectRefProperties everywhere.

7.2 FScriptStruct (Rev 3 reshape per FIX-R2-MAJ-2 + FIX-R2-MED-1: adopt FakeVTable pattern + expand Capabilities to 32 bits)

FScriptStruct extends FStruct with a CppStructOps handler table and is the runtime descriptor for non-XObject reflected structs (FVector, FRotator, FTransform, FLinearColor, custom user-defined structs). Rev 1 had 7 capability bits inlined; Rev 2 expanded inlined to ~27 function pointers (which would have made sizeof structurally 224 bytes — the Rev 2 declared 112 + 144 static_assert was impossible). Rev 3 corrects this two ways:

  • Adopt the FakeVTable pattern for FScriptStruct ICppStructOps (FIX-R2-MAJ-2): replace the inlined function pointers with a single FakeVTable pointer pointing at a per-struct-type FCppStructOpsFakeVTable in .rodata. Mirrors the FProperty FakeVTable pattern (FIX-2) for consistency. ICppStructOps on FScriptStruct collapses to Capabilities (4) + _pad (4) + FakeVTablePtr (8) = 16 bytes per FScriptStruct instance.
  • Expand Capabilities to the full UE-equivalent 27+ bit surface (FIX-R2-MED-1): UE's UScriptStruct::ICppStructOps has 27 capability bits (verified at Engine/Source/Runtime/CoreUObject/Public/UObject/Class.h:1163-1201). Rev 3 expands the Rev 2 16-bit set (12 active + 4 reserved) to 32 bits (24 active + 8 reserved). Reserved bits cost zero runtime; they're unused bit positions in the uint32 Capabilities mask. Added (declared bit, deferred handler): HasCopy, HasMoveAssign, IsPlainOldData, IsUECoreType, IsUECoreVariant, HasGetPreloadDependencies (asset cooking), HasFindInnerPropertyInstance (editor PropertyPath), HasVisitor (FPropertyVisitor), ClearOnFinishDestroy, HasIntrusiveUnsetOptionalState (FOptionalProperty post-MVP), HasStructuredSerializer, HasStructuredSerializeFromMismatchedTag.

The CppStructOps FakeVTable mirrors UE's UScriptStruct::ICppStructOps virtual interface (Class.h:1774) but lifted to a function-pointer table in .rodata so hot-reload doesn't bump a vtable (consistent with the FProperty FakeVTable pattern from FIX-2).

// FCppStructOpsFakeVTable: one per FScriptStruct subtype, in .rodata.
// Mirrors the FProperty FakeVTable pattern (FIX-2 + Rev 3 FIX-R2-MAJ-2).
// Header (8 bytes): Capabilities + reserved. Followed by 16 handler slots (8 bytes each)
// = 128 bytes. Header + slots = 136 bytes per subtype, rounded to 8-byte alignment.
// The 16 slot positions correspond to the bits in Capabilities that have callable handlers
// (handlers for capability-only bits like IsPlainOldData are nullptr or sentinel).
enum class ECppOpSlot : uint32_t {
    PostScriptConstruct = 0,
    AddStructReferencedObjects,

    NetDeltaSerialize,
    PostSerialize,
    ExportTextItem,
    ImportTextItem,

    StructuredSerializeFromMismatchedTag,   // post-MVP slot (reserved)

static_assert(sizeof(FCppStructOpsFakeVTable) == 136,
    "FCppStructOpsFakeVTable ABI lock: 8-byte header + 16 handler slots = 136 bytes per FScriptStruct subtype");

// Capability bitmask layout (32 bits; 24 active + 8 reserved per Rev 3 FIX-R2-MED-1).
// MVP-active bits: HasNoOpConstructor, HasZeroConstructor, HasDestructor,
// HasPostScriptConstruct, HasSerializer, HasIdentical, HasNetSerializer,
// HasNetDeltaSerializer, HasAddStructReferencedObjects, HasGetTypeHash,

// HasStructuredSerializer, HasStructuredSerializeFromMismatchedTag, plus 5 unallocated

struct alignas(8) FScriptStruct : FStruct {

    // to a single FakeVTable pointer pointing at a per-subtype handler table in .rodata.
    // Per-instance footprint: 16 bytes (4 capabilities + 4 pad + 8 FakeVTable pointer).

    "FScriptStruct ABI lock (Rev 4: FStruct 112 base + 16 ICppStructOps FakeVTable pattern = 128 bytes; "

The capability bitmask (Capabilities) lets callers test whether a handler is populated without null-deref; a bit set implies the corresponding handler is callable via CppOpsTable->Slots[ECppOpSlot::X]. XHT emits the capability bitmask at compile time by inspecting the struct's C++ traits (std::is_trivially_destructible_v, presence of NetSerialize member function, etc.) and emits the corresponding constinit FCppStructOpsFakeVTable in .rodata alongside the FScriptStruct descriptor.

Capability-bitmask co-allocation note (Rev 3 FIX-R2-MED-4): FScriptStruct's ICppStructOps Capabilities (handler-availability for struct-level operations, 24 active + 8 reserved = 32 bits) is a DIFFERENT bitmask from FProperty's FFakeVTable Capabilities (slot-availability for FProperty dispatch, 15 bits). They are co-located in name only; the bits index different operation sets. Cross-reference: see §5.4 for FProperty's Capabilities semantics.

FakeVTable pattern divergence acknowledgement (Rev 3 FIX-R2-MED-2): UE applies the TStructOpsFakeVTable mechanism only to UScriptStruct::ICppStructOps (Class.h:1737-1768), not to FProperty. XPact applies it to BOTH (FProperty dispatch in §5.4 AND FScriptStruct ICppStructOps here). The broader-application is XPact-novel per Prime Directive — avoids the hot-reload vtable-mismatch class that UE's FProperty virtuals introduce. Documented as a deliberate divergence.

7.5.1 Interface dispatch (Rev 2 added per FIX-8)

Per the spec's design rule that descriptors don't carry virtuals, FInterface itself has no dispatch surface beyond the per-function signature-hash table. Three concrete dispatch shapes apply depending on who is calling:

  • C++ user-class implementing the interface: standard virtual dispatch through the user-class's own vtable. The FInterface descriptor records that the class implements the interface (via the FClass's InterfaceImplementations table); the descriptor does NOT participate in C++-side dispatch. Example: class XValve : public IInteractable { virtual void OnInteract() override; }; dispatches via XValve's normal C++ vtable.
  • C# transpiled-class implementing the interface: XIL2CPP emits a C++ class with virtual methods matching the C# interface declaration; dispatch is via the emitted C++ vtable, structurally identical to the C++-user-class shape above. The transpiler ensures the vtable layout matches the C++-declared interface.
  • Blueprint VM / scripting / reflection-driven dispatch: the caller has a function FName and an XObject instance; it must find the implementing function. The lookup walks the FClass's InterfaceImplementations table for the requested FInterface descriptor, finds the FFunctionDescriptor by SignatureHash + FName, and dispatches via the FFunctionDescriptor's resolved function pointer. This is the only path that consults the FInterface descriptor at dispatch time.

The InterfaceImplementations table lives on the FClass (one entry per implemented interface), keyed by FInterface descriptor pointer, valued as TArray<FFunctionDescriptor*> — one entry per function the implementing class provides. XHT emits this at .gen.cpp time by inspecting the C# class's interface declarations (or the C++ class's public IFoo inheritance) and emitting the descriptor table.

8.4 Per-type SchemaHash discipline (Rev 2 reshape per FIX-10)

The per-type SchemaHash on FStruct (Section 7.1) is computed by XHT at emit time from a stable canonical form of the declared shape (FIX-10). Rev 1 included Prop.Offset and Prop.ElementSize in the hash — both are compiler-dependent (alignment, packing, struct-layout rules, float-vs-double widths on 32-bit-pointer targets, etc.). Rev 2 hashes only declared shape so the SchemaHash identifies the type's identity rather than its compiled layout.

// Pseudo-algorithm XHT runs at .gen.cpp emit time (Rev 2; declared-shape only per FIX-10).
uint64_t ComputeSchemaHash(const FStructInfo& Struct) {
    FBlake3Builder Builder;
    Builder.AppendBytes(Struct.SuperStructSchemaHash);   // chain through parent (FIX-11)
    for (const FPropertyInfo& Prop : Struct.PropertiesInDeclaredOrder) {
        Builder.AppendUtf8(Prop.Name);                   // property name (FName bytes)
        Builder.AppendUtf8(Prop.CanonicalTypeName);      // declared C++/C# type name, canonical UTF-8 form
        Builder.AppendBytes(Prop.DeclaredFlags);         // bitfield of declared XPROPERTY specifiers
        Builder.AppendBytes(Prop.ReplicationCondition);  // declared XPROPERTY(Replicated, Condition=...)
        Builder.AppendUtf8(Prop.RepNotifyFuncName);      // declared OnRep_ function name (FName bytes)
        Builder.AppendBytes(Prop.ArrayDim);              // declared XPROPERTY([N]) array dimension
        // For container properties, recurse into the inner type's SchemaHash:
        if (Prop.IsContainerProperty) {
            Builder.AppendBytes(Prop.InnerSchemaHash);   // already-computed inner-type hash
        }
        // EXCLUDED (per FIX-10): byte Offset, byte ElementSize, byte Alignment.
        // These are post-compile artifacts that vary by compiler/packing flags;
        // they are not part of the type's *identity* (declared shape).
    }
    return Builder.Finalize().LowerUInt64();  // BLAKE3 lower 64 bits
}

8.4.1 SchemaHash semantics (Rev 2 added per FIX-10)

The SchemaHash identifies the declared shape of the type, not its compiled layout. Different compilers / packing flags / 32-vs-64-bit pointer targets produce different memory layouts but the same SchemaHash — which is correct, because the FCustomVersion contract is about shape identity (does this serialized payload describe the same logical type?), not memory identity (does the in-memory layout match byte-for-byte?). XSerialization handles memory-layout reads via per-field offset metadata at runtime; the SchemaHash answers the orthogonal question of whether the field set itself has changed.

8.4.2 SchemaHash truncation-collision policy (Rev 2 added per FIX-12)

BLAKE3 truncated to uint64 has 2-64 collision probability per pair; over ~107 type pairs in a large engine the residual risk is ~5×10-12. XHT detects truncation collisions at link time (each module's emitted .gen.cpp publishes a manifest of (SchemaHash, FullTypeName) pairs; the link-time merger verifies uniqueness). On collision detection:

XHT diagnostic:
XCore4b003 — schema-hash truncation collision: types {X} and {Y} produce identical
              64-bit hash 0x{hash}. Resolve by renaming one type (changes the canonical
              type-name input to the hash); the renaming is also a useful documentation
              signal that two types occupied the same conceptual space and one was poorly
              named.

8.4.3 SchemaHash through SuperStruct + XBT transitive-dirty (Rev 2 added per FIX-11)

Rev 1 already chained SuperStructSchemaHash into child SchemaHashes (preserved in Rev 2). However, this means hot-patching a parent class's XPROPERTY layout without rebuilding child classes leaves a stale parent-hash compiled into the child's .gen.cpp. Rev 2 addresses this with a new acceptance criterion C5 (see §13) tied to XBT's transitive-dirty graph:

  • Acceptance criterion C5 (FIX-11): modifying a parent class's XPROPERTY layout (declared shape) without rebuilding child classes flags XCore4b002 build error from XBT's transitive-dirty graph. XBT's per-file dependency model (Step 0.5 addendum) records the child-on-parent SchemaHash dependency; touching the parent's XPROPERTY declaration dirties every child's .gen.cpp transitively, forcing a rebuild that picks up the new parent-hash.

8.4.4 BLAKE3 implementation-swap path (Rev 2 added per FIX-23)

SchemaHash values are not stable across BLAKE3 implementation swaps (Master Plan §2a B-3 future-eval marker triggers a benchmark of XPact's hand-rolled BLAKE3 vs reference Rust BLAKE3 at MVP+1; if >2× slower on the per-cooked-asset fingerprint path, swap to vendored upstream). The swap path is one-XCore-4a-revision; all SchemaHashes recompute on the next clean build. XCookOnTheFly + XDerivedDataCache cache keys that incorporate SchemaHash will invalidate atomically on the swap; the invalidation is acceptable because the swap is a Master-Plan-scheduled event with a deliberate clean-build expectation.

8.4.5 Version-bump triggers (preserved from Rev 1)

Version-bump triggers (per Master Plan Rev 5): a version bump on type T is required when (a) an XPROPERTY of T is added, removed, renamed, or changes type; (b) the reflection-level layout (FProperty list ordering, replication-condition set, RepNotify binding) changes; (c) the binary serialization format for T changes. XHT enforces this at build time by storing the schema-hash in the type's generated header and emitting compile error XCore4b001 — schema-hash drift on type {T}: hash changed from 0x{old} to 0x{new} but SchemaVersion not bumped when the layout changes without a matching SchemaVersion increment.

The discipline is the heart of XPact's divergence from UE on this front: UE's FCustomVersion is purely runtime/serialization-side; UE has no compile-time gate that the FProperty layout matches the version. XPact's compile-time gate closes the silent serialization-deserialization mismatch class of bugs (UE's bug pattern: change XPROPERTY layout; forget to bump version; ship; in-the-field data corrupts silently on next load).

9. Hot-Reload Compatibility

Hot-reload is a Master-Plan-locked decision. XCore-4b's reflection runtime must survive a downstream module's hot-reload DLL patch without breaking the registry, the FName intern table, or any FProperty / FClass / FStruct pointer the patched DLL held before the patch.

9.1 No virtual methods on XCore-4b descriptors

Every XCore-4b descriptor type (FField, FFieldClass, FProperty, every FProperty subclass, FStruct, FScriptStruct, FClass, FEnum, FInterface) is virtual-method-free. Per Rev 2 (FIX-2), FProperty subclass dispatch lives in a shared per-subclass FFakeVTable in .rodata referenced via an 8-byte DispatchTable pointer; FScriptStruct's CppStructOps is a function-pointer table populated at construction (FIX-5). Consequence: there are no vtables that hot-reload could mismatch.

Contract Rev 13.7 §7.1 ConstInit posture is the mechanism: XHT emits the descriptor data as constexpr initialisation; runtime fixups only resolve cross-DLL super-class pointers. The FFakeVTable resides in .rodata of the owning DLL and is referenced by the FProperty instance's DispatchTable pointer; a hot-reload patch can rewrite the implementation but the new FakeVTable lives in the patched DLL's .rodata and the FProperty instance's DispatchTable pointer is updated via the patch DLL's relocation table. The runtime never holds a stale vtable.

9.2 Stable Itanium-mangled symbol names

Per Contract Rev 13.7 §1.4 + Section 10.2 cross-tool symbol-space convention: every XHT-emitted singleton-getter and constructor uses Itanium-LengthPrefixed-v1 mangling (Z_Construct_X<Kind>_<Module>_<Type>). The mangling is language-agnostic (post-X-strip engine names are unique across C++ and C#). The mangling is stable across XHT revisions within a single Contract version.

XCore-4b's XReflectionRuntime registry stores const FField* pointers (descriptor pointers) in TMap<FName, const FField*>. When a hot-reload patch swaps in a new descriptor for the same type, the registry's lookup is updated (registration calls overwrite the previous entry by FName). Any code that held a stale FField* pointer from before the patch is on the patch consumer to refresh; the patch contract is that "type pointers may invalidate at patch time" (matching UE's Live Coding policy).

9.3 Intern-table survival

The FName intern table lives in the XCore module's address space and is allocator-backed by the XCore-4a Phase-1g allocator whose lifetime is the whole process. The intern table is NEVER reset across patches. An FName Index created before patch remains valid after patch — the bytes it points to are still in the intern-table entry pool.

9.4 Per-DLL static_assert pins

Per the Stage B addendum, every XHT-emitted .gen.cpp carries static_asserts pinning the ABI tags (XPACT_FNAME_LAYOUT_TAG, XPACT_FPROPERTY_LAYOUT_TAG v2, XPACT_FSTRUCT_LAYOUT_TAG v4, XPACT_FCLASS_LAYOUT_TAG v4, XPACT_FSCRIPTSTRUCT_LAYOUT_TAG v4, XPACT_FENUM_LAYOUT_TAG v4, XPACT_FINTERFACE_LAYOUT_TAG v4, XPACT_FCUSTOMVERSION_LAYOUT_TAG, XPACT_REPMETA_LAYOUT_TAG v2, XPACT_FFAKEVTABLE_LAYOUT_TAG v2, XPACT_FCPPSTRUCTOPSFAKEVTABLE_LAYOUT_TAG v1). A patch DLL compiled against a different ABI fails to link with a clean compile-time error before any runtime damage occurs.

  • FindClass(FName): O(1) via TMap (SwissTable); typical hot-path latency <50 ns on Win64 desktop, <100 ns on Quest 3.

12. Engineering-Principles Compliance Summary (Rev 2 tightened per FIX-6 + FIX-28)

Per master plan engineering principles: "We have to ensure we create the best system we can, with absolute stability, capability, and performance. ... We are trying to build an engine that avoids the stability, capability, and performance issues Unreal Engine typically has." XCore-4b beats UE Core's reflection runtime in 11 concrete ways (Rev 1 listed 12; Rev 2 FIX-6 drops the false FRWLock claim and consolidates).

  1. FName is case-sensitive in MVP. Closes the silent-mismatch class of bugs where two FNames that look identical compare unequal because of subtle case differences at intern time. UE's case-insensitive default + case-preserving Editor mode duality creates a maintenance footgun that XPact eliminates by picking case-sensitive once.
  2. FProperty AND FScriptStruct dispatch are shared FakeVTables in .rodata, not per-instance vtables. Rev 2 (FIX-2) for FProperty; Rev 3 (FIX-R2-MAJ-2) for FScriptStruct: hot-reload-patch-bumped-vtable bugs (UE's most frequent Live Coding failure) cannot occur because there's no vtable to bump; each FProperty instance carries an 8-byte DispatchTable pointer to a shared .rodata-resident FFakeVTable per subclass (128 bytes per subclass, 15 dispatch slots), each FScriptStruct instance carries an 8-byte CppOpsTable pointer to a shared FCppStructOpsFakeVTable per subtype (136 bytes per subtype, 16 handler slots). UE applies the TStructOpsFakeVTable mechanism only to UScriptStruct::ICppStructOps (Class.h:1737-1768); XPact applies it more broadly to both FProperty subclass dispatch AND FScriptStruct ICppStructOps dispatch — deliberate divergence per Prime Directive (FIX-R2-MED-2).
  3. Per-type SchemaHash is compile-time-checked AND hashes declared shape (not compile offsets). Rev 2 (FIX-10): XHT emits a build error when an XPROPERTY declared shape changes without a matching SchemaVersion bump. UE's runtime-only FCustomVersion silently corrupts data when the bump is forgotten. XPact's SchemaHash identifies type identity (declared shape), portable across compilers/packing flags.
  4. Push-model is declared via CPF_PushModel bit in EPropertyFlags. Rev 2 (FIX-1): the flag is enough. XNetworking's FReplicationStateDescriptorRegistry caches resolved push-state in its descriptors at session-init. No per-property hash-table lookup at replication tick time; no per-FProperty bitfield slot.
  5. RepNotify resolution is cached in the XNetworking descriptor at session-init. Rev 2 (FIX-1): FProperty carries the FName only (matches UE shape and avoids FProperty bloat); the descriptor builder resolves to a callable once per session, not per replication event.
  6. FName intern table is case-sensitive + 256-shard high-byte selection + no LowercaseProbeHash. Rev 2 (FIX-6 correction): UE 5.4+ uses FRWLock too (UnrealNames.cpp:889), so the lock primitive is not the win. The win is the case-sensitive design (half the intern-table memory, no silent corruption), the LowercaseProbeHash elimination, and the 256-shard high-byte selection tuned to XPact's smaller name population.
  7. Single FName layout always; no UE_FNAME_OUTLINE_NUMBER build-flag variability. One performance profile, one set of test vectors. UE's variability creates test-matrix blowup.
  8. UInterface / IInterface duality collapsed to one FInterface descriptor. No per-interface dispatch-table indirection beyond the direct function-pointer call. UE's pattern is so confusing it has its own dedicated documentation page. Rev 2 (FIX-8) documents the three concrete dispatch shapes (C++ user-class, C# transpiled, scripting-driven) explicitly.
  9. FField has no EObjectFlags slot. UE deprecated the slot in 5.8 but still carries the 4 bytes for legacy compatibility; XPact starts greenfield without the slot.
  10. Dense ObjectRefProperties TArray for GC scan (not linked-list RefLink). Rev 2 (FIX-13): contiguous array on FStruct populated at FClass::Link; meets Foundation Prototype criterion (b) <50ms full-heap-scan on Quest 3 for 100k XObjects. UE's linked-list RefLink pointer-chases the ARM64 cache.
  11. Per-.gen.cpp static_assert pins on every ABI layout tag. A patch DLL compiled against a different ABI fails to link with a clean compile-time error before any runtime damage occurs. UE has no equivalent compile-time gate; UE's ABI mismatches manifest as runtime crashes mid-session.

12.1 UE patterns XPact rejects (Rev 2 added per FIX-28)

The flip side of the 11 wins above: XCore-4b also rejects three UE patterns that have proved problematic, with rationale.

  • Deprecated EObjectFlags slot on FField. UE deprecated this slot in 5.8 but still carries the 4 bytes for legacy compatibility. XPact starts greenfield without it (saves 4 bytes per FField × thousands of FFields in a typical project).
  • UInterface/IInterface dual-type pattern. UE's "every interface is two classes" (a UObject-derived UInterface for reflection + an IInterface for C++ implementation) is a footgun for blueprint authors; "should I derive from IFoo or UFoo?" is the kind of question new UE developers ask repeatedly. XPact's single FInterface descriptor with the dispatch table directly on it eliminates the duality.
  • CASTCLASS_FNumericProperty polymorphic base. UE's FNumericProperty is a polymorphic base for FIntProperty / FFloatProperty / etc. with a virtual GetNumericValue interface. XPact rejects this for two reasons: (a) the virtual dispatch is contrary to XCore-4b's zero-virtuals discipline; (b) the FNumericProperty abstraction provides little value vs the direct per-type FProperty subclass with its own GetValueFn/SetValueFn dispatch slots in the FakeVTable.

13. Acceptance Criteria

The implementation phase will validate XCore-4b against these acceptance gates. Each gate is a pass/fail predicate executable in CI; aggregate pass is the merge criterion.

A. FName intern table

  • A2. FromString same string twice returns the same Index. Asserted via direct intern-table inspection.

19.2 Prime Directive analysis (Option A vs Option B)

Per Prime Directive (engineering_principles.md: "Use the thing that is correct not the thing that is easier to implement"), two responses were considered:

  • Option A: Refactor XCore-4a to make DefaultAllocator truly stateless. Move FMemTag attribution to the per-allocation callsite (every FMemory::Malloc(size, FMemTag::X) call). Pros: 16-byte TArray as Rev 3 intended; ~8 bytes saved per TArray instance (cumulative savings across reflection runtime ~8 KB module-wide; cumulative savings across user code ~bytes-per-container-instance × container-instance count, e.g. ~80 KB savings for 10k user containers). Cons: substantial XCore-4a churn (~10k LoC touched across all containers; all containers + tests re-verified for the API surface change); API friction (FMemTag becomes an explicit parameter at every allocation callsite, propagating through every container method that allocates); loses the leak-tracker integration shape (per-container attribution becomes per-call attribution, which is noisier and harder to consume in leak reports); breaks XCore-4a's locked static_assert(sizeof(DefaultAllocator) == 2) ABI and forces a Contract Rev 14.x bump.
  • Option B (Rev 4 adopts): Acknowledge XCore-4a's design choice and ship accurate sizes. Pros: matches actual implementation; preserves XCore-4a's leak-tracker + memory-budget attribution feature (a deliberate XCore-4a design choice already shipped in commits ba6455a, 984ef9a, 1195f31, 34d6826, 589d247); no XCore-4a churn; no Contract Rev 14 bump (the change is confined to XCore-4b spec + .gen.cpp emitter byte-totals). Cons: ~8 bytes per TArray vs theoretical optimum (the cost is bounded and small at scale; FStruct/FClass/FEnum/FInterface together carry 5 TArrays in the reflection-runtime hot path, so ~40 bytes per class hierarchy × ~5000 reflected classes in a large project ≈ 200 KB).

Rev 4 adopts Option B. The FMemTag-per-allocator design is a load-bearing XCore-4a feature consumed by Phase 1b leak detection + Master Plan §2b memory budget telemetry, and it's already shipped and locked. The Prime Directive instructs "do it right the first time, not the easy way" — in this case, the right thing is to honour XCore-4a's deliberate design decision (per-container memory attribution) rather than to retrofit XCore-4a for a minor reflection-runtime footprint win. The 8-byte/TArray cost is acceptable for the attribution capability; Option A is recorded here for future consideration if the cost ever becomes load-bearing (e.g., a future Quest 3 memory-budget escalation that needs to recover the ~200 KB).

19.3 Recommendation: Option A as a separate future task

If the user wants to revisit Option A in a separate task, the work would be:

  • Refactor Engine/Source/Runtime/XCore/Public/Containers/DefaultAllocator.h to remove FMemTag m_tag; update the locked static_assert(sizeof(DefaultAllocator) == 2) to == 1 (effectively empty) or to a true empty-base class.
  • Audit every TArray/TMap/TSet/TQueue/FString allocation callsite in XCore-4a (~10k LoC) to add an explicit FMemTag parameter.
  • Update the leak-tracker integration shape to consume per-call attribution rather than per-container; this is a meaningful API + telemetry change.
