1. Purpose, Scope, and Locked Decisions

1.1 What XCore-4a is

XCore-4a is the no-reflection C++ foundation of the XPact Engine. It is the first C++ system in the engine build order (plan Section 4 Step 3) and the substrate every later C++ module sits on. The ten internal areas in scope are:

  1. Memory + Allocator — one binned allocator, mandatory tagging, deterministic OOM policy.
  2. Containers — TArray, TMap, TSet, TBitArray, TStaticArray, with GC-aware partial specializations.
  3. Math — vectors, quaternions, matrices, transforms; sim-path-disciplined two-header model.
  4. Platform HAL — Win64 / Linux / Android facades for misc, time, process, atomics, virtual memory.
  5. Threading Primitives — atomics, recursive mutex, RWLock, event, SPSC/MPSC queues. No TaskGraph (Step 8).
  6. CVars — IConsoleManager, FAutoConsoleVariable, five-level SetByPriority cascade.
  7. Stat — XSTAT_* macros with compile-time stat IDs; per-thread shards merged once per frame.
  8. FText + FString runtime — UTF-8 throughout; per-locale loctable; FUTF16String Win32 escape hatch.
  9. Leak Detection — Debug/Development always-on tagged tracking with platform-specific stack walks.
  10. Header Macros — XCONSTINIT, XPACT_* portability + build-config-aware XPACT_CHECK.

1.2 What XCore-4a is NOT

The following are explicit non-goals at System 3 and are deferred to later systems in the build order:

  • Reflection runtime. FClass, FStruct, FEnum, FInterface, FProperty, FField are XCore-4b (plan Section 4 Step 4). XCore-4a declares the interfaces those types consume (XGCRootSpan, ABI tags, mangling tags) but ships none of the reflected-type machinery. The existing XReflectionRuntime.h stub stays as XCore-4b scaffolding and is NOT part of XCore-4a's public API (see Section 13).
  • FName exception (fix C-1). FName is a special case: XCore-4a forward-declares the 8-byte handle type struct FName { uint32_t Index; uint32_t SerialNumber; } (layout-locked) so that XCore-4a's containers can instantiate TMap<FName, V> and TSet<FName> without a circular dependency on XCore-4b. XCore-4a defines ONLY the type and its static_assert(sizeof(FName) == 8) ABI lock; the interning table, hashing, equality, FromString, and ToString implementations all ship in XCore-4b. See Section 11.8 for the locked declaration.
  • XObject heap and GC collector. The non-moving mark-and-sweep collector, card-table write-barrier intrinsic implementation, allocator-XObject integration, and weak-reference plumbing land in XCoreXObject at plan Section 4 Step 5. XCore-4a's containers call into the GC root-registration ABI (per Contract Rev 13.7 §3) but do not implement it; the call site is the contract.
  • TaskGraph and named threads. Worker pools, named threads (Game / Render / RHI), dependency-edge scheduling, priority levels are XTaskGraph at plan Section 4 Step 8. XCore-4a ships only the threading primitives the TaskGraph itself will build on.
  • Renderer, RHI, scene graph, gameplay framework. Anything that would normally live in UE Core but conceptually belongs to higher layers ships in those later systems.
  • Network bit-level serialization (fix Rev 3 m5). FBitReader / FBitWriter (UE-equivalent Serialization/BitReader.h and Serialization/BitWriter.h) are deferred to XSerialization (Layer 1, post-XCore-4a per Master Plan §3). XCore-4a's FArchive forward-declaration in §4.1 stays; XSerialization fills in the byte-level + bit-level serialization surfaces. XCore-4a never reads or writes individual bits to a stream — the bit-level facility belongs with the network replication code that consumes it, not with the foundation. Cross-reference: any XCore-4a TU that needs bit-level packing (none currently) would forward-declare FBitReader / FBitWriter the same way FArchive is forward-declared.

1.4 Dependencies

XCore-4a depends on XBT (System 1, plan Section 4 Step 1) for compilation and XHT (System 2, plan Section 4 Step 2) for the reflection-marker scan. Since XCore-4a defines no reflection markers itself, XHT's actual emit for XCore-4a is a no-op set of empty sentinel .gen.h + .gen.cpp files and a minimal .gen.manifest — the XHT integration is exercised but produces no reflected types. This is the cleanest possible boundary at System 3 and a useful baseline for downstream modules that DO carry markers.

XHT empty-emit no-op contract (fix MAJOR). XHT runs for XCore-4a and produces a deterministic no-op manifest with the following exact shape: the .gen.manifest file contains { "Module": "XCore", "Types": [] } (canonical JSON, fixed key order, trailing newline), and the XCore.init.gen.cpp file contains only the manifest-verification static_assert (a single static_assert verifying the manifest hash matches the build's expected hash). The pair of files links cleanly without symbol conflicts against the XCore-4a translation units. This is the minimum-viable XHT integration baseline: every downstream module that DOES carry reflection markers compiles against the same emit-and-link contract, so XCore-4a's empty-emit serves as the smoke test for the integration. Acceptance criterion J-extra (added to §17.10): "XHT invocation on XCore-4a produces an empty-but-valid .gen.manifest and an .init.gen.cpp that links without symbol conflicts."

Downstream consumers include every C++ module the engine ships: XCore-4b (reflection runtime), XCoreXObject (GC heap + collector), XTaskGraph, the renderer, the gameplay framework, and the user's training-content modules. XCore-4a's API surface is the lingua franca of the engine's C++ tier.

1.5 Static-init phase ladder (fix C-2)

XCore-4a defines an explicit three-step static-init phase ladder. Every subsystem in this specification declares which phase it comes up in; the cross-cutting "subsystem X must initialise before subsystem Y" claims throughout the rest of the document refer to positions on this ladder rather than relying on undefined static-initialiser ordering across translation units.

namespace XCore::HAL {

enum class EInitPhase : uint8_t {
    PreStaticInit  = 0,   // allocator, threading primitives, macros
    PostStaticInit = 1,   // CVars, Stat side-table, FText fallback
    FrameZero      = 2,   // everything else (renderer, gameplay, content)
};

// Single global; updated by XEngineInit's bootstrap before any user-level static-init runs.
extern std::atomic<EInitPhase> g_EngineInitPhase;

inline EInitPhase EngineInitPhase() noexcept { return g_EngineInitPhase.load(std::memory_order_acquire); }

} // namespace XCore::HAL

Phase assignments (referenced from Sections 3-13):

  • PreStaticInit: FMemory (Section 4), threading primitives (Section 8), macro suite (Section 13), platform HAL atomics (Section 7). These have no inter-module dependencies and may be used by any constinit object.
  • PostStaticInit: IConsoleManager CVar drain (Section 9.5), Stat side-table build (Section 10.5), FLocalizationManager en-US fallback (Section 11.2). All require the allocator to be live.
  • FrameZero: every gameplay-tier and content-tier subsystem; FText locale tables beyond en-US fallback.

Invariant. Every public API that depends on PostStaticInit-or-later state begins with XPACT_CHECK(::XCore::HAL::EngineInitPhase() >= EInitPhase::PostStaticInit). The check is Debug/Dev only (zero-cost in Shipping) and surfaces "called too early" bugs at the call site rather than producing wrong values silently. This replaces the handwaved "Stat runs before CVars" claim in Section 3's earlier prose with an explicit ladder.

Cyclic risk resolution (fix C-5). CVars want a name string (FString); FString uses the allocator (XMemory); XMemory might want a CVar to expose wasted-bytes for tuning — circular. Resolution: XMemory exposes wasted-bytes via Stat at EInitPhase::PreStaticInit (Section 1.5), not via a CVar. Stat's hot-path counters write to per-thread shards at PreStaticInit; the Stat side-table that maps FStatId.Hash back to (Name, Group) is built at PostStaticInit (it is a diagnostic-side concern, not a counter-write concern). The CVar system comes up at PostStaticInit. The two systems do not race: any read of IConsoleVariable::GetInt, GetFloat, or GetString begins with XPACT_CHECK(::XCore::HAL::EngineInitPhase() >= EInitPhase::PostStaticInit), so calling a CVar accessor from a PreStaticInit constructor aborts in Debug/Dev rather than seeing a default value silently. Allocator tuning knobs that genuinely need to be runtime-settable are CVars in the bin-size table sense; the tuning knobs that need to be cheap to read every alloc (e.g., a "trim threshold") are compiled into the binary as constexpr values.

Stat TLS shard lazy-init contract (fix Rev 3 M1). The Stat hot path is well-defined at PreStaticInit because the shard's slot table is constinit-initialised to zero and the open-addressing path needs no further setup. The TLS shard (XPACT_TLS_MODULE_SAFE(FStatShard, g_shard); Section 10.5) is lazy-initialised on first XSTAT_INC per thread; XSTAT_INC invoked at PreStaticInit (e.g., from a constinit constructor) is well-defined because the shard's 1024-slot open-addressed table is zero-initialised at static-storage-duration time, before any user code runs. The perfect-hash table (built at PostStaticInit; Section 10.5 fix M-10) is layered on top of the always-available open-addressing path; writes to the shard ALWAYS go to the open-addressing slot, even after the perfect-hash table publishes — the perfect-hash is consulted only by FStatRegistry::MergeFromAllThreads and by FStatRegistry's lookup-by-name surface, never by XSTAT_INC / XSTAT_ADD. The contract: writes are always to the open-addressing slot; the perfect-hash table is read-only and merger-only. This eliminates the apparent "Stat needs side-table before PreStaticInit" race; the side-table is a read-side optimisation, not a write-side prerequisite.

One allocator ships: FMallocBinned-X, a descendant of UE's Binned3 design. Per-thread small-bin (32 B ↔ 16 KiB) with a global large-bin freelist + slab list. Cross-thread Free routes the block to the owning thread's MPSC reclaim queue (drained on next allocation call on that thread). The bin-size table mirrors UE Binned3 tuning, exposed via Stat counters for measurement.

OOM contract (fix M-2). Direct FMemory::Malloc callers may receive nullptr when the active FOOMPolicy is ReturnNull (Dev configuration default). However, every container layer in XCore-4a (TArray, TMap, TSet, FString, TBitArray, the lock-free queues' growth paths) routes its allocation through FMemory::MallocOrAbort — a thin wrapper that calls Malloc and aborts if the return is null. Containers cannot safely propagate ReturnNull: a half-constructed container with an already-registered XGCRootSpan would expose a dangling buffer base to the collector. The choice is deliberate: direct callers that genuinely want to attempt-and-recover on OOM (e.g., a high-water-mark scratch buffer the engine could shed) use Malloc + null check; container library code uses MallocOrAbort and trusts the engine to have provisioned realistic memory budgets. MallocOrAbort in Shipping (where the active policy is Abort) is equivalent to Malloc; the wrapper exists for the Dev configuration where direct callers see ReturnNull but containers must not.

C# binding. No direct surface; IL2CPP emits FMemory::Malloc for non-GC containers with tag inferred from the container type. One helper exists: FMemoryScope.NoAlloc() returning IDisposable wrapping FScopedNoAlloc.

4.2 Threading contract

All three core methods (Malloc, Realloc, Free) are thread-safe. The fast path is lock-free: a per-thread TLS cache holds bundles of free blocks per bin; cross-thread frees enqueue into the owner's MPSC reclaim queue. The owner thread drains the queue on each subsequent allocation; an idle thread's queue is drained at thread exit. The global large-bin path acquires a single global mutex (a recursive SRWLock on Win, pthread_mutex_t on POSIX).

TLS module-safety (fix B-C1). The per-thread TLS cache is declared via XPACT_TLS_MODULE_SAFE(FBinnedTlsCache, g_TlsCache) (Section 13), NOT raw thread_local. Win64 and Android host hot-reloadable DLLs; raw thread_local in a DLL leaves dangling TLS-block entries pointing into freed code when the DLL unloads, which leaks the cache and may corrupt the next module loaded into the same address space. The module-safe macro routes through FPlatformTLS::AllocSlot/GetValueInSlot on those platforms (UE's TModuleSafeThreadLocal pattern) and falls through to native thread_local on the Linux server (no DLL hot-reload at MVP). The choice is mandatory for any TLS-resident state owned by XCore-4a; see also Section 10.5 for the Stat-shard analogue.

TLS owner-lock during quiesce (fix B-C2). Each per-thread cache carries a std::atomic<bool> bLockedByOwnerThread flag. Any cross-thread access — the GC trimming the cache, the allocator-reclaim path stealing free blocks from an idle thread, or the hot-reload quiesce path freezing the cache for inspection — must first acquire the owner-lock via compare_exchange_strong(false, true, memory_order_acq_rel). The owner thread checks the flag at every cache-touching operation in Debug/Dev (zero-cost in Shipping); a sister thread that holds the lock will release it only at the quiesce point.

4.3 Determinism contract

Allocation order on the sim path is deterministic given identical call sequences. The allocator contributes no nondeterminism (no time-based randomization, no address-space layout randomization within the allocator's reserved VM).

FScopedNoAlloc Shipping discipline (fix A-MIN4). FScopedNoAlloc is the RAII contract for proving a sim-path inner loop is allocation-free; it asserts on any Malloc/Realloc call inside its scope. The discipline is split by TargetConfiguration:

  • Debug / Development / Test: the scoped guard is live; every FMemory::Malloc / Realloc inside the scope aborts with a clear stack trace naming the offending tag and size.
  • Shipping: the constructor and destructor compile to ((void)0); the guard is a zero-cost no-op.

Locked assumption: sim-path TUs are exhaustively unit-tested in Dev/Test to be alloc-free; a Test-config violation slipping through to Shipping is a process failure (insufficient test coverage), not a runtime check failure. The decision is principled: the Shipping cost of one extra TLS-counter increment per allocation is unjustified when the Test gate is the right place to catch the bug. The cost is borne by the test suite, which runs every alloc-counted scenario before merge.

4.4 GC interaction

XCore-4a's allocator does not know about XObject. XObject allocations go through a distinct entry point in XCoreXObject (Step 5) that internally calls into the same binned slabs but tags them FMemTag::XObject and registers with the collector. A single hook, RegisterXObjectAllocator(void*(*)(size_t, size_t)), is installed at engine startup by XCoreXObject. The mark-bit metadata is co-located in the slab header; XCore-4a defines the slab-header layout (so the GC can find the metadata) but does not fill the mark bits.

Pre-registration link error (fix C-8). The XObject allocator hook is implemented as a function-pointer variable initialised to nullptr at link time:

// XCore-4a side: declaration + zero-initialised hook
namespace XCore::HAL {
extern void* (*s_XObjectAllocator)(size_t Size, size_t Align) noexcept;  // nullptr until RegisterXObjectAllocator runs

void* NewXObject(size_t Size, size_t Align) noexcept {
    XPACT_CHECK(s_XObjectAllocator != nullptr);  // aborts cleanly in XCore-4a-only test build

In an XCore-4a-only test build (XCore-4b not linked), any code that constructs an XObject-derived type calls into NewXObject, which fires the XPACT_CHECK in Debug/Dev and aborts cleanly. In Shipping (which requires the full engine, so XCore-4b is always present), the check is compiled out but the registration is guaranteed to have happened during EInitPhase::PreStaticInit. The pattern makes "called XObject construction before XCore-4b registration" a deterministic, attributable abort with a clear stack trace, rather than a silent nullptr-call segfault.

Note that the abort is at runtime, not link time, because the symbol s_XObjectAllocator is defined in XCore-4a as a tentative-definition extern; the XCore-4b definition is the strong definition. In a pure XCore-4a-only test linking-without-XCore-4b configuration, the build system inserts a fallback null-initialised stub via a weak symbol, so the executable links cleanly and the abort fires at the construction site.

4.5 Divergences from UE

Allocator-family rationale (fix B-M1). XPact descends FMallocBinned-X from UE's Binned3 design rather than vendoring mimalloc, snmalloc, or jemalloc. The decision is driven by the non-moving GC's mark phase: the collector iterates allocations at predictable VM strides (each bin's reserved VM range is contiguous, and the slab headers carry the per-allocation mark-bit metadata in a known offset from the slab base). Binned3's per-bin contiguous VM range is the right substrate for this iteration pattern. Mimalloc's slab-and-segment layout interleaves bin sizes within a segment, which would force the GC to either (a) chase per-allocation back-pointers or (b) reserve separate VM ranges per bin externally — both options re-implement Binned3's structure with extra indirection. Snmalloc's per-thread message-passing-free model is similarly orthogonal to a non-moving collector. Jemalloc's arena model is closer but does not expose the slab metadata layout cleanly to a GC root walk.

Trade-off cost (locked). Descending Binned3 makes XPact's allocator ~5–15% slower than mimalloc on raw small-allocation throughput benchmarks (Aerospike, Linux kernel hash-set). The GC integration wins (predictable mark-iteration, no per-allocation back-pointer overhead, no separate VM-range bookkeeping) pay the cost back. The performance bar in §17.1 A1 is raised accordingly: XPact's tuned Binned3-descendant should measurably beat UE's because we eliminate UE's accumulated dead code (Binned2 fallback paths, multi-allocator dispatch, runtime allocator-switching CVars).

The XPACT_NO_UNIQUE_ADDRESS attribute (Section 13) means that when AllocatorT is an empty type, the allocator member occupies zero bytes; the compiler folds it into adjacent padding or omits it entirely. However, XPact's DefaultAllocator is NOT empty: it carries a 2-byte FMemTag field (verified at DefaultAllocator.h:178-186 with static_assert(sizeof(DefaultAllocator) == 2)). Per-container memory attribution is a load-bearing Phase 4b.5 requirement and the tag cannot be removed. The compiler therefore allocates 2 bytes for the allocator member; padding rounds the struct up to the next 8-byte boundary (the pointer's natural alignment), yielding sizeof(TArray<int, DefaultAllocator>) == 24 bytes (8-byte data pointer + 4-byte size + 4-byte capacity + 2-byte allocator + 6-byte tail padding). XPACT_NO_UNIQUE_ADDRESS cannot fold an FMemTag-carrying allocator, because the attribute is a hint applicable to objects of size zero only; a 2-byte object cannot overlap with same-byte fields. The XCore-4a TArray sizeof is therefore 24 bytes, not 16; the prior "16 bytes via EBO" wording assumed an empty allocator and is corrected here per Round 2 audit MAJOR-1. The cascade ripples through XCore-4b's FStruct/FClass/FEnum/FInterface layouts (per XCore-4b Rev 4 §5.3 + §11.6 layout tags); XPACT_NO_UNIQUE_ADDRESS still appears in the conceptual layout because future allocator implementations on debug-only / non-tagged builds could be empty and benefit; for the production tagged allocator the attribute is a no-op. See §5.5 for the (revised) divergence row.

5.2 Threading contract

Containers are not thread-safe. Thread-safe variants are distinct types (e.g., TThreadSafeQueue<T>, TThreadSafeCounter32/64, TConcurrentLinearAllocator) and live alongside the standard types but are explicitly named. UE's "flip a template arg for thread-safety" pattern creates same-type-different-locking bugs; XPact splits the types. Concurrent mutation of an unsynchronised TArray is undefined behaviour (asserted in Debug under TSan; race in Shipping).

5.3 Determinism contract

All container operations are deterministic at the algorithm level. Hash maps use the SwissTable-style algorithm (abseil flat_hash_map-equivalent: open-addressing with SIMD probe groups + a per-slot control byte holding the H2 hash fragment) keyed by XXH3 scalar (fixed zero seed); UE's randomly-seeded mode is banned (Contract §4). The SwissTable algorithm is chosen over robin-hood for the cache-friendlier control-byte stride; the XXH3 scalar path (no SIMD; see §11.9) is chosen for bit-exact-cross-architecture replay. Iteration order on a TMap/TSet is implementation-defined (per the SwissTable algorithm); sim-path code MUST NOT rely on iteration order at all, not even pre-first-remove. Stable element addresses are NOT preserved across Add — rehashing on grow relocates every entry. This is a divergence from UE's TSet/TMap stability guarantee (which uses TSparseArray-backed slots whose addresses are stable until explicit compaction); XPact's flat-storage SwissTable trades that guarantee for cache-friendlier lookup. Code that needs address stability stores via std::unique_ptr<V> in the value position. Lock-free queues are sim-path-incompatible (the sim path is single-threaded per master plan); calling TMpscQueue::Enqueue from a sim-path TU is a compile-error via [[deprecated]].

5.4 GC interaction (locked decisions 7 and 9)

Per Contract Rev 13.7 §3, GC-aware containers carry an embedded XGCRootSpan via partial template specialization:

  • TArray<T*> where T : XObject embeds XGCRootSpan, kind = Strong, move-only.
  • TArray<TWeakObjectPtr<T>> embeds XGCRootSpan, kind = Weak.
  • TArray<FVector> and other pure-value-type instantiations carry no span; pure RAII; copy allowed.
  • TArray<XAny> (untyped-XObject editor scratch) carries a Conservative span and emits a sim-path build-time warning.

Construction protocol (per Contract §3.6 N6): m_rootSpan = { nullptr, sizeof(void*), 0, kind, 0 }; then XGC_RegisterRootSpan(&m_rootSpan) before any buffer allocation. This makes the constructor exception-safe: if the subsequent Malloc throws or returns null, the span is registered with count = 0 and the destructor's Unregister is a no-op clean teardown.

XGCRootKind enum (fix Rev 3 m3). The collector distinguishes three root kinds, declared as a uint8_t-backed enum so the XGCRootSpan can pack it into byte 24:

enum class XGCRootKind : uint8_t {
    Strong,         // pin every XObject pointer in the slot against collection;
                    // the most common kind (TArray<XActor*>, TMap<FName, XActor*>
                    // value position).
    Weak,           // null the slot if the pointee is collected; the collector
                    // updates weak slots in a second pass after mark. Used by
                    // TArray<TWeakObjectPtr<T>>.
    Conservative,   // mark every word in the slot as a potential pointer; the
                    // collector walks the slot bytes and treats any value that
                    // looks like a valid XObject* as a root. Used by TArray<XAny>
                    // (untyped-XObject editor scratch). Conservative kinds emit a
                    // sim-path build-time warning per Contract §3.2.
};

static_assert(sizeof(XGCRootKind) == 1, "XGCRootKind ABI lock");

XGCRootSpan layout (fix M-12). The span sums to 32 bytes on 64-bit targets:

struct XGCRootSpan {
    void**       base;          //  0  +8   pointer to first slot
    size_t       stride;        //  8  +8   bytes between slots
    size_t       count;         // 16  +8   number of slots
    XGCRootKind  kind;          // 24  +1   strong / weak / conservative
    uint8_t      _padHead[3];   // 25  +3   alignment pad placed BEFORE flags so
                                //          uint32_t flags has natural 4-byte alignment
    uint32_t     flags;         // 28  +4   reserved future flags (must be 0 at Rev 13.7)
};

static_assert(sizeof(XGCRootSpan)  == 32, "XGCRootSpan ABI lock");
static_assert(alignof(XGCRootSpan) ==  8, "XGCRootSpan alignment lock");

The 32-byte layout aligns one span per cache line on most modern targets (Quest 3 Snapdragon XR2 Gen 2 = 64-byte line; Win64 Ryzen = 64-byte line; Linux server = 64-byte line). The earlier 24-byte size in the macro was a documentation bug; the genuine struct on every supported target rounds to 32. The contract sums layout = void** (8) + size_t (8) + size_t (8) + XGCRootKind (1) + 3 bytes head-pad + uint32_t (4) = 32. Errata note (Phase 1a implementation finding): earlier draft revisions of this section placed uint32_t flags at byte offset 25 with the 3-byte pad as a trailing _tailPad[3] at offset 29. That layout was incorrect: standard C++ alignment requires the uint32_t to start at a 4-byte boundary, so the compiler would either misalign (UB on ARM64) or insert 3 implicit pad bytes before flags — making the struct 35 bytes natural & 40 bytes after the trailing pad, NOT 32. The corrected layout puts the explicit 3-byte head-pad before flags so the natural 4-byte alignment is honoured AND the total is exactly 32 bytes. The byte-content of bytes 25..31 is identical in either layout because flags must be zero at Rev 13.7; the visible difference is the field name (_padHead vs _tailPad) and the offset of flags (28 vs 25). Phase 1a's XGCDeclarations.h ships the corrected layout.

Resize protocol: allocate new buffer, relocate elements, single XGC_UpdateRootSpan(&m_rootSpan, newBase, newCount) call; mark-phase atomicity is guaranteed by Contract §3.6 (the collector and span update are mutually serialised).

Destruction protocol: XGC_UnregisterRootSpan first (so the collector cannot observe a stale span pointing to the about-to-be-freed buffer), then free the buffer.

Move protocol: per Contract §3.4 M1, GC-aware containers are move-only. The move transfers span ownership: re-register at the destination, zero the source's count via UpdateRootSpan. The two spans never both point at the same live buffer.

Nested-container protocol (locked decision 9): each GC-aware container instance owns and manages exactly one XGCRootSpan. Nesting (e.g., TMap<FString, TArray<XActor*>>) is supported through move-propagation: when the outer TMap rehashes, the inner TArray's move-ctor is invoked, which updates its own embedded span as part of the move. The outer TMap does not need to know which value-types contain spans; the compiler dispatches correctly through partial specialization.

Write-barrier call site (locked decision 7, ordering fix C-4): when a GC-aware container stores an XObject pointer (e.g., TArray<XActor*>::operator[](i) = newActor), the implementation invokes the barrier and the store in a fixed order:

// Pre-store write-barrier semantics (fix C-4): the barrier marks the card
// for &slot BEFORE the slot is updated. This guarantees the collector
// scanning the marked card always sees newValue (the post-barrier store
// is release-ordered; the barrier itself is the synchronisation point).
XGC_WriteBarrier(&slot, newValue);
slot = newValue;                  // memory_order_relaxed equivalent

Memory-order locked. The barrier (XGC_WriteBarrier) is a memory_order_release on the published-slot read inside the collector implementation (XCore-4b's mark thread reads the card via memory_order_acquire). The slot store itself is memory_order_relaxed; the barrier's release ordering is what makes the new value visible to the collector. Inverting the order (store first, then barrier) is a contract violation: a concurrent mark-thread observing the card mid-write could see the slot at an intermediate state. XCore-4a's containers MUST emit the barrier-store pair in this exact order; the build's TSan suite verifies the invariant under load. Calling XGC_WriteBarrier with a slot pointer that does not lie within any currently-registered XGCRootSpan is undefined behaviour in Shipping; XCore-4b's Debug/Development implementation aborts with XPACT_CHECK(::XGC::IsSlotInRegisteredSpan(slot)) at the barrier entry, so the violation surfaces as a clean abort during pre-Shipping testing rather than a silent card-table corruption later (fix Rev 3 m2).

The XCore-4a implementation of XGC_WriteBarrier is a no-op weak-symbol stub; XCore-4b replaces it with the card-table-marking real intrinsic. The call site is the contract. The function signature is locked at extern "C" void XGC_WriteBarrier(void** slot, void* newValue) noexcept — see Section 13 declarations.

Hot-reload: per Contract §3.7, GC-aware container layouts are frozen mid-session. The X_DECLARE_GC_AWARE_CONTAINER macro (Section 13) injects a static constexpr bool x_container_layout_frozen = true sentinel that XLiveCoding's patch-validation pass reads on patch.

6.1.6 FRandomStream RNG (fix B-MIN3)

Per Master Plan Section 2 Determinism row, the engine's deterministic RNG is xoshiro256++ (David Blackman & Sebastiano Vigna, 2019; public-domain reference implementation at prng.di.unimi.it/xoshiro256plusplus.c). The state is 4 × uint64_t = 32 bytes; the algorithm has a 2¹⁸⁴−1 period and passes BigCrush. It is sim-path-safe (no platform RNG, no time-based seed; the seed is supplied per session from the synchronized seed established at session-start).

Determinism contract: identical seed + identical call sequence produces bit-identical output across all three target platforms. The Fork operation uses splitmix64 over the parent's current state to derive a child seed, so a forked stream is independent of subsequent parent draws while remaining deterministic. The runtime never seeds sim-path code from time(), /dev/urandom, or any platform entropy source.

Non-deterministic seeding for non-sim consumers (fix Rev 3 M5). Sub-systems that legitimately need a non-deterministic seed (editor random-asset preview; plugin authentication tokens; one-shot debugging-state perturbation) construct an FRandomStream from FPlatformMisc::GetEntropy:

The split is enforced at the header level; a stray FPlatformMisc::GetEntropy call in a sim-path TU fails the build with the deprecation diagnostic. See §7.5 cross-reference for the editor-tier example.

memory_order discipline (fix M-4). No method on FAtomicInt32/64/Ptr has a default memory_order parameter. Every caller MUST specify; the named convenience variants (LoadAcquire, StoreRelease, FetchAddRelaxed, etc.) cover the common cases. Defaulting to memory_order_seq_cst (UE's historical pattern) is banned for a concrete reason: on ARM64 (Quest 3 Snapdragon XR2 Gen 2, Apple Silicon hosts in Phase 2), seq_cst stores issue a full dmb ish instruction, which costs 10–50× the latency of an acquire or release variant. On x86_64 the cost difference is negligible (the architecture's strong memory model makes seq_cst free for stores), but XPact ships the same code on both targets — defaulting to seq_cst would silently hide the ARM64 cost cliff from the call site. Forcing the caller to choose makes the cost trade-off visible at the source level.

TBoundedMpscQueue (fix B-C4). The MPSC family ships in two variants:

8.2 Threading contract

Each method is atomic at-or-stricter than its name suggests. FCriticalSection always recursive on every platform (Win CRITICAL_SECTION is naturally recursive; Linux/Android pthread_mutex_t initialised with PTHREAD_MUTEX_RECURSIVE). FMutex (fix M-5) is the non-recursive companion: PTHREAD_MUTEX_NORMAL on POSIX, Win SRWLock on Win64. FRWLock is reader-preferring on Win and writer-preferring on POSIX by default; XPact's wrapper standardises on writer-preferring across all three to avoid reader-starvation surprises.

Condvar pairing (fix M-5). FConditionVariable::Wait takes FMutex&. Passing an FCriticalSection is a compile error via the XNonRecursiveMutex concept on the templated overload. The constraint exists because pthread_cond_wait with a recursive mutex held at recursion depth > 1 is undefined behaviour: the condvar implementation internally unlocks the mutex once, but a recursive mutex held N times requires N unlocks to be released, so the unlock-then-block is incorrect. POSIX documents the UB; XPact prevents the call at compile time.

Not sim-path-safe. The sim path is single-threaded per master plan. Using any threading primitive in a sim-path TU is a build error via [[deprecated]] on the wrapper types.

8.5 ABI / Hot-reload (locked answer to brief item 6)

All threading-primitive types have no virtual methods — they are POD-like wrappers around OS handles (SRWLOCK, pthread_mutex_t, Win32 HANDLE, condvar). Hot-reload patches function bodies, not the wrapper types. An FCriticalSection embedded in a hot-reloaded type continues working because (1) wrapper size and layout are part of the contract and never change, (2) the underlying OS handle stays valid across DLL reload, and (3) the wrapper destructor sees the same OS handle. Each wrapper carries a static_assert(sizeof(T) == X) at every revision; any size change triggers an explicit ABI version bump in XPACT_GC_ROOT_ABI_TAG (Section 13).

9.5 Lifetime / static-init ordering (locked answer to brief item 7; fix C-6)

Registration: FAutoConsoleVariable at file scope queues itself onto a lock-free Treiber stack during static-init. The head pointer is declared constinit std::atomic<FAutoConsoleVariable*> at file scope; each constructor pushes onto the stack via compare_exchange_weak(memory_order_acq_rel). The Treiber stack is correct under parallel constructor invocation — e.g., the platform loader running C++ constructors for two newly-loaded DLLs on sister threads via dlopen on Linux or the OS-internal parallel-loader on Win64. IConsoleManager::Initialize (called from XEngineInit::Phase_PostStaticInit, see Section 1.5 phase ladder) drains the stack into the hash map. Querying: Find walks under a shared RW lock and switches to a lock-free published pointer in steady state.

Content-hash keying (fix C-6). RegisterInt/RegisterFloat/RegisterString key the hash map by content hash of the name bytes (XXH3 over the UTF-8 byte sequence with the engine's fixed zero seed per Section 5.3) — NOT by const char* pointer identity. Pointer-identity keying fails when two DLLs include the same CVar literal (two distinct const char* values pointing at byte-identical strings); the registrations would collide silently in pointer-keyed maps, producing the "second DLL's CVar shadows the first" bug. Content-hash keying makes the collision an explicit registration failure that the engine reports at the call site. The same content-hash discipline is required for Find at runtime.

Build-time double-registration error (fix M-7). XBT pre-scans the codebase for FAutoConsoleVariable constructions (file-scope statics and accessible globals) at build time. For every detected CVar literal name, XBT records (name, module, source-location). After the scan completes, XBT emits a build error if two distinct constructions share the same name — across the same or different DLLs. The error message lists both source locations so the developer can rename one or consolidate the registration. The runtime content-hash keying remains as defense-in-depth for dynamically-registered CVars (e.g., plugin-provided CVars that escape the build-time scan), but the build-time scan catches the common case before the binary ships. Acceptance criterion F-extra (added to §17.6): "Two CVars registered with the same name across different DLLs trigger an XBT build error with both source-location citations."

Ordering guarantee: pre-EInitPhase::PostStaticInit reads return the registered default and assert in Debug / warn in Dev. This inverts UE's pattern where reads against not-yet-registered CVars silently mis-see later registrations (the bug appears as "first cold-start has wrong value; second start is fine").

Typed cached handle (fix B-C3). FAutoConsoleVariable<T> exposes a TConsoleVariableHandle<T> that wraps a direct pointer into the value cell. Read of the cached cell is a single load with memory_order_acquire; no string lookup, no map walk, no lock. Hot-path CVar reads use the cached handle exclusively. IConsoleManager::Find(name) remains in the API for diagnostic and one-shot use (e.g., the console parser); its use in hot-path code is a documented anti-pattern. See Section 9.6 for the divergence row noting UE's hot-path string-walk pattern.

10.5 Threading model (locked answer to brief item 8; fixes B-C1, C-7, M-10)

Per-thread shards. XSTAT_INC writes to XPACT_TLS_MODULE_SAFE(FStatShard, g_shard) (Section 13) with no synchronization. The module-safe macro is mandatory: raw thread_local FStatShard m_shard in a hot-reloadable DLL on Win64/Android leaves the shard dangling on unload, which corrupts the next module's first stat write into that thread's slot. Linux server falls through to native thread_local.

Shard layout (fix M-10). Each shard is a 24 KiB fixed array of 1024 slots, each slot 24 bytes: (uint64_t hash, int64_t count, uint64_t padding). Indexing is FStatId.Hash & (1024 - 1). Collision policy is open-addressing with linear probing (up to 8 slots forward); if all 8 probe slots are occupied with non-matching hashes, the write falls through to a per-thread overflow path — a 16-entry linear-probe overflow array (Phase 1g spec correction: prior Rev 3 text said "a small TMap<uint64_t, int64_t>"; the shipping implementation in FStatShard.h:106 uses a 16-entry linear-probe array, which avoids TMap hot-path cross-coupling per Prime Directive "absolute performance" — TMap pulls in the SwissTable load-factor + allocator path on a code path that should only see ~zero traffic in well-tuned production). Overflow writes log a Dev warning on first insertion. Chaining is rejected because it requires per-slot pointer chasing in the hot path; open-addressing keeps the hot path cache-friendly.

Perfect-hash build-time table (fix M-10). At module init, the Stat side-table is built from a generated header that XBT's XSTAT_DECL scan emits during the reflection-marker pass. The generated header contains a perfect-hash table mapping each declared FStatId.Hash to a fixed shard slot, eliminating runtime probing for declared stats entirely. Stats inserted dynamically (e.g., a plugin's XSTAT_DECL in a hot-reloaded module) use the runtime open-addressing path until the next perfect-hash regeneration; the perfect-hash table is keyed by the generated-header content's BLAKE3 hash so a stale plugin against a fresh table fails the patch's manifest-validation pass.

Thread-exit shard handoff (fix C-7). When a thread exits, its FStatShard destructor migrates any remaining un-merged counts to static FStatExitOverflowQueue (a Treiber stack at file scope) via compare_exchange_weak(memory_order_acq_rel). The destructor runs BEFORE the thread_local table itself is torn down (C++ destruction-order guarantee on a thread-local with a non-trivial destructor). The next FStatRegistry::MergeFromAllThreads pops the overflow queue and folds it into the global tree before walking live threads. The locked ordering: thread-exit destructor → overflow-queue enqueue → live-thread merge → overflow-queue drain. Under 100-thread spawn/exit churn the invariant holds: every XSTAT_INC issued before thread exit is observable in the next frame's merge total.

Merge runs on a sync point (between Tick phases) walking each thread's shard into the global tree. The hot path is lock-free; correctness is guaranteed by the sync point plus the overflow queue.

Hot-path lazy-init lifecycle (fix Rev 3 M1). The Stat hot path is well-defined at every engine phase, including PreStaticInit. The TLS shard XPACT_TLS_MODULE_SAFE(FStatShard, g_shard) is lazy-initialised on first XSTAT_INC per thread; lazy-init is safe because the shard's slot table is constinit-initialised to zero (the storage has static-storage duration and is zero-initialised before any user code runs). The lifecycle contract enumerates which code path the hot loop takes at each phase:

  • PreStaticInit (or on any thread that started before PostStaticInit): XSTAT_INC writes via the open-addressing fallback path (Section 10.5 above) into the per-thread shard. No perfect-hash lookup; no side-table read; no synchronisation. The path is always available because the shard's storage is constinit-zero.
  • PostStaticInit and later: the perfect-hash table is built and published. The hot path remains UNCHANGED — XSTAT_INC still writes to the open-addressing slot. The perfect-hash table is consulted ONLY by (a) FStatRegistry::MergeFromAllThreads as it walks the shard during the per-frame merge, and (b) FStatRegistry's lookup-by-name diagnostic surface (e.g., the profiler's "find stat by name" query). This preserves a single-path hot loop with no phase-conditional branch.

The contract is locked: writes are always to the open-addressing slot; the perfect-hash table is only consulted by the merger and by the StatRegistry's lookup-by-name surface. An XSTAT_INC from a constinit constructor (PreStaticInit) on a fresh thread does not abort and increments the slot correctly; the count survives into PostStaticInit's first merger pass via the open-addressing slot the merger walks regardless of perfect-hash state. Acceptance criterion G-extra (added to §17.7): "XSTAT_INC from a constinit constructor (PreStaticInit) on a fresh thread does not abort and increments the slot correctly; the count survives into PostStaticInit's first merger pass."

11.1 Public API — FString

SSO layout (fix M-1, M-6, M-16, B-M4, B-MIN1; re-derived cleanly in Rev 3 fix M2). FString is a 64-byte struct (one cache line on every supported target). Byte 63's role is uniform across both modes: its high bit is the discriminator. In SSO mode the remaining bits carry the byte length (0..47 fits in 6 bits with 1 bit left over for a future flag). In heap mode the byte-length field lives at bytes 8–15; byte 63's remaining bits are reserved. There is no "shadow" overlap between the two layouts — the 64-byte storage is reinterpreted entirely by mode. The SSO threshold of 47 usable bytes is tuned to cover the 90th percentile asset-path workload (~80–120 bytes); paths exceeding 47 bytes go to heap by construction, which is unavoidable in the engine's working set (a measurement plan for Foundation Prototype samples the actual distribution and re-tunes if the 90th-percentile assumption proves wrong).

11.1.4 Discriminator encapsulation (Rev 3 fix M2)

User code NEVER reads the SSO/heap discriminator directly. FString::IsInSso() is a private helper used internally by the FString implementation (and by the IL2CPP transpiler for the interned-literal layout stability guarantee in §11.1.5); it is not part of the public surface. The discriminator's location (byte 63, high bit) is an implementation detail that is documented here for ABI auditing but is not contractually fixed for user-code observation. Any future widening of the discriminator (e.g., to two bits to encode a third mode) is a non-breaking change for user code because no user code observes the bit pattern. The public API exposes only mode-agnostic accessors: LenBytes, LenCodepoints, ByteAt, CodepointAt, etc. The ABI locks (sizeof(FString) == 64 and alignof(FString) == 16) are the only guarantees that downstream callers may rely on.

11.1.5 XCSharpString IL2CPP transpilation handle (NEW)

Per Contract Rev 13.7 §6.1, the IL2CPP boundary lowers C# string to a value-type handle:

struct XCSharpString {
    const FString* m_storage;    // points at an interned FString in .rodata OR
                                 // at a transient FString cached for the call.
};

static_assert(sizeof(XCSharpString)  == sizeof(void*), "XCSharpString is pointer-sized handle");
static_assert(alignof(XCSharpString) == alignof(void*), "XCSharpString natural-aligned handle");

Interning + pointer identity contract.

  • C# string literals compile to constinit const FString objects placed in the DLL's .rodata segment. XIL2CPP emits these from the IL string-literal table at transpile time; the build is a hard error if two distinct C# literals would resolve to the same address (which would break ReferenceEquals).
  • SSO/heap discriminator stability: for an interned literal, the FString's SSO-or-heap discriminator is stable across hot-reload sessions. .rodata addresses do not change within a given DLL revision; an interned literal that was SSO before a reload is SSO after a reload (and vice versa), so the discriminator does not need to be inspected at the IL2CPP boundary.
  • Pointer-identity guarantee for nameof: ReferenceEquals(nameof(X), "X") is a build-time emit guarantee from XIL2CPP. The transpiler resolves both sides to the same .rodata FString and emits a single pointer compare. A unit test in Tests/IL2CPP/StringInternIdentity sweeps 1000+ literal pairs across two DLLs and asserts pointer identity holds.
  • User-code surface: XCSharpString never appears in user code directly; it is the IL2CPP transpilation target for C# string. C++ code that wants to interact with a C# string sees a const FString& (the storage pointed to by XCSharpString::m_storage) and treats it as an immutable view. Mutation of an interned literal is undefined behaviour (the storage is const in .rodata).

UTF-8 semantics (locked answer to brief item 1):

  • s[i] is not provided. The C# transpiled form uses CodepointAt(i), O(n) per Contract §6.4. Sim-path TUs are forbidden unless annotated [XFunction(SimPathStringIndexOK = true)].
  • LenBytes: O(1) byte count.
  • LenCodepoints: O(n) first call; cached afterward (O(1)). Cache invalidated on any mutation.
  • Iteration: per Contract §6.4, the Codepoints() iterator is the recommended idiom.
  • std::string interop: implicit constructor from std::string (assumed UTF-8); explicit constructor FString(s.c_str(), s.size()).
  • Win32 wide-char syscalls: via FUTF16String escape hatch — conversion at the syscall boundary, never silent. Bare std::wstring is banned via a clang-tidy rule shipped with the engine.

11.9 Hash library (fix A-M8 hash portion, A-M19)

XCore-4a ships a small, vendored hash library covering the three hash kinds used internally and exposed for downstream consumers. Each function takes (const void* Data, size_t Length) and returns either a std::array<uint8_t, N> digest or a primitive. All three are sim-path-safe; the determinism contract is non-negotiable, so non-sim-path SIMD acceleration paths are explicitly excluded.

namespace XCore::Hash {

// BLAKE3-team/BLAKE3 vendor at known revision; 256-bit content hash.
// Sim-path-safe; bit-exact across platforms. Used by leak-tracker shadow-table
// chains, FText loctable BLAKE3 header, XStat side-table generated-header keying.
std::array<uint8_t, 32> BLAKE3(const void* Data, size_t Length) noexcept;

// xxHash vendor at known revision; 64-bit fast hash.
// SCALAR FALLBACK ONLY — no SIMD code paths. The vendored fork strips the
// XXH3_SIMD_* paths to preserve bit-exactness across architectures. Used
// internally by TMap and TSet (sim-path-safe when the fixed zero seed is honoured).
uint64_t XXH3(const void* Data, size_t Length, uint64_t Seed = 0) noexcept;

// Hand-rolled CRC-32C (~30 LoC; Castagnoli polynomial 0x1EDC6F41).
// Sim-path-safe; used for legacy file-format checksums and FArchive integrity tags.

} // namespace XCore::Hash

Trade-off (locked). Scalar XXH3 is ~30% slower than SIMD XXH3 on x86_64. The performance gap is accepted because bit-exactness across Win64-x86_64 / Linux-x86_64 / Android-ARM64 is a load-bearing replay-determinism contract; a TMap built on a SIMD-XXH3-x86_64 host that replays on Android-ARM64 with a different hash output would have different iteration order, different probe sequences, and (in worst case) different collision behaviour. The trade is non-negotiable.

TMap performance acceptance bar (revises §5.6). "TMap lookup meets-or-beats abseil flat_hash_map's scalar-hash configuration." The gap to abseil's SIMD-XXH3 configuration is the cost of bit-exactness, not the cost of the hash-map algorithm; the algorithm-vs-algorithm comparison (SwissTable + scalar XXH3 against abseil + scalar hash) is what XCore-4a commits to.

Shadow-table sizing (fix A-MIN5). The shadow table is a per-tag chained hash map with bounded chain depth = 16 (warning logged at first chain that reaches 16 in a given table; subsequent overflow chains are absorbed but counted into a "skipped-attribution" diagnostic). The max-live-allocation default is 10 M entries, sized against Master Plan §2 Memory budget (Quest 3 4 GB RAM, typical 400-byte average allocation: 10 M × 400 B = 4 GB attribution coverage). On overflow the table evicts the oldest entry (LRU); an eviction emits a single warning of the form "shadow table overflow at N allocations; oldest entries forgotten" and increments a leak-attribution-loss counter that the captured report surfaces. Per-platform stack-walk depth is fixed at 24 frames across Win64 / Linux / Android, matching the FStackBucket::Frames array length in §12.1.

13.2 Threading / Determinism / GC

Macros only; no runtime state. The XGC_WriteBarrier declaration is a single ABI-stable extern that XCore-4b implements; the XCore-4a build links against a weak-symbol no-op stub that does nothing, so the binary can stand alone without XCore-4b at integration time.

13.3 Divergences from UE

Clean superset of UE's FORCEINLINE / check() macros. The main divergence: XPACT_CHECK in Shipping is ((void)0), not __assume(Expr). The Prime Directive forbids silent corruption that would arise from a check expression getting wrong-branch-pruned (UE's checkSlow uses __assume; XPact does not). XPACT_ASSUME is the explicit branch-pruning macro for the rare site where we genuinely know the invariant, and where any error is the developer's, not the user's.

13.4 Test strategy

  • Compile-test every macro under each TargetConfiguration on each platform.
  • XPACT_CHECK fails in Debug; logs + aborts in Dev; is no-op in Shipping (verified by binary lacking the check's expression string in .rdata).
  • XPACT_DEPRECATED triggers warning on use.
  • XGC_WriteBarrier resolves to the weak-symbol stub in an XCore-4a-only build; replaced cleanly by the XCore-4b real intrinsic at link time.

Vendor Sleef-3.6+ (latest; no-FMA mode); integrate via XSimPathMathOverrides.h's #include block aliasing ::sqrtf -> Sleef_sqrtf_u10, ::sinf -> Sleef_sinf_u35, etc. The expanded contract covers four sub-items:
    • License. Sleef-3.6+ is BSL-1.0 (Boost Software License). This is aligned with Master Plan ThirdParty inventory's BSL-1.0 entry for the bit-exact transcendental library. The license is verified at vendoring time by checking Engine/Source/ThirdParty/Sleef/LICENSE.txt against the upstream Sleef release; a license-text mismatch is an XBT build error.

The canonical tier for sin, cos, tan, atan2 is u35 (35 ULP max error) — cheaper than u10 by a measured ~1.5×, and trig errors do not accumulate in a typical Verlet step (they appear as a constant phase offset that is bit-exact across platforms because the same Sleef path runs on all three). The tier choice is locked at the override-header level; a sim-path TU that wants u10 trig must opt in explicitly via a per-call alternate alias (not part of XCore-4a's sim-path overlay).
    • Build-config flags. Sleef's CMake gates no-FMA via -DSLEEF_BUILD_INLINE_HEADERS=ON plus --ffp-contract=off plus excluding the _finz_ (fast-math-finite-only) and *_fma symbol variants from the vendored amalgamation. Critical: on AArch64, the vendored amalgamation uses the pure scalar variants — NEON's FMA cannot be disabled at the instruction-set level (the FPU is FMA-by-default on ARMv8). Even with --ffp-contract=off, vectorised NEON kernels may still emit fmla, fnmla, or vfma instructions. The scalar-only constraint on AArch64 is the price of bit-exactness; the sim path's measured cost on Quest 3 is documented in the perf-bar test in §17.3. On x86_64 the SSE2 path is used (sim-path is capped at SSE42 per Contract Rev 13.7 §4.2; no AVX, no FMA via that route).

Acceptance criteria C2 + C4 + C-extra (§17.3) gate on this step; the XPACT_SIMPATH_PROVISIONAL=1 build flag (documented in §6.3) must be removed before Foundation Prototype merges.

15. Hot-Reload Compatibility (cross-cutting)

Per Contract Rev 13.7 §7.1 and the Master Plan Hot-reload commitment row, XCore-4a maintains the following invariants:

  • Stable vtable layouts. Types with virtuals (IConsoleVariable) ship with static_assert(sizeof(T) == X) at every revision. Virtual methods are append-only; existing slot ordering never changes. Removal or reorder triggers an explicit ABI version bump.
  • Stable exported symbol names. All public functions use Itanium-style mangling (Contract §1.4 / §2.2). XCore-4a is C++ source; the compiler-derived mangling is locked by the same rule that locks the Itanium scheme. XPACT_MANGLING_SCHEME_TAG in Section 13 is the single source of truth.
  • No constexpr-only definitions that prevent patch-DLL link. Every public API has an out-of-line definition in XCore/Private/. Inline definitions are limited to small accessors and templates.
  • Non-moving GC compatibility. XCore-4a containers register XGCRootSpans for XObject-holding instantiations. The collector (XCore-4b) is non-moving; XObject pointers stay valid across collections. The container's job is to keep the registered span describing the current live buffer; nothing more.
  • Layout-frozen sentinel. Every GC-aware container type carries static constexpr bool x_container_layout_frozen = true via the X_DECLARE_GC_AWARE_CONTAINER macro (Section 13); XLiveCoding's patch-validation pass uses this sentinel to gate the Contract §3.7 layout-equality check before accepting a hot-reload patch.
  • ABI tag static_asserts. The three ABI tags (XPACT_GC_ROOT_ABI_TAG, XPACT_EXCEPTION_ABI_TAG, XPACT_MANGLING_SCHEME_TAG) plus the CVar vtable tag (XPACT_CVAR_ABI_TAG, fix M-9) are emitted as static_asserts in XHT's per-.gen.cpp output; XHT validates the active tags against the manifest's TargetInfo ABI envelope on every build. A drift between the manifest and the live runtime fails at compile time, not at hot-reload time.
  • Reserve-trailing-virtuals pattern (fix M-9 generalised). Every public virtual interface that XCore-4a defines (currently IConsoleVariable; future analogues in XCore-4b, XTaskGraph, the renderer) declares a fixed count of trailing reserved virtual slots (typically 4). Adding a real virtual into a reserved slot is a MINOR ABI bump (the corresponding XPACT_*_ABI_TAG string bumps; runtime hot-reload remains compatible because the slot was always there). Consuming all reserved slots + needing more is a MAJOR ABI bump (full engine restart required, no in-session hot-reload). The pattern is mandatory for every interface that the engine commits to keeping vtable-stable across rev boundaries. The reserved-slot implementations are no-op inline functions; their existence pads the vtable to the committed size without runtime cost on un-used reserved slots.

16. Engineering-Principles Compliance Summary

The concrete ways XCore-4a is better than UE Core, in terms of the engineering principles document and the master plan's "absolute stability / capability / performance" mandate:

  1. Mandatory allocator tagging. Always-on leak attribution; UE's LLM is opt-in and routinely missing on hot paths.
  2. One allocator, not four. Removes the runtime-allocator-selection footgun; preserves replay-bit-exact across all targets.
  3. Sim-path determinism is a compile-time invariant. Sim-path TUs cannot call libm (header poisoning), read wall-clock time (deprecation), or use s[i] on FString (Contract §6.4 error). Failures surface at the call site, never at runtime.
  4. Container GC integration is partial-template specialization. Zero-cost for TArray<int>; full span protocol for TArray<XActor*>; nesting works via move-propagation. UE relies on reflection to mark slots; XPact does not need reflection at System 3.
  5. UTF-8 throughout. Disk-size + Vulkan + JSON + Linux/Android-syscall wins; UE's UTF-16 is a legacy footgun that costs per-syscall transcoding.
  6. FRotator ↔ FQuat conversion is explicit. Eliminates UE's #1 rotation-bug source. FRotator stays in the API for designer ergonomics but is never silently converted.
  7. FMatrix row-major. Matches the modern math / C# convention; C# interop is simpler.
  8. FVector is float, with explicit large-world type. Quest 3 cache + GPU bandwidth dominate; the rare large-scene case is forced to be explicit at the type level.
  9. Stat shards merged once per frame. Avoids UE's CAS-per-Inc cost; compile-time stat IDs avoid the FName dependency that blocks XCore-4a.
  10. CVar static-init ordering is gated. UE's read-during-static-init race is closed; "where did this CVar come from?" is queryable in Dev.
  11. Five-level SetByPriority cascade. Sufficient for every realistic case; 11 levels of UE noise removed.
  12. Header poisoning over "be careful" comments. Sim-path discipline surfaces as compile errors, not runtime divergence.
  13. Mandatory ABI tags as static_asserts. Drift between XBT's manifest and the live runtime fails at compile time.
  14. Three platforms, three concrete classes. UE's 28 platform-subclass surface collapses to the platforms XPact actually targets.
  15. Threading primitives have no virtuals. POD wrappers around OS handles; hot-reload-safe without ceremony.
  16. Mandatory phase ladder (Rev 2). Every public API that depends on PostStaticInit-or-later state gates on EngineInitPhase(); no implicit static-init order races. UE silently sees defaults from cross-TU static-init reads.
  17. TLS module-safe (Rev 2). Hot-reloadable DLLs route TLS through XPACT_TLS_MODULE_SAFE rather than raw thread_local; no thread_local-in-unloadable-DLL footgun.
  18. GC write-barrier ordering locked (Rev 2). Pre-store barrier semantics with memory_order_release on the card mark; no marker-vs-mutator race.
  19. 64-bit FStatId hash (Rev 2). Zero collision risk vs UE's 32-bit name hashing (1-in-4-billion per pair).
  20. No-default atomic memory_order (Rev 2). Every FAtomicInt32/64/Ptr call site specifies; no accidental seq_cst on ARM64 (10–50× cost cliff hidden).
  21. FMutex non-recursive for condvar (Rev 2). Concept-constrained FConditionVariable::Wait rejects FCriticalSection at compile time; closes the pthread_cond_wait-with-recursive-mutex UB pairing.
  22. Bounded MPSC for allocator-reclaim (Rev 2). TBoundedMpscQueue<T, N> with fixed ring buffer + back-pressure; no per-enqueue allocation; sim-path-deterministic allocator.
  23. Typed cached CVar handle (Rev 2). TConsoleVariableHandle<T> reduces a CVar read to a single atomic load; no per-frame string-walk through a name-keyed map.
  24. 110% UE Binned3 perf bar (Rev 2). XPact's tuned Binned3-descendant measurably faster than UE's on small-allocation workload (legacy Binned2 fallback paths removed).
  25. SwissTable-style TMap (Rev 2). Open-addressing + SIMD probe groups + control bytes; matches abseil flat_hash_map's algorithm (scalar XXH3 for bit-exactness).
  26. std::hardware_destructive_interference_size (Rev 2). Correct cache-line padding throughout cross-thread-shared data structures; falls back to platform-correct constant when the standard value is unavailable.

18.5 Deferred subsystems (Rev 3 Round 2 audit FIX-R2-MED-NEW-4/5/6)

XCore-4a is the foundation layer; several adjacent UE subsystems are deliberately deferred to higher-layer modules so the foundation stays minimal and the layering is enforceable. The deferrals are documented here so callers do not search the XCore-4a surface for a missing subsystem.

Deferred surfaceUE sourceXPact target layerPhase 1 substitute
FRunnable / FRunnableThread / FThread family Engine/Source/Runtime/Core/Public/HAL/Runnable.h, RunnableThread.h, HAL/Thread.h XTaskGraph (Layer 2) or a follow-up XCore-4c phase — whichever lands the higher-level threading abstractions first. XCore-4a's HAL ships the primitives (FAtomicInt32/64, FMutex, FCriticalSection, FRWLock, FConditionVariable, TBoundedMpscQueue); callers needing a long-running worker thread compose those primitives directly until XTaskGraph lands. The deferral is by design (Prime Directive: ship a focused HAL, defer higher-level scheduling).
FOutputDevice / structured logging surface Engine/Source/Runtime/Core/Public/Misc/OutputDevice.h, OutputDeviceConsole.h, UE_LOG family XLog (Phase 2) per Master Plan §3 L1. XCore-4a's HAL uses std::fprintf(stderr, ...) for diagnostics in the absence of XLog. This is the documented Phase 1 baseline; failure modes (allocator OOM, lock-discipline violations, leak-tracker output) print to stderr directly. The plain-C path is chosen deliberately to avoid bootstrap-cycle hazards (XLog cannot be a dependency of the allocator that XLog itself uses). Phase 2 swaps stderr for the XLog structured surface without changing the call sites.
XInsights telemetry hookups (allocator fragmentation gauge, GC pause-time histogram) UE's Insights / TraceLog family (Engine/Source/Runtime/TraceLog/). XInsights (Master Plan §2a Engine-telemetry row). XCore-4a's allocator (FMallocBinnedX) and the GC declarations (XGCDeclarations) include comment blocks marking the XInsights hookup points; the telemetry callbacks are weak-symbol stubs that XInsights replaces at link time. The recursion hazard documented in FMallocBinnedX.h §B9 / FMallocBinnedX.cpp:40-78 (telemetry callbacks must not re-enter the allocator) is the load-bearing constraint that locks the deferral.

None of the three deferrals masks a correctness gap (Prime Directive § "When Phase 2 Deferral Is Legitimate"). The dependencies (XTaskGraph, XLog, XInsights) genuinely do not exist yet; the opt-out paths (compose primitives, use stderr, use weak-symbol stubs) are correct in the absence of those subsystems; and the deferral is documented at the same revision as the surfaces being deferred from. New code introduced after Phase 1 that needs FRunnable / FOutputDevice / XInsights must land the dependency or pick a documented alternative; "FRunnable doesn't exist yet" is NOT a reason to ship a stub.
