Rev 8 (Round-6 Phase 1 hardening capture — UBT-comparison audit closure):

  • Section 5.2 / 5.4 — IExternalAction.DependencyListFile field added. A new nullable FileItem property DependencyListFile ships on IExternalAction, defaulting to null in Phase 1. (FileItem rather than string keeps the field inside XBT's path-discipline contract: the file goes through the FileItem intern table and shares the same identity machinery as every other prerequisite / produced item.) Phase 2 populates it from Clang's -MF output or MSVC's /sourceDependencies JSON; the planned CppDependencyCache (Section 15.3) will read the file and attach the resolved header set as recorded prerequisites for the action's next-cycle invalidation. The field is part of IExternalAction's reflected property set, so adding it rotated the internal ActionHistory.CurrentVersion digest (forcing a one-time recompute on first run after Round 6); it is not part of ContractSurface (only enums + an explicit element list drive the public ContractVersion), so ContractVersion.Current remains "13.2+b04ae3cc84cdd9f3". See Section 8.1 (ContractSurface exclusions) for the surface boundary.
  • Section 5.4 / 15.2 — ActionHistory.RecordContentHash now wired into ParallelExecutor. Pre-Round-6 the API was present but uncalled, so the rule-3 prereq-hash comparison in Addendum Section 4.3 returned IoHash.Zero for every raw source on every build and the actual invalidation signal silently flowed through FileItem mtime — a violation of Contract Section 2.1's mtime ban. Post-Round-6 the executor calls RecordContentHash(prereq, prereq.ContentHash) for every raw-source prerequisite after a successful action; producer-output prerequisites are skipped (the upstream's own RecordHash covers them). The Contract's mtime ban is now fully honored in Phase 1.
  • Section 5.3 — ActionGraph.Link conflict-detection extended. The duplicate-producer check now compares prerequisite-item sets and working directory in addition to command-version, so two actions producing the same file with the same command but different prereq sets or different cwd are correctly flagged as conflicting at link time instead of silently aliasing in the action-history partition.
  • Section 19.3 (NEW Rev 8) — Windows Job Objects. ParallelExecutor creates a job object on Windows and assigns every action subprocess to it with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. If XBT crashes (or is taskkill /F'd), every spawned child (cl.exe, link.exe, clang.exe, link, lld, ...) is killed by the OS automatically — no orphan-compiler reaping required by the next-startup sweep. Linux / Mac are no-ops at Phase 1 (POSIX process groups are an acceptable Phase 1 gap; the cancellation-grace path in Section 6.4 covers SIGINT, and orphan temp files are still swept at next startup).
  • Section 19.4 (NEW Rev 8) — antivirus-retry on Windows file operations. A new FileSystemOps.RetryOnTransientIOException helper wraps the 5 file-write call sites where AV scanners can intermittently lock newly-written or about-to-be-moved files: manifest JSON writer, manifest FBS writer, ActionHistory.Save, executor temp-file move/delete, and the PCH wrapper write. The retry schedule is [100ms, 200ms, 1000ms, 5000ms] with exponential-then-bounded back-off; transient IOException is the only caught class (real I/O errors still surface immediately on the final attempt).
  • Section 19.5 (NEW Rev 8) / Section 22.x — proactive MAX_PATH validation on Windows. After the action graph is built, ActionGraph.CheckPathLengths() walks every prerequisite-item and produced-item full path and verifies it is ≤ 260 characters on Windows. Failure exits with code 71 (LinkFailed, the closest-fit code pending a dedicated PathTooLong mnemonic in a future Contract revision) and a diagnostic naming both the offending path and the action that referenced it. The check runs before any subprocess dispatch, so a violation is reported at the start of the build rather than partway through. See the Section 1.3 exit-code summary for the code-71 dual-meaning note.
  • Section 1.1 / 1.2 / 6.x — SingleInstance build mutex with -NoMutexWait flag. BuildMode acquires a named mutex XBT_Build_<HashOf(engineRoot+target+config+platform)> at the start of every build to prevent two concurrent XBT instances from racing on the same ActionHistory.bin partition file. Default behaviour: wait indefinitely for the other instance to release. New CLI flag -NoMutexWait (Phase 1 minor addition) causes the mutex acquire to fail immediately if held, suitable for CI agents that prefer fast-fail. Cross-platform: the mutex is OS-named so the same coordination works between two MSVC compile shells and the inevitable IDE-spawned background-builder. See Section 6.x for the failure mode.

Round-6 lands alongside Contract Rev 13.5's Section 10.3 IExternalAction code-listing update (adds the DependencyListFile field with the Phase 1 / Phase 2 framing), Section 13.1 exit-code-71 dual-meaning annotation, and refreshed cross-references in Section 0 pointing at the new Addendum Revision 4 closures. 0. Purpose, Scope, Tier Membership

XBT is the build orchestrator for every XPact build. It is the first system implemented after the Toolchain Contract (plan Section 4 Step 1), and every later system — engine, editor, studio plugin, project — is compiled by XBT. XBT is the analog of Unreal Engine's UnrealBuildTool (UBT), restructured to honour the foundational decisions locked in plan Section 2 and the seams locked in the Toolchain Contract (Rev 12).

XBT is delivered as a single C# .NET 8 self-contained standalone executable. It has no XPact runtime dependencies — it cannot reference XCore, XCoreXObject, or any engine type. The build artefact is a Win64 / Linux / Android-host-x86_64 binary plus a small set of data files (banned-API list, default toolchain table, contract-surface manifest used to derive ContractVersion, the bundled Manifest.fbs schema per Contract Rev 12 Section 10.2). XBT is invoked by developer scripts, by IDE delegation hooks (Rider, clangd), and by XAutomationTool's release pipeline. Roslyn is an optional dependency: it is loaded only when a module ships a .Build.cs escape-hatch descriptor (Section 3.6); pure-TOML projects never load Microsoft.CodeAnalysis.

Tier membership. Plan Section 3: "All inventory systems are Engine-tier (live in /Engine/)." XBT's source lives under /Engine/Source/Programs/XBT/. XBT is itself reusable across every Simgenics training product and every plugin, mirroring the engine's universal-reuse posture (plan Section 2 Folder structure row, Rev 6).

Position in the build pipeline. XBT drives the pipeline locked in Toolchain Contract Section 10.1: discovery and graph build, manifest emit (JSON + FlatBuffers sidecar per the bundled Manifest.fbs schema), concurrent XHT + XIL2CPP invocation, copyright validation, C++ compile actions, link. Every step is an action in XBT's action graph; XBT is itself the only tool that owns the graph. XHT (System 2) and XIL2CPP (System 6) are sub-tools XBT invokes, never the other way round.

What XBT does not own. It does not parse reflection markers (that is XHT's job, per Contract Section 7). It does not transpile C# (that is XIL2CPP's job, per Contract Sections 2, 3, 5, 6). It does not own GC root primitives (those are XCoreXObject's job, per Contract Section 3 — now the XGC_RegisterRootSpan / XGC_UpdateRootSpan / XGC_UnregisterRootSpan family per Contract Rev 11). It does not own runtime hot-patch dispatch (XLiveCoding's job; XBT provides hook seams only). It does not handle deployment, code signing, or symbol upload (XAutomationTool's job, plan Section 3 Layer 0). XBT's responsibility ends when the link step produces a well-formed binary that the next pipeline stage can pick up.

Phase awareness. XBT MVP is Phase 1 in plan Section 5 (MVP subset). The Phase 2 readiness items called out in this document — distributed execution, full Live Coding integration, advanced PCH, Visual Studio project files — are designed as no-cost stubs at Phase 1 so post-MVP work does not require XBT redesign. Section 5.1 reserves XActionType enum slots so adding Phase 2 action types does not break the field-set hash that auto-derives CommandVersion.

1.5 Output format (REVISED Rev 2)

Default output: human-readable progress to stdout, errors and diagnostics to stderr, structured JSON build log written incrementally to Intermediate/Build/<Target>/<Config>/BuildLog.json. Streaming JSON error channel (NEW Rev 2; see Section 21.2): in addition to the human-readable stderr stream, XBT emits a parallel one-line-JSON channel suitable for IDE / CI subscription. The channel is implemented either as a dedicated file descriptor (Linux/Android) or as stdout lines prefixed with a sentinel @@XBT-JSON@@ (Windows; the same on Linux when no FD is available). Subscribers read the JSON channel; humans read stderr; the two are content-equivalent at the diagnostic level.

Cancellation via Ctrl-C is graceful and deterministic: outstanding actions are allowed to complete or fail cleanly; partially-produced outputs follow the atomic-rename + temp-file convention pinned in Section 6.4 and Section 21.3; the build log records the cancellation event. This is a Phase 1 commitment and the analog of UBT's UseStartupTraceListener option, refined.

-WarningsAsErrors=false (NEW Rev 2): The default is true at the target level. Developers can override per build via the CLI flag; the override is logged into BuildLog.json so a build with warnings-as-errors disabled is recognisable from the log. The override is intentionally not exposed to .Build.toml — relaxing warnings-as-errors should be a developer-level deliberate act, not a module-level configuration.

3. Declarative Descriptors — .Build.toml / .Target.toml (REVISED Rev 3; declarative-first with Phase 1 Roslyn escape hatch)

Foundational decision (Rev 2, reaffirmed Rev 3). Rev 1 chose Roslyn-compiled .Build.cs, mirroring UBT. The Rev 2 audit identified two material problems: (a) cold start was dominated by Roslyn compile, even with per-scope caching; (b) the rules surface was unbounded — any .Build.cs could in principle read arbitrary files, fork processes, mutate global state. Rev 2 reversed the decision: 95% of modules are pure declaration in TOML; the remaining 5% that need conditionals use a tiny sandboxed expression language. Per Contract Rev 12 Section 9.6, the declarative-first surface is normative. Rev 3 restores the Phase 1 Roslyn escape hatch for modules that legitimately need full C# in their build descriptor (a corner the Contract retains for the cases the audit acknowledges may exist); see Section 3.6.

The expected payoff:

  • 50–100× faster cold start than Roslyn on a clean checkout (no MSBuild graph, no compile, no assembly load, no System.Reflection walks).
  • Bounded surface: a malformed or hostile .Build.toml cannot execute arbitrary code; the parser is data-only and the expression evaluator runs in a sandbox with explicit allow-listed names.
  • Stable across .NET SDK changes: no Roslyn version pin, no LanguageVersion tracking, no Microsoft.CodeAnalysis ABI risk.

  • /Engine/Plugins/<Plugin>/Source/<Module>/ — engine plugins.

3.3 The sandboxed expression sub-language — Bazel Starlark 0.10.0 pin (REVISED Rev 3 — Contract Rev 12 N3)

The 5% of modules that need conditional logic carry a sibling .Build.expr file. Per Contract Rev 12 Section 9.6 (N3), the expression language is the Bazel Starlark 0.10.0 specification (mirrored at ThirdParty/Specs/starlark-spec-0.10.0.md) with the deviations enumerated in the Contract. XBT.Configuration's evaluator implements the BNF grammar productions reproduced in Contract Section 9.6.

Deviations from Bazel Starlark 0.10.0 (enumerated per Contract; XBT enforces all):

  • (a) No file I/O. load, print, and any file-reading functions are banned. The interpreter has no concept of "file" in its API surface.
  • (b) No mutation of arguments. Functions are pure: no parameter mutation, no global state mutation, no side effects observable outside the return value.
  • (c) No recursion past depth 32. The interpreter caps evaluation depth at 32 frames; recursive function definitions parse but exceeding the call depth fails with a diagnostic (exit code 30).
  • (d) No string interpolation via %. Only the explicit .format() method on string is supported.
  • (e) No binary integer arithmetic. Bazel Starlark supports the full + / - / * / / / % / ** set on integers; the XPact subset omits all of them. Only the unary + and - operators on integer literals are supported (per StarlarkEvaluator.cs:867–883). The numeric protection is at the literal-parse boundary instead: integer literals are bounded by long.MaxValue / long.MinValue (parsed via long.TryParse at StarlarkEvaluator.cs:627) and over-range literals fail the build with the OutOfRange diagnostic at the literal's source location. Without binary arithmetic there is no overflow path to detect at runtime.
  • (f) Evaluation budget: 100,000 instructions per top-level expression. Exceeding the budget fails the build with exit code 30 and a diagnostic naming the expression and the budget.
  • (g) No def function definitions; the interpreter is pure-expression-plus-top-level-assignment. List / dict comprehensions are omitted for budget predictability (per Contract).

It has no System.IO, no System.Diagnostics.Process, no System.Reflection.Emit; static analysis at parse time rejects any reference to disallowed names. The evaluator is a pure function of (parsed AST, bound name map) → (TOML patch); it is deterministic by construction. The 0.10.0 spec commit is part of the contract by reference; a future re-mirror to a newer commit requires a manual ContractSurface.SemanticVersionTag bump (the spec bytes are not in the auto-derived ContractSurface; the hand-bump discipline covers substantive changes per Contract Section 10.2).

3.4 Caching (REVISED Rev 2)

Descriptor cache key is the BLAKE3 content hash of all .Build.toml + .Build.expr files. Never mtime. The cache is partitioned per scope (engine, per-plugin, per-project) so a project-tier edit does not invalidate engine-tier descriptors. A scope cache hit skips the parse, expression evaluation, and merge entirely.

Cache entries are stored at Intermediate/Build/Descriptors/<Scope>.<Hash>.bin with a sidecar JSON index. Invalidation rules:

  • Any input .Build.toml or .Build.expr content hash differs → reparse + re-merge.
  • Any input .Target.toml content hash differs → reparse.
  • XBT binary hash differs → re-merge (handles XBT updates that change the merge semantics).
  • ContractVersion (auto-derived per Section 8.1) differs → re-merge.

3.5 Failure handling (REVISED Rev 2)

If a .Build.toml is malformed (TOML syntax error, unknown field, bad enum value, conflicting fields), or a .Build.expr references a disallowed name, XBT prints the diagnostic in file(line,col): error XBT030: message format and exits with the contract code 30 ("descriptor evaluation failure" — the contract Rev 11 renames the Rev 1 "RulesAssembly compile failure" to this). Multiple errors from a single scope are reported together so the user can fix them in one pass.

3.6 Phase 1 Roslyn escape hatch (REVISED Rev 3 — Contract Rev 12 contradiction resolution)

Rev 3 reversal. Rev 2 dropped the escape hatch to Phase 2. The Rev 12 contract reconciliation retains it at Phase 1 because the cost of carrying an optional dependency is small and the alternative ("wait for Phase 2 to do X") closes off legitimate uses the audit explicitly acknowledges may exist. XBT.html Rev 3 aligns with the Contract:

  • Phase 1 fallback. A module MAY ship a .Build.cs file alongside (or instead of) .Build.toml. XBT detects .Build.cs during the descriptor walk (Section 3.1) and falls back to Roslyn-compiled rules for that module only. Other modules in the same scope continue through the TOML + .Build.expr pipeline.
  • Roslyn dependency is optional in Phase 1. Microsoft.CodeAnalysis is referenced as a lazy-load assembly. The first observed .Build.cs in a build session triggers the load; pure-TOML projects never page Roslyn in. A Foundation Prototype build of an empty repo therefore pays zero Roslyn cost.
  • Cache parity. Roslyn-compiled .Build.cs output is cached by BLAKE3 content hash of the source file, identical to the model used for TOML descriptors (Section 3.4). Cache entries live under Intermediate/Build/Descriptors/<Scope>.<Hash>.bin. A .Build.cs whose content hash matches a cache entry reuses the compiled RulesAssembly without re-invoking Roslyn.
  • Failure handling. A Roslyn compile error fails with exit code 30 ("descriptor evaluation failure"; same code the TOML / .Build.expr path uses) and the MSBuild-style file(line,col): error CSxxxx diagnostic emitted by Roslyn is propagated unchanged.
  • Surface caveat. The .Build.cs surface is the same ModuleRules POCO documented in Section 4.2; the difference is only in how the POCO is populated (declarative merge vs. C# field assignment). Authors should prefer TOML+expr; .Build.cs is the escape hatch for genuinely-irreducible cases.

Should a more powerful Phase 2 escape hatch become necessary (a per-target opt-in to load a signed Build.Plugin.dll compiled out-of-band), it is additive to this surface and does not retire the per-module .Build.cs path.

4.5 SimPath constraints (REVISED Rev 3)

When SimPath = true:

  • FPSemantics is auto-promoted from Default to Precise. Explicit FPSemantics = FPSemantics.Imprecise on a SimPath module fails the build (banned per Contract Section 4).
  • PCHUsage must be NoSharedPCHs. If a SimPath module declares UseSharedPCHs or UseExplicitOrSharedPCHs, the build fails with exit 30 and a diagnostic. SimPath modules cannot participate in SharedPCH because the SharedPCH would otherwise have to honour the sim-path math overrides for every consumer, and a consumer that is itself not sim-path would silently inherit the overrides through the PCH. The Rev 2 audit identified this as a correctness boundary.
  • .gen.h emitted into the same module is excluded from any SharedPCH (per Section 15.4) regardless of the PCH usage mode of other modules.
  • SimdLevel is clamped to ≤ SSE42 — any of None, SSE2, SSE42, or Default (which resolves to SSE42 for SimPath). SimdLevel.AVX / AVX2 / AVX512 on a SimPath module fails the build with exit 41 (banned-flag check) — the higher SIMD levels enable FMA paths that violate determinism. On Clang, -mno-fma is also emitted as a belt-and-braces guard regardless of the chosen SimdLevel.

4.8 Unity-build determinism (NEW Rev 2)

With bUseUnity = true (default), source files in a module are clustered into unity TUs. UBT's Unity.cs is known to have a race in how it assigns files to buckets — XPact preempts this by locking the rule:

  1. Sort the module's source files by BLAKE3 content hash (ordinal comparison on the hash bytes).
  2. Compute bucket_count = ceil(N / max_files_per_bucket) where max_files_per_bucket = 16 by default. The bucket count is locked per module across a build session; it changes only when source-file membership changes.
  3. Assign file i (in the sorted order) to bucket i % bucket_count.
  4. Emit unity TUs <Module>.unity.<bucket>.cpp with includes listed in sorted-by-hash order.

The rule is purely a function of the file set and their content hashes — no mtime, no filesystem ordering, no environment dependence. Two builds of the same source tree on different machines produce identical unity TUs. The Rev 2 audit finding cites UBT's Unity.cs lines 32–44 as the divergence point this rule fixes.

4.10 StationRole compile-define propagation (NEW Rev 3)

The compiled DLL must know its StationRole at runtime so role-gated behaviour (e.g. the Trainee-station hot-reload prohibition per Section 16.4) can be enforced inside C++ code, not only at the build-graph layer. Rev 2 used StationRole to gate hot-reload action emission but did not surface the role to the compiled code. Rev 3 propagates it as a compile-time symbol:

  • On every compile action whose target type is Game, XBT emits -DXPACT_STATION_ROLE=Engineer (or Instructor / Trainee) as an MSVC / Clang preprocessor definition.
  • Engineer-station Editor builds also receive -DXPACT_STATION_ROLE=Engineer. The Editor target is the canonical Engineer authoring environment.
  • The symbol is added to PublicDefinitions at the target level so dependent modules see the same value through normal include propagation.
  • Server targets receive no XPACT_STATION_ROLE macro (the Server target does not run on a training station; Section 16.4 disables hot-reload unconditionally for Server).

The corresponding C++ surface in XCore declares an XStationRole enum with values Engineer/Instructor/Trainee and an XPACT_STATION_ROLE token-paste convention so that #if XPACT_STATION_ROLE == Trainee compiles. The macro is part of the target's CacheKeyComponents (Section 5.2) so changing StationRole invalidates the compile cache. Per Contract Rev 12 Section 4.5, the per-target settings struct already carries StationRole to XHT and XIL2CPP; Rev 3 extends the same value to native compile actions.

ActionGraph.Link() builds the producer map from FileItem → IExternalAction (every produced FileItem must have exactly one producer; duplicate-producer errors are caught here). CheckForConflicts() verifies that no two actions produce the same FileItem with conflicting identity; Rev 8 extends the comparison from CommandVersion-only to the full tuple (CommandVersion, sorted PrerequisiteItems, WorkingDirectory). Two actions that produce the same path with the same command but different prereq sets or different cwd are now flagged as conflicting at link time instead of silently aliasing in the action-history partition (the latter would produce a stale cache hit whose recorded prereqs match neither emitter's expected invalidation surface). DetectActionGraphCycles() runs a DFS for cycles; on detection, the cycle is printed and the build exits 80. Sort() produces a topological order with a deterministic tiebreaker (by CommandVersion) so the same graph yields the same execution order across machines.

CheckPathLengths() (NEW Rev 8 — Round-6 proactive MAX_PATH validation). After the graph is linked, on Windows CheckPathLengths() walks every prerequisite-item and produced-item FullPath and verifies it is ≤ 260 characters (Win32 MAX_PATH). A violation exits with code 71 (LinkFailed per Section 1.3 / Contract Section 13.1 — reused as the closest-fit code pending a dedicated PathTooLong mnemonic in a future Contract revision) and a diagnostic naming the offending path + the action that referenced it. The check runs before any subprocess dispatch so the violation is reported up-front instead of mid-build from a downstream cl.exe failure with a cryptic stderr. Non-Windows builds skip the check entirely (Linux and Android filesystems have no comparable per-path limit at the kernel level relevant to XBT's intermediate trees). The check complements the ModuleRules.ShortName escape hatch documented in Section 18.3: ShortName is the developer-side mitigation (shorten the module's path component); CheckPathLengths is the build-time fail-fast that catches the case where ShortName was not applied to a path that needs it.

BuildSubset(IEnumerable<ModuleName> roots) (NEW Rev 2 — see Section 16.6 for the Live Coding use case): returns the action sub-graph rooted at the given module set, validated and topologically ordered, suitable for executor dispatch. The method ships in Phase 1; Phase 2 XLiveCoding will use it for incremental compile-only passes.

5.4 ActionHistory (REVISED Rev 8 — RecordContentHash wired into the production executor)

Per Contract Section 10.3: incremental rebuilds. XBT's ActionHistory is a binary-serialised map from FileItem → IoHash(commandVersion + responseFileContents + CacheKeyComponents + relevant flags), partitioned by CacheBucket so two unrelated buckets can be read/written in parallel.

CurrentVersion is derived from a hash of the IExternalAction field set — specifically, BLAKE3 of the property names and types in alphabetical order (the implementation pre-sorts the reflected properties with StringComparer.Ordinal to insulate the hash from Roslyn / .NET MetadataToken ordering changes; see Addendum Section 5.5). Any schema change to IExternalAction changes the version automatically; UE's ActionHistory.CurrentVersion = 3 manual bump is gone (footgun #8). The reserved XActionType slots (Section 5.1) preserve the hash across Phase 2 enum additions. Round 6 rotated this digest when DependencyListFile was added to IExternalAction (Section 5.2); the rotation is internal to the schema-version digest and does not bump the public ContractVersion.

Prerequisite content-hash recording (REVISED Rev 8 — Round-6 wire-up; Contract mtime-ban closure). The invalidation rules in Addendum Section 4.3 expect ActionHistory to carry a recorded ContentHash for every raw-source prerequisite. Pre-Round-6, the recording API (ActionHistory.RecordContentHash(FileItem, IoHash)) existed but the production executor never invoked it, so the rule-3 lookup returned IoHash.Zero on every build and the actual invalidation signal silently flowed through FileItem mtime — a violation of the Contract Section 2.1 mtime ban. Round-6 wires the recording loop: after a successful action, ParallelExecutor calls RecordContentHash(prereq, prereq.ContentHash) for every entry of PrerequisiteItems classified as a raw-source file. Producer-output prerequisites are skipped (the upstream action's own RecordHash covers them when the upstream succeeds; double-writing would be redundant and would race with the upstream's atomic write). The Contract's mtime ban is now fully honored in Phase 1; the change closes the gap that Addendum Revision 3 Section 10 item 1 implied (and that Revision 4 marks CLOSED as item 1a).

Why object, not IExternalAction? The cast-at-link-time pattern is intentional. XBT.Configuration declares IBuildHook alongside ModuleRules (which a .Build.toml populates); XBT.ActionGraph declares IExternalAction and depends on XBT.Configuration to consume ModuleRules when linking the graph. If IBuildHook.CreateAction returned IExternalAction directly, XBT.Configuration would have to reference XBT.ActionGraph — producing a project-level cycle. The object return + cast-at-link-time keeps the dependency direction acyclic; the action-graph layer's cast both validates the return and surfaces a clear exit-81 diagnostic on non-conforming returns. The cost (one cast per hook invocation) is paid once per build at link time, not per action execution.

Action type reuse. Hooks do not get a dedicated XActionType value. The action a hook returns from CreateAction reuses an existing action type that matches the work — CompileCppAction when the hook compiles a generated file, LinkModuleAction when the hook links auxiliary artefacts, WriteManifestAction when the hook emits structured manifest data, etc. The action's Provenance_Module records the hook's module so build-log attribution is preserved (Section 21.5). If no existing action type maps cleanly to the hook's work, the hook should produce a WriteManifestAction-like generic action whose command is the hook's binary — new bespoke action types require a Phase 2 enum reservation (Section 5.1).

Hook declaration. Hooks are registered through XBT.Configuration's descriptor system — a module's .Build.toml can declare a hook by name; XBT resolves the name to a registered C# implementation, instantiates it, and appends the instance to ModuleRules.PreBuildHooks or PostBuildHooks (Section 4.2). There is no path that lets a .Build.toml declare an arbitrary shell command. The same hook interface is exercised by XBT.Tests integration tests (Section 22.6).

Validation. A hook with no declared inputs is a build-graph anomaly that XBT flags as a warning — the hook will run on every build and never cache. A hook that touches an output file not in OutputFiles fails the build with exit 81. A hook that fails to produce a declared output also fails with exit 81. The Contract's reference anti-pattern (UE's CustomBuildSteps.cs shelling out arbitrary strings) is rejected entirely.

6. Executor (Phase 1 = local only)

Phase 1 XBT ships with a single executor: ParallelExecutor. Sized by default to Environment.ProcessorCount; configurable via -Workers=N. Worker threads pull from a job queue; each job is one IExternalAction. The queue is sorted before dispatch by CommandVersion so dispatch order is deterministic (mirrors UBT footgun #6 fix at the executor level).

6.1 Scheduling

Topological order from ActionGraph.Sort respects the dependency graph; within a single ready-set, the dispatcher picks actions in CommandVersion order to keep ordering deterministic for log diffing and reproducibility tests. Actions with Weight > 1 are dispatched only when at least Weight workers are free.

6.2 Failure isolation (REVISED Rev 2)

Each action runs in its own subprocess (or in-process when both XHT and XIL2CPP are loaded as libraries — XBT picks subprocess for Phase 1 simplicity, in-process is a Phase 2 perf option). A non-zero exit code captures stderr to the build log and emits a streaming JSON error record (Section 21.2) and marks the action failed. Failure propagates: dependent actions are skipped, the build's final exit code reflects the worst category encountered (per Contract Section 13). One action's failure never corrupts another's outputs: each action writes to a temp file <output>.tmp.<pid>.<actionid> in the same directory as the final output (same-volume guarantee, atomic rename), and atomically renames into place on success. On failure, the temp is deleted.

6.3 The CanExecuteRemotely flag

Present on IExternalAction (Rev 10 rename from bCanExecuteRemotely — un-prefixed per code reality at IExternalAction.cs + Contract Section 10.3) but ignored at Phase 1. Phase 2: XPactBuildAccelerator (plan Section 3 Layer 0 Rev 7) will consume the flag and dispatch eligible actions to a worker pool of remote machines. XBT must not preclude this; the executor surface in XBT.Executor is an interface, not a single class, so Phase 2 can register a second implementation alongside ParallelExecutor.

6.4 Cancellation + atomic-rename contract (REVISED Rev 2 — audit finding #1)

Rev 1's Sections 6.2, 6.4, and 21.3 contained mutually contradictory rules for what happens to in-flight files when XBT is killed. Rev 2 pins one rule across all three, derived from the audit:

  1. Temp-file naming. Every action that produces a file <output> writes first to <output>.tmp.<pid>.<actionid> — pid is the OS process id, actionid is a monotonic counter scoped to the run. The temp lives in the output's own directory, never %TEMP% or /tmp. The same-directory constraint guarantees the final rename is on the same filesystem volume; cross-volume rename is non-atomic on Windows and a known UBT race.
  2. SIGINT path. SIGINT installs a CancellationToken. Outstanding actions are given a 5-second grace period to complete cleanly. After grace, in-flight subprocesses are killed; their temp files remain on disk (uncleaned because the killed subprocess could not run its delete-on-fail). XBT's main process catches the cancellation, sweeps temp files matching *.tmp.<mypid>.*, and exits 130.
  3. taskkill /F path. XBT's main process is killed outright. Temp files for this pid remain orphaned. There is no cleanup opportunity for this build.
  4. Orphan sweep at next startup. Every XBT startup begins with a sweep of the intermediate tree. Any *.tmp.<pid>.* whose pid is not currently running (queried via OS process-id lookup) is deleted. This guarantees no resource leak from a prior taskkill /F.
  5. Atomic rename. On Win64, MoveFileEx with MOVEFILE_REPLACE_EXISTING. On Linux/Android, renameat2 or fallback rename. The semantic is: the final output never appears half-written; readers see either the pre-existing file or the new one, never an intermediate state.

This rule applies uniformly to compile outputs (.obj / .o), generated headers (.gen.h), generated cpp (.gen.cpp), transpiled outputs (.cs.cpp), the manifest, the binary FlatBuffers sidecar, the build log, and the action-history files. Every writer in XBT.Core's atomic-file-IO surface enforces this naming convention.

6.5 SingleInstance build mutex (NEW Rev 8 — Round-6 concurrent-build coordination)

Two concurrent XBT processes targeting the same (engineRoot, target, configuration, platform) tuple race on a single resource: the ActionHistory.bin partition file (Section 5.4 + Addendum Section 5.1). The atomic-rename + per-partition-lock contract guarantees that any single writer's snapshot is well-formed, but two interleaved writers can each clobber the other's partition updates depending on dispatch timing. The pre-Round-6 reality was: most developer workflows happened to be single-build by convention, but the IDE-spawns-background-builder + developer-runs-shell-build pattern hit the race exactly when it hurt most (the developer's foreground build's ActionHistory updates were silently lost when the IDE's background build wrote out first).

The fix. BuildMode acquires a named OS mutex at the top of RunInternal:

// Per-instance mutex name derived from the build identity tuple
// (engineRoot, target, configuration, platform). Two builds with
// different identities (e.g. Editor + Game in parallel) do not collide.
string name = $"XBT_Build_{Blake3HexShort(engineRoot + target + config + platform)}";
using var mutex = new Mutex(initiallyOwned: false, name);

Default behaviour: mutex.WaitOne() blocks until the other holder releases. The lock is acquired before any action-graph work and released in the finally after ActionHistory.Save, so a holder's full build window is mutually exclusive. Two builds targeting different identities (e.g. Editor + Game in parallel on the same project) use different mutex names and proceed concurrently — the lock is per-build-tuple, not per-engine.

With -NoMutexWait (Section 1.1): mutex.WaitOne(TimeSpan.Zero). If the mutex is held, the call returns false and XBT exits with code 1 and a diagnostic naming the held identity and suggesting either dropping the flag (wait) or aborting the other build. Suitable for CI agents that prefer fast-fail over indefinite block on a stuck build.

Cross-platform: .NET's Mutex(initiallyOwned, name) maps to CreateMutex on Windows and to a POSIX named semaphore (/dev/shm-backed) on Linux + Android, so the same coordination works between two MSVC compile shells and between, e.g., a docker-compose build + a developer's host build. The mutex is intentionally OS-named (not file-locked) so a stale lock from a crashed XBT does not survive the OS reaping the process — the kernel releases the mutex automatically when its last referencing process exits.

Interaction with the orphan-temp sweep (Section 6.4): the mutex is taken after the orphan-temp sweep (which is purely read-only against the filesystem and safe to run while a holder owns the build mutex elsewhere). The two are complementary: the mutex prevents concurrent writers; the sweep cleans up after a prior crashed writer.

XResult RAII destructor (NEW Rev 3 — Contract Rev 12 M2). This guarantees correct teardown along the failure path where a callee wrote a success result and a subsequent operation throws before the function returns. The destructor body is identical across configs (Dev/Test and Shipping), so cross-config link is preserved. XBT does not need special handling — it ingests the .cs.cpp from XIL2CPP and compiles it like any other authored C++; the per-config exception-flag emission in Section 7 / Section 4 is what XIL2CPP relies on when lowering the destructor itself.

8.1 ContractVersion auto-derivation (REVISED Rev 5 — surface description aligned to implementation)

Rev 1 hand-typed "ContractVersion": "v1". Per Contract Rev 11 change #6 the value is auto-derived from a BLAKE3 hash of a canonicalised contract surface; any contract change that affects what XHT or XIL2CPP read produces a new ContractVersion automatically. The composite format is:

ContractVersion = $"{ContractSurface.SemanticVersionTag}+{StructureHash[0..16]}"
                  // e.g. "13.2+b04ae3cc84cdd9f3"

The canonical contract surface (the input to StructureHash) is defined by ContractSurface in Engine/Source/Programs/XBT/XBT.Manifest/ContractSurface.cs — the C# implementation is the source of truth. The surface is the union of:

  1. SemanticVersionTag — hand-bumped per Contract revision (currently "13.2"). The tag flows before the + separator so a textually-large but structurally-small Contract revision can still produce a new ContractVersion string.
  2. Every public enum declared in the Simgenics.XPact.XBT.Manifest namespace. ContractSurface.ReflectEnums walks the assembly at static-init, picks the public enums whose Namespace equals ContractSurface's, sorts them by name, and emits each member as name=ordinal sorted by ordinal. This is the "add an enum and it lands in the surface" property: a future SimdLevel rung or a new StationRole automatically rolls ContractVersion. Private / internal types are deliberately out of scope.
  3. Marker macros (ContractSurface.MarkerMacros) — the locked C++ reflection-marker vocabulary from Contract Section 1.1 in declared order. Adding / removing / reordering rolls the hash.
  4. Body-macro suffixes (ContractSurface.BodyMacroSuffixes) — the suffix table from Contract Section 1.3 in declared (composition) order.
  5. Mangling-rule example (ContractSurface.ManglingRuleExample) — the locked Itanium-ABI-style example string "XN1A1BE". Any grammar change must bump the example so the hash picks the change up.
  6. File-ID scheme (ContractSurface.FileIdScheme) — the per-file ID grammar from Contract Section 1.4.
  7. Exit codes (ContractSurface.ExitCodes) — the exit-code table from Contract Section 13, sorted by integer code at canonicalisation time (reordering the literal array does not change the hash; adding / removing / renaming any entry does).
  8. Action-type slot names (ContractSurface.ActionTypes) — every named action type in XActionType that is also enumerated in ContractSurface.ActionTypes. Post-Round-5a the surface enumerates slots 0–8, 13, and 16: the original Phase 1 emit set (slots 0–8) plus Tier2WholeProgramPass (slot 13) and BuildPluginManifestAction (slot 16), both of which Phase 1 can emit. Reserved slots (9–12, 14–15) are intentionally excluded from the hash so Phase-2 additions that land in those slots do not force a full rebuild of every existing target. ADDING a slot to ActionTypes (as Round 5a did for slots 13 and 16) does rotate the hash, which is the desired behaviour for slots that Phase 1 can emit — a rename on either name would otherwise be a silent contract drift.

The canonicalisation algorithm (ContractVersion.ComputeStructureHash) writes a deterministic UTF-8 line-based serialisation with NewLine = "\n" unconditionally (so the same source produces the same hash on Windows and Linux); the resulting bytes are BLAKE3-hashed and the first 16 hex chars become the StructureHash suffix. The full 32-byte hash is exposed via ContractVersion.StructureHash for diagnostics; the 16-char composite is what flows into the Manifest.ContractVersion field on disk and through XIL2CPP symbol mangling per Contract Section 2.

Notably NOT in the surface (intentional exclusions):

  • The Module / Manifest DTO field set in ManifestSchema.cs. The DTO shape is a derived view of the surface above; rolling its fields without rolling an enum / marker / exit code is a no-op from the contract's perspective. (A future audit may move the DTO into the surface; for now the policy is "surface = symbolic vocabulary + table-of-content, not the wire bytes that carry them".)
  • The FBS schema bytes (Manifest.fbs). Append-only changes to the FBS schema do not roll ContractVersion automatically — the Phase 1 discipline is that Subagent B updates ContractSurface.SemanticVersionTag by hand when the schema gets a substantive non-additive change.
  • IExternalAction's reflected property set (NEW Rev 8 explicit listing). IExternalAction's field shape is reflected by ActionHistory.ComputeCurrentVersion into the internal schema-version digest (Section 5.4); that digest is embedded in ActionHistory.bin and a mismatch on read invalidates every entry. It is not a member of ContractSurface: adding or removing a property on IExternalAction (such as Round-6's DependencyListFile field) rotates the internal schema digest but leaves ContractVersion.Current unchanged. This split is deliberate — the action-graph schema is an XBT internal evolution surface (consumed only by XBT's own ActionHistory), whereas ContractVersion is the cross-tool wire identity. The two move on different cadences.
  • Per-tool versions (XBT / XHT / XIL2CPP binary content hashes). These are part of the per-action cache key (Section 15.1) but not the contract surface itself.

For the current Contract revision (Rev 13.2 at this snapshot), the derived value is computed once at static-init by ContractVersion.Current and baked into every emitted manifest. A future Contract bump simply rebuilds XBT; the manifest reader's compatibility check still works because XHT / XIL2CPP compute the same hash from the same source.

8.4 JSON parse safety (REVISED Rev 3 — FBS verifier limits pinned)

The manifest is the protocol between XBT and IDE / subprocess invocations. A malicious or malformed manifest must not DoS the build agent. Rev 2 pinned reader options for every System.Text.Json manifest read; Rev 3 mirrors the same numeric limits explicitly on the FlatBuffers verifier (Section 8.5) so the JSON and binary paths share one safety budget.

// JSON path
var options = new JsonReaderOptions
{
    MaxDepth = 64,                       // hard cap on nesting; 8 is typical
    CommentHandling = JsonCommentHandling.Disallow,
    AllowTrailingCommas = false
};

// Plus, at the stream level:
const long MaxManifestBytes = 100L * 1024 * 1024;   // 100 MB hard ceiling
if (stream.Length > MaxManifestBytes) throw new ManifestTooLargeException(...);

// Per-string field limits (typical):
const int MaxStringField = 16 * 1024;     // 16 KB per field
const int MaxArrayCount  = 65536;         // 64K entries per array (modules, source files, etc.)

// FBS path — mirror of the JSON limits, expressed on FlatBuffers' Verifier
const int FbsMaxDepth        = 64;
const int FbsMaxBytes        = 100 * 1024 * 1024;   // 100 MB
const int FbsMaxStringLength = 16 * 1024;            // 16 KB
const int FbsMaxVectorLength = 65536;

Violations produce ManifestMalformedException → exit code 50. The FlatBuffers verifier is configured with these limits explicitly; the unchecked-reader path is never used for manifest reads.

8.5 Binary FlatBuffers sidecar (REVISED Rev 5 — plain filename, no hash component)

Tools read the binary sidecar; humans read the JSON. Both are emitted in lockstep from the same C# manifest object; their content is structurally equivalent. The schema file is normatively defined in Contract Rev 13.2 Section 10.2 and shipped at /Engine/Source/Programs/XBT/XBT.Manifest/Manifest.fbs as a Phase 1 deliverable. XBT's manifest emitter compiles the schema to C# at XBT-build-time via FlatSharp; XHT and XIL2CPP build readers from the same schema. The file_identifier is "XMFT" per the schema.

Emission paths and atomicity. On every successful build XBT writes both forms to deterministic paths:

  • Intermediate/Build/<Target>/<Configuration>/Manifest.json — the human-readable form.
  • Intermediate/Build/<Target>/<Configuration>/Manifest.fbs.bin — the FlatBuffers binary sidecar (plain filename; no content-hash component).

Each write uses the atomic temp-file + rename pattern from Section 6.4: write to <name>.tmp.<pid>.<guid> in the same directory, fsync, then File.Move(..., overwrite: true) for the atomic swap. Both forms are always current after a successful build; an external observer never sees a partially-written manifest.

Append-only versioning (Contract N4). XBT (writer) and XHT / XIL2CPP (readers) honour the schema's append-only discipline:

  • New fields are appended to the end of their table; never reordered, never deleted.
  • FlatBuffers default-value semantics fill in missing fields for older readers (an XHT compiled against schema version N reading a manifest written by an XBT using schema version N+1 sees defaults for the new fields).
  • Enum values are appended; never reordered, never deleted.
  • Removing a field or repurposing a slot requires a contract revision and a ContractStructureHash bump per Contract Section 10.2.

Why a sidecar (not a replacement): JSON remains readable in editors and diffable in version control; FlatBuffers is unreadable. Tools want fast parsing; humans want introspection. Maintaining both costs almost nothing because the C# DTO is the single source of truth.

Read precedence. When XHT or XIL2CPP starts, it reads Manifest.fbs.bin with the FlatBuffers verifier enabled and the limits from Section 8.4. The binary form is preferred. If the binary is missing or fails verification (a corrupted write, an out-of-sync write from an unrelated tool, etc.), the tool falls back to Manifest.json with the hardened reader options. Because both forms are written atomically from the same C# object on every build, the two are structurally equivalent at every observation point — there is no JSON-newer-than-binary tiebreak. If both forms fail verification, exit 50.

9.3 Cross-language compatibility

XHT reads both C++ headers (single-pass marker tokenizer) and attribute-marked .cs sources from the same module (Contract Section 1.1). It emits unified registration scaffolding so a single FClass entry can describe a type whose .h declares the C++ surface and whose .cs declares the C# surface. XBT does not need to participate in that — XBT only sees the manifest go in and the per-module outputs come out.

9.4 The XHT actions (REVISED Rev 2 — split into ParseHeaders + EmitReflection)

Per the Rev 2 audit, XHT's work splits into two action types so the executor can parallelise across modules at finer grain:

  • ParseHeadersAction: one per module. Prerequisites: every .h and .cs in the module + the JSON manifest + the binary FBS sidecar + XHT's own binary content hash. Produces: a per-module token-AST cache file under Intermediate/.../<Module>/<Module>.tokens.bin.
  • EmitReflectionAction: one per module. Prerequisite: the corresponding ParseHeadersAction's output. Produces: .gen.h per reflected header + .gen.cpp per reflected header + <Module>.init.gen.cpp aggregator + <Module>.gen.manifest. (Rev 9 correction: per-header .gen.cpp + per-module .init.gen.cpp aligns with UHT precedent and XHT.html Rev 2 Section 8.)

The split lets module B's ParseHeadersAction run in parallel with module A's EmitReflectionAction — useful when modules are large enough that parse-phase becomes a sequential bottleneck. The token-AST cache is also separately invalidatable: an edit that changes a header's reflection markers reparses only that module, not every module that includes the header.

Copy attempts in dependent C++ code fail at compile time with a clear error (the = delete diagnostic); XBT's compile-action infrastructure surfaces the diagnostic through the standard error CSxxxx / MSBuild-format pipeline and exits 70. No additional pre-compile check or build-graph plumbing is needed.

XBT forwards the platform's reproducibility flags to XIL2CPP via the manifest. XIL2CPP propagates these through to the generated C++ headers (e.g. predicating #line directives so cross-machine line-number consistency holds). The forwarded flags now include the full envelope in Section 19.1 (not just /Brepro).

10.4 Downstream compile

XBT then schedules a CompileCppAction for each transpiled .cpp exactly as if it were an authored .cpp. The transpiled headers participate in the include graph; the dependency cache covers them like any other header. From the C++ compile's perspective the file is indistinguishable from a hand-written one — that is the contract's intent.

10.5 The XIL2CPPAction

One action per module containing C# sources. Prerequisites: every .cs in the module + manifest (JSON + FBS) + XIL2CPP's own binary content hash + XCoreXObject's exported header surface (for the GC ABI emit, per Contract Section 3.1). Produces: transpiled .cpp/.h + a per-module transpilation manifest listing the inputs and produced outputs.

10.6 Concurrent XHT + XIL2CPP scheduling (REVISED Rev 2 — Contract Rev 11 #4)

Rev 1 implied a sequential order: XHT first, then XIL2CPP. Contract Rev 11 corrects this: the two run concurrently. XHT does not depend on XIL2CPP output; XIL2CPP does not depend on XHT output (their interleaved consumption happens at the compile step on the generated cpp files, which is downstream of both).

The action graph reflects this: EmitReflectionAction(M) and XIL2CPPAction(M) for the same module M are independent peers; their only common predecessor is WriteManifestAction. The executor schedules them in parallel within the available worker pool. This typically halves the latency of the prologue (the portion of the build before CompileCppActions can start).

10.7 Tier 2 classification sequencing (NEW Rev 3 — Contract Rev 12 N2)

Per Contract Rev 12 Section 5.2 (N2), XIL2CPP's Tier 1 / Tier 2 classification is a two-pass scheme. XBT orchestrates the sequencing:

  • Pass 1 — per-module, concurrent (mandatory MVP). Each XIL2CPPAction classifies functions purely from its own module's source. Cross-module callees are conservatively assumed Tier 1 unless the callee carries an explicit [XFunction(NoThrow = true)] annotation visible through XHT-emitted reflection metadata. The per-module action publishes its per-function tier assignments to Intermediate/Build/<Target>/<Configuration>/TierTable.partial.<Module>.json. Pass 1 alone is correct — the MVP ships with conservative-only and accepts the lost Tier 2 opportunities.
  • Pass 2 — whole-program, sequential (optional, post-MVP). When the CLI flag -EnableTier2WholeProgram is set (default: off in MVP), XBT injects an additional sequential action that fires after every per-module XIL2CPPAction completes. The action merges all TierTable.partial.* files into TierTable.json and re-invokes XIL2CPP in a whole-program-propagation mode that promotes Pass-1-Tier-1 functions to Tier 2 where the cross-module call graph proves the callee is noexcept-safe. Pass 2 never demotes Tier 2 to Tier 1; it is a strict optimization.

The action graph in Pass-2-enabled builds adds: Tier2WholeProgramPass action with prerequisites = every per-module XIL2CPPAction; producers = TierTable.json + a per-module re-emit cpp file (delta only). CompileCppAction on Pass-2-revised TUs picks up the revised tier assignment. Per the MVP correctness statement in Contract Section 5.2, omitting Pass 2 is sound; the only consequence is suboptimal classification.

Implementation note: the cache key is the content hash, not the mtime, so re-cloning the repo does not re-trigger validation (footgun #1 preempt).

Banned-API on preprocessed text (NEW Rev 3 — Contract Rev 12 M3). Per Contract Rev 12 Section 4.4, the SimPath banned-API check runs against post-preprocessor source (cl /E on MSVC, clang -E on Clang), not raw source — macro-wrapped bypasses (e.g. #define SAFE_TIME() QueryPerformanceCounter()) are otherwise invisible to the regex pass. XBT implements both pre-compile validators through one shared preprocess action:

  • Single preprocess invocation. Per TU, XBT invokes the platform preprocessor exactly once and writes the preprocessed text to a temp file using the pinned .tmp.<pid>.<actionid> convention (Section 6.4). On Win64 the invocation is cl /E; on Clang it is clang -E. The preprocessed text is the input both validators consume.
  • Banned-API check action. The regex pass runs against the preprocessed temp file; matches are reported with the original file:line via the #line directives the preprocessor emits. Failures exit 41.
  • Copyright validation. The copyright validator still reads the raw source file's first line — the copyright header is a property of the authored file, not its preprocessed form — but its action shares the same predecessor preprocess action for ordering, so the temp-file lifecycle is bounded.
  • Performance. Preprocessing is part of the compile pipeline anyway; XBT measures < 5% overhead on typical SimPath TUs (per Contract Section 4.4 performance note). The temp file is purged after both validators complete.

11.2 Failure mode

A missing or malformed header fails the build with exit 40 (per Contract Section 13) and a diagnostic naming the file's absolute path. Multiple offenders are batched into one error report so the developer can fix them in a single pass.

Cross-tier dynamic-load edges (Section 13.1 matrix) resolve through the typed IXModule / IXSymbolTable / GetModulePtr() protocol locked in Contract Rev 12 Section 9.7. XBT participates in two ways:

A DynamicallyLoadedModuleNames entry pointing at a module that does not export GetModulePtr fails the build at resolution with exit 24 ("plugin not found / not enabled", reused for the symbol-surface mismatch) and a diagnostic naming both endpoints.

The check runs on the preprocessed source (Section 11.1) so macro-wrapped bypasses are caught. All other code must resolve dynamic symbols through IXSymbolTable.

The validation surface is a build-time check; runtime hot-reload integration with IXModule's Initialize / Shutdown happens in Phase 2 XLiveCoding (XBT only provides the build-time guarantees per Section 16.1).

15. Caching (REVISED Rev 2)

Three layers, all content-hash-keyed, none mtime-keyed (footgun #1 preempt).

15.1 TargetMakefile — complete cache key (REVISED Rev 2; Phase 1 status note added Rev 5)

Phase 1 status: TargetMakefile is not yet implemented (see XToolchainContractAddendum-Step05.html Section 10 item 2). Phase 1 re-parses every descriptor on every build invocation; the 15-input cache key below describes the Phase 2 target. Two specific inputs in the list are flagged as currently-unimplemented even when the makefile lands — the reproducibility-envelope flag set (item 15) and the descriptor inputs (items 1–3) — per Addendum Section 10 items 2 and 10.

A binary-serialised pre-built action graph + module-info object stored at Intermediate/Build/<Target>/<Config>/Makefile.bin. Rev 1's listed cache-key inputs were incomplete; the Rev 2 audit (finding #3) requires the key to be the entire reproducibility envelope — if it influences output, it influences the cache key. The explicit list:

  1. Descriptor inputs: content hash of every .Build.toml, .Build.expr, .Target.toml in the active scope set.
  2. Plugin descriptors: content hash of every reachable .xplugin.
  3. Project descriptor: content hash of the .xproject.
  4. Engine descriptor: content hash of /Engine/Engine.xengine.
  5. XBT binary: content hash of XBT.exe.
  6. XHT binary: content hash of XHT.exe.
  7. XIL2CPP binary: content hash of XIL2CPP.exe.
  8. Contract surface: the auto-derived ContractVersion (Section 8.1).
  9. .NET SDK version: the major.minor.patch of the .NET runtime hosting XBT.
  10. Toolchain version: XToolChain.ToolchainVersion for every toolchain referenced by the target.
  11. Sim-path policy files: content hash of XSimPathBannedAPIs.txt and XSimPathMathOverrides.h. These were missed in Rev 1.
  12. Architecture: the target architecture string, even when omitted from on-disk paths (Section 18.1).
  13. FipsMode flag: the boolean from TargetRules.bFipsMode.
  14. StationRole: the role from TargetRules.StationRole (affects hot-reload eligibility per Section 16.4).
  15. Reproducibility envelope flag set: a hash of the toolchain's emitted reproducibility flag list per Section 19.1 (defends against a toolchain upgrade that silently changes flag defaults).

On a Makefile hit, XBT skips the entire descriptor parse + module-graph walk and goes straight to action execution. This is the largest single perf win for incremental builds. On a miss, all 15 inputs are recomputed.

The CacheKeyComponents field (Section 5.2) lets actions declare hidden inputs that don't appear in the command line but still influence output (SimdLevel, FpSemantics, FIPS mode, etc.).

Raw-source prerequisite recording (REVISED Rev 8 — Round-6 wiring). Per Section 5.4: after every successful action, the production executor records every raw-source prerequisite's live ContentHash into the appropriate partition via RecordContentHash. This makes the rule-3 prereq comparison in Addendum Section 4.3 fully wired in Phase 1 — raw-source invalidation now flows through recorded content hashes rather than implicit FileItem mtime sampling, closing the gap the Addendum's Revision 4 marks as item 1a.

Phase 1 status: the cache class itself is not yet implemented — see Section 5.5 and XToolchainContractAddendum-Step05.html Section 6 / Section 10 item 1. 15.4 SharedPCH — include-order policy (REVISED Rev 2)

When two or more non-SimPath modules in a target use the same SharedPCHHeaderFile, XBT generates a single precompiled-header artefact at Intermediate/.../PCH/PCH.<ContentHash>.h (file name uses the content hash of the inputs — mirrors UE pattern but with hash-named files for cleaner caching). MSVC consumes via /Yu, Clang via -include-pch. SharedPCH is opt-in via PCHUsage = UseSharedPCHs on the module rules; default is Default which lets XBT pick.

Include-order policy (NEW Rev 2 — audit finding #12): the SharedPCH header's #include lines are emitted in alphabetical-by-logical-path order. The order is independent of the declared order in any .Build.toml, of filesystem enumeration, and of build-machine environment. This guarantees deterministic PCH bytes for a given input set across runs and machines.

SimPath exclusion (NEW Rev 2): SimPath modules are forced to PCHUsage = NoSharedPCHs (Section 4.5). Additionally, any .gen.h emitted into a SimPath module is excluded from any SharedPCH consumed by non-SimPath callers — the .gen.h may carry sim-path-specific macro state that would leak into non-sim-path code.

15.5 BLAKE3 throughout

XBT uses BLAKE3 as its content-hash algorithm for all three cache layers. BLAKE3 is fast (typically 6 GB/s single-threaded), unkeyed, 256-bit output, has stable cross-platform implementations, and matches the spirit of UE's IoHash.

16.5 IQuiesceParticipant interface (REVISED Rev 3 — GC markers quiesce FIRST)

The Live Coding cascade's Phase 2 (function-pointer / vtable rewrite) requires that all reader threads be quiesced before the rewrite begins, and resumed afterward. The participants in the quiesce protocol are runtime-side subsystems, but XBT pre-declares the interface so the contract is locked at build time and every participating subsystem agrees on the same shape.

Rev 3 ordering fix. Rev 2 listed GCMarkerThreads = 6 (highest numeric priority = quiesces last). That is wrong — the hot-reload cascade requires GC markers to drain before any function-pointer write, otherwise a concurrent mark phase can observe a pointer mid-rewrite and follow a torn value (Contract Rev 11 Hot-Reload row exactly states this). Rev 3 moves GC markers to QuiescePriority = 0 (highest priority = quiesces first) and renumbers the remaining threads accordingly.

public interface IQuiesceParticipant
{
    string ThreadName { get; }                  // diagnostic
    QuiescePriority Priority { get; }           // lower numbers quiesce first
    Task QuiesceAsync(CancellationToken ct);
    Task ResumeAsync(CancellationToken ct);
}

public enum QuiescePriority
{
    // REVISED Rev 3: GC markers MUST quiesce before function-pointer writes
    // so no concurrent mark phase observes a pointer mid-rewrite during the
    // patch window. Contract Rev 11 Section 3 (span-based ABI) + Contract
    // Rev 11 Hot-Reload row jointly require this ordering.
    GCMarkerThreads   = 0,    // highest priority — quiesces first
    GameThread        = 1,
    RenderThread      = 2,
    RHIThread         = 3,
    AudioThread       = 4,
    LoadingThreads    = 5,
    SimPathWorkerPool = 6,
}

Ordering rationale. GC markers quiesce first so that no concurrent mark phase observes a pointer mid-rewrite during the patch window. Once markers are drained, function-pointer / vtable writes happen on the patch DLL while the rest of the runtime is still live (game thread, render thread, etc. are then drained in dependency order before the actual patch swap). On resume, marker threads come back last — symmetric with the quiesce order — so the runtime has fully re-attached to patched code before any mark phase walks it.

Phase 1's list of registered participants is empty. Phase 2 XLiveCoding registers participants for concurrent GC marker threads, game thread, render thread, RHI thread, audio thread, loading threads, and the sim-path worker pool, in this priority order.

16.7 Patch-DLL discovery path (REVISED Rev 3 — per-(Target, Module) <gen> scope)

When XLiveCoding cascades a patch, the patched DLL has the same module name as the live module — it cannot share a path or the OS file lock will reject the write. Rev 2 reserved a known location at Phase 1 so Phase 2 does not need to negotiate one; Rev 3 pins the <gen> counter's scope to remove ambiguity:

/Intermediate/Build/<Target>/<Configuration>/LiveCoding/<Module>.patch.<gen>.dll

<gen> scope (Rev 3 clarification): per-(Target, Module). A counter for each (Target, Module) pair, incrementing monotonically per the pair within a session. Two concurrent patches to different modules in the same target use independent counters; two concurrent patches to the same module in different targets likewise use independent counters; only sequential patches to the same module in the same target share a counter sequence. This guarantees collision-free naming under concurrent patching across modules and across targets without requiring inter-target coordination.

Counter persistence across XBT invocations (NEW Rev 4 — closes the "second invocation collides with first" gap). The counter is not kept in a separate persistence file. At XBT startup, when XLiveCoding requests a patch-DLL write for (Target, Module), XBT scans /Intermediate/Build/<Target>/<Configuration>/LiveCoding/<Module>.patch.*.dll, parses the integer suffix from every match, takes max(observed), and starts at max + 1 — or at 0 if no prior patch-DLLs exist. This means: repeated XBT invocations in the same physical directory monotonically advance the counter without any external state; a fresh CI agent (with no prior LiveCoding/ directory) starts at 0; deleting old patch-DLLs by hand resets the high-water mark naturally. The scan is O(n) in the number of prior patch-DLLs for that (Target, Module) pair — typically < 100 in a long session; near-zero on a clean checkout. No dedicated reset mode exists in Phase 1 (D-C5 fix Rev 7): the directory can be cleaned manually, or Phase 2 may introduce an explicit xbt clean-livecoding mode alongside the rest of the XLiveCoding wire-up. Phase 1's clean mode (Section 1.1) targets per-target intermediate + binaries trees, not the LiveCoding/ subdirectory specifically.

Phase 1 XBT does not write to this location; it does not even create the directory. Phase 2 XLiveCoding writes here; XBT's subset-build action graph outputs to this path when invoked with -LiveCoding=true. The path is reserved — nothing else writes to LiveCoding/ — so Phase 2 can rely on the per-(Target, Module) naming discipline.

16.8 Container hot-reload layout-freeze (NEW Rev 3 — Contract Rev 12 N1)

Per Contract Rev 12 Section 3.7, container class layouts (any class with an embedded XGCRootSpan member) are layout-frozen within a hot-reload session. A patch that changes the m_rootSpan offset, the field-offset list, or the vtable shape of a container type would leave the collector reading the span at the wrong offset on every live instance — corruption, not just a wrong value. XLiveCoding rejects such patches at patch-DLL load time.

XBT's role. XBT pre-validates at build time when emitting the patch DLL via ActionGraph.BuildSubset (Section 16.6) under the -LiveCoding=true path:

  • The XIL2CPP emit pass marks every class with an embedded XGCRootSpan as container = true in its class-descriptor table (per Contract Section 3.7). XBT inspects the patch DLL's emitted descriptors before allowing the patch DLL to be written out.
  • For every container = true class, XBT compares the patch DLL's field-offset list and vtable shape against the live DLL's class-descriptor (the original-build output, read from disk). A mismatch fails the patch build with an exit in the Live Coding domain range (90–99 per Contract Section 13).
  • Allowed mid-session patches: function-body changes to Add / Remove / RemoveAt / EnsureCapacity / iterator methods; new non-virtual methods; new virtual methods only on classes with zero live instances. These pass the field-offset check.
  • Disallowed mid-session patches: adding, removing, or reordering data fields; relocating m_rootSpan; changing m_rootSpan kind (Strong ↔ Weak ↔ Conservative); changing container stride. These fail the patch build and require the close-reopen flow.

Phase 1 XBT does not run this validation (no patch DLLs are produced in Phase 1). The validator infrastructure ships at Phase 1 as part of XBT.LiveCoding but is invoked only by the Phase 2 -LiveCoding=true path.

19.3 Windows Job Objects for subprocess kill-on-crash (NEW Rev 8 — Round-6)

On Windows, ParallelExecutor creates a single Job Object at executor construction and assigns every action subprocess (cl.exe, link.exe, clang.exe, lld, etc.) to that job via AssignProcessToJobObject. The job is configured with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE in its basic-limit information block, which instructs the OS to terminate every assigned process when the last handle to the job closes.

Failure-mode coverage:

  • XBT process crash. When XBT's process exits abnormally (access violation, unhandled exception, OOM kill), the job handle closes; the OS reaps every spawned compile / link process within milliseconds. No orphan cl.exe burning CPU after a developer's session aborts.
  • taskkill /F XBT.exe. Same path: the kernel cleans up XBT's handles, the job closes, the children die. The next XBT startup's orphan-temp sweep (Section 6.4) finds no live PIDs to spare; cleanup is total.
  • Ctrl-C / SIGINT. The graceful path in Section 6.4 still applies first — the cancellation token lets subprocesses finish or quit cleanly within the 5-second grace, after which XBT calls Process.Kill(entireProcessTree: true). The job object is the belt; the cancellation path is the suspenders.

Linux / Mac (Phase 1 acceptable gap). POSIX process groups (setpgid + killpg) are the rough equivalent, but the Phase 1 implementation is a no-op on non-Windows hosts. The rationale: the SIGINT-grace path in Section 6.4 covers the Ctrl-C case, the next-startup orphan-temp sweep handles the abnormal-exit case, and Linux + Android compile orchestration on developer machines is less common than Win64 in the Phase 1 customer profile. Phase 2 may add process-group wiring on POSIX if profiling shows it matters; the executor surface is already abstracted behind ProcessActionRunner so the change is local.

19.4 Antivirus-retry on Windows file operations (NEW Rev 8 — Round-6)

Windows antivirus scanners (Defender, third-party endpoint security suites) intermittently hold open handles on newly-written or about-to-be-moved files for a short window after creation, causing transient IOExceptions in atomic-rename writers. Pre-Round-6, these failures surfaced as spurious build failures that disappeared on retry. Round-6 introduces FileSystemOps.RetryOnTransientIOException, a thin helper that wraps a file-system action with a bounded retry loop on IOException.

Retry schedule: [100ms, 200ms, 1000ms, 5000ms] — exponential ramp with a 5s cap. The loop retries up to 4 times after the initial attempt; the 5th attempt's exception is re-thrown. Real I/O errors (disk full, permission denied) propagate as soon as the final attempt fails; transient AV holds resolve well within the first second on every observed scanner.

Call sites (5):

  • ManifestJson.Serialize — temp-file write + atomic rename for Manifest.json.
  • ManifestFbs.Serialize — temp-file write + atomic rename for Manifest.fbs.bin.
  • ActionHistory.Save — the temp-file + atomic-rename emission of ActionHistory.bin.
  • ParallelExecutor's post-action temp-file move (the <output>.tmp.<pid>.<actionid> → <output> rename) and the on-failure temp-file delete.
  • The PCH wrapper-header write (the SharedPCH.<hash>.h stub the toolchain emits to drive /Yu / -include-pch).

Compile / link subprocesses themselves are not wrapped — AV holds on .obj / .lib outputs would surface inside the toolchain process and are already handled by the toolchain's own retry posture. The helper is XBT's own file-IO surface specifically. Linux / Android are unaffected (POSIX inotify-style scanners do not hold open handles synchronously); the helper's retry loop is still safe to invoke cross-platform — on a fast-failing-permission case it returns the first exception immediately.

19.5 MAX_PATH proactive validation on Windows (NEW Rev 8 — Round-6)

Windows enforces a per-path length cap of 260 characters (MAX_PATH) for most filesystem APIs. Deep module trees + long intermediate-path components can blow the cap silently, surfacing only at compile or link time as a cryptic toolchain stderr ("file not found" with no further context). Round-6 introduces ActionGraph.CheckPathLengths(), called once after ActionGraph.Link() + CheckForConflicts() and before executor dispatch (XBT-startup pipeline). The check:

  1. Walks every action's PrerequisiteItems and ProducedItems on Windows.
  2. Computes FullPath.Length for each FileItem.
  3. If any path is > 260 characters, exits with code 71 (LinkFailed per Section 1.3 / Contract Section 13.1 — reused as the closest-fit code pending a dedicated PathTooLong mnemonic) and prints a diagnostic naming the offending path + the action that referenced it ({action.CommandDescription}: {action.StatusDescription}) so the developer can correlate to a module / TU at a glance.

Non-Windows hosts skip the check. Linux + Android filesystems have no comparable per-path cap relevant to XBT's intermediate trees; the check would impose overhead without value.

Relationship to ShortName (Section 18.3). ModuleRules.ShortName is the developer-side mitigation: a module declares a short alias and XBT substitutes it in path construction. CheckPathLengths() is the build-time fail-fast for the case where ShortName was either not applied or not sufficient. The two are complementary: developers who hit the diagnostic should set ShortName; the diagnostic exists so the failure is loud and early, not silent and late.

Contract Section 13 exit-code note. Code 71 (LinkFailed) gains a dual meaning at Rev 8: it covers the existing link-action-failure case (linker stderr non-zero) and the new MAX_PATH validation failure (link-graph pre-flight rejects an over-long path). The reuse is honest within the closest-fit-code-pending-dedicated-mnemonic discipline already established for run-xht's exit-24 (Section 1.4); a future Contract revision may introduce a PathTooLong mnemonic and remap the validation failure to it.

20. Threading Model

XBT's own threading is conservative and easy to reason about.

20.1 Main thread

Mode dispatch, CLI parse, manifest emit, ActionGraph operations (Link, CheckForConflicts, DetectActionGraphCycles, Sort, BuildSubset). These are inherently serial — running them on multiple threads buys nothing and risks ordering nondeterminism.

20.2 Worker pool

Sized to Environment.ProcessorCount (overridable with -Workers=N). The pool services:

  • Action execution (Section 6).
  • Descriptor parsing across scopes (Section 3; each scope parses in parallel).
  • Plugin discovery (Section 17.1; each plugin root walks in parallel).
  • Manifest assembly (per-module manifest entry construction).

No global locks. Per-scope cache locks (one lock per descriptor scope; one lock per ActionHistory bucket). Lock granularity is fine enough that contention is rare in practice.

20.3 Cancellation threading (NEW Rev 2 — audit MINOR #15)

In-process XHT and XIL2CPP (the Phase 2 perf option per Section 9 / Section 10) receive the cancellation token through their entry-point signature. The check points are: at every foreach over modules, at every per-file iteration within a module, and immediately before any write to a temp file. Subprocess XHT and XIL2CPP receive cancellation through SIGINT / Ctrl-C in the same way as any other action subprocess. The 5-second grace period in Section 6.4 applies uniformly.

21. Error Handling and Diagnostics (REVISED Rev 2)

21.1 Diagnostic format

XBT emits diagnostics in MSBuild's file(line,col): error CODE: message format so IDEs and CI dashboards can parse them with the same regex they use for compiler errors. Each diagnostic carries an XBT-specific code (per Contract Section 13; per-diagnostic codes have the form XBT<NNN>).

21.2 Streaming JSON error channel (NEW Rev 2 — audit finding #5)

Rev 1 wrote a single post-hoc JSON build log at end of build. Rev 2 adds a streaming JSON channel that emits diagnostics in real-time, suitable for IDE / CI subscription.

The channel is implemented two ways depending on platform:

  • Linux / Android: a dedicated file descriptor (FD 3 by default, configurable via -JsonFd=N). The IDE opens a pipe and passes the read end as FD 3.
  • Windows: stdout lines prefixed with the sentinel @@XBT-JSON@@ . The IDE filters these out of the human-visible stream. The fallback Linux/Android encoding is the same when no extra FD is available.

Activation rule (Rev 5): On Linux / Android the channel activates whenever -JsonFd=N is supplied (the IDE explicitly opts in by providing the pipe). On Windows the channel activates automatically when stdout is not a TTY and no -JsonFd was provided; the IDE consumer is assumed to redirect stdout to a pipe and filter the sentinel-prefixed lines. Interactive terminal use (TTY stdout, no explicit FD) suppresses the channel so a human running XBT.exe build at a console does not see @@XBT-JSON@@ noise interleaved with the human-readable progress.

Every diagnostic produces one JSON line on the channel and one human-readable line on stderr. They are content-equivalent. The JSON record shape:

{"action":"link","module":"XScoring","level":"error","code":"XBT071",
 "file":"Engine/Source/Runtime/XScoring/Private/XScoring.cpp","line":42,"column":7,
 "message":"undefined reference to `XSleef_sin'","tier":"Engine","simpath":true,
 "target":"MiningTrainingEditor","configuration":"Development","platform":"Win64",
 "timestamp":"2026-05-19T14:00:42.123Z"}

Rev 7 fix (D-m3): the example diagnostic above carries an unresolved-symbol message ("undefined reference"), which is a linker failure category. Code XBT071 (LinkFailed per Section 1.3 + Contract Section 13.1) is the correct match. The Rev 5 example mislabelled the same payload as XBT070 (CompileFailed); the code-vs-message mismatch is corrected here.

The channel is streaming — records are written and flushed as they happen, not buffered until end of build. This lets the IDE highlight a compile error within milliseconds of the compile failing, not at end-of-build.

21.3 Cancellation (REVISED Rev 2)

Ctrl-C / SIGINT installs a CancellationToken. The dispatcher stops queueing new actions; in-flight subprocesses are given a 5-second grace period; partial outputs follow the pinned temp-file convention (Section 6.4) and are swept either by the current process (on SIGINT) or at next startup (on taskkill /F); the build log records the cancellation with timestamp; the streaming JSON channel emits a final {"event":"cancelled","timestamp":"..."} record. Exit code 130.
