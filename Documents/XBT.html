0. Purpose, Scope, Tier Membership

XBT is the build orchestrator for every XPact build. It is the first system implemented after the Toolchain Contract (plan Section 4 Step 1), and every later system — engine, editor, studio plugin, project — is compiled by XBT. XBT is the analog of Unreal Engine's UnrealBuildTool (UBT), restructured to honour the foundational decisions locked in plan Section 2 and the seams locked in the Toolchain Contract (Rev 11).

XBT is delivered as a single C# .NET 8 self-contained standalone executable. It has no XPact runtime dependencies — it cannot reference XCore, XCoreXObject, or any engine type. The build artefact is a Win64 / Linux / Android-host-x86_64 binary plus a small set of data files (banned-API list, default toolchain table, contract-surface manifest used to derive ContractVersion). XBT is invoked by developer scripts, by IDE delegation hooks (Rider, clangd), and by XAutomationTool's release pipeline.

Tier membership. Plan Section 3: "All inventory systems are Engine-tier (live in /Engine/)." XBT's source lives under /Engine/Source/Programs/XBT/. XBT is itself reusable across every Simgenics training product and every plugin, mirroring the engine's universal-reuse posture (plan Section 2 Folder structure row, Rev 6).

Position in the build pipeline. XBT drives the pipeline locked in Toolchain Contract Section 10.1: discovery and graph build, manifest emit (JSON + FlatBuffers sidecar), concurrent XHT + XIL2CPP invocation, copyright validation, C++ compile actions, link. Every step is an action in XBT's action graph; XBT is itself the only tool that owns the graph. XHT (System 2) and XIL2CPP (System 6) are sub-tools XBT invokes, never the other way round.

What XBT does not own. It does not parse reflection markers (that is XHT's job, per Contract Section 7). It does not transpile C# (that is XIL2CPP's job, per Contract Sections 2, 3, 5, 6). It does not own GC root primitives (those are XCoreXObject's job, per Contract Section 3 — now the XGC_RegisterRootSpan / XGC_UpdateRootSpan / XGC_UnregisterRootSpan family per Contract Rev 11). It does not own runtime hot-patch dispatch (XLiveCoding's job; XBT provides hook seams only). It does not handle deployment, code signing, or symbol upload (XAutomationTool's job, plan Section 3 Layer 0). XBT's responsibility ends when the link step produces a well-formed binary that the next pipeline stage can pick up.

Phase awareness. XBT MVP is Phase 1 in plan Section 5 (MVP subset). The Phase 2 readiness items called out in this document — distributed execution, full Live Coding integration, advanced PCH, Visual Studio project files — are designed as no-cost stubs at Phase 1 so post-MVP work does not require XBT redesign. Section 5.1 reserves XActionType enum slots so adding Phase 2 action types does not break the field-set hash that auto-derives CommandVersion.

1.3 Exit codes — cross-reference to Contract Rev 11 (REVISED Rev 2)

The exit-code surface is shared between XBT, XHT, and XIL2CPP. Rev 2 moves the table out of XBT.html and into the contract so all three tools use one source of truth. See Contract Rev 11 Section 13 — Exit Code Surface. XBT.html does not duplicate the table; doing so would diverge over time as new categories land. XBT's XBT.Entry imports the contract's exit-code constants at build time (the contract publishes the codes as a small C# data file alongside the HTML).

The contract's table includes the codes XBT relies on most: success (0), generic failure (1), CLI argument error (10), discovery failure (20), tier violation (21), circular dependency (22), engine-version mismatch (23), plugin not found (24), declarative descriptor evaluation failure (30 — replaces "RulesAssembly compile failure" from Rev 1), copyright validation failure (40), SimPath banned-API check failure (41), manifest malformed (50), XHT subprocess failure (60), XIL2CPP subprocess failure (61), compile action failure (70), link action failure (71), action-graph cycle (80), and SIGINT cancellation (130). Per Contract Rev 11 Section 13, new categories take the next free integer; codes are stable across versions.

1.4 CLI wrapper modes (REVISED Rev 2)

RunXHT and RunXIL2CPP are convenience wrappers for IDE callers that already have a manifest path in hand and want a one-line invocation. They delegate to XHT.exe and XIL2CPP.exe respectively; XBT does not re-implement either tool's logic. The wrappers exist so an IDE single-file refresh can call XBT.exe RunXHT -Manifest=... -Module=... without first locating the standalone exe on PATH; XBT knows the toolchain root.

1.5 Output format (REVISED Rev 2)

Default output: human-readable progress to stdout, errors and diagnostics to stderr, structured JSON build log written incrementally to Intermediate/Build/<Target>/<Config>/BuildLog.json. Streaming JSON error channel (NEW Rev 2; see Section 21.2): in addition to the human-readable stderr stream, XBT emits a parallel one-line-JSON channel suitable for IDE / CI subscription. The channel is implemented either as a dedicated file descriptor (Linux/Android) or as stdout lines prefixed with a sentinel @@XBT-JSON@@ (Windows; the same on Linux when no FD is available). Subscribers read the JSON channel; humans read stderr; the two are content-equivalent at the diagnostic level.

Cancellation via Ctrl-C is graceful and deterministic: outstanding actions are allowed to complete or fail cleanly; partially-produced outputs follow the atomic-rename + temp-file convention pinned in Section 6.4 and Section 21.3; the build log records the cancellation event. This is a Phase 1 commitment and the analog of UBT's UseStartupTraceListener option, refined.

-WarningsAsErrors=false (NEW Rev 2): The default is true at the target level. Developers can override per build via the CLI flag; the override is logged into BuildLog.json so a build with warnings-as-errors disabled is recognisable from the log. The override is intentionally not exposed to .Build.toml — relaxing warnings-as-errors should be a developer-level deliberate act, not a module-level configuration.

3. Declarative Descriptors — .Build.toml / .Target.toml (REVISED Rev 2; Roslyn dropped)

Foundational decision reversed. Rev 1 chose Roslyn-compiled .Build.cs, mirroring UBT. The Rev 2 audit identified two material problems: (a) cold start was dominated by Roslyn compile, even with per-scope caching; (b) the rules surface was unbounded — any .Build.cs could in principle read arbitrary files, fork processes, mutate global state. Both problems compound as the engine grows. Rev 2 reverses the decision: 95% of modules are pure declaration in TOML; the remaining 5% that need conditionals use a tiny sandboxed expression language. Per Contract Section 9.5 (Rev 11): "XPact's choice between Roslyn-compiled rules and a declarative-only subset is internal to XBT — either approach satisfies this contract." This revision is internal-to-XBT and does not reopen the contract surface (audit finding #2).

The expected payoff:

  • 50–100× faster cold start than Roslyn on a clean checkout (no MSBuild graph, no compile, no assembly load, no System.Reflection walks).
  • Bounded surface: a malformed or hostile .Build.toml cannot execute arbitrary code; the parser is data-only and the expression evaluator runs in a sandbox with explicit allow-listed names.
  • Stable across .NET SDK changes: no Roslyn version pin, no LanguageVersion tracking, no Microsoft.CodeAnalysis ABI risk.

3.1 Discovery (REVISED Rev 2)

XBT discovers .Build.toml and .Target.toml files (with optional .Build.expr sidecars for the conditional cases) by walking the conventional roots:

  • /Engine/Source/<ModuleType>/<Module>/ — engine modules (where <ModuleType> is the Unreal-convention sub-folder per plan Section 6 footnote, e.g. Runtime, Editor, Developer, Programs).
  • /Engine/Plugins/<Plugin>/Source/<Module>/ — engine plugins.
  • /Studio/Plugins/<Plugin>/Source/<Module>/ — studio plugins.
  • /Projects/<P>/Source/<Module>/ — project modules.
  • /Projects/<P>/Plugins/<Plugin>/Source/<Module>/ — project plugins.

Module discovery enumerates directories in a stable order: alphabetical by absolute path after canonicalising case (Windows) and resolving symlinks. This guarantees the JSON manifest's Modules[] array (Contract Section 10.2) is the same across runs and machines.

A typical .Build.toml is pure declaration:

Field names follow snake_case in TOML and translate one-to-one to the C# ModuleRules fields in Section 4. Unknown fields fail discovery (closed surface, exit 30) so typos never silently degrade behaviour.

3.3 The sandboxed expression sub-language (NEW Rev 2)

The 5% of modules that need conditional logic carry a sibling .Build.expr file. The expression language is a deliberately tiny subset of Starlark (the configuration language used by Bazel and Buck), with these reductions:

  • No I/O. No load(), no file reads, no environment access except through pre-bound names.
  • No top-level mutation. The evaluator runs a pure expression and returns a value or a small record patch.
  • No for over user-defined sequences. List/dict comprehensions over pre-bound names are allowed.
  • Bound names: target.type, target.platform, target.configuration, target.station_role, module.tier, module.sim_path. These are the only inputs.
  • Return value: a TOML-shaped patch dictionary merged into the base .Build.toml.

Example: a module that wants to disable exceptions only in Shipping:

# /Engine/Source/Runtime/XScoring/XScoring.Build.expr

{
  "module": {
    "enable_exceptions": target.configuration != "Shipping"
  }
}

The evaluator is implemented in pure C# in XBT.Configuration. It has no System.IO, no System.Diagnostics.Process, no System.Reflection.Emit; static analysis at parse time rejects any reference to disallowed names. The evaluator is a pure function of (parsed AST, bound name map) → (TOML patch); it is deterministic by construction.

3.4 Caching (REVISED Rev 2)

Descriptor cache key is the BLAKE3 content hash of all .Build.toml + .Build.expr files. Never mtime. The cache is partitioned per scope (engine, per-plugin, per-project) so a project-tier edit does not invalidate engine-tier descriptors. A scope cache hit skips the parse, expression evaluation, and merge entirely.

Cache entries are stored at Intermediate/Build/Descriptors/<Scope>.<Hash>.bin with a sidecar JSON index. Invalidation rules:

  • Any input .Build.toml or .Build.expr content hash differs → reparse + re-merge.
  • Any input .Target.toml content hash differs → reparse.
  • XBT binary hash differs → re-merge (handles XBT updates that change the merge semantics).
  • ContractVersion (auto-derived per Section 8.1) differs → re-merge.

3.5 Failure handling (REVISED Rev 2)

If a .Build.toml is malformed (TOML syntax error, unknown field, bad enum value, conflicting fields), or a .Build.expr references a disallowed name, XBT prints the diagnostic in file(line,col): error XBT030: message format and exits with the contract code 30 ("descriptor evaluation failure" — the contract Rev 11 renames the Rev 1 "RulesAssembly compile failure" to this). Multiple errors from a single scope are reported together so the user can fix them in one pass.

3.6 Migration from Rev 1's Roslyn surface (NEW Rev 2)

Existing engine code that was authored against the Rev 1 sketch (a Roslyn-compiled .Build.cs class) has not yet shipped — the Rev 1 spec was never implemented. There is no Rev 1 corpus to migrate. The single example in Rev 1 Section 4.7 is rewritten in TOML form above (Section 3.2).

Should a future need for full general-purpose code in a build descriptor arise, the right answer is a Phase 2 escape hatch: a per-target opt-in to load a Build.Plugin.dll compiled out-of-band and signed, never a per-module .Build.cs. Phase 1 does not need this.

4.5 SimPath constraints (REVISED Rev 2)

When SimPath = true:

  • FPSemantics is auto-promoted from Default to Precise. Explicit FPSemantics = FPSemantics.Imprecise on a SimPath module fails the build (banned per Contract Section 4).
  • PCHUsage must be NoSharedPCHs. If a SimPath module declares UseSharedPCHs or UseExplicitOrSharedPCHs, the build fails with exit 30 and a diagnostic. SimPath modules cannot participate in SharedPCH because the SharedPCH would otherwise have to honour the sim-path math overrides for every consumer, and a consumer that is itself not sim-path would silently inherit the overrides through the PCH. The Rev 2 audit identified this as a correctness boundary.
  • .gen.h emitted into the same module is excluded from any SharedPCH (per Section 15.4) regardless of the PCH usage mode of other modules.
  • SimdLevel is forced to ≤ SSE42. SimdLevel.AVX / AVX2 / AVX512 on a SimPath module fails the build — the higher SIMD levels enable FMA paths that violate determinism. On Clang, -mno-fma is also emitted as a belt-and-braces guard.

4.8 Unity-build determinism (NEW Rev 2)

With bUseUnity = true (default), source files in a module are clustered into unity TUs. UBT's Unity.cs is known to have a race in how it assigns files to buckets — XPact preempts this by locking the rule:

  1. Sort the module's source files by BLAKE3 content hash (ordinal comparison on the hash bytes).
  2. Compute bucket_count = ceil(N / max_files_per_bucket) where max_files_per_bucket = 16 by default. The bucket count is locked per module across a build session; it changes only when source-file membership changes.
  3. Assign file i (in the sorted order) to bucket i % bucket_count.
  4. Emit unity TUs <Module>.unity.<bucket>.cpp with includes listed in sorted-by-hash order.

The rule is purely a function of the file set and their content hashes — no mtime, no filesystem ordering, no environment dependence. Two builds of the same source tree on different machines produce identical unity TUs. The Rev 2 audit finding cites UBT's Unity.cs lines 32–44 as the divergence point this rule fixes.

5.3 ActionGraph operations

ActionGraph.Link() builds the producer map from FileItem → IExternalAction (every produced FileItem must have exactly one producer; duplicate-producer errors are caught here). CheckForConflicts() verifies that no two actions produce the same FileItem with different commands. DetectActionGraphCycles() runs a DFS for cycles; on detection, the cycle is printed and the build exits 80. Sort() produces a topological order with a deterministic tiebreaker (by CommandVersion) so the same graph yields the same execution order across machines.

BuildSubset(IEnumerable<ModuleName> roots) (NEW Rev 2 — see Section 16.6 for the Live Coding use case): returns the action sub-graph rooted at the given module set, validated and topologically ordered, suitable for executor dispatch. Phase 1 implements; Phase 2 XLiveCoding uses for incremental compile-only passes.

5.4 ActionHistory

Per Contract Section 10.3: incremental rebuilds. XBT's ActionHistory is a binary-serialised map from FileItem → IoHash(commandVersion + responseFileContents + CacheKeyComponents + relevant flags), partitioned by CacheBucket so two unrelated buckets can be read/written in parallel.

6. Executor (Phase 1 = local only)

Phase 1 XBT ships with a single executor: ParallelExecutor. Sized by default to Environment.ProcessorCount; configurable via -Workers=N. Worker threads pull from a job queue; each job is one IExternalAction. The queue is sorted before dispatch by CommandVersion so dispatch order is deterministic (mirrors UBT footgun #6 fix at the executor level).

6.1 Scheduling

Topological order from ActionGraph.Sort respects the dependency graph; within a single ready-set, the dispatcher picks actions in CommandVersion order to keep ordering deterministic for log diffing and reproducibility tests. Actions with Weight > 1 are dispatched only when at least Weight workers are free.

6.2 Failure isolation (REVISED Rev 2)

Each action runs in its own subprocess (or in-process when both XHT and XIL2CPP are loaded as libraries — XBT picks subprocess for Phase 1 simplicity, in-process is a Phase 2 perf option). A non-zero exit code captures stderr to the build log and emits a streaming JSON error record (Section 21.2) and marks the action failed. Failure propagates: dependent actions are skipped, the build's final exit code reflects the worst category encountered (per Contract Section 13). One action's failure never corrupts another's outputs: each action writes to a temp file <output>.tmp.<pid>.<actionid> in the same directory as the final output (same-volume guarantee, atomic rename), and atomically renames into place on success. On failure, the temp is deleted.

6.3 The bCanExecuteRemotely flag

Present on IExternalAction but ignored at Phase 1. Phase 2 work (post-MVP per plan Section 5): XPactBuildAccelerator (plan Section 3 Layer 0 Rev 7) consumes the flag and dispatches eligible actions to a worker pool of remote machines. XBT must not preclude this; the executor surface in XBT.Executor is an interface, not a single class, so Phase 2 can register a second implementation alongside ParallelExecutor.

6.4 Cancellation + atomic-rename contract (REVISED Rev 2 — audit finding #1)

Rev 1's Sections 6.2, 6.4, and 21.3 contained mutually contradictory rules for what happens to in-flight files when XBT is killed. Rev 2 pins one rule across all three, derived from the audit:

  1. Temp-file naming. Every action that produces a file <output> writes first to <output>.tmp.<pid>.<actionid> — pid is the OS process id, actionid is a monotonic counter scoped to the run. The temp lives in the output's own directory, never %TEMP% or /tmp. The same-directory constraint guarantees the final rename is on the same filesystem volume; cross-volume rename is non-atomic on Windows and a known UBT race.
  2. SIGINT path. SIGINT installs a CancellationToken. Outstanding actions are given a 5-second grace period to complete cleanly. After grace, in-flight subprocesses are killed; their temp files remain on disk (uncleaned because the killed subprocess could not run its delete-on-fail). XBT's main process catches the cancellation, sweeps temp files matching *.tmp.<mypid>.*, and exits 130.
  3. taskkill /F path. XBT's main process is killed outright. Temp files for this pid remain orphaned. There is no cleanup opportunity for this build.
  4. Orphan sweep at next startup. Every XBT startup begins with a sweep of the intermediate tree. Any *.tmp.<pid>.* whose pid is not currently running (queried via OS process-id lookup) is deleted. This guarantees no resource leak from a prior taskkill /F.
  5. Atomic rename. On Win64, MoveFileEx with MOVEFILE_REPLACE_EXISTING. On Linux/Android, renameat2 or fallback rename. The semantic is: the final output never appears half-written; readers see either the pre-existing file or the new one, never an intermediate state.

This rule applies uniformly to compile outputs (.obj / .o), generated headers (.gen.h), generated cpp (.gen.cpp), transpiled outputs (.cs.cpp), the manifest, the binary FlatBuffers sidecar, the build log, and the action-history files. Every writer in XBT.Core's atomic-file-IO surface enforces this naming convention.

Exception calling convention split (NEW Rev 2 — Contract Rev 11 Section 5). XBT's toolchain emits a per-function flag in the compile command that XIL2CPP and XHT both consume: -DXPACT_EXC_SHIM on boundary functions, nothing on direct-noexcept. The flag is derived from the XHT-emitted reflection metadata (functions marked CanThrow + boundary-crossing) merged with the toolchain's noexcept deduction pass.

8. Manifest Format (REVISED Rev 2)

8.1 ContractVersion auto-derivation (REVISED Rev 2)

Rev 1 hand-typed "ContractVersion": "v1". The Rev 2 audit (per Contract Rev 11 change #6) identifies this as fragile: a contract revision that changes the surface without bumping the string lets old and new manifests look identical. Rev 2 auto-derives:

ContractVersion = "x" + BLAKE3-16(canonicalize(ContractRev11Surface))[:8].hex()

The "contract surface" is the canonicalized list of: every named field in every C# DTO declared in XBT.Manifest (sorted), the FBS schema bytes, the exit-code table from Contract Section 13. Canonicalisation strips comments, normalises whitespace, sorts field declarations alphabetically. The hash is reproducible across machines; any contract change that affects what XHT or XIL2CPP read produces a new ContractVersion, automatically.

For the current contract (Rev 11), the derived value is computed at XBT build time and baked into XBT.Manifest's constants. A future contract bump simply rebuilds XBT; the manifest reader's compatibility check still works.

8.4 JSON parse safety (NEW Rev 2 — audit finding #10)

The manifest is the protocol between XBT and IDE / subprocess invocations. A malicious or malformed manifest must not DoS the build agent. Rev 2 pins reader options for every System.Text.Json manifest read:

var options = new JsonReaderOptions
{
    MaxDepth = 64,                       // hard cap on nesting; 8 is typical
    CommentHandling = JsonCommentHandling.Disallow,
    AllowTrailingCommas = false
};

// Plus, at the stream level:
const long MaxManifestBytes = 100L * 1024 * 1024;   // 100 MB hard ceiling
if (stream.Length > MaxManifestBytes) throw new ManifestTooLargeException(...);

// Per-string field limits (typical):
const int MaxStringField = 16 * 1024;     // 16 KB per field
const int MaxArrayCount  = 65536;         // 64K entries per array (modules, source files, etc.)

Violations produce ManifestMalformedException → exit code 50. The same posture applies to the binary FlatBuffers sidecar: FlatBuffers' built-in verifier is enabled (Verifier with strict depth + size limits), not just the unchecked-reader path.

8.5 Binary FlatBuffers sidecar (NEW Rev 2 — Contract Rev 11 #5)

Tools read the binary sidecar; humans read the JSON. Both are emitted in lockstep from the same C# manifest object; their content is structurally equivalent. The FBS schema lives in XBT.Manifest/Manifest.fbs and is versioned alongside the JSON schema. The sidecar file is Manifest.bin alongside the Manifest.json.

Why a sidecar (not a replacement): JSON remains readable in editors and diffable in version control; FlatBuffers is unreadable. Tools want fast parsing; humans want introspection. Maintaining both costs almost nothing because the C# DTO is the single source of truth.

Verification: when XHT or XIL2CPP starts, it reads Manifest.bin with the FlatBuffers verifier enabled; if the verifier rejects, it falls back to Manifest.json with the hardened reader options (Section 8.4); if both fail, exit 50.

9. XHT Integration

XBT invokes XHT either as a subprocess or in-process via the EpicGames.UHT-style library pattern (UE reference brief). Phase 1 picks subprocess for simplicity; the in-process path is a Phase 2 perf option. The choice is internal — XHT sees only the manifest.

9.1 Invocation

# XBT calls:
XHT.exe -Manifest=Intermediate/Build/MiningTrainingEditor/Development/Manifest.json
        -ManifestBin=Intermediate/Build/MiningTrainingEditor/Development/Manifest.bin
        -Module=XScoring

XBT can also call XHT once with no -Module= filter, in which case XHT processes every module in the manifest. XBT chooses the per-module form so XHT actions can run in parallel across modules (Contract Section 10.1 step 3).

9.2 Outputs

XHT writes outputs to paths derived from the manifest's BaseDirectory + OutputDirectory conventions; XBT discovers them via the per-module text manifest XHT emits alongside its binary outputs (Contract Section 7.1). XBT does not parse .gen.h or .gen.cpp — their content is opaque (plan Section 4 Rev 5 clarification).

Outputs per module (Contract Section 7.1):

  • Intermediate/.../<Module>/<Header>.gen.h per reflected header.
  • Intermediate/.../<Module>/<Module>.gen.cpp — aggregator.
  • Intermediate/.../<Module>/<Module>.gen.manifest — text manifest listing every input source file and the generated files it produced. This is the file XBT uses for cross-language incremental builds: when a .cs changes, XBT reads the manifest to discover which .gen.h may have changed and reinvalidates downstream .cpp compiles whose .deps records reference those headers.

9.3 Cross-language compatibility

XHT reads both C++ headers (single-pass marker tokenizer) and attribute-marked .cs sources from the same module (Contract Section 1.1). It emits unified registration scaffolding so a single FClass entry can describe a type whose .h declares the C++ surface and whose .cs declares the C# surface. XBT does not need to participate in that — XBT only sees the manifest go in and the per-module outputs come out.

9.4 The XHT actions (REVISED Rev 2 — split into ParseHeaders + EmitReflection)

Per the Rev 2 audit, XHT's work splits into two action types so the executor can parallelise across modules at finer grain:

  • ParseHeadersAction: one per module. Prerequisites: every .h and .cs in the module + the JSON manifest + the binary FBS sidecar + XHT's own binary content hash. Produces: a per-module token-AST cache file under Intermediate/.../<Module>/<Module>.tokens.bin.
  • EmitReflectionAction: one per module. Prerequisite: the corresponding ParseHeadersAction's output. Produces: .gen.h per reflected header + <Module>.gen.cpp + <Module>.gen.manifest.

The split lets module B's ParseHeadersAction run in parallel with module A's EmitReflectionAction — useful when modules are large enough that parse-phase becomes a sequential bottleneck. The token-AST cache is also separately invalidatable: an edit that changes a header's reflection markers reparses only that module, not every module that includes the header.

10. XIL2CPP Integration

XBT invokes XIL2CPP the same way it invokes XHT. The two are independent — XHT extracts reflection metadata, XIL2CPP transpiles C# source — and they run concurrent, not sequential, in the action graph (Rev 2; see Section 10.6).

10.1 Invocation

XIL2CPP.exe -Manifest=Intermediate/Build/MiningTrainingEditor/Development/Manifest.json
            -ManifestBin=Intermediate/Build/MiningTrainingEditor/Development/Manifest.bin
            -Module=XScoring

10.2 Outputs

For each .cs in the module's SourceFiles.CSharp, XIL2CPP emits a transpiled .cpp + paired .h under Intermediate/.../<Module>/Transpiled/. Each emitted symbol is mangled per Contract Rev 11 Section 2 using the Itanium-ABI-style length-prefixed components rule. GC root scaffolding emits using the span-based ABI (Contract Rev 11 Section 3: XGC_RegisterRootSpan family, not per-slot). Exception codegen splits per Contract Rev 11 Section 5 (shim/direct). C# string mapping is per Contract Section 6.

10.3 Reproducibility forwarding

XBT forwards the platform's reproducibility flags to XIL2CPP via the manifest. XIL2CPP propagates these through to the generated C++ headers (e.g. predicating #line directives so cross-machine line-number consistency holds). The forwarded flags now include the full envelope in Section 19.1 (not just /Brepro).

10.4 Downstream compile

XBT then schedules a CompileCppAction for each transpiled .cpp exactly as if it were an authored .cpp. The transpiled headers participate in the include graph; the dependency cache covers them like any other header. From the C++ compile's perspective the file is indistinguishable from a hand-written one — that is the contract's intent.

10.5 The XIL2CPPAction

One action per module containing C# sources. Prerequisites: every .cs in the module + manifest (JSON + FBS) + XIL2CPP's own binary content hash + XCoreXObject's exported header surface (for the GC ABI emit, per Contract Section 3.1). Produces: transpiled .cpp/.h + a per-module transpilation manifest listing the inputs and produced outputs.

10.6 Concurrent XHT + XIL2CPP scheduling (REVISED Rev 2 — Contract Rev 11 #4)

Rev 1 implied a sequential order: XHT first, then XIL2CPP. Contract Rev 11 corrects this: the two run concurrently. XHT does not depend on XIL2CPP output; XIL2CPP does not depend on XHT output (their interleaved consumption happens at the compile step on the generated cpp files, which is downstream of both).

The action graph reflects this: EmitReflectionAction(M) and XIL2CPPAction(M) for the same module M are independent peers; their only common predecessor is WriteManifestAction. The executor schedules them in parallel within the available worker pool. This typically halves the latency of the prologue (the portion of the build before CompileCppActions can start).

12. Engine Version Enforcement

Per plan Section 2 Plugin versioning & pinning row (Rev 8 + Rev 9 compatibility-from-first-build) and Contract Section 9.4.

12.1 Inputs

  • /Engine/Engine.xengine — declares the engine's EngineVersion (e.g. "0.1.0"). Currently committed at the repo root.

14. Project File Generation

Per plan Section 5 MVP list (IDE delegation is implicit in the developer workflow; explicit Rev 10 commitment is in this spec). MVP outputs are Rider and clangd; Visual Studio and Xcode are Phase 2.

14.1 Lazy generation (footgun #9)

UBT regenerates project files for the full cross-product of targets × platforms × configurations, which is slow at XPact scale (3 targets × 3 platforms × 5 configurations × ~200 modules). XBT instead generates project files only for the target the IDE has selected, identified by the CLI flags passed to GenerateProjectFiles. The first invocation per session generates; subsequent invocations of the same target are cached.

14.2 Rider

Emits .idea/ directory tree at the project root. Module-level .idea/modules.xml + per-module .iml with the right source roots and dependencies. Build commands invoke XBT directly (mirrors UBT's delegation model; Rider sees a "fake" toolchain whose compile button shells out to XBT.exe Build).

14.3 clangd

Emits compile_commands.json at the repo root containing one entry per .cpp (authored, XHT-generated, XIL2CPP-generated) with the full compile-command vector. clangd consumes this for IntelliSense; the file is regenerated on every GenerateProjectFiles invocation. C# files are not in compile_commands.json (clangd doesn't read them); C# editing in clangd-aware editors is via a separate omnisharp.json XBT can emit as a sidecar.

14.4 Delegation back to XBT

Generated project files invoke XBT.exe Build for actual compilation. The IDE's per-file build is mapped to a single CompileCppAction XBT exposes through the RunXHT / RunXIL2CPP / WriteManifest trio (which expose lower-level entry points for IDE single-file actions). Mirrors UBT's delegation model.

15. Caching (REVISED Rev 2)

Three layers, all content-hash-keyed, none mtime-keyed (footgun #1 preempt).

15.1 TargetMakefile — complete cache key (REVISED Rev 2)

A binary-serialised pre-built action graph + module-info object stored at Intermediate/Build/<Target>/<Config>/Makefile.bin. Rev 1's listed cache-key inputs were incomplete; the Rev 2 audit (finding #3) requires the key to be the entire reproducibility envelope — if it influences output, it influences the cache key. The explicit list:

  1. Descriptor inputs: content hash of every .Build.toml, .Build.expr, .Target.toml in the active scope set.
  2. Plugin descriptors: content hash of every reachable .xplugin.
  3. Project descriptor: content hash of the .xproject.
  4. Engine descriptor: content hash of /Engine/Engine.xengine.
  5. XBT binary: content hash of XBT.exe.
  6. XHT binary: content hash of XHT.exe.
  7. XIL2CPP binary: content hash of XIL2CPP.exe.
  8. Contract surface: the auto-derived ContractVersion (Section 8.1).
  9. .NET SDK version: the major.minor.patch of the .NET runtime hosting XBT.
  10. Toolchain version: XToolChain.ToolchainVersion for every toolchain referenced by the target.
  11. Sim-path policy files: content hash of XSimPathBannedAPIs.txt and XSimPathMathOverrides.h. These were missed in Rev 1.
  12. Architecture: the target architecture string, even when omitted from on-disk paths (Section 18.1).
  13. FipsMode flag: the boolean from TargetRules.bFipsMode.
  14. StationRole: the role from TargetRules.StationRole (affects hot-reload eligibility per Section 16.4).
  15. Reproducibility envelope flag set: a hash of the toolchain's emitted reproducibility flag list per Section 19.1 (defends against a toolchain upgrade that silently changes flag defaults).

On a Makefile hit, XBT skips the entire descriptor parse + module-graph walk and goes straight to action execution. This is the largest single perf win for incremental builds. On a miss, all 15 inputs are recomputed.

15.2 XActionHistory

FileItem → IoHash(commandVersion + responseFile + CacheKeyComponents + relevant env), partitioned by CacheBucket. Stored at Intermediate/Build/<Target>/<Config>/ActionHistory.<Bucket>.bin. CurrentVersion auto-derived from the SHA-256 of the IExternalAction field set (footgun #8 preempt). The CacheKeyComponents field (Section 5.2) lets actions declare hidden inputs that don't appear in the command line but still influence output (SimdLevel, FpSemantics, FIPS mode, etc.).

15.3 XCppDependencyCache

Per-TU header trees from MSVC /showIncludes and Clang -MD. Each TU's .deps records the full transitive include set with content hashes. On the next build, XBT replays content hashes and reinvalidates if any included header has changed.

15.4 SharedPCH — include-order policy (REVISED Rev 2)

When two or more non-SimPath modules in a target use the same SharedPCHHeaderFile, XBT generates a single precompiled-header artefact at Intermediate/.../PCH/PCH.<ContentHash>.h (file name uses the content hash of the inputs — mirrors UE pattern but with hash-named files for cleaner caching). MSVC consumes via /Yu, Clang via -include-pch. SharedPCH is opt-in via PCHUsage = UseSharedPCHs on the module rules; default is Default which lets XBT pick.

Include-order policy (NEW Rev 2 — audit finding #12): the SharedPCH header's #include lines are emitted in alphabetical-by-logical-path order. The order is independent of the declared order in any .Build.toml, of filesystem enumeration, and of build-machine environment. This guarantees deterministic PCH bytes for a given input set across runs and machines.

SimPath exclusion (NEW Rev 2): SimPath modules are forced to PCHUsage = NoSharedPCHs (Section 4.5). Additionally, any .gen.h emitted into a SimPath module is excluded from any SharedPCH consumed by non-SimPath callers — the .gen.h may carry sim-path-specific macro state that would leak into non-sim-path code.

15.5 BLAKE3 throughout

XBT uses BLAKE3 as its content-hash algorithm for all three cache layers. BLAKE3 is fast (typically 6 GB/s single-threaded), unkeyed, 256-bit output, has stable cross-platform implementations, and matches the spirit of UE's IoHash.

When XLiveCoding cascades a patch, the patched DLL has the same module name as the live module — it cannot share a path or the OS file lock will reject the write. Rev 2 reserves a known location at Phase 1 so Phase 2 does not need to negotiate one:

/Intermediate/Build/<Target>/<Configuration>/LiveCoding/<Module>.patch.<gen>.dll

Where <gen> is a generation counter (monotonically increasing per patch) so patches can be ordered and prior generations cleaned up. Phase 1 XBT does not write to this location; it does not even create the directory. Phase 2 XLiveCoding writes here; XBT's subset-build action graph outputs to this path when invoked with -LiveCoding=true. The path is reserved — nothing else writes to LiveCoding/ — so Phase 2 can rely on collision-free naming.

17. Plugin Discovery and Enumeration (REVISED Rev 2)

Per plan Section 2 Plugins row (Rev 6 three-tier) and Folder structure row.

17.1 Walk

XBT walks the three plugin roots:

  • /Engine/Plugins/<Plugin>/<Plugin>.xplugin — engine plugins.
  • /Studio/Plugins/<Plugin>/<Plugin>.xplugin — studio plugins.
  • /Projects/<P>/Plugins/<Plugin>/<Plugin>.xplugin — project plugins.

The walk is parallel (each root spawns a discovery task). Results aggregate into a ConcurrentDictionary<string, PluginInfo>.

17.2 Shadow precedence — all observed records (REVISED Rev 2 — audit finding #8)

If a plugin name appears in two tiers, the higher (closer-to-product) tier wins. Project plugin HMIPanels shadows Studio plugin HMIPanels; Studio plugin HMIPanels shadows Engine plugin HMIPanels. Mirrors UBT pattern.

Rev 1 recorded only the winning shadow's content hash. The Rev 2 audit identifies this as a cache-key correctness bug: a non-shadowed plugin elsewhere on the filesystem could be edited and the cache would not invalidate. Rev 2 records all observed plugin descriptors of each name, tier-tagged, with shadow resolution explicit:

// In the TargetMakefile cache key:
"PluginShadowRecords": [
  {
    "Name": "HMIPanels",
    "Resolved": { "Tier": "Project", "Path": "Projects/Mining-Training/Plugins/HMIPanels/HMIPanels.xplugin", "Hash": "..." },
    "Shadowed": [
      { "Tier": "Studio", "Path": "Studio/Plugins/HMIPanels/HMIPanels.xplugin", "Hash": "..." },
      { "Tier": "Engine", "Path": "Engine/Plugins/HMIPanels/HMIPanels.xplugin", "Hash": "..." }
    ]
  }
]

Every recorded hash participates in the makefile cache key. Editing the shadowed Studio-tier HMIPanels descriptor now correctly invalidates the makefile, even though the Project-tier shadow wins resolution. This prevents the spurious-no-rebuild case the audit identified.

17.3 EngineVersion validation

For every discovered .xplugin, XBT validates MinEngineVersion ≤ engine ≤ MaxEngineVersion up-front (before any module-graph walk). Failure mode: fail-fast, exit 23. Per plan Rev 8: this is a deliberate divergence from UBT, which warns and continues. UBT's warn-and-continue causes downstream build failures with unhelpful diagnostics; XPact prefers a single clear diagnostic at the earliest point.

17.4 Plugin disable

A project's .xproject can disable an enabled plugin by name. Disabled plugins are still discovered (so the disable list is validated against actual plugin presence) but their modules do not enter the dependency graph.

20. Threading Model

XBT's own threading is conservative and easy to reason about.

20.1 Main thread

Mode dispatch, CLI parse, manifest emit, ActionGraph operations (Link, CheckForConflicts, DetectActionGraphCycles, Sort, BuildSubset). These are inherently serial — running them on multiple threads buys nothing and risks ordering nondeterminism.

20.2 Worker pool

Sized to Environment.ProcessorCount (overridable with -Workers=N). The pool services:

  • Action execution (Section 6).
  • Descriptor parsing across scopes (Section 3; each scope parses in parallel).
  • Plugin discovery (Section 17.1; each plugin root walks in parallel).
  • Manifest assembly (per-module manifest entry construction).

No global locks. Per-scope cache locks (one lock per descriptor scope; one lock per ActionHistory bucket). Lock granularity is fine enough that contention is rare in practice.

20.3 Cancellation threading (NEW Rev 2 — audit MINOR #15)

In-process XHT and XIL2CPP (the Phase 2 perf option per Section 9 / Section 10) receive the cancellation token through their entry-point signature. The check points are: at every foreach over modules, at every per-file iteration within a module, and immediately before any write to a temp file. Subprocess XHT and XIL2CPP receive cancellation through SIGINT / Ctrl-C in the same way as any other action subprocess. The 5-second grace period in Section 6.4 applies uniformly.

21. Error Handling and Diagnostics (REVISED Rev 2)

21.1 Diagnostic format

XBT emits diagnostics in MSBuild's file(line,col): error CODE: message format so IDEs and CI dashboards can parse them with the same regex they use for compiler errors. Each diagnostic carries an XBT-specific code (per Contract Section 13; per-diagnostic codes have the form XBT<NNN>).

21.2 Streaming JSON error channel (NEW Rev 2 — audit finding #5)

Rev 1 wrote a single post-hoc JSON build log at end of build. Rev 2 adds a streaming JSON channel that emits diagnostics in real-time, suitable for IDE / CI subscription.

The channel is implemented two ways depending on platform:

  • Linux / Android: a dedicated file descriptor (FD 3 by default, configurable via -JsonFd=N). The IDE opens a pipe and passes the read end as FD 3.
  • Windows: stdout lines prefixed with the sentinel @@XBT-JSON@@ . The IDE filters these out of the human-visible stream. The fallback Linux/Android encoding is the same when no extra FD is available.

Every diagnostic produces one JSON line on the channel and one human-readable line on stderr. They are content-equivalent. The JSON record shape:

{"action":"compile","module":"XScoring","level":"error","code":"XBT070",
 "file":"Engine/Source/Runtime/XScoring/Private/XScoring.cpp","line":42,"column":7,
 "message":"undefined reference to `XSleef_sin'","tier":"Engine","simpath":true,
 "target":"MiningTrainingEditor","configuration":"Development","platform":"Win64",
 "timestamp":"2026-05-19T14:00:42.123Z"}

The channel is streaming — records are written and flushed as they happen, not buffered until end of build. This lets the IDE highlight a compile error within milliseconds of the compile failing, not at end-of-build.

21.3 Cancellation (REVISED Rev 2)

Ctrl-C / SIGINT installs a CancellationToken. The dispatcher stops queueing new actions; in-flight subprocesses are given a 5-second grace period; partial outputs follow the pinned temp-file convention (Section 6.4) and are swept either by the current process (on SIGINT) or at next startup (on taskkill /F); the build log records the cancellation with timestamp; the streaming JSON channel emits a final {"event":"cancelled","timestamp":"..."} record. Exit code 130.

21.4 Structured build log (REVISED Rev 2 — streaming + provenance)

Every build writes Intermediate/Build/<Target>/<Config>/BuildLog.json incrementally (not all-at-end). The log is well-formed JSON throughout the build — partial logs from cancelled builds are still parseable. Schema:

Every action carries full provenance: source file × module × target × configuration × platform × tier. 22. Threading the Test Loop — How XBT Validates Itself

Per plan Section 6: every system has a sibling tests module; per Section 9: every system has a four-layer verification approach. XBT's tests module (XBT.Tests) covers all of XBT.

22.1 Unit tests

  • ActionGraph cycle detection: synthetic graphs with known cycles → assert DetectActionGraphCycles reports them at the right edge set.
  • ActionGraph.BuildSubset: synthetic graph with known structure; assert BuildSubset(["A","B"]) returns exactly the transitive predecessor set of A ∪ B.
  • ActionHistory hashing: hash collisions across the field set are detected (the SHA-256 derivation in Section 5.4 is exercised on representative field permutations, including the CacheKeyComponents field).
  • ModuleRules validation: a tier-violating link-dep entry → expected exit 21; a banned-flag entry on SimPath → expected exit 41; a SimPath module declaring UseSharedPCHs → expected exit 30; a non-SimPath module with SimdLevel.AVX succeeds (no rule); a SimPath module with SimdLevel.AVX → expected exit 30.
  • Manifest serialisation round-trip: build manifest, write JSON + FBS, read JSON + FBS, build manifest, assert structural equality (both formats).
  • JSON parse safety: a manifest with depth > 64 / size > 100 MB / array length > 64K → expected exit 50; FlatBuffers verifier rejection of a tampered sidecar → expected fallback to JSON, then exit 50 if JSON also fails.
  • Descriptor parse: malformed .Build.toml → expected exit 30 with file:line in the diagnostic; .Build.expr referencing a disallowed name → expected exit 30.
  • Copyright validation: a synthetic file missing the header → expected exit 40 with the file path in the diagnostic.
  • Atomic-rename + orphan sweep: simulate taskkill /F mid-build (kill subprocess; rerun XBT); assert orphan temp files are deleted at next startup.

22.2 Integration tests

A fixture project under XBT.Tests/Fixtures/HelloWorldXPact/ exercises every action type end-to-end:
