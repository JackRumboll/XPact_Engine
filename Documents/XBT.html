0. Purpose, Scope, Tier Membership

XBT is the build orchestrator for every XPact build. It is the first system implemented after the Toolchain Contract (plan Section 4 Step 1), and every later system — engine, editor, studio plugin, project — is compiled by XBT. XBT is the analog of Unreal Engine's UnrealBuildTool (UBT), restructured to honour the foundational decisions locked in plan Section 2 and the seams locked in the Toolchain Contract.

XBT is delivered as a single C# .NET 8 self-contained standalone executable. It has no XPact runtime dependencies — it cannot reference XCore, XCoreXObject, or any engine type. The build artefact is a Win64 / Linux / Android-host-x86_64 binary plus a small set of data files (banned-API list, default toolchain table, contract-version manifest). XBT is invoked by developer scripts, by IDE delegation hooks (Rider, clangd), and by XAutomationTool's release pipeline.

Tier membership. Plan Section 3: "All inventory systems are Engine-tier (live in /Engine/)." XBT's source lives under /Engine/Source/Programs/XBT/. XBT is itself reusable across every Simgenics training product and every plugin, mirroring the engine's universal-reuse posture (plan Section 2 Folder structure row, Rev 6).

Position in the build pipeline. XBT drives the pipeline locked in Toolchain Contract Section 10.1: discovery and graph build, manifest emit, XHT invocation, XIL2CPP invocation, copyright validation, C++ compile actions, link. Every step is an action in XBT's action graph; XBT is itself the only tool that owns the graph. XHT (System 2) and XIL2CPP (System 6) are sub-tools XBT invokes, never the other way round.

What XBT does not own. It does not parse reflection markers (that is XHT's job, per Contract Section 7). It does not transpile C# (that is XIL2CPP's job, per Contract Sections 2, 3, 5, 6). It does not own GC root primitives (those are XCoreXObject's job, per Contract Section 3.5). It does not own runtime hot-patch dispatch (XLiveCoding's job, plan Section 2 Hot-reload row). It does not handle deployment, code signing, or symbol upload (XAutomationTool's job, plan Section 3 Layer 0). XBT's responsibility ends when the link step produces a well-formed binary that the next pipeline stage can pick up.

Phase awareness. XBT MVP is Phase 1 in plan Section 5 (MVP subset). The Phase 2 readiness items called out in this document — distributed execution, full Live Coding integration, advanced PCH, Visual Studio project files — are designed as no-cost stubs at Phase 1 so post-MVP work does not require XBT redesign.

1.4 Output format

Default output: human-readable progress to stdout, errors and diagnostics to stderr, structured JSON build log to Intermediate/Build/<Target>/<Config>/BuildLog.json. The JSON build log carries action-level granularity (mode, action type, prerequisites, outputs, duration, exit code) and is consumable by IDE log viewers and CI dashboards. Cancellation via Ctrl-C is graceful: outstanding actions are allowed to complete or fail cleanly; partially-produced outputs are removed; the build log records the cancellation event. This is a Phase 1 commitment and the analog of UBT's UseStartupTraceListener option, refined.

3. RulesAssembly — .Build.cs / .Target.cs Loading

Per Contract Section 9.5: "XPact's choice between Roslyn-compiled rules and a declarative-only subset is internal to XBT — either approach satisfies this contract. The contract only requires: hash-keyed caching of the rules artefact; deterministic ordering of module discovery; clear failure mode when a .Build.cs fails to compile or load." XBT chooses Roslyn-compiled rules, mirroring UBT's well-tested approach but with the UE footguns preempted.

3.1 Compilation

XBT discovers .Build.cs and .Target.cs files by walking the conventional roots:

  • /Engine/Source/<Tier>/<Module>/ — engine modules (where <Tier> is the Unreal-convention sub-folder per plan Section 6 footnote, e.g. Runtime, Editor, Developer, Programs).
  • /Engine/Plugins/<Plugin>/Source/<Module>/ — engine plugins.
  • /Studio/Plugins/<Plugin>/Source/<Module>/ — studio plugins.
  • /Projects/<P>/Source/<Module>/ — project modules.
  • /Projects/<P>/Plugins/<Plugin>/Source/<Module>/ — project plugins.

Compilation uses Microsoft.CodeAnalysis.CSharp (Roslyn). The compilation factory pins:

  • LanguageVersion.CSharp12 (matches plan Section 2 C# version row).
  • OptimizationLevel.Release.
  • deterministic: true (solves UE footgun #6 — UE often forgets this flag).
  • SourceHashAlgorithm.Sha256 for embedded source hashes.

Per-scope assembly emission: an Engine-scope assembly aggregates all /Engine/Source/<...>/.Build.cs files; a per-plugin assembly aggregates the plugin's .Build.cs set; a per-project assembly aggregates the project's. This scope-split solves UE footgun #2 (one giant engine-wide rules assembly with a global lock costs ~2s) and lets XBT compile assemblies in parallel.

3.2 Cache

The assembly cache is keyed by a JSON manifest of: each input source file's path + content hash (BLAKE3, never mtime — solves UE footgun #1), the contract version (so a contract revision invalidates everything), and XBT's own binary content hash (so a self-rebuild invalidates everything). Cache entries are stored at Intermediate/Build/RulesAssemblies/<Scope>.<Hash>.dll with a sidecar JSON manifest.

Invalidation rules:

  • Any input .Build.cs content hash differs → recompile.
  • Any input .Target.cs content hash differs → recompile (target-rule files participate in the same cache key).
  • XBT binary hash differs → recompile (handles XBT.dll updates that change rule API surface).
  • Contract version differs → recompile.

3.3 Failure handling

If any .Build.cs fails to compile, XBT prints the diagnostic in Roslyn's standard format (file path + line + column + diagnostic ID + message) and exits with code 30. Multiple errors from a single scope are reported together so the user can fix them in one pass.

3.4 Deterministic module discovery

Module discovery enumerates directories in a stable order: alphabetical by absolute path after canonicalising case (Windows) and resolving symlinks. This guarantees the JSON manifest's Modules[] array (Contract Section 10.2) is the same across runs and machines.

4.4 Tier validation

After every .Build.cs has been instantiated, XBT walks the directed dependency graph and rejects any edge violating Contract Section 9.3: Engine modules may depend on Engine only; Studio modules on Studio or Engine; Project modules on any tier. Violations exit 21 with a diagnostic naming both endpoints. The check is on the declared Tier field, not the source-tree path (plan Section 2 Tier dependency enforcement row Rev 7).

4.5 FPSemantics auto-set on SimPath

If SimPath = true and FPSemantics is still at Default after rule construction, XBT promotes it to Precise before passing the rule to the action graph. Explicit FPSemantics = FPSemantics.Imprecise on a SimPath module fails the build (the combination is incoherent; Contract Section 4 bans the imprecise flags).

4.6 Engine version compatibility

Contract Section 9.4 plus plan Section 2 Plugin versioning row Rev 8 + Rev 9: XBT reads /Engine/Engine.xengine, every reachable .xplugin, and the project's .xproject. The project's EngineVersion must equal the engine's. Every enabled Studio plugin's MinEngineVersion ≤ EngineVersion ≤ MaxEngineVersion. Violations exit 23. Engine plugins are tip-of-main within the engine version (their version equals the engine's) and skip the range check.

Mirrors UBT's IExternalAction design but with the UE footguns preempted. Every step that produces or consumes files is an action. The graph is built once per build, validated for cycles and conflicts, then handed to the executor.

public interface IExternalAction
{
    XActionType ActionType { get; }

    // SortedSet for determinism (mirrors UBT footgun #6 fix).
    SortedSet<FileItem> PrerequisiteItems { get; }
    SortedSet<FileItem> ProducedItems { get; }
    SortedSet<FileItem> DeleteItems { get; }

    // Command surface.
    string CommandPath { get; }
    string CommandArguments { get; }
    string ResponseFileContents { get; }
    string WorkingDirectory { get; }
    string CommandDescription { get; }
    string StatusDescription { get; }

    // Auto-derived from the field set above by ActionGraph.Link — solves
    // UE footgun #8 (UE's ActionHistory.CurrentVersion must be manually
    // bumped on schema change; XPact computes it from a hash of the field set).
    byte[] CommandVersion { get; }

    // Scheduling.
    int Weight { get; }              // 1.0 = single core; >1 means action runs multi-threaded internally.
    bool bCanExecuteRemotely { get; } // Phase 1: ignored. Phase 2: XPactBuildAccelerator consults.
    string CacheBucket { get; }      // group for sharing across builds (used by Phase 2 DDC).
    ArtifactMode ArtifactMode { get; }
}

public enum ArtifactMode { None, Cacheable, NotShareable }

Flat bCanExecuteRemotely flag. UBT carries a per-executor matrix (bCanExecuteRemotelyWithSNDBS, bCanExecuteRemotelyWithXGE, bCanExecuteRemotelyWithUBA). XPact flattens to one flag because there is exactly one Phase 2 distributed executor (XPactBuildAccelerator), and exposing per-vendor flags calcifies the design against a single vendor — the same trap UBT fell into.

5.3 ActionGraph operations

ActionGraph.Link() builds the producer map from FileItem → IExternalAction (every produced FileItem must have exactly one producer; duplicate-producer errors are caught here). CheckForConflicts() verifies that no two actions produce the same FileItem with different commands (UBT shows this can happen when two modules accidentally share a generated path; XBT catches it earlier). DetectActionGraphCycles() runs a DFS for cycles; on detection, the cycle is printed and the build exits 80. Sort() produces a topological order with a deterministic tiebreaker (by CommandVersion) so the same graph yields the same execution order across machines.

5.4 ActionHistory

Per Contract Section 10.3: incremental rebuilds. XBT's ActionHistory is a binary-serialised map from FileItem → IoHash(commandVersion + responseFileContents + relevant flags), partitioned by CacheBucket so two unrelated buckets can be read/written in parallel.

CurrentVersion is derived from a hash of the IExternalAction field set — specifically, the SHA-256 of the field names and types in declaration order. Any schema change to IExternalAction changes the version automatically; UE's ActionHistory.CurrentVersion = 3 manual bump is gone.

5.5 XCppDependencyCache

Per-TU header-include graph, captured from the compiler's dependency output (/showIncludes on MSVC, -MD on Clang). Stored in Intermediate/Build/<Target>/<Config>/Deps/<ModuleHash>.deps. On the next build, XBT replays each consumed include's content hash; if any differs, the consumer TU is recompiled.

6. Executor (Phase 1 = local only)

Phase 1 XBT ships with a single executor: ParallelExecutor. Sized by default to Environment.ProcessorCount; configurable via -Workers=N. Worker threads pull from a job queue; each job is one IExternalAction. The queue is sorted before dispatch by CommandVersion so dispatch order is deterministic (mirrors UBT footgun #6 fix at the executor level).

6.1 Scheduling

Topological order from ActionGraph.Sort respects the dependency graph; within a single ready-set, the dispatcher picks actions in CommandVersion order to keep ordering deterministic for log diffing and reproducibility tests. Actions with Weight > 1 are dispatched only when at least Weight workers are free.

6.2 Failure isolation

Each action runs in its own subprocess (or in-process when both XHT and XIL2CPP are loaded as libraries — XBT picks subprocess for Phase 1 simplicity, in-process is a Phase 2 perf option). A non-zero exit code captures stderr to the build log and marks the action failed. Failure propagates: dependent actions are skipped, the build's final exit code reflects the worst category encountered (see Section 1.3). One action's failure never corrupts another's outputs — each action writes to a private temp file and atomically renames into place on success.

6.3 The bCanExecuteRemotely flag

Present on IExternalAction but ignored at Phase 1. Phase 2 work (post-MVP per plan Section 5): XPactBuildAccelerator (plan Section 3 Layer 0 Rev 7) consumes the flag and dispatches eligible actions to a worker pool of remote machines. XBT must not preclude this; the executor surface in XBT.Executor is an interface, not a single class, so Phase 2 can register a second implementation alongside ParallelExecutor.

6.4 Ctrl-C / cancellation

SIGINT installs a cancellation token. Outstanding actions are given a brief grace period (5 seconds) to complete cleanly. After grace, in-flight subprocesses are killed; their partial outputs are removed; the build log records the cancellation event. Exit code 130 (POSIX SIGINT convention).

7.2 XMSVCToolChain (Win64)

Supports MSVC ≥ 17.10 (VS 2026 BuildTools) and clang-cl ≥ 18 as the alternate front-end. DiscoverEnvironment probes the registry and runs vswhere.exe to locate the MSVC installation (mirrors UBT's VCEnvironment). Toolchain selection per target is in TargetRules; default is MSVC.

FPSemantics translation: FPSemantics.Precise → /fp:precise; FPSemantics.Imprecise → /fp:fast (only valid for non-SimPath modules, see Section 4.5). On clang-cl, the same semantics map via /clang:-ffp-contract=off → off, etc.; XBT prefers the cl-style flag when both are accepted.

Reproducibility: /Brepro is unconditional on every Win64 build, not only sim-path TUs (Contract Section 2.1). Without it, the embedded timestamp in the PE breaks byte-identical builds.

7.3 XClangToolChain (Linux + Android)

Linux: Clang ≥ 18, located via the LLVM_HOME environment variable or /usr/lib/llvm-18/-style default paths.

Android: Clang via NDK r26+. NDK location via ANDROID_NDK_ROOT. The toolchain produces .so targeting ARM64-v8a and (Phase 2 readiness) x86_64-emulator.

Reproducibility flags: -frandomize-layout-seed-file= pinned to an empty deterministic seed, -fno-ident for object-file determinism, -Wl,--build-id=none at link (Contract Section 2.1).

7.4 SimPath additions (Contract Section 4.3)

When a module has SimPath = true, the toolchain class injects:

  • A force-include of XSimPathMathOverrides.h via /FI XSimPathMathOverrides.h (MSVC) or -include XSimPathMathOverrides.h (Clang).
  • Banned-flag check: any flag in the per-platform banned set (/fp:fast, -ffast-math, -mfma, etc.) on a SimPath module fails the build with diagnostic + exit 41.
  • Link-line exclusion of platform libm (/NODEFAULTLIB:libcmt.lib components selectively on MSVC; -nostdlib++ equivalent posture on Clang) plus addition of the vendored Sleef library. Any unresolved transcendental at link is then a clear diagnostic.

9. XHT Integration

XBT invokes XHT either as a subprocess or in-process via the EpicGames.UHT-style library pattern (UE reference brief). Phase 1 picks subprocess for simplicity; the in-process path is a Phase 2 perf option. The choice is internal — XHT sees only the manifest.

9.1 Invocation

# XBT calls:
XHT.exe -Manifest=Intermediate/Build/MiningTrainingEditor/Development/Manifest.json
        -Module=XScoring

XBT can also call XHT once with no -Module= filter, in which case XHT processes every module in the manifest. XBT chooses the per-module form so XHT actions can run in parallel across modules (Contract Section 10.1 step 3).

9.2 Outputs

XHT writes outputs to paths derived from the manifest's BaseDirectory + OutputDirectory conventions; XBT discovers them via the per-module text manifest XHT emits alongside its binary outputs (Contract Section 7.1). XBT does not parse .gen.h or .gen.cpp — their content is opaque (plan Section 4 Rev 5 clarification).

Outputs per module (Contract Section 7.1):

  • Intermediate/.../<Module>/<Header>.gen.h per reflected header.
  • Intermediate/.../<Module>/<Module>.gen.cpp — aggregator.
  • Intermediate/.../<Module>/<Module>.gen.manifest — text manifest listing every input source file and the generated files it produced. This is the file XBT uses for cross-language incremental builds: when a .cs changes, XBT reads the manifest to discover which .gen.h may have changed and reinvalidates downstream .cpp compiles whose .deps records reference those headers.

9.3 Cross-language compatibility

XHT reads both C++ headers (single-pass marker tokenizer) and attribute-marked .cs sources from the same module (Contract Section 1.1). It emits unified registration scaffolding so a single FClass entry can describe a type whose .h declares the C++ surface and whose .cs declares the C# surface. XBT does not need to participate in that — XBT only sees the manifest go in and the per-module outputs come out.

9.4 The XHTAction

One action per module. Prerequisites: every .h and .cs in the module + the JSON manifest + XHT's own binary content hash. Produces: every output listed in the per-module text manifest XHT emits. The text manifest's existence is itself a produced item; on its first emit, XBT records the output set and uses it for subsequent incremental decisions.

10. XIL2CPP Integration

XBT invokes XIL2CPP the same way it invokes XHT. The two are independent — XHT extracts reflection metadata, XIL2CPP transpiles C# source. Their outputs both feed the C++ compile step.

10.1 Invocation

XIL2CPP.exe -Manifest=Intermediate/Build/MiningTrainingEditor/Development/Manifest.json
            -Module=XScoring

10.2 Outputs

For each .cs in the module's SourceFiles.CSharp, XIL2CPP emits a transpiled .cpp + paired .h under Intermediate/.../<Module>/Transpiled/. Each emitted symbol is mangled per Contract Section 2.2 with the locked _v1 contract version. GC root scaffolding (Contract Section 3), exception codegen (Contract Section 5), and C# string mapping (Contract Section 6) all emit at this stage.

10.3 Reproducibility forwarding

XBT forwards the platform's reproducibility flags to XIL2CPP via the manifest (the contract specifies that XIL2CPP's own build must be reproducible — /Brepro, -frandomize-layout-seed-file=, etc., per Contract Section 2.4 item 4). XIL2CPP propagates these through to the generated C++ headers (e.g. predicating #line directives so cross-machine line-number consistency holds).

10.4 Downstream compile

XBT then schedules a CompileCppAction for each transpiled .cpp exactly as if it were an authored .cpp. The transpiled headers participate in the include graph; the dependency cache covers them like any other header. From the C++ compile's perspective the file is indistinguishable from a hand-written one — that is the contract's intent.

10.5 The XIL2CPPAction

One action per module containing C# sources. Prerequisites: every .cs in the module + manifest + XIL2CPP's own binary content hash + XCoreXObject's exported header surface (for the GC ABI emit, per Contract Section 3.1). Produces: transpiled .cpp/.h + a per-module transpilation manifest listing the inputs and produced outputs (mirrors the XHT manifest pattern so XBT's incremental logic is uniform).

11. Copyright Validation

Per plan Section 2 Copyright / licensing row (Rev 6) and Contract Section 10.1 step 5: every authored .h, .cpp, .cs file in the build must begin with // Copyright Simgenics. All Rights Reserved. as its first line. /Engine/Source/ThirdParty/ is excluded; those files retain their original licensing headers.

11.1 Action

ValidateCopyrightAction runs before any CompileCppAction. Per source file: the action reads only the first line (a few hundred bytes at most) and matches the literal string. The action is cached by source-file content hash — an unchanged file is not re-validated. Implementation note: the cache key is the content hash, not the mtime, so re-cloning the repo does not re-trigger validation (footgun #1 preempt).

11.2 Failure mode

A missing or malformed header fails the build with exit 40 and a diagnostic naming the file's absolute path. Multiple offenders are batched into one error report so the developer can fix them in a single pass.

11.3 Standalone invocation

The ValidateCopyright CLI mode (Section 1.1) runs the action standalone — useful for CI pre-flight gates before a full build is attempted. -Paths= accepts multiple roots; -Exclude= accepts patterns (typically Engine\Source\ThirdParty).

12. Engine Version Enforcement

Per plan Section 2 Plugin versioning & pinning row (Rev 8 + Rev 9 compatibility-from-first-build) and Contract Section 9.4.

12.1 Inputs

XBT reads at module-resolution time:

  • /Engine/Engine.xengine — declares the engine's EngineVersion (e.g. "0.1.0"). Currently committed at the repo root.
  • Every reachable .xplugin — engine plugins, studio plugins, project plugins. Each declares its tier, its own version (for studio/project plugins), and (for studio plugins) MinEngineVersion + MaxEngineVersion.
  • <Project>.xproject — declares the engine version the project is built against + the plugin pin map.

12.2 Rules

  1. The project's EngineVersion must equal the engine's EngineVersion. (Future MAJOR-compat work may relax this; MVP requires equality.)
  2. Every enabled Studio plugin must satisfy MinEngineVersion ≤ EngineVersion ≤ MaxEngineVersion.
  3. Engine plugins are tip-of-main within the engine version; their version equals the engine's; they skip the range check.
  4. Pinned plugin versions in the project's .xproject map (e.g. "IndustrialEquipment": "^2.3") must be available and within the declared range.

12.3 Failure

Any violation exits 23 with a diagnostic naming all offending entries in one report. Example:

error XBT023: Engine-version compatibility violation.
  Engine: 0.1.0 (Engine/Engine.xengine)
  Project: Mining-Training (Projects/Mining-Training/Mining-Training.xproject)
    declares EngineVersion = 0.2.0 (mismatch — MVP requires equality with engine)
  Studio plugin: IndustrialEquipment 2.4.0 (Studio/Plugins/IndustrialEquipment/IndustrialEquipment.xplugin)
    declares MinEngineVersion = 0.2.0, MaxEngineVersion = 0.4.0
    not satisfied by engine 0.1.0

12.4 Standalone invocation

The ValidateEngineVersion CLI mode (Section 1.1) is standalone for CI pre-flight gates. It performs the same checks but does not require a full target / configuration selection.

13. Tier Enforcement

Per plan Section 2 Tier dependency enforcement row (Rev 7) and Contract Section 9.3.

13.1 Rules

  1. An Engine module may depend only on Engine modules.
  2. A Studio module may depend on Studio or Engine modules.
  3. A Project module may depend on any tier.
  4. The check is on the declared Tier field in .Build.cs, NOT on the source-tree path. Symlinked / restructured layouts do not change the declared tier.

13.2 Hoisting workflow

Per plan Section 2 Folder structure row (Rev 6): "Hoisting principle: when a behaviour gets used in a second product, it gets hoisted from /Projects/<A>/ into /Studio/. When something in /Studio/ proves universally applicable, it gets hoisted into /Engine/." When a .Build.cs changes its Tier value as part of a hoist, XBT cooperates with the hoisting workflow:

  • The hoist must move the module's source folder to the new tier's location and change the .Build.cs's Tier field.
  • XBT regenerates XCoreRedirects entries (plan Section 2 Cross-tier asset references row Rev 8) so existing assets referencing the old location resolve. The redirects file is emitted to the destination plugin/project's .xredirects with Scope = "Global" for a hoist (this is the documented use of global-scope redirects per plan Rev 9 plugin-namespace scoping).
  • The build then proceeds with the new tier. Existing dependents that still target the old name see the redirect and continue to build.

13.3 Failure

Any violation exits 21 with a diagnostic naming both endpoints and the offending edge. Example:

error XBT021: Tier violation in module dependency graph.
  Module: XCore (Tier = Engine, /Engine/Source/Runtime/XCore/XCore.Build.cs)
  declares PublicDependencyModuleNames = [..., "IndustrialEquipment", ...]
  but "IndustrialEquipment" has Tier = Studio
    (/Studio/Plugins/IndustrialEquipment/Source/IndustrialEquipment/IndustrialEquipment.Build.cs)
  Engine-tier modules may depend only on Engine-tier modules.

14. Project File Generation

Per plan Section 5 MVP list (IDE delegation is implicit in the developer workflow; explicit Rev 10 commitment is in this spec). MVP outputs are Rider and clangd; Visual Studio and Xcode are Phase 2.

14.1 Lazy generation (footgun #9)

UBT regenerates project files for the full cross-product of targets × platforms × configurations, which is slow at XPact scale (3 targets × 3 platforms × 5 configurations × ~200 modules). XBT instead generates project files only for the target the IDE has selected, identified by the CLI flags passed to GenerateProjectFiles. The first invocation per session generates; subsequent invocations of the same target are cached.

14.2 Rider

Emits .idea/ directory tree at the project root. Module-level .idea/modules.xml + per-module .iml with the right source roots and dependencies. Build commands invoke XBT directly (mirrors UBT's delegation model; Rider sees a "fake" toolchain whose compile button shells out to XBT.exe Build).

14.3 clangd

Emits compile_commands.json at the repo root containing one entry per .cpp (authored, XHT-generated, XIL2CPP-generated) with the full compile-command vector. clangd consumes this for IntelliSense; the file is regenerated on every GenerateProjectFiles invocation. C# files are not in compile_commands.json (clangd doesn't read them); C# editing in clangd-aware editors is via a separate omnisharp.json XBT can emit as a sidecar.

14.4 Delegation back to XBT

Generated project files invoke XBT.exe Build for actual compilation. The IDE's per-file build is mapped to a single CompileCppAction XBT exposes through the RunXHT / RunXIL2CPP / WriteManifest trio (which expose lower-level entry points for IDE single-file actions). Mirrors UBT's delegation model.

15. Caching

Three layers, all content-hash-keyed, none mtime-keyed (footgun #1 preempt).

15.1 TargetMakefile

A binary-serialised pre-built action graph + module-info object stored at Intermediate/Build/<Target>/<Config>/Makefile.bin. Invalidated when:

  • Any .Build.cs or .Target.cs content hash changes (forcing RulesAssembly recompile, in turn invalidating the Makefile).
  • Any .xplugin / .xproject / .xengine content hash changes.
  • XBT's binary content hash changes.
  • Contract version changes.

On a Makefile hit, XBT skips the entire RulesAssembly compile + module-graph walk and goes straight to action execution. This is the largest single perf win for incremental builds.

15.2 XActionHistory

FileItem → IoHash(commandVersion + responseFile + relevant env), partitioned by CacheBucket. Stored at Intermediate/Build/<Target>/<Config>/ActionHistory.<Bucket>.bin. CurrentVersion auto-derived from the SHA-256 of the IExternalAction field set (footgun #8 preempt).

15.3 XCppDependencyCache

Per-TU header trees from MSVC /showIncludes and Clang -MD. Each TU's .deps records the full transitive include set with content hashes. On the next build, XBT replays content hashes and reinvalidates if any included header has changed.

15.4 SharedPCH

When two or more modules in a target use the same SharedPCHHeaderFile, XBT generates a single precompiled-header artefact at Intermediate/.../PCH/PCH.<ContentHash>.h (file name uses the content hash of the inputs — mirrors UE pattern but with hash-named files for cleaner caching). MSVC consumes via /Yu, Clang via -include-pch. SharedPCH is opt-in via PCHUsage = UseSharedPCHs on the module rules; default is Default which lets XBT pick.

15.5 BLAKE3 throughout

XBT uses BLAKE3 as its content-hash algorithm for all three cache layers. BLAKE3 is fast (typically 6 GB/s single-threaded), unkeyed, 256-bit output, has stable cross-platform implementations, and matches the spirit of UE's IoHash. The Step 0.5 addendum (Contract Section 8.4) will canonicalise this choice; pending that, BLAKE3 is XBT's recommendation.

16. Live Coding Hook (Phase 2 Readiness, Phase 1 Stub)

Per plan Section 2 Hot-reload row + Hot-reload cascade row Rev 8 + Rev 10 UX/timeout addendum.

16.1 Architecture only at Phase 1

XBT exposes IActionGraphPatcher as a public interface. The patcher list is consulted by ActionGraph after Link() and before executor dispatch:

public interface IActionGraphPatcher
{
    string Name { get; }
    void Patch(ActionGraph graph, IReadOnlyDictionary<string, ModuleRules> modules);
}

Phase 1 returns an empty list. The plumbing is in place; the patcher implementations are not.

16.2 Per-toolchain patching (footgun #5)

Patchers register with a XToolChain subclass, not with an executable name. UE's Live Coding pattern hardcodes cl-filter.exe / cl.exe / clang-cl.exe / verse-clang-cl.exe in a switch statement; renaming the wrapper exe breaks Live Coding silently. XBT routes through XToolChain.GetActionPatchers() so the patcher inherits the toolchain's understanding of its own command line.

16.3 Phase 2 cascade design

Plan Section 2 Hot-reload cascade row Rev 8 mandates a two-phase apply: Phase 1 of the cascade compiles every dependent module (rollback supported by not committing); Phase 2 quiesces mutators and GC markers, then issues function-pointer / vtable rewrites (no rollback). XBT participates in Phase 1 (the compile-only pass). XLiveCoding is the system that owns Phase 2; XBT provides the action subset and the per-toolchain patchers.

16.4 Trainee / Server build disable

Plan Rev 10: Trainee + Server shipping builds disable XLiveCoding entirely so trainee sessions cannot freeze mid-procedure. XBT enforces this at TargetRules validation: bAllowHotReload on a module is rejected if the target is BuildTargetType.Game + BuildConfiguration.Shipping + a Trainee station role (the station role is conveyed in the target descriptor; for MVP, the Game-Shipping pair is sufficient because Trainee and Instructor share the Game target). Editor + Engineer-station builds default bAllowHotReload = true for modules tagged ModuleType = Editor.

17. Plugin Discovery and Enumeration

Per plan Section 2 Plugins row (Rev 6 three-tier) and Folder structure row.

17.1 Walk

XBT walks the three plugin roots:

  • /Engine/Plugins/<Plugin>/<Plugin>.xplugin — engine plugins.
  • /Studio/Plugins/<Plugin>/<Plugin>.xplugin — studio plugins.
  • /Projects/<P>/Plugins/<Plugin>/<Plugin>.xplugin — project plugins.

The walk is parallel (each root spawns a discovery task). Results aggregate into a ConcurrentDictionary<string, PluginInfo>.

17.2 Shadow precedence

If a plugin name appears in two tiers, the higher (closer-to-product) tier wins. Project plugin HMIPanels shadows Studio plugin HMIPanels; Studio plugin HMIPanels shadows Engine plugin HMIPanels. Mirrors UBT pattern. Useful for per-product overrides of shared studio behaviour.

17.3 EngineVersion validation

For every discovered .xplugin, XBT validates MinEngineVersion ≤ engine ≤ MaxEngineVersion up-front (before any module-graph walk). Failure mode: fail-fast, exit 23. Per plan Rev 8: this is a deliberate divergence from UBT, which warns and continues. UBT's warn-and-continue causes downstream build failures with unhelpful diagnostics; XPact prefers a single clear diagnostic at the earliest point.

17.4 Plugin disable

A project's .xproject can disable an enabled plugin by name. Disabled plugins are still discovered (so the disable list is validated against actual plugin presence) but their modules do not enter the dependency graph.

19. Determinism and Reproducibility

Per Contract Section 2.4 + Section 12.1 + plan Section 11 Foundation Prototype criterion (g): two clean builds of the same source on the same machine produce byte-identical compile + link outputs.

19.1 What XBT does

  1. Every sort is deterministic. SortedSet<FileItem> uses ordinal string comparison; the executor dispatcher tiebreaks ready actions by CommandVersion hash.
  2. Every cache key is content-hashed (BLAKE3) — never mtime. Footgun #1 preempt.
  3. Every Roslyn CSharpCompilation sets deterministic: true. Footgun #6 preempt; the option is global in XBT.Configuration's compilation factory.
  4. /Brepro on Win64 unconditional. -frandomize-layout-seed-file=, -fno-ident, --build-id=none on Linux/Android unconditional.
  5. XIL2CPP mangled symbols are reproducible by construction (Contract Section 2.4): purely structural, no hash, no random.
  6. Paths embedded in metadata go through CppRootPaths-equivalent canonicalisation. UBT's FileMetadataPrefetch race (footgun #7) is skipped at MVP — XBT does the prefetch synchronously at start-up if it does it at all.

19.2 Verification

The reproducibility test (Section 22.3) builds the same source twice in a row and asserts byte-identical artefacts. Pass criterion: zero diffs across the entire Intermediate/ + Binaries/ tree, modulo allowlisted timestamp-bearing files that the executor refused to emit at all.

20. Threading Model

XBT's own threading is conservative and easy to reason about.

20.1 Main thread

Mode dispatch, CLI parse, manifest emit, ActionGraph operations (Link, CheckForConflicts, DetectActionGraphCycles, Sort). These are inherently serial — running them on multiple threads buys nothing and risks ordering nondeterminism.

20.2 Worker pool

Sized to Environment.ProcessorCount (overridable with -Workers=N). The pool services:

  • Action execution (Section 6).
  • RulesAssembly compilation across scopes (Section 3.1; each scope compiles in parallel).
  • Plugin discovery (Section 17.1; each plugin root walks in parallel).
  • Manifest assembly (per-module manifest entry construction).

No global locks. Per-scope cache locks (one lock per RulesAssembly scope; one lock per ActionHistory bucket). Lock granularity is fine enough that contention is rare in practice.

21. Error Handling and Diagnostics

21.1 Diagnostic format

XBT emits diagnostics in MSBuild's file(line,col): error CODE: message format so IDEs and CI dashboards can parse them with the same regex they use for compiler errors. Each diagnostic carries an XBT-specific code (Section 1.3 lists the exit codes; per-diagnostic codes have the form XBT<NNN>).

21.3 Cancellation

Ctrl-C / SIGINT installs a CancellationToken. The dispatcher stops queueing new actions; in-flight subprocesses are killed after a 5-second grace period; partial outputs are removed; the build log records the cancellation with timestamp. Exit code 130.

21.4 Diagnostic dump command

The QueryTargets mode (Section 1.1) emits a JSON dump of the discovered target / module / plugin set, useful for debugging discovery and tier-enforcement issues without running a full build.

22. Threading the Test Loop — How XBT Validates Itself

Per plan Section 6: every system has a sibling tests module; per Section 9: every system has a four-layer verification approach. XBT's tests module (XBT.Tests) covers all of XBT.

22.1 Unit tests

  • ActionGraph cycle detection: synthetic graphs with known cycles → assert DetectActionGraphCycles reports them at the right edge set.
  • ActionHistory hashing: hash collisions across the field set are detected (the SHA-256 derivation in Section 5.4 is exercised on representative field permutations).
  • ModuleRules validation: a tier-violating PublicDependencyModuleNames entry → expected exit 21; a banned-flag entry on SimPath → expected exit 41.
  • Manifest serialisation round-trip: build manifest, write JSON, read JSON, build manifest, assert structural equality.
  • RulesAssembly Roslyn compilation: malformed .Build.cs → expected exit 30 with the Roslyn diagnostic preserved.
  • Copyright validation: a synthetic file missing the header → expected exit 40 with the file path in the diagnostic.

22.2 Integration tests

A fixture project under XBT.Tests/Fixtures/HelloWorldXPact/ exercises every action type end-to-end:

  • A C++ Hello-World module produces a .dll / .so.
  • A C# Hello-World module transpiles via a stubbed XIL2CPP (Phase 1 ships a placeholder XIL2CPP that emits a trivial C++ wrapper so XBT.Tests does not need real XIL2CPP work).
  • A mixed-language module exercises both XHT and XIL2CPP simultaneously.
  • A SimPath module exercises the FPSemantics + banned-API + libm-exclusion path.

22.3 Reproducibility test

Build the fixture project once into BuildA/; clean; build again into BuildB/; assert BuildA and BuildB are byte-identical for every produced file. This maps directly to plan Section 11 Foundation Prototype criterion (g) and Contract Section 12.1.

22.4 Tier enforcement test

A malformed fixture under XBT.Tests/Fixtures/BadTier/ declares an Engine module depending on a Studio module. Test asserts XBT exits 21 with the expected diagnostic substring. Symmetric tests for circular dependency (exit 22), engine-version mismatch (exit 23), copyright (exit 40).

22.5 Cross-config ABI test

Per Contract Section 12.3: build a C# module in Development and in Shipping, link the Dev binary against the Shipping module's import lib, run a smoke test, assert no ABI mismatch. This is a longer-running test (full build × 2 configs) and runs in CI nightly rather than on every PR.

25. Verification (Build-Time Checks)

What passing XBT must demonstrate end-to-end. The list is the merge gate for the XBT system — per plan Section 7, both subagents A and B must agree before main agent commits.

  1. Builds a Hello-World C++ TU. A trivial module under XBT.Tests/Fixtures/HelloWorldXPact/ with one .cpp emitting a "hello" log line. End-to-end: XBT.exe Build — success — produces .dll — .dll runs.
  2. Builds a Hello-World C# TU via the placeholder XIL2CPP. A .cs file in the same fixture transpiles to .cpp via a stubbed XIL2CPP (real XIL2CPP arrives at System 6); the resulting .dll exports the C# symbol per the Contract Section 2.2 mangling rule.
  3. Reports clear errors on invalid Tier. A fixture declaring an Engine module dependent on a Studio module exits 21 with a diagnostic naming both endpoints.
  4. Refuses to build with missing copyright. A fixture file missing line 1 fails with exit 40.
  5. Reproducibility. Two clean builds of the same fixture produce byte-identical artefacts (Section 19, Section 22.3).
  6. Engine-version compatibility rejection. A fixture project pinning a mismatched EngineVersion exits 23.
  7. Circular-dependency rejection. A fixture with A → B → A exits 22 with the cycle named.
  8. SimPath flag propagation. A fixture SimPath module compiles with /fp:precise / -ffp-contract=off, includes XSimPathMathOverrides.h, links against Sleef not platform libm. Verified by disassembly of the produced object file (the test asserts sin resolves to XSleef_sin).
  9. Banned-API rejection. A SimPath fixture using QueryPerformanceCounter exits 41 with the file:line reported.
  10. Cross-config ABI smoke. Per Section 22.5 + Contract Section 12.3.
  11. Plugin enumeration order is deterministic. Two runs of QueryTargets on the same repo produce byte-identical JSON dumps.
  12. Project-file generation is lazy. Per Section 14.1: GenerateProjectFiles for one target does not write project files for other targets.
  13. Mode-dispatch help message. XBT.exe with no arguments prints a list of modes with one-line summaries. XBT.exe <Mode> -Help prints that mode's argument schema.
  14. Cancellation graceful. Pressing Ctrl-C mid-build does not leave partially-produced outputs in the binary tree; exit 130 is reported; the build log is well-formed up to the cancellation point.
  15. JSON build log is well-formed. Every build emits a JSON log validating against the schema in Section 21.2.
