Rev 1 — initial Stage-A specification. This document is the system spec for the XPact Header Tool, the second build-order system in the engine plan (plan Section 4 build order; XHT lands at Step 2 after XBT at Step 1). XHT is the analog of Unreal Engine's UnrealHeaderTool, restructured around three XPact-specific commitments that make it a deliberately divergent design from UHT rather than a port: (a) XHT is a standalone .NET 8 executable, not a UBT mode (UHT today is UnrealBuildTool -Mode=UnrealHeaderTool); (b) XHT parses both .h headers and .cs sources, with attribute markers on the C# side as co-equal first-class reflection input (UHT parses only headers); (c) XHT emits a per-module machine-readable .gen.manifest so XBT's per-file dependency model (Toolchain Contract Section 8 + Addendum Section 4) can consume XHT's outputs opaquely, never parsing .gen.h or .gen.cpp content.

Per Toolchain Contract Section 7.1 (Rev 13.6), the XHT emit mode is locked at Stage A as ConstInit-style; the concrete emit struct layouts (FName / FClass / FProperty / FField byte order including the full replication-metadata surface) are frozen at the Stage B addendum that lands when XCore-4b ships at plan Section 4 Step 4. This document is the Stage A spec. The parser is the load-bearing deliverable at System 2; the emitter ships provisional in layout (mode locked, byte layout deferred) and finalises at Step 4. Every layout-related decision in this spec carries a <!-- STAGE-B: ... --> marker plus an italic note; everything else is final at Step 2 ship.

0. Purpose, Scope, Tier Membership

XHT extracts reflection metadata from authored C++ headers and authored C# source, and emits the registration scaffolding that XCoreXObject's reflection runtime consumes at engine boot. The reflection metadata covers classes (XCLASS / [XClass]), structs (XSTRUCT / [XStruct]), enums (XENUM / [XEnum]), interfaces (XINTERFACE / [XInterface]), functions (XFUNCTION / [XFunction]), properties (XPROPERTY / [XProperty]), delegates (XDELEGATE / [XDelegate]), function parameters (XPARAM / [XParam]), and enum-value metadata (XMETA / [XMeta]) per Contract Section 1.1. The full specifier vocabulary — what specifiers each marker accepts and what their semantics are — is locked at Contract Section 1.2.

The marker vocabulary mirrors Unreal Engine's; the divergence is at the boundaries:

  • Dual-language input. UHT reads only headers. XHT reads both headers (.h) and C# sources (.cs) in the same module pass and produces a unified registration record per type that is callable from either side at runtime.
  • Standalone tool. UHT today runs as a UBT mode (UnrealBuildTool.exe -Mode=UnrealHeaderTool ...) sharing UBT's process. XHT runs as XHT.exe, a separate self-contained .NET 8 binary. The decoupling lets XBT (Step 1) invoke XHT as a per-module action without dragging XBT's whole address space into the reflection-extraction pass, and lets IDE / CI dashboards run XHT directly on a manifest without a build session.
  • XBT-consumed text manifest per module. UHT writes a single newline-separated external-dependencies file back to UBT, plus mechanically-predictable per-header outputs UBT pre-discovers. XHT writes a per-module .gen.manifest text file that XBT parses as XHT's opaque output surface (Contract Section 7.1 + Section 8.2 + Addendum Section 11). XBT never reads .gen.h or .gen.cpp; the manifest is the join.

Tier membership. XHT's source lives under /Engine/Source/Programs/XHT/. Plan Section 3: every inventory system is Engine-tier. XHT is itself reusable across every Simgenics training product and every plugin, mirroring the engine's universal-reuse posture (plan Section 2 Folder structure row, Rev 6). The XHT binary ships as part of the engine release.

Position in the build pipeline. XHT is the System 2 deliverable in plan Section 4's build order — ships after XBT (System 1, Step 1) and before XCore-4a (Step 3). XBT invokes XHT once per module after writing the JSON + FlatBuffers manifest (Contract Section 10.1 step 3). XHT runs concurrent with XIL2CPP (Contract Section 10.1 step 4; the two have no inter-dependency, both consume the manifest, both feed compile). Per-module pipelining (Contract Section 10.1 step 5) means once XHT finishes module A and XIL2CPP finishes module A, the C++ compile actions for module A's TUs can start — the C++ compile does not wait for XHT or XIL2CPP to finish all modules.

What XHT does not own. XHT does not orchestrate the build (XBT). It does not transpile C# source bodies (XIL2CPP). It does not own the reflection runtime — the FClass / FProperty / FField runtime types are owned by XCoreXObject (System 5; multiple sub-docs). XHT's responsibility ends when the emitted .gen.h, .gen.cpp, .init.gen.cpp, and .gen.manifest are written atomically to the module's intermediate directory and the exit code is reported back to XBT.

Phase awareness. XHT MVP is Phase 1 of plan Section 5 (MVP subset). Phase 2 deferrals called out in this document — Verse-like third-language support, distributed XHT execution, full per-file invalidation, an interactive query-the-AST CLI mode — are designed as no-cost stubs at Phase 1 so post-MVP work does not require XHT redesign.

1.3 Exit codes — cross-reference to Contract Section 13

Exit codes are owned by the Toolchain Contract. See XToolchainContract.html Section 13. XHT's XHT.Entry imports the contract's exit-code constants at build time exactly as XBT does (XBT.html Section 1.3).

Codes XHT emits:

  • 0 — success.
  • 1 — generic failure (uncategorised).
  • 10 — CLI argument error (mode / flag invalid).
  • 50 — manifest malformed / unreadable (covers JSON schema violations, FlatBuffers verifier rejection, ContractVersion mismatches, both forms missing, AND module-not-in-manifest lookup failure). Rev 3 remap (X-CR1): the Rev 2 "module not in manifest" diagnostic previously exited 30 — that's XBT's RulesCompileFailed code per Contract Section 13.1, owned by XBT exclusively. The situation IS a manifest-coherence concern (the requested module isn't present in the manifest XBT emitted, so the manifest and the caller's expectation disagree); remapping to 50 keeps XHT's surface within the 50 / 62 / 130 band, avoids adding a new exit code, and avoids rotating ContractSurface.ExitCodes. Matches Contract Section 13.3 per-tool emit discipline.
  • 62 — XHT parse or emit internal failure (per Contract Section 13.1). When XHT is invoked as a subprocess by XBT, XBT aggregates 62 into the surface exit 60 (XhtSubprocessFailure); when XHT exits 62 standalone (CI pre-flight, IDE), the caller sees 62 directly. This split lets XBT-driven builds present a uniform "XHT failed" surface to the developer while still giving CI gates the detail.
  • 130 — cancelled by user (Ctrl-C; matches POSIX SIGINT convention).

XHT does not emit exit codes 20–24 (XBT's discovery / tier / engine-version / plugin categories), 30 (XBT's RulesCompileFailed per Contract Section 13.1; module-not-in-manifest is remapped to 50 per X-CR1), 40 (copyright validation; XBT owns it), 41 (banned-API check; XBT owns it), 60 (the XBT-aggregated XhtSubprocessFailure), 61 (XIL2CPP's category), 70–71 (compile / link), 80–81 (action-graph / hook), or 90–99 (Live Coding reserved). The boundary keeps the per-tool diagnostic surface coherent.

The contract's stability commitment (Section 13.2) carries: adding a new XHT exit-code category takes the next free integer (currently 64 is the first free in the 60–69 XHT/XIL2CPP band); removing or repurposing a code is forbidden.

1.4 Output format

Default output: human-readable progress to stdout, errors and diagnostics to stderr in MSBuild diagnostic format (Section 12.1). A parallel streaming JSON diagnostic channel (Section 12.4) emits one JSON line per diagnostic for IDE / CI subscription, mirroring XBT.html Section 21.2's channel design. The channel uses either a dedicated FD (Linux / Android, default FD 3, configurable via -JsonFd=N) or stdout lines prefixed with the sentinel @@XHT-JSON@@ (Windows fallback; also Linux fallback when no FD is available). Activation mirrors XBT.html Section 21.2: explicit opt-in on Linux / Android via -JsonFd=; automatic on Windows when stdout is not a TTY.

Cancellation via Ctrl-C is graceful and deterministic (Section 11.5). Outstanding parse / emit tasks are allowed to complete cleanly or fail at the next cancellation checkpoint; partially-produced outputs follow the atomic-rename + temp-file convention pinned in Section 8.5 (mirroring XBT.html Section 6.4); the streaming JSON channel emits a final {"event":"cancelled","timestamp":"..."} record; exit code 130.

1.5 Subprocess invocation contract

When XBT invokes XHT as a subprocess (XBT.html Section 9.1, Phase 1 default), the invocation:

  • Working directory: the engine repository root (the directory containing Engine/), so all relative paths in the manifest resolve identically across machines.
  • Environment variables: XBT propagates XPACT_TOOLCHAIN_VERSION (XBT's own toolchain version) and XPACT_CONTRACT_VERSION (the derived ContractVersion.Current string). Rev 2 clarification (Rev 3 cross-ref correction per Xm2; Rev 4 disambiguation per Xm4): earlier drafts claimed XBT propagates LANG=C.UTF-8 on POSIX for explicit locale stability; the actual XBT environment-propagation surface does not currently include this variable, and XHT does not rely on it (XHT forces UTF-8 internally per Contract §6 (UTF-8 handling) — the engine-wide UTF-8 commitment — regardless of the inherited locale). Setting LANG=C.UTF-8 from the XBT side is a deferred Phase 2 hardening item; no XHT behaviour depends on it at Phase 1. No PATH manipulation; XHT does not shell out to subprocesses.
  • Cancellation: SIGINT / Ctrl-C is honoured (Section 11.5). XBT's ParallelExecutor (XBT.html Section 6.1 for scheduling; Section 6.4 for cancellation discipline — Rev 3 cross-ref correction per X-M16) propagates cancellation to the XHT subprocess via SIGINT on POSIX and GenerateConsoleCtrlEvent(CTRL_C_EVENT) on Windows; XHT cleans up its own temp files within the 5-second grace window. If the grace window expires (Rev 3 mechanism correction per X-M17): on Windows, XBT relies on the Job Object JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE discipline (XBT.html Section 19.3) — the executor closes the job handle and the OS kills every assigned subprocess (including the XHT child) atomically; on POSIX, XBT issues kill(SIGKILL) to the child PID. XHT's orphan temp files are reaped by XBT's next-startup sweep (XBT.html Section 6.4 rule 4).
  • Streams: XHT's stdout / stderr are captured by XBT's executor and forwarded to XBT's build log and streaming JSON channel. The diagnostic channel's records carry the "tool":"XHT" attribution so log readers can filter.

When XHT is invoked standalone (CI gate, IDE), the caller sets up the working directory + environment as needed; XHT does not assume XBT's process context.

3. Parser Model

XHT runs two parsers in parallel within a module, both producing tokens that feed the same marker-driven dispatcher (Section 3.4). The C++ side uses a handwritten tokenizer; the C# side uses Roslyn. Both share the AST hierarchy (Section 4); both honour the same resolve pipeline (Section 5; seven active phases post-None — Pairings, InvalidCheck, BindSuperAndBases, RecursiveStructCheck, ResolveBases, Properties, Final).

3.1 C++ parser — handwritten tokenizer

XHT carries a single-pass, hand-written C++ tokenizer in XHT.Parser/Cpp/XhtCppTokenizer.cs. The choice is deliberate. XHT is not a full C++ compiler; it does not need to type-check, name-resolve C++ symbols against the broader translation unit, or expand macros — those are the platform compiler's job, downstream of XHT. XHT only needs to recognise marker macros (XCLASS(...), XSTRUCT(...), etc.), specifier values, body-macro placement (XGENERATED_BODY()), and the surface text of fields and method signatures inside reflected types. A heavyweight parser (libclang, fork of Clang's frontend, ANTLR grammar) would impose 100+ MB of dependencies and a 1–3 second cold start per process on what is fundamentally a token-recognition problem.

UHT made the same trade-off in EpicGames.UHT/Tokenizer/UhtTokenBufferReader.cs (1,048 lines). XHT mirrors the trade-off, with one correctness tightening: every token carries a column range (start column + end line + end column), not just a start line. This closes UHT footgun #1 from the reference brief (UHT only tracks line-level diagnostics; column-precise IDE underlining is impossible). The cost is one extra (line, column, endLine, endColumn) quad per token; the benefit is that every diagnostic XHT emits (Section 12) carries a token range an IDE can render as a precise red squiggle.

Token kinds (the same set UHT uses, except the column tightening):

public enum XhtTokenKind
{
    Identifier,
    Symbol,
    FloatConst,
    DecimalConst,
    HexConst,
    CharConst,
    StringConst,
    EndOfFile,
    EndOfType,           // terminator the dispatcher injects between types
    EndOfDeclaration,    // semicolon terminator
    EndOfDefault,        // close of a default-value expression
    Line                 // synthetic newline used by the preprocessor
}

public readonly record struct XhtToken(
    XhtTokenKind Kind,
    ReadOnlyMemory<char> Value,   // zero-copy slice into source text
    int    StartLine,
    int    StartColumn,
    int    EndLine,
    int    EndColumn,
    bool   FromSource);            // false for tokens the dispatcher injects

Capacity limits (mirroring UHT's): MaxNameLength = 1024, MaxStringLength = 1024. Per UHT precedent these are pragmatic ceilings; any reflected source field longer than 1024 chars is almost certainly a generated artefact that shouldn't be reflected.

The reader supports peek vs consume, token recording (used to capture declaration bodies for downstream resolve passes), comment tracking (most recent comments associated with the next token become tooltip metadata), and state save / restore for speculative parses. A second reader XhtTokenReplayReader reads from a pre-recorded token list — used by the AST cache replay path (Section 16).

Template-type tokenization (NEW Rev 2). Reflected property types frequently use template instantiations: TArray<XActor*>, TMap<FName, TArray<FString>>, TWeakObjectPtr<UFoo>. The tokenizer treats < and > as ordinary symbol tokens at the lexer level; template-aware reassembly happens in the property-type parser (XHT.Parser/Cpp/XhtPropertyParser.cs) via a depth-counter approach:

  • The parser maintains a templateDepth integer initialised to zero.
  • On <: increment templateDepth only when the preceding token is identifier-like (an Identifier token of kind XhtTokenKind.Identifier, or a closing > of a prior template list). Otherwise the < is left as a comparison or shift operator and not consumed as a template opener. This disambiguates X < Y (comparison) from TArray<Y> (template open).
  • On >: decrement templateDepth when positive; the >> right-shift digram is tokenised as two separate > tokens by the lexer (a known C++ language ambiguity, resolved by templates-context preference per C++11+), so the parser consumes them serially.
  • The template's inner-type list is parsed recursively, populating XhtArrayProperty.InnerProperty / XhtMapProperty.KeyProperty + .ValueProperty / etc., with each inner type going through the same property-type lookup machinery.

Mirrors UHT's UhtPropertyParser approach (UhtPropertyParser.cs depth tracking). The reflection extraction does not require a full C++ template-instantiation machinery — it only needs to recover the inner-type spelling to resolve the inner property's type through the symbol table.

3.2 C++ preprocessor model

The C++ preprocessor in XHT.Parser/Cpp/XhtCppPreprocessor.cs recognises a deliberately restricted set of directives. Per the UHT reference brief, UHT recognises only:

  • #if CPP / #if !CPP — text inside CPP blocks is skipped by XHT (it's pure C++).
  • #if 0 / #if 1 — zero-blocks are scanned for content but their reflected types are dropped; one-blocks pass through.
  • #if WITH_EDITOR / WITH_EDITORONLY_DATA / WITH_ENGINE / WITH_XCORE / WITH_HOT_RELOAD / WITH_TESTS — tracked as a flag set on declarations (the XhtCompilerDirective enum). Unknown directives become Unrecognized. The current directive stack composes via OR — a declaration inside #if WITH_EDITOR and #if WITH_TESTS carries both flags.
  • #include — only inspected for the #include "X.gen.h" self-include rule (Section 19.6; must appear last; XHT errors with the "Linux case-sensitivity hint" diagnostic if missing or out of order).
  • #define, #undef, #pragma — skipped (largely ignored for reflection extraction).
  • #error — passthrough; ignored for reflection.

Crucially, no macro expansion. Macro-like all-caps identifiers are heuristically detected and skipped (mirroring UHT's ProbablyAnUnknownObjectLikeMacro at UhtHeaderFileParser.cs:766–797: starts with _ or capital, all subsequent chars must be [A-Z0-9_], and must have at least one underscore). This is the deliberate trade-off: XHT can't compile arbitrary C++ but it parses fast and doesn't need a real preprocessor.

Replacing the UHT-style directive list with a real C-preprocessor would invalidate the design's premise (Section 25.2 item 4). XHT inherits UHT's footgun that user code containing macro-defined types (e.g. type aliases via #define) is opaque to XHT — the workaround is to write the explicit type. XHT's diagnostic on a token it cannot resolve to a type points at the source line and recommends "write the explicit type or factor the macro into a typedef." Errors are explicit, not silent.

3.3 Namespace handling

Namespaces are stacked via XhtCppNamespaceParser. XPact divergence from UHT (Rev 2 clarification): UHT carries an AllowUETypesInNamespaces flag toggling whether reflected types declared inside C++ namespaces participate in reflection at all. XPact does not carry such a flag — the manifest schema declares none, and namespaces are always honoured. Per Section 4.1, namespaces participate in mangling unconditionally; the singleton-getter naming scheme (Section 10.2) includes the namespace path verbatim, so the Z_Construct_U<Name> name-collision footgun UHT suffers (Section 25.3 footgun #9) does not apply, and the UHT opt-in / opt-out posture becomes superfluous.

Cross-language binding clarification (REVISED Rev 3 per Xm3; Rev 2 addition with prefix-stripping rule corrected). XHT's symbol table is keyed on the engine name — the prefix-stripped, caseless form of the source identifier. The prefix-stripping rule (Rev 3 correction): C++ identifiers strip exactly one leading uppercase letter from the UE-convention set A / U / I / F when followed by another uppercase letter; the stripping is single-pass, not iterative. C# identifiers carry no prefix and are used as-is. The case-folding rule: all identifiers lowercase for the caseless lookup. The XPact X prefix is NOT a strippable UE convention prefix — it is XPact's permanent project-wide prefix (per plan Section 2 Naming row, the only rename from UE is UObject → XObject; the X persists into the engine name). Two examples illustrating the corrected model:

  • A C++ class declared class AXValve : public AXActor { ... }; — source name AXValve; strip leading A (UE convention prefix for AActor-derived) → XValve → engine name xvalve (lowercase). The X is NOT stripped because it's the permanent XPact prefix, not a UE-convention prefix. This populates one caseless symbol-table entry xvalve pointing at the XhtClass with SourceLanguage = Cpp.
  • A C# class declared [XClass] public partial class Valve : Actor { ... } — source name Valve, no leading UE-prefix to strip, engine name valve (lowercase). Note: this is a different engine name from the AXValve example above (valve vs xvalve); cross-language partial-pairing requires the engine names to match exactly. The standard convention is for the C++ side to declare class XValve : public XActor (using the permanent X prefix without the optional A UE-prefix) and the C# side to declare public partial class Valve — both engine-name valve — OR for both sides to use the prefixed form (AXValve + a C# attribute that explicitly names the engine identifier). The resolver detects engine-name matches and links the two as a cross-language partial pairing (each side carries its SourceLanguage, and the entry's chain holds both); engine-name mismatches result in two separate symbols.

This unified caseless symbol-table model is what makes cross-language references work transparently at parse time. The cased table (Section 5.3) preserves the original source identifier for diagnostic output and for the source-prefix-aware singleton-getter naming.

Classes and structs push an XhtParsingScope. Each scope has its own keyword sub-table (Global, Class, Struct, Function, Enum, Interface) per the table layout in Section 18.1. The scope stack mirrors UHT's EpicGames.UHT/Parsers/UhtParsingScope.cs.

3.4 Marker-driven dispatcher

Top-level markers (XCLASS, XSTRUCT, XENUM, XINTERFACE, XDELEGATE) are recognised by the keyword table, populated declaratively by attributes mirroring UHT's EpicGames.UHT/Parsers/UhtClassParser.cs:

// XHT.Parser.Cpp.XhtClassParser
[XhtKeyword(Extends = XhtTableNames.Global)]
private static XhtParseResult XCLASS_Keyword(XhtParsingScope topScope, XhtParsingScope actionScope, ref XhtToken token)
{
    return ParseXClass(topScope, ref token);
}

The C# name of the method (stripped of the _Keyword suffix) becomes the matched identifier — so a method XCLASS_Keyword matches the literal text XCLASS in source. Attributes can override with Keyword = "..." when the method name and the source identifier diverge (e.g., legacy alias support).

XFUNCTION / XPROPERTY are recognised inside class / struct / interface scope by the same mechanism, but they extend the Class / Struct / Interface table rather than Global. Specifier extension via the same mechanism (Section 18.1):

[XhtSpecifier(Extends = XhtTableNames.Property)]
private static void EditAnywhere_Specifier(XhtSpecifierContext context, XhtSpecifierState state)
{
    context.PropertyFlags |= XhtPropertyFlags.EditAnywhere;
}

The dispatcher is the same code path for the C++ and C# parsers — both feed token streams into the unified table. The language tag is set on the produced AST node based on which tokenizer originated the stream.

3.5 C# parser — Roslyn-based

For .cs files, XHT.Parser/CSharp/XhtCSharpParser.cs hosts Microsoft.CodeAnalysis.CSharp. Roslyn gives XHT every modern C# feature for free (records, primary constructors, file-scoped namespaces, init-only properties, required members) without a hand-rolled grammar.

The C# parser flow:

  1. Parse to syntax tree. CSharpSyntaxTree.ParseText(source, options, path) with LanguageVersion.CSharp12 pinned. options.DocumentationMode = DocumentationMode.Parse so XML-doc comments are preserved for tooltip extraction (Section 6.4). options.SourceCodeKind = SourceCodeKind.Regular — XHT does not consume scripts.
  2. Walk the syntax tree. A custom XhtCSharpAttributeWalker : CSharpSyntaxWalker visits every ClassDeclarationSyntax, StructDeclarationSyntax, EnumDeclarationSyntax, InterfaceDeclarationSyntax, DelegateDeclarationSyntax, FieldDeclarationSyntax, PropertyDeclarationSyntax, and MethodDeclarationSyntax. At each node the walker inspects the AttributeListSyntax collections for XPact markers ([XClass], [XProperty], etc.) and, if present, builds the corresponding AST node.
  3. Token range projection. Roslyn carries token spans natively (each SyntaxToken exposes SpanStart + Span.End + line / column via LineSpan). XHT projects these into the same XhtToken shape Section 3.1 declares so the downstream resolver and emitter can branch on language uniformly.
  4. No semantic-model use at parse time. Roslyn's SemanticModel (which would resolve using directives, generic instantiations, and the like) is not invoked. XHT only needs the syntax tree's literal attribute names; symbol resolution happens in Section 5's seven-active-phase resolver, against XHT's own symbol table, not Roslyn's. This keeps Roslyn's hosting cost bounded: parse-only mode is ~50–100 MB resident, not the multi-hundred-MB cost of full Compilation with semantic services.

Why not use Roslyn for C++ too? Roslyn is C#-only. There is no equivalent for C++; libclang exists but at the dependency cost ruled out in Section 3.1.

Cross-language considerations. A type declared in .cs can be the type of a property in .h (and vice versa). The resolver (Section 5) handles cross-language references via the symbol table's caseless lookup, populated by both parsers in parallel before the BindSuperAndBases resolve phase runs. The C# side's using Simgenics.XPact.GameFramework; import resolution is XHT-internal — it walks the namespace path through the symbol table directly, not through Roslyn's semantic model.

3.6 Comment + whitespace handling

Comments are collected during whitespace-skip but committed only when a token is actually consumed (mirrors UHT). ///-style and /** */-style become "tooltip" metadata on the next declaration. This is how Blueprint hover tooltips work (Section 6.4 covers the tooltip metadata mechanism for XPact's Project Settings UI per plan Section 2 "Developer settings" row).

The C# side: Roslyn carries XML-doc comments natively via SyntaxTrivia of kind SingleLineDocumentationCommentTrivia or MultiLineDocumentationCommentTrivia. The walker extracts the trivia immediately before each marker-attributed declaration and projects it into the same tooltip-metadata slot the C++ parser uses.

3.7 Error recovery

XHT does not stop on first error. Errors are added to the session's message list via IXhtMessageSession.AddMessage; parsing continues. Each top-level Try(...) block at the orchestration level catches exceptions and turns them into messages (mirrors UHT's pattern). Per-header TryHeader wraps each header parse. The session terminates with HasErrors = true if any error was emitted, but produces as many diagnostics as possible — a developer fixing reflection errors should see all of them at once, not one-at-a-time.

When the C++ statement parser hits an unrecognised construct, it calls SkipDeclaration (in XhtParsingScope) which scans forward to the next ; or } — a coarse but practical recovery scheme matching UHT.

3.8 What XHT does not parse

XHT does not parse template metaprogramming, SFINAE constructs, concepts, lambdas, or anything outside a reflected type's body or member list. Reflected members must be simple declarations the C++ compiler later compiles; XHT's tokenizer skips function bodies, template bodies, and other constructs that aren't part of the reflection surface. Per UHT precedent and per the "XHT is not a full C++ compiler" rule.

4. AST Model

XHT's AST is a unified type hierarchy. Every node carries a SourceLanguage tag (Cpp / CSharp) so emit and downstream consumers (XIL2CPP, XCoreXObject) can branch where the language matters, but the structure is the same regardless of origin language. This is a deliberate departure from UHT's pattern of bolting a new language (Verse) onto the existing AST via flag explosion (Section 25.3 footgun #3); XPact's C# support is co-equal from day one, so the polymorphism is designed-in.

The hierarchy mirrors UHT's EpicGames.UHT/Types/ with two divergences:

  1. Column ranges throughout. Every XhtType carries (LineNumber, ColumnStart, ColumnEnd) in addition to LineNumber. The token reader writes them at parse time; the emitter writes them into the JSON diagnostic channel and the .gen.manifest for IDE integration. UHT carries only LineNumber.
  2. Language tag. Every node carries SourceLanguage : XhtSourceLanguage (Cpp / CSharp). Emit branches on this at the few sites that matter (the body-macro emission uses C++-specific macro suffixes; the IL2CPP-target metadata emit uses C#-aware mangling); everywhere else, the language is transparent.

4.2 Inheritance

XhtClass.Super (single base; resolved during StepBindSuperAndBases), XhtClass.BaseIdentifiers (interface bases; resolved likewise), XhtClass.SuperIdentifier (string, resolved later). Unresolved at parse time; resolved during StepResolveBases (Section 5.1).

For C# classes, the Super comes from Roslyn's BaseTypeSyntax; for C++ classes, from the C++ tokenizer's parse of the : public BaseClass clause. The structural representation is identical; the parse path differs.

4.3 Nesting

Every type has an Outer pointer (header file, namespace, or parent class). Children is a list of contained XhtTypes. Properties live as children of their owning class / struct / function. The Outer chain bottoms out at the XhtPackage (one per module, named /Script/<ModuleName> mirroring UHT's UhtPackage).

4.4 Property typing

Each concrete XhtProperty subclass knows its CPP type spelling, its EngineClassName (e.g. "IntProperty", "BoolProperty", "ObjectProperty"), and its constructor parameters. Containers (XhtArrayProperty, XhtMapProperty, XhtSetProperty, XhtOptionalProperty) hold inner properties recursively. Object-references (XhtObjectProperty, XhtSoftObjectProperty, XhtWeakObjectProperty, XhtClassProperty, XhtSoftClassProperty) hold an XhtClass reference.

The property-type set mirrors UHT's EpicGames.UHT/Types/Properties/ (43 files in total, 39 non-Verse — Rev 3 count correction matching actual FS state). XHT supports the same set with cross-language consistency: XhtIntProperty covers int32 X; on the C++ side and int X; (or int32 X; with the int32 typedef from the C# binding surface; Section 16) on the C# side. The handle records its source language for code-gen, but the structural type is unified.

4.5 Interface pairing

An XINTERFACE produces two XhtClass nodes — one with ClassKind = Interface (the "X"-prefix type) and one with ClassKind = NativeInterface (the "I"-prefix type). They're paired during StepResolvePairings (Section 5.1). The split mirrors UE's UInterface / IInterface runtime model and is preserved for surface compatibility with the Unreal idiom.

For C# [XInterface]-attributed interfaces, only the I-prefix variant is produced (C# interfaces are first-class and don't need the C++ vtable-anchor companion type). The emit step (Section 8) elides the U-prefix half on the C# side.

4.6 Delegate signatures

An XhtFunction with EFunctionFlags.Delegate (potentially also MulticastDelegate, SparseDelegate). It still has Children of XhtProperty for params. Emit produces a thunk-trampoline + a static invoker (per UHT precedent, with the calling-convention tier from Contract Section 5.2 applied: delegate thunks cross the language boundary and are therefore Tier 1).

4.7 Properties also have

  • PropertyFlags (the EPropertyFlags bitfield, ~50+ flags including EditAnywhere, BlueprintReadWrite, Replicated, Net, ConstParm, OutParm, etc.; mirrors UHT).
  • PropertyExportFlags (XHT-internal — Public / Private / Protected, Getter / Setter info, XPact-specific Modbus / multi-user / scenario-metadata flags per Section 19, etc.).
  • MetaData (a XhtMetaData dictionary).
  • DefineScope (which #if block it was inside).
  • SourceLanguage (per Section 4.1).

4.8 Type-graph immutability after resolve

Once the resolver's Final phase completes, the AST is treated as immutable. The emitter (Section 8) reads but does not mutate. Downstream consumers (XIL2CPP, the JSON dump in dump-ast mode) see a frozen graph. This invariant matters for the byte-identical-output guarantee (Section 14): emit must be a pure function of the resolved AST plus the manifest's target settings.

5. Type Resolution + Cross-Module References

XHT's resolution model mirrors UHT's linker model: parse each file independently in parallel; then run a sequence of resolve phases across the full module set, each phase doing work that depends on the previous phase being complete.

5.2 XhtSession orchestrator

The session in XHT.Resolver/XhtSession.cs mirrors UHT's EpicGames.UHT/Utils/UhtSession.cs (3,167 lines in UHT; XHT targets ~2,000 lines by scoping out the Verse-specific code paths). Per-session lifecycle:

  1. StepReadManifest — deserialise the XBT manifest (Section 7.1).
  2.   3. StepDiscoverHeaders — enumerate the module's .h + .cs files from the manifest's SourceFiles list (Addendum Section 3.4).
  4. StepParseHeaders — parallel parse via Parallel.ForEach (Section 11.1).
  5. StepWriteInputCache (optional; Section 16) — serialise the parsed AST to a per-module Brotli-compressed cache for faster incremental rebuilds.
  6. StepPopulateTypeTable — build the symbol table (Section 5.3).
  7. Run the resolve phases in this order (Rev 4 corrected sequence, X-CR2-Round2):
    1. StepResolvePairings
    2. StepResolveInvalidCheck
    3. StepBindSuperAndBases — symbol-table-driven super-name + base-name lookup; populates XhtClass.Super pointers.
    4.     5. StepResolveBases — cross-type type-pointer resolution (transitive base classes, interface-base type pointers, ClassWithin outer-type pointer per Section 7.4).
    6. StepResolveProperties
    7. StepResolveFinal — serial; whole-program checks.
    Rev 4 phase-model convergence (X-CR2-Round2): the Rev 3 sequence (RecursiveStructCheck running BEFORE BindSuperAndBases, with BindSuperAndBases + ResolveBases as sub-steps within a single "Bases" phase) was a phase-ordering regression.   8. StepResolveValidate — run the specifier validators (Section 6.1).
  9. StepCollectReferences — walk the resolved type graph to build the cross-module reference set per header (used by the emitter to write the extern declarations in .gen.cpp; Section 8.2).
  10. StepLinkModules — assemble the per-module package + final module-level metadata.
  11. StepTopologicalSortHeaderFiles — sort the headers within the module so emit's reference resolution emits its externs in dependency order.
  12. StepExport — run the registered exporters (Section 18.3). The default code-gen exporter (Section 8) is one of them.

The orchestrator mirrors UHT's pipeline step-for-step. The renaming is cosmetic; the structure is the same.

5.3 Symbol table

Two tables (XHT.Resolver/XhtSymbolTable.cs; mirrors UHT's UhtSymbolTable.cs):

  • Cased — case-sensitive, by source name (the C++ identifier as written: AXValve; the C# identifier as written: Valve).
  • Caseless — case-insensitive, by engine name (the prefix-stripped name: valve).

Each symbol has a MatchOptions mask (XhtFindOptions) — class, struct, enum, function, package, property, namespace — so the same name can be disambiguated by kind at lookup time. Symbols form linked chains per name (caseless name → first cased index → chain via NextIndex; UHT's exact data structure, mirrored).

Cross-language resolution. A C++ XPROPERTY(EditAnywhere) Valve* MyValve; referring to a C#-declared [XClass] public partial class Valve : Actor resolves via the caseless lookup: both parsers populate the same symbol table, both emit one symbol per declared type, the caseless lookup finds the C#-side Valve entry (with its source-language tag) when the C++ parser asks for the type. The reverse works too: a C# field [XProperty] public AXValve OtherValve; resolves to the C++-side AXValve entry.

The cross-language resolution is what makes XHT's dual-language input model coherent. UHT does not have this because UHT does not parse C# at all; UHT's symbol table is C++-only.

5.4 Forward declarations

Headers record forward declarations declaratively (XhtHeaderFile.References.ForwardDeclarations and .ForwardDeclarationStrings) and emit them in the .gen.h (Section 8.1). XHT does not fully resolve a forward-declared class — it leaves a "lazy" reference resolved during StepResolveBases (mirrors UHT).

For C#, Roslyn provides every type used by an attribute or field declaration as a name-bound reference; XHT's parser builds the forward-declaration set during the parse walk and the resolver does the same lazy-resolution as the C++ side.

5.5 Module completeness

XHT must be invoked with all modules the build target references — it's module-complete, not file-incremental. Cross-module references work because every dependency module is in the same manifest (Contract Section 10.2 lists all modules participating in the build).

A module's headers are first parsed independently (parallel), then StepPopulateTypeTable builds the global symbol table, then Step*Resolve* phases run. This is the same model UHT uses; the divergence is that XHT can be invoked per-module (-Module=XScoring) provided the manifest enumerates every dependency module's types in a separately-loaded form. Phase 1: XHT loads every dependent module's headers in the same session (it's mode-complete). Phase 2: a separately-cached "exported types only" form per dependent module could speed up the per-module invocation (post-MVP optimization; not in System 2's scope).

5.6 Sessions and packages

  • XhtSession = one XHT run (one manifest read).
  • XhtModule = one XBT module (one entry in the manifest's Modules array).
  • Each module has a primary XhtPackage named /Script/<ModuleName> (the package the types belong to at runtime; mirrors UE).
  • XhtHeaderFile is contained in a module but its types are owned by the package.

A module can declare links to other modules via the manifest's module_dependencies list. XHT validates cross-module type references unconditionally in Phase 1. (Rev 2 correction: earlier drafts gated this on a non-existent ValidateModuleDependencies target-level flag; the manifest's TargetInfo object does not declare such a field, and the validation is correctness-critical rather than performance-optional, so there is no reason to make it opt-in.) The check walks every property reference and asserts the referent's module is in the consumer module's link-dependency closure.

ModuleDep filtering (REVISED Rev 4, X-Round2-M1). The validation walks the manifest's module_dependencies list excluding entries where is_dynamic = true (per Addendum §3.4 FBS-side flag, set by XBT's manifest emitter from ModuleRules.DynamicallyLoadedModuleNames). This corresponds at the C# descriptor surface to PublicDependencyModuleNames + PrivateDependencyModuleNames (link-time linkable deps); DynamicallyLoadedModuleNames are runtime-resolved via IXSymbolTable per Contract §9.7. The reason for the filter: a property holding a pointer to a runtime-resolved type cannot be represented as a direct reflection record without an IXSymbolTable::Resolve<T> lookup; the reflection emit would otherwise reference a singleton-getter symbol that's not link-visible. A property whose referent type lives only in a dynamically-loaded module errors with diagnostic XHT121 — Type <type> referenced through dynamic-only module dependency; reflection must go through IXSymbolTable::Resolve<T> rather than a direct property reference. Mark the property type via [XProperty(SymbolTableResolved = true)] or move the type into PublicDependencyModuleNames / PrivateDependencyModuleNames if it should link directly. The diagnostic fires at StepResolveFinal (the cross-language consistency pass — same phase as the existing XHT120 cross-module reference check). An Engine module referencing a Studio type without a declared link-tier dependency fails the build at the same phase under the standard XHT120 diagnostic. This is the XHT-side enforcement of Contract Section 9.3's tier dependency edge matrix (locked unconditionally per the matrix itself); XBT enforces the matrix at module-resolution time, XHT enforces it at type-reference time. (Rev 3 wording referred to PublicDependencyModuleNames / PrivateDependencyModuleNames as manifest fields; those are ModuleRules C# descriptor surface names, not manifest fields. The manifest schema carries the per-edge is_dynamic flag on ModuleDep instead, per Addendum §3.4. Rev 4 reworded to make the manifest-side vs descriptor-side surfaces explicit.)

5.7 Cross-language type-reference checks (NEW Rev 1 vs UHT)

At StepResolveFinal, XHT runs the cross-language consistency pass. The pass walks every property in every reflected type and asserts:

  • If a C++ property references a C#-declared type, the C# type must be reflected ([XClass] / [XStruct] / [XEnum] attributed). A non-reflected C# type is an error.
  • If a C# property references a C++-declared type, the C++ type must be reflected (XCLASS / XSTRUCT / XENUM markered). A non-reflected C++ type is an error.
  • If a C# property is of a primitive C# type (int, float, string, etc.), the C++ side's emit uses the canonical C++ binding for that type (int32, float, FString; Section 16.3).
  • If a C++ property is of a primitive C++ type (int32, float, FString, etc.), the C# side sees the canonical C# binding (int, float, string) via the IL2CPP-emitted bridge.

The pass is the XHT-side enforcement of the cross-language reflection coherence the engine's runtime relies on. Failures exit 62 with a diagnostic naming both sides of the offending reference.

6. Specifier Validation

Specifier validation is the cross-cutting check phase: after parse, after symbol table population, after the seven resolve phases, before emit. Validators are declarative — methods marked with [XhtSpecifierValidator] attributes (mirroring UHT's EpicGames.UHT/Tables/UhtSpecifierValidatorTable.cs).

6.1 Validator registration

[XhtSpecifierValidator(Extends = XhtTableNames.Property)]
private static void Const_DefaultToInstanced_Validator(XhtProperty property, IXhtMessageSession messages)
{
    if (property.HasFlag(XhtPropertyFlags.Const) && property.HasFlag(XhtPropertyFlags.DefaultToInstanced))
    {
        messages.LogError(property,
            "Property cannot be both Const and DefaultToInstanced — Const properties are not re-initialised per instance.");
    }
}

Every validator runs after StepResolveFinal. Validators read the resolved AST; they do not mutate it. A validator that finds a problem calls messages.LogError (or LogWarning); the session captures the message, the run reports the diagnostic, and the build exits 62 if any error was logged.

6.2 The validator catalog

The Phase 1 validator set covers (Rev 2: explicit migration of specifier-conflict checks from InvalidCheck per UHT precedent):

  • Specifier coherence (XHT110–XHT112): EditAnywhere + Transient (contradictory — Transient is not persisted, EditAnywhere implies persistence); EditAnywhere + EditDefaultsOnly (contradictory); Server + Client + NetMulticast (must be exactly one); BlueprintCallable + BlueprintImplementableEvent (the latter implies the former); a struct cannot declare itself as both BlueprintType and NotBlueprintType.
  • Replication coherence (XHT113): a property marked Replicated on a struct (not a class) is an error; ReplicatedUsing references a method that doesn't exist on the owning class; the lifetime condition COND_None is the default when not specified. RepNotify signature rigor (XHT113 sub-check, Rev 2 addition): the ReplicatedUsing callback must take zero parameters, OR exactly one parameter whose type matches the property's type. Mismatched signatures fire XHT113 — RepNotify callback <name> on property <property> has invalid signature; expected zero-param OR one-param matching <property-type>. The check mirrors UHT's RepNotify rigor in UhtClass.ValidateProperties.
  • FieldNotify coherence: a property marked FieldNotify on a class that does not declare or inherit INotifyFieldValueChanged.
  • Cross-language coherence: a C# property's Category string must not contain "/" if it's targeting a category the C++ Editor consumes (a UE leaked-detail check).
  • Body-macro placement: XGENERATED_BODY() must appear inside the class body before any reflected member; missing or misplaced is an error.
  • Reserved-identifier check: no reflected type name may start with _XID_ (the FileId prefix per Contract Section 1.4); no member name may collide with a generated macro suffix (Section 8.1).
  • ClassWithin validation (XHT118 / XHT119; Rev 2 addition, code-to-validator mapping NEW Rev 4 per X-Round2-M3): per Section 7.4, an XCLASS(Within=Foo) declaration constrains instantiation to occur nested inside a Foo instance. The validator resolves the named outer type via the symbol table (the lookup hooks into StepResolveBases; final consistency check runs here) and asserts compatibility with the super-class's ClassWithin — a class's ClassWithin must be the super's ClassWithin or a subtype thereof. XHT118 is the validator entry-point (ClassWithinValidator); XHT119 fires on Within type incompatible with super's Within (per UHT's UhtClass.SetAndValidateWithinClass precedent: the new Within type must be derived-from-or-equal-to super's Within). Mirrors UHT's UhtClass.ClassWithin resolution + validation.
  • Class-flag coherence (XHT114 / XHT115 / XHT116 / XHT117; Rev 2 addition, code-to-validator mapping NEW Rev 4 per X-Round2-M3): XHT115 fires on Intrinsic + XGENERATED_BODY() (intrinsic classes are runtime-registered, not body-macro-driven); XHT116 fires on MinimalAPI + RequiredAPI (mutually exclusive declarations); XHT117 fires on NoExport + Blueprintable (NoExport elides the body macros that Blueprintable requires); XHT114 fires on NoExport + Config= (NoExport elides the config-bound descriptor accessor body that the runtime config subsystem requires; see §7.4 XHT114 ConfigConflictsWithNoExport). Rev 3 numbered this XHT11A; Rev 4 renumbered to XHT114 for decimal-band compliance per X-Round2-M2 (see §12.3 convention).
  • XPact-specific specifier coherence: Modbus / multi-user / scenario / sim-path markers (Section 19) have their own coherence rules; a property cannot be both Modbus = "..." and Transient (Modbus implies persistence via the modbus runtime).

The list extends via plugins (Section 18.2): an industrial-training plugin can register additional validators alongside its specifier handlers.

6.3 Validator ordering

Validators within a category run in declaration order (the order the methods appear in their declaring class's source). Within XHT-core validators, declaration order is fixed; within plugin validators, declaration order is per-plugin-assembly and stable across plugin loads. Two validators on the same property both fire; neither short-circuits the other.

6.4 Tooltip metadata extraction

The validator pass is also where tooltip metadata is extracted from comments. Each reflected type's comment block is parsed (Section 3.6) and stored as a ToolTip metadata entry. The validator pass walks every reflected member and applies the ToolTip metadata extraction rule:

  • A ///-style or /** */-style comment immediately preceding a reflected member becomes the member's tooltip.
  • If the member already has an explicit ToolTip = "..." meta specifier, the comment is silently ignored (the explicit value wins).
  • If a member has neither a comment nor an explicit ToolTip, and the module's DocumentationPolicy = Strict (a manifest target setting), the validator logs a warning naming the undocumented member. Default policy is None — no warning — matching UHT.

UHT's tooltip extraction is silent (Section 25.3 footgun #13). XHT's is opt-in-strict but still defaults to silent for parity. Plan Section 2 "Developer settings" row implies XPact will eventually want every developer-facing reflected member documented; the strict policy is the lever.

7.3 Body-macro handling (XGENERATED_BODY())

The body macro is a real (non-empty) macro that the C++ compiler expands to the per-line generated body block. Recognition by the keyword table inside class / struct / interface scope:

[XhtKeyword(Extends = XhtTableNames.Class)]
[XhtKeyword(Extends = XhtTableNames.Class, Keyword = "XGENERATED_BODY")]
private static XhtParseResult XGENERATED_BODY_Keyword(XhtParsingScope topScope, XhtParsingScope actionScope, ref XhtToken token)
{
    XhtClass classObj = (XhtClass)topScope.ScopeType;
    classObj.HasGeneratedBody = true;
    classObj.GeneratedBodyLineNumber = topScope.TokenReader.InputLine;
    classObj.GeneratedBodyColumnStart = topScope.TokenReader.InputColumn;   // NEW Rev 1
    return XhtParseResult.Handled;
}

The body macro records the line number (and column, per the column-precise diagnostics commitment) of its appearance. The emitter (Section 8) places its macro #defines relative to that line so that when the user's C++ is compiled, the macro injects the generated declarations exactly there. This is the mechanism by which XGENERATED_BODY() works at compile time; UHT does the same thing.

Per Contract Section 1.4 (Rev 11 audit minor cleanup #3), the FileId scheme uses an Itanium-ABI-style length-prefixed grammar; Section 10 covers the encoding. The macro name embeds the FileId and the line number, so two body-macro sites in the same header at different lines never collide.

7.5 C# attribute body anchoring

On the C# side, attributes anchor themselves to their target (the class / struct / field / method they precede). No XGENERATED_BODY() equivalent is needed because Roslyn's syntax tree gives XHT the attribute target directly. The C# parse walker (Section 3.5) processes the attribute target and produces the AST node; the emit step (Section 8) writes any per-type body block to the corresponding .gen.cpp (for the type's C++-visible surface that XIL2CPP will generate; the cross-language bridge lives there).

The cross-language emit boundary: a C#-only type (one declared in .cs with no C++ companion .h) gets a .gen.cpp entry only, no .gen.h. A C++-only type gets a .gen.h + .gen.cpp per Section 8.1 / 8.2. A type with a partial declaration on both sides — the .h declares the C++ surface and the .cs declares the C# surface of the same logical type, paired by the XCLASS / [XClass] name — gets both, and the .gen.manifest records the pairing so XIL2CPP's emit knows both surfaces exist.

8. Generated Code Emit

XHT emits four kinds of files per module, in ConstInit style (Contract Section 7.1):

  1. One {Header}.gen.h per reflected C++ header (Section 8.1).
  2. One {Header}.gen.cpp per reflected C++ header (Section 8.2).
  3. One {Module}.init.gen.cpp per module (Section 8.3).
  4. One {Module}.gen.manifest per module (Section 9; the XBT-consumed text manifest).

Outputs go to the module's intermediate directory (typically Intermediate/Build/<Target>/<Config>/Generated/<Module>/; XBT.html Section 18.1). The exact path is controlled by the -Out= CLI argument and the manifest's per-module GeneratedCPPFilenameBase (XBT.html Section 8.3).

8.1 .gen.h per reflected header

For input header {ModulePath}/{HeaderName}.h, XHT emits {ModuleIntermediate}/{HeaderName}.gen.h. The file's contents (mirroring UHT's EpicGames.UHT/Exporters/CodeGen/UhtHeaderCodeGeneratorHFile.cs structure):

  1. License header. The literal // Copyright Simgenics. All Rights Reserved. — matches the engine-wide convention XBT enforces (XBT.html Section 11) and lets every emitted file pass the copyright validator even if invoked standalone.
  2. IWYU pragma. #pragma once + a // IWYU pragma: private, include "..." comment pointing at the source header. Mirrors UHT.
  3. Define guard. #ifdef XPACT_GENERATED_GUARD_<FileId>_h + #error "..." + #endif + #define XPACT_GENERATED_GUARD_<FileId>_h. The guard catches double-includes of the same .gen.h — the source header is expected to #include the .gen.h exactly once (the body-macro mechanism requires the .gen.h in scope).
  4. Standard XCore includes. #include "XCoreXObject.h" + #include "ScriptMacros.h" + (when needed) #include "ReflectedTypeAccessors.h", #include "Templates/IsXEnumClass.h", push-model headers. STAGE B: the exact set of includes finalizes at Step 4 when XCoreXObject's surface freezes; Phase 1 emits a provisional set per the dependency requirements analysed at parse time.
  5. Forward declarations. Sorted by namespace, then class name, then source name. Sorted-by-content guarantees byte-identical output across runs (Section 14).
  6. For each reflected type in the header:
    • A code-block comment marker (// XHT body block for AXValve at line 14).
    • #if / #endif wrapping the DefineScope of the type (e.g. #if WITH_EDITOR ... #endif).
    • One or more #define <FileId>_L<LineNumber>_<MacroSuffix> ... macros — one per suffix in the body-macro table (Contract Section 1.3): _PROLOG, _INCLASS, _RPC_WRAPPERS, _ACCESSORS, _FIELDNOTIFY, _VINTERFACES, _STANDARD_CONSTRUCTORS.
    • A final #define <FileId>_L<LineNumber>_GENERATED_BODY ... that composes the per-suffix macros in the order Contract Section 1.3 specifies (_INCLASS → _RPC_WRAPPERS → _ACCESSORS → _FIELDNOTIFY → _VINTERFACES → _STANDARD_CONSTRUCTORS).
  7. Current-file-ID anchor. #define CURRENT_FILE_ID <FileId> at the end. This is how XGENERATED_BODY() the macro (defined in XCoreXObject's ScriptMacros.h) finds its per-line definitions: the macro looks up CURRENT_FILE_ID_L<__LINE__>_GENERATED_BODY after token-pasting.

The macro-suffix vocabulary is locked at Contract Section 1.3. XPact's set is identical to UHT's except XHT does not emit Verse suffixes (no Verse support per Section 25.2 item 6).

Phase 1 suffix vocabulary scope (NEW Rev 3, X-M2). The Phase 1 suffix set is the 8 macros locked in Contract Section 1.3 + ContractSurface.BodyMacroSuffixes: PROLOG, GENERATED_BODY, INCLASS, RPC_WRAPPERS, ACCESSORS, FIELDNOTIFY, VINTERFACES, STANDARD_CONSTRUCTORS. UHT has 22 actual suffixes in its emit pipeline. UHT's additional 14 suffixes (_RPC_WRAPPERS_NO_PURE_DECLS, _ENHANCED_CONSTRUCTORS, _INCLASS_NO_PURE_DECLS, _INCLASS_IINTERFACE, _INCLASS_IINTERFACE_NO_PURE_DECLS, _AUTOGETTERSETTER_DECLS, _CALLBACK_WRAPPERS, _SPARSE_DATA, _ARCHIVESERIALIZER, _GENERATED_UINTERFACE_BODY, _GENERATED_BODY_LEGACY, _DEPRECATED_DECLARATIONS, _INCLASS_DECLARES, _ENHANCED_RPC_WRAPPERS) cover Unreal-specific surfaces: legacy compatibility (_LEGACY migration burden for UE 4 → 5), FFastArraySerializer codec, interface dispatch variants (the IInterface / UInterface separation overhead), AutoGetterSetter properties, and sparse-data delta replication. Phase 1 XHT does not need these because: (a) no legacy _LEGACY migration burden — XPact is greenfield; (b) FFastArraySerializer support is Phase 2 (Section 19.5); (c) interface dispatch uses the unified _INCLASS (XPact has no IInterface / UInterface separation overhead per Section 4.5 + the C# attribute-only variant); (d) AutoGetterSetter and SparseData are post-MVP. Adding any of these suffixes requires a Contract Section 1.3 amendment + ContractSurface.SemanticVersionTag hand-bump (the BodyMacroSuffixes table is part of the auto-derived contract surface per Contract Section 10.2 step 4; adding a suffix automatically rotates the structure hash).

8.2 .gen.cpp per reflected header

For input header {ModulePath}/{HeaderName}.h, XHT emits {ModuleIntermediate}/{HeaderName}.gen.cpp. The file's contents (mirroring UHT's EpicGames.UHT/Exporters/CodeGen/UhtHeaderCodeGeneratorCppFile.cs):

  1. License header.
  2. Required includes. Computed from the resolved type graph. Always includes the source header + the corresponding .gen.h + a small set of XCoreXObject runtime headers.
  3. Static-assert pinning the active object format. static_assert(XPACT_WITH_CONSTINIT_XOBJECT, ...) matching the ConstInit mode lock (Contract Section 7.1). A consumer compiled against the Params-style object format that links against ConstInit-emitted code fails the assert.
  4. Empty-link sentinel. void EmptyLinkFunctionForGeneratedCode_<filename>() {} — a force-link sentinel so the cpp file is not dead-stripped by the linker. Mirrors UHT.
  5. Forward declarations of the singleton-getter functions.
  6. "Cross Module References" section. extern declarations for everything that lives in another module. Sorted by mangled name (Section 14 byte-identical-output requirement).
  7. "Same Module References" section. extern declarations for everything in another header within the same module.
  8. For each reflected type in the header:
    • A Z_Construct_X<ClassName>_Statics struct containing arrays of param descriptors, property data, name data. STAGE B: the byte layout of the descriptors finalizes at Step 4; Phase 1 emits provisional layouts pinned to // STAGE-B-PROVISIONAL comment markers so downstream readers can identify provisional content for invalidation post-Step 4.
    • A Z_ConstInit_X<ClassName>(ETypeConstructPhase) function returning the XClass pointer. Phase 1 emits the ConstInit-style body (constexpr initialization of class descriptors with runtime pointer fixups only, per Contract Section 7.1).
  9. IMPLEMENT_CLASS(...) macro invocation (or IMPLEMENT_INTRINSIC_CLASS for intrinsic types).
  10. GENERATED_NATIVE_INTERFACE definitions for XINTERFACE pairs.

The structure matches UHT line-by-line. XHT's emit code path is the largest single chunk of code in XHT.Emitter (~3,000 lines projected, matching UHT's emit code-gen scale). The complexity is unavoidable; the emit step has to produce per-type descriptors for every reflected language feature.

8.3 {Module}.init.gen.cpp per module

One per module. Mirrors UHT's EpicGames.UHT/Exporters/CodeGen/UhtPackageCodeGeneratorCppFile.cs:

  • License header.
  • Includes. #include "XCoreXObject.h" + (when needed) module-level extension headers.
  • Empty-link sentinel. void EmptyLinkFunctionForGeneratedCode_<Module>_init() {}.
  • Aggregated forward declarations.
  • Linkable-objects table. extern <MODULE>_API XObject* const ModuleLinkableObjects<Module>[N] = { ... }; — used by the runtime to resolve cross-module pointers. Mirrors UHT's ModuleLinkableObjects pattern.
  • The Z_Construct_XPackage_<Module> function. Registers all classes / structs / enums / functions for the module with the runtime FName / FClass table.

8.4 Sentinel outputs for headers without reflected types (REVISED Rev 2)

Rev 1 said: if a header has no reflected types, no .gen.h is emitted and the source header's #include "X.gen.h" would fail to compile, surfacing the issue. That posture contradicted XBT's action-graph contract: XBT pre-discovers expected outputs (Section 9.3.1) and treats every .h as potentially producing a .gen.h + .gen.cpp; the action's ProducedItems (Rev 3 terminology correction per X-M19 — the prior "ActionGraph.ProducedItems" was inaccurate; ProducedItems is a property on the individual IExternalAction, not on the ActionGraph itself) assumes those files exist after a successful run, and the post-XHT consistency check (XBT.html Section 9.4 for the EmitReflectionAction shape + Section 6.4 rule 4 for the orphan-sweep aspect; Rev 3 cross-ref correction per X-M18 + Section 9.3.1 of this spec) treats missing-but-expected files as a graph error rather than a benign empty case.

Rev 2 resolution: XHT emits empty sentinel .gen.h and .gen.cpp files for every header that opens with a #include "<Header>.gen.h" but contains no reflected types. The sentinels carry the license header + a one-line marker comment + the include guard (and, for .gen.cpp, the static empty-link sentinel function); no body-macro content. Example:

// Copyright Simgenics. All Rights Reserved.
// XHT: no reflected types in this header
#pragma once
#ifdef XPACT_GENERATED_GUARD_<FileId>_h
  #error "XPACT_GENERATED_GUARD_<FileId>_h is already defined."
#endif
#define XPACT_GENERATED_GUARD_<FileId>_h
// (no body macros — this header reflects nothing)
#define CURRENT_FILE_ID <FileId>

The sentinel preserves the pre-discovered output set so XBT's action graph stays honest, AND it keeps the source-side #include "X.gen.h" compile-clean. The empty-link sentinel in the corresponding .gen.cpp ensures the TU is not dead-stripped. Diagnostic posture (NEW Rev 2): XHT emits a soft warning XHT070 — header <Header> includes its .gen.h but reflects no types; sentinel emitted by default; the warning is suppressed under -AllowEmptyReflectedHeaders=true for transitional codebases. The warning is intentionally soft because XBT's pre-discovery cannot distinguish "developer added #include "X.gen.h" but forgot to add markers" from "header genuinely reflects no types but exists for forward-declaration value" until parsing completes.

Headers with reflected types continue to emit content-bearing .gen.h + .gen.cpp as before (Sections 8.1 + 8.2). The per-module .init.gen.cpp is emitted unconditionally for every module containing at least one reflected type (across all its headers + .cs files); modules with zero reflected types still emit the file with the empty ModuleLinkableObjects array so the action graph's pre-discovery entry resolves.

8.5 Atomic write-if-changed

Every output is written to a <filename>.tmp.<pid>.<guid> first, then content-compared against the existing file. If the content matches byte-for-byte, the temp is deleted and the existing file's mtime is left alone. If the content differs, the rename swaps in the new file atomically. This is critical for incremental builds — if XHT regenerates the same content (because the .cs / .h didn't change in any way that affected reflection), the on-disk timestamp doesn't change and the C++ compiler doesn't recompile the consumer.

The pattern mirrors UHT's UhtExportFactory.SaveIfChanged (UhtSession.cs:375–476) and XBT.html Section 6.4's atomic-rename contract. The temp-file naming convention <output>.tmp.<pid>.<guid> matches XBT's exactly, so XBT's orphan-temp sweep (XBT.html Section 6.4 rule 4) cleans up XHT's orphans the same way it cleans up XBT's compile orphans. The GUID component avoids the timestamp-leak footgun XBT.html Section 6.4 already mitigates (XPact-wide reproducibility envelope, Contract Section 2.1).

-FailIfChanges=true mode. When set, content mismatch produces a .conflict file (the new content written to <filename>.conflict for inspection) plus an error exit 62. Used in CI to enforce that all generated code is checked in — if XHT's emit produces different content than the committed .gen.h, CI fails. Mirrors UHT's -FailIfGeneratedCodeChanges.

8.6 Reference-snapshot modes (-WriteRef / -VerifyRef)

For golden-output testing (Section 21.3): -WriteRef=<dir> writes every emitted file to <dir>/ in addition to the normal output path. -VerifyRef=<dir> compares every emitted file against the reference set in <dir>/ and exits 62 on any mismatch (with a unified diff in the diagnostic). XHT also supports -VerifyRef as the default in CI — CI runs with -VerifyRef=<committed-snapshot> on every PR, so any drift in XHT's emit shape is caught at PR time. This is a Section 25.2 item 8 divergence from UHT (UHT's -WriteRef / -VerifyRef are opt-in).

9. Manifest Contract with XBT

XBT consumes XHT's per-module text manifest (.gen.manifest) as XHT's opaque output surface. XBT does not parse .gen.h or .gen.cpp content; the manifest is the join. The manifest's design is the largest XHT divergence from UHT (Section 25.2 item 2): UHT writes only an "external dependencies file" and relies on UBT pre-computing the output filenames mechanically.

9.1 Input from XBT

XBT writes Intermediate/Build/<Target>/<Configuration>/Manifest.json + Manifest.fbs.bin (Contract Section 10.2, Addendum Section 3.3). XHT reads the binary sidecar preferentially; falls back to JSON on FBS verify failure. The manifest's per-module record carries everything XHT needs:

  • Name — the module name.
  • Tier, ModuleType, Languages — for tier-aware emit decisions and language switching.
  • BaseDirectory — the module's source root, relative to RootLocalPath.
  • SourceFiles — the list of every .h + .cpp + .cs under the module, with IsCSharp / IsHeader / IsTestOnly flags. XHT iterates over the entries with IsHeader = true to find C++ headers to parse, and the entries with IsCSharp = true to find C# files to parse.
  • IncludePaths — for resolving #include directives during the C++ preprocessor pass.
  • PublicDefines — for honouring #if directives at parse time.
  • ModuleDependencies — for cross-module type-reference validation.
  • GeneratedCPPFilenameBase — XHT uses this to name the per-module {base}.init.gen.cpp and {base}.gen.manifest.
  • Target object — the ABI envelope (Architecture, GCRootABI, ExceptionABI, ManglingScheme), StationRole, FipsMode, etc. XHT uses the envelope at emit time to choose the correct ABI version of the emitted descriptors (Phase 1 only emits the v1 ABI, but the envelope is checked so a future ABI change is caught at the manifest layer).

The Phase 1 limitations called out in Addendum Section 10 apply to XHT:

  • ClassesHeaders not in the schema (Addendum item 4): XHT does not consume ClassesHeaders; modules that legitimately ship UE-style Classes/ headers place them in SourceFiles with IsHeader = true, and XHT picks them up normally.
  • Header-category lists empty in Phase 1 (Addendum item 5): the PublicHeaders / PrivateHeaders / InternalHeaders arrays in the manifest are emitted empty. XHT discovers headers from the full SourceFiles list (where every header carries IsHeader = true).
  • No CppDependencyCache in Phase 1 (Addendum item 1): XHT emits actions whose PrerequisiteItems are explicit lists of every header consumed. The XBT-side ParseHeadersAction + EmitReflectionAction (XBT.html Section 9.4) consume the manifest's SourceFiles list directly; transitive header dependency tracking is Phase 2.

9.2 Output from XHT: the .gen.manifest

For each module, XHT emits {Module}.gen.manifest alongside the generated headers + cpp files. The manifest is a text file with a stable line-oriented format that XBT parses for two purposes:

  1. Output enumeration — XBT needs to know the list of .gen.h and .gen.cpp files XHT actually produced this run, so XBT can wire them up as ProducedItems in the action graph.
  2. Cross-language input tracking — for each .gen.h, XBT records the list of input .h + .cs files that contributed to it. When any of those input files changes, the .gen.h is reinvalidated; when the .gen.h's content hash changes, downstream .cpp compiles that listed it in their PrerequisiteItems are reinvalidated.

Format (illustrative; Phase 1 schema):

# XHT module manifest — XScoring
# Schema version: 1
# ContractVersion: 13.2+b04ae3cc84cdd9f3
# Module: XScoring
# Tier: Engine
# EmitMode: ConstInit
# GeneratedAtUtc: 2026-05-20T14:00:42Z

[Generated]
XValve.gen.h       hash=ab12cd34ef561234
XValve.gen.cpp     hash=bc23de45f0671234
XScoring.gen.h     hash=cd34ef56a1781234
XScoring.gen.cpp   hash=de45f067b2891234
XScoring.init.gen.cpp   hash=ef56a178c39a1234

[Inputs]
XValve.gen.h: Public/XValve.h
XValve.gen.cpp: Public/XValve.h
XScoring.gen.h: Public/XScoring.h, Private/ScoringRubric.cs, Private/ScoringSession.cs
XScoring.gen.cpp: Public/XScoring.h, Private/ScoringRubric.cs, Private/ScoringSession.cs
XScoring.init.gen.cpp: Public/XScoring.h, Private/ScoringRubric.cs, Private/ScoringSession.cs

[Types]
XValve C++ Public/XValve.h:14:1
ScoringRubric C# Private/ScoringRubric.cs:8:14
ScoringSession C# Private/ScoringSession.cs:12:14

[Errors]
# (empty on success; one line per error otherwise)

[Warnings]
# (empty on success; one line per warning otherwise)

Sections:

  • [Generated] — one line per emitted file with the content hash. XBT uses the hash as the action's ContentHash. Rev 2 correction: earlier drafts emitted a per-file bExcludeFromSharedPCH=true flag on the .gen.h rows; the actual schema (Manifest.fbs Module.b_exclude_from_shared_pch; ManifestSchema.cs:60 Module.ExcludeFromSharedPCH) carries the flag only at module granularity, and XBT's BuildSharedPchGroups (XBT.html §15.4) consults the per-module flag exclusively. The .gen.h's location under Generated/ is the implicit signal the SharedPCH grouper uses; no per-file .gen.manifest flag is needed in Phase 1.
  • [Inputs] — for each generated file, the list of input source files that contributed to it. XBT uses this to set up the per-action PrerequisiteItems when scheduling the consumer compile actions.
  • [Types] — for each reflected type, the source language tag, the declaring file, and the line:column of the declaration. Useful for IDE integration (jump-to-source on a reflection inspector).
  • [Errors] and [Warnings] — diagnostic surface, MSBuild-format lines. Empty on success.

Schema versioning. The first three lines are header comments: Schema version identifies the manifest grammar revision; XBT validates the schema version against the version it knows. ContractVersion is the contract-surface hash; mismatches are caught at the join-key level by XBT's own action history. EmitMode is the lock on Contract Section 7.1; mismatches are caught here. Schema additions are append-only; new sections may be added at the bottom without breaking older XBT readers (the reader stops at # End of XHT manifest if present, otherwise consumes to EOF).

Path constraints (NEW Rev 3, Xm4). Paths in the [Inputs] section MUST NOT contain commas (the section uses comma-separated input lists per the format above; an embedded comma would be ambiguous with the list separator). XHT's manifest writer validates every input path at write time and rejects with a build error XHT005 — Source path <path> contains comma; the .gen.manifest [Inputs] section format reserves commas as separators. before write. This is a pre-write check, not a parser-side check; the manifest never persists invalid bytes. Developers hitting the error rename the offending file (no engine path requires commas; the constraint is mild).

Whitespace alignment (NEW Rev 3, Xm5). Fields within [Generated] / [Inputs] lines are whitespace-separated; the alignment shown in the example above (extra spaces between filename and hash= column for readability) is for HUMAN READABILITY ONLY. Parsers consume one or more whitespace characters between tokens (the standard whitespace-token rule); two-space, four-space, tab-separated forms are all equivalently valid. XHT's writer emits column-aligned content by default to minimise diff churn when filenames are similar lengths, but a manifest manually edited to compact-space form parses identically.

Hash format (REVISED Rev 4 per Xm2; NEW Rev 3 X-M9). Hashes in the [Generated] section are the 16-hex prefix of BLAKE3. Timing detail: hashes are computed over the temp file's byte sequence (which becomes the final on-disk content post-atomic-rename); the value flows into the .gen.manifest after the rename completes. The Rev 3 wording "computed AFTER the temp→final swap" was misleading — the bytes hashed pre-rename ARE the bytes that persist post-rename (the atomic rename is bytewise; no transformation is applied), but the computation itself happens before the rename so the manifest emit can include the hash in the same write pass. The full 256-bit BLAKE3 is computed internally but only the first 16 hex chars (64 bits of collision resistance) flow into the .gen.manifest — matching the truncation discipline XBT uses for ContractStructureHash + the discipline XBT's per-action cache key uses. The hash is over the file's byte content only, not its filename or mtime.

ContractSurface boundary (REVISED Rev 3, X-M10 + Rev 2 clarification). The .gen.manifest grammar is XHT-side-stable but is NOT part of ContractSurface — the surface that drives the auto-derived structure hash in ContractVersion.Current (XBT.html Section 8.1) excludes the XHT manifest grammar by construction (only namespace-scoped public enums + the explicit element list participate). The Schema version bump on substantive .gen.manifest schema changes (e.g., adding a new section, changing the line-format of an existing section, repurposing a field) therefore requires a coordinated ContractSurface.SemanticVersionTag hand-bump from XBT.html so the version-rotation cascades through the on-disk artefact set. Cross-reference: ContractSurface.cs at Engine/Source/Programs/XBT/XBT.Manifest/ContractSurface.cs is the C# source of truth for the surface; see Contract Section 10.2 for the canonical surface enumeration. Cosmetic header-comment edits (e.g., adjusting the GeneratedAtUtc field's emission rules under -VerifyRef) do not require the hand-bump. Who initiates the bump (X-M10): coordinated SemanticVersionTag bumps are initiated by the XHT team in coordination with the Contract maintainers. The XHT.Tests schema-stability test fails the build if XHT emits a .gen.manifest at a different schema version than the test expects; this gate requires an explicit SemanticVersionTag bump in ContractSurface.cs to land alongside the XHT-side change. The bump-initiation discipline keeps the XHT-emitter schema and the Contract surface in lockstep without either side drifting silently.

9.3 Pre-discovery vs. discovered outputs

UHT's contract with UBT is that UBT pre-discovers output filenames mechanically: For each reflected header H: out += H.generated.h, H.gen.cpp; For each module M: out += M.init.gen.cpp (UHT reference brief, UHTExecution.cs:1208–1225). UBT therefore builds the compile graph before UHT runs.

XPact's per-file dependency model (Contract Section 8 + Addendum Section 4) needs XHT to write back a richer manifest: XBT needs to know what XHT actually produced, not just what UHT-style pre-discovery would predict. The .gen.manifest is the answer. XBT still pre-discovers what XHT will produce (Section 9.3.1 below), so the action graph can be built before XHT runs — but after XHT runs, XBT reads the .gen.manifest to confirm and to pick up the per-file input lists and the content hashes.

9.3.1 XBT's pre-discovery rule (REVISED Rev 2 — sentinel convergence)

Before invoking XHT, XBT pre-computes the expected output set per module:

  • For every .h in the module's SourceFiles with IsHeader = true: expect {HeaderName}.gen.h and {HeaderName}.gen.cpp. (Rev 2: XHT emits sentinel files for headers that include their .gen.h but reflect no types, per Section 8.4, so the expected set is the actually-generated set; the pre-discovery and post-run sets converge.)
  • For every module containing at least one .h or .cs: expect {GeneratedCPPFilenameBase}.init.gen.cpp and {GeneratedCPPFilenameBase}.gen.manifest.

XBT seeds the action graph with these expected outputs. After XHT runs successfully, XBT reads the .gen.manifest's [Generated] section and verifies the expected set matches the actually-generated set:

  • Match: the action graph is correct as built; XBT proceeds.
  • Expected but not generated: per the Rev 2 sentinel rule, this case is restricted to headers that do NOT include a .gen.h (developer never wrote #include "X.gen.h"); the pre-discovered output entries for those headers are removed from the graph and the build continues.
  • Generated but not expected: error (XHT produced a file XBT didn't plan for — either a stale output from a previous run or a bug). The error message names the file.

The Phase 1 implementation skews conservative on the expected set: a stale .gen.h from a previous run that isn't in the current .gen.manifest is treated as orphan and the orphan-sweep step (XBT.html Section 6.4 rule 4) reaps it. The reaping rule for .gen.h orphans specifically: any *.gen.h or *.gen.cpp in the module's intermediate directory that isn't in the current .gen.manifest's [Generated] section gets deleted by XBT at the start of the next build. This mirrors UHT's CullOutput mode (UHT reference brief, "If CullOutput is set, the exporter compares declared outputs against the directory contents and deletes any files matching its filter patterns that weren't generated this run.") and prevents stale .gen.h from a deleted reflected type causing ghost compile errors.

9.4 Manifest read by XHT

XHT reads the manifest at StepReadManifest (Section 5.2). The path comes from the -Manifest= + -ManifestBin= CLI args. Both forms are read; FBS is preferred. The FBS reader uses the FlatSharp greedy-materialised serializer path (Addendum Section 3.2). Hardened reader limits per Contract Section 10.2: MaxDepth = 64, MaxBytes = 100 MiB, MaxStringLength = 16 KiB, MaxVectorLength = 65,536. Limit violations exit 50.

The XHT-side reader is in XHT.Manifest/XhtManifestReader.cs. It does not depend on XBT.Manifest at runtime — both projects reference the same Manifest.fbs schema and the same C# DTOs as a NuGet package; XHT links against the schema-compiled types only, never XBT's binary.

10. Mangling + FileId Scheme

The mangling rule for transpiled C# symbols is locked in Contract Section 2. The FileId scheme for body macros is locked in Contract Section 1.4. XHT implements both at emit time.

10.1 FileId encoding

Per Contract Section 1.4, the FileId format is:

_XID_N<PluginNameLen><PluginName>N<LogicalPathSegCount>{N<SegLen><SegName>}_L<LineNumber>_<Suffix>

Each N<Len><Token> is a decimal length prefix immediately followed by the ASCII token. The grammar is bijective by length-prefixing: any (PluginName, LogicalPath, LineNumber) triple maps to exactly one symbol, and every well-formed symbol decodes back to exactly one triple. Collisions between Foo_Bar/X.h and Foo/Bar_X.h are impossible because each segment carries its own length.

XHT's encoder is in XHT.Emitter/XhtFileIdEncoder.cs. It takes the (PluginName, LogicalPath, LineNumber, Suffix) tuple and produces the symbol bytes. The encoder also handles the reserved-character escape: any byte in <Token> outside [A-Za-z0-9] is itself length-prefixed and emitted as its hex escape; this keeps the grammar bijective even for non-alnum-clean path segments. UTF-8 source on Linux paths with diacritics (per the engine-wide UTF-8 commitment at Contract Section 6 — Rev 3 cross-ref correction per Xm2) is handled by the hex-escape rule. The encoder's output is pure ASCII (no UTF-8 bytes survive into the linker-visible symbol).

The decoder in the same file is symmetric. It's used at diagnostic time when a runtime error references a symbol and the human-readable form is reverse-engineered. The diagnostic surface (Section 12) carries both the mangled symbol and the decoded form when the symbol is a generated one.

10.2 Singleton-getter symbol naming

XPact's singleton naming uses the module name as a prefix to avoid UHT's collision footgun (Section 25.3 footgun #9). Format:

Z_Construct_X<Kind>_<ModuleName>_<TypeNameChain>

Where:

  • Kind = Class | Struct | Enum | Interface | Function | DelegateFunction.
  • ModuleName = the manifest's per-module Name verbatim.
  • TypeNameChain = the source-named type, joined with the outer chain via _ for nested types (e.g., a nested struct Outer::Inner becomes Outer_Inner).

For XClass AXValve in module XGameFramework, the singleton-getter is Z_Construct_XClass_XGameFramework_AXValve. The ConstInit variant strips the Z_Construct_ prefix and substitutes Z_ConstInit_: Z_ConstInit_XClass_XGameFramework_AXValve.

For comparison, UHT's pattern Z_Construct_U<EngineName> strips prefixes and omits the module — so two classes named UFoo in different modules collide at link time. XHT's pattern preserves both the source-language prefix (the A or X per the engine naming convention) and the module name, guaranteeing collision-free linker symbols.

10.3 IL2CPP transpiled-symbol mangling

Per Contract Section 2.2, the IL2CPP-emitted symbol format is:

{ContractVersion}__{Namespace}::{Type}::{Method}{GenericArgManglings}{ParamManglings}

XHT does not produce IL2CPP-mangled symbols (that's XIL2CPP's emit job per Section 17.1). XHT's emit references the IL2CPP-mangled names indirectly via the cross-language type-reference table (Section 17.2): for each C#-declared type in the module's reflection surface, XHT emits the IL2CPP-mangled extern declaration in the corresponding .gen.cpp so the runtime's class-descriptor table can resolve the C# type at link time.

XHT's emit uses the IL2CPP mangling rule (Contract Section 2.2) at link time; XIL2CPP's emit produces the actual symbol definition. The two tools share the mangling rule via a shared XPact.Mangling NuGet package referenced by both.

For AXValve at line 14 of plugin Engine with logical path XGameFramework/Public/Valves/XValve (the example from Contract Section 1.4):

// Suffixes for the same site:

_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_ACCESSORS

// Singleton-getter:

10.5 Line-number sensitivity and the hot-reload concern

The FileId scheme embeds the line number of the XGENERATED_BODY() macro. UHT does this too; UHT footgun #10 (Section 25.3) is that inserting lines above the class invalidates the macro name — Live Coding gets confused and builds fail with cryptic "undefined macro" errors.

XPact inherits this concern. Mitigation: the body-macro name is content-dependent on the line, but the singleton-getter name (Section 10.2) is not — the runtime's class lookup resolves through the singleton-getter, not through the body macro. Live Coding patches the singleton-getter; the body macro is consumed at compile time and never appears in the linker-visible symbol set.

Phase 2 deliberation: a stable token (FileId + class name, sans line number) for the body macro is an open question (Section 26). Adopting it would require a Contract Section 1.4 revision because the file-ID grammar is one of the 8 elements in ContractSurface per Step 0.5 Addendum Section 3.5 (Rev 3 wording correction per Xm6 — specifically ContractSurface.FileIdScheme, element 6 of the canonical 8-element serialisation enumerated at Addendum Section 3.5; the prior wording "step 6 of the auto-derived structure hash" was imprecise about which mechanism establishes the surface membership). The Phase 1 commitment is the UHT-equivalent line-based scheme; deviation is post-MVP.

11. Threading + Parallelism

XHT's threading model mirrors XBT.html Section 20 (XBT's threading): a small main-thread surface plus a worker pool sized to Environment.ProcessorCount. The work is parallel where the resolve phase permits it (Section 5.1) and serial where the type-graph dependencies require it.

11.1 Parallel-per-source-file parse

The StepParseHeaders phase (Section 5.2) uses Parallel.ForEach over the module's source files. Each file parses independently, producing a partial AST and a list of forward declarations. The session's symbol table is not written during this phase — population happens in the next phase (StepPopulateTypeTable), serially, so write contention is zero.

For each parser instance, the C++ tokenizer is per-thread (the thread-local specifier-parser optimization from Section 7.2). The Roslyn parser is also per-thread: CSharpSyntaxTree.ParseText allocates its own immutable parse tree per call, so concurrent calls don't contend on shared state. The threading overhead is one Task per file, which is well-amortised over the parse cost.

11.2 Parallel resolve phases

Per Section 5.1 (7 active phases post-None per Rev 4 X-CR2-Round2):

  • Pairings and InvalidCheck: per-header parallel.
  • BindSuperAndBases: per-header parallel; populates each type's Super pointer from its declared SuperIdentifier string by symbol-table lookup.
  • RecursiveStructCheck: per-header parallel; walks each struct's Super chain + field-type graph for cycles (depends on Super pointers being populated by the prior phase, matching UHT UhtSession.cs:1461 precedent).
  • ResolveBases and Properties: per-header parallel (each header's resolve doesn't need the full type graph for these phases, only the symbol table, which is read-only after StepPopulateTypeTable).
  • Final: serial (cross-language consistency walk; see Section 5.7).

Mitigating Final's single-threadedness (Section 25.3 footgun #4): XHT scopes Final to genuinely-whole-program checks. The validator pass (Section 6) runs after Final and is per-type parallel.

11.3 Parallel emit

The emit phase (Section 8) runs per-header parallel within a module: every .gen.h + .gen.cpp pair is independent. Per-module {Module}.init.gen.cpp + {Module}.gen.manifest are written as the final aggregation step, after all per-header emit completes; this requires the full set of emitted hashes.

Per UHT precedent, the per-header emit task can be scheduled with prerequisite edges — module B's EmitReflectionAction can wait on ParseHeadersAction for module A (per XBT.html Section 9.4 split). XHT itself runs as a per-module subprocess invocation (XBT.html Section 9.1), so the inter-module parallelism is XBT's responsibility; within a single XHT subprocess, the parallelism is intra-module per-header.

11.4 Byte-identical-output guarantee under parallelism

The byte-identical-output requirement (Section 14) is critical for the Foundation Prototype reproducibility criterion (Contract Section 12.1). Achieving it under parallel emit requires:

  • Sorted iteration order wherever the emit consumes a collection. Symbol-table queries return results in deterministic order (caseless name lookup is by hash-bucket then within-bucket sorted-ordinal); type-graph walks iterate Children in source-declaration order (a stable property of the AST since the parser writes children in source order); cross-module reference lists are sorted by mangled name before emit.
  • Per-task isolation. The emitter writes to per-header temp files; no shared accumulator. The aggregation step (per-module init.gen.cpp) walks the per-header outputs in sorted order.
  • StringComparer.Ordinal throughout. No culture-aware comparisons. Matches XBT's discipline (Addendum Section 2.3).
  • No timestamps in emit. The GeneratedAtUtc in the manifest (Section 9.2) is the one exception — it's a diagnostic field for humans, not part of the byte-identical surface. Phase 1 emits a fixed sentinel 2026-05-20T00:00:00Z when running under -VerifyRef to preserve byte-identicalness; production emits the real UTC time but the field is in a comment-line at the top of the manifest and is also excluded from XBT's content hash by hashing only the body (everything after the header comment block).
  • Roslyn determinism — partial class file ordering (NEW Rev 3, X-M4). C# source-file enumeration order is OrdinalSort(manifest.SourceFiles where IsCSharp = true) before invoking the Roslyn walker; partial-class declarations are merged in this canonical order so the resulting AST is independent of filesystem dir-walk order. Filesystem traversal order can differ between Linux (ext4 inode-order walk) and Windows (NTFS B-tree-order walk); the explicit ordinal sort makes the AST independent of the underlying filesystem's enumeration semantics. Two partial-class fragments declared in different files but with the same containing class name see consistent declaration order in the merged AST.

11.5 Cancellation

Ctrl-C / SIGINT installs a CancellationToken. The token is honoured at:

  • Every foreach over headers / modules.
  • Every per-file iteration within a header.
  • Immediately before any write to a temp file (so a partial write doesn't begin).
  • Between resolve phases.

5-second grace period (matches XBT.html Section 6.4). After grace, in-flight work is interrupted; partial outputs follow the pinned temp-file convention (Section 8.5) and are swept either by the current process (on SIGINT) or at next startup (on taskkill /F); the streaming JSON channel emits a final cancellation record; exit code 130. Symmetric with XBT.

Job Objects and process trees (Rev 2 clarification). XHT does not spawn subprocesses (per Section 1.5: "no PATH manipulation; XHT does not shell out to subprocesses"). The Windows Job Object discipline that XBT.html Section 19.3 documents (JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE ensuring every spawned child dies with the parent) applies to XBT-as-orchestrator, not to XHT-as-standalone. In the XHT-as-subprocess case (XBT invoking XHT.exe with cancellation propagation per Section 1.5), XBT's Job Object is the discipline; XHT itself contains no orphan-child reaping logic. In the XHT-as-standalone case (CI gate, IDE invocation), there is no child-process tree to manage — XHT is a leaf process. The Windows-specific reaping infrastructure is therefore unneeded inside XHT.

11.6 SingleInstance discipline (NEW Rev 3, X-M7; anchor added Rev 4 per X-Round2-M5)

XHT acquires a per-module named OS mutex when running emit-module or parse-module modes, mirroring XBT.html Section 6.5's discipline. The mutex name format:

XHT_Emit_<Blake3HexShort(EngineRoot + Module + Configuration + Platform)>

The mutex is per-module (not per-target as in XBT) because each module's output directory is disjoint — two concurrent XHT invocations targeting different modules in the same target write to disjoint Generated/<Module>/ trees and do not race. Two invocations targeting the same module's emit DO race on the .gen.h / .gen.cpp / .init.gen.cpp / .gen.manifest outputs (the temp-file-+-rename atomic-write protocol guarantees no torn writes, but the order of which invocation's content lands is unpredictable; downstream consumers may pick up the loser's output).

Default behaviour: mutex.WaitOne() blocks until the other holder releases. The lock is acquired before parse begins and released in the finally after the manifest emit completes.

With -NoMutexWait: mutex.WaitOne(TimeSpan.Zero) — if the mutex is held, XHT exits 1 with a diagnostic naming the held module identity. Suitable for CI agents that prefer fast-fail over indefinite block (matches XBT's -NoMutexWait shape per XBT.html Section 1.1).

Modes that DO NOT acquire the mutex: validate-only, dump-ast, help, version. These are read-only (validate-only emits no output files; dump-ast writes to stdout or a caller-named file; help / version touch no module-level resources). The mutex is unnecessary; acquiring it would needlessly serialise read-only invocations.

Cross-platform: .NET's Mutex(initiallyOwned, name) maps to CreateMutex on Windows and to a POSIX named semaphore (/dev/shm-backed) on Linux + Android, so the same coordination works between an XBT-spawned XHT subprocess and a developer's standalone XHT.exe invocation on the same module.

12. Error Reporting

XHT emits diagnostics in MSBuild format on stderr and in parallel JSON form on a streaming channel. Both forms are content-equivalent at the diagnostic level. The discipline mirrors XBT.html Section 21.

12.1 MSBuild text format

Every diagnostic uses the format:

<file>(<line>,<column>): <severity> XHT<NNN>: <message>

Severities: error, warning, info, trace, deprecation. The XHT<NNN> code is XHT-specific (not the exit code — the exit code is one of the contract codes in Section 1.3; the per-diagnostic code identifies the diagnostic kind for IDE / CI filtering).

Examples:

Engine/Source/Runtime/XGameFramework/Public/XValve.h(14,1): error XHT040: Missing XGENERATED_BODY() in reflected class <AXValve>.
Engine/Source/Runtime/XScoring/Public/XScoring.h(28,5): error XHT051: Specifier 'BlueprintReadOnly' conflicts with 'EditAnywhere' on property <OpenFraction>.
Studio/Plugins/IndustrialEquipment/Source/IndustrialEquipment/Private/Pump.cs(42,17): error XHT062: Cross-language reference: property <Inlet> of type <ValveBase> resolves to a non-reflected C# type. Add [XClass] to ValveBase or remove the reflection marker.
Engine/Source/Runtime/XGameFramework/Public/XValve.h(14,1): warning XHT104: Reflected type <AXValve> has no tooltip metadata; documentation policy is Strict.

XHT's diagnostic format diverges from UHT's in one respect: column-precise (Section 25.3 footgun #1 preempt). The (line,column) pair pinpoints the offending token's start. IDEs can render an exact red squiggle; CI dashboards can deep-link to the offending byte. UHT carries only the line.

12.2 Token range carry-through

The C++ tokenizer (Section 3.1) records (StartLine, StartColumn, EndLine, EndColumn) per token. The Roslyn parser (Section 3.5) carries equivalent ranges via Roslyn's SyntaxToken.SpanStart + Span.End, projected into XhtToken. The AST node (Section 4.1) carries the range. The diagnostic site (Section 12.3) carries it again. Every diagnostic in XHT therefore has a token-precise range; the format above shows only the start (line, column) but the JSON channel (Section 12.4) carries the full quad.

12.3 Diagnostic catalog

The Phase 1 diagnostic code allocation:

  • XHT001–XHT009 — CLI / manifest infrastructure.
  • XHT010–XHT039 — parser / tokenizer (C++ + C#).
  • XHT040–XHT069 — AST / symbol resolution.
  • XHT070–XHT099 — emit / output.
  • XHT100–XHT119 — validators (specifier coherence, replication, FieldNotify, tooltip).
  • XHT120–XHT139 — cross-language consistency.
  • XHT140–XHT159 — plugin / extensibility.
  • XHT160–XHT179 — XPact-specific markers (Modbus, multi-user, scenario, sim-path).
  • XHT900–XHT999 — internal compiler error (the "Ice" tier; corresponds to UHT's UhtIceException per Section 12.5).

Decimal-only convention (NEW Rev 4, X-Round2-M2). All XHT diagnostic codes are decimal in the range XHT001-XHT999. No hex extensions; bands are tight 20-slot ranges. Rev 3 introduced an XHT11A code in §7.4 (the ConfigConflictsWithNoExport validator) which would have overflowed the validator band XHT100-XHT119 if interpreted decimally (decimal 11A doesn't parse; hex 11A = decimal 282 lands outside the validator band entirely). Rev 4 renumbered the offender to XHT114 (a free decimal slot in the validator band) and adopts this convention explicitly to prevent recurrence. The band layout above is normative; new codes go to the next free decimal integer in the band that matches the diagnostic's category.

The full catalog with one-line descriptions ships at System 2 launch as /Engine/Source/Programs/XHT/XHT.Reference/XHTDiagnostics.md. The catalog is part of the contract surface to the extent that codes are stable across versions: adding a code takes the next free integer; removing or repurposing a code is forbidden. Matches Contract Section 13.2's commitment for exit codes, applied to per-diagnostic codes.

12.4 JSON channel parity with XBT

Per Section 1.4: XHT emits a parallel streaming JSON diagnostic channel mirroring XBT.html Section 21.2. The activation rule matches XBT: explicit opt-in on Linux / Android via -JsonFd=<FD>; automatic on Windows when stdout is not a TTY (sentinel @@XHT-JSON@@ prefix on stdout lines).

JSON record shape:

{"tool":"XHT","action":"parse-module","module":"XScoring","level":"error","code":"XHT051",
 "file":"Engine/Source/Runtime/XScoring/Public/XScoring.h",
 "startLine":28,"startColumn":5,"endLine":28,"endColumn":34,
 "message":"Specifier 'BlueprintReadOnly' conflicts with 'EditAnywhere' on property <OpenFraction>.",

The shape mirrors XBT's record (XBT.html Section 21.2) with "tool":"XHT" attribution. The token range carries through as startLine, startColumn, endLine, endColumn. The source language tag ("sourceLanguage": "Cpp" or "CSharp") lets IDE consumers branch on the parser surface for highlighting.

12.5 Internal compiler errors

Bugs in XHT throw XhtIceException. The session catches and emits an XHT900 "Internal Compiler Error" severity message with the stack trace attached as a "stackTrace" field on the JSON record. Parsing continues if possible (the session does its best to drain to a clean stopping point). On exit, the bug-report URL https://github.com/Simgenics/XPact-Engine/issues/new?labels=xht-ice&template=ice.md is printed to stderr with the captured trace formatted for paste.

Mirrors UHT's UhtIceException handling. Matches the convention XBT.html Section 21 uses for its own internal compiler errors.

12.6 Error vs warning policy

-WarningsAsErrors=true promotes every warning to an error (matches UHT). HasErrors = ErrorCount > 0 || (WarningsAsErrors && WarningCount > 0). The session's exit code is 62 if HasErrors is true.

Per-issue suppression via per-module manifest setting: SuppressDiagnostics = ["XHT104", "XHT115"] would silence those specific diagnostics for that module. Phase 1 does not implement per-module suppression at the manifest level — the manifest schema is locked at Contract Section 10.2 and doesn't expose a suppression slot. Phase 2 may add a per-module diagnostic_suppression field; until then, suppression is global via the -SuppressDiagnostic=XHT104 CLI flag (intended for transitional codebases only; CI gates the flag at "no suppression" by default).

12.7 No fix-it suggestions in Phase 1

UHT has no fix-it suggestions either (Section 25.3 footgun #15). XHT Phase 1 also lacks them; Phase 2 may add structured suggestions for the common cases (missing #include "X.gen.h", missing XGENERATED_BODY(), missing [XClass] on a referenced type). The JSON channel record shape reserves a "fixIt" field for the eventual addition; Phase 1 emits it as null.

13. Hot-Reload + Live Coding Integration

XHT cooperates with XLiveCoding (Phase 2 system) by emitting symbol names that are stable across reflection-preserving edits. The cooperation surface is the singleton-getter name (Section 10.2) and the cross-module reference table (Section 8.2 "Cross Module References" section).

13.1 Phase 1 status

Phase 1 XHT does not have a live-coding-specific code path. The atomic write-if-changed pattern (Section 8.5) supports incremental Live Coding workflows by not touching mtimes on no-op regenerations. UHT's posture (UHT reference brief Section 13) is that UHT is fully snapshot-based; the runtime hot-reload layer takes the generated symbols as input. XHT inherits the posture.

The interface IXhtLiveCodingPatcher is declared in XHT.Tables as a placeholder — Phase 2 XLiveCoding will register a patcher that, given a list of changed source files, asks XHT to emit only the affected .gen.h / .gen.cpp + a delta manifest. The Phase 1 surface is empty.

13.2 Singleton-getter stability across edits

The singleton-getter naming (Section 10.2) uses (Kind, ModuleName, TypeNameChain) — not line numbers. Adding properties, changing function bodies, or reordering members within a reflected type does not change the singleton-getter symbol. Renaming the type does. Live Coding patches resolve through the singleton-getter, so non-renaming edits preserve the patch link.

Line-edit nuance (NEW Rev 3, Xm8). The singleton-getter symbol is stable across non-renaming edits (Section 10.2 naming uses (Kind, ModuleName, TypeNameChain) only); the per-file body-macro FileId shifts with line-number changes (Section 10.5) but Live Coding rebuilds the affected TUs — the body macros are consumed at C++ compile time, not at link time, so a body-macro name change forces a recompile of the consumer TU but does NOT break the linker-visible singleton-getter symbol that the patch link resolves through. The two name spaces are decoupled by design: line-sensitive symbols stay in the source-only body-macro layer (compile-time), line-insensitive symbols stay in the linker-visible layer (link-time + patch-time).

The body-macro names do use line numbers (Section 10.5). The body macros are consumed at C++ compile time and never appear in the linker-visible symbol set, so they don't affect Live Coding's patch link directly — but they do affect whether the C++ compile succeeds. Editing source above a class invalidates the body-macro name; XBT detects the change (the .gen.h's content hash changes), reruns XHT, the regenerated .gen.h picks up the new line number, the next C++ compile is correct.

13.3 Container hot-reload constraints

Per Contract Section 3.7 (Rev 12 N1), container types embedding XGCRootSpan are layout-frozen within a hot-reload session. XHT's reflection emit is independent of the GC-root layout (XHT does not enumerate m_rootSpan as a reflected property; the XPROPERTY set covers only user-authored properties). The reflection metadata XHT emits is therefore unaffected by the container layout-freeze rule. XIL2CPP enforces the layout-freeze at transpile time; XHT's posture is that container reflection (if any user explicitly opts in via XPROPERTY(VisibleAnywhere) TArray<XActor*> ActiveActors) emits the array-property descriptor with the inner-type XActor resolved through the symbol table normally.

(STAGE B) Container-type instantiations like TArray<XActor*>, TMap<FName, FString>, and TSet<UFoo*> produce property descriptors whose byte layout — specifically the inner-property pointer storage, the optional key/value pair offsets for map types, and the variant-tag for the GC-root-span integration — is provisional until the Step 4 XCore-4b addendum freezes the FProperty surface. Phase 1 emits the provisional layout pinned to a // STAGE-B-PROVISIONAL comment marker so downstream consumers can identify provisional content for post-Step-4 invalidation.

13.4 Validator pass on hot-reload-eligible types

When a module's manifest entry has AllowHotReload = true (XBT.html Section 8.3), the Section 6 validator pass runs an additional check: every reflected class in the module must satisfy the layout-stability rules Contract Section 3.7 lists for the container subset. The check is symbolic only at Phase 1 (no actual layout introspection happens until XIL2CPP emit / XCoreXObject runtime); the validator confirms that the class doesn't reorder fields or add fields between two reflection passes by storing the prior pass's field-order hash in the AST cache (Section 16) and comparing.

Phase 1 ships the validator as a no-op (since XLiveCoding isn't operational; there's no patch-DLL to validate against). The validator interface is in place; Phase 2 wires up the layout-comparison logic against XLiveCoding's prior-DLL snapshot.

14. Determinism Contract

Two clean XHT runs over the same input must produce byte-identical output for all four output kinds. This is a critical requirement: Foundation Prototype reproducibility (Contract Section 12.1) cannot be satisfied if XHT introduces drift. The discipline:

14.1 Sorted iteration everywhere

Every collection emit uses sorted iteration:

  • Forward declarations in .gen.h: sorted by (namespace, class name, source name) ordinal.
  • "Cross Module References" + "Same Module References" sections in .gen.cpp: sorted by mangled name.
  • ModuleLinkableObjects array in init.gen.cpp: sorted by type-name ordinal.
  • Per-module .gen.manifest sections: each section internally sorted by filename ordinal.
  • Property descriptors per class: emitted in declaration order (a stable property of the AST since the parser writes children in source-declaration order).

StringComparer.Ordinal + string.CompareOrdinal throughout. No culture-aware comparisons.

14.2 No timestamps, no random

The reflection emit has zero sources of non-determinism:

  • No DateTime.Now embedded in emitted code.
  • No Guid.NewGuid() in symbol names. (The temp-file naming uses Guid per Section 8.5, but the temps are renamed away and never observed in the final output.)
  • No System.Random. No hash-seed-dependent layouts.
  • No file-mtime-dependent invalidation. Per Contract Section 2.1.

The GeneratedAtUtc field in the per-module .gen.manifest is the one observable timestamp; per Section 11.4 it's elided from the byte-identical surface (header comment, excluded from XBT's content hash).

14.3 Parallel-safe

The per-header emit tasks are independent (Section 11.3); no shared accumulator. Per-task output is per-temp-file. The aggregation step walks per-header outputs in sorted order. Two parallel runs of the same module's emit produce the same per-temp-file content; the rename order may differ (depending on dispatch timing) but the final on-disk content is the same set.

14.4 Reproducibility-envelope forwarding

XHT does not emit C++ compile flags — that's XBT's job (XBT.html Section 19). XHT's emit is plain C++ source that the downstream C++ compile consumes; the reproducibility envelope (Contract Section 2.1) is applied at C++ compile time, not at XHT emit time. XHT's only contribution to the envelope is byte-identical emit output (this section's discipline).

14.5 Reference snapshot verification

Per Section 8.6, -VerifyRef=<dir> compares current emit against a committed snapshot. CI runs -VerifyRef on every PR (XHT's "default in CI" mode per Section 25.2 item 8). Any drift in XHT's emit shape is caught at PR time.

The reference snapshot lives under /Engine/Source/Programs/XHT/XHT.Tests/References/<Fixture>/<Module>/ in version control. Updating the snapshot is a deliberate developer act (XHT.exe emit-module -WriteRef=... + commit the diff); CI gates the update via PR review.

15. Caching + Incremental Rebuild

XHT cooperates with XBT's action history (XBT.html Section 15.2) for action-level caching: when the input set (manifest + module's source files + XHT binary's own content hash + ContractVersion) is unchanged, XBT's ActionHistory.IsActionOutdated returns false and the action is skipped entirely. XBT owns the action-level cache; XHT's only responsibility is byte-identical output so the content-hash equality holds.

Within XHT, there's one optional cache layer for incremental performance: the per-module AST cache (Section 16). The cache is opt-in via the CLI flag -EnableInputCache=true and disabled by default in Phase 1; enabling it skips the parse phase when the source files are unchanged but other XHT inputs (e.g., a specifier-validator plugin) changed.

15.1 What XHT does not cache

XHT does not own a cross-tool cache layer. The reflection metadata XCoreXObject's runtime consumes is the freshly-emitted .init.gen.cpp output, recompiled and relinked on every build that changed it; there's no DDC / derived-data layer at XHT.

UHT's "input cache" (UHT reference brief Section 9; UhtInputCache.cs) is a Brotli-compressed per-module AST cache. XHT adopts the same model but as an opt-in (UHT defaults to off too; the cache is for measurable-perf-improvement edge cases). Section 16 covers the format.

15.2 No partial caching

XHT does not cache per-type or per-property partial results. The cache granularity is per-module — one cache file per module per build. This matches UHT's granularity and is justified: the resolve phases need the full module's symbol table, so partial caching would not help the bottleneck (Section 5.1's Final phase).

Per-file incremental invalidation across XBT runs is XBT's responsibility via the action history; per-file incremental invalidation within an XHT run is not implemented.

16. AST Cache (Optional)

When -EnableInputCache=true, XHT serialises the parsed AST per module to a Brotli-compressed binary cache file under {ModuleIntermediate}/{Module}.tokens.bin. On the next run, if the source files are unchanged (validated by ContentHash per source-file entry), the parse step deserialises the cache instead of re-tokenizing. The format is XHT-internal; no other tool reads it.

16.1 Cache file format

[Header]
"XHTC"             4-byte magic
uint32 version     // current = 1
uint32 contractHash // first 16 hex of ContractVersion (Section 8.1) packed as uint32 pair
uint64 xhtAssemblyDateUtc  // UTC ticks of XHT.exe's own build date
uint32 entryCount

[Entry]  (repeated)
  uint32 pathLength
  byte[pathLength] pathUtf8  // relative to RootLocalPath
  uint64 sourceLastWriteUtc  // for first-line invalidation gate
  uint64 sourceContentHashLo, sourceContentHashHi // BLAKE3 128-low bits
  uint32 uncompressedAstSize
  uint32 compressedAstSize
  uint32 astByteOffset  // offset into the cache file's [AST blob] section

[AST blob section]
  Brotli-compressed binary AST serialisation, format per AST nodes' Write methods.

On the xhtAssemblyDateUtc field (Rev 3 polish per Xp2; Rev 2 footnote moved from in-block to inline prose). The field cross-references the XHT.exe content-hash exposed by the version-derived ContractVersion; assembly-date stability is reproducibility-aligned per Contract Section 2.1 because assembly-date stability tracks build-input stability, not wall-clock time. Future polish: replace with the 16-hex-char prefix of XHT.exe's BLAKE3 content hash for stronger invalidation when an XHT binary is rebuilt without a date change (edge case: a forced rebuild via touch may carry the same date as the prior build).

16.2 Validation gates

The cache is validated against:

  • Magic + version: magic must read "XHTC"; version must be the current value. Mismatch → treat cache as empty.
  • ContractVersion hash: a contract revision invalidates the entire cache (since the AST shape may have changed).
  • XHT assembly date: an XHT binary upgrade invalidates the cache (since the serialisation format may have changed).
  • Source content hash per entry: a source-file edit invalidates that entry only; other entries remain valid.
  • Source last-write UTC per entry: a fast-path gate before content-hash — if the mtime matches the recorded one, skip the content-hash recompute. This is a perf optimisation; the content-hash is authoritative. (Note: mtime is used for the fast-path gate only; the actual invalidation surface is content-hash, per Contract Section 2.1's mtime ban for engine-wide invalidation. The fast-path mtime gate is an XHT-internal optimisation that doesn't violate the ban because it never decides invalidation by itself — it only skips work when the content-hash would have agreed.)

16.3 Per-AST-node serialisation

Every XhtType subclass implements a (XhtInputCacheReader reader, XhtType outer) constructor and a Write(XhtInputCacheWriter writer) method. The methods serialise / deserialise the node's fields verbatim. Mirrors UHT's UhtTables.ValidateCacheableTypes reflection check (UHT reference brief Section 9).

The serialised form includes the token range (StartLine, StartColumn, EndLine, EndColumn) so cached diagnostics remain column-precise.

16.4 Cache statistics

The session reports cache statistics on completion:

17. C# Binding Surface + IL2CPP Integration

XHT's C# binding surface is the set of attributes, marker placement rules, and metadata conventions a C# developer writing reflected code targets. The IL2CPP integration is the set of metadata entries XHT emits that the XIL2CPP transpiler (System 6) consumes to produce the cross-language bridge.

17.1 The C# attribute surface

The attribute set mirrors Contract Section 1.1 verbatim: [XClass], [XStruct], [XEnum], [XInterface], [XFunction], [XProperty], [XDelegate], [XParam], [XMeta]. The attributes are declared in the namespace Simgenics.XPact.Reflection, in the package Simgenics.XPact.Reflection.dll (Engine-tier, ships in the engine release artefact). Every C# module that participates in reflection references this package.

Specifier passing on C# attributes uses named parameters: [XProperty(EditAnywhere = true, BlueprintReadWrite = true, Replicated = true)]. The boolean specifiers default to false when omitted; string specifiers default to null. This is a deliberate divergence from C++ (where specifiers are tokens not name=value pairs): C# attribute parameter syntax is named pairs, and forcing positional ordering would be unidiomatic. XHT's parser accepts both conventions on the C# side and normalises to the same internal representation.

The C# attribute declaration in Simgenics.XPact.Reflection:

// Simgenics.XPact.Reflection — XClass attribute (illustrative)
[AttributeUsage(AttributeTargets.Class)]
public sealed class XClassAttribute : Attribute
{
    public bool Blueprintable     { get; set; } = false;
    public bool BlueprintType     { get; set; } = false;
    public bool Abstract          { get; set; } = false;
    public bool Transient         { get; set; } = false;
    public string? ClassGroup     { get; set; } = null;
    public string? Within         { get; set; } = null;
    // ... full set per Contract Section 1.2
}

The attribute carries data only; the runtime sees the marker via XHT's emitted metadata, not via reflection on the attribute itself. The attribute class declaration is therefore minimal — just typed property bags.

17.2 IL2CPP touchpoints

XHT and XIL2CPP run concurrent: Contract Section 10.1 step 3 (XHT) + step 4 (XIL2CPP) are scheduled as concurrent peers, not sequential phases (Rev 2 cross-ref correction). They share the manifest XBT emits. They emit independent outputs. They communicate only via the cross-language reflection metadata XHT writes to the .gen.cpp + .init.gen.cpp — specifically, the FProperty descriptors for C# fields that XIL2CPP's transpiler emits as the C# side of the bridge.

The bridge protocol:

  1. XHT parses the .cs file and produces a reflected type record per [XClass]-attributed class.
  2. XHT emits the C++ side in {Header}.gen.cpp: the FClass descriptor + FProperty descriptors for each [XProperty]-attributed C# field, with the property type resolved through the symbol table (Section 5.3).
  3. XIL2CPP, running independently, transpiles the same .cs file's body (the C# code that implements the methods). XIL2CPP emits the transpiled C++ in Intermediate/.../<Module>/Transpiled/<CSFile>.cs.cpp + .cs.h.
  4. The two emit paths converge at the C++ compile step: the transpiled .cs.cpp #includes the {Header}.gen.h XHT produced, picking up the property accessors XHT emitted; the link step resolves the singleton-getter references between the transpiled and the reflected sides.

The Phase 2 NoThrow lookup (Contract Section 5.2 N2) consults XHT's emitted reflection metadata for cross-module callee classification. XHT's emit therefore carries the NoThrow annotation per Contract Section 1.2 (function-calling-convention specifier).

17.3 Cross-language reflection manifest entry

For each cross-language type pair (a C++ class + a C# partial class declaring the same type), the .gen.manifest's [Types] section emits both source files. This lets XIL2CPP see the pairing at transpile time so the IL2CPP-emitted body code can target the same singleton-getter the C++ side references.

The XIL2CPP-XHT interchange protocol is: XHT emits the cross-language type list before XIL2CPP runs (XBT schedules EmitReflectionAction as a prerequisite of XIL2CPPAction when the two share input .cs files; the action graph encodes this via the manifest's per-module source-file overlap detected by XBT's pre-discovery rule, Section 9.3.1). XIL2CPP reads the per-module .gen.manifest at transpile time (XIL2CPP's own subprocess is launched by XBT with the manifest path passed via the same -Manifest arg XHT uses).

STAGE B: the exact byte layout of the cross-language reflection metadata (the C# field's reflected FProperty descriptor on the C++ side) freezes at Step 4 with the rest of the FProperty surface. Phase 1 emits provisional layouts; XIL2CPP's transpiler honours the provisional shape via the schema-version field in the descriptor.

18. Specifier Extensibility (Plugin Model)

XHT's extensibility surface is attribute-driven, mirroring UHT's EpicGames.UHT/Utils/UhtTables.cs plugin model. New specifiers, new keywords, new exporters, new property types, and new validators are added by writing a method with the appropriate attribute. No source-code edits to XHT itself.

18.1 The five extension points

Each extension point has an attribute defined in XHT.Tables:

  • [XhtSpecifier(Extends = ...)] — specifier handler. The method signature is (XhtSpecifierContext context, XhtSpecifierState state) => void. The method modifies context to record the specifier's effect on the parsed entity.
  • [XhtSpecifierValidator(Extends = ...)] — cross-cutting validator (Section 6.1). Runs after the resolve pipeline (Section 5; seven active phases post-None).
  • [XhtKeyword(Extends = ...)] — keyword recognizer (Section 3.4). The method signature is (XhtParsingScope topScope, XhtParsingScope actionScope, ref XhtToken token) => XhtParseResult.
  • [XhtPropertyType(CppTypeName = "...")] — property-type registration. Maps a C++ type spelling (e.g., "FRotator") to a property class (FRotatorProperty) the parser instantiates when it encounters the type.
  • [XhtExporter(Name = "...", Description = "...")] — custom output exporter. The default code-gen exporter (Section 8) is itself written this way; new exporters can dump JSON, statistics, or custom formats.

The Extends argument names the table the extension contributes to (Global, Class, Struct, Function, Property, PropertyMember, PropertyArgument, Enum, Interface). Tables inherit from base tables: a specifier registered at Field is automatically available in Class, Struct, Enum. Same for keywords. Mirrors UHT's inheritance pattern in UhtStandardTables.InitStandardTables at UhtTables.cs:380–422.

PropertyMember vs PropertyArgument split (NEW Rev 2). UHT distinguishes specifiers valid on function parameters (the call-site argument descriptor) from specifiers valid on class fields (the persisted member descriptor). XHT adopts the same split:

  • PropertyArgument table — specifiers legal on function parameters only: ConstParm, OutParm, ReferenceParm, ReturnParm, UPARAM(ref)-equivalent.
  • PropertyMember table — specifiers legal on class fields only: EditAnywhere, BlueprintReadOnly, BlueprintReadWrite, Replicated, ReplicatedUsing, SaveGame, Transient, Config, FieldNotify.
  • Property table — specifiers legal in both contexts (the base table both inherit from): Category, DisplayName, Meta, NoClear, EditCondition.

Validators catch context mismatches: BlueprintReadOnly on a function parameter fires XHT111 — specifier 'BlueprintReadOnly' valid on members only; not allowed on function parameter <param>. OutParm on a class field fires the symmetric diagnostic. Mirrors UHT's UhtPropertyMemberSpecifier / UhtPropertyArgumentSpecifier distinction.

Conflict detection at table-merge time (NEW Rev 1 vs UHT). Section 25.3 footgun #7: UHT silently coexists with conflicting specifiers (two specifiers with the same name in compatible tables). XHT detects the collision at table-merge time: when a plugin loads, every specifier name is checked against the existing table; a duplicate registration without explicit override flag fails the load with diagnostic XHT140 — Duplicate specifier 'X' registered by both <plugin A> and <plugin B>. The opt-in override flag is [XhtSpecifier(Extends = ..., AllowOverride = true)].

18.2 Plugin discovery

Phase 1 plugin discovery is a filesystem scan (Rev 2). The manifest does not carry a dedicated XhtPlugins entry — neither Manifest.fbs nor ManifestSchema.cs nor ModuleRules.cs declares such a field, and no TOML parser path consumes a xht_plugin = "..." attribute. Instead, at StepLoadPlugins (Section 5.2), XHT walks the manifest's module list and, for each module, scans the tier-appropriate directory tree for sibling *.XhtPlugin.dll assemblies:

  • Engine-tier plugins: <EngineRoot>/Engine/Plugins/<Plugin>/Binaries/<Platform>/*.XhtPlugin.dll.
  • Studio-tier plugins: <StudioRoot>/Studio/Plugins/<Plugin>/Binaries/<Platform>/*.XhtPlugin.dll.
  • Project-tier plugins: <Project>/Plugins/<Plugin>/Binaries/<Platform>/*.XhtPlugin.dll.

Tier identification follows the directory structure verbatim; the scan honours the same tier-order load discipline (Engine first, Studio second, Project third) per Section 20.3 so conflict diagnostics name the redefining tier clearly. Each discovered assembly is loaded via Assembly.LoadFile; XHT scans every type for [XhtPlugin]-attributed types, and scans every method on those types for the extension-attribute set above. Each method is registered into the appropriate table.

Plugin discovery details (NEW Rev 3, X-M8 hole-filling):

  • <Platform> resolution. <Platform> in the directory templates above is the manifest's TargetInfo.Platform value (Win64, Linux, or Android per Contract Section 10.2's FBS schema). It is NOT a .NET RID like win-x64; the per-plugin Binaries/<Platform>/ directory uses XPact's platform vocabulary. The mapping from manifest platform ↔ .NET RID happens at XHT's build / publish step (Section 2.5), not at plugin-load time.
  • <StudioRoot> derivation. <StudioRoot> is derived as the parent directory of <EngineRoot> containing a /Studio/ subdirectory at sibling level (the standard XPact three-tier filesystem layout: RepoRoot/Engine/ + RepoRoot/Studio/ + RepoRoot/Projects/). XHT walks from manifest.RootLocalPath upward looking for a directory containing /Studio/. If no /Studio/ is found anywhere on the upward walk, the studio scan is skipped silently (no studio plugins; the absence is benign — not every repo layout includes a Studio tier).
  • Per-plugin Binaries/<Platform>/ location. Plugin DLLs are located under each plugin's Binaries/<Platform>/ subdirectory (matching the engine-wide platform-binary layout). Absence of Binaries/<Platform>/ for a given plugin is benign (the plugin simply has no XHT-side DLL for that platform); the scan continues to the next plugin without diagnostic.
  • Plugin version-compatibility attribute. Each *.XhtPlugin.dll carries an [assembly: XhtPluginCompiledAgainst("<XHT-version>+<structure-hash-prefix>")] attribute (declared in XHT.Tables/XhtPluginCompiledAgainstAttribute.cs and applied by the plugin's .csproj at build time). XHT validates the attribute against its own version at load:
    • Match: plugin loads normally.
    • Major-version mismatch: plugin load fails with diagnostic XHT142 — Plugin <name> compiled against XHT <plugin-ver> but running on XHT <current-ver>; rebuild plugin against current XHT. Exit 62. The plugin author is expected to recompile their plugin against the new XHT-version's XHT.Tables assembly.
    • Missing attribute: diagnostic XHT143 — Plugin <name> missing XhtPluginCompiledAgainst attribute; plugin compatibility unknown. (Soft warning; load continues.)
  • Specifier-collision rule across tiers. If two plugins from different tiers register the same specifier name with AllowOverride = true, tier-load order applies (Engine first, then Studio, then Project — later wins). Within the same tier, alphabetical plugin name order applies. XHT logs XHT145 — Specifier '<name>' overridden by <plugin-name>; previous registration from <prior-plugin>. as a warning (severity warning, not error) so the user is aware of the override but the build continues. Without AllowOverride = true on the second plugin, the collision fires XHT140 per Section 18.1 (error; load fails).

Phase 2 deferral. A manifest-extension entry — e.g., a per-target XhtPlugins list populated from a future xht_plugin = "..." field on ModuleRules — could replace the filesystem scan with explicit declaration, mirroring UHT's UhtManifest.UhtPlugins pattern. The field is reserved as a Phase 2 enhancement; see §26.2 for the open-question entry. Phase 1 ships filesystem-scan discovery only.

Plugin sandbox. Plugins are .NET 8 assemblies running in XHT's address space. There's no sandbox at Phase 1 (a malicious plugin could shell out, allocate unbounded memory, or call Environment.Exit). Per the engineering posture XPact takes for descriptor evaluation (Contract Section 9.6 sandboxed Starlark), plugins are trusted — they're shipped by Simgenics or signed Studio plugins, not arbitrary user code. The sandbox can land Phase 2 if untrusted-plugin scenarios emerge.

18.3 The default code-gen exporter

XHT's own emit (Section 8) is one such exporter, registered at XHT.Emitter/XhtDefaultCodeGenExporter.cs:

[XhtExporter(Name = "DefaultCodeGen", Description = "Standard XPact ConstInit-style code generation",
             Options = XhtExporterOptions.Default,
             CppFilters = ["*.gen.cpp"], HeaderFilters = ["*.gen.h"])]

{
    // Walk factory.Session.Modules; for each module, emit per-header outputs +

The CppFilters + HeaderFilters patterns are used by the CullOutput step (Section 9.3.1) to identify orphaned outputs from prior runs.

18.4 Alternative exporters

Phase 1 ships three exporters in addition to the default:

  • JsonDumpExporter — emits the resolved AST as JSON. Triggered by dump-ast CLI mode (Section 1.1). Useful for IDE plugins and reflection inspectors.
  • StatsExporter — emits a stats file summarising parse/resolve/emit timing per module, property counts, reflection coverage percentage. Useful for build-time observability.

19. XPact-Specific Markers

XHT supports XPact-specific specifiers via the plugin model (Section 18). Phase 1 ships a single internal plugin assembly — XPact.IndustrialTraining.XhtPlugin.dll — that registers the four XPact-specific specifier groups called out in the master plan: Modbus, multi-user replication, scenario / scoring, and lockstep-determinism sim-path.

19.1 Modbus property markers

Industrial training modules expose values to Modbus PLCs via the engine's Modbus runtime. The Modbus binding is a per-property specifier:

XCLASS(BlueprintType)
class AXValve : public AXActor
{
    XGENERATED_BODY()

    XPROPERTY(EditAnywhere, Modbus = "HoldingRegister:40001")
    float OpenFraction = 0.0f;

    XPROPERTY(EditAnywhere, Modbus = "Coil:00100")
    bool IsManualOverride = false;
};

The Modbus specifier accepts a string of the form "<RegisterType>:<Address>" where <RegisterType> is one of HoldingRegister, InputRegister, Coil, DiscreteInput. XHT validates the string format at parse time (validator XHT160 Modbus_FormatValidator); invalid format fails the build with a column-precise diagnostic.

XHT emits the parsed Modbus binding as metadata on the FProperty descriptor: Property->SetMetaData("Modbus.RegisterType", "HoldingRegister"); Property->SetMetaData("Modbus.Address", "40001");. The runtime Modbus subsystem (separate from XHT, lives in Engine plugin XModbus) reads the metadata at engine boot to wire properties to PLC registers.

19.2 Multi-user replication metadata

Multi-user simulation scenarios (Instructor + Trainee stations sharing simulation state) need replication-condition slots beyond UE's standard set. The XPact plugin registers:

  • COND_InstructorOnly — replicated only to Instructor stations.
  • COND_TraineeOnly — replicated only to Trainee stations.
  • COND_PrimaryTraineeOnly — replicated only to the primary Trainee station (the one currently performing the procedure).

The specifier is on properties: XPROPERTY(Replicated, ReplicationCondition = COND_TraineeOnly). XHT emits the condition value into the FProperty descriptor's ELifetimeCondition slot (Contract Section 1.2). STAGE B: the ELifetimeCondition enum's byte layout freezes at Step 4; Phase 1 emits provisional ordinals.

Plugin-registered ELifetimeCondition extensions (NEW Rev 3 clarification per Xp3). The three XPact-specific conditions above (COND_InstructorOnly / COND_TraineeOnly / COND_PrimaryTraineeOnly) are extensions to UE's standard ELifetimeCondition enum vocabulary. How extension values flow to the runtime is a Phase 2 deferral: the Phase 1 emit reserves a small ordinal range for XPact-specific conditions but does not finalise the mechanism by which a plugin-registered condition value is bound to a runtime dispatch. Three options were considered: (a) a reserved-slot pattern in the enum (impossible if the enum is frozen at the Stage B addendum); (b) a separate XLifetimeConditionExtensions table populated from XHT-emitted metadata (works but requires runtime cooperation from the replication subsystem; the runtime is not in System 2 scope); (c) Phase 2 deferral with explicit note. Recommended: option (c) — Phase 2 deferral. The Phase 1 emit treats the XPact-specific conditions as opaque metadata strings; the runtime maps them to dispatch behaviour. The mapping mechanism (option a vs option b) is decided when XCore-4b's replication subsystem lands at Step 4.

19.3 Scenario / scoring metadata markers

Training scenarios use scoring metadata to drive the post-session evaluation. The plugin registers:

  • XPROPERTY(Scoring = "Critical") on a property indicating the property's value is part of the trainee's scoring outcome.
  • XFUNCTION(ScoringEvent = "ValveOpen") on a function indicating the function call should be logged as a scoring event for replay analysis.
  • XCLASS(ScenarioRole = "ProcessVessel") on a class indicating the class participates in a specific scenario role (Process Vessel, Pump Station, Valve Manifold, etc.).

The scoring metadata is reflection-only: XHT emits the metadata on the FProperty / UFunction / UClass; the runtime XScoring subsystem reads it at scenario boot to build the scoring graph.

19.4 Lockstep-determinism sim-path markers

Per Contract Section 4 (sim-path determinism), modules marked sim_path = true in their .Build.toml must satisfy banned-API, no-FMA, etc. The XPact plugin registers an additional per-type specifier:

  • XCLASS(SimPathParticipant = true) on a class indicating it actively participates in the lockstep simulation update. XHT emits the marker as metadata; the runtime sim-path orchestrator (XSimPath Engine module) uses it to schedule the class's tick.
  • XFUNCTION(SimPathTick = true) on a function indicating the function is the per-tick entry point for the class. The orchestrator calls these functions in deterministic order each lockstep tick.

Cross-references Contract Section 1.2's SimPathStringIndexOK = true (Rev 11 audit finding #2 specifier). XHT validates that SimPathTick functions don't carry SimPathStringIndexOK — tick functions on the sim path should never index strings on the hot path; the diagnostic catches the contradiction.

19.5 FastArraySerializer-derived detection (post-MVP, REVISED Rev 3 rationale)

UE's replication runtime supports FFastArraySerializer-derived structs as a delta-compressed alternative to TArray replication. UHT specifically recognises the inheritance chain and emits inner-element-type metadata into the FProperty descriptor so the runtime can drive per-item delta encoding without runtime type inspection.

XHT Phase 1 posture (X-M15 rationale strengthening). FastArraySerializer-derived structs (the FFastArraySerializer pattern) get per-element delta encoding in Unreal's replication runtime. Phase 1 XHT emits the property descriptors WITHOUT the inner-element-type metadata UE's FFastArraySerializer runtime relies on — replicated TArray<FFastArraySerializer-derived> properties WORK but transmit full-array snapshots instead of element-level deltas. The replication-efficiency cost is real but acceptable for Phase 1 because:

  • (a) Bounded cardinality. XPact's training scenarios are bounded-cardinality — on the order of hundreds of replicated entities at peak (a multi-station industrial-training scenario with 100 valves + 50 pumps + 20 vessels). The full-snapshot transmission cost at this scale is well within network budgets for the LAN-deployed instructor / trainee station topology XPact targets.
  • (b) Lockstep-determinism + input replication is the primary networking architecture. Per master plan Section 13, XPact's networking is built on lockstep-determinism + input replication: each station receives the same input stream and runs the same deterministic simulation tick, so most state does not need to be replicated through the property-rep path. Property replication is the FALLBACK / latecomer path (for catch-up on join, for non-deterministic state, for spectator views) — not the primary state channel. Delta-compression efficiency on the fallback path is a polish concern, not a correctness one.
  • (c) Phase 1 emit shape compatibility. The Phase 1 property descriptor is the standard TArray form; consumers see a normal replicated array. Phase 2 can add the inner-type metadata without invalidating Phase 1's on-disk descriptor format — the addition is additive (a new FProperty descriptor extension field).

Phase 2 deferral with milestone gate. Phase 2 adds the FFastArraySerializer recognition + inner-type emit, gated on the year-3 lockstep-validation milestone (master plan Section 10) determining whether property-rep is the production path. If lockstep-determinism + input-replication proves insufficient for XPact's deployment topology and property-rep becomes load-bearing on the hot path, Phase 2 lands the delta-encoding metadata. The Phase 2 work splits into: (a) a struct-super-chain walk in StepResolveFinal to identify FastArraySerializer-derived structs; (b) an FProperty descriptor extension carrying the inner-element type pointer; (c) a validator pass asserting the struct contains exactly one TArray<T> field marked with the FastArraySerializer-item attribute, mirroring UE's convention. Adding the FProperty descriptor extension is a Stage B change (frozen at Step 4 alongside the rest of the FProperty surface).

19.6 #include last-line rule

Per UHT precedent and Contract Section 1.5 implication, the source header must #include "<HeaderName>.gen.h" as the last #include in the file. The order matters because the .gen.h's macro #defines use the CURRENT_FILE_ID macro that the file's last #include sets.

XHT's validator XHT020 IncludeOrderValidator checks this at parse time. Missing or misplaced #include: error with the column-precise location and a hint. Linux case-sensitivity hint: when the #include's filename case doesn't match the on-disk file's case (the cross-platform Linux footgun where #include "xvalve.gen.h" works on Windows but fails on Linux), the error message appends "On Linux, file names are case-sensitive; verify the #include matches the on-disk casing." This matches XBT.html's diagnostic approach for the same class of error and the Round-3 audit fix to the Contract.

20. Plugin Model — .xplugin and .Build.toml Descriptor Recognition

XHT consumes the manifest XBT emits, which itself encodes the plugin set (Contract Section 9.4 + XBT.html Section 17). XHT does not directly read .xplugin or .Build.toml — XBT pre-processes those into the manifest. The XHT-side responsibility is to honour the manifest's per-module entries.

20.1 Three-tier plugin recognition

Per plan Section 2 Folder structure row (Rev 6), XPact's three-tier reusability model: Engine plugins under /Engine/Plugins/, Studio plugins under /Studio/Plugins/, Project plugins under /Projects/<P>/Plugins/. XBT's manifest records each module's Tier as Engine / Studio / Project; XHT consumes the tier at StepResolveValidate (Section 5.2) to enforce cross-tier type-reference rules.

The cross-tier dependency edge matrix (Contract Section 9.3) is enforced by XBT at module-resolution time (XBT.html Section 13). XHT-side enforcement covers the type-reference subset: a C++ class in an Engine module cannot reference a Studio-only type at the reflection layer (the reflection record would need to point at the Studio class's singleton-getter, which the Engine module's link line doesn't include for link-time deps; the link would fail). XHT catches the case at StepResolveValidate by walking every property reference and asserting the referent's module is in the consumer module's link-dependency closure.

20.2 .xplugin recognition

XHT does not parse .xplugin files. XBT does, and the result — the set of enabled plugins and their tier — is encoded in the manifest's per-module records. XHT inspects the manifest's Tier field per module.

If a Studio plugin is disabled in the project's .xproject, XBT filters the plugin's modules out of the manifest. XHT only sees the enabled set.

20.3 Plugin-emitted XHT plugins

Per Section 18.2, plugin assemblies that extend XHT itself (registering custom specifiers / validators / property types / exporters) are discovered by filesystem scan in Phase 1 — the manifest does not carry a dedicated XhtPlugins entry. The plugin-source-tier is identified by the assembly's directory location: an Engine plugin contributes an XHT plugin DLL under /Engine/Plugins/<PluginName>/Binaries/<Platform>/<XhtPluginName>.XhtPlugin.dll; Studio plugins likewise contribute under /Studio/Plugins/<PluginName>/Binaries/<Platform>/; Project plugins under /Projects/<P>/Plugins/<PluginName>/Binaries/<Platform>/.

XHT loads plugin DLLs in tier order: Engine first, Studio second, Project third. The order matters for the conflict-detection rule (Section 18.1) — if a Studio plugin tries to override an Engine-registered specifier without AllowOverride = true, the conflict surfaces clearly with the Studio side as the redefinition. Mirrors UHT's plugin discipline tier-extended.

21. Test Strategy

Per plan Section 6 (every system has a sibling tests module) and Section 9 (four-layer verification approach): XHT's tests live in /Engine/Source/Programs/XHT/XHT.Tests/ using xUnit. 21.1 Unit tests

  • Tokenizer: synthetic C++ source inputs → assert correct token stream (with column-precise spans). Edge cases: trailing whitespace, multi-line strings, line continuation, comment-then-token, hex/decimal/float literal forms.
  • Roslyn integration: synthetic C# source → assert the walker produces the expected AST nodes with correct attribute extraction and correct token-range projection.
  • Specifier table: registration / lookup / inheritance (a Field-registered specifier is visible at Class); conflict detection on duplicate registration (assert XHT140 diagnostic).
  • Symbol table: case-sensitive vs case-insensitive lookups; cross-language resolution (a C# type found from a C++ reference and vice versa); forward-declaration lazy resolution.
  • Resolver phases: synthetic AST with known references → assert BindSuperAndBases resolves SuperIdentifier strings to Super pointers; assert ResolveBases resolves cross-type type-pointers (including ClassWithin outer-type per Section 7.4); assert Properties resolves inner-property types.
  • Validators: synthetic ASTs exhibiting each diagnostic in the catalog → assert the validator fires with the right code and location.
  • FileId encoder: known (PluginName, LogicalPath, Line, Suffix) tuples → assert the encoded bytes match the Contract Section 1.4 example expansion verbatim. Includes round-trip via the decoder.
  • Mangling: known type / module pairs → assert the singleton-getter symbol matches Section 10.2's format.
  • Atomic write-if-changed: emit twice with identical content → assert the on-disk file's mtime is unchanged after the second emit. Emit twice with different content → assert the file's content updated atomically (no torn state).
  • Manifest reader: well-formed JSON + FBS round-trip; malformed JSON (depth > 64, size > 100 MB, array > 64K) → assert exit 50; FBS verifier rejection of a tampered sidecar → assert fallback to JSON, then exit 50 if JSON also fails.

21.3 Golden-output tests

Each integration fixture has a committed reference snapshot under XHT.Tests/Fixtures/<Fixture>/Reference/ covering the .gen.h / .gen.cpp / .init.gen.cpp / .gen.manifest outputs. CI runs XHT.exe emit-module -VerifyRef=<reference> on every PR. Drift in any output's bytes fails the test.

Updating a reference snapshot is a deliberate developer act: run XHT.exe emit-module -WriteRef=<reference> and commit the diff. CI gates the update via PR review — reviewers see the unified diff in the PR and decide whether the change is intentional. This is the Section 25.2 item 8 discipline: verify mode is the default in CI, not opt-in.

21.4 Fuzz tests

The fuzz harness in XHT.Tests/Fuzz/ generates random C++ and C# source with weighted patterns: well-formed marker placements, randomly malformed marker placements, randomly placed #includes, randomly malformed specifier strings, randomly large source files (up to 1 MB). The harness asserts that:

  • XHT does not crash on any input (no uncaught exception escapes to the runtime; the XhtIceException safety net catches all internal bugs).
  • XHT exits with a recognised exit code (0, 50, 62; never 1 / unknown).
  • XHT's emit, when it succeeds, produces deterministic output (running the same fuzz input twice produces byte-identical emit; checked over 1000 random inputs per CI run).

The fuzz tests are a Phase 1 deliverable. The corpus grows over time as bug-triggering inputs are added to the regression suite.

21.5 Reproducibility tests

Per Section 14.5: XHT.exe emit-module -VerifyRef=<snapshot> on every PR. CI also runs a double-emit comparison nightly: emit the entire engine's reflection set twice in separate processes, assert byte-identicalness of every output. The test catches per-run nondeterminism that the per-PR golden-output check might miss (e.g., if the snapshot was generated with the same non-determinism).

21.6 Performance benchmarks

Per Section 22, XHT carries a performance budget. The performance benchmarks live in XHT.Tests/Benchmarks/ and assert:

  • 200-module full pass under 30s on the reference hardware (Section 22.1).
  • Per-module incremental rebuild under 5s on the reference hardware (Section 22.2).
  • Cold-start under 500 ms (the Roslyn-load cost is the dominant component; Section 2 module description).

Benchmarks run nightly on a dedicated CI agent; regressions are reported as CI warnings, not failures (per the engineering posture: perf regressions trigger investigation but don't block PRs).

22. Performance Characteristics

XHT's performance budget is locked at the brief: < 30s for a 200-module engine full pass; < 5s per-module incremental. These numbers are achievable based on UHT's reference numbers and the architectural choices in this spec.

22.1 200-module full pass < 30s

Reference hardware: Win64 with 16-core CPU + NVMe SSD. UHT's published numbers (UE 5.4 internal benchmarks; not cited verbatim but observed in master-plan-tier UE source tree builds) put a 200-module engine pass at ~12–18 seconds. XHT's projected number is 18–25 seconds because:

  • Dual-language input adds the Roslyn parse cost. Per-module Roslyn parse is ~30–100 ms for typical C# files; 200 modules with ~10 .cs files each adds 60–200 seconds in serial. Parallelism shaves this to 4–15 seconds on 16 cores; under Parallel.ForEach the Roslyn parse interleaves with the C++ tokenizer parse.
  • The C++ tokenizer cost is roughly equivalent to UHT's (same algorithm, similar implementation language).
  • The resolver runs per-header-parallel for 6 of 7 active phases — Pairings, InvalidCheck, BindSuperAndBases, RecursiveStructCheck, ResolveBases, Properties — with Final serial (Section 5.1); the Final phase is scoped to genuinely-whole-program checks (Section 11.2) so its duration is < 1 second even on 200 modules.
  • The emit phase is per-header parallel (Section 11.3); aggregation is the per-module init.gen.cpp + manifest emit, which is fast (string concatenation + sorted iteration).

The 30s budget includes the Roslyn load cost (~250–400 ms per session) amortised over the full pass. CI dashboards report the budget; regressions trigger investigation.

Final-phase complexity bound (NEW Rev 3, X-M13). The Final phase is O(P) where P is total property count across all modules. On a 200-module engine with ~50k properties, measured Final-phase wall time is < 1 second on the reference hardware (Win64, 16-core CPU, NVMe SSD). The Final phase is single-threaded by design (cross-language symbol-table consistency walk requires whole-program visibility; concurrent walks risk read-during-write races on the symbol table even after StepPopulateTypeTable finalises — the table is conceptually frozen but the validators that run in Final append diagnostic-side metadata onto the AST nodes they visit, which must be serialised); parallelization would require a partitioned symbol table which is deferred to post-MVP. The complexity bound + the measured wall time together mean Final is not a contributor to the 30s budget even at the largest realistic engine scale.

22.2 Per-module incremental < 5s

Reference workflow: a developer edits one .cs file in one module, runs xbt build. XBT detects the change, runs XHT only for the affected module (per Section 11.3 module-level parallelism, the incremental case is a single-module run). The 5s budget covers:

  • Cold-start (Roslyn load): ~250–400 ms.
  • Manifest read: ~50–100 ms (FBS sidecar mmap + zero-copy reads).
  • Per-module parse (single module): ~500–1500 ms depending on module size (typical ~10 .h + ~10 .cs).
  • Per-module resolve: ~300–800 ms.
  • Per-module emit: ~500–1000 ms (atomic write, byte-compare, write-if-changed for each output).
  • Manifest write: ~50–100 ms.

Total typical: ~2–4 seconds. The 5s budget is comfortable. The AST cache (Section 16) could shave parse time when enabled; Phase 1's incremental case typically falls within budget without the cache.

22.3 Performance bottlenecks and mitigations

The known bottlenecks:

  1. Roslyn cold-load. The first call to CSharpSyntaxTree.ParseText in a process incurs the assembly-load cost (~250–400 ms). Mitigation: XHT loads Roslyn eagerly at Main entry (not lazily on first .cs file) so the cost is paid in parallel with the manifest read. Subsequent parses are amortised. Rev 3 verification commitment (X-M12): the ~250–400 ms estimate is based on internal sampling on Win64 with a 16-core CPU + NVMe SSD reference hardware. The actual cold-start figure will be measured at System 2 verification (per Section 26.4 final validation gates); the 30s / 200-module budget is adjusted if actual cold-start exceeds 800 ms. Worst-case adjustment paths: (a) increase the full-pass budget to 60s while keeping the per-module incremental at < 5s; or (b) accept a per-target Roslyn workspace cache (hosted in a dedicated AssemblyLoadContext — .NET 8 has no AppDomain isolation) that amortises cold-load across multiple parse-module / emit-module invocations in the same build (the workspace would live for the build's duration, paid once per build instead of once per module).
  2. Final resolve phase. Single-threaded by Section 5.1. Mitigation: scope Final tightly. The validator pass (Section 6) runs after Final and is parallel.
  3. Symbol-table writes. The StepPopulateTypeTable step is serial because the symbol table is written, not read. Mitigation: the step is fast (linear in the type count, no synchronisation overhead since no concurrency).
  4. Specifier-parser allocations. One specifier parser is reused per thread per header (the thread-local optimization, Section 7.2). UHT identifies this as a significant perf win; XHT adopts it directly.

22.4 Memory budget

Typical full-engine pass: ~500 MB peak resident. Components:

  • Roslyn (loaded): ~100 MB.
  • Parsed AST: ~50–100 MB depending on engine size.
  • Symbol table: ~10–20 MB (sorted-set of every type name + outer chain).
  • Emit-time string builders: ~50–100 MB transient.
  • Manifest: < 100 MB (Contract Section 10.2 hard ceiling).

The memory ceiling is comfortable on developer machines. CI agents with 16 GB RAM run XHT in parallel with XIL2CPP, XBT, and C++ compile jobs without contention.

23. Failure Modes

Categorised failure modes XHT exhibits, the diagnostic surface for each, and how the build recovers.

23.1 Source-level failures

  • Missing XGENERATED_BODY() — diagnostic XHT040; exit 62; the developer adds the macro.
  • Missing #include "<Header>.gen.h" — diagnostic XHT020 with Linux case-sensitivity hint; exit 62; the developer adds the include.
  • Conflicting specifiers — diagnostic XHT051 et al.; exit 62; the developer removes one of the conflicting specifiers.
  • Reflection marker on unreflectable construct — diagnostic XHT042 — XCLASS on a template class is not supported; exit 62; the developer factors the template out or removes the marker.
  • Cross-language type-reference mismatch — diagnostic XHT120 — reflected C++ property references non-reflected C# type; exit 62; the developer adds the marker to the referenced type.
  • XPact-specific marker malformed — diagnostic XHT160 Modbus_FormatValidator et al.; exit 62; the developer corrects the marker string.

23.2 Configuration-level failures

  • Manifest missing — diagnostic XHT001 — Manifest not found at <path>; exit 50; XBT regenerates the manifest.
  • Manifest schema mismatch — diagnostic XHT002 — ContractVersion mismatch <manifest> vs <xht>; exit 50; the developer rebuilds XBT and XHT against a consistent contract version.
  • Manifest verifier rejection — diagnostic XHT003 — Manifest exceeds verifier limits; exit 50; XBT investigates the offending manifest.
  • Module not in manifest — diagnostic XHT004 — Module <name> specified via -Module= is not in the manifest; exit 50 (Rev 3 remap per X-CR1; was exit 30 in Rev 2 — that's XBT's RulesCompileFailed); the caller corrects the module name or the manifest.
  • Plugin assembly load failure — diagnostic XHT141 — XhtPlugin assembly failed to load: <reason>; exit 62; the developer inspects the plugin DLL.

23.3 Infrastructure-level failures

  • Disk full during atomic write (REVISED Rev 3, X-M14) — classified as a recoverable I/O failure, NOT as an internal compiler error. The atomic-write call sites in XHT.Core catch IOException whose HResult matches the disk-full error codes (Windows ERROR_DISK_FULL = 0x70; POSIX ENOSPC) and emit diagnostic XHT091 — Disk full during atomic write to <path>; ensure adequate disk space. Exit 62. Not classified as ICE — no bug-report URL is printed (the disk-full condition is a user-actionable environment failure, not an XHT bug). The XHT900-series codes remain reserved for genuine XhtIceException paths (Section 12.5). The developer frees disk space and re-runs.
  • Permission denied on temp-file write — uncaught UnauthorizedAccessException; same path; exit 62; the developer fixes filesystem permissions.
  • Antivirus interference on temp-file rename — on Windows, transient IOException. Phase 1 XHT does not implement an AV-retry helper symmetrically to XBT's FileSystemOps.RetryOnTransientIOException (XBT.html Section 19.4); the cost is small but the Phase 1 surface is bounded. Polish path (Rev 2): XHT's atomic-write call sites (Section 8.5) are the obvious entry points for importing XBT's FileSystemOps.RetryOnTransientIOException helper — the retry schedule ([100ms, 200ms, 1000ms, 5000ms]) is already validated in XBT and the helper is suitable for cross-process reuse. Phase 2 should hoist the helper into XHT.Core (its current XBT-private location forbids direct import; the polish work is a small refactor). Until then, the diagnostic includes the suggestion "if this happens repeatedly, check antivirus exclusions on the Intermediate directory."
  • MAX_PATH violation on Windows — XBT's ActionGraph.CheckPathLengths (XBT.html Section 19.5) catches this before XHT runs. If XHT is invoked standalone (CI gate, IDE) without XBT's pre-flight check, XHT may hit MAX_PATH at write time and report XHT090 — Output path too long on Windows; exit 62.
  • Cancellation — SIGINT / Ctrl-C; partial outputs cleaned up per Section 11.5; exit 130.

23.4 Internal compiler errors

Section 12.5 covers the Ice (Internal Compiler Error) tier. Any uncaught exception inside XHT's own code is caught by the session and emitted as XHT900; the bug report URL is printed; exit 62 (the ICE doesn't get a separate exit code since the contract surface only exposes 60–63 for the XHT/XIL2CPP band).

24. Forward Compatibility

The reflection metadata XHT emits is consumed at runtime by XCoreXObject and across DLL boundaries by every dependent module. Forward compatibility — the property that an older consumer module can still link against newer XHT-emitted metadata — is essential for incremental engine updates without full-rebuild requirements.

24.1 Schema versioning

The .gen.manifest carries a Schema version: 1 header line (Section 9.2). New manifest sections append at the bottom. A schema-version bump requires a Contract revision; the per-section append-only discipline (matches Contract Section 10.2's FBS schema discipline) ensures Phase 2 additions don't break Phase 1 readers.

The emitted C++ side (the .gen.h + .gen.cpp) carries its own schema version via the static-assert: static_assert(XPACT_WITH_CONSTINIT_XOBJECT, ...) per Section 8.2. The ConstInit mode lock is part of the schema version — a Params-style consumer cannot consume ConstInit-emitted code; the static-assert catches the mismatch at C++ compile.

24.2 FCustomVersion-style migration

UE supports FCustomVersion for serialised data migration: a serialised stream embeds a version GUID, and the runtime applies a migration sequence when reading old data. XHT's reflection metadata is not serialised data (it's runtime-constructed from the per-DLL Z_Construct_* singletons), so the FCustomVersion mechanism doesn't apply directly. STAGE B: the FProperty descriptor surface, when frozen at Step 4, will gain a per-property schema-version field to support forward compatibility of replication-metadata changes; Phase 1 emits a constant 1 placeholder.

24.3 Marker vocabulary stability

The marker vocabulary (Contract Section 1.1) is part of the contract surface (Contract Section 10.2 step 3 of the auto-derived structure hash). Adding a new marker (e.g., a hypothetical Phase 2 XSCENARIO top-level marker) requires a Contract revision; removing or repurposing a marker is forbidden. The stability commitment matches Contract Section 13.2's commitment for exit codes.

The XPact-specific markers (Section 19) are layered on top via the plugin model (Section 18); they don't appear in the core marker vocabulary at Contract Section 1.1. Modbus, multi-user, scenario, sim-path markers can evolve via the plugin's own versioning without requiring a Contract revision.

24.4 Specifier vocabulary stability

Specifier vocabulary at Contract Section 1.2 is similarly stable. Adding a new specifier (e.g., a hypothetical Phase 2 HardObjectReference = true) requires a Contract revision; removing or repurposing is forbidden. Plugin-registered specifiers (Section 18) don't enter the core vocabulary; they live in the plugin's own specifier namespace.

24.5 ABI envelope stability

The manifest's Target object carries the ABI envelope (Architecture, GCRootABI, ExceptionABI, ManglingScheme) per Contract Section 10.2 + XBT.html Section 8.2. XHT reads the envelope at emit time and emits the matching ABI version of the descriptors. Phase 1: only the "Span-based v1" / "Tier1-Shim/Tier2-Direct" / "Itanium-LengthPrefixed-v1" tuple is emitted. Phase 2: the envelope is the negotiation point if XCore or XIL2CPP ships a new ABI; XHT's emit branches on the envelope tuple.

24.6 Plugin assembly forward compatibility

Plugin assemblies (Section 18.2) are .NET 8 assemblies referencing XHT.Tables. The plugin's compiled-against XHT version is recorded in the plugin's manifest. A plugin compiled against XHT v1 should continue to load against XHT v1.x for any minor revision; XHT v2 may require plugin recompilation. Mirrors the standard .NET assembly compatibility model.

  • Stable-token body-macro names (Section 10.5). Current line-based scheme inherits UHT footgun #10.
