1. Purpose, Scope, and Locked Decisions

1.1 What XCoreXObject is

Umbrella-spec posture (Rev 2; addresses FIX-A-MIN-46 / O11 arbitration). Master Plan Rev 15 §11 Step 5 wording “will split into multiple docs” was design-time guidance from when the system scope had not yet crystallized. Rev 2 commits to a unified umbrella spec with a structural §-substructure that maps directly to implementation sub-phases (§15 phase ladder). At implementation phase, Phase 5.b (allocator), Phase 5.f (write barriers), and Phase 5.g (collector mark phase) can split into independent design docs if the work units crystallize that way; until then the design decisions are tight cross-cutting (e.g., allocator slab layout informs collector mark-bit lookup; card-size informs allocator fragmentation budget; schema-vector emit informs both XHT emit and the collector inner loop). Splitting at the design phase would force cross-document references for every cross-cutting decision and increase the inconsistency risk. The Master Plan Rev 16 amendment commits the umbrella-spec posture explicitly. XBT, XCore-4a, and XCore-4b all shipped as single docs of ~25-30k words; this spec is consistent with that posture.

XCoreXObject is the System 5 deliverable per Master Plan Rev 15 §4 Step 5: the C++ runtime that ships XObject (the gameplay-object base class), the GC-managed heap (the object pool every XObject lives in), the non-moving precise mostly-concurrent mark-and-sweep collector (the algorithm that reclaims unreachable XObjects), the card-table write-barrier intrinsic implementation (the real implementation behind XCore-4a's weak-symbol XGC_WriteBarrier stub), the GC root protocol (the way stacks, statics, native handles, and container-resident XObject pointers are enumerated at mark time), the object-handle family (XPtr, XWeakPtr, XSoftPtr, XObjectKey, XStrongPtr), the Class Default Object (CDO) lifecycle, the FXObjectInitializer + CreateDefaultSubobject design (UE-MISS-2 fix; §8.4), the schema-vector GC walker (UE-MISS-1 fix; §7.4) and the hot-reload survival protocol that lets every previously-allocated XObject keep running after a downstream module's DLL is swapped.

XCoreXObject is the system that turns XCore-4b's reflection types from descriptors-for-things-that-don't-exist into descriptors-for-real-runtime-objects. XCore-4b's FClass exists but has no instances; XCore-4b's FProperty::ObjectRefProperties dense TArray exists but is never walked; XCore-4b's FClass::ClassDefaultObject atomic slot exists but is always nullptr. XCoreXObject populates all three.

The deliverables of XCoreXObject are:

  • The XObject base type — a 56-byte header carrying FClass*, Outer*, FName, EObjectFlags, InternalIndex, SerialNumber, plus a 16-byte cluster reservation; the universal parent of every reflected gameplay type in C++ and (via XIL2CPP transpilation) C#. (Rev 2 size justification: not smaller than UE's UObjectBase; UE's UObjectBase is 40 bytes + FUObjectItem ~24 bytes (separate allocation) = ~64 bytes effective. XPact's 56 bytes unifies header + cluster + GC reservation into one indirection at GC walk — see §2.2 prose.) Per FIX-A-CRIT-7.
  • The XObject heap (FXObjectAllocator / FXObjectArray) — a size-class-segregated slab allocator owning every XObject's storage, layered on XCore-4a's FMallocBinnedX (rationale §3.1), with type-segregated free-lists to bound fragmentation (Foundation Prototype criterion (h) <15% wasted heap over 4 hours of continuous load on Quest 3).
  • The non-moving precise mostly-concurrent mark-and-sweep collector — locked algorithm per Master Plan §2a Memory/GC row, hitting Foundation Prototype criterion (a) <5 ms typical pause on Quest 3 and criterion (b) <50 ms full-heap-scan fallback on Quest 3.
  • The schema-vector GC walker (Rev 2 addition; UE-MISS-1 fix) — FStruct's RefSchema pointer references a packed FXObjectRefSchema opcode vector emitted by XHT at compile time, replacing the slower FProperty pointer-chase. The dense ObjectRefProperties TArray (XCore-4b FIX-13) remains as the slow-path inspection surface; the schema vector is the fast-path GC walk. See §7.4.
  • The card-table write barrier — the real implementation of XCore-4a's weak-symbol XGC_WriteBarrier, marking 512-byte cards dirty so the next minor collection can skip clean cards entirely. Card granularity, byte vs bit table layout, and the snoop-vs-pre-store ordering are all specified in §5.
  • The GC root protocol — the XGCRootSpan ABI (from XCore-4a §5.4) is registered by every GC-aware container; native code uses XGCRoot::AddRoot; precise stack scanning uses XIL2CPP-emitted stack maps; the conservative-root fallback for non-statically-typed C# containers (List<object>) emits a build-time sim-path warning per Master Plan §2a.
  • The object-handle family — XPtr<T> (strong, GC root via the container the XPtr sits in), XWeakPtr<T> ({InternalIndex; SerialNumber} 8-byte handle resolved at deref time), XSoftPtr<T> (FSoftObjectPath shape; resolves on demand), XObjectKey ({InternalIndex; SerialNumber} stable across hot-reload class replacement), XStrongPtr<T> (per FIX-A-MIN-38; non-container strong hold equivalent to UE TStrongObjectPtr, uses FXObjectArray refcount slot).
  • The FXObjectInitializer + default-subobject (DSO) construct (Rev 2; UE-MISS-2 fix) — destructor-driven finalization that fires PostInitProperties after construction; supports CreateDefaultSubobject<T>(Name) from C++ constructor bodies; sub-objects are templated from the CDO. See §8.4.
  • The Class Default Object lifecycle — one CDO per FClass; constructed lazily on first NewObject<T> call OR at module-init time depending on per-class registration policy (§8); the CDO is the property-default-value source the editor's XPropertyEditor and the network reconciliation engine both consume. CDOs are immutable post-construction (per FIX-A-MED-30; XPact ships UE's experimental UE_WITH_IMMUTABLE_CDO as default).
  • The hot-reload survival protocol — how an XObject created against the pre-patch FClass keeps running after a downstream module's DLL is swapped: XObjectKey survives the swap, FClass* is rebound by XLiveCoding's cascade, instance vtables (where any exist in user-class C++ derivation) are versioned per XCore-4b's hot-reload commitment. The XLiveCoding quiesce parks an explicit thread set (game, render, RHI, audio, loading, worker-pool, GC marker, PSO compile, asset workers, audio mixer) per FIX-A-HIGH-14.
  • The NewObject + lifecycle surface — NewObject<T>(Outer, Name, Flags) (infallible; returns T*) and TryNewObject<T>(Outer, Name, Flags) (fallible; returns Result<T*, FNewObjectError>) per FIX-A-MED-29; XObject::PostInitProperties() (function-pointer slot, NOT virtual), XObject::BeginDestroy() / IsReadyForFinishDestroy() / FinishDestroy(), deferred destruction queue, NewObject-during-GC defensive abort, NewObject sim-path runtime invariant (FIX-A-CRIT-1).
  • The XInsights runtime API bridge (Rev 2; FIX-A-CRIT-6) — weak-symbol XInsights::Emit(Category, Event, Payload) that XCoreXObject calls for GC / Allocator / HotReload telemetry; becomes a no-op until XInsights links its strong implementation. See §10.5.
  • The cross-system integration with XReflectionRuntime, XCore-4a's FMemTag::XObject slot, FLeakTracker (XObject leaks attribute to the same tracker), the Phase-1g weak-symbol GC stubs (XCoreXObject is the strong-symbol replacement), and XHT-emitted .gen.cpp registration paths (XHT emits the Z_Construct_FClass_* functions whose runtime side is implemented here).
  • The C++ macro surface — XCLASS(), XPROPERTY(), XFUNCTION(), XINTERFACE() — XHT-parsed; XHT emits the .gen.h / .gen.cpp per module per Contract Rev 13.8 (Rev 13.9 micro-bump applied); XCoreXObject is the runtime side those generated files call into.
  • The Toolchain Contract delta — XCoreXObject triggers a Contract Rev 13.9 micro-bump (per FIX-A-CRIT-3 / O1 arbitration) to add the FClass LifecycleTable pointer + the FStruct RefSchema pointer (+8 bytes each; Rev 3 corrected per FIX-C-R2-1: FClass sizeof 224 → 240 [Rev 2 declared 232 with inconsistent arithmetic], FStruct sizeof 112 → 120). XCoreXObject adds new XPACT_*_LAYOUT_TAG string-literal pins per §11: XPACT_XOBJECT_LAYOUT_TAG, XPACT_XGC_CARDTABLE_LAYOUT_TAG, XPACT_XOBJECTARRAY_ENTRY_LAYOUT_TAG, XPACT_XOBJECTKEY_LAYOUT_TAG, XPACT_XWEAKPTR_LAYOUT_TAG, XPACT_XPTR_LAYOUT_TAG, XPACT_XOBJECT_LIFECYCLE_TABLE_TAG, XPACT_FSTRUCT_LAYOUT_TAG (v5; Rev 3 added per FIX-C-R2-1 / FIX-N-R2-1), XPACT_FCLASS_LAYOUT_TAG (v6; updated for both appended pointers), XPACT_FXOBJECTREFSCHEMA_LAYOUT_TAG (Rev 2 addition for schema-vector). 1.2 What XCoreXObject is NOT

XCoreXObject is bounded narrowly to the substrate. It does NOT ship:

  • XActor, XComponent, XWorld, XGameInstance, XGameMode. These are L7 gameplay framework systems that derive from XObject (via XCLASS). XCoreXObject ships the base; the gameplay-framework types are downstream.
  • UFunction-equivalent (XFunction reflected method dispatch). XCore-4b's FClass::NetFields + FInterface::InterfaceFunctions reserve the slot; the runtime VM that dispatches XFunction calls lives in XBlueprintVM at L21. XCoreXObject calls into the slot via a function pointer when invoked (e.g., for PostInitProperties hooks), but does not own the dispatch infrastructure.
  • XPackage / UPackage-equivalent. The package abstraction (groups of XObjects that load/save as a unit) lives in XSerialization (System 9) and XAssetRegistry (System 16). XCoreXObject's XObject::Outer slot supports the Outer chain that packages will use, but the package type itself is downstream.
  • Asset serialization (FArchive<XObject> round-trip). XSerialization (System 9) implements the binary format; XCoreXObject's XObject participates via the per-FClass SerializeStructFn slot on FStruct (XCore-4b §7.1), but the FArchive itself is XSerialization's deliverable.
  • Replication metadata host. Per Master Plan Rev 15 §3 L1 explicit note: “XCoreXObject (XObject + reflection runtime + GC; NOT a replication-metadata host — that responsibility moved to XNetworking's FReplicationStateDescriptorRegistry at L13 per Rev 13 FIX-A).” XNetworking owns FReplicationStateDescriptorRegistry; XCoreXObject's role is solely to ensure that the GC walk visits XObject reference properties (via FStruct::ObjectRefProperties dense array per XCore-4b FIX-13) so reachability is correct.
  • The cluster pattern (UE's UObjectCluster). UE optimizes GC by clustering related objects into a single mark unit; XCoreXObject Rev 1 ships without clustering (clustering is a per-FClass declaration that, when set, makes the FClass's instances share a mark bit with their Outer chain). Clustering is a forward-compatibility hook: the EObjectFlags::ClusterRoot bit is reserved, but the cluster traversal path is a TODO(Phase 2) item with a clean opt-out path. Rationale: clusters add significant complexity (cluster-mutation tracking, cluster-spanning weak refs, cluster-replacement during hot-reload), and the Foundation Prototype's <5 ms typical-pause / <50 ms fallback targets are achievable without clustering for the MVP object population (XPact targets ~50k XObjects in a typical training session vs UE games' 200k-500k).
  • Generational copying / compacting. Master Plan §2a is explicit: non-moving. Stable pointers across object lifetime is a foundational invariant (the only model compatible with hot-reload's stable-symbol / stable-vtable requirements). The card-table is for scan-reduction, not for promotion.
  • Cross-process / distributed GC. Multi-user lockstep is a per-process concern; each client runs its own collector; lockstep determinism applies to gameplay state, not to GC bookkeeping (the GC is non-sim-path; see §4.6).
  • Conservative scanning of the C++ stack. Master Plan §2a is explicit: precise (no conservative stack scanning). C++ stack frames are not GC-scanned at all; gameplay-tier C++ code that holds a temporary XObject pointer on the stack must either (a) hold it through a container that registers an XGCRootSpan, (b) call XGCRoot::AddRoot explicitly for the duration, or (c) prove via stop-the-world coordination that no GC can run during the stack window (the SimPathSerialExecutor's frame boundary is the only such window). The XIL2CPP-transpiled C# stack IS precise-scanned via XIL2CPP-emitted stack maps; see §5.3.
  • Roslyn source-generator hosting. Per Master Plan §2a C# version row, deferred to post-MVP.

1.4 Dependencies

  • Hard dependencies on XCore-4a:
    • FMallocBinnedX (the XObject heap allocator uses XCore-4a's binned allocator as its backing store for the slab pool, attributing all allocations to FMemTag::XObject; the XObject heap is a layer on top of FMallocBinnedX, not a replacement — rationale §3.1).
    • FMemTag::XObject (already reserved as slot 9 in XCore-4a's enum; this spec activates it). Card table allocates under FMemTag::Reflection, not FMemTag::XObject, per FIX-A-MIN-39 — the card table is reflection-runtime metadata, not gameplay heap.
    • FLeakTracker (XObject leaks report through the same tracker; §10.5).
    • TArray, TMap, TSet (the FXObjectArray, the FClass-to-CDO map, the deferred destruction queue all use XCore-4a containers).
    • FRWLock, FCriticalSection, FAtomicInt32, FAtomicInt64, FAtomicPtr (collector phase coordination).
    • FXxh3 / FBlake3 (XObjectKey hashing, not on hot paths and not callable from sim-path code per FIX-A-CRIT-2).
    • XGCRootSpan ABI (XCore-4a §5.4 + XGCDeclarations.h; this spec is the consumer that implements the four XGC_* functions as strong symbols).
    • EInitPhase ladder. (Rev 2 reconciliation per FIX-A-CRIT-5.) The phase ladder for XCoreXObject is:
      1. Static-init (TU init order; pre-EInitPhase ladder): constinit FClass instances are initialized. They reference FStruct/FProperty in .rodata (XCore-4b output).
      2. EInitPhase::PreStaticInit: XCore-4a's FMemory::__Init() runs. XObject heap is NOT yet ready (XCoreXObject's PostStaticInit gate). FMemory is ready but NewObject is deferred.
      3. EInitPhase::PostStaticInit: XCoreXObject heap + collector come up here (Rev 2 corrected; Rev 1 incorrectly said PreStaticInit). XReflectionRuntime::RegisterClass calls are accepted at this gate. CDO construction (lazy by default per §8.1) defers to first NewObject<T>; eager-CDO classes opt into PostStaticInit-time CDO construction via a deferred linker walk (Rev 3 per FIX-H-R2-6): LinkClass queues EagerCDO classes onto g_PendingEagerCDOs during static-init, then XCoreXObject's PostStaticInit boot drains the queue after the heap is up. The earlier Rev 2 wording "eager-CDO classes opt into PostStaticInit-time CDO construction" understated the ordering discipline; Rev 3 formalizes it. NewObject entry path asserts XPACT_CHECK(EngineInitPhase() >= EInitPhase::PostStaticInit); the deferred queue ensures EagerCDO Z_Construct paths never trip that assert.
    • s_XObjectAllocator hook signature (FIX-A-CRIT-4). XCore-4a Rev 3 shipped with a 2-arg hook signature void* (*)(size_t Size, size_t Align) noexcept. XCoreXObject's FXObjectAllocator::AllocateRaw is 3-arg: void* (size_t Size, size_t Align, const FClass* ClassDescriptor) noexcept — the FClass argument is load-bearing for type-segregated free-list lookup per §3.4. Rev 2 amends the cross-system contract: XCore-4a's hook signature MUST expand to 3 args as an XCore-4a Rev 4 follow-up note (forward-only; no breaking change to XCore-4a Rev 3 callers since the hook is uncalled until XCoreXObject ships). This is filed as an XCore-4a Rev 4 note to land before XCoreXObject implementation begins.
  • Hard dependencies on XCore-4b:
    • FClass (XObject carries const FClass*; FClass.ClassDefaultObject is the CDO slot XCoreXObject populates).
    • FStruct::ObjectRefProperties dense TArray (the slow-path GC inspection reads this contiguously; XCore-4b FIX-13). Rev 2: FStruct gains a FXObjectRefSchema* RefSchema pointer (sibling of ObjectRefProperties; emitted by XHT at compile time) used by the fast-path GC walk — UE-MISS-1 fix §7.4. Both fields exist; they serve different consumers.
    • FProperty::DispatchTable->ContainsObjectReferenceFn (the slot the FClass::Link path probes when populating ObjectRefProperties).
    • FName (XObject.Name).
    • XReflectionRuntime (XCoreXObject calls RegisterClass(...) at FClass-init time to populate the registry; conversely, XCoreXObject calls FindClass when a serialized XObject is loaded from disk — though the actual deserialization is XSerialization's responsibility, the FindClass path is consumed here).
    • FObjectProperty, FWeakObjectProperty, FSoftObjectProperty, FSoftClassProperty (the four XCore-4b property subclasses that hold XObject references; XCoreXObject's handle family is the runtime payload for these property types).
    • FCustomVersion (XObject layout itself is a FCustomVersion'd type; a future XObject header change would bump the custom version).
    • EClassFlags::Intrinsic (Rev 2 addition; FIX-A-HIGH-20). XPact's foundational classes (XObject, XStruct, XClass, XEnum, XInterface) opt out of normal registration; their FClass instances live in .rodata and are bootstrap-registered at XCoreXObject's PostStaticInit before any user class registers. The Intrinsic flag breaks the bootstrap loop (XObject can't be registered until XReflectionRuntime is up; XReflectionRuntime needs XObject to be live).
  • Phase-1g GC stubs (XCore-4a): XCoreXObject's link is the strong-symbol replacement for XCore-4a's weak-symbol XGC_WriteBarrier / XGC_RegisterRootSpan / XGC_UpdateRootSpan / XGC_UnregisterRootSpan stubs. The replacement happens at link time without source changes on the XCore-4a side. Additionally, XCore-4a §4.4 declared an s_XObjectAllocator function-pointer hook (Rev 4 expanded to 3-arg per above); XCoreXObject's PostStaticInit code calls RegisterXObjectAllocator(&FXObjectAllocator::AllocateRaw) to install the strong implementation.
  • XCoreDelegates dependency (FIX-A-MIN-44). XCoreXObject fires the following XCoreDelegates:
    • OnGCBegin(FGCBeginContext) — collection trigger acknowledged.
    • OnGCEnd(FGCEndContext) — cycle complete; statistics published.
    • OnHotReloadStart(FHotReloadContext) — cascade quiesce entered.
    • OnHotReloadComplete(FHotReloadContext) — cascade resumed.

2. XObject Base Type

2.1 Design philosophy

The XObject base type is the universal parent of every reflected gameplay type in the engine. Every XActor, every XComponent, every XScenario, every XAsset is an XObject. Per Master Plan §3 L1 inventory note: “XObject + reflection runtime + GC.” The design must therefore:

  • Be size-correct relative to UE (Rev 2 corrected per FIX-A-CRIT-7) — UE's UObjectBase is 40 bytes (static_assert at UObjectHash.cpp:40); UE's FUObjectItem is ~24 bytes; the two are SEPARATE allocations. XPact's XObject at 56 bytes is LARGER than UObjectBase alone by 16 bytes — but unifies the GC state (mark bit, pending-destroy, root-pinned, cluster reservation, hot-reload state) into the same indirection as the header, vs UE's two indirections (UObjectBase* → FUObjectItem*). For 50k typical XObjects the 16-24 byte/object cost is ~1 MB — well within Quest 3's 4 GB budget. The cache-coherency advantage at GC walk dominates this RAM cost. Per Prime Directive: this is the correct trade-off, not the easy one. See §2.2 prose for the full trade analysis.
  • Avoid virtuals on the GC-relevant surface per Prime Directive + hot-reload commitment. UE's UObjectBase has a virtual destructor and a virtual DeferredRegister; XPact replaces both with function-pointer slots populated by the FClass's FakeVTable pattern (XCore-4b's discipline applied to XObject as well).
  • Be precise-scan-friendly — the FClass* must be at a stable offset so the GC walk can decode reachability without virtual dispatch.
  • Support weak references via a per-object 32-bit SerialNumber that increments on object slot reuse; a weak pointer holds {InternalIndex, SerialNumber} and verifies on deref. Cross-arch determinism invariant (FIX-A-CRIT-2): sim-path code MAY NOT read SerialNumber directly; sim-path SerialNumber access is guarded by XPACT_CHECK_SL.
  • Support hot-reload-survivable identity via XObjectKey ({InternalIndex, SerialNumber}); the same handle remains valid across a class replacement because the InternalIndex slot is preserved. (XObjectKey is UE-faithful per FIX-A-HIGH-10: UE's FObjectKey at ObjectKey.h:18-60 has the same {InternalIndex, SerialNumber} 8-byte shape; the genuine divergence is XPact's stable XClass identity across hot-reload via XLiveCoding's versioned-vtable + stable exported-name ABI, where UE has only WITH_EDITOR-only SetClass at UObjectBase.h:486.)
  • Support the Outer chain — XObject.Outer is the parent in the ownership/scoping hierarchy (Asset Outer is Package; Component Outer is Actor; etc.). Outer is itself an XObject and is GC-traced.
  • Support reflection-driven access — FClass* lookup is O(1) (direct member access); property iteration via FStruct::PropertyLink (XCore-4b); GC-walk iteration via FStruct::RefSchema schema vector (Rev 2; §7.4).
  • Reserve cluster bookkeeping space (Rev 2 per FIX-A-MIN-49 / O5 arbitration) — the cluster pattern (UE's UObjectCluster) is a Phase 2 feature. Rev 2 reserves 16 bytes (matching UE's FCluster shape) inline at offset 40-55 of XObject. The previous 8-byte _reservedRemoteId reservation is DROPPED (no system inventory line was claiming it; the 8 bytes are reabsorbed into the expanded cluster reservation). Net XObject sizeof remains 56 bytes.

2.2 XObject header layout (56 bytes)

// Rev 2: XObject header. sizeof = 56 bytes. Cluster reservation expanded to
// 16 bytes (matches UE FCluster shape per FIX-A-MIN-49 / O5 arbitration);
// _reservedRemoteId dropped (no system inventory claimant; bytes reabsorbed
// into cluster expansion). Net sizeof unchanged.
// All field offsets are part of the Stage B addendum extension
// (XPACT_XOBJECT_LAYOUT_TAG; Contract Rev 13.8 + Rev 13.9 micro-bump for FClass).
// Hot-reload commitment: NO virtual methods on this surface. Subclass behavior is
// dispatched via the FClass's FakeVTable (XCore-4b pattern, extended to XObject lifecycle).
//
// FIELD ORDERING RATIONALE:
//   * ClassPrivate at offset 0 lets GC mark walk decode the FClass* with a single
//     load from the object pointer (no offset arithmetic) -- the hottest GC path.
//   * InternalIndex at offset 8 is the FXObjectArray index; precedes Outer because
//     the GC walk needs the InternalIndex before it needs the Outer for the per-object
//     mark bit (mark bits are stored in the FXObjectArray, not on the XObject itself).
//   * SerialNumber at offset 12 sits in the same cache line as InternalIndex
//     (XWeakPtr deref reads both together). Sim-path access to SerialNumber is
//     guarded by XPACT_CHECK_SL per FIX-A-CRIT-2.
//   * Outer at offset 16 -- GC walk visits the Outer chain after the FStruct property
//     walk; placing it in the second 16 bytes keeps the first 16 bytes hot.
//   * NamePrivate at offset 24 -- 8-byte FName handle. Diagnostic / debug; not on the
//     GC hot path.
//   * ObjectFlags at offset 32 -- 32-bit atomic; lifecycle state (RF_NeedLoad,
//     RF_NeedPostLoad, RF_BeginDestroyed, RF_FinishDestroyed, RF_ClassDefaultObject,
//     RF_MarkedAsGarbage, RF_Public, RF_LoadCompleted, RF_NonPIETransient, ...).
//   * _padObjectFlags at offset 36 -- 4-byte pad.
//   * Cluster reservation at offset 40-55 -- 16 bytes for the cluster pattern
//     (Phase 2; mirrors UE FCluster shape per FIX-A-MIN-49 / O5). Holds (when
//     activated): cluster-root index (8 bytes) + cluster-flags + remembered-set
//     state (8 bytes). Pre-Phase-2 value is zeros; the bytes are part of the
//     56-byte ABI lock.

class XObject {
public:
    // === GC-hot identity (first cache line) ===
    const FClass*           ClassPrivate;        //  0  +8   FClass descriptor; GC walk's first load
    int32_t                 InternalIndex;       //  8  +4   FXObjectArray slot index (-1 = uninitialized)
    uint32_t                SerialNumber;        // 12  +4   bumps on slot reuse; XWeakPtr deref checks this
                                                 //          (sim-path read forbidden per FIX-A-CRIT-2)

    // === Identity continuation (second half of first line) ===
    XObject*                Outer;               // 16  +8   parent in ownership chain; GC-traced
    FName                   NamePrivate;         // 24  +8   debug/diagnostic name (FName 8-byte handle)

    // === Lifecycle state (second cache line, first 16 bytes) ===
    std::atomic<uint32_t>  ObjectFlags;         // 32  +4   EObjectFlags (RF_*) atomic
    // Rev 3 (FIX-M-R2-3): per-object reachability flag (3 rotating reachability bits +
    // 29 reserved bits). Consumes the former _padObjectFlags slot. Moves the mark-bit
    // lookup from FXObjectArrayEntry.StateBits (one indirection through entry table)
    // to inline-on-XObject (zero indirection in the GC mark inner loop). The 32-bit
    // word holds bits 0..2 for rotating-cycle reachability (one bit set per cycle;
    // the others clear naturally as GC advances three cycles), bits 3..7 reserved
    // for GC-internal state (kPendingDestroy mirror, kRootPinned mirror), bits 8..31
    // reserved for future GC scheme extensions.
    std::atomic<uint32_t>  ReachabilityFlag;    // 36  +4   3 rotating reachability bits + 29 reserved

    // === Cluster reservation (16 bytes; UE FCluster shape, Phase 2) ===
    uint64_t                _reservedCluster0;   // 40  +8   cluster-root index (Phase 2: bit 63 = is-root, bits 0..30 = idx)
    uint64_t                _reservedCluster1;   // 48  +8   cluster-flags + remembered-set state (Phase 2)

    // No virtual methods. Subclass lifecycle (PostInitProperties / BeginDestroy /
    // FinishDestroy / AddReferencedObjects) is dispatched via the FClass's
    // FakeVTable, which lives in .rodata per the XCore-4b pattern (see §2.4).
    // Standard C++ derivation IS permitted -- a user-class can be `class XActor :
    // public XObject` and provide virtual methods of its own. The GC walk does
    // NOT consult any user-class vtable; it consults only the FClass's FakeVTable
    // and the FStruct::RefSchema schema vector. This is what makes hot-reload
    // safe: a user-class vtable change is fine (the GC doesn't read it); only
    // changes to XObject's own implicit destructor would matter, and XObject has
    // none (the FakeVTable replaces it).

    // === Constructors ===

    // Default ctor: zero-initializes; expects subsequent NewObject path to fill
    // ClassPrivate / InternalIndex / SerialNumber / Outer / NamePrivate.
    // The "real" construction path is NewObject(); this ctor exists only for
    // the consteval CDO bootstrap (where the FClass populates the fields at
    // compile time).
    XObject() noexcept = default;

    // Consteval ctor (per Master Plan §2a C++ standard row + XCore-4b consteval
    // CDO posture): constructs a constinit-friendly XObject for the FClass static
    // initialization path.
    explicit consteval XObject(const FClass* cls, XObject* outer, FName name,
                                uint32_t flags) noexcept
        : ClassPrivate(cls), InternalIndex(-1), SerialNumber(0),
          Outer(outer), NamePrivate(name), ObjectFlags(flags),
          ReachabilityFlag(0), _reservedCluster0(0), _reservedCluster1(0) {}

    // === Accessors (non-virtual; inline) ===
    XPACT_FORCEINLINE const FClass* GetClass() const noexcept { return ClassPrivate; }
    XPACT_FORCEINLINE XObject*       GetOuter() const noexcept { return Outer; }
    XPACT_FORCEINLINE FName          GetFName() const noexcept { return NamePrivate; }
    XPACT_FORCEINLINE int32_t        GetInternalIndex() const noexcept { return InternalIndex; }

    // SerialNumber accessor — sim-path forbidden per FIX-A-CRIT-2 cross-arch determinism invariant.
    XPACT_FORCEINLINE uint32_t       GetSerialNumber() const noexcept {
        XPACT_CHECK_SL(!::XCore::HAL::IsSimPathTU());   // compiled-in guard on sim-path TUs
        return SerialNumber;
    }

    // EObjectFlags read with explicit memory order
    XPACT_FORCEINLINE uint32_t       GetFlags(std::memory_order o = std::memory_order_relaxed) const noexcept {
        return ObjectFlags.load(o);
    }
    XPACT_FORCEINLINE bool           HasAnyFlags(uint32_t mask) const noexcept {
        return (GetFlags() & mask) != 0;
    }
    XPACT_FORCEINLINE bool           HasAllFlags(uint32_t mask) const noexcept {
        return (GetFlags() & mask) == mask;
    }

    // Atomic flag mutation (CAS-loop; see §2.3 for ordering rules)
    void                             SetFlags(uint32_t bits) noexcept;
    void                             ClearFlags(uint32_t bits) noexcept;

    // Mark-as-Garbage (per FIX-A-HIGH-19; mirrors UE MarkAsGarbage).
    // Sets RF_MarkedAsGarbage; next GC pass clears references to this object via
    // XPACT_GC_OPTION_ELIMINATE_GARBAGE_REFS sweep option.
    // Rev 3 (FIX-M-R2-10): MarkForKill is non-sim-path. Calling it from a sim-path TU
    // is forbidden because the next-GC-sweep timing is non-deterministic (the actual
    // ref-nulling happens whenever the next GC cycle runs, which is not bound to a
    // sim-tick boundary). Guarded via XPACT_CHECK_SL at entry.
    void                             MarkForKill() noexcept;
    // (Implementation: void XObject::MarkForKill() noexcept {
    //      XPACT_CHECK_SL(!::XCore::HAL::IsSimPathTU(),
    //          "MarkForKill is non-sim-path; the next-GC-sweep timing is non-deterministic");
    //      SetFlags(uint32_t(EObjectFlags::MarkedAsGarbage));
    //  }
    //  See §6 sim-path policy + §4.2 sweep options.)
    XPACT_FORCEINLINE bool           IsMarkedAsGarbage() const noexcept {
        return HasAnyFlags(uint32_t(EObjectFlags::MarkedAsGarbage));
    }

    // === Identity APIs ===
    FString                          GetFullName() const;  // "Package.Outer.Name" form
    FString                          GetPathName() const;
    // GetKey is non-sim-path; XObjectKey hash is forbidden on sim-path TUs.
    XObjectKey                       GetKey() const noexcept;  // see §6.4

    // === Class hierarchy APIs ===
    bool                             IsA(const FClass* cls) const noexcept;  // O(1) via ClassCastFlags or O(depth) via SuperStruct walk
    template <typename T>
    bool                             IsA() const noexcept { return IsA(T::StaticClass()); }

    template <typename T>
    T*                               CastTo() noexcept {  // returns nullptr on type mismatch

    }
};

UE's FUObjectItem (the per-instance GC-state entry in FUObjectArray) is ~24 bytes (carrying FlagsAndRefCount, ObjectPtr, SerialNumber, ClusterRootIndex). XPact's XObject at 56 bytes is LARGER than UE's UObjectBase alone by 16 bytes — but the 56 bytes UNIFY the header with cluster reservation + GC state shape inline. The split happens differently: XPact's FXObjectArrayEntry (32 bytes; §3.3) holds the mark bit + state bits separately, but the cluster reservation + remote-id reservation are inline in the XObject header (not in the entry). At GC walk time, the inner loop hits one XObject* dereference + the FStruct::RefSchema vector walk; UE's walk hits the UObjectBase* AND fetches the parallel FUObjectItem* from the chunk pointer array.

For 50k typical XObjects, the 16-24 byte/object cost is ~0.8-1.2 MB (range bounded by 16-byte minimum cost × 50,000 = 800 KB and 24-byte maximum cost × 50,000 = 1.2 MB; Rev 3 per FIX-N-R2-3 precision update) — well within Quest 3's 4 GB budget. The cache-coherency advantage at GC walk dominates: a single L1/L2 miss per ref-property walk costs ~50-200 cycles on Quest 3 ARM64. Across 100k objects each with 5-10 ref properties, the saving is order-of-megabytes of cycles per cycle — significantly better than the byte cost.

Per Prime Directive: the correct trade-off (more bytes per header, fewer indirections at GC walk) wins over the easy trade-off (mirror UE's split shape). This is intentional design.

2.3 EObjectFlags layout

EObjectFlags is a 32-bit bitmask of lifecycle and policy flags. The atomic semantics matter: multiple threads can set/clear flags concurrently (e.g., the loader sets RF_NeedLoad, the loader thread sets RF_NeedPostLoad, the GC sets RF_BeginDestroyed). The CAS loop ensures no flag is lost. Rev 2 expanded the taxonomy per FIX-A-HIGH-18 and FIX-A-HIGH-19 to add load-bearing flags missing from Rev 1.

// EObjectFlags (Rev 2 expanded; FIX-A-HIGH-18 + FIX-A-HIGH-19; covers the UE
// load-bearing set, drops UE-historical deprecated flags per §2.3.1 mapping table).
// Hot-reload commitment: bit positions are part of the Stage B addendum.
enum class EObjectFlags : uint32_t {
    None                       = 0,

    // === Allocation / lifecycle ===
    NeedInitialization         = 1u <<  0,   // post-allocation, pre-PostInitProperties
    ClassDefaultObject         = 1u <<  1,   // this is the CDO for its FClass
    ArchetypeObject            = 1u <<  2,   // template object used as construction template
    Transient                  = 1u <<  3,   // do not serialize
    NeedLoad                   = 1u <<  4,   // serialized data not yet loaded
    NeedPostLoad               = 1u <<  5,   // PostLoad pending
    Standalone                 = 1u <<  6,   // root-set member; persists across GC
    BeginDestroyed             = 1u <<  7,   // BeginDestroy has been called
    FinishDestroyed            = 1u <<  8,   // FinishDestroy has been called (object slot may now be reused)

    // === GC ===
    MarkAsRootSet              = 1u <<  9,   // pinned in GC root set
    MarkAsNative               = 1u << 10,   // constinit-allocated; lives in .rodata or process-static memory
    DefaultSubObject           = 1u << 11,   // CDO-template-spawned child object
    MarkedAsGarbage            = 1u << 12,   // Rev 2 (FIX-A-HIGH-19); next GC sweep clears refs to this object
                                              // via XPACT_GC_OPTION_ELIMINATE_GARBAGE_REFS

    // === Hot-reload ===
    BeingReplaced              = 1u << 13,   // hot-reload swap in progress for this object's class
    HotReloadReplaced          = 1u << 14,   // post-swap; instance was rebound to a new FClass*

    // === Loader/serialization (Rev 2 added per FIX-A-HIGH-18 / UE-MISS-4) ===
    Public                     = 1u << 15,   // visible across package boundaries; UE-faithful RF_Public
    HasExternalPackage         = 1u << 16,   // object has an external (non-Outer-derived) Package
    LoadCompleted              = 1u << 17,   // post-load is fully resolved (all references bound)
    NonPIETransient            = 1u << 18,   // transient in PIE but persistent outside PIE

    // === Debug ===
    DebugLogged                = 1u << 19,   // already emitted a debug-print on lifecycle event

    // === Reserved for engine extensions ===
    _Reserved20                = 1u << 20,
    _Reserved21                = 1u << 21,
    _Reserved22                = 1u << 22,
    _Reserved23                = 1u << 23,

    // === High bits reserved for plugin / user policy flags (Rev 3 expanded per FIX-M-R2-2) ===
    UserFlag_Begin             = 1u << 24,
    UserFlag_1                 = 1u << 24,
    UserFlag_2                 = 1u << 25,
    UserFlag_3                 = 1u << 26,
    UserFlag_4                 = 1u << 27,
    UserFlag_5                 = 1u << 28,
    UserFlag_6                 = 1u << 29,
    UserFlag_7                 = 1u << 30,
    UserFlag_8                 = 1u << 31,
    UserFlag_End               = 1u << 31,
};

Atomic mutation pattern. Both SetFlags and ClearFlags use a CAS loop with memory_order_acq_rel on success and memory_order_acquire on failure (matching UE's FORCENOINLINE AtomicallySetFlags in UObjectBase.h). The atomic operations are released so that observers reading the flag with memory_order_acquire see a happens-before-correct view of the object state at the time the flag was set.

2.4 XObject lifecycle dispatch (FakeVTable pattern extended to XObject)

UE's UObject has ~30 virtual methods (PostInitProperties, BeginDestroy, FinishDestroy, IsReadyForFinishDestroy, Serialize, PostLoad, PreSave, ...). Each is a hot-reload risk: a patch DLL whose user-class overrides a virtual method must be recompiled against the exact same vtable layout. XPact's pattern extends XCore-4b's FakeVTable mechanism (which was applied to FProperty and FScriptStruct ICppStructOps) to XObject lifecycle dispatch too: the FClass carries a per-class function-pointer table (the “XObjectLifecycleTable”), populated at FClass static-init time, that holds the lifecycle slots.

// FXObjectLifecycleTable: one per FClass, in .rodata. The FClass references this
// table via a new const FXObjectLifecycleTable* LifecycleTable field (8 bytes
// appended to FClass; Rev 3 corrected per FIX-C-R2-1: FClass sizeof 224 -> 240
// per Contract Rev 13.9 micro-bump, FIX-A-CRIT-3 / O1 arbitration. The +16
// growth comes from FStruct +8 RefSchema + FClass-specific +8 LifecycleTable
// landing together at Rev 13.9; LifecycleTable lands at FClass-absolute offset 232).
//
// SLOT TABLE (8 slots; mirrors UE's UObject lifecycle virtuals, dropped to the
// MVP-load-bearing set; Serialize slot signature accepts FArchiveContext void*
// per FIX-A-HIGH-13 for XSerialization forward-compat):

enum class EXObjectLifecycleSlot : uint32_t {
    PostInitProperties      = 0,   // void(*)(XObject*); called after NewObject construction + default-value copy
    BeginDestroy            = 1,   // void(*)(XObject*); first-phase destruction; instance is still mostly valid
    IsReadyForFinishDestroy = 2,   // bool(*)(XObject*); returns true when FinishDestroy is safe to call
    FinishDestroy           = 3,   // void(*)(XObject*); second-phase destruction; instance bytes are about to be freed
    Serialize               = 4,   // void(*)(XObject*, FArchive&, const FArchiveContext*) noexcept; FIX-A-HIGH-13
    AddReferencedObjects    = 5,   // void(*)(XObject*, FXGrayQueue&); explicit GC root-walk hook for user-managed references
    PostLoad                = 6,   // void(*)(XObject*); post-deserialize; runs after the entire object graph is loaded
    PreSave                 = 7,   // void(*)(XObject*, const FObjectPreSaveContext*); pre-serialize; runs before write
    Count                   = 8,   // sentinel
};

struct alignas(8) FXObjectLifecycleTable {
    uint32_t Capabilities;          // 4-byte bitmask: bit N set => slot N is non-null
    uint32_t _padHeader;            // 4-byte pad
    void   (*Slots[8])(void);       // 8 * 8 = 64 bytes; cast to per-slot signature at dispatch
    // Total: 8 + 64 = 72 bytes per FClass, in .rodata.
};

static_assert(sizeof(FXObjectLifecycleTable) == 72,
              "FXObjectLifecycleTable ABI lock: 8-byte header + 8 slots = 72 bytes per FClass");
static_assert(static_cast<uint32_t>(EXObjectLifecycleSlot::Count) == 8,
              "EXObjectLifecycleSlot count lock: 8 slots");

Serialize slot signature (FIX-A-HIGH-13 / FIX-A-HIGH-21). The Serialize slot accepts a third argument const FArchiveContext* Ctx alongside FArchive& Ar. The FArchiveContext is an XSerialization-defined opaque type (forward-declared as struct FArchiveContext; in XCoreXObject's header, no member definitions visible to XCoreXObject). XSerialization owns the type definition and can extend it without breaking the lifecycle-table ABI — the table holds a function-pointer; only XSerialization-emitted Serialize implementations need to know the full type. This is the standard void*-style forward-compat pattern: the type's identity is fixed (FArchiveContext); its layout is XSerialization's concern. Per FIX-A-MIN-45, XSerialization is the downstream consumer that fills this slot.

FClass LifecycleTable field (Contract Rev 13.9). The FClass references this table via a new const FXObjectLifecycleTable* LifecycleTable field (one 8-byte pointer added to FClass at the end of its layout). The Stage B addendum extension pin XPACT_XOBJECT_LIFECYCLE_TABLE_TAG covers the table layout; the updated XPACT_FCLASS_LAYOUT_TAG (v6) reflects the +8 byte FClass sizeof.

Contract Rev 13.9 micro-bump (decided per FIX-A-CRIT-3 / O1 arbitration; Rev 3 corrected per FIX-C-R2-1). The FClass sizeof change from 224 → 240 (Rev 2 declared 232 with inconsistent arithmetic; Rev 3 corrects to 240) IS a Contract delta. The +16 byte growth comes from FStruct +8 (RefSchema, FIX-A-CRIT-8) + FClass-specific +8 (LifecycleTable). The alternative — placing the LifecycleTable pointer in a parallel TMap<const FClass*, const FXObjectLifecycleTable*> lookup — was rejected: the lookup would cost a TMap hash probe per PostInitProperties / BeginDestroy / FinishDestroy call, which is wrong per Prime Directive (the table-pointer is a single direct member load). The alternative of inlining the 8-slot table into FClass directly (72 bytes per FClass × 10k classes = 720 KB module footprint) was also rejected per Prime Directive (wrong space cost). The bump is the right answer. Master Plan Rev 16 amendment to file (filed by main agent).

2.5 Dispatch call sites

The runtime calls into the FakeVTable at the following points:

  • NewObject path calls PostInitProperties after construction + default-value copy from the CDO. If the slot is null (Capabilities bit 0 = 0), no call. (See §8.4 for the FXObjectInitializer destructor-driven trigger.)
  • FClass::Link path (XCore-4b §7.3) does not call any slot, but is part of XCoreXObject's responsibility because Link populates FStruct::ObjectRefProperties for the slow-path inspection AND FStruct::RefSchema for the fast-path GC walk (§7.4).
  • GC sweep phase calls BeginDestroy on each unreachable XObject. After BeginDestroy returns, the object enters the deferred-destruction queue.
  • Deferred-destruction queue drain (runs in the worker pool, between GC cycles) calls IsReadyForFinishDestroy repeatedly until it returns true, then calls FinishDestroy. Only after FinishDestroy returns does the FXObjectArray slot become available for reuse (SerialNumber bumps; FXObjectAllocator marks the slab cell free).
  • XSerialization save/load paths call PreSave, Serialize (with the FArchiveContext void* per FIX-A-HIGH-13), PostLoad through this table.
  • GC mark phase calls AddReferencedObjects on objects whose class declares the slot (typically rare; the schema-vector walk covers most cases. AddReferencedObjects exists for native-only types that hold XObject pointers in non-reflected slots — e.g., editor caches, runtime pools).

2.6 XObject sizeof / cache-line considerations

XObject sizeof = 56 bytes. The first cache line (typical 64 bytes on Quest 3 ARM64 + Win64 x86_64) holds:

  • Offset 0-15 (16 bytes): ClassPrivate + InternalIndex + SerialNumber — the GC-hot identity block.
  • Offset 16-31 (16 bytes): Outer + NamePrivate — identity continuation, also in the first cache line.
  • Offset 32-55 (24 bytes): ObjectFlags + pad + cluster reservation — lifecycle + Phase-2 reservation.

The next 8 bytes (offset 56-63) of cache line are available for the first 8 bytes of subclass state (e.g., XActor's first member). This is intentional: an XActor with a 12-byte Transform Location field has Location.X / Location.Y in the same cache line as the XObject header, hot at GC-walk time. The header layout is optimized for the GC-walk pattern (header load + ref-property fetch + Outer chase) all hitting cache hot.

2.7 Forward-compat reservation rationale (Rev 2 corrected)

Rev 1 reserved 16 bytes in two separate 8-byte slots (cluster + remote-id). Rev 2 per FIX-A-MIN-49 / O5 arbitration consolidates this:

  • The cluster reservation EXPANDS to 16 bytes (matching UE FCluster shape; supports cluster-root index + cluster-flags + remembered-set state inline).
  • The remote-id reservation DROPS (no system inventory line claims it; the 8 bytes are reabsorbed into the cluster expansion).
  • Net XObject sizeof remains 56 bytes; the reservation is now correctly sized for the Phase-2 cluster activation per UE-VER-7 (FIX-A-MED-23 3-rotating-reachability-flags trick benefits from inline cluster bookkeeping).

Per Prime Directive: this is the correct trade-off, not the easy one. Reserving 16 bytes for a properly-shaped cluster activation is right; reserving 8 bytes that would force later layout pain when clustering ships is wrong.

3. The XObject Heap (Allocator)

3.1 Design decision: separate XObject heap, layered on FMallocBinnedX

Critical design decision (per spec critical-decisions list, item 1): the XObject heap is a separate allocator layer, built on top of XCore-4a's FMallocBinnedX as a backing-store consumer. It is NOT a fully independent allocator (that would duplicate FMallocBinnedX's VM reservation, slab discipline, and OS-page management) and it is NOT a thin tag-wrapper around FMallocBinnedX (that would lose the type-segregated free-lists and the scenario-boundary mark-region clearing that bound fragmentation).

The layering:

  • Tier 1 (XCore-4a): FMallocBinnedX manages OS virtual memory in 56 per-bin reserved ranges (XCore-4a §4 design). Each VM range is a contiguous slab of pages.
  • Tier 2 (XCoreXObject, this spec): FXObjectAllocator reserves a dedicated set of slabs from FMallocBinnedX via the existing FMemory::Malloc entry point with FMemTag::XObject attribution. Each slab becomes the backing storage for a size-class pool that owns multiple XObject slots.
  • Tier 3 (XCoreXObject, this spec): within each size-class pool, the allocator maintains type-segregated free-lists — the slab is sub-divided into runs of cells, with each run dedicated to a specific FClass*. This is the fragmentation-mitigation per Master Plan §2a FIX-A-I-2.

Why separate XObject heap from FMallocBinnedX:

  • XObject lifetime is GC-managed: the allocator must know which addresses are XObject candidates so the GC's iteration can decode them (mark bit lookup, FClass* dispatch). FMallocBinnedX has no concept of "this block is an XObject"; tagging it post-hoc would require either (a) per-block back-pointer lookup (cost: one indirection per GC mark, multiplied by ~50k objects per scan = 50k extra cache misses per scan; busts the <50 ms ARM64 budget) or (b) probing the FMallocBinnedX tag side-table at mark time (same cost shape).
  • Size-class segregation for fragmentation: XObject sizes cluster around a few specific values (XActor = ~128 bytes, XComponent = ~96 bytes, XScenario step nodes = ~64 bytes, etc.). Size-class pools that match the actual XObject size distribution waste less heap than FMallocBinnedX's general-purpose 56-bin schedule.
  • Type-segregation within size class: all XActor instances share a sub-pool inside the 128-byte size class. When the scenario unloads, the entire XActor sub-pool can be returned to the size class's free list in O(1), regardless of reachability of individual instances. This is the scenario-boundary mark-region clearing optimization that breaks fragmentation creep over multi-hour Quest 3 sessions.
  • Mark-bit co-location: each size-class pool stores its mark bits in a dedicated bitmap at the head of the slab, separate from the user-visible cells. The bitmap is one bit per cell; for a 64 KB slab containing 1024 64-byte cells, the bitmap is 128 bytes (0.2% overhead).
  • Hot-reload bookkeeping: when a downstream module is hot-reloaded and an FClass is replaced, the XObject allocator must walk every instance of the affected FClass (via the FXObjectArray) and rebind. The type-segregated sub-pools make this walk efficient (visit only the affected sub-pool, not the entire heap).

Why layer on FMallocBinnedX rather than reserve VM directly: FMallocBinnedX already owns OS page management (Win32 VirtualAlloc, mmap on Linux, Android's allocator); duplicating that would re-create complexity. FMallocBinnedX's FMemTag attribution feeds XCore-4a's leak tracker and memory-budget telemetry. FMallocBinnedX's per-thread TLS caches accelerate allocation of new slabs.

3.3 FXObjectArray (the global object table)

The FXObjectArray is a global table indexed by InternalIndex; it holds metadata for every live XObject. UE's equivalent is FUObjectArray at CoreUObject/Public/UObject/UObjectArray.h. XPact's design diverges in three ways: (a) the array is a single sparse-array (not the UE chunk-pointer-array indirection); (b) each entry is 32 bytes (not UE's 48-64 depending on options); (c) the entry carries the XObject pointer + mark bit + cluster bit + flags directly, not a separate parallel array.

// FXObjectArray entry (32 bytes; one cache-half-line).
// Stored densely in a contiguous TArray-like structure backed by FMallocBinnedX
// with FMemTag::XObject. The array grows in 1 MB increments (32k entries per grow);
// existing entries are NEVER relocated (pointer-stability of the entry, distinct
// from pointer-stability of the XObject; see §9.1).
struct alignas(8) FXObjectArrayEntry {
    XObject*              Object;             //  0  +8   null = entry slot is free (waiting reuse)
    uint32_t              SerialNumber;       //  8  +4   bumps on each Object replacement; XWeakPtr deref checks
    uint32_t              ClusterRootIndex;   // 12  +4   if this object is in a cluster, the index of the cluster root (Phase 2)
    std::atomic<uint64_t> StateBits;          // 16  +8   atomic: mark bit (bit 0), pending-destroy bit (bit 1),
                                              //          root-pinned bit (bit 2), hot-reload-in-progress bit (bit 3)
    uint64_t              _reserved;          // 24  +8   future use (e.g., remote-handle bookkeeping)
};

static_assert(sizeof(FXObjectArrayEntry)  == 32, "FXObjectArrayEntry ABI lock: 32 bytes (1/2 cache line)");
static_assert(alignof(FXObjectArrayEntry) ==  8, "FXObjectArrayEntry alignment lock");

FXObjectArray API:

class FXObjectArray {
public:
    int32_t  ReserveSlot(uint32_t* OutSerialNumber) noexcept;
    void     BindObject(int32_t InternalIndex, XObject* Object) noexcept;
    void     MarkPendingDestroy(int32_t InternalIndex) noexcept;
    void     ReleaseSlot(int32_t InternalIndex) noexcept;   // bumps SerialNumber

    // Rev 3 (FIX-M-R2-3): Mark API operates on XObject.ReachabilityFlag directly,
    // not on FXObjectArrayEntry.StateBits. One less indirection per call (the
    // ReachabilityFlag is co-located with the XObject header, hot in the cache after
    // the first reference load). The `kMarkBit` constant maps onto the rotating
    // reachability bit selected by the current cycle.
    XPACT_FORCEINLINE bool IsMarked(int32_t InternalIndex) const noexcept {
        XObject* obj = Entries[InternalIndex].Object;
        if (obj == nullptr) return false;
        const uint32_t mask = CurrentCycleReachabilityMask();   // 1 << g_CurrentReachabilityIndex (0/1/2)
        return (obj->ReachabilityFlag.load(std::memory_order_acquire) & mask) != 0;
    }
    XPACT_FORCEINLINE void Mark(int32_t InternalIndex) noexcept {
        XObject* obj = Entries[InternalIndex].Object;
        if (obj == nullptr) return;
        const uint32_t mask = CurrentCycleReachabilityMask();
        obj->ReachabilityFlag.fetch_or(mask, std::memory_order_acq_rel);
    }
    XPACT_FORCEINLINE void ClearMark(int32_t InternalIndex) noexcept {
        XObject* obj = Entries[InternalIndex].Object;
        if (obj == nullptr) return;
        const uint32_t mask = CurrentCycleReachabilityMask();
        obj->ReachabilityFlag.fetch_and(~mask, std::memory_order_acq_rel);
    }

    template <typename Visitor> void ForEachObject(Visitor&& v) const noexcept;
    template <typename Visitor> void ForEachObjectOfClass(const FClass*, Visitor&& v) const noexcept;

    int32_t  GetLiveCount() const noexcept;

private:
    TArray<FXObjectArrayEntry>  Entries;
    TArray<int32_t>             FreeList;    // LIFO; recently-released slot first
    FCriticalSection            AllocLock;

    // Rev 3 (FIX-M-R2-3): the rotating reachability bits MOVED to XObject.ReachabilityFlag.
    // The FXObjectArrayEntry retains only the state bits that don't participate in the
    // GC mark inner loop (pending-destroy, root-pinned, hot-reload, garbage).
    //
    // The IsMarked / Mark / ClearMark accessors below READ FROM XObject.ReachabilityFlag,
    // not from FXObjectArrayEntry.StateBits — one less indirection per mark loop iteration.
    // The accessors take an InternalIndex, fetch the XObject* from the entry, then
    // access XObject.ReachabilityFlag directly. This saves one cache miss per object
    // marked (~50-200 cycles on Quest 3 ARM64; significant at 100k objects per scan).
    static constexpr uint64_t kPendingDestroyBit    = 1ull << 1;
    static constexpr uint64_t kRootPinnedBit        = 1ull << 2;
    static constexpr uint64_t kHotReloadInProgress  = 1ull << 3;
    // Bit 7: Garbage flag (mirror of EObjectFlags::MarkedAsGarbage for fast sweep check; FIX-A-HIGH-19)
    static constexpr uint64_t kGarbageBit           = 1ull << 7;
};

// Rev 3 (FIX-M-R2-3 + FIX-M-R2-11): kMarkBit is the ACTIVE mark bit. Implementation
// details on the rotating-flag scheme:
//
// The XObject.ReachabilityFlag uint32 holds (low to high):
//   bit 0: kReachabilityFlag0 (rotating; one of 0/1/2 is "current cycle" per cycle counter)
//   bit 1: kReachabilityFlag1
//   bit 2: kReachabilityFlag2
//   bits 3..7: reserved for GC-internal mirrors (PendingDestroy/RootPinned/Garbage shadow)
//   bits 8..31: reserved for future GC scheme additions
//
// Per cycle, the global `g_CurrentReachabilityIndex` (uint8 in 0/1/2) selects which
// of bits 0..2 is the "this-cycle's" mark bit. The GC's IsMarked / Mark / ClearMark
// API operates with the logical "current cycle's reachability bit"; a software
// indirection masks the rotating index onto the physical bit. Three flag bits used
// in rotation; exactly one bit always represents "current cycle reachable"; the two
// unused-this-cycle bits clear naturally as GC advances three cycles (the cycle that
// USED bit N two cycles ago is the one whose objects must be swept this cycle if
// still unmarked).
//
// This is the UE 5.x EInternalObjectFlags::ReachabilityFlag0/1/2 pattern (ObjectMacros.h:678-680)
// faithfully ported with the optimization that the bits live on the XObject header
// (FIX-M-R2-3) rather than the entry table (avoid the indirection).

Index 0 is reserved: a freshly-zeroed XWeakPtr / XObjectKey with InternalIndex == 0 represents "null"; the FXObjectArray never allocates index 0 to a real object.

3.5 Allocation hot-path

Two signatures (FIX-A-MED-29):

  • NewObject<T>(Outer, Name, Flags) — infallible-style; returns T*; asserts on allocation failure (treats OOM as a programmer error, abort in Shipping per error handling discipline §2a).
  • TryNewObject<T>(Outer, Name, Flags) — fallible-style; returns Result<T*, FNewObjectError>; intended for OOM-tolerant call sites (loader paths, async streaming workers).
// Hot-path NewObject allocation (six load/store-bound steps; no locks on fast path).
// Rev 2 adds: init-phase gate (FIX-A-CRIT-5), sim-path runtime invariant
// (FIX-A-CRIT-1 / O10), FXObjectInitializer destructor-driven PostInitProperties
// (UE-MISS-2 / FIX-A-HIGH-12; see §8.4).

template <typename T>
T* NewObject(XObject* Outer, FName Name, EObjectFlags Flags) {
    const FClass* cls = T::StaticClass();

    // Pre-condition: NewObject during GC mark is forbidden (could leak the
    // new object from the mark phase). XPACT_CHECK in Dev; no-op in Shipping.
    XPACT_CHECK(!FXObjectCollector::IsMarking());

    // Pre-condition: init phase gate (Rev 2 per FIX-A-CRIT-5). The heap + collector
    // come up at PostStaticInit, not PreStaticInit. NewObject before PostStaticInit
    // is a bootstrap-ordering bug.
    XPACT_CHECK(EngineInitPhase() >= EInitPhase::PostStaticInit);

    // Pre-condition: sim-path runtime invariant (Rev 2 per FIX-A-CRIT-1 / O10).
    // Sim-path TUs must call NewObject only from the SimPathSerialExecutor thread.
    // Non-sim-path TUs (editor, asset pipeline, loader workers) may call from any thread.
    XPACT_CHECK_SL(::XCore::HAL::IsSimPathThread() || !::XCore::HAL::IsSimPathTU());

    // 1. Allocate raw storage from the size-class pool (3-arg signature per FIX-A-CRIT-4).
    void* storage = g_XObjectAllocator.AllocateRaw(
        cls->PropertiesSize, cls->MinAlignment, cls);

    // 2. Reserve an entry slot in the FXObjectArray.
    uint32_t serial;
    int32_t  internalIndex = g_XObjectArray.ReserveSlot(&serial);

    // 3. Construct via the FClass's ClassConstructorFn (placement new +
    //    default-value initialization from the CDO). The FXObjectInitializer is
    //    stack-constructed and threaded through ClassConstructorFn (see §8.4);
    //    its destructor (~FXObjectInitializer at scope exit) calls PostInitProperties.
    //
    // Rev 3 (FIX-M-R2-4): if RF_NeedLoad is set on entry, the loader is responsible
    // for invoking PostInitProperties later (after Serialize completes); skip the
    // FXObjectInitializer construction to avoid firing PostInitProperties twice.
    // See §10.6.1 for the async loading path.
    const bool bSkipInitializer = (uint32_t(Flags) & uint32_t(EObjectFlags::NeedLoad)) != 0;
    if (bSkipInitializer) {
        cls->ClassConstructorFn(storage, FFieldVariant(Outer), /*Initializer=*/nullptr);
    } else {
        FXObjectInitializer Initializer(storage, cls, Outer, Name);
        cls->ClassConstructorFn(storage, FFieldVariant(Outer), Initializer);
    }

    // 4. Fill XObject header.
    XObject* obj = static_cast<XObject*>(storage);
    obj->ClassPrivate    = cls;
    obj->InternalIndex   = internalIndex;
    obj->SerialNumber    = serial;
    obj->Outer           = Outer;
    obj->NamePrivate     = Name;
    obj->ObjectFlags.store(static_cast<uint32_t>(Flags | EObjectFlags::NeedInitialization),
                            std::memory_order_release);

    // 5. Bind XObject to the FXObjectArray slot.
    g_XObjectArray.BindObject(internalIndex, obj);

    // 6. (~FXObjectInitializer fires here at the end of the function scope.)
    //    Its destructor calls PostInitProperties via the FClass lifecycle FakeVTable
    //    AFTER all CreateDefaultSubobject calls made from the user-class ctor body
    //    have completed (FIX-A-HIGH-12 / UE-MISS-2; see §8.4).

    obj->ClearFlags(uint32_t(EObjectFlags::NeedInitialization));
    return static_cast<T*>(obj);
}

3.6 Fragmentation discipline (Foundation Prototype criterion h)

Three layered defenses for <15% wasted heap over 4-hour Quest 3 continuous-load:

  1. Size-class segregation: per-cell waste bounded by size-class spacing (worst case 33% at the 384-byte class).
  2. Type-segregated free-lists: cells in a free-list are reused by the same FClass, so cells are always sized exactly right for the next allocation of that class.
  3. Scenario-boundary mark-region clearing: at scenario unload, the entire FClass sub-pool for scenario-scoped types is released to the size class's free-list in O(1), regardless of individual reachability.

Mark-region clearing protocol: XScenarios marks itself as the "owning scenario" for every XObject created during its load. On scenario unload, XScenarios calls FXObjectAllocator::ReleaseClassPool(cls). The allocator validates: walks FXObjectArray entries for instances of cls and confirms each is reachable ONLY from the scenario root. If any escape is detected, the call returns Result::Err(FScenarioBoundaryError::EscapedReference) and the scenario falls back to GC-driven collection. On success: all sub-pool cells return to the size-class free-list, the FXObjectArray entries are released, and SerialNumbers bump for every released slot.

Slab return to OS: slabs are NOT returned to FMallocBinnedX during normal operation. At process exit, all slabs are released. Hot-reload of a downstream module does NOT release the module's slabs; the post-hot-reload heap state preserves all live objects.

Idle slab coalescence (Rev 2; FIX-A-MED-24). At idle (post-quiesce, between scenarios), the engineer station may invoke XCoreXObject::CoalesceIdleSlabs() to merge under-utilized size-class pools and return slabs to FMallocBinnedX. Trainee build does NOT call this; the long-running engineer session does. The coalescence is gated by a CVar-tunable threshold (default: pool occupancy below 25% across >3 consecutive idle samples). Returned slabs are tagged for re-allocation at the next pool growth; the FXObjectArray pointer-stability invariant is preserved (the entries are not affected). XInsights emits Allocator.PoolReleaseAtScenarioBoundary with the freed-byte count for telemetry.

Per-FClass sub-pool rebind on class replacement (Rev 2; FIX-A-MIN-40). The class replacement protocol (§9.2) includes invalidating the OldClass's sub-pool entry in FXObjectAllocator. Cells in the OldClass sub-pool are migrated to the NewClass sub-pool (the cells themselves don't move; only the sub-pool ownership changes). This preserves the type-segregation invariant across hot-reload: after replacement, all NewClass instances continue to share a coherent sub-pool.

3.7 Cross-thread allocation

XObject allocation is permitted from any worker-pool thread. Per-thread TLS cache holds a small bundle of free cells per active FClass (~16 cells). Cells exhausted: refill from the pool's per-FClass free-list (under PoolLock). Cross-thread free: enqueue onto the owner-pool's MPSC reclaim queue (XCore-4a TBoundedMpscQueue); owner-pool drains on next allocation. FXObjectArray ReserveSlot/ReleaseSlot takes the AllocLock (one global mutex; uncontended).

Determinism contract: allocation IS deterministic given identical call sequences from a fixed thread set. BUT cross-thread allocation order is not deterministic. Convention: sim-path NewObject calls happen on the SimPathSerialExecutor's thread (per Master Plan §2a Threading row); cross-thread NewObject is reserved for non-sim-path code.

4. GC Collector Algorithm

4.0 EXGCOptions enum (Rev 3 per FIX-N-R2-6)

The collector exposes a runtime-tunable options bitmask EXGCOptions. Callers pass the bitmask via XGarbageCollect::CollectGarbage(EXGCOptions Opts) (or via the heuristic-driven internal trigger which selects defaults). Rev 3 formalizes the enum that earlier prose referred to as XPACT_GC_OPTION_* sentinel macros:

// Rev 3 (FIX-N-R2-6): EXGCOptions enum. Bitmask of per-cycle GC tunables.
enum class EXGCOptions : uint32_t {
    kNone                    = 0,
    kEliminateGarbageRefs    = 1u << 0,   // sweep also nulls references to RF_MarkedAsGarbage objects (FIX-A-HIGH-19)
    kPreserveCDO             = 1u << 1,   // never collect class default objects even if otherwise unreachable
    kForceFullScan           = 1u << 2,   // bypass card-table optimization for this cycle (debug/diagnostic use)
    kSkipDeferredDestruction = 1u << 3,   // synchronous BeginDestroy/FinishDestroy this cycle (shutdown path)
    kIncrementalMark         = 1u << 4,   // explicit incremental mark request (default is mostly-concurrent)
    kEmitInsightsTelemetry   = 1u << 5,   // emit XInsights GC.CycleComplete event (default: yes; opt-out for benchmarks)
    kEmitVerboseLog          = 1u << 6,   // emit XLog::XCoreXObject.GC at Verbose verbosity (default: Display)
    // bits 7..31 reserved for future GC scheme additions.
};
XPACT_FORCEINLINE EXGCOptions operator|(EXGCOptions a, EXGCOptions b) noexcept {
    return static_cast<EXGCOptions>(uint32_t(a) | uint32_t(b));
}
XPACT_FORCEINLINE bool HasFlag(EXGCOptions opts, EXGCOptions flag) noexcept {
    return (uint32_t(opts) & uint32_t(flag)) != 0;
}

The kEliminateGarbageRefs option is referenced from MarkForKill (§2.2) + the sweep flow (§4.2); the rest are heuristic-tunable for specific scenarios (e.g., kForceFullScan at scenario unload to validate fragmentation discipline). The runtime default for an unannotated CollectGarbage() call is kEliminateGarbageRefs | kEmitInsightsTelemetry.

4.1 Algorithm choice (locked per Master Plan §2a)

The collector is non-moving precise tracing mostly-concurrent mark-and-sweep with card-table generational scan-reduction. Each adjective is load-bearing:

  • Non-moving: objects never relocate post-allocation. Stable pointers across object lifetime is a hot-reload commitment; XPtr can be a raw T* without forwarding-table indirection.
  • Precise: every reference traversed is known to be a real XObject* (not a heuristic guess). Boehm-style conservative scanning is rejected (the Master Plan B-2 affirmation forbids it).
  • Tracing: reachability is determined by reachability from a root set (not via reference counting). Tracing handles cycles; reference counting does not.
  • Mostly-concurrent: the mark phase runs concurrently with the mutator (gameplay tick). Only a brief safe-point is taken to snapshot the root set; the bulk of the work overlaps with the next frame's execution.
  • Mark-and-sweep: two-phase algorithm. Mark phase visits every reachable object and sets the mark bit. Sweep phase walks the FXObjectArray entries and reclaims any unmarked entry.
  • Card-table generational scan-reduction: a card-table (one byte per 512 bytes of XObject heap) tracks which cards have been written to since the last minor collection. Minor collections skip clean cards entirely.

4.2 Phase structure

A collection cycle has the following phases:

  1. Trigger (mutator thread): the GC heuristic (allocation rate, heap occupancy, time since last collection) decides a collection is due. The trigger is also explicit: a NewObject call that would push heap occupancy past a threshold can synchronously trigger; a long idle period can trigger lazily.
  2. Safe-point handshake (~50-200 μs typical): the collector signals every worker thread + the named major threads to reach a safe-point. Threads check the safe-point flag at every back-edge / function-return / allocation; when set, they spin briefly until the snapshot is complete. The safe-point exists to (a) snapshot the precise stack roots from XIL2CPP-emitted stack maps, (b) drain in-flight write-barrier queues, (c) clear the card-table (snapshotting the dirty cards before the sweep). The safe-point is the only synchronous-with-mutator phase.
  3. Root enumeration (mark thread; concurrent): walks XGCRoot::EnumerateRoots(), the FXObjectArray's pinned-root entries, the XGCRootSpans registered by GC-aware containers, the per-thread stack-root snapshots, and any AddReferencedObjects callbacks for native types. Each root produces one or more "gray" objects (in the mark queue, not yet scanned).
  4. Mark (mark threads; concurrent): drain the gray queue. For each gray object, mark its FXObjectArrayEntry, then walk its FClass->FStruct::RefSchema schema vector (Rev 2; UE-MISS-1 fast-path; §7.4); for each reference, if unmarked, push it onto the gray queue. The schema vector replaces Rev 1's FProperty pointer-chase walk; the dense ObjectRefProperties TArray (XCore-4b FIX-13) remains as the slow-path inspection surface (used by debugger / introspection). Workers run in parallel; the gray queue is per-thread with work-stealing to balance.
  5. Write-barrier-set drain (mark threads; concurrent): the card-table marks cards as dirty when the mutator writes a reference into an old-generation slot. At end of mark, the collector re-scans dirty cards to find any object that may have been added to the live graph mid-mark. Drain is iterative until no new dirty cards remain.
  6. Sweep (sweep threads; concurrent): walk the FXObjectArray; for each unmarked, non-pinned, live entry, set the PendingDestroy bit and enqueue onto the deferred-destruction queue. If the XPACT_GC_OPTION_ELIMINATE_GARBAGE_REFS option is set (FIX-A-HIGH-19), the sweep also nulls out any reference to an object that has RF_MarkedAsGarbage set, even if the referent is otherwise reachable. The sweep is NOT mutator-stopping (the mutator can NewObject during sweep; new objects bypass the sweep by being created post-mark with their mark bit set to "this cycle's color").
  7. Deferred destruction (worker pool; over multiple frames): drain the deferred-destruction queue. For each pending object, call BeginDestroy, then poll IsReadyForFinishDestroy until true (or after a per-object timeout), then call FinishDestroy, then release the FXObjectAllocator cell and the FXObjectArray slot.
  8. Cycle end: collector resets state, increments cycle counter, updates statistics via XInsights (§10.12), evaluates heuristic for next cycle.

4.2.1 Three-rotating-reachability-flags scheme (Rev 2; FIX-A-MED-23 / UE-VER-7; Rev 3 relocated per FIX-M-R2-3)

UE 5.x uses a 3-rotating-flag scheme in EInternalObjectFlags::ReachabilityFlag0/1/2 (ObjectMacros.h:678-680): each GC cycle picks one as "this-cycle-reachable" and another as "previous-cycle-reachable"; flipping one bit avoids a clear-pass over every entry's flag word. XPact mirrors this exactly. Rev 3 storage location (per FIX-M-R2-3): the 3 rotating reachability bits live on the XObject header (the std::atomic<uint32_t> ReachabilityFlag field at offset 36, consuming the former _padObjectFlags pad slot), NOT on the FXObjectArrayEntry. This eliminates one indirection in the GC mark inner loop: previously the mark walker had to dereference the FXObjectArrayEntry, now it can read the bit directly off the XObject* that's already in the gray queue.

The GC cycle counter modulo 3 selects "this-cycle's" bit; the bit-rotation eliminates the clear-pass at cycle start (saves ~5 ms on 100k entries on Quest 3 ARM64). One bit always represents "current cycle reachable"; the other two clear naturally as GC advances three cycles (the cycle that USED bit N two cycles ago is the one whose still-unmarked objects must be swept this cycle).

Layout (Rev 3):

  • XObject.ReachabilityFlag (uint32 at offset 36; FIX-M-R2-3): bit 0 = kReachabilityFlag0 (rotates per cycle), bit 1 = kReachabilityFlag1, bit 2 = kReachabilityFlag2; bits 3..31 reserved. The "current cycle's" bit is selected by the global g_CurrentReachabilityIndex (uint8 in 0/1/2; advances monotonically per GC cycle).
  • FXObjectArrayEntry.StateBits (uint64 at entry offset 16): bit 1 = kPendingDestroyBit, bit 2 = kRootPinnedBit, bit 3 = kHotReloadInProgress, bit 7 = kGarbageBit (mirror of EObjectFlags::MarkedAsGarbage for fast sweep check). Bits 0, 4, 5, 6 are reserved (Rev 2's mark + rotating-reachability bits relocated to XObject in Rev 3).

Why move them (FIX-M-R2-3 rationale). The GC mark inner loop visits each gray object's XObject pointer, walks its RefSchema, and recursively marks referenced objects. Marking a referenced object previously required: (i) load the FXObjectArrayEntry from the global table at entry[InternalIndex] (cache miss in steady state), (ii) atomic fetch_or on the StateBits. With Rev 3's relocation, marking is just (i) atomic fetch_or on obj->ReachabilityFlag — one less memory load. The savings compound across hundreds of thousands of mark operations per cycle.

kMarkBit clarification (Rev 3 per FIX-M-R2-11). The legacy kMarkBit = 1ull << 0 constant from Rev 2 was an alias for the current-cycle's reachability bit. Rev 3 makes the mechanism explicit: the IsMarked/Mark/ClearMark API operates on a mask CurrentCycleReachabilityMask() = 1u << g_CurrentReachabilityIndex (where the index is 0/1/2 cycling per GC cycle). The mask rebinds at cycle boundary; in any single cycle, exactly one of bits 0/1/2 on each XObject's ReachabilityFlag represents "marked this cycle". The other two bits clear naturally three cycles later. This is the standard UE 5.x rotating-flag pattern (no novel mechanism); Rev 3 documents the operating model explicitly so implementation cannot accidentally treat kMarkBit as a fixed bit position.

4.2.2 3-color invariant SATB preserves (Rev 2; FIX-A-MED-34 / MAJOR-A11)

The mostly-concurrent SATB algorithm preserves the standard 3-color invariant:

  • White: candidate-unreachable (not yet visited, or known dead). All entries start the cycle as White.
  • Gray: visited but its references not yet traversed (in the mark queue).
  • Black: visited AND its references fully traversed (mark bit set, no entry in any worker's gray queue).

The SATB pre-store barrier (§5.2) captures the OLD value before reassignment, ensuring objects that were reachable at snapshot time remain reachable across the cycle even if the mutator removes references mid-collection. The invariant: a Black object never holds a reference to a White object. The SATB barrier preserves this by recording the old (potentially-White-soon) reference; the next mark drain visits the recorded object and re-establishes the invariant.

4.3 Mostly-concurrent marking: the snapshot-at-the-beginning (SATB) discipline

Critical design decision (per spec critical-decisions list, item 2): how does mostly-concurrent marking interact with the mutator?

XCoreXObject Rev 1 adopts the snapshot-at-the-beginning (SATB) discipline (the same family as Azul's C4, Shenandoah's pre-Brooks-pointer phase, and Mono's SGen). SATB is the correct choice over the alternative incremental-update (Yuasa's algorithm) for these reasons:

  • SATB closes the race once at safe-point start: the root set is snapshotted under the safe-point handshake, and from that moment any reference deleted from the snapshot is still considered reachable until the cycle ends. This means the mutator is free to overwrite slots concurrently with marking; the dirty-card pre-store barrier remembers the OLD reference value, ensuring the SATB snapshot remains complete.
  • Incremental-update requires a snoop barrier on every read: the mutator must record what it sees so the collector can re-trace. This is incompatible with the <5 ms pause budget on Quest 3 because the read-barrier cost per-frame would compound across all GC-aware field accesses.
  • SATB's worst case (floating garbage) is bounded: objects deleted mid-cycle are not reclaimed until the next cycle. For XPact's tick rate (90 Hz Quest 3) and cycle cadence (per-second typical, per-frame stress), floating garbage is at most one cycle's worth of allocation, which is well within the heap budget.
  • SATB integrates with XCore-4a's existing pre-store write barrier: the locked XGC_WriteBarrier(slot, newValue) is a pre-store barrier (mark card dirty BEFORE the slot is updated; XCore-4a XGCDeclarations.h line 207). This IS the SATB barrier; the implementation just needs to additionally record the old value of the slot for the snapshot.

Pre-store SATB barrier semantics:

// Mutator code (transparent to the user; emitted by XIL2CPP for C# writes,
// inserted by user code for C++ writes via the XPACT_GC_STORE macro):
//
//     XPACT_GC_STORE(parent, slot, newValue);
//
// expands to (in Dev / when marking is active):
//
//     {
//         XObject* oldValue = *slot;
//         if (oldValue != nullptr &&
//             FXObjectCollector::IsMarking()) {
//             // SATB: ensure the OLD value is retained in the snapshot
//             g_SATBQueue.PushTLS(oldValue);
//         }
//         FXGC_CardTable::MarkCardDirty(slot);   // generational scan-reduction
//         *slot = newValue;                       // store
//     }
//
// In Shipping (no marking active), the barrier collapses to:
//
//     {
//         FXGC_CardTable::MarkCardDirty(slot);
//         *slot = newValue;
//     }
//
// (Constant-folding eliminates the IsMarking() branch when marking is provably
// inactive at the call site; the typical call site cannot prove this, so the
// IsMarking() check is always emitted but is cheap -- one TLS load + branch).

SATB queue management: the SATB queue is per-thread (TLS), with a 256-entry circular buffer. When full, the buffer flushes into the global SATB log (a lock-free MPSC list, drained by the mark workers). At cycle end, the SATB log is drained; any object referenced in the SATB log is marked if not already.

4.4 Worker-pool concurrency

The collector spawns N worker jobs at mark phase entry, where N is the number of available worker-pool threads minus 1 (reserve one for the gameplay tick to avoid starving the frame). Each worker has a private gray queue + per-worker SATB drain; work-stealing balances. The mark phase ends when all gray queues + SATB queues are empty AND no dirty cards remain to scan.

The sweep phase similarly parallelizes by partitioning the FXObjectArray into N chunks (one per worker), each worker walks its chunk independently. Sweep workers do not coordinate (each FXObjectArrayEntry is touched by exactly one worker).

Determinism note (per §1.3): GC operations are non-sim-path; the worker scheduling is non-deterministic. This is acceptable because GC operations do not affect sim state — they only reclaim unreachable storage. The only sim-observable GC effect is the BeginDestroy / FinishDestroy callbacks on destroyed objects; XCoreXObject sequences these via the deferred-destruction queue (which IS drained in deterministic order: monotonically increasing InternalIndex order).

4.5 Card-table generational scan-reduction

The card-table is a flat byte array, one byte per 512-byte card of XObject heap. Card 0 covers heap bytes 0-511; card 1 covers heap bytes 512-1023; etc.

Card byte semantics (one byte instead of one bit for simpler memory ordering on ARM64; the byte cost is negligible: 1 MB of XObject heap = 2 KB card table = 0.2% overhead):

  • 0x00 — clean (no writes since last clearance).
  • 0x01 — dirty (one or more writes since last clearance).
  • Other values reserved for future card-aging schemes.

Card index from address: cardIdx = (addr - heapBase) >> 9. (The 512-byte card size = 2^9 makes the shift a single instruction.)

Mark dirty:

// Implementation of XGC_WriteBarrier (replaces XCore-4a's weak-symbol stub).
extern "C" void XGC_WriteBarrier(void** Slot, void* NewValue) noexcept {
    // 1. SATB pre-store barrier (only if marking is active; checks TLS flag).
    if (FXObjectCollector::IsMarkingActive()) {
        void* oldValue = *Slot;
        if (oldValue != nullptr) {
            g_SATBQueue.PushTLS(static_cast<XObject*>(oldValue));
        }
    }

    // 2. Card-table dirty mark (always; cost is one byte store).
    const size_t cardIdx = (reinterpret_cast<uintptr_t>(Slot) - g_XObjectHeapBase) >> 9;
    g_CardTable[cardIdx] = 0x01;
}

Minor collection scan-reduction: instead of walking every old-generation object's reference properties, the minor collection walks only objects whose covering card is dirty. The cost is O(dirty-cards) instead of O(old-generation-objects).

Failure mode: remembered-set saturation (per Master Plan §2a):

  • If the dirty-card count exceeds kSaturationThreshold (initial value: 50% of total cards), the collector falls back to a full-heap scan. Rev 3 verification note (per FIX-N-R2-7): the 50% threshold is calibrated against Foundation Prototype criterion (b) <50ms on Quest 3 — the 50%-dirty-card scan time must complete within budget. Forward-task: validate at Phase 5.f (card-table) implementation by measuring actual scan time on a representative 50%-dirty heap; tune threshold up/down if measured time leaves <10ms slack or exceeds budget.
  • The fallback emits an XInsights telemetry event: {type: "rememberedSetSaturation", cycleId: N, dirtyCardCount: M, totalCardCount: T, fallbackPauseMs: P}.
  • Card-table scan-reduction is automatically re-enabled when the old-to-young write rate stays below kReentryRateThreshold for kReentryStabilityCycles consecutive collections.
  • In a lockstep multi-user session, a full-heap-scan fallback is a session-interrupting event: the slowest client's fallback pause delays the lockstep barrier. XCoreXObject's policy: when fallback is triggered and the local heap exceeds kLockstepHardLimitMB, the session pauses (instructor sees a modal: "GC saturation on client X; continue / abort"). The hard limit is calibrated so fallback pauses stay under the 50 ms criterion (b) target.

4.6 Sim-path / GC boundary

The collector is non-sim-path. GC operations:

  • NEVER run inside a sim tick. The sim tick boundary is the only window where GC can start. XScenarios / XPhysics / animation evaluation runs are exclusive of GC mark/sweep.
  • The collector's mostly-concurrent mark CAN overlap with the next frame's render + the next frame's audio, but not with the next frame's sim tick.
  • If a sim tick approaches and the collector is still in mark phase, the sim tick BLOCKS until mark completes. This is a known pessimization that requires the typical pause + concurrent overlap to fit within one frame budget; the <5 ms typical pause target is the constraint.
  • Sweep + deferred-destruction CAN overlap with sim ticks because they do not write to live XObject reference slots (only mark bits + FXObjectArray entries that are not visible to gameplay code).

Implication for cross-arch determinism (criterion c): GC has no observable effect on sim state. The same sim-path operations produce bit-exact results regardless of when GC runs. Cross-arch determinism testing (the 100-replay matrix) does NOT need to control GC timing; it suffices that GC never mutates a sim-observable property.

4.7 Trigger heuristic

The collector decides when to run based on:

  • Heap occupancy: if live XObject heap exceeds kOccupancyThreshold (default 70% of available budget), schedule a collection.
  • Allocation rate: if allocations-per-second exceeds kAllocationRateThreshold (default 5000 obj/s), schedule a collection earlier.
  • Idle window: if the engine has been idle for > kIdleCollectMs (default 5 s), run an opportunistic collection.
  • Explicit request: XGarbageCollect::CollectGarbage() from C++ or GC.Collect() from C#.
  • Pre-scenario-unload: XScenarios triggers a collection before mark-region clearing to maximize the size-class pool's reclaim opportunity.

The trigger runs on the GC marker thread. GC thread architecture (Rev 2 per FIX-A-MED-36):

  • MVP (pre-XTaskGraph; pre-System-8): XCoreXObject spawns a dedicated marker thread at __Init(). The thread is otherwise idle; it sleeps on a condition variable and wakes on trigger. This is the standalone path used until XTaskGraph ships.
  • Post-XTaskGraph (post-System-8): the marker thread becomes a worker-pool participant via XTaskGraph's tagged-pool API. The collector posts mark/sweep jobs to a GC-tagged worker pool; XTaskGraph routes them.

The transition (MVP dedicated thread → XTaskGraph worker-pool integration) is a non-breaking refactor planned for Phase 5.j or System-8 integration. The §1.3 reference framing "worker-pool participant" is the post-XTaskGraph end state; the §4.7 framing "dedicated thread" is the MVP shipped state. Both are documented; see Master Plan §3 L0 inventory.

4.8 Acceptance: pause budget breakdown

The <5 ms typical pause budget (criterion a) decomposes as:

  • Safe-point handshake: 50-200 μs (dominated by stack-root snapshot of all threads).
  • Synchronous root enumeration of pinned roots + XGCRootSpans: 200-500 μs (typical 1000 pinned + 5000 root spans).
  • Card-table snapshot + clear: 100-300 μs.
  • Final-mark drain (the brief synchronous re-trace after concurrent mark): 1-3 ms.
  • Pre-sweep accounting: 100-200 μs.

The remaining ~1 ms is slack for variance + cache effects. The concurrent mark + sweep phases run outside this budget (overlapped with mutator).

The <50 ms full-heap-scan fallback (criterion b) decomposes as:

  • Safe-point handshake: 200 μs.
  • Synchronous full-heap mark of 100k XObjects, each with 5-10 ObjectRef properties: ~30 ms (estimate from prefetched dense-array walk on Quest 3 ARM64, ~3 properties/μs sustained).
  • Sweep over 100k entries: ~5 ms (Mark-bit read + entry-flag write per entry).
  • Deferred-destruction enqueue: ~3 ms.
  • Pre-sweep accounting: 200 μs.

Total ~40 ms with 10 ms slack within the 50 ms budget.

5. Write Barriers + GC Root Protocol

5.1 Card-table layout

The card-table is a single contiguous byte array sized to cover the entire XObject heap (allocated at XCoreXObject startup, with the heap-base address fixed at PreStaticInit). Layout:

// Card-table layout (Stage B addendum extension XPACT_XGC_CARDTABLE_LAYOUT_TAG).
namespace XCore::XObject {

inline constexpr size_t kCardSizeBytes = 512;        // 2^9; shift = 9
inline constexpr size_t kCardSizeShift = 9;

// Heap-base address is fixed at XCoreXObject startup. XObject heap is at most
// kMaxXObjectHeapBytes large; the card-table is sized to cover the full max.

The 4 GB max XObject heap aligns with the Quest 3 trainee app's 4 GB total budget (Master Plan §2a Memory budget placeholder row). 5.2 Write-barrier emission

Critical design decision (per spec critical-decisions list, item 3): how do XIL2CPP-transpiled C# writes emit barriers?

C++ writes use the explicit XPACT_GC_STORE(parent, slot, newValue) macro at every reference-storing site. Container code (XPtr, TArray>, TMap with XObject* values, etc.) wraps the macro. User-class C++ code that stores an XObject* directly into a non-container slot (e.g., this->OwnerRef = newOwner;) MUST use the macro — XHT's static analysis pass enforces this at build time (looks for raw assignment of XObject-derived pointers to reflected XPROPERTY slots; emits diagnostic XCoreXObject001 — missing XPACT_GC_STORE on reflected reference slot if found).

C# transpiled writes use the XIL2CPP codegen pattern. Every C# assignment of the form obj.Field = value; where Field is an XObject reference (or contains XObject references in its type tree) lowers to:

// C# source:
//   actor.Owner = newOwner;
//
// XIL2CPP emits (simplified):
{
    XObject** slot = &reinterpret_cast<XActor*>(actor)->Owner;
    XGC_WriteBarrier(reinterpret_cast<void**>(slot), newOwner);
    *slot = newOwner;
}

XIL2CPP recognizes reference-storing assignments through type analysis (the C# field's reflected type is FObjectProperty, FWeakObjectProperty, FStructProperty containing reference, FArrayProperty/FMapProperty/FSetProperty with reference inner, etc.). The codegen pass inserts the barrier emission at the IL-to-C++ lowering stage.

Performance cost of the barrier: ~3-5 cycles per emit (TLS load + branch for SATB check, indexed byte store for card mark). On a frame with 100k reference stores (typical for VFX-heavy training scenarios), barrier cost is ~0.3-0.5 ms. This is within the per-frame budget (90 Hz = 11 ms per frame; barrier is ~3-5% of frame). The cost is the price of generational scan-reduction; the alternative (no barrier, full-heap scan every cycle) would consume far more.

5.3 GC root protocol

The mark phase begins from the root set. The root set has four sources:

  1. Pinned roots in FXObjectArray: any XObject with the kRootPinnedBit set on its FXObjectArrayEntry is unconditionally a root. Set via XGCRoot::AddRoot(XObject*) from native code, cleared via RemoveRoot. Used for: native singletons that must persist (XEngine, XGameInstance), editor-toolwindow held objects, pre-CDO bootstrap.
  2. XGCRootSpans from GC-aware containers: the XGCRootSpan ABI (XCore-4a §5.4) is registered by every GC-aware container's constructor. The collector walks the registered spans at mark phase; each span enumerates its slots and pushes referenced XObjects into the gray queue.
  3. Precise stack roots from XIL2CPP-emitted stack maps: every transpiled C# function emits a stack-map record listing the byte offsets of XObject references in its stack frame (locals + temporaries + arguments). At the safe-point handshake, the collector walks each suspended thread's stack frames, looks up the stack-map for the current PC, and enumerates the live XObject references.
  4. AddReferencedObjects callbacks: for native types that hold XObject references in non-reflected slots (e.g., editor caches, runtime pools), the FClass's lifecycle FakeVTable's AddReferencedObjects slot is invoked. The callback enumerates references via a visitor object provided by the collector.

XGCRoot::AddRoot/RemoveRoot API:

namespace XCore::XObject {

class XGCRoot {
public:
    // Pin an XObject as a GC root. Idempotent: multiple AddRoot calls on the
    // same object are reference-counted; the object stays pinned until the
    // matching number of RemoveRoot calls.
    static void AddRoot(XObject* Object) noexcept;
    static void RemoveRoot(XObject* Object) noexcept;

    // For native code that holds an XObject* as a member but cannot register
    // an XGCRootSpan (because the slot is not an array). The visitor is called
    // synchronously during mark with the slot's current value.
    using FRootVisitor = void(*)(XObject** slot);
    static void RegisterStaticRootVisitor(FRootVisitor visitor) noexcept;
    static void UnregisterStaticRootVisitor(FRootVisitor visitor) noexcept;

    // Iterate every currently-registered root span (collector internal use).
    template <typename V> static void EnumerateAllRootSpans(V&& v) noexcept;

    // Iterate every pinned XObject (collector internal use).
    template <typename V> static void EnumeratePinnedObjects(V&& v) noexcept;
};

} // namespace XCore::XObject

Conservative root registration for non-statically-typed C# containers (per Master Plan §2a Memory/GC row):

List<object> and similar non-statically-typed C# containers can hold XObject references mixed with non-XObject values. The XIL2CPP transpiler cannot statically determine which slots hold XObject references. The discipline:

  • XIL2CPP emits a conservative root-registration scaffold: every slot of the container is treated as a potential XObject* via the XGCRootSpan kind XGCRootKind::Conservative (per XCore-4a XGCDeclarations.h).
  • The collector, when scanning a Conservative root span, validates each candidate in a strict order (Rev 2 per FIX-A-MED-35; NEVER deref before validation):
    1. Heap-range check: candidate address must lie within the XObject heap address range [g_XObjectHeapBase, g_XObjectHeapBase + currentHeapSize).
    2. FXObjectArray index-range check: the candidate's putative InternalIndex (derived from slab + cell math) must be within [1, g_XObjectArray.Num()). Index 0 is the null sentinel.
    3. Entry-bind check: load FXObjectArrayEntry at that index; its Object field must be non-null.
    4. SerialNumber match check: the entry's SerialNumber must match the candidate's putative serial (derived from the entry's bound XObject's SerialNumber field).
    Only after all four checks pass is the candidate treated as a real root. NEVER deref the candidate as XObject* before step 3 succeeds; the candidate may be a spurious value.
  • XIL2CPP emits a build-time warning when a Conservative span appears on a sim-path TU. This is the explicit per-mutation root-register/unregister cost the Master Plan acknowledges.
  • The cost: each Conservative slot is ~10-20 cycles to validate (vs ~2-3 cycles for a precise reference). For a container with 1000 conservative slots scanned per GC cycle, the cost is ~10-20 μs; bursts of conservative scanning can show in the pause budget.

5.4 Precise stack scanning

The XIL2CPP-emitted stack map is a per-function table mapping PC ranges (within the function body) to the byte offsets within the stack frame that hold XObject references at each PC. Format:

// Per-function stack map (emitted alongside the function body).
// Static const data in .rodata; one record per "live range" within the function.
struct alignas(8) FStackMapRecord {
    uint32_t pcRangeBegin;     //  0  +4   byte offset within the function
    uint32_t pcRangeEnd;       //  4  +4   byte offset
    uint16_t numLiveRefs;      //  8  +2
    uint16_t _pad;             // 10  +2
    int32_t  liveRefOffsets[]; // 12 +4*N  byte offsets within the stack frame (negative = below stack-pointer)
};

At safe-point, the collector iterates each thread's stack. For each frame, it locates the FStackMapRecord whose pcRange covers the current return-address-to-callsite distance, and enumerates the liveRefOffsets to find XObject references. Each found reference is pushed onto the gray queue.

Stack-map size budget: typical XIL2CPP-transpiled function has 1-3 live ranges with 2-5 references each — ~30 bytes per function. For a project with 10k transpiled C# functions, stack-map data is ~300 KB. This is a one-time per-binary cost.

5.5 Safe-point handshake protocol

At collection trigger, the GC sets a global flag g_SafePointRequested. Every worker-pool thread + the major named threads check this flag at safe-point insertion points:

  • Every NewObject call (path through the allocator already accesses the flag for the "no NewObject during mark" assertion).
  • Every GC-aware container mutation (TArray::Add of an XPtr, TMap insertion, etc.).
  • Every XIL2CPP-emitted function entry (the compiler inserts the check at function prologue; cost is ~3-5 cycles).
  • Every long loop's back-edge (the compiler inserts the check at backward branches in loops > some-threshold-iterations).

When the flag is set, the thread suspends (parks on a condition variable) until the collector signals "safe-point complete". The collector waits for all threads to suspend before snapshotting roots; typical wait is <200 μs on Win64, <500 μs on Quest 3 ARM64.

Hot-path cost in steady state: when no safe-point is requested, the flag check is one TLS-cached read + one branch (~2 cycles). The branch is statically predicted "not taken" so the cost is near-zero in the steady-state mutator.

5.6 Hot-reload coordination

During XLiveCoding's Phase 2 quiesce window (per Contract Rev 13.7 §7.1, also referenced from XCore-4a §4.2.5), the GC must be in a coherent state. Specifically:

  • No collection cycle may straddle the quiesce window. XLiveCoding signals BeginHotReloadQuiesce(FHotReloadThreadEnumeration), which waits for any in-progress cycle to complete and blocks new cycle starts.
  • During quiesce, write-barriers continue to push to per-thread SATB queues (so post-quiesce collections see consistent state), but the global SATB log drain is paused.
  • XLiveCoding's class-replacement phase (the cascade) calls XCoreXObject::ApplyClassReplacement(OldClass, NewClass) for each replaced FClass; this walks the FXObjectArray for instances of OldClass, rebinds them to NewClass, and triggers re-initialization of any property whose layout has not changed (Master Plan hot-reload commitment: no class-layout changes mid-session; layout-drift check at XLiveCoding Phase 1 pre-commit gate per FIX-A-HIGH-14).
  • After class replacement, XLiveCoding calls FinishHotReloadCascade(FClassReplacementMap), which resumes the SATB log drain and unblocks new cycle starts.

SATB queue bound during quiesce (Rev 2; FIX-A-MED-37 / MAJOR-A30). During hot-reload quiesce, the per-thread SATB queues continue to receive entries from write-barriers (256-entry circular buffer per thread). The global drain is paused. If a per-thread queue fills, the writer thread blocks until quiesce ends. This is bounded by §11 acceptance criterion (e) cascade hot-patch timeout (<120 s nominal / <150 s kill). Memory pressure during quiesce is bounded by:

  • Per-thread queue: 256 entries × 8 bytes (XObject*) = 2 KB per thread.
  • Total on an 8-thread machine (game + render + RHI + audio + 4 worker pool): 16 KB.
  • On a 16-thread machine (Win64 desktop): 32 KB.

Memory pressure during quiesce is negligible (< 64 KB even on the largest target hardware); the bound is set by the cascade timeout, not by memory.

6. Object Handles (XPtr, XWeakPtr, XSoftPtr, XObjectKey)

Four handle types cover the spectrum of XObject reference semantics. Each has a distinct lifetime contract, root-participation rule, and ABI shape.

6.1 XPtr<T> (strong reference)

XPtr<T> is the strong typed pointer. It is a thin wrapper around T* with the following invariants:

  • The XPtr does NOT itself register as a GC root. Rooting is determined by the container the XPtr lives in: an XPtr in a TArray that registers an XGCRootSpan is a root; an XPtr in a stack frame that the XIL2CPP stack-map enumerates is a root; an XPtr in a plain stack frame (un-mapped C++) is NOT a root and the pointee may be collected if no other reference exists.
  • Construction from a raw T* is checked: in Dev, asserts the pointer is a valid live XObject; in Shipping, trusts the caller.
  • Assignment uses XPACT_GC_STORE if the XPtr is inside a reflected slot (the container handles this); raw stack-local XPtr assignments do not emit barriers (no card to mark; stack is not in the XObject heap).
  • Dereference is a raw load; no SerialNumber check (the pointee is alive by contract because the XPtr held a strong reference path through its container).
// XPtr<T>: 8-byte strong typed pointer. Compatible with raw T* layout for
// interop with XHT-emitted reflection metadata (FObjectProperty's stored
// payload is XPtr-shaped).
template <typename T>
class XPtr {
public:
    constexpr XPtr() noexcept : Ptr(nullptr) {}
    constexpr XPtr(std::nullptr_t) noexcept : Ptr(nullptr) {}
    explicit XPtr(T* p) noexcept;            // Dev-checks p is a live XObject
    XPtr(const XPtr&) noexcept            = default;
    XPtr(XPtr&&) noexcept                 = default;
    XPtr& operator=(const XPtr&) noexcept = default;
    XPtr& operator=(XPtr&&) noexcept      = default;
    ~XPtr() noexcept                      = default;

    XPACT_FORCEINLINE T*  Get() const noexcept { return Ptr; }
    XPACT_FORCEINLINE T*  operator->() const noexcept { return Ptr; }
    XPACT_FORCEINLINE T& operator*() const noexcept { return *Ptr; }
    XPACT_FORCEINLINE explicit operator bool() const noexcept { return Ptr != nullptr; }

    XPACT_FORCEINLINE bool operator==(const XPtr& o) const noexcept { return Ptr == o.Ptr; }
    XPACT_FORCEINLINE bool operator!=(const XPtr& o) const noexcept { return Ptr != o.Ptr; }
    XPACT_FORCEINLINE bool operator==(const T* o) const noexcept { return Ptr == o; }
    XPACT_FORCEINLINE bool operator!=(const T* o) const noexcept { return Ptr != o; }

    // Cast helpers (delegating to XObject::CastTo / IsA via the FClass).
    template <typename U> XPtr<U> Cast() const noexcept {
        return Ptr != nullptr ? XPtr<U>(Ptr->template CastTo<U>()) : nullptr;
    }

private:
    T* Ptr;
};

static_assert(sizeof(XPtr<XObject>) == 8, "XPtr ABI lock: 8 bytes (raw-pointer-compatible)");

The static_assert ensures XPtr<T> can be reinterpreted-cast to T* for ABI interop with the reflected FObjectProperty payload. This is load-bearing: XCore-4b's FObjectProperty stores its value as a raw XObject* at the property's offset; consumers (XPropertyEditor, XSerialization, XNetworking) read the slot via *reinterpret_cast<XObject**>(instance + property.Offset). An XPtr<T> in the same slot must read identically.

6.2 XWeakPtr<T> (weak reference)

XWeakPtr<T> is the weak pointer. It does NOT keep its pointee alive and resolves to nullptr if the pointee has been collected. ABI shape: {InternalIndex, SerialNumber} 8-byte handle (matches XCore-4b's FWeakObjectPtr placeholder shape).

// XWeakPtr<T>: 8-byte weak typed pointer. Layout matches XCore-4b's
// FWeakObjectPtr placeholder so FWeakObjectProperty's payload IS an XWeakPtr.
// The 8-byte handle is {int32 InternalIndex; uint32 SerialNumber}.
// Stage B addendum extension XPACT_XWEAKPTR_LAYOUT_TAG covers this.
template <typename T>
class XWeakPtr {
public:
    constexpr XWeakPtr() noexcept : InternalIndex(0), SerialNumber(0) {}
    constexpr XWeakPtr(std::nullptr_t) noexcept : InternalIndex(0), SerialNumber(0) {}
    explicit XWeakPtr(T* p) noexcept;        // captures {p->InternalIndex, p->SerialNumber}
    XWeakPtr(const XWeakPtr&) noexcept            = default;
    XWeakPtr& operator=(const XWeakPtr&) noexcept = default;
    ~XWeakPtr() noexcept                          = default;

    // Resolve: returns the pointee if still alive, else nullptr.
    T* Get() const noexcept;
    // IsValid: faster check, true if pointee is alive without returning the pointer.
    bool IsValid() const noexcept;
    bool IsExplicitlyNull() const noexcept { return InternalIndex == 0; }

    XPACT_FORCEINLINE bool operator==(const XWeakPtr& o) const noexcept {
        return InternalIndex == o.InternalIndex && SerialNumber == o.SerialNumber;
    }
    XPACT_FORCEINLINE bool operator!=(const XWeakPtr& o) const noexcept { return !(*this == o); }

private:
    int32_t  InternalIndex;     //  0  +4   FXObjectArray slot (0 = null)
    uint32_t SerialNumber;      //  4  +4   captured at construction time
};

static_assert(sizeof(XWeakPtr<XObject>) == 8, "XWeakPtr ABI lock: 8 bytes (matches FWeakObjectPtr)");

Get() implementation:

template <typename T>
T* XWeakPtr<T>::Get() const noexcept {
    if (InternalIndex == 0) return nullptr;
    const FXObjectArrayEntry& entry = g_XObjectArray.GetEntry(InternalIndex);
    if (entry.SerialNumber != SerialNumber) return nullptr;     // slot was reused
    XObject* obj = entry.Object;
    if (obj == nullptr) return nullptr;                          // slot is unbound
    if (obj->HasAnyFlags(uint32_t(EObjectFlags::BeginDestroyed))) return nullptr;
    return static_cast<T*>(obj);
}

Get() does NOT acquire a lock; the FXObjectArrayEntry fields are atomic (SerialNumber is updated under the AllocLock at slot release, and the SerialNumber compare uses memory_order_acquire). The cost is ~5-10 ns per call (one indexed load + two compares).

6.3 XSoftPtr<T> (soft path-based reference)

XSoftPtr<T> is the soft pointer: a path-based reference that resolves on demand. The path is an FSoftObjectPath-shape from XCore-4b's FSoftObjectProperty. It does NOT register as a GC root (the pointee can be unloaded; resolution loads on demand).

Use case: scenario authoring. A scenario references an XActor by path; the path is serialized; the actor itself is not loaded until the scenario unloads or until the user explicitly resolves the reference.

// XSoftPtr<T>: path-based soft reference. Larger than XPtr/XWeakPtr because
// it carries the path string; typical sizeof varies with path length.
template <typename T>
class XSoftPtr {
public:
    XSoftPtr() noexcept = default;
    explicit XSoftPtr(const FSoftObjectPath& path) noexcept;
    explicit XSoftPtr(T* p) noexcept;            // captures the asset path from p's Outer chain

    // Resolve: loads the asset if not already loaded; returns nullptr on miss.
    T* Resolve() noexcept;
    // Resolve without loading; returns nullptr if not loaded.
    T* GetIfLoaded() const noexcept;

    const FSoftObjectPath& GetPath() const noexcept { return Path; }
    bool IsNull() const noexcept { return Path.IsNull(); }

    XPACT_FORCEINLINE bool operator==(const XSoftPtr& o) const noexcept { return Path == o.Path; }
    XPACT_FORCEINLINE bool operator!=(const XSoftPtr& o) const noexcept { return !(*this == o); }

private:
    FSoftObjectPath Path;     // path is an FName + sub-path FString (variable size)
};

The actual ABI size depends on FSoftObjectPath's layout (typically 8 + FString = ~24-32 bytes depending on the path string's interning). XSoftPtr is NOT in the ABI-lock set because its size is necessarily variable; FSoftObjectProperty's storage in reflected slots is its own bounded payload.

6.4 XObjectKey (stable identity across hot-reload)

Critical design decision (per spec critical-decisions list, item 5): how does XObjectKey survive a class replacement?

XObjectKey is the {InternalIndex, SerialNumber} 8-byte handle, ABI-compatible with XWeakPtr but used for stable identity rather than weak-resolve semantics. The key difference: XObjectKey survives a hot-reload class replacement because the InternalIndex slot is preserved across the replacement.

The rebind protocol:

  1. Pre-hot-reload: an XObjectKey holds {idx=42, serial=7}. The FXObjectArray entry at idx 42 has Object = oldInstance (type oldClass), SerialNumber = 7.
  2. Hot-reload cascade replaces oldClass with newClass (per §9).
  3. During cascade, the FXObjectArray entry at idx 42 is rebound: the old instance is destructed in-place, a new instance of newClass is placement-new constructed at the same address (assuming compatible layout per the hot-reload commitment: no class-layout changes mid-session), and the entry's Object pointer remains the same address. SerialNumber is NOT bumped because the instance is logically the same.
  4. Post-hot-reload: XObjectKey {idx=42, serial=7} resolves to the rebound instance at the same address. The instance's FClass* now points at newClass.

The key difference from XWeakPtr: XWeakPtr's Get() returns nullptr if the slot has been logically released and re-acquired by a different object (SerialNumber bump). XObjectKey's Get() returns the rebound instance even after a class replacement because the SerialNumber is preserved across hot-reload.

When XObjectKey returns nullptr: only when the object was actually destroyed (the FXObjectArray slot was released and re-acquired by a different object, which bumps SerialNumber). A hot-reload class replacement does not destroy the object; it rebinds the FClass pointer.

// XObjectKey: 8-byte handle, ABI-compatible with XWeakPtr.
// Stage B addendum extension XPACT_XOBJECTKEY_LAYOUT_TAG covers this.
class XObjectKey {
public:
    constexpr XObjectKey() noexcept : InternalIndex(0), SerialNumber(0) {}
    explicit XObjectKey(const XObject* o) noexcept
        : InternalIndex(o ? o->GetInternalIndex() : 0),
          SerialNumber (o ? o->GetSerialNumber()  : 0) {}

    // Resolve to live XObject if still extant (including post-hot-reload rebound instances).
    XObject* Resolve() const noexcept;

    XPACT_FORCEINLINE bool IsNull() const noexcept { return InternalIndex == 0; }
    XPACT_FORCEINLINE bool operator==(const XObjectKey& o) const noexcept {
        return InternalIndex == o.InternalIndex && SerialNumber == o.SerialNumber;
    }
    XPACT_FORCEINLINE bool operator!=(const XObjectKey& o) const noexcept { return !(*this == o); }

    // Hash for TMap<XObjectKey, V> usage.
    friend uint64_t GetTypeHash(const XObjectKey& k) noexcept {
        return XCore::Hash::XXH3(&k, 8, 0);
    }

private:
    int32_t  InternalIndex;
    uint32_t SerialNumber;
};

static_assert(sizeof(XObjectKey) == 8, "XObjectKey ABI lock: 8 bytes");

Note that XObjectKey and XWeakPtr have the same byte layout. They differ only in the resolution semantics and the API surface. They are NOT type-interchangeable (no implicit conversion); each is used in distinct call sites. Note also (per FIX-A-HIGH-10 / UE-VER-3): the XObjectKey 8-byte layout {InternalIndex, SerialNumber} is a UE-faithful mirror of UE's FObjectKey (ObjectKey.h:18-60). The genuine divergence from UE is XPact's stable XClass identity across hot-reload via XLiveCoding's versioned-vtable + stable-exported-name ABI — UE has only WITH_EDITOR-only SetClass at UObjectBase.h:486.

6.5 XStrongPtr<T> (Rev 2; FIX-A-MIN-38 / ALT-HANDLE-2)

XStrongPtr<T> is the non-container strong hold equivalent to UE's TStrongObjectPtr (UE-VER-4 / FIX-A-HIGH-11). It uses the FXObjectArrayEntry's refcount slot (8-byte StateBits has a refcount sub-field; per-entry refcount is incremented at construction and decremented at destruction). The GC walk treats objects with non-zero refcount as root-pinned for the duration of the hold. Per Subagent A: UE has TStrongObjectPtr + per-entry refcount mechanism (UObjectArray.h AddRef/ReleaseRef on FlagsAndRefCount). XPact's per-slot rooting concept is UE-faithful; the novel piece (per FIX-A-HIGH-11) is XPact's XGCRootSpan byte-stride range-span shape + Conservative-kind opt-in build-time warning, not this XStrongPtr.

// XStrongPtr<T>: 8-byte non-container strong reference. Increments the FXObjectArrayEntry's
// refcount at construction; decrements at destruction; the GC walk treats refcount>0 entries
// as root-pinned (per the kRootPinnedBit equivalent on StateBits).
template <typename T>
class XStrongPtr {
public:
    constexpr XStrongPtr() noexcept : Ptr(nullptr) {}
    explicit XStrongPtr(T* p) noexcept;                       // increments refcount on p's entry
    XStrongPtr(const XStrongPtr&) noexcept;                   // increments refcount
    XStrongPtr& operator=(const XStrongPtr&) noexcept;
    XStrongPtr(XStrongPtr&&) noexcept;                        // moves; no refcount change
    XStrongPtr& operator=(XStrongPtr&&) noexcept;
    ~XStrongPtr() noexcept;                                    // decrements refcount

    XPACT_FORCEINLINE T*  Get() const noexcept { return Ptr; }
    XPACT_FORCEINLINE T*  operator->() const noexcept { return Ptr; }
    XPACT_FORCEINLINE T& operator*() const noexcept { return *Ptr; }
    XPACT_FORCEINLINE explicit operator bool() const noexcept { return Ptr != nullptr; }

    void Reset() noexcept;                                    // decrements + sets nullptr

private:
    T* Ptr;
};

static_assert(sizeof(XStrongPtr<XObject>) == 8, "XStrongPtr ABI lock: 8 bytes");

Use case: editor tooling, third-party C++ code, async I/O work items that need to hold a strong reference without being a container or registering an XGCRootSpan. UE pattern parallel: TStrongObjectPtr<UObject> used by AsyncTask, AssetRegistry, level-streaming.

6.7 Phantom-ptr / alternative architecture note (Rev 2; FIX-A-MIN-55)

Subagent B's review flagged that the handle family does not include a "phantom pointer" abstraction (a handle that triggers a callback when the pointee becomes unreachable, equivalent to Java's PhantomReference). XPact's stance: phantom-ptr is intentionally out of scope. Use case mapping: the editor's "ref-count-to-zero-then-delete" pattern is satisfied by XStrongPtr; the loader's "object reachable but pre-PostLoad" gate is satisfied by RF_NeedPostLoad; the networking layer's "object replicated but local instance pending" gate is satisfied by RF_NeedLoad. Adding a 5th handle type for phantom-ref would over-engineer the surface; revisit if a real use case emerges post-MVP.

7. Reflection Runtime Integration with FClass

7.1 XObject derives from FClass

Every XObject carries a const FClass* ClassPrivate at offset 0. The FClass is constructed at module-init by XHT-generated .gen.cpp code: each XCLASS-declared type emits a constinit const FClass in .rodata plus a Z_Construct_FClass_* function that calls XReflectionRuntime::RegisterClass at module load.

XCoreXObject's role:

  • Populates FClass::ClassConstructorFn (the function called from NewObject's step 3).
  • Populates FClass::ClassDefaultObject atomic slot (the CDO).
  • Populates the new FClass::LifecycleTable pointer added by this spec (Contract Rev 13.9 micro-bump).
  • Populates FStruct::ObjectRefProperties dense TArray at FClass::Link time by walking the FProperty chain and probing each property's DispatchTable->ContainsObjectReferenceFn slot.
  • Calls XReflectionRuntime::RegisterClass(&XActor_Class) from the per-module init aggregator.

7.2 FClass::Link — the post-registration finalization

After XReflectionRuntime::RegisterClass is called, the FClass's runtime-derived fields must be populated. This is the Link phase (mirrors UE's UClass::Link). XCoreXObject implements Link as a free function called from RegisterClass:

namespace XCore::XObject {

void LinkClass(FClass* cls) {
    // 1. Compute PropertyLink + DestructorLink + PostConstructLink chains
    //    by walking ChildProperties from most-derived to base.
    //    (This is XCore-4b reflection setup; XCoreXObject calls into it.)
    cls->PropertyLink = ComputePropertyLink(cls);
    cls->DestructorLink = ComputeDestructorLink(cls);
    cls->PostConstructLink = ComputePostConstructLink(cls);

    // 2. Populate FStruct::ObjectRefProperties (FIX-13 dense array, slow-path inspection)
    //    by probing each FProperty's DispatchTable->ContainsObjectReferenceFn slot.
    //    The `encountered` TArray is caller-allocated per-walk per FIX-A-MIN-42 / MAJOR-A13.
    cls->ObjectRefProperties.Empty();
    TArray<const FStructProperty*> encountered;
    for (const FProperty* p = cls->PropertyLink; p != nullptr; p = p->PropertyLinkNext) {
        const auto* fakeVT = p->DispatchTable;
        const auto containsFn = reinterpret_cast<FProperty::ContainsObjectReferenceFn>(
            fakeVT->Slots[uint32_t(ESlot::ContainsObjectReference)]);
        encountered.Empty();   // caller clears between walks
        if (containsFn != nullptr && containsFn(encountered)) {
            cls->ObjectRefProperties.Add(const_cast<FProperty*>(p));
        }
    }

    // 3. Resolve FStruct::RefSchema pointer (Rev 2; UE-MISS-1 / FIX-A-CRIT-8 fast-path).
    //    XHT emits the RefSchema vector at compile time in .rodata; LinkClass merely
    //    verifies the pointer is non-null and the vector's terminator opcode is well-formed.
    //    (See §7.4 for the RefSchema opcode design.)
    XPACT_CHECK(cls->RefSchema != nullptr);
    XPACT_CHECK(cls->RefSchema->TerminatorIsWellFormed());

    // 4. Populate ClassReps (FRepRecord array) by walking PropertyLink and
    //    expanding ArrayDim > 1 properties into multiple FRepRecord entries.
    //    (XHT pre-emits ClassReps as constinit per FIX-R2-LOW-8; Link verifies
    //    the constinit length matches.)
    VerifyAndLinkClassReps(cls);

    // 5. Optionally construct the CDO (eager vs lazy policy; see §8).
    if (cls->HasAnyClassFlags(EClassFlags::EagerCDO)) {
        FClassDefaultObjectFactory::ConstructCDO(cls);
    }

    // 6. Register the class in the per-class IsA acceleration tables
    //    (cast-flag bitmask propagation through SuperStruct chain).
    PropagateCastFlags(cls);
}

7.3 Slow-path: FStruct::ObjectRefProperties dense TArray (for debugger / introspection)

The dense ObjectRefProperties TArray (XCore-4b FIX-13) is retained as the slow-path inspection surface. Consumers: debugger (XEditor.PropertyInspector reads ObjectRefProperties to list reference fields), introspection (gameplay code that wants to enumerate "which properties hold XObject references"). The fast-path GC walk uses the schema vector (§7.4); the slow-path inspector uses ObjectRefProperties. Both live on FStruct; they are not redundant — they serve different consumers.

7.4 Fast-path: schema-vector GC walker (Rev 2; UE-MISS-1 / FIX-A-CRIT-8)

UE 5.x uses a schema-driven reference collection in FastReferenceCollector.h + GarbageCollectionSchema.h — each UClass owns an FSchemaOwner ReferenceSchema built once at class registration. The schema is a packed array of EMemberType opcodes (Reference / ReferenceArray / StructArray / StridedArray / StructSet / FieldPath / FieldPathArray / Optional / DynamicallyTypedValue / ARO / SlowARO / MemberARO). The GC interpreter walks the schema, dispatching each opcode to the matching reference-collector helper. This replaced the older FProperty pointer-chase walk in UE 5.x — per Subagent A's analysis, the schema vector is “the single largest perf miss” Rev 1 had relative to UE 5.x.

Rev 2 adopts the schema-vector approach. XHT emits the packed opcode vector at compile time per XCLASS, encoding the GC-ref properties as offset+stride+kind triples. The GC walk inner loop iterates opcodes (cache-coherent), reads offset + stride + kind directly without FProperty pointer-chase.

// Rev 3 (FIX-N-R2-10): cross-compiler prefetch abstraction. Defined in XCore-4a
// macros header (or in XCoreXObject's gen-h if XCore-4a's header is unavailable
// at the call site). Falls through to no-op on unknown compilers; on supported
// ones, drives the platform's prefetch intrinsic at L1-hot temporal-locality 3.
#if defined(_MSC_VER)
  #define XPACT_PREFETCH(ptr) _mm_prefetch((const char*)(ptr), _MM_HINT_T0)
#elif defined(__clang__) || defined(__GNUC__)
  #define XPACT_PREFETCH(ptr) __builtin_prefetch(ptr, 0, 3)
#else
  #define XPACT_PREFETCH(ptr) ((void)0)
#endif

// Rev 3 fast-path mark-phase per-object scan. Replaces Rev 1's FProperty pointer-
// chase loop with cache-coherent opcode iteration. Targets 4000+ refs/ms on Quest 3
// (vs Rev 1's 3000 refs/ms target with FProperty chase).
void ScanObjectReferences_FastPath(XObject* obj, FXGrayQueue& gray) {
    const FClass* cls = obj->GetClass();
    const FXObjectRefSchema* schema = cls->RefSchema;
    const FXObjectRefSchemaOp* ops = schema->Ops;
    const uint32_t numOps = schema->NumOps;
    uint8_t* instance = reinterpret_cast<uint8_t*>(obj);

    for (uint32_t i = 0; i < numOps; ++i) {
        // Prefetch i+4 ahead (deeper than the FProperty walk because opcodes are smaller).
        // Rev 3 (FIX-N-R2-10): cross-compiler prefetch via XPACT_PREFETCH macro
        // defined in XCore-4a macros header (MSVC -> _mm_prefetch; Clang/GCC -> __builtin_prefetch;
        // otherwise no-op). Earlier Rev 2 had a bare __builtin_prefetch which would fail to compile
        // on MSVC.
        if (i + 4 < numOps) {
            XPACT_PREFETCH(&ops[i + 4]);
        }

        const FXObjectRefSchemaOp& op = ops[i];
        switch (op.Op) {
            case EXObjectRefSchemaOp::Object: {
                XObject** slot = reinterpret_cast<XObject**>(instance + op.Offset);
                MarkRefIfUnmarked(*slot, gray);
                break;
            }
            case EXObjectRefSchemaOp::ArrayOfObject: {
                ScanArrayOfObject(instance + op.Offset, gray);
                break;
            }
            case EXObjectRefSchemaOp::StridedArrayOfObject: {
                ScanStridedArray(instance + op.Offset, op.ArrayDim, op.StrideBytes, gray);
                break;
            }
            case EXObjectRefSchemaOp::Struct: {
                ScanNestedStruct(instance + op.Offset, op.NestedSchema, gray);
                break;
            }
            // ... other opcodes handled similarly
            case EXObjectRefSchemaOp::ARO: {
                DispatchAROCallback(obj, gray);
                break;
            }
            case EXObjectRefSchemaOp::Terminator:
                goto done;
            default:
                XPACT_UNREACHABLE();
        }
    }
    done:;

    // Outer-chain walk (unchanged from Rev 1; the Outer is part of the live graph).
    if (obj->Outer != nullptr) {
        MarkRefIfUnmarked(obj->Outer, gray);
    }
}

Per Subagent A: this is “the single largest perf miss” Rev 1 had relative to UE 5.x. Rev 2 closes it. The performance critically depends on the schema vector being in .rodata (.rodata reads are L2-cached for the duration of the GC walk; the 24-byte opcode size means each cache line (64 B) holds 2-3 opcodes), and the FXObjectArray entry's cache locality (32-byte entries, two per cache line).

7.5 FindClass on deserialize

When XSerialization loads an XObject from disk, the archive contains the FClass's name (FName); XSerialization calls XReflectionRuntime::FindClass(name) to resolve the live FClass*, then calls XCoreXObject's NewObject<XObject>(outer, name, RF_NeedLoad) with the resolved FClass to construct the instance. The post-construction Serialize call (dispatched via the FClass's lifecycle FakeVTable with the FArchiveContext void* per FIX-A-HIGH-13) fills in the property values from the archive.

8. CDO Pattern

8.1 Critical design decision: when does the CDO get built?

Per spec critical-decisions list, item 4: CDO construction order.

The CDO (Class Default Object) is the per-class template instance whose property values are the defaults for any NewObject of that class. UE constructs all CDOs at engine startup (during the class-registration phase). This is simple but slow: a typical UE game registers 10k-50k classes at boot, and constructing each CDO takes ~50-200 μs, leading to a 1-10 second startup hit.

XPact uses a per-class policy:

  • Eager CDO (declared via XCLASS(MyType, MyBase, EagerCDO)): the CDO is constructed at FClass::Link time, during module DLL load. Used for classes whose CDO is consumed by FClass::Link itself (i.e., the property defaults are needed for the initial property-link calculation). This is the minority; typically only engine-tier classes. Rev 3 ordering (per FIX-H-R2-6): EagerCDO construction is deferred to a PostStaticInit-time linker walk, NOT done at static-init time. See §8.1.1 below.
  • Lazy CDO (default; no annotation needed): the CDO is constructed on the first NewObject call for that class, OR on the first XPropertyEditor query for default values, OR on the first XSerialization save (which needs the default to determine which properties differ from default and need persisting). The construction happens under a per-class atomic CAS on FClass::ClassDefaultObject to ensure thread-safety.

Rationale: editor cold-start ≤ 15 s on 1000-asset project (Foundation Prototype criterion (i)) demands aggressive lazy-load. Eager CDO construction was UE's well-known editor-startup hot spot; lazy is the correct fix per Prime Directive.

8.1.1 Immutable-CDO default + EagerCDO PostStaticInit ordering (Rev 2 + Rev 3 per FIX-H-R2-6)

The CDO is immutable post-construction. FClass::DefaultObject is std::atomic<const XObject*> (not std::atomic<XObject*>). Mutating a CDO at runtime is a bug; the type-system enforces it via the const XObject* accessor + the compile-time const FClass. UE's experimental UE_WITH_IMMUTABLE_CDO path is XPact's default.

Rationale: editor + delta-serialization + replication reconciliation all read the CDO concurrently. Mutating it would require locking; immutability eliminates the race. UE 5.6+ has been moving in this direction; XPact ships the destination state from day one.

Hot-reload note: CDO replacement is the only operation that "modifies" the CDO; it does so via an atomic pointer swap (the old CDO is retired to the deferred-destruction queue; the new CDO is published atomically). See §9.3.

EagerCDO + PostStaticInit ordering (Rev 3 per FIX-H-R2-6). The Rev 2 design had a subtle bootstrap ordering bug: constinit const FClass instances are created at static-init time (pre-EInitPhase ladder), but the NewObject entry path asserts XPACT_CHECK(EngineInitPhase() >= EInitPhase::PostStaticInit). If an EagerCDO class's Z_Construct_FClass_* function (in the module DLL's static-init phase) tries to construct the CDO via NewObject<CDO>, the assert fires and the engine aborts before reaching main(). Rev 3 resolves this with the following ordering discipline:

  1. Static-init time (TU initializers): the Z_Construct_FClass_* functions run for every reflected class. They register the FClass with XReflectionRuntime AND call XCoreXObject's LinkClass for the structural setup (PropertyLink computation, ObjectRefProperties population, RefSchema verification). For EagerCDO-flagged classes, LinkClass queues the CDO-construction request onto a deferred list (one global TArray<const FClass*> g_PendingEagerCDOs) instead of calling NewObject immediately.
  2. EInitPhase::PreStaticInit: XCore-4a's FMemory::__Init() runs. No XCoreXObject work yet.
  3. EInitPhase::PostStaticInit: XCoreXObject's __Init() runs — brings up the XObject heap, the FXObjectArray, the collector. After heap is ready, XCoreXObject walks g_PendingEagerCDOs and constructs each queued CDO via the standard NewObject path (now safe because the phase gate has crossed). The order of construction within the list is monotonic by registration order (which is itself deterministic per Master Plan TU-init policy).

This is Option A from the FIX-H-R2-6 analysis. The alternative (Option B — EagerCDO restricted to plugin/Studio/Project modules loaded after PostStaticInit) was rejected because the engine itself has at least one EagerCDO requirement (the transient package + bootstrap singletons) and forcing those into dynamic-load mode is awkward. The deferred-PostStaticInit walk is the correct trade-off per Prime Directive: zero NewObject calls at static-init time, deterministic CDO order, no ordering surprises.

Foundational classes opt-out (Rev 2 FIX-A-HIGH-20 reaffirmed): XObject, XStruct, XClass, XInterface, XEnum use EClassFlags::Intrinsic and bypass normal CDO construction entirely. Their FClass instances live in .rodata with the FClass header pre-populated by XHT; they are hand-constructed during XCoreXObject::__Init() at PostStaticInit boundary BEFORE the g_PendingEagerCDOs walk fires. Intrinsic classes' CDOs are themselves Intrinsic-allocated (they sit in .rodata, not in the XObject heap; their InternalIndex is a sentinel negative value indicating "not in FXObjectArray").

Acceptance gate addition (Rev 3 per FIX-H-R2-6): X-INIT-EAGER — test that an EagerCDO class's CDO is constructed exactly once, at PostStaticInit, after the heap is up but before any user code runs. Catches the bootstrap-ordering bug at first NewObject call from EagerCDO Z_Construct path.

8.2 Lazy CDO construction

namespace XCore::XObject {

class FClassDefaultObjectFactory {
public:
    // Returns the CDO, constructing on first call. Thread-safe.
    static XObject* GetOrConstructCDO(const FClass* cls);

    // Force eager construction (called from FClass::Link for EagerCDO classes).
    static XObject* ConstructCDO(const FClass* cls);

    // Discard and rebuild (used during hot-reload class replacement; see §9).
    static void RebuildCDO(FClass* cls);
};

XObject* FClassDefaultObjectFactory::GetOrConstructCDO(const FClass* cls) {
    XObject* existing = cls->ClassDefaultObject.load(std::memory_order_acquire);
    if (existing != nullptr) {
        return existing;
    }

    // Construct under a per-class lock to ensure single construction.
    static FCriticalSection s_ConstructionLock;
    FScopedLock lock(s_ConstructionLock);

    // Re-check after lock (double-checked locking pattern).
    existing = cls->ClassDefaultObject.load(std::memory_order_acquire);
    if (existing != nullptr) {
        return existing;
    }

    // Construct the CDO. The Outer is the "transient package" sentinel; the
    // Name is "Default__<ClassName>"; flags include RF_ClassDefaultObject.
    XObject* cdo = NewObject<XObject>(
        g_TransientPackage,
        ComposeCDOName(cls->NamePrivate),
        EObjectFlags::ClassDefaultObject | EObjectFlags::MarkAsRootSet);

    // Publish atomically.
    const_cast<FClass*>(cls)->ClassDefaultObject.store(cdo, std::memory_order_release);
    return cdo;
}

} // namespace XCore::XObject

The CDO is itself pinned in the GC root set (RF_MarkAsRootSet flag): a CDO is never collected during normal operation. Hot-reload class replacement is the only time a CDO is destroyed and rebuilt.

8.3 CDO consumers

  • NewObject: copies the CDO's property values into the new instance during step 3 (the FClass's ClassConstructorFn handles this).
  • XPropertyEditor: the editor's property-inspector reads default values from the CDO when displaying "Reset to Default" affordances or when comparing instance values against defaults.
  • XSerialization: the saver compares each instance property against the CDO's value; only differing properties are persisted (the "delta serialization" optimization).
  • XNetworking: replication reconciliation uses CDO values for the "factory defaults" baseline.

8.4 FXObjectInitializer + Default Sub-objects (DSO) (Rev 2; FIX-A-HIGH-12 / UE-MISS-2)

UE's pattern (UObjectGlobals.h:1315-1346 + UObjectGlobals.h:1387-1419) uses FObjectInitializer as a destructor-driven finalization construct. The C++ class constructor body calls Initializer.CreateDefaultSubobject<T>(Name) to register sub-objects with stable names. The destructor ~FObjectInitializer triggers PostInitProperties on the just-constructed object. NewObject<T>(Outer, Name, Flags) creates the FObjectInitializer on stack, constructs T (T's ctor runs CreateDefaultSubobject calls), then ~FObjectInitializer fires PostInitProperties.

Rev 2 mirrors this UE pattern. The FXObjectInitializer is the destructor-driven construct; CreateDefaultSubobject is the construction-time API; FObjectInstancingGraph (mirroring UE's FObjectInstancingGraph) handles archetype-aware reconstruction at deserialize.

// Rev 2: FXObjectInitializer. Stack-allocated by NewObject path (§3.5).
// Threaded through ClassConstructorFn so the user-class constructor body can call
// CreateDefaultSubobject. Destructor fires PostInitProperties.
class FXObjectInitializer {
public:

    ~FXObjectInitializer() noexcept;       // fires PostInitProperties; non-throwing

    // stable name. The sub-object's Outer is *this object*, its name is the
    // provided FName, its flags include DefaultSubObject.

    T* CreateDefaultSubobject(FName SubobjectName, EObjectFlags Flags = EObjectFlags::None) noexcept;

    // Used when the type T is not known at compile time (rare, but supported for

                                     EObjectFlags Flags = EObjectFlags::None) noexcept;

    template <typename T> void SetPropertyValue(const FProperty* prop, const T& value);

    XObject*               TargetObject;
    const FClass*          ClassDescriptor;
    XObject*               OuterAtConstruction;
    FName                  NameAtConstruction;
    FObjectInstancingGraph InstancingGraph;   // archetype-aware sub-object tree (UE-faithful)
    bool                   bPostInitFired = false;   // Rev 3 (FIX-M-R2-5): wired into ~FXObjectInitializer for idempotency
};

// Rev 3 (FIX-M-R2-5): ~FXObjectInitializer wires bPostInitFired for idempotency.
// Inheritance-chain ctors pass `const FXObjectInitializer& Initializer` down by
// const-ref; the most-derived initializer's destructor is the canonical PostInitProperties
// trigger. The flag ensures multiple Initializer destructor firings (e.g., a copy
// stored elsewhere, an explicit Initializer.Reset() call, etc.) don't double-fire
// PostInitProperties. PostInitProperties is dispatched via the FClass lifecycle
// FakeVTable (the FakeVTable's PostInitProperties slot's signature is `void(XObject*)`).
inline FXObjectInitializer::~FXObjectInitializer() noexcept {
    if (bPostInitFired) {
        // Already fired (e.g., the inheritance chain's leaf initializer already triggered).
        return;
    }
    bPostInitFired = true;
    if (TargetObject != nullptr && ClassDescriptor != nullptr &&
        ClassDescriptor->LifecycleTable != nullptr) {
        const uint32_t kPostInitBit = 1u << uint32_t(EXObjectLifecycleSlot::PostInitProperties);
        if ((ClassDescriptor->LifecycleTable->Capabilities & kPostInitBit) != 0) {
            auto* postInitFn = reinterpret_cast<void(*)(XObject*)>(
                ClassDescriptor->LifecycleTable->Slots[
                    uint32_t(EXObjectLifecycleSlot::PostInitProperties)]);
            postInitFn(TargetObject);
        }
    }
}

Sub-object templating: CDO sub-objects are deep-copied for non-CDO instances unless overridden.

The placement-new call within the implementation reads new (InstancePtr) ClassType(Initializer); the user-class constructor's signature must accept the const-ref to compile.

9. Hot-Reload Survival

9.1 Pointer stability vs identity stability

XCoreXObject distinguishes two kinds of stability:

  • Pointer stability for object lifetime: the XObject*'s value (the address in memory) does not change from NewObject to FinishDestroy. This is the non-moving GC commitment; XPtr<T> relies on it.
  • Identity stability across hot-reload: an XObjectKey (or an XWeakPtr) resolves to the "same logical object" across a downstream module's hot-reload, even if the FClass* is replaced. This is the XObjectKey rebind protocol from §6.4.

The two are independent: a hot-reload class replacement preserves identity (XObjectKey resolves) but may or may not preserve the pointer value (it does, in MVP, because XPact's hot-reload commitment forbids class-layout changes mid-session, so the same memory address remains a valid instance).

9.2 Cascade hot-patch protocol

XLiveCoding orchestrates the cascade. The protocol involves XCoreXObject as follows. Layout-drift check moved (Rev 2 per FIX-A-HIGH-14): the layout-drift check is now performed at XLiveCoding's Phase 1 pre-commit gate, before BeginHotReloadQuiesce. XCoreXObject assumes any patch reaching FinishHotReloadCascade has cleared the upstream layout check. Patches with layout drift are rejected at Phase 1 (the close/reopen flow is required; FIX-A-HIGH-17).

  1. XLiveCoding signals BeginHotReloadQuiesce(FHotReloadThreadEnumeration). XCoreXObject quiesces the explicitly-enumerated thread set (Rev 2 per FIX-A-HIGH-14; Rev 3 extension-hook discipline per FIX-M-R2-9 below):
    • Game thread: parked at frame boundary.
    • Render thread: parked after pending RenderCommand flush.
    • RHI thread: parked after pending GPU fence wait.
    • Audio thread: parked after audio mixer flush.
    • Loading threads (async asset I/O workers): parked at next sleep point.
    • Worker-pool threads: each worker drains its queue then parks.
    • GC marker thread: completes in-progress cycle then parks.
    • PSO compile threads: parked at next sleep point.
    • Asset workers (texture-streaming, mesh-streaming): parked at next sleep point.
    • Audio mixer: parked after sample-frame flush.
    Extension-hook discipline (Rev 3 per FIX-M-R2-9). Future engine systems beyond the foundation set (XAutomationTool, XBuildPatchTool, XCloudPersistence, etc.) need to participate in the hot-reload quiesce without forcing a spec edit for each new addition. The hot-reload quiesce thread-set is registered via: 
    // Rev 3 (FIX-M-R2-9) extension hook on XLiveCoding's registry.
namespace XLiveCoding {
    void RegisterThreadRole(FName RoleName,
                             void(*ParkHook)(),
                             void(*UnparkHook)()) noexcept;
    void UnregisterThreadRole(FName RoleName) noexcept;
} // namespace XLiveCoding
    XCoreXObject pre-registers the 10 core roles enumerated above (GameThread, RenderThread, RHIThread, AudioThread, AudioMixerThread, LoadingThread, WorkerPoolThread, GCMarkerThread, PSOCompileThread, AssetWorkerThread). Plugins can extend the parkable set at module-load time by calling XLiveCoding::RegisterThreadRole; the registered ParkHook fires during quiesce, the UnparkHook fires when the cascade completes. The hook contract: the ParkHook must drain its system's work queue, set the system to a quiescent state, and signal completion via the standard quiesce-completion API; the UnparkHook restores normal operation. The framework keeps Rev 3's enumeration intentionally complete for the foundation (so the core systems' quiesce is testable now), while supporting forward-only extension without spec edit. Additionally, XCoreXObject:
    • Waits for any in-progress GC cycle to complete.
    • Blocks new GC cycles from starting.
    • Pauses the SATB log drain (per-thread SATB queues continue to receive entries; see §5.6).
    • Quiesces the FXObjectArray AllocLock (no new ReserveSlot / ReleaseSlot during cascade).
    Fires OnHotReloadStart delegate (FIX-A-MIN-44).
  2. XLiveCoding loads the new module DLL. The new DLL's .init.gen.cpp aggregator calls XReflectionRuntime::RegisterClass(&NewClass) for each new FClass. The new FClass coexists temporarily with the old FClass.
  3. XLiveCoding identifies the replaced class set: for each old FClass that the new module replaces, XLiveCoding constructs an FClassReplacement {OldClass, NewClass} entry and calls XCoreXObject::ApplyClassReplacement(OldClass, NewClass).
  4. ApplyClassReplacement:
    • Walks the FXObjectArray for instances whose FClass == OldClass.
    • For each instance, rebinds ClassPrivate = NewClass (atomic store).
    • The new class's property layout must match the old's exactly (verified by XLiveCoding's Phase 1 pre-commit gate per FIX-A-HIGH-14; XCoreXObject does NOT re-check at this point). Rev 2 removes the additive-property branch (FIX-A-HIGH-16): if new class has properties old class didn't, the layout-drift check at XLiveCoding Phase 1 has rejected the patch; that code path is unreachable here.
    • The XObjectKey for each instance remains valid (InternalIndex + SerialNumber unchanged).
    • Per-FClass sub-pool rebind in FXObjectAllocator (per FIX-A-MIN-40 §3.6).
    • Fires OnClassReplaced(FClassReplacementContext) delegate per FIX-A-MED-33 (XNetworking, XCoreDelegates listeners receive notification).
  5. XLiveCoding signals FinishHotReloadCascade(FClassReplacementMap). XCoreXObject:
    • Resumes the SATB log drain.
    • Unblocks new GC cycles.
    • Releases the FXObjectArray AllocLock.
    • Resumes the quiesced thread set (game / render / RHI / audio / loading / worker-pool / GC marker / PSO compile / asset workers / audio mixer).
    • Triggers a deferred GC cycle to reclaim any objects that are now unreachable post-cascade (e.g., temporary objects from the old module that the new module doesn't reference).
    • Fires OnHotReloadComplete delegate.

Reinstancer fallback (Rev 2; FIX-A-HIGH-17 / ALT-HOTRELOAD-2). If layout drift is detected at XLiveCoding's Phase 1 pre-commit gate, the patch is REJECTED. There is no in-place reconstruction with layout change. UE's FBlueprintCompileReinstancer pattern (reallocate at new size + redirect references) is rejected by XPact because:

  • The non-moving GC commitment (§1.3) forbids the “reallocate at new size” step — the XObject pointer must not move.
  • The XObjectKey rebind protocol (§6.4) preserves identity only when the underlying address is preserved.
  • The Master Plan hot-reload commitment locks “no class-layout changes mid-session”.

XPact's only path for layout-changing edits is the close-and-reopen flow (the user saves work, the editor closes, recompiles, reopens with the new layout). XLiveCoding's Phase 1 gate enforces this by rejecting layout-drift patches with a clear message: “Property layout changed; close and reopen the editor.” Fires OnHotReloadAbort delegate.

9.3 CDO replacement during hot-reload

The CDO must be re-constructed against the new FClass. FClassDefaultObjectFactory::RebuildCDO(cls):

  • Marks the existing CDO with EObjectFlags::BeingReplaced.
  • Constructs the new CDO via the standard lazy path against the new FClass.
  • Atomically swaps cls->ClassDefaultObject to point at the new CDO.
  • Marks the old CDO for destruction (it enters the deferred-destruction queue at the next GC cycle).

9.4 Single-method hot-patch

For a single-method change (the <30s cascade-free hot-patch from Foundation Prototype criterion (d)), the class layout is unchanged and only one function-pointer slot moves. The protocol:

  • XLiveCoding identifies the changed function symbol.
  • If the function is in an FClass's LifecycleTable, the LifecycleTable's slot is updated via atomic pointer store (the LifecycleTable lives in .rodata of the patched DLL; the new DLL has a new .rodata with the new slot value).
  • If the function is a user-class virtual method, the user-class vtable in the patched DLL has the new slot; instances continue to dispatch via the user-class vtable, picking up the new function on next call.
  • No FClass rebind needed (the FClass is unchanged).
  • No GC cycle needed.

This is the fastest path because no FXObjectArray walk happens. Latency is dominated by XBT recompile + XLiveCoding's DLL patch (typically <20 s) plus the function-pointer swap (microseconds).

9.5 Survival across module unload

If a plugin module unloads while instances of its classes exist, the instances are orphaned: the FClass becomes invalid; XObjectKey resolution returns nullptr (because the FClass* would be a dangling pointer). The discipline:

  • Module unload sets EObjectFlags::BeingReplaced on every instance of any FClass from the unloading module.
  • The next GC cycle marks all such instances as unreachable (their FClass is invalid; they cannot be safely traced) and destroys them.
  • Any XObjectKey referencing such an instance resolves to nullptr after the GC cycle.
  • Module unload of a plugin while gameplay code holds strong references is an explicit programming error; XLiveCoding refuses to unload until gameplay code drops the references (per Master Plan hot-reload commitment).

10.6.1 Async loading object graph (Rev 2 + Rev 3; FIX-A-MED-28 / UE5-IMPRV-3 / FIX-M-R2-4)

Async loading worker calls NewObject<T>(Outer, Name, RF_NeedLoad) with RF_NeedLoad set. The flag inhibits PostInitProperties; the object's references are not yet resolved. Async loading completes when all RF_NeedLoad objects' Serialize calls finish, then RF_NeedPostLoad triggers PostLoad in batch.

RF_NeedLoad + FXObjectInitializer interaction (Rev 3 per FIX-M-R2-4). Async loading bypasses the FXObjectInitializer destructor-driven PostInitProperties flow. The loader's NewObject call sets RF_NeedLoad on the object; in this mode, the NewObject path does NOT construct an FXObjectInitializer on stack; PostInitProperties is deferred until after Serialize completes (and only fires if the object did not have RF_NeedLoad set on entry). Once Serialize sets the references, PostInitProperties + PostLoad fire in batch via the loader's batch-finalize step.

The control-flow:

  1. Loader allocates each object with RF_NeedLoad | RF_NeedPostLoad. NewObject path detects the RF_NeedLoad bit at entry and skips the FXObjectInitializer construction (no ~FXObjectInitializer firing PostInitProperties at scope exit). The object is left in a "constructed but uninitialized" state.
  2. Loader runs Serialize via the FClass's lifecycle FakeVTable to fill in property values from archive (XSerialization is the strong-symbol provider of the Serialize slot per FIX-A-HIGH-13).
  3. When all RF_NeedLoad objects in the load batch have completed Serialize, the loader clears RF_NeedLoad on all.
  4. For each object with RF_NeedPostLoad set, the loader calls PostInitProperties via the lifecycle FakeVTable FIRST (the FXObjectInitializer's destructor-trigger was bypassed in step 1), then calls PostLoad via the lifecycle FakeVTable. Order is important: PostInitProperties sees the deserialized property values (since Serialize ran in step 2); PostLoad sees the fully-bound object graph.
  5. After PostLoad, the loader clears RF_NeedPostLoad. The object is fully active.

Inline code example (loader path):

// Async loader's per-object create + serialize + finalize sequence (Rev 3).
namespace XSerialization {

XObject* AsyncLoader::CreateAndSerialize(const FClass* cls,
                                          XObject* outer,
                                          FName name,
                                          FArchive& archive) {
    // Step 1: NewObject with RF_NeedLoad bypasses FXObjectInitializer.
    XObject* obj = NewObject<XObject>(outer, name,
        EObjectFlags::NeedLoad | EObjectFlags::NeedPostLoad);
    obj->ClassPrivate = cls;   // overridden because the FClass is resolved late

    // Step 2: Serialize from archive (via FClass's lifecycle FakeVTable).
    auto* serializeFn = reinterpret_cast<void(*)(XObject*, FArchive&, const FArchiveContext*)>(
        cls->LifecycleTable->Slots[uint32_t(EXObjectLifecycleSlot::Serialize)]);
    if (serializeFn) {
        serializeFn(obj, archive, /*Ctx=*/nullptr);
    }

    return obj;
}

void AsyncLoader::FinalizeBatch(TArrayView<XObject*> batch) {
    // Step 3: clear RF_NeedLoad on all.
    for (XObject* obj : batch) {
        obj->ClearFlags(uint32_t(EObjectFlags::NeedLoad));
    }
    // Step 4: PostInitProperties then PostLoad (in batch order; respects archive order).
    for (XObject* obj : batch) {
        if (obj->HasAnyFlags(uint32_t(EObjectFlags::NeedPostLoad))) {
            auto* postInitFn = reinterpret_cast<void(*)(XObject*)>(
                obj->ClassPrivate->LifecycleTable->Slots[
                    uint32_t(EXObjectLifecycleSlot::PostInitProperties)]);
            if (postInitFn) postInitFn(obj);
            auto* postLoadFn = reinterpret_cast<void(*)(XObject*)>(
                obj->ClassPrivate->LifecycleTable->Slots[
                    uint32_t(EXObjectLifecycleSlot::PostLoad)]);
            if (postLoadFn) postLoadFn(obj);
        }
    }
    // Step 5: clear RF_NeedPostLoad.
    for (XObject* obj : batch) {
        obj->ClearFlags(uint32_t(EObjectFlags::NeedPostLoad));
    }
}

} // namespace XSerialization

The loader thread is included in the hot-reload quiesce thread enumeration (§9.2 per FIX-A-HIGH-14).

10.7.1 C# Generic Instantiation Reflection (Rev 2; FIX-A-HIGH-15 / MOD-CS-1)

Each closed C# generic instantiation needs explicit reflection at compile time. The protocol:

  1. XIL2CPP analyzes each closed C# generic instantiation at compile time.
  2. For each generic instantiation, walks the closed type tree (fields recursively).
  3. If any (transitive) member is XObject-derived: emit a typed XGCRootSpan with byte-stride.
  4. If a member is object (System.Object) or open-typed: emit Conservative XGCRootSpan with build-time warning on sim-path TUs.
  5. Pure-value generics (e.g., List<int>, Dictionary<string, double>) emit no XGCRootSpan.

Example: List<XActor> emits a typed XGCRootSpan with stride 8 (the XPtr<XActor> payload). List<object> emits Conservative XGCRootSpan plus a build-time sim-path warning. Dictionary<FName, XActor> emits typed-by-value (value stride) XGCRootSpan.

Closed-type-tree analysis bounds (Rev 3 per FIX-M-R2-7). XIL2CPP's generic-instantiation walk is bounded by:

  • Max recursion depth 16. Closed generic types nest at most 16 levels deep before the walk halts. Depth 16 covers all reasonable nested-generic patterns (e.g., List<Dictionary<FName, List<XPtr<XActor>>>> is depth 4; depth 16 is well over typical engine use).
  • Cycle-detection HashSet of visited type instantiations. C# generics can in principle declare cyclic dependencies (e.g., class A<T> { B<T> b; } class B<T> { A<T> a; }); the walk records every visited closed-type instantiation in a HashSet and refuses to revisit. The HashSet is per-walk (one walk per top-level reflected type emit).

On exceeding either bound, XIL2CPP emits a build-time error:

  • XIL2CPP123 — generic instantiation closure exceeds depth 16 — the offending closed type is identified in the error message with its instantiation path.
  • XIL2CPP124 — cyclic generic type closure detected — the cycle members are enumerated in the error message.

The error is non-overrideable (no opt-out flag); the build fails per Prime Directive on either condition. The user must redesign the generic dependency graph.

Conservative XGCRootSpan warning timing (Rev 3 per FIX-M-R2-8). When XIL2CPP emits a Conservative XGCRootSpan for a closed type (List<object>, Dictionary<K, object>, open-typed members, etc.), it fires a build-time warning once per closed-type instantiation, suppressed on subsequent occurrences in the same build. The de-duplication uses XIL2CPP's build cache: each Conservative-emit records the canonical closed-type signature; subsequent emits with the same signature skip the warning. Warning category: XIL2CPP-Conservative. Format:

XIL2CPP-Conservative: closed type `<name>` emits Conservative XGCRootSpan at <file>:<line>.
This adds 10-20 cycles per slot validation at GC time. If this type is consumed
from sim-path code, validate at sim-path TUs: the type's mutations cannot be
sim-path-deterministic. Consider switching to a statically-typed container
(List<XActor> instead of List<object>) to eliminate the conservative scan.

The warning is informational (Build succeeds); the user can resolve it by refining the C# code's type annotations.

10.7.2 C# async/await with XObject captures (Rev 2; FIX-A-MED-25 / MOD-CS-2)

Transpiled C# async state machines emit XGCRootSpan registration at MoveNext entry; unregister at completion. Awaiter frames containing XObject captures stay live across await suspension. Pattern:

// C# source:
//   async Task DoTask(XActor actor) {
//       await Task.Delay(100);
//       actor.Tick();
//   }
//
// XIL2CPP emits a state-machine struct with `actor` as a captured field, and
// the MoveNext() method registers an XGCRootSpan over `actor` at entry,
// unregisters at completion. While the await is suspended, the XGCRootSpan
// keeps `actor` alive even if the original caller goes out of scope.

10.7.3 C# IDisposable + XObject lifetime (Rev 2; FIX-A-MED-26 / MOD-CS-3)

XObject implements IDisposable in the C# surface. Dispose() calls obj.MarkForKill() (alias for EObjectFlags::MarkedAsGarbage from FIX-A-HIGH-19), which makes the next GC cycle reclaim the object. Raw destruction (calling the destructor directly) is forbidden — reference safety can't be guaranteed without GC participation. Users who hold C# using blocks around XObject-derived types get the expected disposal behavior.

10.7.4 C# struct-with-XObject-field handling (Rev 2; FIX-A-MED-27 / MOD-CS-4)

C# struct types containing XObject fields are GC-rooted via different mechanisms depending on storage location:

  • Stack-stored: XIL2CPP stack-map registers the byte offset of the XObject field. The precise stack scan (§5.4) enumerates the field as a root.
  • Class-field: parent class's FProperty walk (via schema-vector) handles it via EXObjectRefSchemaOp::Struct opcode + nested RefSchema reference (recurses into the struct's RefSchema; §7.4).
  • Array-stored: TArray<TStruct> with XGCRootSpan partial specialization that recurses into each struct's schema vector.

10.8 XCore-4a XGC_* function replacement + s_XObjectAllocator 3-arg hook

XCoreXObject's link step replaces XCore-4a's weak-symbol stubs for XGC_WriteBarrier / XGC_RegisterRootSpan / XGC_UpdateRootSpan / XGC_UnregisterRootSpan with strong-symbol implementations. The replacement is automatic at link time; no source change to XCore-4a is needed.

XCore-4a's s_XObjectAllocator function-pointer hook (XCore-4a §4.4) is installed by XCoreXObject's PostStaticInit code (Rev 2 corrected init phase per FIX-A-CRIT-5) via RegisterXObjectAllocator(&FXObjectAllocator::AllocateRaw). The hook signature is 3-arg: void* (*)(size_t Size, size_t Align, const FClass* ClassDescriptor) noexcept — XCore-4a Rev 4 follow-up expands the existing 2-arg signature (FIX-A-CRIT-4). This ensures the link-error-on-uninstalled-allocator gate from XCore-4a remains a real gate (test builds without XCoreXObject linked get the clear abort with stack trace).

10.9 XSerialization integration (System 9)

XSerialization is a downstream consumer of XCoreXObject (per FIX-A-MIN-45 direction-of-dependency). XCoreXObject defines the Serialize slot signature; XSerialization fills the slot. The signature (per FIX-A-HIGH-13): void(*)(XObject* self, FArchive& Ar, const FArchiveContext* Ctx) noexcept. The FArchiveContext is an opaque void* (XSerialization-defined) for forward-compat.

XSerialization's archive paths call into XCoreXObject:

  • Save: walks the FStruct::PropertyLink for each object; delta-compares against the CDO; persists only differing properties. Each persisted XObject reference is encoded as {ClassName FName + ObjectPath FName}.
  • Load: resolves {ClassName} via XReflectionRuntime::FindClass; allocates via NewObject; calls Serialize via the FClass's lifecycle FakeVTable to fill in properties.
  • PostLoad: after the entire archive's object graph is loaded, walks each object and calls the PostLoad lifecycle slot.

10.10 XNetworking integration (System 13)

XNetworking's FReplicationStateDescriptorRegistry caches XObjectKey instances for the replication state's referenced objects. The XObjectKey-based identity is what survives across multiplayer reconnection and hot-reload. XNetworking's NetSerialize path for XObject references encodes the XObjectKey (8 bytes); on receive, the receiving end resolves the key via XCoreXObject's XObjectKey::Resolve() to find the corresponding local instance.

10.10.1 Cache invalidation on class replacement (Rev 2; FIX-A-MED-33 / X-SYS-5)

When a class is replaced by hot-reload, XCoreXObject fires OnClassReplaced(FClassReplacementContext) delegate via XCoreDelegates (per FIX-A-MIN-44). XNetworking listens to this delegate and invalidates its FReplicationStateDescriptorRegistry cache for the affected class. The cache rebuild happens on next net-serialize of the affected class instances. This ensures correct replication shape after a hot-reload (the FProperty layout may not change, but the rep-record schema may — e.g., a property's Replicated flag could be added or removed even within the same layout).

10.11 XLog category integration (Rev 2; FIX-A-MED-31 / X-SYS-2)

XCoreXObject emits XLog category lines via the X_LOG macro (per XCore-4a's logging discipline). Categories:

  • XCoreXObject.GC — cycle start/end, mark phase progress, sweep counts.

12.2 XPROPERTY

Declares a reflected member. XHT parses the specifier list (EditAnywhere, BlueprintReadWrite, Replicated, etc.) and emits the FProperty descriptor in .gen.cpp. The XHT-emitted FProperty includes the dispatch table pointer to the per-subclass FFakeVTable (XCore-4b FIX-2).

12.3 XFUNCTION

Declares a reflected method. XHT parses the specifier list (BlueprintCallable, Server, Client, NetMulticast, etc.) and emits the FFunctionDescriptor in .gen.cpp. The function is then callable via reflection (e.g., from Blueprint VM); native callers continue to call the C++ method directly.

12.4 XINTERFACE

Declares a reflected interface. XHT emits the FInterface descriptor and the per-implementing-class InterfaceImplementations table (XCore-4b §7.5.1).

The following list enumerates the deliberate divergences from UE that this spec ships, each justified per Prime Directive.

  1. 56-byte XObject vs UE's 40-byte UObjectBase + ~24-byte FUObjectItem split (Rev 2 corrected per FIX-A-CRIT-7). UE's UObjectBase is 40 bytes (static_assert at UObjectHash.cpp:40); UE's FUObjectItem is ~24 bytes; the two are SEPARATE allocations. XPact's XObject at 56 bytes is LARGER than UE's UObjectBase alone by 16 bytes — but unifies the header with cluster + GC reservation into ONE indirection at GC walk time (the XObject*), not TWO (UE's UObjectBase* → FUObjectItem* chunk-pointer-array indirection). The 16-24 byte size increase trades RAM for cache-coherency at GC walk; for 50k typical XObjects, the cost is ~1 MB — well within Quest 3's 4 GB budget. The cache-coherency advantage saves an L1/L2 miss per ref-property walk, which dominates at scale. Per Prime Directive: this is the correct trade-off, not the easy one.
  2. No virtuals on the XObject GC-relevant surface (PostInitProperties / BeginDestroy / FinishDestroy / AddReferencedObjects all dispatched via FXObjectLifecycleTable in .rodata). UE's pattern requires hot-reload-DLL vtable matching; XPact's pattern is structurally immune to that class of bug.
  3. Non-moving precise mostly-concurrent collector — UE's GC is also non-moving and mark-and-sweep, but UE's pause behavior is significantly worse than the <5 ms target (UE typically incurs 20-100 ms pauses on big object populations). XPact's design (schema-vector GC walk per Rev 2 / FIX-A-CRIT-8 + SATB pre-store barrier + worker-pool parallel mark + safe-point handshake + 3-rotating-reachability-flag scheme) targets sub-5-ms pauses with the same correctness guarantees.
  4. Card-table generational scan-reduction — UE's GC does a full-heap scan every cycle (no generational optimization). XPact's card-table elides scans of cards with no recent writes; minor collections amortize cost.
  5. SATB always-on barrier vs UE's incremental-only barrier (Rev 2 corrected per FIX-A-HIGH-9 / UE-VER-2). UE 5.x has an INCREMENTAL-only write barrier (FObjectPtr::ConditionallyMarkAsReachable, gated on EGCOptions::IncrementalReachability + GIsIncrementalReachabilityPending; ObjectPtr.h:74-77, 140-167). XPact's barrier is always-on for permanent generational scan-reduction. UE's barrier only fires during incremental cycles — not the same kind of barrier as XPact's. The XPact barrier enables true mostly-concurrent marking and powers the card-table scan-reduction; UE has no card table at all (per Subagent A's deep-read).
  6. Size-class-segregated allocator with type-segregated free-lists — UE's FUObjectAllocator uses a simpler page-based pool; fragmentation creeps over long sessions. XPact's design specifically targets <15% wasted heap over 4-hour Quest 3 sessions.
  7. Scenario-boundary mark-region clearing — UE has no equivalent; long-running training sessions hold scenario-scoped objects indefinitely. XPact's design lets XScenarios bulk-reclaim per-scenario object pools at unload.
  8. Lazy CDO construction — UE constructs all CDOs at engine boot, costing 1-10 s of cold-start time. XPact's lazy default targets the ≤ 15 s editor cold-start criterion (i).
  9. XObjectKey UE-faithful + stable XClass identity across hot-reload (Rev 2 corrected per FIX-A-HIGH-10 / UE-VER-3). The XObjectKey 8-byte layout {InternalIndex, SerialNumber} is a UE-faithful mirror of UE's FObjectKey (ObjectKey.h:18-60). The genuine divergence is XPact's stable XClass identity across hot-reload via XLiveCoding's versioned-vtable + stable-exported-name ABI — where UE has only WITH_EDITOR-only SetClass at UObjectBase.h:486. UE's UClass identity at the binary level can change mid-session in editor-only paths; XPact's XClass identity is always stable, which is what makes the “XObjectKey survives hot-reload class replacement” property work in production builds too.
  10. Single FXObjectArray sparse-array vs UE's chunked-array indirection — UE's FUObjectArray uses a chunk-pointer-array of chunks of entries to avoid contiguous reallocation; XPact uses a single sparse array (resized in 1 MB increments). The indirection cost on every FXObjectArray access is ~2 cycles in UE; XPact's direct access is 1 cycle.
  11. 32-byte FXObjectArrayEntry vs UE's 48-64-byte equivalent — UE carries extra fields (RemoteObjectId, ObjectClusterRootObject pointer, EInternalObjectFlags) inline; XPact's design separates concerns (cluster support is in XObject's inline reservation; flags are on XObject not the entry).
  12. Pre-store SATB always-on barrier (Rev 2 corrected per FIX-A-HIGH-9) — XPact's barrier is always on (paying ~3-5 cycles per reference write). UE's barrier is incremental-only. XPact's pattern enables true concurrent marking + card-table scan-reduction; UE has no card table.
  13. Conservative root scanning + XGCRootSpan byte-stride range-span shape (Rev 2 corrected per FIX-A-HIGH-11 / UE-VER-4). UE has TStrongObjectPtr + per-entry refcount mechanism (UObjectArray.h AddRef/ReleaseRef on FlagsAndRefCount). XPact's XStrongPtr (Rev 2 added per FIX-A-MIN-38) IS the same per-slot rooting concept as UE's TStrongObjectPtr. XPact's novel piece is the XGCRootSpan byte-stride range-span shape + Conservative-kind opt-in build-time warning — not the per-slot rooting itself. XGCRootSpan supports byte-strided iteration over heterogeneous-type containers (e.g., List<XObject> with mixed concrete types) and the Conservative-kind warning catches sim-path-determinism violations at build time. UE has nothing comparable.
  14. Precise C# stack scanning via XIL2CPP stack maps — Unity's IL2CPP does precise stack scanning via similar maps; UE's blueprint VM doesn't have a comparable concept. XPact picks the precise approach as the only one compatible with the Master Plan's "no conservative stack scanning" lock.
  15. Toolchain Contract pinning of every byte layout — UE has no equivalent build-time-pinned ABI surface; UE's binary-compatibility breaks routinely on minor-version updates. XPact's static_assert pin set (§11.3) catches drift at compile time.
  16. Schema-vector GC walker (Rev 2 added per FIX-A-CRIT-8 / UE-MISS-1) — XPact ADOPTS the UE 5.x FSchemaOwner / EMemberType opcode vector pattern (the single largest perf miss in Rev 1 per Subagent A). FStruct's RefSchema pointer references a packed opcode vector emitted by XHT; the GC walk iterates opcodes (cache-coherent) instead of pointer-chasing FProperty linked-lists.
  17. FXObjectInitializer + CreateDefaultSubobject + FObjectInstancingGraph (Rev 2 added per FIX-A-HIGH-12 / UE-MISS-2) — XPact ADOPTS the UE FObjectInitializer destructor-driven finalization pattern; CreateDefaultSubobject for sub-object templating; FObjectInstancingGraph for archetype-aware sub-object reconstruction at deserialize.

Deferred-to-other-system items (per FIX-A-MIN-54 / UE-MISS-8, UE-MISS-9):

  • UE-MISS-9 (FCustomVersion for asset format evolution): deferred to XSerialization for the asset-format custom-version system; FStruct::SchemaHash + FCustomVersion are already in XCore-4b's surface.
