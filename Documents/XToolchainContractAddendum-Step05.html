2. File Discovery — how XBT identifies the input file set per module

2.1 Descriptor discovery (implemented)

Module descriptors are discovered by ModuleEnumerator.Enumerate (Engine/Source/Programs/XBT/XBT.Discovery/ModuleEnumerator.cs, lines 96–119 for the entry point). The walk:

  1. Parallel-walks every source root passed in (Engine Source/, optional Studio Source/, optional Project Source/, and every discovered plugin's Source/).
  2. Within each root, recursively scans for *.Build.toml and *.Build.cs via two Directory.GetFiles calls with EnumerationOptions (RecurseSubdirectories = true, IgnoreInaccessible = true).
  3. Groups results by containing directory: at most one descriptor pair (TOML + CS) per directory; if both exist, the .Build.cs wins per Contract Section 9.6 and the TOML is logged-and-ignored.
  4. Filters out XBT's own placeholder .Build.cs files (those under /Engine/Source/Programs/XBT/ — they are self-referential informational stubs guarded by #if XBT_HAS_MODULERULES, never defined).

The case-sensitivity of the descriptor-directory dictionary is StringComparer.Ordinal (case-sensitive). The intent — documented inline at ModuleEnumerator.cs:215–220 — is to expose two real, physically-distinct paths on Linux as two modules rather than collapsing them. Windows case-folds before keys ever differ, so the choice is observationally equivalent there.

2.2 Source-file enumeration (Phase 1 reality)

Per-module source files are enumerated not by ModuleEnumerator but by a private helper inside BuildMode: EnumerateModuleFiles(string moduleDir). The helper:

  • Walks the module directory recursively with Directory.EnumerateFiles(moduleDir, "*.cpp", …).
  • Walks again with "*.h".
  • Walks again with "*.cs", excluding descriptor files matching *.Build.cs (those are build metadata XBT compiles via the Roslyn fallback, not module source code).
  • Sorts all three lists by FullPath with string.CompareOrdinal so iteration order is reproducible across runs and machines.
  • Does not distinguish Public/, Private/, Internal/, or Classes/ subtrees — every .h, .cpp, and .cs under moduleDir is treated equally. The header-category split that the manifest schema exposes is not derived from filesystem layout in Phase 1; it carries whatever a parser populated on ModuleRules through unchanged.

The three lists feed the manifest emitter (Section 3.3 / 3.4) directly: C++ sources and headers populate the SourceFiles list with IsHeader flags; C# sources populate SourceFiles with IsCSharp = true and the dedicated CSharpSources field. The header-category lists (PublicHeaders, PrivateHeaders, InternalHeaders) remain a Phase 1 limitation — the filesystem walk does not split by subtree, so XHT must continue treating those lists as best-effort descriptor authoring (see Section 10).

2.3 The ordinal-comparer choice (load-bearing for determinism)

Every collection in the dependency model that is hashed or persisted is sorted with StringComparer.Ordinal / string.CompareOrdinal. The sites:

  • ExternalAction.Create — refuses to construct an action whose PrerequisiteItems, ProducedItems, or DeleteItems are not sorted ordinal (ExternalAction.cs:159–180, throws ArgumentException on violation).
  • ActionHistory.Save — sorts every partition's entries by path ordinal before writing (ActionHistory.cs:363).
  • ActionHistory.ComputeCurrentVersion — sorts the reflected IExternalAction property set alphabetically before hashing (ActionHistory.cs:508). This is a deliberate post-audit fix; relying on MetadataToken order would have made the version hash dependent on Roslyn implementation details.
  • ActionGraph._producerByPath — StringComparer.Ordinal dictionary (ActionGraph.cs:101).
  • EnumerateModuleFiles — final sort step at BuildMode.cs:1265–1267.

The choice is not aesthetic. Ordinal comparison is the only stable cross-platform sort: it gives the same answer on Win64 NTFS (case-insensitive filesystem) and Linux ext4 (case-sensitive filesystem). Any path-keyed structure that uses culture-aware or case-insensitive comparisons would yield non-reproducible serialised bytes between the two hosts.

3. Manifest Format — the wire surface XHT and XIL2CPP consume

3.1 JSON form

The JSON manifest is the human-debuggable form. Its schema is the canonical C# DTO declared in XBT.Manifest/ManifestSchema.cs: Manifest (lines 71–84), Module (lines 41–64), SourceFile (lines 29–33), and ModuleDep (in ModuleDep.cs).

Serialisation goes through ManifestJson.SerializeToJson with JsonSerializerOptions:

  • WriteIndented = true — output is indented for readability + clean diffs.
  • JsonStringEnumConverter — enums render as PascalCase strings, not integers.
  • DefaultIgnoreCondition = Never — no field is elided; the JSON is the audit trail.

Deserialisation goes through ManifestJson.DeserializeFromJson and enforces the hardened-reader options the main contract Section 8.4 requires: MaxDepth = 64, AllowTrailingCommas = false, CommentHandling = Disallow. The payload is also pre-tokenised against those options to reject violations before the deserialiser sees the bytes (ManifestJson.cs:100–105).

Post-parse, ValidateLimits walks the materialised graph and enforces:

  • MaxManifestBytes = 100 MiB
  • MaxStringField = 16 KiB
  • MaxArrayCount = 65,536

Any violation throws ManifestMalformedException → exit code 50 (per Contract Section 13).

3.2 FlatBuffers binary sidecar

The binary sidecar is the canonical machine-read form. Its schema lives at Engine/Source/Programs/XBT/XBT.Manifest/Manifest.fbs, compiled to C# at XBT build time via FlatSharp (project file: XBT.Manifest/XBT.Manifest.csproj; FlatSharp targets imported via XBT.Manifest/FlatSharp.targets).

The schema's file_identifier is "XMFT" — four ASCII bytes at offset +4 of the buffer (FlatBuffers wire layout: bytes 0–3 are the uoffset to the root table; bytes 4–7 are the identifier). ManifestFbs.VerifyFileIdentifier (lines 290–301) reads exactly those four bytes and refuses the buffer if they don't match.

Verifier limits, enforced on every deserialise (FbsVerifierLimits.ContractDefaults, lines 60–76):

  • MaxDepth = 64 — FlatBuffers object nesting depth, applied via WithObjectDepthLimit.
  • MaxBytes = 100 MiB — buffer size hard ceiling.
  • MaxStringLength = 16 KiB — per UTF-8 string field.
  • MaxVectorLength = 65,536 — per vector field.

FlatSharp does not natively tune string and vector limits, so ManifestFbs.EnforcePostParseLimits walks the greedy-materialised object graph and rejects any limit violation (ManifestFbs.cs:302–391). Any verifier violation throws ManifestException → exit code 50.

The schema uses append-only versioning per Contract Rev 13 Section 10.2 N4: new fields are appended; never reordered, never deleted. FlatBuffers default-value semantics fill in missing fields for older readers, so an XHT compiled against schema version N reading a manifest written by an XBT at schema version N+1 sees defaults for the new fields. Removing or repurposing a field requires a contract revision and a ContractStructureHash bump.

3.3 Read-prefer-binary, fall-back-to-JSON pattern

The main contract describes a read-precedence rule: prefer the binary sidecar, fall back to JSON only when the binary is stale. XBT emits both forms on every successful invocation, before any action emission, at the following deterministic paths:

  • Intermediate/Build/<Target>/<Configuration>/Manifest.json — the human-debuggable form.
  • Intermediate/Build/<Target>/<Configuration>/Manifest.fbs.bin — the FlatBuffers binary sidecar; canonical machine-read form.

The emission path runs inside BuildMode.RunInternal after module discovery + tier validation, before the per-module action emission loop. Both writes use the atomic temp-file + rename pattern (ManifestJson.Serialize + ManifestFbs.Serialize internally write to <name>.tmp.<pid>.<guid> then File.Move(overwrite: true)) so an external observer never sees a partially-written manifest. The temp-file naming follows the engine-wide no-timestamp convention (Toolchain Contract Rev 13 Section 2.1 footgun #1).

Phase 1 does not express the emission as a WriteManifestAction in the action graph. The XActionType.WriteManifestAction slot at ordinal 1 in XActionType.cs:41 remains reserved — the slot is preserved for a future phase that wants to integrate the manifest into the action-cache invalidation surface. The direct-emission approach taken here is forward-compatible: a future WriteManifestAction constructed via ExternalAction.Create can declare the same two output paths as ProducedItems without changing the manifest's contents or wire format. Phase 1's manifest is not yet a CacheKeyComponent for any downstream action, so the action-graph integration is not load-bearing at this commit.

3.5 ContractVersion auto-derivation (implemented)

The manifest's contract_version field is computed at static-init by ContractVersion.Current (XBT.Manifest/ContractVersion.cs:51). The composition is:

Current = $"{ContractSurface.SemanticVersionTag}+{StructureHash.ToString().Substring(0, 16)}"

Where StructureHash is a BLAKE3 over a deterministic UTF-8 line-based serialisation of ContractSurface (ContractVersion.cs:124–197). The serialised stream:

  1. SemanticVersionTag + LF (currently "13.2").
  2. Every enum surfaced by ContractSurface.Enums, sorted by enum name, each member emitted as name=ordinal sorted by ordinal, blank line terminator.
  3. Every marker macro (preserved declaration order).
  4. Every body-macro suffix (preserved order).
  5. mangling:{ManglingRuleExample} — the locked Itanium-ABI-style example ("XN1A1BE").
  6. file_id:{FileIdScheme}.
  7. Every exit code (sorted by code) as exit:{code}={mnemonic}.
  8. Every action type (declaration order = slot ordinal) as action:{name}.

Line endings are LF unconditionally — the StreamWriter at ContractVersion.cs:108 sets NewLine = "\n" so a hash computed on Windows matches one computed on Linux.

The 16-hex-char truncation (64 bits of collision space) sacrifices entropy for brevity; full 256-bit hash is still available via ContractVersion.StructureHash for callers that need it.

4. Per-Action Dependency Tracking

4.1 IExternalAction shape

The action contract is IExternalAction in XBT.ActionGraph/IExternalAction.cs. The implementation surface (every property, all get-only):

  • ActionType — XActionType slot.
  • PrerequisiteItems, ProducedItems, DeleteItems — IReadOnlyList<FileItem>, not SortedSet<FileItem> as XBT.html Rev 4 Section 5.2 declares. The interface XML-doc at IExternalAction.cs:26–37 explains the divergence: consumers iterate, the action graph hashes the serialised form, and the spec plan explicitly requested IReadOnlyList. The sort invariant is enforced at construction by ExternalAction.Create — passing an unsorted or duplicate-containing list throws ArgumentException (ExternalAction.cs:159–180).
  • CommandPath, CommandArguments, ResponseFileContents, WorkingDirectory — the execution payload.
  • CommandVersion — IoHash; lazily auto-derived from a BLAKE3 of the payload. See Section 4.2.
  • CommandDescription, StatusDescription — verb + object for the progress channel.
  • CanExecuteRemotely — bool hint; Phase 1 ignores it (no remote executor yet), Phase 2 XPactBuildAccelerator reads it as a hard gate.
  • CacheKeyComponents — IReadOnlyList<string> of hidden inputs that influence output but are not in the command line. See Section 8.
  • Weight — scheduler cost hint.
  • CacheBucket — nullable string; reserved for partitioning hints, currently informational.
  • bUseActionHistory — opt-out; default true.
  • Module, Tier, SimPath, Configuration, Platform — metadata for the streaming JSON channel and the toolchain's banned-flag emit decisions.

The default implementation is the sealed record ExternalAction in XBT.ActionGraph/ExternalAction.cs. It is constructed via the Create(prototype) factory which runs the sort-and-uniqueness validation; the public parameterless constructor exists only so C#'s with-expression continues to work for tests that need to build degenerate cases.

4.2 CommandVersion auto-derivation

The action's CommandVersion is a BLAKE3 hash, lazily computed on first access via Interlocked.CompareExchange (ExternalAction.cs:110–126). The hash inputs, in fixed order, with length prefixes so adjacent fields cannot collide (ComputeCommandVersion, ExternalAction.cs:189–248):

  1. ActionType ordinal as little-endian int32.
  2. CommandPath — length-prefixed UTF-8.
  3. CommandArguments count, then each argument length-prefixed UTF-8 (in declared order; ["a","bc"] and ["ab","c"] cannot collide).
  4. ResponseFileContents — if null, the sentinel -1 length; otherwise length-prefixed UTF-8.
  5. WorkingDirectory — length-prefixed UTF-8.
  6. CacheKeyComponents count + each component length-prefixed UTF-8.
  7. Configuration + Platform as little-endian int32s.
  8. SimPath flag as a single byte.

Excluded inputs (intentional — these do not influence the on-disk output):

  • Weight — scheduler-only.
  • CacheBucket — partitioning hint only.
  • Module, Tier, CommandDescription, StatusDescription — diagnostic metadata.
  • PrerequisiteItems, ProducedItems, DeleteItems — the file lists are graph topology, not command identity; ActionGraph.Link uses them to resolve edges, but two TUs that compile with identical commands but produce different objects must still have distinct CommandVersions via their distinct CommandArguments (which include the output path).

4.3 What constitutes "outdated"

An action is outdated per ActionHistory.IsActionOutdated(LinkedAction) (ActionHistory.cs:225–303) iff any of the following holds:

  1. A produced file is missing on disk. The first check; File.Exists(produced.FullPath) on every entry of ProducedItems. A short-circuit return at the first miss.
  2. The action's current key has shifted since the last record. ComputeActionKey(action) is run live; for every produced item, GetStoredHash(produced) must equal the freshly-computed key. Mismatch → outdated.
  3. A prerequisite's content hash has shifted from what's recorded. For each FileItem in PrerequisiteItems, if a recorded hash exists in the partition, it is compared against the prerequisite's live ContentHash. If the file is missing on disk or the hashes diverge, the action is outdated.

Note the asymmetric semantics of rule 3 on first observation: a prerequisite that has never been recorded (a fresh raw source file XBT has not seen before) returns IoHash.Zero from GetStoredHash, and the rule is skipped on that build — rules 1 and 2 carry the dependency check. Round-6 closes the recording loop: after a successful action, the production executor (ParallelExecutor) calls ActionHistory.RecordContentHash(prereq, prereq.ContentHash) for every raw-source prerequisite, populating the partition so the next build's rule-3 comparison has a recorded value to diverge from. Producer-output prerequisites are skipped at this step (the upstream action's own RecordHash already covers them when it succeeds). The Revision-3 phrasing — "the first build after any new prerequisite appears trusts the live content hash; subsequent builds compare against the recorded value" — remains correct, but the recording is now an actively wired step inside the executor rather than a latent API. The Contract's mtime ban (Section 2.1 reproducibility envelope) is now fully honored in Phase 1: raw-source prereq invalidation no longer silently relies on FileItem mtime sampling, which was the pre-Round-6 reality flagged in Revision 3's Section 10 item 1.

4.4 Cross-module dependencies (the manifest-based opaque-consumption model)

Per the main contract Section 8: dependencies between modules are manifest-based. XBT does not parse .gen.h content to compute edges; instead, each consumer compile action carries its consumed files as PrerequisiteItems, and the consumer's CommandVersion + the consumed files' ContentHashes together form the invalidation surface.

In Phase 1 the cross-language flow is:

  1. A change to module A's .h changes that file's ContentHash. Module B's compile action lists the .h in its PrerequisiteItems iff (a) the path is in module B's IncludePaths and (b) module B's source actually #includes it. Phase 1 only emits the source file (and PCH artefacts) as prerequisites: see XMSVCToolChain.CompileSource (XMSVCToolChain.cs:254–268) and XClangToolChain.CompileSource (XClangToolChain.cs:303–314). Header dependencies are not in the prerequisite list.
  2. The compile action's CommandArguments includes the /I<modA> flag, so a change to which directories A exposes would re-derive the CommandVersion. But a change to the content of A's header without a manifest-level dep edge being recorded does not invalidate B's compile in Phase 1.

This is the central Phase 1 limitation for XHT: XBT today does not track per-TU transitive header dependencies. See Section 6 for the full status of /showIncludes / -MD parsing.

5. ActionHistory On-Disk Format

5.1 Directory layout (one file, not many)

XBT.html Section 15.2 prescribes Intermediate/Build/<Target>/<Configuration>/ActionHistory.<Bucket>.bin — multiple files, one per CacheBucket. The implementation at ActionHistory.cs:104 emits one file:

<intermediateRoot>/<Configuration>/ActionHistory.bin

From BuildMode.cs:278, intermediateRoot is <engineRoot>/Intermediate/Build/<target.Name>, and ActionHistory.Open(intermediateRoot, target.Configuration) appends the configuration subdirectory and the file name. Concrete example for an Editor / Development build at the engine root:

<engine>/Intermediate/Build/MiningTrainingEditor/Development/ActionHistory.bin

The 256 partitions documented in 5.2 are inside that single binary file as sequential [entry count][entries] blocks. The CacheBucket field on IExternalAction exists but has no on-disk effect at Phase 1; it is reserved as a partitioning hint for Phase 2.

5.2 The 256-partition rule (in-memory)

ActionHistory.PartitionCount = 256 (ActionHistory.cs:60). Each partition is an in-memory Dictionary<string, IoHash> keyed on file path with StringComparer.Ordinal, guarded by a per-partition lock (ActionHistory.cs:561–602).

The partition assignment for a given path is PartitionOf(fullPath) at ActionHistory.cs:484–492: BLAKE3 the UTF-8 path bytes, take the first byte of the 32-byte digest. Distribution is roughly uniform across the 256 slots.

Concurrent reads are lock-free at the partition level (the per-partition lock is taken even for reads to be conservative; see the comment at ActionHistory.cs:566–572). Cross-partition writes never contend.

5.3 Atomic write protocol

ActionHistory.Save (ActionHistory.cs:315–380) implements the atomic-rename contract that XBT.html Section 6.4 specifies. Notable details:

  • Temp-file naming. The format is ActionHistory.bin.tmp.<pid>.<guid> — PID + a fresh Guid.NewGuid().ToString("N"). The GUID component is deliberate (ActionHistory.cs:329–338): the Toolchain Contract Rev 13 Section 2.1 reproducibility envelope bans timestamps in artefact names, and a timestamp suffix would smuggle a clock value into the post-mortem if the temp file outlives the crash. The Guid gives collision avoidance without any time leak.
  • Atomic rename via File.Move(tempPath, _archivePath, overwrite: true) (ActionHistory.cs:379). On Win64 this maps to MoveFileEx with MOVEFILE_REPLACE_EXISTING; on Linux to rename(2), which is atomic when source and destination share a volume — guaranteed here because both live in the same directory.
  • Sorted serialisation. Each partition's entries are written sorted by path with StringComparer.Ordinal (ActionHistory.cs:363) so the on-disk byte sequence is invariant across writers. Relying on Dictionary<>.GetEnumerator order would have made the file non-reproducible (a footgun the implementation explicitly calls out at ActionHistory.cs:357–362).
  • Magic + format version. The file begins with "XAH1" (ASCII bytes), then a little-endian FormatVersion = 1, then a 32-byte CurrentVersion digest, then a PartitionCount = 256 int, then 256 partitions of [count][entry][entry]… records.
  • Per-record shape. Each entry is [path UTF-8 length : int32][path UTF-8 bytes : N][hash : 32 bytes].
  • Corruption tolerance. LoadFromDisk (ActionHistory.cs:388–469) returns an empty archive on missing file, magic mismatch, format-version mismatch, schema-version mismatch (a CurrentVersion change wholesale invalidates all previous entries), truncation, or any IOException. Path length is bounded at 4096 bytes; longer is rejected as malformed.

5.4 Orphan-sweep at startup

Before the build dispatches anything, ParallelExecutor.SweepOrphanedTempFiles(intermediateBuildRoot) (ParallelExecutor.cs:408–482) walks the entire intermediate-build tree and deletes any *.tmp.<pid>.<actionid> file whose <pid> does not correspond to a currently-running process. The sweep:

  • Parses the temp-file naming convention via TryParseTempFilePid — rejects anything that isn't a strict <output>.tmp.<pid>.<actionid> match.
  • Tests pid liveness via Process.GetProcessById. The pid lookup is intentionally permissive: a sibling XBT instance owning a temp file (whether or not it's the same user) defeats the delete. Access-denied responses from the OS are treated as "leave alone" so the sweep never destroys another user's in-progress build.

It is called from BuildMode.RunInternal at line 290 (under a try/catch wrapper because the sweep is best-effort and must never abort a build).

5.5 Versioning — the schema-hash auto-derivation

ActionHistory.CurrentVersion is not the same as ContractVersion.Current. It is computed at first access by ComputeCurrentVersion (ActionHistory.cs:494–553):

  1. Reflect every public, instance property on typeof(IExternalAction).
  2. Sort the property array alphabetically by name with StringComparer.Ordinal (ActionHistory.cs:507–508). The implementation explains the choice: alphabetical ordering is stable across Roslyn versions, .NET versions, and architectures; MetadataToken ordering depends on compiler implementation details that are not spec-guaranteed.
  3. Reflect every named value in typeof(XActionType) in declaration order (the slot ordinal). Reserved slots (9–15) are part of this list, so adding a Phase 2 action type that lands in a reserved slot does not bump the hash, but adding a value beyond ordinal 16 would.
  4. BLAKE3 the concatenation: length-prefixed action-type names, then for each property a length-prefixed name and a length-prefixed Type.FullName. A property rename, a property addition, a property type change, or an action-type list extension all bump the hash; reordering the declarations alone does not (because of the alphabetical pre-sort).

The hash is embedded in ActionHistory.bin at write time. LoadFromDisk compares the embedded value against the freshly-computed CurrentVersion and silently treats the archive as empty on mismatch — any property-set change invalidates every previous entry.

5.6 ActionHistory action-key composition (the cache-key fingerprint)

ActionHistory.ComputeActionKey(action) (ActionHistory.cs:133–189) is the per-action fingerprint stored against each ProducedItem. The hash inputs, in order:

  1. CurrentVersion (the 32-byte schema digest from 5.5).
  2. action.CommandVersion (the per-action BLAKE3 from 4.2).
  3. ContractVersion.Current as UTF-8 bytes (length-prefixed).
  4. ResponseFileContents — either the sentinel -1 length for null, or length-prefixed UTF-8.
  5. CacheKeyComponents — count, then each component length-prefixed UTF-8.

Any change in any of those five inputs — an interface schema bump, a command-line change, a contract revision, a response-file edit, a hidden-input change — produces a new key, which mismatches the stored value, which marks the action outdated. The CommandVersion already includes CacheKeyComponents; including them again in ComputeActionKey is redundant but defensible (it preserves invalidation if a future refactor moves component handling).

6. Header Dependency Tracking (Phase 1 reality — absent)

This is the most consequential Phase 1 limitation for XHT. XBT in Phase 1 does not parse /showIncludes or -MD output and does not record per-TU transitive header dependency sets.

Concretely:

  • MSVC. XMSVCToolChain.CompileSource does not pass /showIncludes. There is no flag added in the entire XMSVCToolChain.cs file that requests dependency emission. The compile action's PrerequisiteItems list contains the source .cpp plus (when a PCH is bound) the PCH artefact and the PCH header — XMSVCToolChain.cs:254–268. Headers that the source #includes are not in the list.
  • Clang. XClangToolChain.CompileSource does emit -MD + -MF <depfile> (lines 198 and 283–284). The depfile is declared as a second ProducedItem on the compile action (lines 294–298) so the action graph treats it as a build artefact subject to the atomic-rename + ActionHistory recording flow. No code path parses the depfile back into transitive header dependencies. A search across the XBT solution for a .deps parser, a CppDependencyCache class (the cache name XBT.html Section 15.3 specifies), or any consumer of the .o.d output finds zero results.

The class XCppDependencyCache that XBT.html Section 15.3 names does not exist in the codebase. The contract main document Section 8.1 references it; the implementation does not. This is the largest spec/implementation divergence in the dependency model.

6.1 What this means for XHT

XHT must not emit actions that depend on transitive-header invalidation. A .gen.h consumed by a .cpp can be tracked by XBT today only if the .cpp's compile action explicitly lists the .gen.h in its PrerequisiteItems. XHT's emit step should produce action records whose PrerequisiteItems include every .gen.h that any consumer .cpp in the same module will transitively include — the action graph then connects the dots via the producer map (ActionGraph.Link, ActionGraph.cs:122–161).

Phase 2 work item: implement CppDependencyCache; teach XMSVCToolChain to emit /sourceDependencies (the JSON-output form preferred over /showIncludes by MSVC 17.4+); teach an action-post-processing step to parse the depfile output and attach the resolved header set as additional prerequisites for the action's next-cycle invalidation check.

7. Cross-Language Dependency Edges (Phase 1 reality)

The main contract Section 8.1 prescribes the cross-language flow as: a change to a .cs regenerates the corresponding .gen.h; the .gen.h's ContentHash shifts; every consumer .cpp action that listed the .gen.h in its prerequisites becomes outdated; consumers rebuild.

Phase 1 reality:

  • XBT has no .cs source-file discovery in BuildMode's pipeline (Section 2.2).
  • XHT and XIL2CPP are not built yet, so no .gen.h emit action is in the action graph.
  • The XActionType slots ParseHeadersAction (ordinal 2), EmitReflectionAction (3), and XIL2CPPAction (4) exist but have no concrete classes (only ValidateCopyrightAction is realised under XBT.ActionGraph/Actions/).

The infrastructure to flow the change is in place: ActionGraph.Link's producer map, ActionHistory.IsActionOutdated's prerequisite-hash comparison, and the toolchain abstractions are all capable of representing the cross-language graph correctly when XHT/XIL2CPP populate it. But the actual flow is not exercised by any Phase 1 build; it is a Phase 1.5+ wire-up.

9. Concurrency and Determinism Guarantees

XBT's parallel-execution guarantees are narrower than the spec might imply:

  • Worker count. Default Environment.ProcessorCount; configurable via ParallelExecutorOptions.WorkerCount. Workers are Task.Run-dispatched (thread pool), not dedicated threads.
  • Ready-set ordering is deterministic. ActionGraph.Sort drains its SortedSet<LinkedAction> by ordinal comparison on the 32-byte CommandVersion digest (ActionGraph.cs:40–54). Two runs of the same graph yield the same sort order. Tie-breaking is total (no CommandVersion collision survives ActionGraph.Link's producer-conflict check).
  • Dispatch ordering is not deterministic. The BlockingCollection the executor drains is initially seeded in sorted order, but worker contention may pull actions in a different relative order than the sort dictated. The output is the same, but a build log captured by the streaming JSON channel may show actions in different temporal order between runs.
  • Per-output atomic writes. Each ProducedItem is written to <output>.tmp.<pid>.<actionid> in the output's own directory; actionid is a per-executor monotonic counter (Interlocked.Increment(ref actionId) at ParallelExecutor.cs:156). On runner success, File.Move(temp, output, overwrite: true) performs the atomic swap. On any failure or cancellation, the temp is deleted; on a crash, the next-startup SweepOrphanedTempFiles reaps the orphan.
  • Cancellation honour deadline. 5-second grace period (ParallelExecutorOptions.CancellationGracePeriod); ProcessActionRunner polls WaitForExit(250) so a cancellation token fires inside that poll window, then Kill(entireProcessTree: true).
  • Cascading failure. A failed action marks every transitive dependent as "skipped" with exit code 70 ("Skipped: prerequisite <X> failed"); unrelated subtrees continue (SkipDependents, ParallelExecutor.cs:342–372).
  • Single-action runner per executor. The runner is passed in at construction (IActionRunner); the in-process composite CopyrightAndProcessActionRunner in BuildMode dispatches to ProcessActionRunner for everything except ValidateCopyrightAction.

What XBT does not guarantee:

  • Remote execution. CanExecuteRemotely is a hint; Phase 1 ignores it. The Phase 2 XPactBuildAccelerator reads it as a hard gate.
  • Distributed cache. Reserved XActionType slots 9 and 10 exist for Reserved_DistributedCacheCheck and Reserved_DerivedDataFetch; not realised.
  • Live Coding cascade. Reserved slots 11 and 12 (Reserved_LiveCodingCascade, Reserved_PatchDllEmit); the cascade orchestration that the master plan Section 11 promises is Phase 2.

10. Known Phase 1 Limitations

This section is what XHT and XIL2CPP must work around. Each bullet names what's missing or divergent and what the consumer should do today. Two gaps the first draft of this addendum surfaced (manifest emission and .cs source-file enumeration) were fixed concurrently with this write — see Section 12's "post-write fixes" note. Round-6 closure (Revision 4): the previously-unwired ActionHistory.RecordContentHash API is now called by ParallelExecutor after every successful action for every raw-source prerequisite, so the Contract's mtime ban (Section 2.1) is fully honored in Phase 1. The Revision-3 expression of this gap (item 1 below referenced the larger header-dep tracking story; the latent prerequisite-mtime fallback that was implied by an unwired RecordContentHash is marked closed in item 1a below). The schema-stable IExternalAction.DependencyListFile field added in Round 6 (item 1b) gives Phase 2 the hook it needs to land CppDependencyCache without further interface churn.

  1. No CppDependencyCache / no header-dep tracking. The class XBT.html Section 15.3 names does not exist. Neither MSVC (/showIncludes not emitted) nor Clang (-MD/-MF output not parsed) result in any per-TU transitive header set being recorded. XHT cannot assume header-dep tracking when emitting actions; XHT must include every required header in the action's PrerequisiteItems explicitly.
  2. (1a — CLOSED Round 6) Raw-source prereq invalidation no longer silently relies on mtime. Pre-Round-6 reality: the ActionHistory.RecordContentHash(FileItem, IoHash) API existed but was never invoked by the production executor; consequently the rule-3 prereq-hash comparison in Section 4.3 returned IoHash.Zero for every raw source file on every build, and the actual invalidation signal flowed through FileItem mtime sampling — a violation of the Contract's mtime ban (Contract Section 2.1 reproducibility envelope). Post-Round-6: ParallelExecutor calls RecordContentHash(prereq, prereq.ContentHash) for every raw-source prerequisite after a successful action. Producer-output prerequisites are intentionally skipped (the upstream's own RecordHash covers them when the upstream succeeds). Section 4.3 of this addendum now describes the active recording path; the asymmetric first-build semantics noted there persist (a fresh raw source is recorded on its first build's success; subsequent builds compare against the recorded value), but the recording step is no longer latent. Verified by the new round-trip and edit-detection tests in XBT.Tests (contributing to the 363 → 377 test count delta).
  3. (1b — NEW Round 6, Phase 2 hook) IExternalAction.DependencyListFile added as a schema-stable Phase 2 hook. A new nullable FileItem property DependencyListFile ships on IExternalAction, defaulting to null in every Phase 1 emit site. (The C# signature is FileItem? DependencyListFile { get; init; }; the field is FileItem? rather than string? so the depfile path is interned through the same FileItem table that holds every other prerequisite / produced item — XBT's path-discipline contract demands one identity machinery for every action-graph file.) Phase 2 will populate this with a per-action path: .d for Clang (parsed from the -MF <depfile> output that the Clang toolchain already emits) and a /sourceDependencies-style JSON file for MSVC 17.4+. A future post-execute step (the still-pending CppDependencyCache) will read the file and attach the resolved header set as additional recorded prerequisites for the action's next-cycle invalidation. The field is part of IExternalAction's reflected property set, so adding it rotated ActionHistory.CurrentVersion (forcing a one-time recompute on first run after Round 6); it is not part of ContractSurface (IExternalAction property reflection drives the internal schema digest, not the public ContractVersion), so ContractVersion.Current stays at "13.2+b04ae3cc84cdd9f3". The field's presence today gives Phase 2 a stable place to write the depfile path without another interface churn.
  4. No TargetMakefile top-level cache. XBT.html Section 15.1 prescribes a top-level cache that lets the build skip descriptor parsing + module-graph walk on a cache hit. Phase 1 re-parses every descriptor on every build invocation. The 15-input cache-key list in Section 15.1 is not computed.
  5. ActionHistory is one file, not per-bucket. XBT.html Section 15.2 prescribes ActionHistory.<Bucket>.bin (multi-file, per-bucket-partition). Implementation emits one ActionHistory.bin with internal 256-partition framing. The CacheBucket field on IExternalAction is reserved but inert.
  6. ClassesHeaders is in the spec but not the implementation. The XBT.html Section 8.6 JSON example shows the field; neither ManifestSchema.Module nor Manifest.fbs:104's Module table includes it. ModuleEnumerator does not distinguish a Classes/ subtree. Modules that legitimately ship UE-style Classes/ headers must place them in PublicHeaders today.
  7. Header-category lists are emitted empty in Phase 1. The manifest's PublicHeaders, PrivateHeaders, and InternalHeaders fields are emitted as empty string[] arrays because EnumerateModuleFiles does not split the filesystem walk by Public/, Private/, or Internal/ subtree. XHT must consult the full SourceFiles list (which carries every header with IsHeader = true) and derive the public/private split itself if needed — e.g. by re-walking the module directory or by reading the descriptor.
  8. Manifest is not yet a CacheKeyComponent for downstream actions. The manifest is emitted on every successful build, but its content hash is not threaded into the CacheKeyComponents of any other action. A change to the manifest (e.g. adding a module) therefore does not by itself invalidate downstream caches; invalidation has to be triggered by the underlying input change. Phase 2 will integrate the manifest's content hash into the cache-key envelope (and may at that point convert the direct emission to a WriteManifestAction in the action graph — slot 1 is reserved for exactly that).
  9. Shared PCH grouping is single-target only. BuildSharedPchGroups (BuildMode.cs:971–1162) groups modules within one target. Cross-target shared-PCH sharing (the same header consumed by Editor + Game builds reusing one PCH artefact) is not implemented; each target rebuilds its own shared PCH. The downgrade path in XToolChain.ResolvePCHUsage warns "shared PCH is Phase 1.4" and falls back to NoSharedPCHs for any UseSharedPCHs declaration the grouping pass does not pick up.
  10. Live Coding seams are reserved but inert. XBT.LiveCoding exists as a project; the interfaces it ships (IActionGraphPatcher, IQuiesceParticipant) are placeholders for Phase 2 XLiveCoding integration. AllowHotReload on the manifest is read-through with no consumer in Phase 1.
  11. Distributed build executor is not implemented. ParallelExecutor is local-only. CanExecuteRemotely is honoured as a hint (logged) but ignored at dispatch.
  12. The reproducibility envelope flag set is not in the action cache key. The Section 19.1 envelope flags are emitted unconditionally but their content is not a CacheKeyComponent. A toolchain upgrade that silently changes a flag default would not invalidate cached compiles. XBT.html Section 15.1 item 15 prescribes this; the implementation does not honour it.
  13. Banned-API check against preprocessed text is not realised. Contract Section 4.4 + XBT.html Section 11 specify the M3 alignment where the banned-flag pass runs on preprocessed text. The Phase 1 toolchain has a comment placeholder (XMSVCToolChain.cs:243–249) noting that the AdditionalCompilerArguments collection is not yet exposed on ModuleRules; the banned-flag pass runs only against toolchain-emitted flags today, which forecloses the user-smuggling-through-AdditionalArguments vector but does not implement the preprocessed-text check.
  14. Per-file ID grammar example in ContractSurface is a single literal. ContractSurface.FileIdScheme is a documentation-string constant. The actual symbol-mangler is XIL2CPP's responsibility; XBT validates the contract hash includes the scheme description, not that the scheme is implemented.

11. What XHT (System 2) Will Build On

The XBT touchpoints XHT must target:

  • Manifest reader at a deterministic path. XBT emits the manifest on every successful BuildMode invocation at Intermediate/Build/<Target>/<Configuration>/Manifest.json + Manifest.fbs.bin. XHT should prefer the binary sidecar (ManifestFbs.DeserializeFromFbs with FbsVerifierLimits.ContractDefaults); fall back to JSON (ManifestJson.DeserializeFromJson with the hardened reader options) when the binary is missing or fails verification. The file_identifier is "XMFT"; the per-module record fields are documented in Section 3.4 above. Writes are atomic via temp-file + rename, so XHT never sees a torn manifest mid-write.
  • IExternalAction for action emission (REVISED Revision 5; cross-doc cite refreshed Revision 6 to Contract Rev 13.7). XHT's ParseHeadersAction (slot 2) and EmitReflectionAction (slot 3) should be authored as ExternalAction records via ExternalAction.Create. Set PrerequisiteItems sorted ordinal; include every .h the parse step consumes plus the .Build.toml / .Build.cs for the owning module. Set ProducedItems to the per-header {Header}.gen.h + per-header {Header}.gen.cpp outputs PLUS the per-module {Module}.init.gen.cpp aggregator and {Module}.gen.manifest, sorted ordinal (cross-references XHT.html Rev 6 Section 8 + Contract Rev 13.7 Section 7.1 / 10.3). CacheKeyComponents should include any XHT-side configuration that influences emit (specifier vocabulary version, ConstInit emit mode flag, etc.).
  • ActionHistory. XHT does not need a separate cache layer; bUseActionHistory = true (the default) opts the action into XBT's history. The cache key automatically picks up ContractVersion changes (via ComputeActionKey step 3) and IExternalAction schema changes (via step 1).
  • File-discovery rules. XHT can rely on the manifest's SourceFiles list reflecting the filesystem walk: every .cpp, .h, and .cs under the module directory appears with the appropriate flags. The PublicHeaders / PrivateHeaders / InternalHeaders category lists, however, are empty in Phase 1 (see Section 10); if XHT needs the public/private split it should walk the descriptor (or the filesystem) itself rather than trusting those fields. The CSharpSources field is populated from the filesystem walk (with .Build.cs descriptor files excluded).
  • Module-dep traversal. The manifest's module_dependencies entries carry name and interface_module. To traverse the transitive closure XHT must walk the dep graph itself; XBT does not pre-compute a transitive closure into the manifest.
  • Atomic-rename contract. XHT's action runner is XBT's ParallelExecutor; XHT must write to the TempOutputPaths the executor hands it via ActionRunContext, not to the final ProducedItem paths directly. The executor handles the rename.
