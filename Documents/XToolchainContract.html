0. Purpose & Scope

This document is the interfaces-only contract jointly designed for XPact's three build-time tools before any of them gets its own system specification:

  • XBT — XPact Build Tool. C# standalone. Reads .xengine, .xproject, and per-module .Build.cs descriptors. Builds the module dependency graph, drives reflection extraction, drives C# transpilation, schedules compile / link actions. Unreal-equivalent reference: UnrealBuildTool.
  • XHT — XPact Header Tool. C# standalone. Parses reflection markers in .h headers (C++) and reflection attributes in .cs source (C#) and emits the registration scaffolding that the runtime reflection system consumes at engine boot. Unreal-equivalent reference: UnrealHeaderTool.
  • XIL2CPP — XPact IL2CPP transpiler. C# standalone. Transpiles C# source into C++ with GC root scaffolding, exception lowering, C# string mapping, and stable symbol mangling. No Unreal precedent — closest reference is Unity's IL2CPP, but XIL2CPP transpiles directly from C# source (not IL) and emits hot-patchable, hybrid-GC-aware code rather than Mono-runtime-bound code.

The contract locks the wire and surface interfaces between these three tools and the C++ runtime systems they feed (XCore, XCoreXObject, the platform toolchains). The contract is the document each tool's spec writes against. The contract is the document the Foundation Prototype milestone validates against. The contract is the document a contract revision must reopen by name.

The contract does not cover the internal architecture of each tool. XBT's action-graph internals, dependency-cache file format, parallel executor design — not here, they belong in /Documents/XBT.html. XHT's parser AST shape, attribute reader, and emitter internals — /Documents/XHT.html. XIL2CPP's parser, lowering pipeline, and GC-emit pass — /Documents/XIL2CPP.html (will split per plan Section 3, "Systems whose HTML will likely split"). The contract is the seam; the tools are the volumes the seam holds together.

The contract is delivered in two stages per plan Section 4:

  • Stage A — Step 0 (this document). Locks the marker macro vocabulary, the file naming convention, the invocation protocol (JSON manifest), the symbol mangling rule, the GC root-registration ABI, the determinism flag propagation contract, the exception codegen ABI boundary, the C# string mapping, and the module descriptor shape. XBT consumes XHT's output opaquely — XBT does not parse XHT's binary struct layouts — so Stage A is sufficient to build XBT (System 1) and XHT's parser (System 2).
  • Stage B — Contract Addendum at XCore-4b ship (Step 4). Freezes the concrete binary struct layouts — FName, FClass, FProperty, FField with the full replication-metadata surface per plan Section 2 Replication row. XHT's emitter is provisional until then; XHT's emit format finalizes at the Addendum.
  • Step 0.5 addendum (descriptive). Pins the per-file dependency model XBT actually implements once XBT is built. Per plan Section 4: "the Step 0.5 addendum does not change XBT's behavior; it pins the model XBT chose so XHT and XIL2CPP can target it."

Decisions that genuinely await Stage B are marked inline throughout this document with <!-- STAGE-B: ... --> HTML comments and an italic note.

1. Reflection Schema — Name Table, Marker Macros, Surface Vocabulary

Per plan Section 2 Naming row, XPact mirrors Unreal's reflection vocabulary with the only rename being UObject → XObject. The C++ side uses uppercase macros with the X prefix; the C# side uses bracketed PascalCase attributes mirroring the same names.

1.1 Marker macros (C++) and attributes (C#)

The full vocabulary, locked at Stage A:

ConceptC++ markerC# attributePlacement
Reflected classXCLASS(specifiers)[XClass(specifiers)]Immediately before class declaration.
Reflected structXSTRUCT(specifiers)[XStruct(specifiers)]Immediately before struct declaration.
Reflected enumXENUM(specifiers)[XEnum(specifiers)]Immediately before enum class declaration.
Reflected interfaceXINTERFACE(specifiers)[XInterface(specifiers)]Immediately before interface class.
Reflected function/methodXFUNCTION(specifiers)[XFunction(specifiers)]Immediately before method declaration.
Reflected property/fieldXPROPERTY(specifiers)[XProperty(specifiers)]Immediately before field declaration.
Reflected delegateXDELEGATE(specifiers)[XDelegate(specifiers)]Immediately before delegate / event declaration.
Function parameter specXPARAM(specifiers)[XParam(specifiers)]Inline on parameter.
Enum value metadataXMETA(specifiers)[XMeta(specifiers)]Inline on enum member.
Body anchor (C++ only)XGENERATED_BODY()(not applicable — C# attributes are anchored by the attribute target itself)Inside class body, before first member.

To the C++ compiler all markers except XGENERATED_BODY() are empty defines. They are read by XHT's C++ front-end via a lightweight, single-pass tokenizer (not a full Clang parse) and discarded by the C++ compile. XGENERATED_BODY() is a real macro that expands via a file-id / line-number combination to a generated registration block; the line number is load-bearing. Example:

// XGameFramework module — example header
#pragma once
#include "XCoreXObject.h"

XCLASS(BlueprintType)
class AXValve : public AXActor
{
    XGENERATED_BODY()

public:
    XPROPERTY(EditAnywhere, BlueprintReadWrite, Replicated)
    float OpenFraction = 0.0f;

    XFUNCTION(BlueprintCallable)
    void SetOpenFraction(XPARAM(DisplayName = "Open Fraction") float InFraction);
};

The C# equivalent (which XIL2CPP transpiles, and XHT's C# front-end reads for reflection extraction):

// XGameFramework module — example C#
namespace Simgenics.XPact.GameFramework;

[XClass(BlueprintType = true)]
public partial class Valve : Actor
{
    [XProperty(EditAnywhere = true, BlueprintReadWrite = true, Replicated = true)]
    public float OpenFraction = 0.0f;

    [XFunction(BlueprintCallable = true)]
    public void SetOpenFraction([XParam(DisplayName = "Open Fraction")] float inFraction)
    {
        OpenFraction = inFraction;
    }
}

1.2 Specifier vocabulary

Per plan Section 2 Naming row, "Specifiers mirror Unreal verbatim." The MVP-relevant specifier set, locked at Stage A:

  • Class specifiers: Blueprintable, BlueprintType, Abstract, NotBlueprintable, Transient, Config, HideCategories, ShowCategories, ClassGroup, MinimalAPI, NotPlaceable, Placeable, Within, EditInlineNew, DefaultToInstanced.
  • Property specifiers: EditAnywhere, EditDefaultsOnly, EditInstanceOnly, VisibleAnywhere, VisibleDefaultsOnly, VisibleInstanceOnly, BlueprintReadOnly, BlueprintReadWrite, BlueprintAssignable, Replicated, ReplicatedUsing, Transient, Config, SaveGame, Instanced, Category, DisplayName, ToolTip, ClampMin, ClampMax, UIMin, UIMax, Meta.
  • Function specifiers: BlueprintCallable, BlueprintPure, BlueprintImplementableEvent, BlueprintNativeEvent, BlueprintAuthorityOnly, BlueprintCosmetic, Server, Client, NetMulticast, Reliable, Unreliable, Category, DisplayName, Exec, CallInEditor.
  • Replication specifiers (per plan Section 2 Replication row scope expansion): replication-condition values populate the ELifetimeCondition slot on FProperty — COND_None, COND_OwnerOnly, COND_SkipOwner, COND_SimulatedOnly, COND_AutonomousOnly, COND_SimulatedOrPhysics, COND_InitialOnly, COND_ReplayOnly, COND_ReplicatedOnly.

Specifiers parse identically across the C++ and C# front-ends. Unknown specifiers fail the build with a diagnostic naming the marker line. New specifiers may only be added via a Toolchain Contract revision — XHT's compile-time specifier registry is frozen alongside the contract version.

1.3 Body-macro suffix table

For each class containing XGENERATED_BODY(), XHT emits a per-file generated header ({Header}.gen.h) containing macros suffixed by purpose. These compose at the XGENERATED_BODY() expansion site. The suffix set, locked at Stage A:

SuffixPurpose
_PROLOGForward declarations + friend declarations that must appear at file scope before the class body.
_GENERATED_BODYThe composite macro XGENERATED_BODY() resolves to. Concatenates the other suffixes in correct order.
_INCLASSStatic class-registration members: StaticClass(), StaticRegisterNatives*, type-info statics.
_RPC_WRAPPERSServer / Client / NetMulticast RPC dispatch stubs.
_ACCESSORSGenerated property getters/setters where specifier flags require them (e.g., ReplicatedUsing RepNotify binding).
_FIELDNOTIFYUI-binding change-notification slots for properties with BlueprintReadWrite + FieldNotify.
_VINTERFACESVirtual interface dispatch table for interfaces this class implements.
_STANDARD_CONSTRUCTORSDefault constructor + object-initializer constructor declarations.

The composite expansion order is fixed: _INCLASS → _RPC_WRAPPERS → _ACCESSORS → _FIELDNOTIFY → _VINTERFACES → _STANDARD_CONSTRUCTORS. Generated code outside XGENERATED_BODY() — per-file _PROLOG blocks — appears at file scope before the class declaration.

1.4 Per-file ID scheme

UE's reflection system encodes file identity into the body-macro name via the on-disk header path (non-alphanumerics replaced by underscores). This couples the symbol identity to the file's filesystem location: moving a header to a different directory invalidates every consumer's file-ID-derived symbols. Per the UE reference brief gotcha list, XPact decouples file ID from on-disk path.

XPact's file-ID format:

XID_{PluginName}__{LogicalPath}_h_{LineNumber}_{Suffix}

Where:

  • PluginName — the plugin's name as declared in its .xplugin descriptor. For the engine itself this is the literal Engine. For Studio and Project plugins it is the descriptor's Name field.
  • LogicalPath — the header's logical path within the plugin (forward slashes replaced by single underscores), not its absolute filesystem path. The logical path is declared per-module in the module's .Build.cs (PublicIncludePaths / PrivateIncludePaths) and is preserved across folder reorganization. Moving the file on disk does not break consumers as long as the logical path is preserved.
  • LineNumber — line number of the XGENERATED_BODY() macro within the header. Same load-bearing role as UE.
  • Suffix — one of the suffixes from Section 1.3.

Example expansion. For AXValve in /Engine/Source/Runtime/XGameFramework/Public/Valves/XValve.h at line 14 of plugin Engine with logical path XGameFramework/Public/Valves/XValve:

// What XGENERATED_BODY() expands to (composed from generated header):
#define XID_Engine__XGameFramework_Public_Valves_XValve_h_14_GENERATED_BODY \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_INCLASS \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_RPC_WRAPPERS \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_ACCESSORS \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_FIELDNOTIFY \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_VINTERFACES \
    XID_Engine__XGameFramework_Public_Valves_XValve_h_14_STANDARD_CONSTRUCTORS

2. Hot-Reload Symbol Naming — Versioned ABI

Per plan Section 2 XIL2CPP symbol naming row (Rev 7), the transpiled-symbol mangling is a locked ABI in the Toolchain Contract. Per plan Section 2 Hot-reload commitment row, hot-reload requires stable exported symbol names for hot-patchable functions. Per plan Section 11 Step 5.5 (g), repeated XIL2CPP runs over the same input produce byte-identical mangled symbol names. This section locks the mangling rule.

2.1 Native C++ side

Native C++ symbol mangling is whatever the platform compiler produces — MSVC's mangling on Win64, Itanium ABI mangling on Linux and Android (Clang). Both are stable across builds of the same source. The contract requires only that the build be byte-reproducible, which adds two flags to the platform-toolchain flag tables (see Section 4):

  • MSVC: /Brepro to suppress timestamps in the output binary.
  • Clang: -frandomize-layout-seed-file= pinned to an empty / deterministic seed; combined with -fno-ident for object-file determinism; -Wl,--build-id=none at link.

These flags are mandatory on every XBT-driven build, not only sim-path TUs. The Foundation Prototype reproducibility criterion (plan Section 11 Step 5.5 (g)) cannot be satisfied without them.

2.2 Transpiled C# side

XIL2CPP-transpiled symbols use a custom, contract-versioned mangling rule:

{ContractVersion}__{Namespace}::{Type}::{Method}{GenericArgManglings}{ParamManglings}

Component definitions:

  • {ContractVersion}: the literal _v1 for the Stage A contract. A future contract revision that breaks the mangling bumps to _v2. A version bump may only be done via a deliberate Toolchain Contract revision — never silently.
  • {Namespace}: dot-separated namespace path with dots replaced by ::. Example: Simgenics.XPact.GameFramework becomes Simgenics::XPact::GameFramework.
  • {Type}: the simple type name. Nested types are joined by ::.
  • {Method}: the simple method name. C# operator overloads use op_Add, op_Equality, etc. (CLR convention). Constructors are $ctor. Static constructors are $cctor.
  • {GenericArgManglings}: for generic methods, _G_ followed by a comma-separated list of mangled generic argument types in angle brackets, recursively mangled. Empty when not generic.
  • {ParamManglings}: _P_ followed by a parenthesized comma-separated list of mangled parameter types. Reference types prefix R, value types prefix V, by-ref prefix B, in/out prefix I/O. Empty parentheses for parameterless methods.

2.3 Free-function form with explicit self

Per the UE reference brief recommendation: every transpiled C# method becomes a free function (not a member function) with an explicit XObject* self first parameter. This makes Live-Coding-style RVA-rewrite trampolines work cleanly — the patcher writes one jump at the function's entry point, without vtable-slot rewriting. Vtable dispatch for virtual methods is handled by a generated dispatcher (also a free function) that performs the table lookup and tail-calls the resolved free function. Per plan Section 2 Hot-reload commitment row, no virtual-method signature changes are permitted mid-session, so the vtable layout is stable across patches.

Example. Given the C# above:

// C# source
namespace Simgenics.XPact.GameFramework;
public partial class Valve : Actor {
    public void SetOpenFraction(float inFraction) { /* ... */ }
}

The transpiled symbol is:

_v1__Simgenics::XPact::GameFramework::Valve::SetOpenFraction_P_(R Simgenics::XPact::GameFramework::Valve, V float)

And the C++ declaration XIL2CPP emits:

// Transpiled C++ — free function with explicit self
extern "C" void _v1__Simgenics__XPact__GameFramework__Valve__SetOpenFraction_P_R_Simgenics__XPact__GameFramework__Valve_V_float(
    Simgenics::XPact::GameFramework::Valve* self,
    float inFraction);

(The angle-bracket / parenthesis / colon characters in the conceptual mangling above are translated to single-underscore tokens for the actual linker-visible symbol — :: → __, parentheses dropped, commas and spaces → _. The translation is deterministic and reversible.)

2.4 Determinism requirement

Per plan Section 11 Step 5.5 criterion (g): repeated XIL2CPP runs over the same input produce byte-identical mangled symbol names. This requires:

  1. The mangling rule is purely structural — no hash, no random, no build-time-derived suffix.
  2. The generic-instantiation walk visits arguments in source-declaration order.
  3. XIL2CPP's internal dictionary iteration over namespaces / types / methods is sorted by name before emit. No insertion-order dependence on the parse.
  4. The reproducibility flags (/Brepro, -frandomize-layout-seed-file=, etc.) propagate from XIL2CPP's own build of itself, not just the user's build — XIL2CPP's binary is itself reproducible.

3. GC Root-Registration ABI

Per plan Section 2 Memory/GC row, XPact uses a hybrid memory model: a non-moving precise mark-and-sweep GC for XObject-derived types only, with plain C# value types and containers (List<T>, Dictionary<K,V>, string, structs) transpiling to native deterministic-lifetime equivalents that are NOT GC-managed. When a non-GC container holds XObject references, the container explicitly registers GC roots at construction and de-registers at destruction; the IL2CPP transpiler emits this scaffolding by statically analyzing generic instantiations.

This section locks the extern "C" surface XIL2CPP emits at those construction / destruction sites.

3.1 The three primitives

extern "C" {

    // Single-slot registration. slot points to where the XObject*-typed reference
    // lives. The GC dereferences slot each mark cycle and traces through it.
    void XGC_RegisterRoot(void** slot, XGCRootKind kind);

    // Single-slot deregistration. Must be called for every successful RegisterRoot.
    void XGC_UnregisterRoot(void** slot);

    // Conservative range registration. start..start+count*stride is treated as a
    // contiguous array of void* slots. The GC traces each one. Used for
    // List<object>-style non-statically-typed containers where individual
    // per-slot registration would be too noisy.
    void XGC_RegisterRootRange(void** start, size_t count, size_t stride);

    void XGC_UnregisterRootRange(void** start);

}

3.2 XGCRootKind

enum class XGCRootKind : uint8_t {
    Strong,        // mark prevents collection
    Weak,          // GC clears the slot if the referent is collected
    Conservative   // treat slot as possibly-pointer; only register if non-null
                   // during mark; ignore type info. Used for List<object> etc.
};

The transpiler chooses the kind statically based on the generic instantiation:

  • Generic type argument is statically XObject-derived (List<XActor>, Dictionary<FName, XComponent>): XGCRootKind::Strong, registered per slot in XGC_RegisterRoot calls during container growth.
  • Generic type argument is statically a value type (List<int>, List<FVector>): no GC scaffolding emitted at all. The container is pure RAII.
  • Generic type argument is object or a non-statically-typed interface that could hold XObjects (List<object>, Dictionary<string, object>): XGCRootKind::Conservative, registered as a range via XGC_RegisterRootRange.

Per plan Section 2 Memory/GC row: "XIL2CPP emits a build-time warning when such a pattern appears on a sim-path TU because the per-mutation root-register/unregister cost is real." This warning is mandatory; it is not suppressible from .cs source. It is suppressible only at the module level via an explicit SimPathConservativeRootsOK = true field in the module's .Build.cs, which is also visible in build logs.

3.3 Example: List<XActor>

Suppose the C# author writes:

// C# — gameplay code
List<Actor> ActiveActors = new List<Actor>();
ActiveActors.Add(SomeActorRef);
ActiveActors.RemoveAt(0);

XIL2CPP transpiles this with explicit root scaffolding around every container mutation. Conceptual emit shape (illustrative, not normative):

// Transpiled C++ shape
class List_Actor {
    Actor** m_data;       // dynamic array of XObject*-typed slots
    size_t  m_count;
    size_t  m_capacity;

public:
    void Add(Actor* item) {
        EnsureCapacity(m_count + 1);
        m_data[m_count] = item;
        XGC_RegisterRoot(reinterpret_cast<void**>(&m_data[m_count]),
                         XGCRootKind::Strong);
        ++m_count;
    }

    void RemoveAt(size_t i) {
        XGC_UnregisterRoot(reinterpret_cast<void**>(&m_data[i]));
        // shift remaining slots down (each shifted slot gets its registration
        // re-pointed via internal XGC_RebindRoot — not exposed externally)
        ...
    }

    void EnsureCapacity(size_t needed) {
        if (needed <= m_capacity) return;
        // Reallocate. For every live slot, unregister at old address and
        // re-register at new address (the GC slot address must point into
        // the live buffer at all times).
        ...
    }

    ~List_Actor() {
        for (size_t i = 0; i < m_count; ++i)
            XGC_UnregisterRoot(reinterpret_cast<void**>(&m_data[i]));
        free(m_data);
    }
};

3.4 Example: List<object> conservative range

// Transpiled shape for List<object>
class List_object {
    void** m_data;
    size_t m_count;
    size_t m_capacity;

public:
    void EnsureCapacity(size_t needed) {
        if (needed <= m_capacity) return;
        if (m_count > 0) XGC_UnregisterRootRange(m_data);
        void** newData = reinterpret_cast<void**>(realloc(m_data, needed * sizeof(void*)));
        m_data = newData;
        m_capacity = needed;
        if (m_count > 0)
            XGC_RegisterRootRange(m_data, m_count, sizeof(void*));
    }
    // Build-time warning emitted at this instantiation site if the
    // owning module's .Build.cs has SimPath = true.
    ...
};

3.5 Internals not in the contract

The contract locks only the extern "C" surface. The collector's internal root-set data structures, the locking discipline for concurrent registration, the bump-allocated root-table format, the card-table format, the write-barrier intrinsic shape — all internal to XCoreXObject and documented there (plan Section 3: XCoreXObject "will split into multiple docs: allocator + collector + reflection + write-barriers/roots"). 4. Determinism Flag Propagation

Per plan Section 2 Determinism row, sim-path translation units require /fp:precise + -ffp-contract=off + Sleef-vendored transcendentals; -ffast-math / /fp:fast / FMA contraction are banned; platform libm calls error at link on sim-path TUs.

4.1 Module-level declaration

A module declares itself as sim-path via an explicit field on its .Build.cs descriptor:

// XPhysics.Build.cs
public class XPhysics : ModuleRules
{
    public XPhysics(ReadOnlyTargetRules Target) : base(Target)
    {
        Tier = ModuleTier.Engine;
        ModuleType = ModuleType.Runtime;
        Languages = Languages.Cpp;

        SimPath = true;       // <-- declares this module's TUs as sim-path

        PublicDependencyModuleNames.AddRange(new[] { "XCore", "XCoreXObject", "XTaskGraph" });
        // ...
    }
}

The field is on the module level (matches Unreal's per-module enum-then-translate pattern). Per-file overrides are not supported in MVP. If a single file in a non-sim-path module legitimately needs sim-path semantics, the file must be split into its own micro-module. This matches the UE pattern observed in the reference brief.

4.2 Flag translation table

XBT carries a per-platform-toolchain flag translation table. When SimPath = true, XBT adds the following flags to the C++ compile environment for the module's TUs:

ToolchainFlags added on SimPath = trueFlags banned (error if present)
MSVC (Win64) /fp:precise, /Brepro /fp:fast, /fp:except
Clang (Linux) -ffp-contract=off, -fno-fast-math, -fno-finite-math-only -ffast-math, -funsafe-math-optimizations, -ffp-contract=fast, -ffp-contract=on
Clang (Android ARM64) same as Clang Linux + -mno-fma (prevent target-default FMA enablement) same as Clang Linux

Banned flags appearing in any .Build.cs AdditionalCompilerArguments on a SimPath module fail the build with a diagnostic naming the flag and module.

4.3 Transcendental library substitution

For SimPath TUs, XBT substitutes platform libm with Sleef (configured in non-FMA mode) or vendored Chebyshev/Remez polynomial implementations. Substitution mechanism:

  • XBT injects a header gate #include "XSimPathMathOverrides.h" at the top of every TU in the SimPath module via the compiler's /FI (MSVC) or -include (Clang) flag.
  • The override header #defines sin, cos, tan, atan2, sqrt, pow, exp, log, and their f variants to redirect to the Sleef-vendored symbols (e.g., XSleef_sin).
  • Link-time: XBT excludes platform libm from the link line for SimPath modules. Any unresolved reference to __libm_sse2_sin (MSVC) or sin@GLIBC_2.2.5 (glibc) etc. fails the link with a clear diagnostic. The vendored library is linked in its place.

4.4 Banned-API check

SimPath TUs additionally get a build-time error if they call non-deterministic platform APIs. The banned set is enumerated in a small text file (XSimPathBannedAPIs.txt) consulted by an XBT pre-compile action:

# XSimPathBannedAPIs.txt — representative entries
GetSystemTime
GetTickCount
QueryPerformanceCounter   # use XTime::DeterministicNow() instead
gettimeofday
clock_gettime
GetCurrentThreadId        # don't branch on thread identity in sim path
rand
srand

The check is a lightweight regex pass over the TU's source. False positives can be allowlisted per-line via an end-of-line comment marker // XSIMPATH_OK with a rationale string.

4.5 Per-target settings

XBT also propagates a per-target settings struct to XHT and XIL2CPP — the analog of UE's UHTTargetSettings. The struct carries SimPathConservativeRootsAllowed, FipsMode (per plan Section 2 Network security row), the contract version, and the target's platform identifier. XHT and XIL2CPP read this in addition to the per-module manifest.

5. Exception Codegen Switch — ABI-Stable Boundary

Per plan Section 2 Exception handling row: "C++ exceptions off in Shipping, on in Debug/DebugGame/Development/Test. XIL2CPP emits C# throw/catch as native exceptions in Dev/Test configurations and as Result<T,E> lowering in Shipping. ABI stability: public API surfaces of transpiled C# functions go through an ABI-stable boundary layer defined in the Toolchain Contract (Step 0, item 5) — same C function signature across configs, with internal lowering varying. Cross-config linking is supported because all call sites see the same external signature; only the body differs. Third-party libraries linked in Shipping must be exception-clean. Result<T,E> type definition (struct layout, generic instantiation rules, reflection coverage, serialization semantics) is part of the Toolchain Contract's Step 0, item 5 deliverable — not deferred."

5.1 The ABI boundary

Every transpiled C# method gets two artifacts:

  1. A shim entry point: an extern "C" free function with a fixed signature determined by the C# method's static signature. This signature is identical across all build configurations. Call sites — whether from C++, from other transpiled C#, or from Blueprint dispatch — bind against this shim.
  2. A body implementation internal to the shim. The body's lowering differs between Dev/Test (native C++ exceptions) and Shipping (Result<T,E>). The shim adapts the body's output to the contract-defined return discipline.

The shim signature, given C# method T Foo(A a, B b):

// Shim entry point — identical across Dev and Shipping
extern "C" void _v1__Foo_Shim(
    void* self,             // null for static methods
    A a,
    B b,
    XResult* outResult);    // out-parameter for both the value and the error

The XResult out-parameter carries either the successful return value or a typed error descriptor — same layout in both configs.

5.2 XResult layout

// Plain C++ struct — layout locked at Stage A
struct alignas(16) XResult {
    enum class Discriminator : uint8_t { Success, Error };
    Discriminator   discriminator;
    uint8_t         _padding[7];
    union {
        // SuccessValue is type-erased to a tagged buffer. Each shim emits
        // type-specific accessors. Storage is up to 56 bytes inline; larger
        // returns spill via XResult::SpillSlot pointer.
        struct {
            uint8_t       buffer[56];
        } success;
        struct {
            XErrorCode    code;          // numeric ID into XError descriptor table
            const char*   typeName;      // mangled type of the original C# exception
            const char*   message;       // UTF-8, lifetime tied to call stack
            void*         stackTrace;    // null in Shipping; native trace in Dev/Test
        } error;
    };
};

Note: layout is illustrative; final byte-exact layout finalizes at Stage B if FProperty layout influences it. The external surface (discriminator + access pattern) is locked at Stage A.

5.3 Dev/Test lowering — native exceptions

The shim body is wrapped in a try / catch (...) block. On normal return, the shim copies the return value into the XResult::success buffer and sets the discriminator to Success. On caught exception, the shim translates the native exception to XResult::error and sets the discriminator to Error:

// Dev/Test shim body shape
extern "C" void _v1__Foo_Shim(void* self, A a, B b, XResult* outResult) {
    try {
        T value = _v1__Foo_Body(self, a, b);   // body throws on C# throw
        outResult->discriminator = XResult::Discriminator::Success;
        new (outResult->success.buffer) T(std::move(value));
    } catch (const XCSharpException& ex) {
        outResult->discriminator = XResult::Discriminator::Error;
        outResult->error.code = ex.code;
        outResult->error.typeName = ex.typeName;
        outResult->error.message = ex.message;
        outResult->error.stackTrace = ex.captureStack();
    }
}

5.4 Shipping lowering — Result<T,E>

In Shipping, C# throw sites lower to early-return of an XResult with the error discriminator. Every C# try / catch lowers to discriminator-checked dispatch. The shim becomes a thin pass-through:

// Shipping shim body shape
extern "C" void _v1__Foo_Shim(void* self, A a, B b, XResult* outResult) {
    _v1__Foo_Body(self, a, b, outResult);
    // Body writes to outResult directly. No try/catch — exceptions
    // are not raised in Shipping bodies.
}

The body's internal structure differs between configs; the shim's external signature does not. A C++ caller linking against the shim never sees the difference. Cross-config linking works: an editor module compiled in Development can call into a runtime module compiled in Shipping (or vice versa, for hot-reload scenarios).

5.5 Generic instantiation rules

The contract requires that T and E in Result<T,E> instantiate as either:

  • C++ trivially destructible types (POD, simple value types), or
  • XObject-derived types (which the GC owns and which require no in-buffer destructor — the buffer holds the pointer only).

Non-trivially-destructible non-XObject types (e.g., FString, TArray<T>, custom RAII handles) require explicit destruction. The shim emits the appropriate destructor call when XResult goes out of scope on the calling side; XIL2CPP generates this teardown automatically at every call site.

5.6 Reflection coverage

XResult is itself reflected as an XSTRUCT so editor inspection, serialization, and debugger visualization work uniformly:

XSTRUCT()
struct XResult {
    XPROPERTY(VisibleAnywhere) EDiscriminator Discriminator;
    XPROPERTY(VisibleAnywhere, EditCondition = "Discriminator == EDiscriminator::Error") XErrorDescriptor ErrorInfo;
    // Success value is type-erased; editor renders via owning method's signature.
};

5.7 Serialization semantics

When XResult is serialized (e.g., as a multi-user RPC return), the wire format is: discriminator byte + (on Success: serialized T per its own serializer; on Error: serialized error descriptor — code + typeName + message; stackTrace is dropped on the wire). Cross-config: a Development sender and a Shipping receiver agree on the wire format because both serialize through the same XResult reflection path.

5.8 Third-party library constraint

Per plan Section 2 Exception handling row, third-party libraries linked in Shipping must be exception-clean. XBT validates this at link time on Shipping configs by inspecting the third-party library's metadata: any .lib / .a with EH information present fails the Shipping link with a diagnostic naming the library. /Engine/Source/ThirdParty/Licenses/INVENTORY.html (plan Section 2 Third-party license inventory row) gains a column noting exception-cleanness for each entry.

6. C# string ↔ FString Mapping

Per plan Section 2 String encoding row (Rev 4): FString is UTF-8 on all platforms. C# string transpiles to "a transpiler-emitted immutable string handle wrapping FString — this handle is invisible in C# source code; user code writes string and ReadOnlySpan<char> as in standard C#. Literal C# strings are emitted as UTF-8 constants at build time (no runtime conversion); the transpiler guarantees pointer-identity for compile-time-interned literals so ReferenceEquals(nameof(X), "X") holds." Per plan Section 2 C# string indexing semantics row (Rev 7): s[i] becomes O(n).

6.1 The handle type

XIL2CPP transpiles C# string to a value-type handle:

// Transpiled shape
struct XCSharpString {
    const FString* m_storage;    // points into interned FName table OR
                                 // into per-call cached view
};

The handle is 8 bytes on all platforms, trivially copyable, no destructor. The FString storage it points into is owned either by the global interned literal pool (for compile-time string literals) or by the runtime string-builder allocator (for runtime-computed strings — lifetime tracked by call-stack arena or by explicit user-side GC root in the rare case the string escapes).

6.2 Literal interning

Compile-time C# string literals emit as UTF-8 constants in the binary's read-only data section. XIL2CPP guarantees pointer identity for them: every occurrence of "open valve" in any transpiled C# resolves to the same const FString*. nameof(X), typeof(X).Name, and string-literal usages all participate in the interning pool.

Example:

// C#
string a = "open valve";
string b = "open valve";
if (ReferenceEquals(a, b)) { /* always true under XPact */ }
if (ReferenceEquals(nameof(Valve), "Valve")) { /* also true */ }

Both a and b transpile to handles whose m_storage points to the same const FString* in .rodata.

6.3 The shared FName table

Per the UE reference brief recommendation: a single shared FName table across XHT-generated and XIL2CPP-generated callers, with stable indices across hot-reload. FName::FromString("open valve") from C++ and the C# literal "open valve" resolve to the same FName index. Per plan Section 2 String encoding row, FName is case-sensitive in MVP — hashing and comparison are bytewise.

6.4 Indexing & iteration

The s[i] operator walks UTF-8 to find the i-th codepoint — O(n). XIL2CPP emits a build-time warning on s[i] usage in sim-path TUs. Idiomatic alternatives ship in the C# binding surface:

// C# idiomatic alternatives
ReadOnlySpan<char> span = s.AsSpan();      // O(n) materialize once, O(1) afterward
int idx = s.IndexOf('v');                  // O(n) but single pass
string sub = s.Substring(0, 5);            // O(n) materialize once

// New API documented in the C# binding surface
foreach (int codepoint in s.AsCodepoints())   // iterator, no intermediate buffer
{
    // ...
}

6.5 Runtime conversion at the IL2CPP boundary

When C# string crosses to C++ (e.g., a Blueprint-callable C++ function takes const FString&), the conversion is zero-copy: the handle's m_storage pointer is passed directly. When a C++ FString crosses to C# (e.g., a C++-implemented property returns FString to a C# field), XIL2CPP emits a cached-view wrapper that allocates an XCSharpString handle pointing into the FString. The cached view is interned per-call-stack-frame to avoid repeated allocations for the same FString within a frame.

6.6 What Stage A locks vs. Stage B

Stage A locks: the handle layout, literal interning behavior, FName table sharing, indexing semantics, the iterator surface (AsSpan, AsCodepoints, IndexOf, Substring).

Stage B (Contract Addendum) freezes the FName entry binary layout in the shared table. Until then, FName index space is virtualized via XCore-4a's provisional FName implementation; the index is stable across hot-reload at Stage A, but the on-disk serialized format finalizes at Stage B.

7. Two-Stage XHT Emit-Format Freeze

Per plan Section 4 (Rev 4 two-stage freeze clarification): "XHT's emit format is frozen in two stages. (a) Step 0 contract locks the interface — file naming, invocation protocol, marker macros, surface vocabulary. (b) The binary schema (FName / FClass / FProperty / FField layout, including all replication-metadata slots) is frozen at the Contract addendum that lands when XCore-4b ships at Step 4. Consequence: XHT Step 2 delivers parser-complete + emitter-provisional. XHT's emitter finalizes its concrete output struct layouts at Step 4 when the addendum lands."

7.1 Stage A — what this document locks

Stage A locks the following XHT-relevant interfaces:

  • Generated file naming. For input header {ModulePath}/{HeaderName}.h, XHT emits {ModuleIntermediate}/{HeaderName}.gen.h. For each module, XHT emits {ModuleIntermediate}/{ModuleName}.gen.cpp aggregating all module-level registration calls.
  • Invocation protocol. XHT runs as a subprocess of XBT (or as an in-process library — XBT's choice, internal). XBT writes a JSON manifest (see Section 10) and either passes its path on the command line or calls XHT's in-process entry point with the parsed manifest.
  • Marker macro vocabulary. Section 1 above.
  • Body-macro suffix table. Section 1.3 above.
  • Per-file ID scheme. Section 1.4 above.
  • Per-module text manifest. XHT emits, alongside its binary outputs, a small text manifest ({ModuleName}.gen.manifest) listing the generated files. XBT reads this manifest as XHT's opaque output; XBT does NOT parse the .gen.h or .gen.cpp content. Per plan Section 4: "XBT consumes XHT output opaquely. XBT treats XHT's output as opaque artifacts indexed by file-level dependency markers."

7.2 Stage B — what the Contract Addendum will lock

Stage B (Contract Addendum at XCore-4b ship, Step 4) freezes:

  • FName binary layout — the on-disk and in-memory shared-table entry record.
  • FClass binary layout — class-descriptor struct with vtable info, super-class pointer, property list head, function list head.
  • FProperty binary layout including all replication-metadata slots: ELifetimeCondition, RepNotify callback function-pointer slot, delta-compression hint flags, replication group ID, owner-only / autonomous-proxy-only / simulated-proxy-only flags.
  • FField binary layout — the generalized property-or-field descriptor.
  • The choice between UE's Params-style emit and ConstInit-style emit — XHT spec resolves at System 2.

XHT's parser is complete at System 2 (Step 2 in plan Section 4 build order). The emitter is provisional until Step 4. Consumers of XHT-generated headers between Step 2 and Step 4 build against the parser-provided field set but should not depend on exact binary layout. XCore-4a (Step 3) uses a small set of forward-declared opaque types in places that would otherwise see XHT's output; XCore-4b's ship simultaneously finalizes both XHT's emit and the runtime's consumption.

8. Per-File Dependency Model

Per plan Section 4: "The contract is delivered with explicit 'TBD at XBT implementation' markers for the per-file dependency model (which can only be hardened once XBT is built). Step 0.5 addendum: descriptive — documents the per-file dependency model that XBT actually implements, rather than prescribing one ahead of time."

This section locks the shape of the dependency-tracking surface and defers the algorithm to Step 0.5.

8.1 What XBT identifies

  • C++ dependencies: identified via include-graph walk. Each .cpp's transitive includes form the prerequisite set for its compile action. XBT carries a per-TU CppDependencyCache analogous to UE's; format defined in /Documents/XBT.html.
  • C# dependencies: identified via using directive + assembly-reference walk. Each .cs's referenced assemblies and dependent .cs within the same module form the prerequisite set for its transpilation action.
  • Cross-language dependencies within a module: when a .cpp consumes XHT-generated headers (which contain registration scaffolding for both C++ and transpiled C# types in the module), the .cpp's dependency record lists every {Header}.gen.h it included. When any of those generated headers changes (because the source header or source .cs that produced it changed), the .cpp is reinvalidated.

8.2 Opaque consumption of XHT output

Per plan Section 4: XBT does not parse XHT's binary struct layouts. XBT consumes the per-module text manifest XHT emits (Section 7.1) plus the on-disk content hash of each generated file. When the content hash changes, downstream consumers reinvalidate. This means XBT at Step 1 (System 1) is decoupled from XHT's emit-format finalization at Stage B — XBT does not need to change when XHT's binary schema freezes.

8.3 Cross-language dependency record

For each compile action, XBT records "which XHT-output files were consumed when compiling each .cpp." On the next build, XBT re-checks each recorded file's content hash. If any has changed, the consumer is rebuilt.

Conceptual record shape (illustrative — final format defined in /Documents/XBT.html):

// Per-TU dependency record (.deps file, XBT internal)
{
    "tu": "Engine/Source/Runtime/XGameFramework/Private/XValve.cpp",
    "consumed_xht_outputs": [
        { "path": "Intermediate/Engine/XGameFramework/XValve.gen.h", "hash": "ab12..." },
        { "path": "Intermediate/Engine/XGameFramework/XGameFramework.gen.cpp", "hash": "cd34..." }
    ],
    "consumed_includes": [
        ...
    ]
}

8.4 Step 0.5 addendum scope

The Step 0.5 addendum, delivered after XBT ships at System 1, will document:

  • The exact on-disk format of the dependency cache.
  • The hash algorithm (likely SHA-256 or xxHash3 — XBT spec decides).
  • The invalidation rules for module-graph topology changes (a module added / removed / retiered).
  • The garbage-collection rules for stale dependency records.

Per plan Section 4: "The Step 0.5 addendum does not change XBT's behavior; it pins the model XBT chose so XHT and XIL2CPP can target it."

9. Module Descriptor Shape — .Build.cs

Per plan Section 2 Module composition row: "Mixed-language modules. One module = one DLL = one source tree containing .h/.cpp/.cs freely. XBT enforces a per-file dependency graph so touching one .cs doesn't regen the whole module." Per plan Section 2 Tier dependency enforcement row (Rev 7): "Each module's .Build.cs declares its tier (Tier = Engine | Studio | Project) as an explicit field. XBT rejects dependency edges that violate Engine < Studio < Project ordering at module-resolution time."

This section locks the ModuleRules base class shape that every .Build.cs derives from.

9.1 The base class

// XBT — ModuleRules base (shape locked here; full body in XBT spec)
public abstract class ModuleRules
{
    // === Identity ===

    // Per plan Rev 7 Tier dependency enforcement row.
    public ModuleTier Tier { get; set; }

    // Runtime / Editor / Developer / Programs / ThirdParty.
    // Per plan Section 6 footnote: "Tier" here refers to the Unreal-convention
    // subfolder name — not the three reusability tiers above.
    public ModuleType ModuleType { get; set; }

    // Cpp | CSharp | Both. Mixed-language modules are first-class.
    public Languages Languages { get; set; } = Languages.Cpp;

    // === Sim-path declaration ===

    // Per plan Section 2 Determinism row + Section 4 of this contract.
    public bool SimPath { get; set; } = false;

    // Per Section 3 of this contract — suppresses the List<object> warning
    // when the module legitimately needs it on sim path.
    public bool SimPathConservativeRootsAllowed { get; set; } = false;

    // === Dependencies ===

    // Public: visible to dependents through this module's public headers.
    public List<string> PublicDependencyModuleNames { get; } = new();

    // Private: used only by this module's implementation; not exposed to dependents.
    public List<string> PrivateDependencyModuleNames { get; } = new();

    // Dynamically loaded: this module loads these at runtime via XLiveCoding's
    // hot-load mechanism. Not linked at build time.
    public List<string> DynamicallyLoadedModuleNames { get; } = new();

    // === Include paths ===

    public List<string> PublicIncludePaths { get; } = new();
    public List<string> PrivateIncludePaths { get; } = new();

    // Public include-only dependencies — the dependent module's headers are
    // visible but no link is performed (analog of UE's PublicIncludePathModuleNames).
    public List<string> PublicIncludePathModuleNames { get; } = new();

    // === Preprocessor definitions ===

    public List<string> PublicDefinitions { get; } = new();
    public List<string> PrivateDefinitions { get; } = new();

    // === Compile environment ===

    public PCHUsageMode PCHUsage { get; set; } = PCHUsageMode.Default;

    // Per plan Section 2 Determinism row + Section 4 of this contract:
    // overridden to Precise when SimPath = true.
    public FPSemantics FPSemantics { get; set; } = FPSemantics.Default;

    public OptimizeCodeMode OptimizeCode { get; set; } = OptimizeCodeMode.Default;

    // Per plan Section 2 Exception handling row — per-config bool.
    public bool bEnableExceptions { get; set; } = true;

    public bool bUseRTTI { get; set; } = false;
    public bool bUseUnity { get; set; } = true;
    public bool bWarningsAsErrors { get; set; } = true;

    // === Constructor takes target view ===

    protected ModuleRules(ReadOnlyTargetRules target) { /* ... */ }
}

9.2 Circular dependencies

Per the UE reference brief: UE supports CircularlyReferencedDependentModules as an explicit allow-list. XPact bans circular module dependencies outright at the contract level. XBT fails the build at module-resolution time with a diagnostic naming the cycle. There is no allow-list. Modules that genuinely need bidirectional access must be merged or split — the cycle is an architectural smell that the contract refuses to launder.

9.3 Tier enforcement

XBT validates these edges at module-resolution time:

  1. A module with Tier = Engine may only depend on Engine modules.
  2. A module with Tier = Studio may depend on Studio or Engine modules.
  3. A module with Tier = Project may depend on Project, Studio, or Engine modules.

Per plan Section 2 Tier dependency enforcement row: "Source-tree path checks are NOT used — paths can be symlinked or restructured; the declared tier in .Build.cs is canonical." Violations fail the build at resolution.

9.4 Engine-version compatibility

Per plan Section 2 Plugin versioning & pinning row (Rev 8): XBT enforces engine-version compatibility at build time — the project's declared EngineVersion must satisfy every enabled Studio plugin's MinEngineVersion ≤ EngineVersion ≤ MaxEngineVersion. The plugin descriptor (.xplugin) is read by XBT alongside .Build.cs. Schema validation is part of module resolution.

9.5 RulesAssembly compilation

UE compiles .Build.cs files via Roslyn at startup, caching the assembly by source-hash. XPact's choice between Roslyn-compiled rules and a declarative-only subset is internal to XBT — either approach satisfies this contract. The contract only requires: hash-keyed caching of the rules artifact; deterministic ordering of module discovery; clear failure mode when a .Build.cs fails to compile or load. Plan Section 4 places this decision in XBT's spec, not here.

9.6 Example: a mixed-language module

// /Engine/Source/Runtime/XScoring/XScoring.Build.cs
public class XScoring : ModuleRules
{
    public XScoring(ReadOnlyTargetRules target) : base(target)
    {
        Tier = ModuleTier.Engine;
        ModuleType = ModuleType.Runtime;
        Languages = Languages.Both;          // .h/.cpp/.cs all live here
        SimPath = true;                       // scoring tick participates in lockstep

        PublicDependencyModuleNames.AddRange(new[]
        {
            "XCore", "XCoreXObject", "XSerialization", "XTaskGraph"
        });
        PrivateDependencyModuleNames.AddRange(new[]
        {
            "XTelemetry"
        });

        PublicIncludePaths.Add("XScoring/Public");
        PrivateIncludePaths.Add("XScoring/Private");

        // FPSemantics auto-set to Precise because SimPath = true.

        bUseRTTI = false;
        bWarningsAsErrors = true;
    }
}

10. Toolchain Pipeline — XBT → XHT → XIL2CPP → C++ compile → link

This section locks the end-to-end invocation sequence and the JSON manifest XBT emits as the single source of truth shared with XHT and XIL2CPP. The manifest is the analog of UE's UHTManifest, extended to cover C# files as well.

10.1 The sequence

  1. XBT discovery + graph build. XBT reads the root engine descriptor (/Engine/Engine.xengine), the project descriptor (/Projects/<ProductName>/<ProductName>.xproject), and every reachable .Build.cs. Validates Tier per Section 9.3; validates engine-version compatibility per Section 9.4; validates every enabled plugin's MinEngineVersion / MaxEngineVersion. Builds the module dependency graph. Fails on any cycle or constraint violation.
  2. XBT manifest emit. XBT writes a JSON manifest to Intermediate/Build/{Target}/{Configuration}/Manifest.json (path illustrative). Format below.
  3. XHT invocation. XBT invokes XHT with the manifest path. XHT reads the manifest, parses C++ headers (single-pass tokenizer for reflection markers; the C++ compile happens later and is authoritative for type-checking the C++) and attribute-marked .cs files (XHT's C# front-end), and emits per-header {Header}.gen.h, per-module {Module}.gen.cpp, and the per-module text manifest {Module}.gen.manifest. XHT runs in parallel across modules (no inter-module dependencies in the parse phase).
  4. XIL2CPP invocation. XBT invokes XIL2CPP with the same manifest. XIL2CPP reads the manifest, transpiles .cs files into .cpp/.h with GC root scaffolding (Section 3), exception codegen switch (Section 5), C# string handle emission (Section 6), and symbol mangling (Section 2). XIL2CPP also runs in parallel across modules.
  5. Copyright validation. XBT runs ValidateCopyright action over every authored source file in the build (.h, .cpp, .cs; not generated files; not /Engine/Source/ThirdParty/). Per plan Section 2 Copyright / licensing row: every file must begin with // Copyright Simgenics. All Rights Reserved. Build fails on any missing header. The action is cached by source hash; an unchanged file is not re-validated.
  6. C++ compile actions. XBT schedules compile actions: original .cpp, XHT-generated .gen.cpp, XIL2CPP-generated .cpp. Per-TU flag derivation per Section 4. Action graph — each compile is an IExternalAction with explicit Prerequisites / Produces.
  7. Link. XBT links each module into a DLL. Banned-platform-libm check (Section 4) applies on SimPath modules. Exception-cleanness check on third-party libs (Section 5.8) applies on Shipping.

10.3 Action graph

Every step that produces or consumes files is an action with explicit prerequisites and produced files. The contract names these action types:

  • ValidateCopyrightAction — per source file. Cached by source hash. Output: a marker file in Intermediate.
  • WriteManifestAction — one per build. Output: the JSON manifest.
  • XHTAction — one per module. Inputs: manifest + all module headers + all module .cs (read by XHT's C# front-end). Outputs: {Header}.gen.h per public/private header + {Module}.gen.cpp + {Module}.gen.manifest.
  • XIL2CPPAction — one per module. Inputs: manifest + all module .cs files + (XCoreXObject's compiled header surface, for the GC ABI emit). Outputs: transpiled .cpp/.h in the module's intermediate directory.
  • CompileCppAction — one per .cpp (original, XHT-generated, or XIL2CPP-generated). Inputs: .cpp + transitive includes. Output: .obj/.o.
  • LinkModuleAction — one per module. Inputs: all .obj/.o + dependency-module import libs. Output: module DLL.

Incremental builds re-run only actions whose declared prerequisites have changed. Per plan Section 11 Step 5.5 (g): byte-identical compile output across two clean builds is a Foundation Prototype pass criterion — achieved via the reproducibility flags in Section 2.1 plus deterministic action scheduling.

12. Verification

This section enumerates the verifications that XBT.html, XHT.html, and XIL2CPP.html specs (plus their implementations) must satisfy. Several map directly to Foundation Prototype pass criteria (plan Section 11 Step 5.5). Others are contract-internal acceptance gates that XBT enforces during routine builds.

12.1 Reproducibility test

Statement: Two clean builds of the same source on the same machine produce byte-identical compile outputs and byte-identical link outputs. This includes generated headers, transpiled C++, .obj/.o files, and final DLLs.

Mechanism: The reproducibility flags from Section 2.1 (/Brepro, -frandomize-layout-seed-file=, --build-id=none) plus XIL2CPP / XHT's deterministic ordering disciplines from Section 2.4.

Maps to: Foundation Prototype criterion (g) "Symbol stability: repeated XIL2CPP runs over the same input produce byte-identical mangled symbol names" generalized to the entire toolchain.

12.2 Hot-reload symbol stability test

Statement: Running XIL2CPP twice over the same input .cs source produces byte-identical mangled output symbols. A method in build N+1 has the same symbol name as in build N if its signature is unchanged.

Mechanism: Section 2 mangling rule (purely structural, no hash, no random) + Section 2.4 determinism requirements.

Maps to: Foundation Prototype criterion (g). Critical for XLiveCoding's RVA-rewrite trampolines — the trampoline target's address resolves by symbol name.

12.3 Cross-config ABI test

Statement: The same C# code compiled in Development (with native exceptions) and in Shipping (with Result<T,E> lowering) produces identical extern "C" entry-point signatures. A C++ caller compiled in Development can link against a transpiled C# module compiled in Shipping (and vice versa) without ABI mismatch.

Mechanism: Section 5 ABI-stable boundary — the shim signature is fixed; body lowering differs internally only.

Validation: XBT's per-system test harness includes a cross-config link check — build the same module in Dev and Shipping, link the Dev binary against the Shipping module's import lib, run a smoke test. Failure fails the system's merge.

12.4 Determinism flag-propagation test

Statement: A module declared SimPath = true in its .Build.cs compiles with /fp:precise + -ffp-contract=off + Sleef-vendored transcendentals + the banned-API regex check applied. A SimPath module that includes a header from a non-SimPath dependency does not inherit the dep's flag posture — SimPath is per-module.

Mechanism: Section 4 of this contract. XBT's per-platform-toolchain flag tables + the /FI / -include header gate + the link-time platform-libm exclusion.

Validation: The test harness compiles a synthetic SimPath module containing a single sin(x) call; disassembles the resulting .obj; asserts the call target resolves to XSleef_sin not __libm_sse2_sin / sin@GLIBC. Similarly the test harness validates that banned APIs (QueryPerformanceCounter) on a SimPath TU fail the build.

12.5 Tier enforcement test

Statement: A module declared Tier = Engine in its .Build.cs that lists a Studio module in its PublicDependencyModuleNames fails the build at module-resolution time. The diagnostic names the offending module and the upward edge.

Mechanism: Section 9.3 of this contract.

Validation: The test harness builds a synthetic project with an Engine module declaring a Studio dependency; asserts XBT exits non-zero with a diagnostic matching the expected pattern.

12.6 Copyright validation test

Statement: A source file (.h, .cpp, .cs) under any tier's Source/ that does not begin with // Copyright Simgenics. All Rights Reserved. fails the build. A third-party file under /Engine/Source/ThirdParty/ is excluded from the check.

Mechanism: Section 10.1 step 5 of this contract; plan Section 2 Copyright / licensing row.

Validation: The test harness adds a synthetic source file without the header; asserts XBT's ValidateCopyrightAction fails with a diagnostic naming the file.

12.7 Engine-version compatibility test

Statement: A project pinning EngineVersion = 0.4.0 with a Studio plugin declaring MinEngineVersion = 0.5.0 fails the build at module-resolution time.

Mechanism: Section 9.4 of this contract; plan Section 2 Plugin versioning & pinning row.

Validation: The test harness builds a synthetic project + plugin combination violating the constraint; asserts XBT exits with a clear diagnostic.

12.8 Circular-dependency rejection test

Statement: Two modules with mutual dependencies fail the build at module-resolution time. The diagnostic names the cycle.

Mechanism: Section 9.2 of this contract.

Validation: The test harness constructs a synthetic A → B → A cycle; asserts XBT exits non-zero with a cycle diagnostic.

12.9 Reflection round-trip test

Statement: A transpiled C# property is settable and gettable through XPropertyEditor's reflection-driven path with no marshalling errors.

Maps to: Foundation Prototype criterion (f).

Mechanism: XHT extracts the property from [XProperty]-attributed C# fields; XIL2CPP transpiles to a getter/setter pair the shared FProperty table can call; XCoreXObject's reflection runtime dispatches to them.

12.10 Aggregate gate — the Foundation Prototype

The contract's correct implementation across XBT + XHT + XIL2CPP is the prerequisite for the Foundation Prototype milestone at plan Section 11 Step 5.5. Until criteria (a) through (g) hold, the contract is not validated in implementation. The seven Foundation Prototype criteria are:

  1. GC pause < 5ms typical on Quest 3 (validates the GC root-registration ABI's throughput in steady state).
  2. GC fallback < 50ms on Quest 3 (validates the GC root-registration ABI under saturated remembered-set conditions).
  3. Cross-arch determinism (validates Section 4 flag propagation + Sleef substitution).
  4. Single-method hot-patch latency < 30s (validates Section 2 symbol mangling stability + XLiveCoding's patch-DLL discovery).
  5. Cascade hot-patch latency < 120s nominal / < 150s timeout (validates the XLiveCoding cascade orchestration's interaction with Section 9 module-graph topology).
  6. Reflection round-trip (validates Sections 1 + 7 surfaces against runtime consumption).
  7. Symbol stability (validates Section 2 mangling determinism + Section 2.1 reproducibility flags).

Per plan Section 11: "Fail criterion: any single criterion not met. Failure triggers a foundational-design review — revisit XCoreXObject + XIL2CPP design (and possibly the lockstep-determinism commitment) before committing further engineering effort."
