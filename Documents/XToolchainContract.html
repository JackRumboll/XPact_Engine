0. Purpose & Scope

This document is the interfaces-only contract jointly designed for XPact's three build-time tools before any of them gets its own system specification:

  • XBT — XPact Build Tool. C# standalone. Reads .xengine, .xproject, and per-module descriptors (TOML-first; see Section 9.6). Builds the module dependency graph, drives reflection extraction, drives C# transpilation, schedules compile / link actions. Unreal-equivalent reference: UnrealBuildTool.
  • XHT — XPact Header Tool. C# standalone. Parses reflection markers in .h headers (C++) and reflection attributes in .cs source (C#) and emits the registration scaffolding that the runtime reflection system consumes at engine boot. Unreal-equivalent reference: UnrealHeaderTool.
  • XIL2CPP — XPact IL2CPP transpiler. C# standalone. Transpiles C# source into C++ with GC root scaffolding, exception lowering, C# string mapping, and stable symbol mangling. No Unreal precedent — closest reference is Unity's IL2CPP, but XIL2CPP transpiles directly from C# source (not IL) and emits hot-patchable, hybrid-GC-aware code rather than Mono-runtime-bound code.

The contract locks the wire and surface interfaces between these three tools and the C++ runtime systems they feed (XCore, XCoreXObject, the platform toolchains). The contract is the document each tool's spec writes against. The contract is the document the Foundation Prototype milestone validates against. The contract is the document a contract revision must reopen by name.

The contract does not cover the internal architecture of each tool. XBT's action-graph internals, dependency-cache file format, parallel executor design — not here, they belong in /Documents/XBT.html. XHT's parser AST shape, attribute reader, and emitter internals — /Documents/XHT.html. XIL2CPP's parser, lowering pipeline, and GC-emit pass — /Documents/XIL2CPP.html (will split per plan Section 3, "Systems whose HTML will likely split"). The contract is the seam; the tools are the volumes the seam holds together.

The contract is delivered in two stages per plan Section 4:

  • Stage A — Step 0 (this document). Locks the marker macro vocabulary, the file naming convention, the invocation protocol (JSON + binary sidecar manifest), the symbol mangling rule, the GC root-registration ABI, the determinism flag propagation contract, the exception codegen ABI boundary and noexcept tier, the C# string mapping, the XHT emit mode (ConstInit), and the module descriptor shape. XBT consumes XHT's output opaquely — XBT does not parse XHT's binary struct layouts — so Stage A is sufficient to build XBT (System 1) and XHT's parser (System 2).
  • Stage B — Contract Addendum at XCore-4b ship (Step 4). Freezes the concrete binary struct layouts — FName, FClass, FProperty, FField with the full replication-metadata surface per plan Section 2 Replication row. XHT's emit mode is locked at Stage A (ConstInit, per Rev 11 audit finding); XHT's emit struct byte-layouts are provisional until Stage B.
  • Step 0.5 addendum (descriptive). Pins the per-file dependency model XBT actually implements once XBT is built. Per plan Section 4: "the Step 0.5 addendum does not change XBT's behavior; it pins the model XBT chose so XHT and XIL2CPP can target it."

Decisions that genuinely await Stage B are marked inline throughout this document with <!-- STAGE-B: ... --> HTML comments and an italic note. Decisions that the deep audit promoted from Stage B to Stage A (notably XHT emit mode) are called out in their section header.

1. Reflection Schema — Name Table, Marker Macros, Surface Vocabulary

Per plan Section 2 Naming row, XPact mirrors Unreal's reflection vocabulary with the only rename being UObject → XObject. The C++ side uses uppercase macros with the X prefix; the C# side uses bracketed PascalCase attributes mirroring the same names.

1.1 Marker macros (C++) and attributes (C#)

The full vocabulary, locked at Stage A:

Reflected structXSTRUCT(specifiers)[XStruct(specifiers)]Immediately before struct declaration.
Reflected enumXENUM(specifiers)[XEnum(specifiers)]Immediately before enum class declaration.
Reflected interfaceXINTERFACE(specifiers)[XInterface(specifiers)]Immediately before interface class.
Reflected function/methodXFUNCTION(specifiers)[XFunction(specifiers)]Immediately before method declaration.

To the C++ compiler all markers except XGENERATED_BODY() are empty defines. They are read by XHT's C++ front-end via a lightweight, single-pass tokenizer (not a full Clang parse) and discarded by the C++ compile. XGENERATED_BODY() is a real macro that expands via a file-id / line-number combination to a generated registration block; the line number is load-bearing. Example:

// XGameFramework module — example header
#pragma once
#include "XCoreXObject.h"

XCLASS(BlueprintType)
class AXValve : public AXActor
{
    XGENERATED_BODY()

public:
    XPROPERTY(EditAnywhere, BlueprintReadWrite, Replicated)
    float OpenFraction = 0.0f;

    XFUNCTION(BlueprintCallable)
    void SetOpenFraction(XPARAM(DisplayName = "Open Fraction") float InFraction);
};

The C# equivalent (which XIL2CPP transpiles, and XHT's C# front-end reads for reflection extraction):

// XGameFramework module — example C#
namespace Simgenics.XPact.GameFramework;

[XClass(BlueprintType = true)]
public partial class Valve : Actor
{
    [XProperty(EditAnywhere = true, BlueprintReadWrite = true, Replicated = true)]
    public float OpenFraction = 0.0f;

    [XFunction(BlueprintCallable = true)]
    public void SetOpenFraction([XParam(DisplayName = "Open Fraction")] float inFraction)
    {
        OpenFraction = inFraction;
    }
}

1.3 Body-macro suffix table

For each class containing XGENERATED_BODY(), XHT emits a per-file generated header ({Header}.gen.h) containing macros suffixed by purpose. These compose at the XGENERATED_BODY() expansion site. The suffix set, locked at Stage A:

SuffixPurpose
_PROLOGForward declarations + friend declarations that must appear at file scope before the class body.
_GENERATED_BODYThe composite macro XGENERATED_BODY() resolves to. Concatenates the other suffixes in correct order.
_INCLASSStatic class-registration members: StaticClass(), StaticRegisterNatives*, type-info statics. Rev 11: emitted in ConstInit style — descriptor data initialized as constexpr where the C++ language permits; runtime registration limited to pointer fixups. See Section 7.1.
_RPC_WRAPPERSServer / Client / NetMulticast RPC dispatch stubs.
_ACCESSORSGenerated property getters/setters where specifier flags require them (e.g., ReplicatedUsing RepNotify binding).
_FIELDNOTIFYUI-binding change-notification slots for properties with BlueprintReadWrite + FieldNotify.
_VINTERFACESVirtual interface dispatch table for interfaces this class implements.
_STANDARD_CONSTRUCTORSDefault constructor + object-initializer constructor declarations.

The composite expansion order is fixed: _INCLASS → _RPC_WRAPPERS → _ACCESSORS → _FIELDNOTIFY → _VINTERFACES → _STANDARD_CONSTRUCTORS. Generated code outside XGENERATED_BODY() — per-file _PROLOG blocks — appears at file scope before the class declaration.

1.4 Per-file ID scheme (REVISED Rev 11 — collision-free Itanium-ABI-style mangling)

UE's reflection system encodes file identity into the body-macro name via the on-disk header path (non-alphanumerics replaced by underscores). This couples the symbol identity to the file's filesystem location, AND ad-hoc underscore-replacement permits collisions (e.g., Foo_Bar/X.h and Foo/Bar_X.h both collapse to Foo_Bar_X_h). Per the UE reference brief gotcha list and Rev 11 audit minor-cleanup #3, XPact decouples file ID from on-disk path AND uses an Itanium-ABI-style length-prefixed grammar so escaping is collision-free.

XPact's file-ID format:

_XID_N<PluginNameLen><PluginName>N<LogicalPathSegCount>{N<SegLen><SegName>}_L<LineNumber>_<Suffix>

Where each N<Len><Token> is a decimal length prefix immediately followed by the ASCII token. Logical-path segments are split on forward-slash before encoding. Reserved characters in <Token> (any byte outside [A-Za-z0-9]) are themselves length-prefixed and emitted as their hex escape; this keeps the grammar bijective. Components:

  • PluginName — the plugin's name as declared in its .xplugin descriptor. For the engine itself this is the literal Engine. For Studio and Project plugins it is the descriptor's Name field.
  • LogicalPath segments — the header's logical path within the plugin, split on forward slashes, not its absolute filesystem path. The logical path is declared per-module in the module's .Build descriptor (PublicIncludePaths / PrivateIncludePaths) and is preserved across folder reorganization. Moving the file on disk does not break consumers as long as the logical path is preserved.
  • LineNumber — line number of the XGENERATED_BODY() macro within the header. Same load-bearing role as UE.
  • Suffix — one of the suffixes from Section 1.3.

Example expansion. For AXValve at line 14 of plugin Engine with logical path XGameFramework/Public/Valves/XValve:

// Composed file-ID for the GENERATED_BODY suffix (whitespace added for readability):
_XID_  N6Engine  N4  N14XGameFramework  N6Public  N6Valves  N6XValve  _L14_GENERATED_BODY

// Real symbol (no whitespace):
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_GENERATED_BODY

// The other suffixes for the same site:
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_INCLASS
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_RPC_WRAPPERS
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_ACCESSORS
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_FIELDNOTIFY
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_VINTERFACES
_XID_N6EngineN4N14XGameFrameworkN6PublicN6ValvesN6XValve_L14_STANDARD_CONSTRUCTORS

The decoder reads N, then a decimal length, then that many bytes; the segment count after the plugin-name component is also length-prefixed. This grammar is bijective: any path / plugin-name / line-number triple maps to exactly one symbol, and every well-formed symbol decodes back to exactly one triple. Collisions between Foo_Bar/X.h and Foo/Bar_X.h are impossible because each segment carries its own length.

1.5 What Stage A locks vs. Stage B (REVISED Rev 11)

Stage A (this document) locks: the marker macro / attribute names, the specifier vocabulary, the body-macro suffix table, the file-ID format, the placement rules, the XHT emit mode (ConstInit-style, per Section 7.1), and the PCH policy for SimPath modules (immediately below). Rev 11 audit finding #10 — PCH policy for SimPath modules. SimPath modules must declare PCHUsage = PCHUsageMode.NoSharedPCHs in their descriptor or XBT fails the build with a diagnostic. SharedPCH headers must not #include any .gen.h file; XHT-generated files are excluded from PCH consideration via the manifest field bExcludeFromSharedPCH = true on every generated file. Within a SharedPCH, the include order is alphabetical by logical path — this locks PCH compile determinism in lockstep with the rest of the reproducibility envelope. Per Rev 11 audit finding: SimPath determinism + PCH non-determinism is incoherent; the policy resolves the tension by forbidding the combination.

Per plan Section 2 XIL2CPP symbol naming row (Rev 7), the transpiled-symbol mangling is a locked ABI in the Toolchain Contract. Per plan Section 2 Hot-reload commitment row, hot-reload requires stable exported symbol names for hot-patchable functions. 2.1 Reproducibility envelope — complete flag set (REVISED Rev 11, audit finding #3)

The Rev 10 contract listed only compiler-side flags (/Brepro, -frandomize-layout-seed-file=). The deep audit identified five gaps: linker-side reproducibility was missing entirely; source-path normalization was missing; PE timestamps survived in the binary; incremental linking conflicted with /Brepro on some MSVC builds; LTO determinism was unspecified. Rev 11 closes all five.

MSVC reproducibility flags (Win64)

  • /Brepro — compiler-side: suppresses timestamps in .obj files.
  • /BREPRO — linker-side (link.exe): suppresses timestamps in the linked PE. Separate flag from the compiler's /Brepro; both required.
  • /TIMESTAMP:0 — linker: forces PE header build-time stamp to 0. Required for reproducible PE output independent of /BREPRO (covers older toolchain versions).
  • /pathmap:$(RepoRoot)=X:/R — compiler: normalizes source paths in PDB/embedded debug info. X:/R is the engine-wide virtual repo root used in every developer machine's PDBs.
  • /INCREMENTAL:NO — linker: incremental linking is incompatible with /BREPRO on MSVC 19.30 and earlier; explicitly disabled engine-wide. The incremental-link speed cost is accepted; the alternative is non-reproducible Shipping builds.
  • When LTO / WPO is enabled (/GL + /LTCG): MSVC's /cgthreads must be pinned (default is hardware-dependent and breaks reproducibility). XBT sets /cgthreads:8 on every machine.

Clang reproducibility flags (Linux + Android + provisional Windows)

  • -frandomize-layout-seed-file= pinned to an empty / deterministic seed.
  • -fno-ident — suppresses compiler-identity strings.
  • -Wl,--build-id=none — at link, drops the GNU build-ID.
  • --remap-file=$(RepoRoot)=X:/R — Clang equivalent of MSVC's /pathmap; normalizes source paths in DWARF debug info.
  • When LTO is enabled: -fdeterministic-cgu-order required. Alternative is accepting non-reproducible Shipping builds; the contract picks the determinism side.

Engine-wide invalidation policy

Timestamp-based invalidation is banned engine-wide. XBT's ActionHistory, the per-file dependency cache (Section 8), and the Roslyn rules-assembly cache (XBT spec) all key invalidation on content hashes (BLAKE3, per XBT spec) — never on file mtime. Per Rev 11 audit finding #3: the Rev 10 envelope was incoherent if any cache layer could non-deterministically rebuild based on filesystem timestamps that themselves were non-reproducible.

Foundation Prototype verification procedure

To verify reproducibility before any cross-config or cross-machine work, the Foundation Prototype (plan Section 11 Step 5.5) runs:

# Two clean builds on the same machine, same source tree:
git clean -ffdx
build/clean.bat               # blow away Intermediate/, Binaries/
XBT.exe Build -Target=XPactEditor -Configuration=Development
mv Binaries Binaries_buildA

git clean -ffdx
build/clean.bat
XBT.exe Build -Target=XPactEditor -Configuration=Development

# Compare: every DLL in Binaries/ must hash-match its counterpart in Binaries_buildA/
for /f %f in ('dir /b Binaries\*.dll') do (
    certutil -hashfile Binaries\%f         SHA256 > hashA.txt
    certutil -hashfile Binaries_buildA\%f  SHA256 > hashB.txt
    fc hashA.txt hashB.txt || (echo MISMATCH: %f && exit /b 1)
)

The procedure is identical on Linux with sha256sum in place of certutil. Any mismatch fails the Foundation Prototype reproducibility criterion and triggers a root-cause investigation.

These flags are mandatory on every XBT-driven build, not only sim-path TUs. The Foundation Prototype reproducibility criterion (plan Section 11 Step 5.5 (g)) cannot be satisfied without them.

2.2 Transpiled C# side

XIL2CPP-transpiled symbols use a custom, contract-versioned mangling rule:

{ContractVersion}__{Namespace}::{Type}::{Method}{GenericArgManglings}{ParamManglings}

Component definitions:

  • {ContractVersion}: the literal _v followed by the contract-version short tag from Section 10.2 (the first ten hex characters of the contract-structure BLAKE3, prefixed by a semantic version digit). A future contract revision that breaks the mangling produces a new contract-structure hash and therefore a new tag. A version bump is mechanical — never silent, never hand-typed.
  • {Namespace}: dot-separated namespace path with dots replaced by ::. Example: Simgenics.XPact.GameFramework becomes Simgenics::XPact::GameFramework.
  • {Type}: the simple type name. Nested types are joined by ::.
  • {Method}: the simple method name. C# operator overloads use op_Add, op_Equality, etc. (CLR convention). Constructors are $ctor. Static constructors are $cctor.
  • {GenericArgManglings}: for generic methods, _G_ followed by a comma-separated list of mangled generic argument types in angle brackets, recursively mangled. Empty when not generic.
  • {ParamManglings}: _P_ followed by a parenthesized comma-separated list of mangled parameter types. Reference types prefix R, value types prefix V, by-ref prefix B, in/out prefix I/O. Empty parentheses for parameterless methods.

2.3 Free-function form with explicit self

Per the UE reference brief recommendation: every transpiled C# method becomes a free function (not a member function) with an explicit XObject* self first parameter. This makes Live-Coding-style RVA-rewrite trampolines work cleanly — the patcher writes one jump at the function's entry point, without vtable-slot rewriting. Vtable dispatch for virtual methods is handled by a generated dispatcher (also a free function) that performs the table lookup and tail-calls the resolved free function. Per plan Section 2 Hot-reload commitment row, no virtual-method signature changes are permitted mid-session, so the vtable layout is stable across patches.

Example. Given the C# above:

// C# source
namespace Simgenics.XPact.GameFramework;
public partial class Valve : Actor {
    public void SetOpenFraction(float inFraction) { /* ... */ }
}

The transpiled symbol is (with placeholder contract-version tag v1ab12cd34 illustrative):

_v1ab12cd34__Simgenics::XPact::GameFramework::Valve::SetOpenFraction_P_(R Simgenics::XPact::GameFramework::Valve, V float)

And the C++ declaration XIL2CPP emits:

// Transpiled C++ — free function with explicit self
extern "C" void _v1ab12cd34__Simgenics__XPact__GameFramework__Valve__SetOpenFraction_P_R_Simgenics__XPact__GameFramework__Valve_V_float(
    Simgenics::XPact::GameFramework::Valve* self,
    float inFraction);

(The angle-bracket / parenthesis / colon characters in the conceptual mangling above are translated to single-underscore tokens for the actual linker-visible symbol — :: → __, parentheses dropped, commas and spaces → _. The translation is deterministic and reversible.)

2.4 Determinism requirement

Per plan Section 11 Step 5.5 criterion (g): repeated XIL2CPP runs over the same input produce byte-identical mangled symbol names. This requires:

  1. The mangling rule is purely structural — no hash, no random, no build-time-derived suffix beyond the contract-version tag itself (which is hash-derived but stable across the contract's lifetime).
  2. The generic-instantiation walk visits arguments in source-declaration order.
  3. XIL2CPP's internal dictionary iteration over namespaces / types / methods is sorted by name before emit. No insertion-order dependence on the parse.
  4. The reproducibility flags (/Brepro + /BREPRO + /pathmap + /TIMESTAMP:0 + /INCREMENTAL:NO on MSVC; -frandomize-layout-seed-file= + --remap-file + --build-id=none + -fdeterministic-cgu-order on Clang) propagate from XIL2CPP's own build of itself, not just the user's build — XIL2CPP's binary is itself reproducible.

3. GC Root-Registration ABI (REVISED Rev 11 — span-based ABI)

Per plan Section 2 Memory/GC row, XPact uses a hybrid memory model: a non-moving precise mark-and-sweep GC for XObject-derived types only, with plain C# value types and containers (List<T>, Dictionary<K,V>, string, structs) transpiling to native deterministic-lifetime equivalents that are NOT GC-managed. When a non-GC container holds XObject references, the container registers a GC root span at construction, updates the span on resize, and de-registers at destruction; the IL2CPP transpiler emits this scaffolding by statically analyzing generic instantiations.

Rev 11 audit finding #1 — why span-based, not per-slot. The Rev 10 ABI used per-slot XGC_RegisterRoot(void** slot) / XGC_UnregisterRoot(void** slot) primitives, calling them inside Add / RemoveAt / EnsureCapacity. The audit identified two correctness problems and one performance problem with per-slot:

  1. Mark-phase race window during realloc. Mid-realloc, slots already moved to the new buffer are not yet registered, slots remaining in the old buffer are still registered. If the mark phase runs during this window (which it can — the collector is mostly-concurrent), referents accessible only through moved-but-unregistered slots become invisible to the GC and risk collection-during-use.
  2. O(N) register/unregister cost per resize. Doubling a 10,000-slot list cost 10,000 XGC_UnregisterRoot + 10,000 XGC_RegisterRoot calls just to relocate the slots, plus the per-mutation register/unregister churn.
  3. List<object> required a separate RegisterRootRange primitive, fragmenting the ABI for no reason — the span case generalizes the conservative case.

The span-based ABI fixes all three. The GC iterates live slots during mark by walking registered spans, not a flat slot table.

3.1 The span primitive and ABI surface

// XPact Rev 11 GC root-span ABI — layout part of the contract.
struct XGCRootSpan {
    void**       base;     // pointer to the first slot in the buffer
    size_t       stride;   // bytes between slots; usually sizeof(void*),
                           // larger for SoA layouts
    size_t       count;    // number of slots
    XGCRootKind  kind;     // strong / weak / conservative
    uint32_t     _padding; // future use; must be 0
};

extern "C" {

    // Register a span. O(1) per container. The collector stores a handle
    // to the span pointer; subsequent mark phases walk it as a contiguous
    // array of void* slots according to (stride, count).
    void XGC_RegisterRootSpan(XGCRootSpan* span);

    // Update the span's base and count after a container resize. Safe to
    // call mid-realloc: the collector synchronises with mark via the
    // engine's write-barrier protocol (XCoreXObject internal) so the
    // collector never sees a half-state during the update.
    void XGC_UpdateRootSpan(XGCRootSpan* span,
                            void** newBase,
                            size_t newCount);

    // Unregister. Must be called exactly once for each successful Register.
    void XGC_UnregisterRootSpan(XGCRootSpan* span);

}

The conservative case (List<object>) is the same primitive with kind = Conservative: the span's slots are walked during mark, but each slot's stored value is treated as "possibly a pointer; only register if non-null and only follow if it resolves to a known live XObject." No separate primitive is needed.

3.2 XGCRootKind

enum class XGCRootKind : uint8_t {
    Strong,        // mark prevents collection
    Weak,          // GC clears the slot if the referent is collected
    Conservative   // treat slot as possibly-pointer; only register if non-null
                   // during mark; ignore type info. Used for List<object> etc.
};

The transpiler chooses the kind statically based on the generic instantiation:

  • Generic type argument is statically XObject-derived (List<XActor>, Dictionary<FName, XComponent>): XGCRootKind::Strong, registered once via XGC_RegisterRootSpan at construction.
  • Generic type argument is statically a value type (List<int>, List<FVector>): no GC scaffolding emitted at all. The container is pure RAII.
  • Generic type argument is object or a non-statically-typed interface that could hold XObjects (List<object>, Dictionary<string, object>): XGCRootKind::Conservative via the same XGC_RegisterRootSpan primitive.

Per plan Section 2 Memory/GC row: "XIL2CPP emits a build-time warning when such a pattern appears on a sim-path TU because the per-mutation cost is real." This warning is mandatory; it is not suppressible from .cs source. It is suppressible only at the module level via an explicit SimPathConservativeRootsAllowed = true field in the module's descriptor (Section 9.1), which is also visible in build logs.

3.3 Example: List<XActor> with span ABI

Suppose the C# author writes:

// C# — gameplay code
List<Actor> ActiveActors = new List<Actor>();
ActiveActors.Add(SomeActorRef);
ActiveActors.RemoveAt(0);

XIL2CPP transpiles this with one span per container (registered once at construction, updated on resize, unregistered at destruction). Conceptual emit shape (illustrative, not normative):

// Transpiled C++ shape — Rev 11 span-based ABI
class List_Actor {
    Actor**     m_data;
    size_t      m_count;
    size_t      m_capacity;
    XGCRootSpan m_rootSpan;

public:
    List_Actor() : m_data(nullptr), m_count(0), m_capacity(0) {
        m_rootSpan.base = reinterpret_cast<void**>(m_data);
        m_rootSpan.stride = sizeof(Actor*);
        m_rootSpan.count = 0;
        m_rootSpan.kind = XGCRootKind::Strong;
        m_rootSpan._padding = 0;
        XGC_RegisterRootSpan(&m_rootSpan);
    }

    void Add(Actor* item) {
        if (m_count == m_capacity) EnsureCapacity(m_count + 1);
        m_data[m_count++] = item;
        XGC_UpdateRootSpan(&m_rootSpan,
                           reinterpret_cast<void**>(m_data),
                           m_count);
    }

    void RemoveAt(size_t i) {
        // shift remaining slots down; update span count
        for (size_t j = i; j + 1 < m_count; ++j) m_data[j] = m_data[j+1];
        --m_count;
        XGC_UpdateRootSpan(&m_rootSpan,
                           reinterpret_cast<void**>(m_data),
                           m_count);
    }

    void EnsureCapacity(size_t needed) {
        if (needed <= m_capacity) return;
        size_t newCap = m_capacity ? m_capacity * 2 : 8;
        while (newCap < needed) newCap *= 2;
        Actor** newData = static_cast<Actor**>(realloc(m_data, newCap * sizeof(Actor*)));
        m_data = newData;
        m_capacity = newCap;
        // The single span update is atomic w.r.t. the mark phase — the
        // collector never sees a buffer-base inconsistent with a live count.
        XGC_UpdateRootSpan(&m_rootSpan,
                           reinterpret_cast<void**>(m_data),
                           m_count);
    }

    ~List_Actor() {
        XGC_UnregisterRootSpan(&m_rootSpan);
        free(m_data);
    }
};

Note: the XGCRootSpan member is part of every transpiled container type. XIL2CPP emits it at the end of the class body; reflection (XHT) does not enumerate it (it is not an XPROPERTY).

3.4 Example: List<object> conservative span

// Transpiled shape for List<object> — same primitive, different kind
class List_object {
    void**      m_data;
    size_t      m_count;
    size_t      m_capacity;
    XGCRootSpan m_rootSpan;

public:
    List_object() : m_data(nullptr), m_count(0), m_capacity(0) {
        m_rootSpan = { nullptr, sizeof(void*), 0, XGCRootKind::Conservative, 0 };
        XGC_RegisterRootSpan(&m_rootSpan);
    }
    // EnsureCapacity / Add / RemoveAt mirror List_Actor exactly.
    // The Conservative kind tells the collector to treat null slots as
    // safe-to-skip and non-null slots as possibly-pointers.
    ~List_object() {
        XGC_UnregisterRootSpan(&m_rootSpan);
        free(m_data);
    }
};

3.5 Atomicity contract for UpdateRootSpan

The mark phase and XGC_UpdateRootSpan coordinate via XCoreXObject's internal write-barrier protocol (collector internals; not in this contract). The contract guarantee at this surface is: the mark-phase scan and the span update are mutually serialized such that the collector never observes a span whose (base, count) tuple is inconsistent with a live buffer. Container code does not need additional locks beyond calling XGC_UpdateRootSpan. The serialization protocol is the collector's responsibility, locked in XCoreXObject; the container ABI is locked here.

3.6 Internals not in the contract

The contract locks only the extern "C" surface above plus the XGCRootSpan struct layout. The collector's internal root-set data structures, the locking discipline for concurrent registration, the bump-allocated span-table format, the card-table format, the write-barrier intrinsic shape — all internal to XCoreXObject and documented there (plan Section 3: XCoreXObject "will split into multiple docs: allocator + collector + reflection + write-barriers/roots"). XIL2CPP emits only the surface above.

5. Exception Codegen Switch — ABI-Stable Boundary & Calling-Convention Tier (REVISED Rev 11)

Per plan Section 2 Exception handling row: "C++ exceptions off in Shipping, on in Debug/DebugGame/Development/Test. XIL2CPP emits C# throw/catch as native exceptions in Dev/Test configurations and as Result<T,E> lowering in Shipping. ABI stability: public API surfaces of transpiled C# functions go through an ABI-stable boundary layer defined in the Toolchain Contract (Step 0, item 5) — same C function signature across configs, with internal lowering varying. Cross-config linking is supported because all call sites see the same external signature; only the body differs."

5.1 Two calling-convention tiers (NEW Rev 11 — audit finding #2)

The Rev 10 contract specified a single calling convention: every transpiled C# method got an extern "C" shim with an XResult* outResult parameter, costing 64 bytes of stack + a pointer write per call. The audit identified this as miscalibrated: ABI stability matters at the DLL boundary; it does not matter at every intra-module call site. The shim tax was being paid on millions of internal calls that statically cannot throw.

Rev 11 splits the calling convention into two tiers:

TierCalling conventionApplies toCost
Tier 1: ABI-stable shim extern "C" void _Foo_Shim(void* self, A a, B b, XResult* outResult) (a) Any function that crosses a DLL boundary (i.e. is exported as part of a module's public surface); (b) any function annotated [XFunction(CanThrow = true)]; (c) any function XIL2CPP's analysis cannot prove noexcept. One XResult out-param per call (64 bytes stack + pointer write); cross-config-stable signature.
Tier 2: direct call Plain C++ free function with the C# method's natural lowered signature, no out-param. Functions XIL2CPP statically proves cannot throw AND that do not cross a DLL boundary AND are not annotated [XFunction(CanThrow = true)]. Annotation [XFunction(NoThrow = true)] is an explicit opt-in — XIL2CPP refuses if it cannot satisfy the noexcept proof. Zero overhead vs. handwritten C++.

5.2 Classification algorithm (interface-level)

XIL2CPP analyzes the call graph during transpile. A function f is classified Tier 2 iff:

  1. f is not exported from its owning DLL (i.e. is not part of the module's public API surface as derived from the reflection surface and the module's PublicDependencyModuleNames); AND
  2. f is not annotated [XFunction(CanThrow = true)]; AND
  3. Every callee of f is itself Tier 2 (transitive); AND
  4. f's body contains no throw expression; AND
  5. f does not invoke a C++ function declared without noexcept that XIL2CPP cannot prove safe (the "C++ interop wall" — if the wall is crossed, the wall side must be Tier 1).

The algorithm is a fixpoint pass: initially every function is candidate Tier 2; constraints 1-5 promote functions to Tier 1; the pass iterates until stable. Per plan Section 4 "XIL2CPP analyzes C# call graphs to classify which functions can throw vs are noexcept-safe."

The annotation [XFunction(NoThrow = true)] serves as a developer assertion that the function is Tier 2. XIL2CPP runs the classification algorithm and fails the build with a clear diagnostic if the annotation cannot be satisfied (e.g., a transitively reachable C++ function is not noexcept). Reference: Clang's exception-table emission for noexcept functions skips EH tables entirely; the same posture applies here.

The annotation [XFunction(CanThrow = true)] serves as a developer assertion that the function is Tier 1 even if classification might otherwise rule it noexcept-safe. Used at API surfaces where the function's body is currently noexcept-safe but the maintainer wants the option to add a throw site later without breaking ABI.

5.3 The Tier 1 ABI boundary

Tier 1 functions follow the original Rev 10 ABI — every Tier 1 transpiled C# method gets two artifacts:

  1. A shim entry point: an extern "C" free function with a fixed signature determined by the C# method's static signature. This signature is identical across all build configurations. Call sites — whether from C++, from other transpiled C#, or from Blueprint dispatch — bind against this shim.
  2. A body implementation internal to the shim. The body's lowering differs between Dev/Test (native C++ exceptions) and Shipping (Result<T,E>). The shim adapts the body's output to the contract-defined return discipline.

The shim signature, given C# method T Foo(A a, B b):

// Shim entry point — identical across Dev and Shipping
extern "C" void _v1__Foo_Shim(
    void* self,             // null for static methods
    A a,
    B b,
    XResult* outResult);    // out-parameter for both the value and the error

The XResult out-parameter carries either the successful return value or a typed error descriptor — same layout in both configs.

5.4 The Tier 2 direct convention

Tier 2 functions have the natural C++ signature derived from the C# method:

// Tier 2 direct convention — Rev 11
namespace Simgenics::XPact::GameFramework {
    T Foo(Valve* self, A a, B b);   // returns T directly; cannot throw
}

No extern "C", no shim, no out-param. The function participates in normal C++ overload resolution and inlining. Cross-module calls between two Tier 2 functions of the same module compile to direct call instructions. Tier 2 functions are not hot-reloadable by Live Coding's RVA-rewrite trampoline (which requires the extern "C"-style entry point), but per plan Section 2 Hot-reload commitment row, only public API methods are guaranteed hot-reloadable — internal methods rebuild their owning module.

5.5 XResult layout (Tier 1 only)

// Plain C++ struct — layout locked at Stage A
struct alignas(16) XResult {
    enum class Discriminator : uint8_t { Success, Error };
    Discriminator   discriminator;
    uint8_t         _padding[7];
    union {
        // SuccessValue is type-erased to a tagged buffer. Each shim emits
        // type-specific accessors. Storage is up to 56 bytes inline; larger
        // returns spill via XResult::SpillSlot pointer.
        struct {
            uint8_t       buffer[56];
        } success;
        struct {
            XErrorCode    code;          // numeric ID into XError descriptor table
            const char*   typeName;      // mangled type of the original C# exception
            const char*   message;       // UTF-8, lifetime tied to call stack
            void*         stackTrace;    // null in Shipping; native trace in Dev/Test
        } error;
    };
};

Note: layout is illustrative; final byte-exact layout finalizes at Stage B if FProperty layout influences it. The external surface (discriminator + access pattern) is locked at Stage A.

5.6 Dev/Test lowering — native exceptions (Tier 1 body)

The Tier 1 shim body is wrapped in a try / catch (...) block. On normal return, the shim copies the return value into the XResult::success buffer and sets the discriminator to Success. On caught exception, the shim translates the native exception to XResult::error and sets the discriminator to Error:

// Dev/Test shim body shape (Tier 1)
extern "C" void _v1__Foo_Shim(void* self, A a, B b, XResult* outResult) {
    try {
        T value = _v1__Foo_Body(self, a, b);   // body throws on C# throw
        outResult->discriminator = XResult::Discriminator::Success;
        new (outResult->success.buffer) T(std::move(value));
    } catch (const XCSharpException& ex) {
        outResult->discriminator = XResult::Discriminator::Error;
        outResult->error.code = ex.code;
        outResult->error.typeName = ex.typeName;
        outResult->error.message = ex.message;
        outResult->error.stackTrace = ex.captureStack();
    }
}

5.7 Shipping lowering — Result<T,E> (Tier 1 body)

In Shipping, C# throw sites lower to early-return of an XResult with the error discriminator. Every C# try / catch lowers to discriminator-checked dispatch. The shim becomes a thin pass-through:

// Shipping shim body shape (Tier 1)
extern "C" void _v1__Foo_Shim(void* self, A a, B b, XResult* outResult) {
    _v1__Foo_Body(self, a, b, outResult);
    // Body writes to outResult directly. No try/catch — exceptions
    // are not raised in Shipping bodies.
}

The body's internal structure differs between configs; the shim's external signature does not. A C++ caller linking against the shim never sees the difference. Cross-config linking works: an editor module compiled in Development can call into a runtime module compiled in Shipping (or vice versa, for hot-reload scenarios).

5.8 Generic instantiation rules

The contract requires that T and E in Result<T,E> instantiate as either:

  • C++ trivially destructible types (POD, simple value types), or
  • XObject-derived types (which the GC owns and which require no in-buffer destructor — the buffer holds the pointer only).

Non-trivially-destructible non-XObject types (e.g., FString, TArray<T>, custom RAII handles) require explicit destruction. The shim emits the appropriate destructor call when XResult goes out of scope on the calling side; XIL2CPP generates this teardown automatically at every call site.

5.9 Reflection coverage

XResult is itself reflected as an XSTRUCT so editor inspection, serialization, and debugger visualization work uniformly:

XSTRUCT()
struct XResult {
    XPROPERTY(VisibleAnywhere) EDiscriminator Discriminator;
    XPROPERTY(VisibleAnywhere, EditCondition = "Discriminator == EDiscriminator::Error") XErrorDescriptor ErrorInfo;
    // Success value is type-erased; editor renders via owning method's signature.
};

5.10 Serialization semantics

When XResult is serialized (e.g., as a multi-user RPC return), the wire format is: discriminator byte + (on Success: serialized T per its own serializer; on Error: serialized error descriptor — code + typeName + message; stackTrace is dropped on the wire). Cross-config: a Development sender and a Shipping receiver agree on the wire format because both serialize through the same XResult reflection path.

5.11 Third-party library constraint

Per plan Section 2 Exception handling row, third-party libraries linked in Shipping must be exception-clean. XBT validates this at link time on Shipping configs by inspecting the third-party library's metadata: any .lib / .a with EH information present fails the Shipping link with a diagnostic naming the library. /Engine/Source/ThirdParty/Licenses/INVENTORY.html (plan Section 2 Third-party license inventory row) gains a column noting exception-cleanness for each entry.

6. C# string ↔ FString Mapping (REVISED Rev 11 — s[i] is error on sim path)

Per plan Section 2 String encoding row (Rev 4): FString is UTF-8 on all platforms. C# string transpiles to "a transpiler-emitted immutable string handle wrapping FString — this handle is invisible in C# source code; user code writes string and ReadOnlySpan<char> as in standard C#. Literal C# strings are emitted as UTF-8 constants at build time (no runtime conversion); the transpiler guarantees pointer-identity for compile-time-interned literals so ReferenceEquals(nameof(X), "X") holds." Per plan Section 2 C# string indexing semantics row (Rev 7): s[i] becomes O(n).

6.1 The handle type

XIL2CPP transpiles C# string to a value-type handle:

// Transpiled shape
struct XCSharpString {
    const FString* m_storage;    // points into interned FName table OR
                                 // into per-call cached view
};

The handle is 8 bytes on all platforms, trivially copyable, no destructor. The FString storage it points into is owned either by the global interned literal pool (for compile-time string literals) or by the runtime string-builder allocator (for runtime-computed strings — lifetime tracked by call-stack arena or by explicit user-side GC root in the rare case the string escapes).

6.2 Literal interning

Compile-time C# string literals emit as UTF-8 constants in the binary's read-only data section. XIL2CPP guarantees pointer identity for them: every occurrence of "open valve" in any transpiled C# resolves to the same const FString*. nameof(X), typeof(X).Name, and string-literal usages all participate in the interning pool.

Example:

// C#
string a = "open valve";
string b = "open valve";
if (ReferenceEquals(a, b)) { /* always true under XPact */ }
if (ReferenceEquals(nameof(Valve), "Valve")) { /* also true */ }

Both a and b transpile to handles whose m_storage points to the same const FString* in .rodata.

6.3 The shared FName table

Per the UE reference brief recommendation: a single shared FName table across XHT-generated and XIL2CPP-generated callers, with stable indices across hot-reload. FName::FromString("open valve") from C++ and the C# literal "open valve" resolve to the same FName index. Per plan Section 2 String encoding row, FName is case-sensitive in MVP — hashing and comparison are bytewise.

6.4 Indexing & iteration (REVISED Rev 11 — sim-path s[i] is error not warning)

The s[i] operator walks UTF-8 to find the i-th codepoint — O(n). Rev 11 audit finding #13: XIL2CPP emits a build-time error on s[i] usage in sim-path TUs — previously a warning. The error is suppressible only at function granularity via [XFunction(SimPathStringIndexOK = true)], analogous to the line-level // XSIMPATH_OK suppression for banned APIs in Section 4.4. Per the audit: warnings against accidentally-O(n) behaviour in lockstep simulation paths are too easy to ignore; the contract expresses intent more clearly as a hard error with an explicit opt-in path.

Idiomatic alternatives ship in the C# binding surface:

// C# idiomatic alternatives
ReadOnlySpan<char> span = s.AsSpan();      // O(n) materialize once, O(1) afterward
int idx = s.IndexOf('v');                  // O(n) but single pass
string sub = s.Substring(0, 5);            // O(n) materialize once

// New API documented in the C# binding surface
foreach (int codepoint in s.AsCodepoints())   // iterator, no intermediate buffer
{
    // ...
}

6.5 Runtime conversion at the IL2CPP boundary

When C# string crosses to C++ (e.g., a Blueprint-callable C++ function takes const FString&), the conversion is zero-copy: the handle's m_storage pointer is passed directly. When a C++ FString crosses to C# (e.g., a C++-implemented property returns FString to a C# field), XIL2CPP emits a cached-view wrapper that allocates an XCSharpString handle pointing into the FString. The cached view is interned per-call-stack-frame to avoid repeated allocations for the same FString within a frame.

6.6 What Stage A locks vs. Stage B

Stage A locks: the handle layout, literal interning behavior, FName table sharing, indexing semantics, the iterator surface (AsSpan, AsCodepoints, IndexOf, Substring).

Stage B (Contract Addendum) freezes the FName entry binary layout in the shared table. Until then, FName index space is virtualized via XCore-4a's provisional FName implementation; the index is stable across hot-reload at Stage A, but the on-disk serialized format finalizes at Stage B.

Rev 11 audit finding #4 — emit MODE locked at Stage A, distinct from emit LAYOUT. The Rev 10 contract deferred both "emit mode" (ConstInit-style vs. Params-style) and "concrete struct layouts" to Stage B. The audit identified these as separable choices: the emit-mode choice is interface-level (does StaticClass()'s descriptor initialize as constexpr data with runtime pointer fixups, or via per-class registration function calls at module load?), while struct-layout choice is implementation-level (what bytes does FProperty occupy in what order?). The interface-level choice can and should land at Stage A; deferring it until Stage B unnecessarily delays XHT's design.

7.1 Stage A — emit mode locked to ConstInit (REVISED Rev 11)

XHT emits in ConstInit style. Generated _INCLASS blocks initialize class descriptor data as constexpr where the C++ language permits. Runtime registration at module load is limited to pointer fixups (resolving cross-DLL FClass* superclass references, attaching the class to the global FClass table) — not to constructing the per-class descriptor's primary data. Per UE precedent: Engine/Source/Runtime/CoreUObject/Public/UObject/Class.h lines 1156-1201 (UE::CodeGen::ConstInit namespace) is the implementation pattern XHT mirrors. The motivation matches UE's: module load times scale with reflected-class count when each class runs constructor code at load; constexpr initialization moves the work to compile time, where the build system already amortizes.

This decision does not require knowing FProperty's binary layout — only commits emit shape. Specific struct layouts still finalize at Stage B (FName, FClass, FProperty, FField byte order). XHT's parser and the emit-mode lock together are sufficient for XHT to ship at Step 2 with provisional layouts, validated against the ConstInit emit shape; the Stage B addendum then locks the byte layouts without re-opening the emit mode decision.

Stage A locks the following XHT-relevant interfaces:

  • Generated file naming. For input header {ModulePath}/{HeaderName}.h, XHT emits {ModuleIntermediate}/{HeaderName}.gen.h. For each module, XHT emits {ModuleIntermediate}/{ModuleName}.gen.cpp aggregating all module-level registration calls.
  • Emit mode: ConstInit style. Per the audit finding above.
  • Invocation protocol. XHT runs as a subprocess of XBT (or as an in-process library — XBT's choice, internal). XBT writes a JSON manifest + binary sidecar (see Section 10) and either passes the binary sidecar's path on the command line or calls XHT's in-process entry point with the loaded manifest.
  • Marker macro vocabulary. Section 1 above.
  • Body-macro suffix table. Section 1.3 above.
  • Per-file ID scheme. Section 1.4 above.
  • Per-module text manifest. XHT emits, alongside its binary outputs, a small text manifest ({ModuleName}.gen.manifest) listing the generated files. XBT reads this manifest as XHT's opaque output; XBT does NOT parse the .gen.h or .gen.cpp content. Per plan Section 4: "XBT consumes XHT output opaquely. XBT treats XHT's output as opaque artifacts indexed by file-level dependency markers." Manifest entries carry the bExcludeFromSharedPCH = true flag per Section 1.5.

7.2 Stage B — what the Contract Addendum will lock

Stage B (Contract Addendum at XCore-4b ship, Step 4) freezes:

  • FName binary layout — the on-disk and in-memory shared-table entry record.
  • FClass binary layout — class-descriptor struct with vtable info, super-class pointer, property list head, function list head.
  • FProperty binary layout including all replication-metadata slots: ELifetimeCondition, RepNotify callback function-pointer slot, delta-compression hint flags, replication group ID, owner-only / autonomous-proxy-only / simulated-proxy-only flags.
  • FField binary layout — the generalized property-or-field descriptor.

(Rev 11: the choice between Params-style and ConstInit-style emit, listed as a Stage B item in Rev 10, has been promoted to Stage A and resolved to ConstInit per audit finding #4. Stage B no longer re-opens emit mode.)

XHT's parser is complete at System 2 (Step 2 in plan Section 4 build order). The emitter is provisional in layout until Step 4 but final in mode (ConstInit) from Stage A. Consumers of XHT-generated headers between Step 2 and Step 4 build against the parser-provided field set + ConstInit shape but should not depend on exact binary layout. XCore-4a (Step 3) uses a small set of forward-declared opaque types in places that would otherwise see XHT's output; XCore-4b's ship simultaneously finalizes both XHT's emit layout and the runtime's consumption.

8. Per-File Dependency Model (REVISED Rev 11 — explicit opaque-consumption framing)

Per plan Section 4: "The contract is delivered with explicit 'TBD at XBT implementation' markers for the per-file dependency model (which can only be hardened once XBT is built). Step 0.5 addendum: descriptive — documents the per-file dependency model that XBT actually implements, rather than prescribing one ahead of time."

This section locks the shape of the dependency-tracking surface and defers the algorithm to Step 0.5.

Rev 11 audit minor cleanup: the dependency model is explicitly manifest-based opaque consumption — XBT records "what XHT-output files were consumed when compiling each .cpp" during compile and re-checks the recorded file's content hash on next build. XBT does not parse .gen.h content to determine dependency edges; the hash-of-the-emitted-file is the dependency edge.

8.1 What XBT identifies

  • C++ dependencies: identified via include-graph walk. Each .cpp's transitive includes form the prerequisite set for its compile action. XBT carries a per-TU CppDependencyCache analogous to UE's; format defined in /Documents/XBT.html.
  • C# dependencies: identified via using directive + assembly-reference walk. Each .cs's referenced assemblies and dependent .cs within the same module form the prerequisite set for its transpilation action.
  • Cross-language dependencies within a module: when a .cpp consumes XHT-generated headers (which contain registration scaffolding for both C++ and transpiled C# types in the module), the .cpp's dependency record lists every {Header}.gen.h it included. When any of those generated headers changes (because the source header or source .cs that produced it changed), the .cpp is reinvalidated.

8.2 Opaque consumption of XHT output

Per plan Section 4 and Rev 11 audit framing: XBT does not parse XHT's binary struct layouts. XBT consumes the per-module text manifest XHT emits (Section 7.1) plus the on-disk content hash of each generated file. When the content hash changes, downstream consumers reinvalidate. This means XBT at Step 1 (System 1) is decoupled from XHT's emit-format finalization at Stage B — XBT does not need to change when XHT's binary schema freezes.

8.3 Cross-language dependency record

For each compile action, XBT records "which XHT-output files were consumed when compiling each .cpp." On the next build, XBT re-checks each recorded file's content hash. If any has changed, the consumer is rebuilt.

9.2 Circular dependencies

Per the UE reference brief: UE supports CircularlyReferencedDependentModules as an explicit allow-list. XPact bans circular module dependencies outright at the contract level. XBT fails the build at module-resolution time with a diagnostic naming the cycle. There is no allow-list. Modules that genuinely need bidirectional access must be merged or split — the cycle is an architectural smell that the contract refuses to launder.

9.3 Tier enforcement — cross-tier dependency edge matrix (NEW Rev 11 — audit finding #8)

The Rev 10 rule "tier dependencies must point downward only (Engine ← Studio ← Project)" was over-broad. The audit identified that the correct rule depends on the dependency type: DynamicallyLoadedModuleNames upward edges are how Engine modules consume Studio plugins at runtime via XLiveCoding / plugin load, and forbidding them breaks the hot-reload model entirely. Rev 11 replaces the blanket rule with the matrix below.

Dependency field Edge type Engine → Engine Studio → Engine Studio → Studio Project → Engine Project → Studio Project → Project Upward (Engine → Studio, etc.)

Conditional / optional dependencies. If a Studio plugin is disabled in this product's .xproject at build time, dependent Project modules' declared deps on it are silently dropped — the build proceeds without the plugin. Tier validation runs as if all declared plugins exist (so the matrix is enforced even on missing plugins); a diagnostic fires if a build is configured with a missing Studio plugin enabled-by-default. Per plan Section 2 Tier dependency enforcement row: "Source-tree path checks are NOT used — paths can be symlinked or restructured; the declared tier in .Build.cs is canonical." Violations of the matrix fail the build at resolution.

9.4 Engine-version compatibility

Per plan Section 2 Plugin versioning & pinning row (Rev 8): XBT enforces engine-version compatibility at build time — the project's declared EngineVersion must satisfy every enabled Studio plugin's MinEngineVersion ≤ EngineVersion ≤ MaxEngineVersion. The plugin descriptor (.xplugin) is read by XBT alongside module descriptors. Schema validation is part of module resolution.

Per-module MinimumToolchainVersion (Rev 11 audit finding #15). A module may declare a minimum toolchain version (XBT version) it requires. XBT validates this against its own version at resolution and rejects with a clear diagnostic naming the module, the required version, and the actual version. This solves the "Roslyn API drift" footgun where a module imports a Roslyn feature added in a later toolchain release.

9.5 Build hooks — typed IBuildHook surface (NEW Rev 11 — audit finding #11)

The Rev 10 contract did not specify a build-hook surface, leaving the door open to UE's CustomBuildSteps.cs pattern (freeform shell-command strings with environment variable interpolation). Per the audit: that pattern is the source of most "I cannot reproduce this on my machine" Unreal build bugs. Rev 11 closes the door with a typed interface.

// Rev 11 IBuildHook interface
public interface IBuildHook
{
    // Declared inputs — absolute paths. XBT tracks them as action prerequisites.
    IReadOnlyList<string> InputFiles { get; }

    // Declared outputs — absolute paths. XBT tracks them as action products.
    IReadOnlyList<string> OutputFiles { get; }

    // Build the IExternalAction the hook runs as. The action participates in
    // the action graph: parallelizable, cacheable (by InputFiles content
    // hashes + the action's CacheKeyComponents per Section 10.3), and
    // incrementalizable (skipped if no input changed and outputs are current).

Hooks declare their inputs and outputs ahead of time. A hook with no declared inputs is a build-graph anomaly that XBT flags as a warning (the hook will run on every build and never get cached). A hook that touches an output file not declared in OutputFiles fails the build with a diagnostic. Freeform shell commands without declared inputs/outputs are not supported.

Reference anti-pattern: UE's CustomBuildSteps.cs lines 15-28 (the RunSteps function that Environment.ExpandEnvironmentVariabless a string and shells out). The XPact contract rejects this approach entirely.

9.6 Descriptor evaluation — declarative-first with expression sub-language (REVISED Rev 11 — audit finding #12)

Rev 11 reversal: The Rev 10 contract declared "the choice between Roslyn-compiled rules and a declarative-only subset is internal to XBT — either approach satisfies this contract." The audit identified the Roslyn cold-start cost (~2 seconds per scope on first build, dominating XBT's startup latency in normal workflows) as significant and unnecessary for the 95% of modules whose descriptor expresses no conditionals. Rev 11 locks the descriptor format as declarative-first.

Trade-off. The reversal trades C# muscle memory (the 5% of power users who wrote if (target.platform == BuildPlatform.Win64) in their .Build.cs) for a 50-100× cold-start speedup that every developer pays on every clean build. The trade was deemed acceptable because (a) the conditional cases are rare and well-served by the expression sub-language, (b) the cold-start win is universal, (c) declarative formats are the cross-tool industry norm (Cargo.toml, Bazel BUILD, etc.), and (d) the existing TOML schema can express all current XPact modules without conditionals at all. Cross-reference: Rev 11 audit finding #12.

The format. Module descriptors are TOML files at {Module}/{Module}.Build.toml. Schema mirrors the C# ModuleRules base class field-by-field in snake_case. Example:

The expression sub-language. For the 5% with conditionals, alongside XScoring.Build.toml the author may place XScoring.Build.expr — a small Starlark-inspired file with sandboxed evaluation. Escape hatch. A module that legitimately needs full C# (an edge case the audit acknowledges may exist) can still ship a .Build.cs file alongside the TOML; XBT detects the .Build.cs and falls back to Roslyn for that module only. This isolates the cold-start cost to the modules that genuinely need it; the rest of the engine never pays.

10. Toolchain Pipeline — XBT → XHT & XIL2CPP (concurrent) → C++ compile → link (REVISED Rev 11)

This section locks the end-to-end invocation sequence and the JSON manifest + binary sidecar XBT emits as the single source of truth shared with XHT and XIL2CPP.

10.1 The sequence (REVISED Rev 11 — XHT and XIL2CPP concurrent)

Per Rev 11 audit finding #5: XHTAction and XIL2CPPAction have no dependency on each other in the action graph. Both consume the manifest; both feed compile. Rev 10's sequential ordering was an over-specification that serialized two independent passes.

  1. XBT discovery + graph build. XBT reads the root engine descriptor (/Engine/Engine.xengine), the project descriptor (/Projects/<ProductName>/<ProductName>.xproject), and every reachable module descriptor (TOML or .Build.cs). Validates Tier per the matrix in Section 9.3; validates engine-version compatibility per Section 9.4; validates every enabled plugin's MinEngineVersion / MaxEngineVersion; validates MinimumToolchainVersion per module; checks SimPath modules use PCHUsage = NoSharedPCHs. Builds the module dependency graph. Fails on any cycle or constraint violation.
  2. XBT manifest emit. XBT writes the JSON manifest to Intermediate/Build/{Target}/{Configuration}/Manifest.json AND a binary sidecar to Intermediate/Build/{Target}/{Configuration}/Manifest.{Hash}.fbs.bin (content-addressable; FlatBuffers). Format below.
  3. XHTAction (per module, parallel-concurrent with XIL2CPPAction). XBT invokes XHT with the binary manifest sidecar path. XHT reads the manifest, parses C++ headers (single-pass tokenizer for reflection markers; the C++ compile happens later and is authoritative for type-checking the C++) and attribute-marked .cs files (XHT's C# front-end), and emits per-header {Header}.gen.h, per-module {Module}.gen.cpp, and the per-module text manifest {Module}.gen.manifest. XHT runs in parallel across modules (no inter-module dependencies in the parse phase).
  4. XIL2CPPAction (per module, parallel-concurrent with XHTAction). XBT invokes XIL2CPP with the same binary manifest sidecar. XIL2CPP reads the manifest, transpiles .cs files into .cpp/.h with GC root scaffolding (Section 3), exception codegen + calling-convention tier classification (Section 5), C# string handle emission (Section 6), and symbol mangling (Section 2). XIL2CPP also runs in parallel across modules.
  5. Per-module pipelining. Once XHTAction finishes module A and XIL2CPPAction finishes module A, the C++ compile actions for module A's TUs can start — the compile does not wait for XHT or XIL2CPP to finish all modules. The action graph expresses this as: CompileCppAction[module A, TU t] has prerequisites XHTAction[module A] + XIL2CPPAction[module A] + WriteManifestAction + transitive includes. XHTAction and XIL2CPPAction are NOT prerequisites to each other.
  6. Copyright validation. XBT runs ValidateCopyrightAction over every authored source file in the build (.h, .cpp, .cs; not generated files; not /Engine/Source/ThirdParty/). Per plan Section 2 Copyright / licensing row: every file must begin with // Copyright Simgenics. All Rights Reserved. Build fails on any missing header. The action is cached by source hash; an unchanged file is not re-validated.
  7. C++ compile actions. XBT schedules compile actions: original .cpp, XHT-generated .gen.cpp, XIL2CPP-generated .cpp. Per-TU flag derivation per Section 4. Action graph — each compile is an IExternalAction with explicit Prerequisites / Produces.
  8. Pre/Post build hooks. Each module's PreBuildHooks run before its compile actions schedule; PostBuildHooks run after its link action completes. Hooks are typed actions per Section 9.5 with declared inputs/outputs.
  9. Link. XBT links each module into a DLL. Banned-platform-libm check (Section 4) applies on SimPath modules. Exception-cleanness check on third-party libs (Section 5.11) applies on Shipping.

The binary sidecar (FlatBuffers; machine-read)

XBT writes the same logical content as a FlatBuffers buffer encoded against a fixed schema. Filename is content-addressable: Manifest.{Hash}.fbs.bin where {Hash} is the BLAKE3 of the binary contents. XHT and XIL2CPP receive the binary path on the command line; they mmap the file and read fields zero-copy. The JSON's ManifestBinaryHash field is the cache key for "did we already process this manifest?" — if a tool's per-run cache already holds the hash, the tool skips re-reading entirely.

Schema-evolution discipline: FlatBuffers fields are append-only. Adding a field is backward-compatible; removing a field requires a contract revision (and a ContractStructureHash bump).

ContractVersion auto-derivation

The ContractStructureHash is computed by XBT at build time as BLAKE3 over a canonical serialization of the contract surface:

  • The manifest JSON-Schema (each field name + type).
  • The marker macro list (Section 1.1 table contents).
  • The body-macro suffix list (Section 1.3 table contents).
  • The mangling-rule grammar (Section 1.4 + Section 2.2).
  • The XGCRootSpan struct field list (Section 3.1).
  • The XResult struct field list (Section 5.5).
  • The exit-code table (Section 13).
  • The cross-tier dep matrix (Section 9.3).

The ContractSemanticTag is a short string (e.g., p11 for "post-Rev-11") that an explicit Toolchain Contract revision can bump independent of the hash — useful for revisions that are textually large but structurally small. The composite ContractVersion is "v1" + first-ten-hex-of-hash + "_" + semantic-tag. The composite is what flows through symbol mangling (Section 2) and through ActionHistory's invalidation key. A Stage B addendum or Step 0.5 addendum that touches any surface above automatically bumps the hash; no manual ContractVersion bump is possible.

Both XHT and XIL2CPP consume the binary sidecar. Neither parses any other tool's binary output during their own work. The manifest is the join key.

10.3 Action graph (REVISED Rev 11)

Every step that produces or consumes files is an action with explicit prerequisites and produced files. The contract names these action types:

  • ValidateCopyrightAction — per source file. Cached by source hash. Output: a marker file in Intermediate.
  • WriteManifestAction — one per build. Outputs: the JSON manifest + the FlatBuffers binary sidecar.
  • XHTAction — one per module. Inputs: manifest + all module headers + all module .cs (read by XHT's C# front-end). Outputs: {Header}.gen.h per public/private header + {Module}.gen.cpp + {Module}.gen.manifest. Not prerequisite to XIL2CPPAction.
  • XIL2CPPAction — one per module. Inputs: manifest + all module .cs files + (XCoreXObject's compiled header surface, for the GC ABI emit). Outputs: transpiled .cpp/.h in the module's intermediate directory. Not prerequisite to XHTAction.
  • CompileCppAction — one per .cpp (original, XHT-generated, or XIL2CPP-generated). Inputs: .cpp + transitive includes + (for the module) XHTAction + XIL2CPPAction for that module. Output: .obj/.o.
  • LinkModuleAction — one per module. Inputs: all .obj/.o + dependency-module import libs. Output: module DLL.
  • BuildHookAction — one per IBuildHook instance. Inputs/outputs declared per Section 9.5.

Incremental builds re-run only actions whose declared prerequisites have changed. Per plan Section 11 Step 5.5 (g): byte-identical compile output across two clean builds is a Foundation Prototype pass criterion — achieved via the reproducibility flags in Section 2.1 plus deterministic action scheduling.

IExternalAction extensions for remote cache (NEW Rev 11 — audit finding #16)

12. Verification

This section enumerates the verifications that XBT.html, XHT.html, and XIL2CPP.html specs (plus their implementations) must satisfy. Several map directly to Foundation Prototype pass criteria (plan Section 11 Step 5.5). Others are contract-internal acceptance gates that XBT enforces during routine builds.

12.1 Reproducibility test

Statement: Two clean builds of the same source on the same machine produce byte-identical compile outputs and byte-identical link outputs. This includes generated headers, transpiled C++, .obj/.o files, and final DLLs.

Mechanism: The full reproducibility envelope from Section 2.1 (/Brepro + /BREPRO + /pathmap + /TIMESTAMP:0 + /INCREMENTAL:NO + /cgthreads on MSVC; -frandomize-layout-seed-file= + --remap-file + --build-id=none + -fdeterministic-cgu-order on Clang; engine-wide content-hash-only invalidation) plus XIL2CPP / XHT's deterministic ordering disciplines from Section 2.4.

Validation: The exact procedure in Section 2.1 (certutil -hashfile / sha256sum after two clean builds).

Maps to: Foundation Prototype criterion (g) "Symbol stability: repeated XIL2CPP runs over the same input produce byte-identical mangled symbol names" generalized to the entire toolchain.

12.2 Hot-reload symbol stability test

Statement: Running XIL2CPP twice over the same input .cs source produces byte-identical mangled output symbols. A method in build N+1 has the same symbol name as in build N if its signature is unchanged.

Mechanism: Section 2 mangling rule (purely structural, no hash, no random beyond the contract-version tag itself) + Section 2.4 determinism requirements.

Maps to: Foundation Prototype criterion (g). Critical for XLiveCoding's RVA-rewrite trampolines — the trampoline target's address resolves by symbol name.

12.3 Cross-config ABI test

Statement: The same C# code compiled in Development (with native exceptions) and in Shipping (with Result<T,E> lowering) produces identical extern "C" entry-point signatures for Tier 1 (shimmed) functions. A C++ caller compiled in Development can link against a Tier 1 transpiled C# function compiled in Shipping (and vice versa) without ABI mismatch.

Mechanism: Section 5 ABI-stable boundary (Tier 1) — the shim signature is fixed; body lowering differs internally only.

Validation: XBT's per-system test harness includes a cross-config link check — build the same module in Dev and Shipping, link the Dev binary against the Shipping module's import lib, run a smoke test. Failure fails the system's merge.

12.4 Calling-convention classification test (NEW Rev 11)

Statement: XIL2CPP's classification algorithm (Section 5.2) classifies a known-noexcept-safe internal method as Tier 2 (direct call, no shim). A method annotated [XFunction(NoThrow = true)] with a transitively-reachable non-noexcept callee fails the build.

Mechanism: Section 5.1 — 5.4.

Validation: The test harness builds a synthetic class with one Tier 1 method (public surface) and one Tier 2 method (internal helper); disassembles the resulting .dll; asserts the Tier 2 method has the natural C++ signature with no XResult out-param. Negative case: a synthetic class with [XFunction(NoThrow = true)] calling a non-noexcept C++ helper; asserts XBT fails the build.

12.5 GC span ABI race test (NEW Rev 11)

Statement: Mid-realloc, a concurrent mark phase observes (base, count) tuples that are always consistent with a live buffer — never half-state. Referents stored in slots that survive the realloc are visible to the GC throughout.

Mechanism: Section 3.5 atomicity contract; collector-internal write-barrier serialization (XCoreXObject).

Validation: Stress test: a transpiled List<Actor> grows from 8 to 16,384 entries while the mark phase runs on a worker thread. The mark phase records the slot-pointers it traced; the test asserts that every live referent is in the trace. Per the Foundation Prototype: this gates criterion (a) "GC pause < 5ms typical" by validating the underlying ABI's correctness.

12.6 Determinism flag-propagation test

Statement: A module declared SimPath = true in its descriptor compiles with /fp:precise + -ffp-contract=off + -mno-fma + Sleef-vendored transcendentals + the banned-API regex check + NoSharedPCHs + SimdLevel = None. A SimPath module that includes a header from a non-SimPath dependency does not inherit the dep's flag posture — SimPath is per-module.

Mechanism: Section 4 of this contract + Section 1.5 PCH lock. XBT's per-platform-toolchain flag tables + the /FI / -include header gate + the link-time platform-libm exclusion.

Validation: The test harness compiles a synthetic SimPath module containing a single sin(x) call; disassembles the resulting .obj; asserts the call target resolves to XSleef_sin not __libm_sse2_sin / sin@GLIBC. Similarly the test harness validates that banned APIs (QueryPerformanceCounter) on a SimPath TU fail the build, and that declaring SimPath = true + PCHUsage = UseSharedPCHs fails resolution.

12.7 Tier enforcement test (REVISED Rev 11 — dep matrix)

Statement: A module declared Tier = Engine in its descriptor that lists a Studio module in its PublicDependencyModuleNames fails the build at module-resolution time. The diagnostic names the offending module and the upward edge. The same module listing the Studio plugin in DynamicallyLoadedModuleNames resolves successfully (per the new Rev 11 dep matrix).

Mechanism: Section 9.3 of this contract.

Validation: The test harness builds two synthetic projects — one with the Studio dep in PublicDependencyModuleNames (must fail) and one with it in DynamicallyLoadedModuleNames (must succeed). Both diagnostics match expected patterns.

12.8 Copyright validation test

Statement: A source file (.h, .cpp, .cs) under any tier's Source/ that does not begin with // Copyright Simgenics. All Rights Reserved. fails the build. A third-party file under /Engine/Source/ThirdParty/ is excluded from the check.

Mechanism: Section 10.1 step 6 of this contract; plan Section 2 Copyright / licensing row.

Validation: The test harness adds a synthetic source file without the header; asserts XBT's ValidateCopyrightAction fails with a diagnostic naming the file.

12.9 Engine-version & toolchain compatibility test

Statement: A project pinning EngineVersion = 0.4.0 with a Studio plugin declaring MinEngineVersion = 0.5.0 fails the build at module-resolution time. A module declaring MinimumToolchainVersion = "2.0.0" when running on toolchain 1.7.0 also fails resolution.

Mechanism: Section 9.4 of this contract; plan Section 2 Plugin versioning & pinning row.

Validation: The test harness builds synthetic project + plugin + module combinations violating each constraint; asserts XBT exits with clear diagnostics.

12.10 Circular-dependency rejection test

Statement: Two modules with mutual dependencies fail the build at module-resolution time. The diagnostic names the cycle.

Mechanism: Section 9.2 of this contract.

Validation: The test harness constructs a synthetic A → B → A cycle; asserts XBT exits non-zero with a cycle diagnostic.

12.11 Reflection round-trip test

Statement: A transpiled C# property is settable and gettable through XPropertyEditor's reflection-driven path with no marshalling errors.

Maps to: Foundation Prototype criterion (f).

Mechanism: XHT extracts the property from [XProperty]-attributed C# fields; XIL2CPP transpiles to a getter/setter pair the shared FProperty table can call; XCoreXObject's reflection runtime dispatches to them.

12.12 Manifest binary sidecar test (NEW Rev 11)

Statement: XBT writes both the JSON manifest and the FlatBuffers binary sidecar on every build. XHT and XIL2CPP read the binary sidecar (verified by reading the sidecar file's mtime + content hash after each tool runs — the JSON's mtime is untouched). The JSON's ManifestBinaryPath field points at the sidecar that was written. The binary sidecar's filename hash matches its content.

Mechanism: Section 10.2 of this contract.

Validation: The test harness builds a synthetic module; asserts both files exist; asserts the binary sidecar's content hash matches its filename; asserts the JSON's ManifestBinaryHash matches.

12.13 Aggregate gate — the Foundation Prototype

The contract's correct implementation across XBT + XHT + XIL2CPP is the prerequisite for the Foundation Prototype milestone at plan Section 11 Step 5.5. Until criteria (a) through (g) hold, the contract is not validated in implementation. The seven Foundation Prototype criteria are:

  1. GC pause < 5ms typical on Quest 3 (validates the GC root-span ABI's throughput in steady state).
  2. GC fallback < 50ms on Quest 3 (validates the GC root-span ABI under saturated remembered-set conditions).
  3. Cross-arch determinism (validates Section 4 flag propagation + Sleef substitution + full reproducibility envelope per Section 2.1).
  4. Single-method hot-patch latency < 30s (validates Section 2 symbol mangling stability + XLiveCoding's patch-DLL discovery).
  5. Cascade hot-patch latency < 120s nominal / < 150s timeout (validates the XLiveCoding cascade orchestration's interaction with Section 9 module-graph topology).
  6. Reflection round-trip (validates Sections 1 + 7 surfaces against runtime consumption).
  7. Symbol stability (validates Section 2 mangling determinism + Section 2.1 reproducibility flags).

Per plan Section 11: "Fail criterion: any single criterion not met. Failure triggers a foundational-design review — revisit XCoreXObject + XIL2CPP design (and possibly the lockstep-determinism commitment) before committing further engineering effort."
