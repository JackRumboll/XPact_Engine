1. Overview and Cross-System Posture

1.1 What XIL2CPP is

XIL2CPP is the XPact IL2CPP transpiler: a standalone C# tool that reads C# 12 source files (the .cs files in any module declaring Languages.CSharp) and produces native C++ source files (.cs.cpp + .cs.h under the module's Intermediate/...//Transpiled/ directory) that the same C++ toolchain compiling the rest of XPact compiles into the final binary. Per XToolchainContract.html §0 line 262: “XIL2CPP transpiles directly from C# source (not IL) and emits hot-patchable, hybrid-GC-aware code rather than Mono-runtime-bound code.”

XIL2CPP is the system that turns gameplay-tier C# code (every XActor subclass, every XComponent subclass, every game-logic function, every event handler) into the same kind of native C++ that XHT-emitted .gen.cpp reflection scaffolding is. By compile time, there is no “C# side” and “C++ side” of the gameplay binary; there is only native code that the linker resolves cross-module.

XIL2CPP is the bridge between two architectures that until 2026-05 looked incompatible: C# as the gameplay-author language (because the user base is industrial-simulation domain experts who write C# more comfortably than C++) and native C++ as the gameplay-runtime substrate (because precise cross-arch determinism on Win64 + Quest 3 ARM64, custom non-moving precise GC integration, and RVA-rewrite hot-reload all require native compilation). The transpiler IS the resolution.

1.2 What XIL2CPP is NOT

XIL2CPP is bounded narrowly. It does NOT ship:

  • A managed runtime. XIL2CPP is NOT a CLR. There is no JIT. There is no GC inside the transpiler's output binary other than XPact's custom non-moving precise GC (XCoreXObject's collector). The C# source compiled by XIL2CPP runs as native C++; the GC that scans XObject references is XCoreXObject's collector, not a hosted .NET GC.
  • A C# bytecode interpreter. XIL2CPP does NOT read IL bytecode (per Constraint Q28 + Locked Commitment 1). It reads C# source via Roslyn's parse tree (CSharpSyntaxTree + semantic model). The IL2CPP name is a historical homage to Unity's IL2CPP but XIL2CPP works at a higher abstraction level: C# AST, not IL bytecode. The rationale is that C# 12's source semantics are richer than the IL bytecode they lower to (e.g., required members, pattern matching, primary constructors are AST-level features that round-trip through IL with information loss).
  • A Roslyn source-generator hosting environment. Per XCoreXObject.html §1.3 line 73 + Master Plan §2a C# version row: “Roslyn source-generator hosting deferred to post-MVP.” XIL2CPP reads C# source as-written; it does NOT execute source generators at transpile time. The C# files XIL2CPP reads are the human-authored sources, not the generator-emitted partials.
  • A full System.Reflection.Emit implementation. Per §4.7 (the C# language-coverage matrix), only the read-side of reflection (typeof(T), obj.GetType(), FClass-keyed lookups via XReflectionRuntime::FindClass) is in MVP. Reflection.Emit, Type.GetMethods+MethodInfo.Invoke dynamic invocation, expression-tree compilation are post-MVP.
  • A .NET BCL (Base Class Library) replacement. Most of System.* is NOT supported. A curated subset is mapped to XPact equivalents: System.String → XCSharpString handle (§5.5); System.Collections.Generic.List<T> → TArray<T'>; System.Collections.Generic.Dictionary<K,V> → TMap<K',V'>; System.Collections.Generic.HashSet<T> → TSet<T'>; System.Numerics.Vector4 + System.Numerics.Quaternion → FVector4 + FQuat. Calls to non-mapped BCL types emit diagnostic XIL2CPP010 — BCL type 'System.Foo' is not in the mapped subset; see the language-coverage matrix in XIL2CPP.html §4. The mapped subset is published as a versioned NuGet package XPact.CSharp.BCL.
  • LINQ. System.Linq.Enumerable.* is banned on sim-path TUs (allocation-heavy, defers execution unpredictably) and is in the post-MVP mapped subset for non-sim-path TUs. See §4.7.
  • The dynamic keyword. dynamic requires the DLR (Dynamic Language Runtime) which is part of the managed runtime. Per Locked Commitment 1, no managed runtime exists. dynamic emits diagnostic XIL2CPP011 — 'dynamic' is not supported; XIL2CPP is a static transpiler.
  • Cross-process / RPC. XIL2CPP does not own RPC; gameplay-replication APIs are XNetworking's deliverable.
  • Hot-reload orchestration. XIL2CPP emits symbols with stable mangling, container layouts with the container = true class-descriptor flag, and free-function-with-explicit-self entry points that XLiveCoding's RVA-rewrite trampoline can patch. The orchestration (quiesce, patch DLL discovery, RVA rewrite, resume) is XLiveCoding's deliverable.
  • The IDE plugin. A Roslyn analyzer that surfaces XIL2CPP diagnostics in Rider / Visual Studio is a downstream deliverable shipped as XPact.CSharp.Analyzer NuGet; the analyzer reuses the same diagnostic-code numbers + same semantic-model walk as XIL2CPP's build-time pass, but is OUT-OF-SCOPE for this design doc.

1.3 L-tier position and dependency posture

XIL2CPP is System 6 per the Master Plan build order (XCoreXObject.html §1.5 line 179; XBT.html §10 line 1464). It belongs to Layer 0 standalone tools alongside XBT (System 1), XHT (System 2), XAutomationTool (per XToolchainContract.html §10.2 line 1845: “Layer-0 standalone tools (XBT, XHT, XIL2CPP, XAutomationTool)”).

XIL2CPP is one of the three Toolchain Contract participants alongside XBT (build tool) and XHT (header tool) per XToolchainContract.html §0 line 258-263. All three consume the same contract ABI (symbol mangling, GC root span format, exception calling convention, manifest format).

XIL2CPP runs concurrent with XHT, not sequential (XBT.html §10.6 line 1494-1498; XToolchainContract.html §10.1 line 1704-1713). For module M: XHT(M) parses M's headers + XHT-attributed C# classes and emits .gen.h + .gen.cpp reflection scaffolding; XIL2CPP(M) parses M's C# bodies and emits .cs.cpp + .cs.h transpiled code. Neither is prerequisite to the other; both are prerequisite to M's C++ compile step.

1.5 Hot-reload posture (forward-declared; see §8 for the full design)

XIL2CPP-emitted code is hot-reloadable at the granularity the Toolchain Contract specifies: Tier 1 shims (the extern "C" entry points) are RVA-rewrite-target-eligible; Tier 2 direct calls are NOT individually hot-reloadable but rebuild with their owning module. The structural invariants XIL2CPP commits to at Rev 1:

  • Symbol mangling is byte-identical across repeated transpilation runs of the same input C# source (Contract §12.2 line 2163; criterion (g)).
  • No virtual methods on the FXObjectLifecycleTable surface (PostInitProperties / BeginDestroy / etc.); dispatch is through the function-pointer table per XCoreXObject Rev 4's FakeVTable pattern. Hot-reload class replacement only updates the table contents; the table address is stable across the session.
  • Container layouts are frozen for the hot-reload session; XIL2CPP emits container = true on every class that embeds an XGCRootSpan, which XLiveCoding's patch-validation pass uses to reject any patch that mutates a container's field layout (Contract §3.7 line 737-739).
  • Per-FClass sub-pool rebind cooperation: XIL2CPP-emitted Z_Construct_FClass_* functions register listeners for the per-FClass sub-pool rebind event (FIX-A-MIN-40 in XCoreXObject Rev 4) and do not assume the old FClass*-to-cell-pool mapping survives the patch.

1.6 Sim-path posture (forward-declared; see §7 for the full design)

XIL2CPP emits code for both sim-path TUs (modules with SimPath = true in their .Build.cs / .toml) and non-sim-path TUs. For sim-path TUs, additional emit obligations apply:

  • At every XObject.New<T>(...) call, XIL2CPP emits a runtime check XPACT_CHECK_SL(::XCore::HAL::IsSimPathThread() || !::XCore::HAL::IsSimPathTU()) (the same check XCoreXObject's NewObject path inserts). This is belt-and-suspenders: XCoreXObject's check fires inside the runtime; XIL2CPP's emit-side check fires inline at the call site (avoiding the function call when the assertion is false in Dev builds).
  • C# language features that are deterministically nondeterministic emit build-time errors on sim-path TUs: System.DateTime.Now, System.Diagnostics.Stopwatch, System.Random.Shared, System.Environment.TickCount, System.Threading.Thread.CurrentThread.ManagedThreadId, calls to typeof(T).GetHashCode() when the resulting hash is used for ordering, calls to obj.GetHashCode() on reference-typed objects (because default reference-hash codes are unstable across runs). See §7.4 for the banned set.
  • C# language features that have nondeterministic IL emit but deterministic source emit (e.g., foreach over a HashSet<T>) emit build-time warnings on sim-path TUs (the iteration order is implementation-defined; cross-arch behavior may differ).
  • Cross-arch determinism (Win64 + Quest 3 ARM64 bit-exact) commitment: same C# source → same C++ emit → same runtime behavior on both architectures, including bit-exact floating-point semantics per Contract §4 (which XIL2CPP-emitted .cs.cpp inherits from the per-target compile flags XBT propagates).

1.7 Determinism commitment

XIL2CPP's own behavior MUST be deterministic. Per XToolchainContract.html §2.4 line 519-527 + §12.1 line 2151:

  • Running XIL2CPP twice over identical C# source → byte-identical output .cs.cpp + .cs.h files.
  • Mangling walk is in source-declaration order; XIL2CPP's internal dict iteration is sorted by name before emit.
  • XIL2CPP's own binary is reproducible: built with the reproducibility envelope (deterministic timestamps, deterministic build IDs, deterministic obj-file ordering).
  • The transpilation cache key (per-action) hashes: SHA-256 of every input .cs file, SHA-256 of the XHT-emitted reflection manifest the module consumes, SHA-256 of the per-target settings struct, SHA-256 of the per-module ModuleRules-derived flag set, SHA-256 of every dependent module's TierTable.partial..json (for Pass 2 mode), SHA-256 of XIL2CPP's own binary. Cache hit produces byte-identical outputs.

2. Architectural Commitments (Locked)

2.1 Commitment 1: Pure transpilation (NO hosted CLR)

The commitment. XIL2CPP is a C# source → native C++ compiler operating at build time. The output binary contains only native code. There is no managed runtime hosted at game time. There is no nethost, no hostfxr, no coreclr.dll, no Mono, no P/Invoke marshalling layer, no IL-to-native JIT, no DLR. The only runtime services the transpiled C# code depends on are XPact's own runtimes: XCoreXObject's collector, XCore-4a's allocator, XReflectionRuntime's FName-keyed lookup.

Rationale. Three Foundation Prototype acceptance criteria are jointly unsatisfiable under a hosted-CLR model:

  1. X10 — Precise stack scanning requires the GC to enumerate 100% of XObject pointers live on the stack frame of any function that might be at a safe-point. A hosted .NET CLR runs its own GC over its own managed heap; XPact's collector cannot see into the CLR's managed objects, and the CLR's GC cannot see XPact's XObjects. A bridge GC-handle table (the conventional pattern for managed-native interop) introduces double-tracking, latency between the two collectors, and edge cases where an XObject reference held only by a managed local is invisible to XPact's GC. None of these are acceptable per the < 5 ms GC pause budget (criterion (a)).
  2. Criterion (c) — Cross-arch bit-exact determinism on Win64 + Quest 3 ARM64. The .NET runtime's JIT compiler emits different machine code on x86_64 vs ARM64 from the same IL, and the JIT's choices (whether to inline, which loop unrolling, which SIMD intrinsics to substitute) are not deterministic across .NET versions, GC heap pressure, or even repeated runs of the same binary. The deterministic FP-semantics lock in Contract §4 cannot be enforced over JIT-emitted code. Only AOT-compiled native code under our own toolchain matrix (MSVC 19.44+ / Clang 17+ / GCC 13+ with the locked flag set) gives byte-exact reproducibility.
  3. Criterion (d) — Single-method hot-patch < 30 s via RVA-rewrite trampolines. RVA-rewrite requires the patched function's entry point to be at a stable symbol name resolvable by the patcher. Hosted-CLR managed methods do not have a stable native entry point; the JIT picks the address on first invocation. The conventional alternative (recompile the managed assembly, reload it, fix up references) takes seconds to tens of seconds per assembly — far over the < 30 s budget for a single-method patch.

Beyond the criteria, the hosted-CLR pattern carries a per-call boxing tax (managed-to-native marshalling) and a per-object handle tax (GCHandle for every managed-held native pointer) that compound over a game frame. Unity's gameplay-tier C# is famously the slowest part of Unity programs precisely because of these taxes. XPact rejects them at the architecture level.

Alternatives rejected.

  • Hosted CLR via nethost/hostfxr. The Unity approach. Rejected per the criteria above. The 58-day-old project_architecture memory entry referencing “.NET 9 runtime hosted via nethost/hostfxr APIs … P/Invoke with DisableRuntimeMarshalling, custom NativeMarshalling attributes … ScriptingObject (C++) ↔ Object (C#) bridging with GC handles and IntPtr” was PRE-XPACT and is SUPERSEDED. No subsequent XPact design doc references hosted CLR.
  • Hosted .NET Native AOT. A 2025 .NET feature that AOT-compiles managed code to native. Rejected because (a) it still produces .NET managed-runtime native code with its own GC and managed-object headers, which doesn't unify with XCoreXObject's collector; (b) the AOT-emit choices are not deterministic across host platforms; (c) the .NET AOT toolchain emits Roslyn-internal helpers that we have no control over.
  • IL2CPP-style IL bytecode → C++ transpilation (Unity's approach). Reads compiled IL bytecode; emits C++. Rejected because (a) C# 12's source-level features (required members, primary constructors, record decompositions, file-scoped namespaces) lower to IL with information loss, and the transpiler needs the source-level information to emit clean C++; (b) IL bytecode is denormalized (a single source-level switch with a pattern-match lowers to a Roslyn-emitted state machine in IL that is hard to recover the original intent from); (c) reading C# source via Roslyn is no more complex than reading IL via Mono.Cecil and gives much better diagnostics that point back to the human-author's line numbers.
  • Hybrid: transpile some C#, host CLR for the rest. Rejected because the split is impossible to defend at the design level. If editor-tier C# is hosted-CLR and gameplay-tier C# is transpiled, the boundary becomes a P/Invoke surface that re-introduces the boxing tax + GC handle tax for every editor-driven gameplay update. If sim-path is transpiled and non-sim-path is hosted, the same problem applies + the non-sim-path code can't access XObjects without GC handles. There is no clean split.

Critical design decision (Locked Commitment 1). All XIL2CPP emit MUST assume native-compiled C++ output executing without a managed runtime. Any design proposal in this document that smuggles in IL execution, runtime CLR features, GC handle bridging, or P/Invoke shims MUST be rejected at audit. The Round 1 audit MUST scrutinize this commitment specifically: any section that implicitly assumes a managed runtime is a Rev 1 bug.

2.2 Commitment 2: C# 12 (.NET 8) MVP; .NET 9 post-MVP

The commitment. XIL2CPP MVP targets C# 12 syntax + semantics. Specifically:

  • Language version pinned at LangVersion=12 in every module's .csproj-equivalent metadata. Modules that declare a higher LangVersion fail the build with diagnostic XIL2CPP020 — Module 'M' declares LangVersion 13 but XIL2CPP MVP targets C# 12. Set 12 in the module's TOML or downgrade to MVP-supported features.
  • Runtime target pinned at .NET 8 BCL surface (the BCL types XIL2CPP recognizes in the mapping table per §4.5). .NET 8 was the long-term-support release at MVP design time; .NET 9 is current LTS at Rev 1 authoring time (2026-05-28) but introduces enough preview-feature churn that locking to .NET 8 is the Prime-Directive-correct conservative choice.
  • Roslyn parse via Microsoft.CodeAnalysis.CSharp v4.8+ (the version that supports C# 12 fully; pinned in the XPact.CSharp.Roslyn shared NuGet package).

C# 12 features explicitly in MVP:

  • required members — emit constructor-time validation per §5.4.
  • Primary constructors — emit the primary-constructor parameters as FProperty entries with auto-property semantics per XCore-4b.html line 725.
  • Collection expressions ([1, 2, 3] as List<int> or int[]) — emit as the appropriate container construction.
  • Raw string literals ("""hello""") — emit as interned const FString* in .rodata per §5.5.
  • File-scoped namespaces (namespace X.Y;) — same emit as block-scoped.
  • Pattern matching (positional, property, list, type, relational, logical) — emit as cascading C++ if chains per §5.6.
  • Records (positional, struct, class) — emit as FScriptStruct-shaped types with value-equality per XCore-4b.html line 725.
  • Tuples ((int a, string b)) — emit as anonymous struct or std::tuple-equivalent; see §5.7.
  • Local functions + static local functions — emit as same-file C++ functions in an anonymous namespace.
  • Lambdas + closures (per §5.9) — emit as state-machine struct with XGCRootSpan over captured XObject*.
  • Expression-bodied members — same emit as block-bodied.
  • Generics (closed instantiation walk; max depth 16; cycle detection) — per §5.8 + Constraint §4.6.
  • Generic constraints (where T : XObject, where T : struct, where T : unmanaged, where T : new()) — per §5.8.
  • nameof(X) — emit as interned const FString* per Contract §6.2 line 1117-1120.
  • typeof(T) — emit as const FClass* resolved via XReflectionRuntime::FindClass; see Q7 resolution §5.11.

C# 12 features deferred to post-MVP:

  • async / await on sim-path TUs — Q4 resolution per §7.6: BANNED on sim-path. Non-sim-path async is in MVP per §5.9.
  • System.Reflection.Emit + dynamic code — explicitly post-MVP per XCoreXObject.html §1.3 line 73.
  • dynamic keyword — permanently banned per Locked Commitment 1.
  • Source generators — post-MVP per Master Plan.
  • LINQ on sim-path — permanently banned per §7.4; non-sim-path LINQ is post-MVP (the System.Linq.Enumerable surface is large and the deferred-execution semantics need careful design).
  • P/Invoke (DllImport) — permanently banned per Locked Commitment 1.

Rationale. Conservative; matches what Unity's IL2CPP targets at any given release. Avoids preview-feature churn during XIL2CPP development. C# 12 has been stable since November 2023 (over two years at Rev 1 authoring); the Roslyn parser for C# 12 is mature; the IL semantics are well-understood. .NET 9 introduces interceptors, params Span<T>, alias-any-type, and other features that would require XIL2CPP to handle additional emit cases without giving MVP a strict capability advantage.

Alternatives rejected.

  • C# 13 / .NET 9 MVP. Rejected: preview-feature churn during XIL2CPP's multi-month implementation phase would force scope creep.
  • C# 11 / .NET 7 MVP. Rejected: missing primary constructors (a load-bearing record feature for gameplay-author ergonomics) and collection expressions; net loss vs C# 12.
  • C# 10 / .NET 6 MVP. Rejected: missing required members + primary constructors + collection expressions + raw strings; significant ergonomic regression.

Critical design decision (Locked Commitment 2). Every XIL2CPP emit pass MUST operate on a C# 12 parse tree (via Roslyn 4.8+). Round 1 audit MUST verify that no Rev 1 emit rule relies on C# 13+ syntactic features.

2.3 Commitment 3: Explicit factory required — new Foo() for XObject-derived is a COMPILE-TIME ERROR

The commitment. C# user code that derives from XObject (transitively: any class with XObject in its base-class chain) MUST construct instances via the explicit XObject.New<Foo>(outer, name, flags) factory or one of its overloads. C# source code that contains new Foo() where Foo is XObject-derived emits the diagnostic:

XIL2CPP001: new-expression on XObject-derived type 'Foo'; use XObject.New<Foo>(outer, name, flags) instead.

  File:    Source/Game/MyActor.cs(42,17)
  Source:  var pickup = new HealthPickup();
                       ^^^^^^^^^^^^^^^^^^^

  XObject-derived types require an explicit Outer (the parent in the ownership chain),
  Name (the FName identity for serialization + replication), and Flags (EObjectFlags
  controlling lifecycle behavior). The XObject.New<T> factory enforces this at the
  call site so the ownership tree is always visible.

  Suggested fix:
    var pickup = XObject.New<HealthPickup>(outer: this, name: "Pickup_1", flags: RF_NoFlags);

The error is emitted at build time. Build exits with code 63 (XIL2CPP analysis failure; XBT aggregates as exit 61).

Rationale. Defaults hide lifetime bugs. In Unreal Engine, NewObject<UFoo>() (no arguments) silently defaults Outer to GetTransientPackage(), which means the object is owned by the engine's transient root and will be GC'd at the next sweep unless something else roots it. Every UE shipping title contains pickup actors that disappear after one frame because the developer wrote NewObject<APickup>() without an Outer. The diagnosis trail (“why did my object vanish?” → “the GC swept it” → “why? It has a player reference” → “the reference is a raw pointer not a UPROPERTY”) is the most common UE gameplay-author bug class.

XPact's solution: make the omission a compile-time error. The author MUST write an Outer + Name + Flags at every construction site. The Outer is the ownership root; objects without an Outer cannot exist (the runtime asserts on null Outer). The Name is the FName identity; objects without a Name cannot be replicated or serialized. The Flags are the lifecycle controls (RF_Standalone, RF_NeedLoad, RF_Transient, etc.).

This is the same pattern UE's NewObject<T>(Outer, Name, Flags) uses, but with the defaults removed. UE chose to provide defaults to ease the learning curve; XPact chooses to require explicit construction to eliminate the bug class. Per Prime Directive: “Use the thing that is correct not the thing that is easier to implement.”

The XObject.New<T> static factory in C#. The C# surface exposed to gameplay authors is:

namespace XPact.CoreXObject;

public static class XObject
{
    /// <summary>
    /// Constructs a new XObject-derived instance.
    /// </summary>
    /// <typeparam name="T">The XObject-derived type to construct.</typeparam>
    /// <param name="outer">The ownership parent. Must not be null.</param>
    /// <param name="name">The FName identity. Use NAME_None for engine-internal objects.</param>
    /// <param name="flags">Lifecycle flags. Use RF_NoFlags for plain gameplay objects.</param>
    /// <returns>The constructed instance. Asserts on OOM.</returns>
    public static T New<T>(XObject outer, FName name, EObjectFlags flags) where T : XObject, new();

    /// <summary>
    /// Fallible-style overload returning Result<T, FNewObjectError>.
    /// </summary>
    public static Result<T, FNewObjectError> TryNew<T>(XObject outer, FName name, EObjectFlags flags) where T : XObject, new();
}

XIL2CPP transpiles XObject.New<Foo>(outer, name, flags) to the C++ NewObject<XFoo>(outer, name, flags) per XCoreXObject.html §3.5 line 830. The where T : new() constraint is a Roslyn-side hint for the analyzer; the runtime constructor invocation is via the FClass's ClassConstructorFn slot (NOT through C# reflection).

The diagnostic implementation. XIL2CPP's semantic-analysis pass walks the parse tree looking for ObjectCreationExpressionSyntax nodes whose resolved type derives from XObject. The check is exact:

foreach (var creation in syntaxTree.GetRoot().DescendantNodes().OfType<ObjectCreationExpressionSyntax>())
{
    var typeSymbol = semanticModel.GetTypeInfo(creation).Type;
    if (typeSymbol is null) continue;
    if (IsXObjectDerived(typeSymbol))
    {
        diagnostics.Add(Diagnostic.Create(
            XIL2CPP001,
            creation.GetLocation(),
            typeSymbol.Name));
    }
}

Edge cases the Round 1 audit MUST scrutinize:

  • Generic constructors. new T() in a generic method where T : XObject, new(): this is a deferred construction call that resolves at instantiation time. XIL2CPP defers the diagnostic to instantiation time; if the closed T derives from XObject, the diagnostic fires at the closed-instantiation walk.
  • The XObject.New<T> factory itself. The factory's implementation must construct the instance somehow. The factory's C# body is hidden from the diagnostic via an internal attribute [XObjectInternalConstructor] that XIL2CPP recognizes and suppresses the diagnostic for. Only the factory and its tightly-controlled overloads carry the attribute.
  • Reflection-driven construction. Activator.CreateInstance(typeof(Foo)) bypasses the diagnostic at the source level (the expression's resolved type is object). It is BANNED on sim-path TUs per §7.4 (nondeterministic; same hash-code instability issue) and emits a warning on non-sim-path TUs that suggests rewriting via XObject.New<T>.
  • Object initializers. new Foo { X = 1, Y = 2 } is the same diagnostic as new Foo(); the initializer block does not exempt the construction.
  • Records derived from XObject. C# 12 records can technically derive from XObject (records are sugar over class). The same diagnostic applies; the primary constructor doesn't exempt the diagnostic. Records that derive from XObject are atypical and the documentation discourages them; the diagnostic stays.

Critical design decision (Locked Commitment 3). XIL2CPP MUST emit XIL2CPP001 for every new Foo() on XObject-derived types at every transpile pass. The diagnostic is non-suppressible (no #pragma warning disable XIL2CPP001). Round 1 audit MUST verify that no edge case (generics, records, reflection, object initializers) bypasses the diagnostic.

3.2 Pass-by-pass detail

Pass 1 — Roslyn Parse + Bind. XIL2CPP uses Microsoft.CodeAnalysis.CSharp.CSharpSyntaxTree.ParseText on each .cs file with CSharpParseOptions(LanguageVersion.CSharp12). The set of syntax trees forms a CSharpCompilation with references to: (a) the .NET 8 reference assemblies for the curated BCL subset (the XPact.CSharp.BCL NuGet package's reference-only DLL); (b) the per-module dependency closure (each dependency module's reference DLL is built by an earlier ReferenceCompileCSharpAction ordinal 14 per the XBT action-graph extension specified in §9). The reference DLL is a stub: it contains type signatures + method signatures but no method bodies (compiled with /refonly). This lets XIL2CPP resolve types + perform semantic analysis without parsing every transitive dependency's source.

The semantic model is built lazily per syntax-tree. XIL2CPP walks the parse tree depth-first, requesting semantic info on each node it needs to bind. Type resolution failures (unresolved references, ambiguous overloads, missing using directives) produce standard Roslyn diagnostics with file:line:col location and XPact-augmented context (which module is being transpiled, which dependency module the unresolved reference would belong to).

Pass 2 — AST Normalization. Several C# 12 syntactic constructs are sugar over simpler forms. The normalization pass lowers them to canonical forms so subsequent passes have fewer cases to handle:

  • Expression-bodied members. int Foo() => 42; → int Foo() { return 42; }. Same emit.
  • Pattern matching. Property patterns, list patterns, type patterns, relational patterns, logical patterns lower to nested if/switch chains. Each pattern's when clause becomes an additional if guard. See §5.6.
  • using blocks. using (var x = expr) { ... } → { var x = expr; try { ... } finally { ((IDisposable)x).Dispose(); } }. Subsequent emit passes treat try/finally as the canonical form.
  • Collection expressions. [1, 2, 3] targeted at List<int> → new List<int> { 1, 2, 3 }; targeted at int[] → new int[] { 1, 2, 3 }; targeted at ReadOnlySpan<int> → stackalloc int[] { 1, 2, 3 } wrapped in a Span ctor (per Q10 resolution §5.13).
  • Record positional constructors. public record Foo(int X, int Y); → public record Foo { public int X { get; init; } public int Y { get; init; } public Foo(int X, int Y) { this.X = X; this.Y = Y; } /* + Equals + GetHashCode + Deconstruct + ToString */ }. The compiler-generated members are emitted explicitly so subsequent emit passes treat them uniformly.
  • Record with expressions. record1 with { X = 10 } → the record's copy constructor invocation followed by property setter calls.
  • String interpolation. $"hello {name}" → String.Format("hello {0}", name) → XPact-specific FString builder per §5.5.
  • Local functions. Captured-variable analysis lowers them to a generated class with the captures as fields, similar to lambdas (§5.9). Non-capturing local functions emit as same-file C++ functions in an anonymous namespace.

Pass 3 — Semantic Analysis + Validation. The validation pass walks the normalized tree gathering metadata for the emit pass:

  • XIL2CPP001 diagnostic. Every ObjectCreationExpressionSyntax where the resolved type derives from XObject and the construction is NOT inside the XObject.New<T> factory (identified by the [XObjectInternalConstructor] attribute) emits the diagnostic.
  • Sim-path banned-API enumeration. If the module's sim_path = true, the validation pass walks every MemberAccessExpressionSyntax and InvocationExpressionSyntax and checks the resolved member's full type name against the XSimPathBannedAPIs.txt list (see §7.4). Matches emit diagnostic XIL2CPP040 — sim-path TU calls banned API <FullName>; build exit 41.
  • Reference-store site enumeration. Every AssignmentExpressionSyntax whose LHS is a reference-to-XObject field (resolved via FProperty knowledge from the cross-language type-pair manifest) is recorded for write-barrier emission in Pass 6.
  • Container site enumeration. Every variable declaration / field declaration whose type is List<T>, Dictionary<K,V>, HashSet<T> with an XObject-derived generic argument is recorded; the closed-instantiation walk produces the typed TArray<XPtr<T'>> / TMap<K',XPtr<V'>> / TSet<XPtr<T'>> emit signature.
  • Lambda + closure capture analysis. For each lambda, Roslyn's data-flow analysis enumerates captured variables. Captures that are XObject* are recorded for the closure-struct's XGCRootSpan emission in Pass 6.
  • Async state-machine site enumeration. Every async method is recorded; if the module is sim-path, this is a banned-API diagnostic. Non-sim-path async methods have their locals + parameters analyzed for cross-await-boundary XObject* references, which become the state-machine's XGCRootSpan captures.
  • Generic instantiation closed-walk. Recursively walk the type-argument closure of every generic instantiation reached by the program. Bound by depth 16; cycle-detect via a HashSet of visited (open_generic, type_args) tuples. Depth 17 emits XIL2CPP123; cycle emits XIL2CPP124. The closed-walk produces the list of FClass instances that XIL2CPP must emit at Pass 6.
  • Reflection consumption. Every typeof(T) expression resolves to a const FClass* at emit time; the target type's StaticClass() function is called. Every obj.GetType() resolves to a virtual dispatch through XObject's GetClass() function-pointer slot (NOT through a managed reflection API). Every Type.GetMethods() / MethodInfo.Invoke() emits diagnostic XIL2CPP050 — dynamic reflection invocation is post-MVP; use compile-time FClass dispatch.
  • XHT cross-language type-pair correlation. The module's .gen.manifest (per XHT.html §17.3 line 1580) lists C# types that XHT also produces reflection scaffolding for; XIL2CPP must NOT duplicate the FClass emission for these types but instead consume the XHT-side FClass declaration. The correlation table is consulted at Pass 6 emit time.
  • Cross-module callee NoThrow lookup (Pass 1 mode). Every method call's resolved target is checked: if the target is in another module and the module's XHT-emitted reflection metadata carries [XFunction(NoThrow = true)], the call is potentially Tier 2; otherwise the call forces the caller to Tier 1 (or, in Pass 2 mode, the caller is conservatively Tier 1 and Pass 2 may re-promote).

Pass 4 — Tier Classification (Pass 1). Per-function fixpoint over the module's call graph. Initial assumption: every function is Tier 2. Iteration: for each function f, if f fails any clause of the Tier 2 condition (per Constraint §2.8), demote to Tier 1. Iterate until fixpoint. Cross-module callees are treated per the NoThrow lookup; missing NoThrow means conservative Tier 1. The output is a per-function StableId -> (Tier1 | Tier2) mapping, serialized as JSON to Intermediate/Build/<Target>/<Configuration>/TierTable.partial.<Module>.json.

Pass 5 — Mangling Assignment. Walk every emittable function (every C# method, constructor, static constructor, operator overload, indexer accessor, property getter/setter, lambda body, async MoveNext, local function body, generic instantiation closed form). For each, compute the Itanium-ABI-style length-prefixed mangled name per Contract §2.2 + §2.3. The walk is in source-declaration order (Roslyn provides syntax-tree order; for cross-tree walks the tree order is by file path lexicographic). The output is a per-function (StableId, MangledName, LinkerName) table.

Pass 6 — C++ Emit. The emit pass is the largest single pass in XIL2CPP. It produces:

  • Per .cs file F — one F.cs.cpp + one F.cs.h.
  • Per [XClass]-attributed C# class C — one Z_Construct_FClass_<Module>_<Type> function definition in F.cs.cpp; one constinit const FClass XType_Class in F.cs.cpp's .rodata; one constinit const FXObjectLifecycleTable XType_LifecycleTable in .rodata; Z_PostInitProperties_<Type>, Z_BeginDestroy_<Type>, Z_FinishDestroy_<Type>, etc. function bodies.
  • Per C# method M — one Tier 1 shim function (extern "C") OR one Tier 2 direct function (per the Pass 4 classification) plus a Tier 1 shim if M is exported from the module's DLL; the body lowers C# statements to C++ statements per the mapping rules in §5.
  • Per generic instantiation (closed type tree) — one FClass per closed instantiation reached; one TArray<XPtr<T'>> / TMap<K',XPtr<V'>> partial specialization with XGCRootSpan if the instantiation contains XObject* refs; nothing if pure-value.
  • Per C# lambda — one closure struct in an anonymous namespace; one operator(); XGCRootSpan registration in the struct's constructor if captures include XObject*; XGCRootSpan unregistration in the destructor.
  • Per C# async method — one state-machine struct; the original method body becomes MoveNext(); XGCRootSpan registration over the locals that survive across await boundaries.
  • Per C# function — one FStackMapRecord static const in .rodata listing the byte-offset of every live XObject* local and argument; one safe-point check at function entry; one safe-point check at each loop's back-edge (where the loop is determined-long; the threshold is iteration-count-unknown by static analysis).
  • Per reference-storing assignment — one XPACT_GC_STORE(parent_obj, &slot, new_value) inline expansion (NOT a function call; the macro is defined in XCoreXObject's public header and lowers to the card-table-write + store sequence per XCoreXObject.html §5.2).
  • Per sim-path XObject.New<T> call — one XPACT_CHECK_SL(::XCore::HAL::IsSimPathThread() || !::XCore::HAL::IsSimPathTU()) guard immediately before the NewObject<T>(outer, name, flags) invocation.
  • Per .cs.cpp file — one static_assert(XPactDetail::CompileTimeStrEq(XPACT_FCLASS_LAYOUT_TAG, "v6")) + sibling sizeof pins matching the manifest's ABI envelope tags (per Contract §14.1-14.3 + Constraint §3.12-3.13).

Pass 7 — Output Write. Write all generated .cs.cpp + .cs.h files to Intermediate/Build/<Target>/<Configuration>/<Module>/Transpiled/. Write per-module Transpilation.manifest.json listing every input .cs + every output file + the per-action cache key. Write TierTable.partial.<Module>.json. Emit XInsights events: XIL2CPP.Transpile.ModuleCompleted with metadata {Module: M, Files: N_cs, OutputBytes: B, Tier1Count: T1, Tier2Count: T2, ElapsedMs: E}.

3.3 Two-pass tier classification protocol

The fully-correct tier classification of every function requires whole-program knowledge: f is Tier 2 iff every transitive callee of f is Tier 2, including cross-module callees. But per-module concurrent compilation forbids whole-program knowledge at per-module emit time. XIL2CPP resolves this with a two-pass protocol per Constraint §2.8:

Pass 1 (mandatory MVP). Each per-module XIL2CPPAction classifies its own functions using:

  • Same-module callees: participate in the per-module fixpoint as usual.
  • Cross-module callees: conservatively Tier 1 UNLESS the callee carries [XFunction(NoThrow = true)] annotation in its declaring module's XHT-emitted reflection metadata (which XIL2CPP can read at parse time, since XHT runs concurrent with XIL2CPP and the manifest references both module's outputs).

The output is TierTable.partial.<Module>.json: a sorted-by-StableId JSON map. Schema:

{
  "$schema": "https://xpact.dev/schemas/TierTable.partial.v1.json",
  "schemaVersion": 1,
  "module": "MyModule",
  "contractVersion": "v1ab12cd34",
  "functions": [
    {
      "stableId": "Simgenics.XPact.GameFramework.Valve.SetOpenFraction(System.Single):System.Void",
      "manglingV1": "_v1ab12cd34__Simgenics__XPact__GameFramework__Valve__SetOpenFraction_P_R_Simgenics__XPact__GameFramework__Valve_V_float",
      "tier": "Tier1",
      "reason": "calls cross-module Simgenics.XPact.Telemetry.RecordValveEvent which lacks NoThrow annotation",
      "exported": false,
      "canThrowAttributed": false,
      "noThrowAttributed": false,
      "throwsInBody": false,
      "calleesUnverified": ["Simgenics.XPact.Telemetry.RecordValveEvent(...):..."]
    },
    {
      "stableId": "Simgenics.XPact.GameFramework.Valve.ComputeFlowRate():System.Single",
      "manglingV1": "_v1ab12cd34__Simgenics__XPact__GameFramework__Valve__ComputeFlowRate_P_R_Simgenics__XPact__GameFramework__Valve",
      "tier": "Tier2",
      "reason": "all callees Tier 2; body has no throw; not exported; no unsafe C++ callee",
      "exported": false,
      "canThrowAttributed": false,
      "noThrowAttributed": false,
      "throwsInBody": false,
      "calleesUnverified": []
    }
  ]
}

Pass 2 (post-MVP; default off). When XBT is invoked with -EnableTier2WholeProgram, XBT runs a Tier2WholeProgramPass action (XActionType ordinal 13 per XBT.html §5.1 line 781). The pass:

  1. Reads every per-module TierTable.partial.<Module>.json.
  2. Builds the cross-module call graph.
  3. For each function that Pass 1 conservatively marked Tier 1 due to an unverified cross-module callee, checks whether the callee is now provably Tier 2 (with whole-program knowledge). If yes, promote the function to Tier 2.
  4. Iterate until fixpoint.
  5. Emit a merged TierTable.json with the final tier assignments.
  6. Re-invoke XIL2CPP per affected module in -WholeProgramTier2 mode with the merged tier table as input; XIL2CPP re-emits only the affected functions (the delta), reusing the cached emit for the others.

Critical guarantee. Pass 2 NEVER demotes a function from Tier 2 to Tier 1. Demotion would break ABI (the function's signature would change). Pass 2 only promotes.

Critical design decision. Pass 1 is MANDATORY in MVP. Pass 2 is OPT-IN and post-MVP. Per Prime Directive, “the easy way” would be to skip Pass 1 and always emit Tier 1 (the conservative shape). The Prime-Directive-correct path is Pass 1 fixed at MVP — Pass 1 catches every same-module promotion, which empirically (from Unity's IL2CPP body of work) covers ~85% of methods, and the per-module fixpoint runs in O(call-graph-edges) per module which is fast.

3.4 Incremental compilation discipline

XIL2CPP is incremental at the per-action granularity. The per-module action's cache key (per Constraint §7.4 + XBT.html §15.1 line 1687):

CacheKey = SHA256(
  XIL2CPP_binary_content_hash,
  XPact_Mangling_NuGet_version,
  XPact_CSharp_BCL_NuGet_version,
  XPact_CSharp_Roslyn_NuGet_version,
  Manifest_version,
  Module_name,
  Module_sim_path_flag,
  Module_simd_level,
  Module_pch_usage,
  Per-target settings struct serialized JSON,
  ContractVersion (e.g., "v1ab12cd34"),
  Sorted_concatenation(
    SHA256(every .cs file in csharp_sources, in lexicographic order)
  ),
  Sorted_concatenation(
    SHA256(every dependency module's XHT-emitted reflection manifest)
  ),
  Sorted_concatenation(
    SHA256(every dependency module's TierTable.partial.json)
  )
)

Cache hit → XIL2CPP reuses the prior emit; no parse / no semantic-model / no emit. Cache miss → full pipeline runs. The cache lookup is sub-millisecond (SHA-256 of inputs is computed by XBT and passed as a precomputed CacheKey value).

Cross-module ripple effect. If a dependency module's XHT-emitted reflection manifest changes (e.g., a new FProperty added to a base class), the consuming module's CacheKey changes → cache miss → full retranspile. This is the correct behavior: a base-class property change must propagate through the closed-instantiation walk + the lifecycle slot emit.

Pass 2 mode incremental. When -EnableTier2WholeProgram is set, the consuming module's CacheKey additionally hashes the merged TierTable.json (the whole-program output). Changing any function's tier across the whole program invalidates every module's cache. This is correct but expensive; Pass 2 is opt-in for that reason.

4.2 Why each banned/deferred feature is rejected

BCL-surface dispatch. The mapped BCL types live in the XPact.CSharp.BCL NuGet (reference DLL only; no implementation). XIL2CPP recognizes types by their full namespace-qualified name and dispatches the emit through the per-type mapping table in §5. The reference DLL is C#-source-readable so authors get IntelliSense, but the emit pass replaces every call site with the XPact equivalent.

Why async/await is banned on sim-path. Per Q4 resolution: async continuations resume on the thread pool by default; SynchronizationContext.Current determines the resume thread. Sim-path code MUST run only on SimPathSerialExecutor. If a sim-path async method awaits, the continuation will resume on a worker pool thread, and any subsequent NewObject will violate X-NEW (the sim-path NewObject invariant). The two solutions (ban or enforce continuation-pinning) both have costs; banning is the simpler + safer commitment. Authors who need yield-style cooperative multitasking on sim-path can use the gameplay-tier task system XPact provides (forthcoming XTaskGraph integration), which is sim-path-thread-affined by design.

Why lock(obj) is banned on sim-path. Per Q5 resolution: sim-path code runs on a single serial executor. Acquiring a lock implies waiting; waiting on the serial executor is a deadlock if the holder of the lock is waiting for the same executor. lock on sim-path is therefore a category error. On non-sim-path TUs, lock(obj) maps to an FScopedCriticalSection over a per-object monitor lazy-allocated on first lock.

Why LINQ is banned on sim-path. Per §5.19: LINQ's deferred-execution semantics combined with allocation-heavy operators (.Where(...).Select(...).ToList()) make memory pressure unpredictable on sim-path. The cross-arch bit-exact determinism guarantee requires sim-path memory pressure to be predictable. LINQ also allocates per-call delegate state-objects that would each need XGCRootSpan registration. The combined cost is unacceptable on the sim-path frame budget.

Why dynamic is permanently banned. Per Locked Commitment 1: dynamic requires the DLR (Dynamic Language Runtime), which is part of .NET's managed runtime. XPact has no managed runtime.

Why DllImport is permanently banned. Per Locked Commitment 1: P/Invoke is a managed-to-native marshalling shim. XPact's output is already native; calls to C++ functions happen at the C++ level via direct function call. C# code that needs to call a native function must declare an extern C++ function via the XPact-specific [XExternal] attribute (forthcoming, post-MVP).

4.3 Diagnostic for unsupported feature use

Every feature in the “BANNED” or “post-MVP” status emits a build-time diagnostic at first detection. The diagnostic code is per-feature (see §12 for the full diagnostic catalog). The diagnostic includes:

  • The feature name (e.g., “dynamic keyword”).
  • The exact source location (file:line:col).
  • The rationale (short form: “not supported per Locked Commitment 1: no managed runtime”).
  • The suggested alternative if one exists (e.g., “use a specific generic type instead of dynamic”).

The diagnostic is non-suppressible. Authors cannot #pragma warning disable these (the XIL2CPP analyzer ignores suppression pragmas for the X-prefixed codes, per the same pattern Roslyn's CS-prefixed compiler errors use).

5.3 Statement and expression mappings

Local variable declarations. var x = expr → auto x = expr; (with explicit type if auto can't deduce). int x = 5; → int32_t x = 5;. Locals that are XObject* are tracked in the Pass 6 stack-map record.

Assignments.

// C# input (non-reference LHS):
//   x = 5;

// C++ output:
x = 5;

// C# input (XObject-reference LHS):
//   actor.Owner = newOwner;

// C++ output:
XPACT_GC_STORE(actor, &actor->Owner, newOwner);

The XPACT_GC_STORE macro is defined in XCoreXObject/XGCWriteBarrier.h and lowers to:

#define XPACT_GC_STORE(parent_obj, slot_ptr, new_value) \
    do { \
        ::XCore::Reflect::XGC_WriteBarrier( \
            reinterpret_cast<void**>(slot_ptr), \
            static_cast<void*>(new_value)); \
        *(slot_ptr) = (new_value); \
    } while (0)

Critical design decision (XPACT_GC_STORE emission). The barrier is emitted at every reference-storing assignment, including: direct field writes (obj.Field = x), indirect field writes through pointer chains (a.b.c.Field = x emits a barrier at the final store; intermediate reads are bare loads), array slot writes (arr[i] = x where arr is TArray<XPtr<T>>), TMap slot writes via map[k] = v, and aggregate-assignment via record with-expressions when the record contains XObject refs. Per Constraint §2.6, the barrier is recognized by type analysis: any C# field whose reflected type is FObjectProperty, FWeakObjectProperty, or FStructProperty containing a reference / FArrayProperty containing a reference / FMapProperty containing a reference / FSetProperty containing a reference is a barrier target. The codegen pass inserts the macro expansion at the AST-lowering stage.

Conditional expressions. cond ? a : b → cond ? a : b. Null-coalescing a ?? b → (a != nullptr ? a : b). Null-conditional a?.b → (a != nullptr ? a->b : nullptr).

5.4 Field and property emit

Every C# field (and every auto-property's backing field) emits as a C++ member in source-declaration order. The reflection metadata (FProperty descriptor) is emitted by XHT; XIL2CPP emits only the storage and accessor bodies.

Required members. required int X { get; set; } emits:

  • A C++ member int32_t X = 0;.
  • FProperty descriptor (XHT side) carries the CPF_RequiredInit bit (per XCore-4b.html line 726).
  • Constructor body emits a runtime check: if the C# object initializer did not set X, the construction aborts. The C# compile-error path catches most cases at parse time; the runtime check is belt-and-suspenders for deserialization paths where the initializer is bypassed.

Init-only properties. public int X { get; init; } emit the setter as accessible only from the constructor / object initializer:

// XIL2CPP emits the setter visible only to the constructor.
// Outside the constructor, the setter is mangled with a different suffix that
// the AST-normalization pass rejects.

Nullable reference types. XActor? Owner emits the same C++ member as XActor Owner (no extra storage); the FProperty descriptor (XHT side) carries the CPF_NullableReferenceType bit.

Nullable value types. int? emits as XOptional<int32_t> (a 5-byte struct: 4 bytes int + 1 byte has-value; aligned to 8 bytes net).

5.5 String emit

C# string is mapped to the XCSharpString 8-byte value-type handle per Contract §6.1 line 1098-1104:

struct XCSharpString {
    const ::XCore::Container::FString* m_storage;
};

String literals. Every C# string literal in the source emits as a constinit const FString in the binary's .rodata section. The compile-time interning rule per XCore-4a.html line 1432-1437: two distinct C# literals with the same UTF-8 content resolve to the same address. A build-time error fires if two distinct C# literals would resolve to the same address but have different content (impossible by the interning rule; the error is a safety net).

// C# input:
//   var s = "hello";
//   var t = nameof(SomeMethod);
//   var u = "SomeMethod";  // assume SomeMethod is the method name

// C++ output (in .rodata):

constinit const ::XCore::Container::FString _String_SomeMethod("SomeMethod", 10);

// At use site:
::XCSharpString s{&_String_hello};
::XCSharpString t{&_String_SomeMethod};
::XCSharpString u{&_String_SomeMethod};   // SAME ADDRESS as t per Contract §6.2 line 1117-1120

Pointer-identity guarantee. ReferenceEquals(nameof(X), "X") holds. The test Tests/IL2CPP/StringInternIdentity validates this across 1000+ literal pairs across two DLLs (per XCore-4a.html line 1436).

String interpolation. $"hello {name}" lowers at AST normalization to a builder-based form:

// AST-normalized form:
//   var __sb = new XCSharpStringBuilder();
//   __sb.Append("hello ");
//   __sb.Append(name);

Sim-path s[i] ban. Iterator surface. s.AsSpan(), s.IndexOf(c), s.Substring(i, n), s.AsCodepoints() are mapped to XCSharpString member functions per Contract §6.4 line 1132-1141.

template <>
class ::XCore::Container::TArray<::XCore::Reflect::XPtr<::XActor>> {
public:
    ::XCore::Reflect::XPtr<::XActor>* m_data = nullptr;
    int32_t                            m_count = 0;
    int32_t                            m_capacity = 0;
    ::XCore::Reflect::XGCRootSpan      m_rootSpan;   // GC-aware partial spec
    // copy-ctor = delete;  copy-assign = delete;  (move-only per Contract §3.4)

    TArray() {
        m_rootSpan = ::XCore::Reflect::XGCRootSpan{
            /* base   */ reinterpret_cast<void**>(m_data),
            /* stride */ sizeof(::XCore::Reflect::XPtr<::XActor>),
            /* count  */ 0,
            /* kind   */ ::XCore::Reflect::XGCRootKind::Strong,
            /* _padding */ 0
        };
        ::XCore::Reflect::XGC_RegisterRootSpan(&m_rootSpan);
    }
    ~TArray() {
        ::XCore::Reflect::XGC_UnregisterRootSpan(&m_rootSpan);
    }

    void Add(::XCore::Reflect::XPtr<::XActor> item) {
        if (m_count == m_capacity) GrowAndUpdateRootSpan();
        XPACT_GC_STORE(this, &m_data[m_count], item.Raw());  // store w/ barrier
        m_count++;
        ::XCore::Reflect::XGC_UpdateRootSpan(&m_rootSpan,
            reinterpret_cast<void**>(m_data), m_count);
    }

private:
    void GrowAndUpdateRootSpan() {
        int32_t newCap = (m_capacity == 0) ? 4 : m_capacity * 2;
        auto* newBuf = static_cast<::XCore::Reflect::XPtr<::XActor>*>(
            ::FMemory::Realloc(m_data, newCap * sizeof(::XCore::Reflect::XPtr<::XActor>)));
        m_data = newBuf;
        m_capacity = newCap;
        ::XCore::Reflect::XGC_UpdateRootSpan(&m_rootSpan,
            reinterpret_cast<void**>(m_data), m_count);
    }
};

5.8 Generic emit

Generic types and methods emit as C++ templates. The closed-instantiation walk at Pass 3 enumerates every reachable closed type tree; each closed instantiation emits a per-instantiation FClass with a name suffix (e.g., TArray_int, TArray_XActor) per Constraint §2.14.

The walk recursion bound is depth 16; exceeding emits XIL2CPP123 — generic instantiation closure exceeds depth 16. The walk uses a HashSet<(OpenGeneric, TypeArgs)> for cycle detection; cycles emit XIL2CPP124 — cyclic generic type closure detected.

Generic constraints. The supported constraints:

  • where T : XObject — recipient assumes T-typed XGCRootSpan emission.
  • where T : struct — recipient may rely on value semantics.
  • where T : unmanaged — recipient may rely on POD layout; emit can use direct memcpy.
  • where T : new() — recipient may invoke parameterless constructor.
  • where T : SomeBase — recipient may upcast to SomeBase.
  • where T : ISomeInterface — recipient may dispatch through interface vtable.

Generic variance. in T / out T annotations on interfaces propagate to the C++ template parameters; no runtime cost. Variance-related operations (e.g., upcasting a List<Derived> to IEnumerable<Base>) are emitted as static_cast at the call site.

5.10 Lock and synchronization (Q5 resolution)

Sim-path: BANNED. lock(obj) in a sim-path TU emits XIL2CPP043 — lock(obj) is banned on sim-path TUs (single serial executor; locking is a category error).

Non-sim-path: maps to FScopedCriticalSection over a per-object monitor. Per-object monitors are lazily allocated on first lock; the monitor itself is a 56-byte FCriticalSection from XCore-4a.

// C# input (non-sim-path):
//   lock (someObject) {
//       // critical section
//   }

// C++ output:
{
    ::XCore::Concurrency::FScopedCriticalSection lock(
        ::XCore::Concurrency::FObjectMonitorRegistry::GetOrCreate(someObject));
    // critical section
}

The FObjectMonitorRegistry is a per-process singleton that maintains a thread-safe map from XObject* to FCriticalSection. The map's lifetime is the process; entries are not GC'd individually (the monitor outlives the object's individual access pattern).

5.11 Reflection runtime (Q7 resolution)

XIL2CPP supports a restricted reflection surface:

  • typeof(T) → ::XCore::Reflect::XReflectionRuntime::FindClass(::FName("T")) or the directly-emitted T::StaticClass() when T is statically known.
  • obj.GetType() → obj->GetClass() (the FClass-driven dispatcher returns the object's const FClass*).
  • typeof(T).Name → interned const FString* matching the literal "T" (per Contract §6.2 line 1117-1120).
  • typeof(T).FullName → interned const FString* matching the literal "Namespace.T".
  • (obj as T) / obj is T → ::XCore::Reflect::Cast<T>(obj) / ::XCore::Reflect::IsA<T>(obj); both dispatch through the FClass chain.

Banned:

  • Type.GetMethods(), MethodInfo.Invoke(), Type.InvokeMember() → XIL2CPP050.
  • System.Reflection.Emit → XIL2CPP052 (permanently banned per Locked Commitment 1).
  • System.Activator.CreateInstance → XIL2CPP051 on sim-path; warning on non-sim-path.

5.12 Exception handling (try/catch/finally; throw)

Per Contract §5.6-5.7: try/catch/finally and throw force the enclosing function to Tier 1 (the XResult shim form). The emit differs Dev/Test vs Shipping:

Dev/Test lowering (native exceptions).

// C# input:
//   public void DoWork() {
//       try {
//           SomethingThatMightThrow();
//       }
//       catch (FileNotFoundException ex) {
//           log.Error(ex.Message);
//       }
//       finally {
//           Cleanup();
//       }
//   }

// C++ output (Dev/Test):
extern "C" void _v1..._DoWork_Body(...) {
    try {
        SomethingThatMightThrow_Body(...);
    }
    catch (const ::XCore::Exception::XCSharpException& ex) {
        if (ex.TypeIs<::FileNotFoundException>()) {
            log.Error(ex.Message);
            goto finally_block;
        }
        // Re-throw if no matching catch:
        Cleanup();
        throw;
    }
finally_block:
    Cleanup();
}

Shipping lowering (Result<T, E> early-return).

extern "C" void _v1..._DoWork_Body(::XCore::Exception::XResult* outResult) {
    ::XCore::Exception::XResult inner;
    SomethingThatMightThrow_Body(&inner);
    if (inner.discriminator == ::XCore::Exception::XResult::Discriminator::Error) {
        if (inner.error.code == ::FileNotFoundExceptionCode) {
            log.Error(inner.error.message);
        }
        else {
            // No matching catch; propagate
            *outResult = inner;
            Cleanup();
            return;
        }
    }
    Cleanup();
    outResult->discriminator = ::XCore::Exception::XResult::Discriminator::Success;
}

The XResult RAII destructor. Per Constraint §2.9: XIL2CPP emits the per-call-site destructor teardown for XResult values containing non-trivially-destructible non-XObject types (e.g., FString, TArray<T>). The teardown is emitted automatically at every call site where the function returns an XResult containing such a type.

5.15 IDisposable and using

Per Constraint §4.7: XObject implements IDisposable with Dispose() calling MarkForKill(). Raw ~XObject() direct calls are forbidden (XIL2CPP090 — explicit destructor call on XObject-derived type; use MarkForKill() or let the GC reclaim).

using block lowers at AST normalization to try/finally:

// C# input:
//   using (var x = new Disposable()) { ... }

// AST-normalized:
//   var x = new Disposable();
//   try { ... } finally { ((IDisposable)x).Dispose(); }

// C++ output:
{
    auto x = ::Disposable{};
    try {
        ...
    }
    catch (...) {
        x.Dispose();
        throw;
    }
    x.Dispose();
}

For XObject-derived using targets, Dispose() maps to x->MarkForKill(). The destructor is NOT called; the GC reclaims the slot on next sweep.

5.16 Checked and unchecked arithmetic (Q8 resolution)

Per Q8 resolution: default semantics is unchecked (standard C++ overflow rules: wraps for unsigned; undefined for signed but matches the underlying architecture's two's complement). The checked block emits explicit overflow checks:

// C# input:
//   int Add(int a, int b) {
//       checked {
//           return a + b;
//       }
//   }

// C++ output:
int32_t Add(int32_t a, int32_t b) noexcept {
    int32_t result;
    if (__builtin_add_overflow(a, b, &result)) {
        ::XCore::HAL::Abort("integer overflow in checked arithmetic");
    }
    return result;
}

The overflow check uses __builtin_add_overflow family (Clang / GCC) or _addcarry_u32 / SafeAdd equivalents on MSVC.

The sim-path commitment: cross-arch behavior MUST be identical. Unsigned overflow wraps the same on x86_64 + ARM64 (per the C++ standard); signed overflow is undefined behavior in C++, but the toolchain matrix (MSVC 19.44+ / Clang 17+ / GCC 13+ with -fwrapv when sim-path) defines signed overflow as wrap. Sim-path TUs MUST compile with -fwrapv for Clang/GCC and the MSVC equivalent (/d2overflow- or equivalent flag; under research, may require the integer-overflow wrapper).

Critical design decision (sim-path signed-overflow). Round 1 audit MUST verify the exact MSVC flag for signed-overflow-as-wrap; the spec lists /d2overflow- as provisional pending verification. If MSVC has no clean flag, sim-path TUs targeting Win64 emit explicit overflow checks via __builtin_add_overflow at every signed integer operation (the slowdown is acceptable on sim-path which is single-threaded).

5.17 Fixed statement (Q9 resolution)

Per Q9: non-moving GC means pinning is trivially satisfied. fixed emits as a direct pointer assignment:

// C# input:
//   fixed (int* p = &arr[0]) { *p = 42; }

// C++ output:
{
    int32_t* p = &arr.Data()[0];  // arr's data pointer is already stable per non-moving GC

}

No pinning machinery is generated. Reading C# code that uses fixed on XObject* is rejected as XIL2CPP091 — fixed statement on XObject reference is meaningless; the GC is already non-moving; the C# author should use unsafe + raw pointer arithmetic if they really need the pointer (with the same XObject* unsafe guards from §5.18).

6. GC Integration

XIL2CPP is the largest single contributor to XPact's GC correctness. The collector at runtime (XCoreXObject's mark-and-sweep) relies on XIL2CPP-emitted scaffolding to enumerate roots and locate references. If XIL2CPP misses any of: a stack-resident XObject* local, a container's XGCRootSpan registration, a reference-storing assignment without the write barrier, or a function-entry safe-point check, the collector's correctness is compromised — potentially crashing the game or, worse, silently corrupting state. This section enumerates the emit obligations.

6.1 Precise stack roots: FStackMapRecord per function

Every transpiled C# function (including: instance method, static method, virtual dispatcher, constructor, static constructor, operator overload, property getter/setter, indexer accessor, lambda body, async MoveNext, iterator MoveNext, local function) MUST emit a per-function FStackMapRecord in .rodata listing the byte-offset within the stack frame of every live XObject* (locals, temporaries, arguments).

The record format per XCoreXObject.html §5.4 line 1281-1290:

namespace XCore::Reflect {
    struct alignas(8) FStackMapRecord {
        uint32_t pcRangeBegin;     // byte offset within the function (from function entry)
        uint32_t pcRangeEnd;       // byte offset within the function (from function entry)
        uint16_t numLiveRefs;
        uint16_t _pad;
        int32_t  liveRefOffsets[]; // byte offsets within the stack frame
    };
}

The PC range demarcates the range of program counter values within the function for which the listed live refs are the canonical set. A simple function (no branching) emits one record covering [0, 0xFFFFFFFFu]. A function with conditional locals (e.g., if (cond) { XActor a = ...; }) emits multiple records covering the disjoint PC ranges where the locals are live.

Live-ref-offset computation. XIL2CPP computes byte offsets via the platform ABI's stack-frame layout. The offsets are relative to the function's frame pointer (FP) or, when FP-omission is enabled (release builds with -fomit-frame-pointer), relative to the function's stack pointer at the safe-point. The platform ABI rule is:

  • Win64. Microsoft x64 calling convention. Argument registers RCX/RDX/R8/R9 store first four args; remaining args spill to stack at [RSP+0x28] upward. XObject* in registers requires register-spill at every safe-point; XIL2CPP emits register-spilling assembly that copies the live-ref register values to spill slots, and the FStackMapRecord lists the spill slot offsets.
  • Quest 3 ARM64. AAPCS64 calling convention. Argument registers X0-X7 store first eight args. Same register-spill rule.

Critical design decision (live-ref enumeration via stack-spilling). Per the C++ ABI, function-local variables in registers do not have a stable stack offset until they spill. The naive approach (emit FStackMapRecord with register names) is incompatible with the GC's "read the live ref at this stack offset" model. XIL2CPP solves this by emitting an explicit spill at every safe-point: at function entry, immediately before XPACT_SAFEPOINT_CHECK(), every live XObject* register is spilled to a designated stack slot. The FStackMapRecord lists those slot offsets. After the safe-point, the values may move back to registers. The slot space is per-function, computed at Pass 6.

Size budget per XCoreXObject.html §5.4 line 1292: ~30 bytes per function; ~300 KB for 10k transpiled functions. Cache layout: all FStackMapRecord live in a single .rodata section, indexed by function start address. The collector at safe-point time does a binary search for the running function's start address.

FStackMapRecord emit example.

// C# input:
//   public void DoWork() {
//       XActor a = this.GetActor();
//       XComponent c = this.GetComponent();
//       a.Tick(0.016f);
//       c.Update();
//   }

// C++ output:
extern "C" void _v1..._DoWork(::SomeObject* self) noexcept {
    XPACT_SAFEPOINT_CHECK();
    // Stack-resident XObject* locals; XIL2CPP emits explicit stack slots:
    ::XActor* _slot_a;
    ::XComponent* _slot_c;

    _slot_a = self->GetActor();
    _slot_c = self->GetComponent();
    _slot_a->Tick(0.016f);
    _slot_c->Update();
}

// FStackMapRecord (in .rodata):
static const ::XCore::Reflect::FStackMapRecord _StackMap__DoWork = {
    /* pcRangeBegin */ 0,
    /* pcRangeEnd   */ 0xFFFFFFFFu,
    /* numLiveRefs  */ 3,    // self + _slot_a + _slot_c
    /* _pad         */ 0,
    /* liveRefOffsets[] */ { 8, 16, 24 }  // FP-relative; computed by emit pass
};

// Registration with the collector:
extern "C" int _StackMap_DoWork_RegisterAtLoad = [](){
    ::XCore::Reflect::XStackMapTable::Register(
        reinterpret_cast<uintptr_t>(&_v1..._DoWork),
        sizeof(_v1..._DoWork),  // function size (linker-resolved)
        &_StackMap__DoWork);
    return 0;
}();

The function-size-at-link-time computation is supported on all three toolchains (MSVC: __ImageBase + linker-emitted symbol size; Clang/GCC: __builtin_function_size or the linker's .size directive).

6.2 Container roots: XGCRootSpan emit

Per Constraint §2.3 + Contract §3.1 line 547-575: every transpiled container type that may hold XObject references embeds an XGCRootSpan member at the end of the class body. The container's constructor registers the span; resizing updates it; the destructor unregisters it.

Selection rules per Constraint §3.2:

  • Generic arg statically XObject-derived (List<XActor>, Dictionary<FName, XComponent>) → XGCRootKind::Strong.
  • Generic arg statically value type (List<int>) → NO GC scaffolding (pure RAII).
  • Generic arg object or non-statically-typed interface that could hold XObjects → XGCRootKind::Conservative + build-time warning XIL2CPP070 on sim-path TUs.

The container is move-only per Contract §3.4 line 665-699: copy-constructor and copy-assignment are = delete. Move construction/assignment transfer span-registration ownership atomically with respect to the mark phase (the GC's mark phase has a snapshot mechanism per XCoreXObject.html §4 that handles the transfer).

XIL2CPP emits container = true on the class-descriptor flag per Contract §3.7 line 759. XLiveCoding's patch-validation pass reads this flag to enforce the layout-freeze invariant on hot-reload.

6.3 Write barriers: XPACT_GC_STORE emission

Per Constraint §2.6: every reference-storing assignment emits XPACT_GC_STORE. The detection rule:

  1. Pass 3 walks every AssignmentExpressionSyntax in the parse tree.
  2. Resolve the LHS's type via Roslyn semantic model.
  3. If the LHS's resolved FProperty kind is one of: FObjectProperty, FWeakObjectProperty, FStructProperty containing a reference (recursive check), FArrayProperty with reference inner, FMapProperty with reference inner, FSetProperty with reference inner, then mark the assignment for barrier emission.
  4. Pass 6 emits XPACT_GC_STORE(parent_obj, &slot, new_value) at the LHS site.

Read sites do NOT emit a read barrier. Per XCoreXObject.html §5.2: the SATB pre-store barrier model requires only a write barrier; reads are bare pointer loads.

When the barrier is omitted. Three cases where XIL2CPP intentionally omits the barrier:

  1. New-object initialization. When the assignment occurs inside the object's constructor before the object is reachable (i.e., before the constructor returns and the object is registered with the collector), the barrier is omitted. The mark bit on the new object is set to the current mark cycle so it cannot be missed; the bare store is safe.
  2. Within an XCS_OPAQUE region. A future optimization (post-MVP) lets authors annotate a code region as "I promise no GC can run here" via XCS_OPAQUE_BEGIN() / XCS_OPAQUE_END(). Within the region, the barrier is omitted. Out-of-scope for MVP; flagged here as a forward hook.
  3. Stack-local pointer chase intermediate. obj.a.b.c.Field = x: the intermediate reads of obj.a, obj.a.b, obj.a.b.c are bare loads (no barrier; reads have no barrier in any case). The final assignment ... = x emits the barrier.

6.4 Outer-chain emit (Locked Commitment 3 enforcement)

Per Locked Commitment 3 + §5.3: every XObject.New<T>(outer, name, flags) call site has an explicit Outer. XIL2CPP enforces this at emit time:

  1. Pass 3 verifies that every XObject.New<T> call has all three arguments at the call site (Roslyn's overload resolution catches missing arguments at parse time, but XIL2CPP double-checks for defensive depth).
  2. Pass 3 verifies that the outer argument is NOT null (a literal null in the source emits diagnostic XIL2CPP002 — XObject.New<T> called with null Outer; pass an actual owning XObject).
  3. Pass 6 emits the C++ NewObject<T'>(outer, name, flags) directly; XCoreXObject's runtime path asserts outer != nullptr as belt-and-suspenders.

Note: bona fide null-outer use cases (root objects of an ownership chain) must use the explicit XObject.NewRoot<T>(name, flags) factory which has no outer parameter and is restricted to internal engine use via an [XObjectInternalConstructor] attribute. Gameplay-author C# cannot call it. This pattern matches UE's NewObject<T>(Outer=GetTransientPackage(), ...) default but makes the omission explicit at the type level.

6.5 Safe-point checks at function entry and back-edge

Per Constraint §2.5: every XIL2CPP-emitted function entry inserts a function-entry safe-point check; every long-loop back-edge inserts a back-edge safe-point check.

The safe-point macro:

// In XCoreXObject/Internal/XSafePoint.h:
#define XPACT_SAFEPOINT_CHECK() \
    do { \
        if (XPACT_UNLIKELY(::XCore::Reflect::XGCSafepoint::s_pendingFlag.load(std::memory_order_relaxed))) { \
            ::XCore::Reflect::XGCSafepoint::HandlePending(); \
        } \
    } while (0)

#define XPACT_BACKEDGE_SAFEPOINT_CHECK() XPACT_SAFEPOINT_CHECK()

The cost is ~3-5 cycles per call per XCoreXObject.html §5.5 line 1301.

Long-loop detection rule. Pass 3 analyses every for, while, do/while, and foreach loop. The loop is "long" if:

  1. The iteration count is unbounded by static analysis (the loop's iteration count is not a compile-time constant or trivially-bounded variable), OR
  2. The iteration count is a compile-time constant > 16 (the default threshold; configurable per-module via SafePointLoopThreshold in the ModuleRules).

If the loop is long, the back-edge safe-point check is emitted. If the loop is provably short (compile-time constant ≤ 16), the back-edge check is omitted.

Critical design decision (safe-point coverage). The GC's mark phase relies on every running function reaching a safe-point in bounded time. If any function or any loop bypasses the check, the GC's mark phase can hang indefinitely. Per XCoreXObject.html §5.5: the coverage guarantee is “100%”. Round 1 audit MUST verify that no XIL2CPP emit path omits the entry-safe-point check. The corollary: XIL2CPP-emitted code MUST NOT call C++ functions that loop unboundedly without their own safe-point check; this is enforced at Tier 1/Tier 2 classification (Pass 4 marks any callee that's not XPact-internal as potentially-blocking and forces the caller to a Tier 1 shim with a safe-point check at shim entry).

6.6 Conservative root scanning for List<object>

When the C# container's generic argument is object or a non-XObject-derived interface that could hold an XObject (e.g., IDamageable), XIL2CPP cannot statically prove whether the contents are XObjects. The container emits an XGCRootKind::Conservative span; the collector treats every slot as a potential XObject* and validates at scan time (the slot is dereferenced as XObject* only if it's a valid pointer into the XObject heap).

Sim-path TUs emit warning XIL2CPP070 — Conservative XGCRootSpan used; cross-arch determinism may be affected. Consider replacing object with a typed reference. The warning is per-closed-type-instantiation, deduplicated via the XIL2CPP build cache.

6.7 Struct-with-XObject-field handling

A C# struct that contains an XObject reference field is handled per storage:

  • Stack-stored. The function's FStackMapRecord registers the byte offset of the struct's XObject field (relative to the stack-frame).
  • Class-field. The enclosing class's schema vector recurses via EXObjectRefSchemaOp::Struct opcode.
  • Array-stored. TArray<TStruct> with an XGCRootSpan partial specialization that recurses; the stride accounts for the struct's size; the GC walks each array element's XObject field as a root.

8. Hot-reload Integration

8.1 Symbol mangling stability (criterion g)

Per Contract §12.2 line 2163: running XIL2CPP twice over the same input C# source produces byte-identical mangled output symbols. A method in build N+1 has the same symbol name as in build N if its signature is unchanged.

XIL2CPP's mangling rules per Contract §2.2 are deterministic by construction:

  • The mangled name depends only on (a) the contract version hash, (b) the namespace-qualified type name, (c) the method name (CLR convention), (d) the generic-arg manglings (in source-declaration order), (e) the parameter manglings (in declaration order; reference / value / by-ref / in / out prefixes).
  • The walk is deterministic: source-tree depth-first; per-tree by file path lexicographic.
  • Internal dict iteration is sorted by name before emit.

XIL2CPP's own binary is reproducible per Contract §2.4 line 526: deterministic timestamps, deterministic build IDs.

8.2 Vtable stability across patches

Per Contract §2.3 line 496: “no virtual-method signature changes are permitted mid-session, so the vtable layout is stable across patches.” XIL2CPP enforces this structurally:

  • The FXObjectLifecycleTable function-pointer slots are at fixed offsets (XCoreXObject §2.4); slot index is part of the cross-tool ABI envelope (the tag XPACT_XOBJECT_LIFECYCLE_TABLE_TAG pins the layout).
  • Adding a new virtual method to an XClass mid-session is rejected by XLiveCoding's Phase 1 layout-drift gate (per FIX-A-HIGH-14 in XCoreXObject Rev 4).
  • XIL2CPP emits virtual dispatchers as free functions (per §5.2); the dispatcher's address is stable across hot-reload (the symbol mangling is unchanged for unchanged signatures).

8.3 Container layout freeze

Per Contract §3.7 line 737-739: container class layouts (any class with an embedded XGCRootSpan member) are layout-frozen within a hot-reload session. XIL2CPP emits container = true on every such class-descriptor.

XLiveCoding's patch-validation pass compares field-offset list field-by-field; mismatch fails patch with exit codes 90-99 (Live Coding domain). Allowed: function-body changes; adding new non-virtual methods. Disallowed: adding/removing/reordering data fields, relocating m_rootSpan, changing span kind, changing stride.

8.4 Sub-pool rebind cooperation (FIX-A-MIN-40)

Per FIX-A-MIN-40 in XCoreXObject Rev 4: hot-reload class replacement migrates cells from the OldClass sub-pool to the NewClass sub-pool. XIL2CPP-emitted code MUST NOT assume the specific FClass*-to-cell-pool mapping survives hot-reload.

The corollary: XIL2CPP-emitted code that caches FClass* (e.g., per-instantiation generic FClass cache) MUST register a listener on the OnClassReplaced delegate to invalidate the cache. The registration is auto-emitted at Z_Construct_FClass_* aggregation time:

extern "C" const ::XCore::Reflect::FClass* Z_Construct_FClass_MyModule_XHealthPickup() noexcept

9.8 Reference DLL pipeline (ReferenceCompileCSharpAction)

XIL2CPP needs to resolve types across modules. The conventional approach (full source compilation per-dependency) is rejected because it makes per-module XIL2CPP serially dependent on every dependency.

Rev 1 specifies a new XBT action: ReferenceCompileCSharpAction (XActionType ordinal 14, post-Rev-13.9 contract extension). For each module M with C# sources:

  1. XBT runs ReferenceCompileCSharpAction(M) which compiles M's .cs files to a reference-only DLL (M.refonly.dll) using Roslyn's /refonly flag. The reference DLL contains type signatures + method signatures but no method bodies.
  2. The reference DLL is published to Intermediate/.../<Module>/Reference/M.refonly.dll.
  3. XIL2CPP(M') for any module M' depending on M loads M.refonly.dll as a MetadataReference. Type resolution + semantic analysis works against the reference DLL without parsing M's source.

The reference-DLL action is fast (~1 sec per 1k LoC) and runs concurrent with XIL2CPP(M) for each M.

Critical design decision (ReferenceCompileCSharpAction). Rev 1 introduces this action as a forward extension to the XBT action graph. Round 1 audit MUST validate that this fits cleanly into XBT.html's action ordering and the per-action CacheKeyComponents surface. If the audit finds a cleaner alternative (e.g., reading M's C# source directly from the cache; lazy parsing on demand), the design adjusts. Flagged in §14 as audit item.

10. XHT Reflection Consumption

10.1 The XHT / XIL2CPP boundary

Per XHT.html §17.2 line 1565-1574: XHT and XIL2CPP run concurrent against the same module. The boundary is:

  • XHT parses the module's .cs files for [XClass] / [XStruct] / [XEnum] / [XInterface] attributes; emits the C++-side .gen.h (declarations) + .gen.cpp (FClass / FStruct / FEnum / FInterface descriptor static-initialization).
  • XIL2CPP parses the same module's .cs files for bodies; emits .cs.h (per-class declarations matching the C++ structure XHT declared) + .cs.cpp (per-method bodies + lifecycle-slot bodies + ClassConstructorFn).
  • The two converge at the C++ compile step: .cs.cpp #includes .gen.h to pick up property accessors; the linker resolves Z_Construct_FClass_* symbol references between .gen.cpp (declaration of extern) and .cs.cpp (definition).

10.2 XHT-emitted metadata XIL2CPP reads

Per Constraint §8.2:

  • FClass descriptors for cross-module classes (XHT publishes via .gen.cpp; XIL2CPP reads via standard C++ include of .gen.h).
  • FProperty descriptors for each [XProperty]-attributed field.
  • NoThrow annotation bit on function descriptors (XHT emits; XIL2CPP reads at Pass 4 tier classification).
  • FXObjectRefSchemaOp opcode arrays (XHT emits per §10.4 below).
  • FXObjectLifecycleTable for C++-declared classes (XHT emits; XIL2CPP emits the matching table for C#-declared classes).

10.3 Cross-language type-pair manifest

Per XHT.html §17.3 line 1580: for each cross-language type pair (a C++ class + a C# partial class declaring the same type), the .gen.manifest's [Types] section emits both source files. XIL2CPP reads this at transpile time so the IL2CPP-emitted body code can target the same singleton-getter the C++ side references.

10.4 Q14 resolution: schema-vector emit ownership

Constraint Q14 surfaces a contradiction. XCoreXObject.html §7.4.1 line 1773 says: “XHT's emit pass walks FClass.ObjectRefProperties at compile time and emits one FXObjectRefSchemaOp per reference-carrying FProperty.” But Contract §10.2 line 1818 says: “XIL2CPP emits the matching definition in its transpiled C++ output” for C#-declared types' singleton-getters. Does the schema-vector .rodata array live with XHT-emitted .gen.cpp or XIL2CPP-emitted .cs.cpp?

Rev 1 resolution: XHT emits the schema vector for BOTH C++-declared and C#-declared classes. XIL2CPP emits only the singleton-getter function body + the FXObjectLifecycleTable slot bodies + the ClassConstructorFn.

Rationale. XHT already has the full FProperty knowledge from its [XProperty]-attribute scan of C# fields. The same scan that emits the FProperty descriptors emits the schema-vector opcodes; they're peers. Splitting this responsibility (XHT for C++; XIL2CPP for C#) would duplicate the FProperty-walking logic and create a contract surface where the two tools must produce byte-identical schema bytes for the same class. Per Prime Directive: the integrated solution is correct; the split is the easier-to-implement-but-fragile alternative.

Implication. Round 1 audit MUST surface this to the XHT design owner. The XHT Rev 7+ document must reflect:

  • XHT emits the schema vector for C# [XClass]-declared types (in addition to the existing C++ emit per XCoreXObject.html §7.4.1).
  • XHT emits the schema vector in .gen.cpp, not the C#-side .cs.cpp.
  • The cross-tool symbol contract (XToolchainContract.html §10.2 line 1818) is amended: XHT emits the FClass constinit + the schema vector; XIL2CPP emits the singleton-getter + lifecycle bodies + ClassConstructorFn. Round 1 audit must verify this consistent split with the Contract owner.

10.5 Cross-language binding table (shared NuGet)

Per XHT.html §17.4 line 1617: both tools share the binding table via the XPact.Mangling shared NuGet. XIL2CPP at parse + emit time consults the table for: primitive mappings (bool→bool, int→int32_t, float→float, string→XCSharpString), container mappings (List<T>→TArray<T'>, etc.), XObject subclass mappings.

10.6 What XIL2CPP does NOT consume

Per Contract §10.2 line 2029: neither parses any other tool's binary output during their own work. The manifest is the join key. XIL2CPP does NOT parse XHT's .gen.h content as data; it reads it via standard C++ include for the property accessors.

15. Implementation Order (Sub-Phase Breakdown)

XIL2CPP is the largest single tool in the XPact toolchain after XCoreXObject. The implementation phase (Phase 6, post-XCoreXObject Phase 5 completion) is broken into sub-phases. Each sub-phase has clear deliverables, testing gates, and a duration estimate at the foundation-tool cadence.

  1. Phase 6.a — Roslyn front-end + parse-tree consumption (Pass 1): ship the XIL2CPP CLI binary scaffold; integrate Microsoft.CodeAnalysis.CSharp v4.8+; implement the manifest reader (JSON + FBS); implement the per-module C# parse via CSharpSyntaxTree.ParseText + CSharpCompilation with reference-DLL metadata; ship the ReferenceCompileCSharpAction (XBT extension ordinal 14). Unit tests verify parse of every C# 12 syntax feature in §4.1. Estimated: 2-3 weeks.
  2. Phase 6.b — AST normalization + semantic analysis (Pass 2 + Pass 3): ship the AST normalization pass (expand expression-bodied members, lower pattern matching, flatten using-blocks, expand collection expressions, normalize record positional ctors, expand with expressions, lower string interpolation); ship semantic analysis (XIL2CPP001 diagnostic; sim-path banned-API enumeration; reference-store enumeration; container enumeration; lambda capture analysis; async/iterator site enumeration; generic instantiation closed-walk; reflection consumption; cross-module callee NoThrow lookup). Unit tests verify each pass output against a golden corpus. Estimated: 3-4 weeks.
  3. Phase 6.c — Tier classification Pass 1 (Pass 4): ship the per-module fixpoint Tier 2 classification; ship TierTable.partial.<Module>.json emit; ship cross-module callee NoThrow lookup via XHT-emitted reflection metadata. Unit tests verify Tier 2 classification against synthetic corpus + verify Tier 1 conservatism on unresolved cross-module callees. Estimated: 1-2 weeks.
  4. Phase 6.d — Two-pass tier classification Pass 2 (post-MVP): ship the Tier2WholeProgramPass action (XActionType ordinal 13); ship the -WholeProgramTier2 XIL2CPP mode; ship the per-module re-emit deltas. Unit tests verify Tier 2 promotion never demotes; verify whole-program fixpoint converges. Estimated: 1-2 weeks. Off-MVP-critical-path; can ship after Phase 6.l.
  5. Phase 6.e — C++ emit: classes / methods / properties (Pass 5 + Pass 6 baseline): ship the mangling assignment (Pass 5); ship the basic C++ class emission (XCLASS body, ctor, FClass StaticClass() body, ClassConstructorFn, Z_PostInitProperties_*, lifecycle slot bodies, FXObjectLifecycleTable bridge); ship per-method Tier 1 shim + Tier 2 direct emit; ship the property getter/setter pair emit. Unit tests verify the emitted C++ compiles standalone; verify mangling determinism; verify ABI envelope static_asserts emit at the top of every .cs.cpp. Estimated: 4-5 weeks.
  6. Phase 6.f — C++ emit: container types + GC-aware partial specializations: ship the per-closed-instantiation container emission (TArray, TMap, TSet partial specs with XGCRootSpan registration in ctor + update on resize + unregister in dtor); ship move-only semantics; ship container = true class-descriptor flag; ship Conservative kind warning + dedup. Unit tests verify the emitted containers pass round-trip serialization + survive synthetic GC cycles + survive hot-reload class replacement. Estimated: 3-4 weeks.
  7. Phase 6.g — Stack-map emit + safe-point check + GC root span emit: ship the per-function FStackMapRecord emission with explicit register spilling at every safe-point; ship the XPACT_SAFEPOINT_CHECK at function entry + back-edge; ship the long-loop detection (Pass 3 augmentation); ship the FStackMapTable registration at module load. Unit tests verify 100% function coverage + verify the collector's binary search finds the right record + verify long-loop detection threshold. Estimated: 3-4 weeks. X-IL2CPP-STACKMAP-COV + X10 acceptance gates.
  8. Phase 6.h — Write barrier insertion: ship the XPACT_GC_STORE emission at every reference-store site (per Pass 3 enumeration); ship the new-object-init barrier omission; ship the cross-property-chain emit. Unit tests verify 100% barrier coverage + verify barrier cost ≤ 5 cycles. Estimated: 2 weeks. X-IL2CPP-BARRIER-EMIT + X4 acceptance gates.
  9. Phase 6.i — async/await + lambda + iterator state-machine emit (with sim-path enforcement): ship the closure-struct emit for lambdas with XObject captures; ship the state-machine emit for async methods (non-sim-path); ship the state-machine emit for yield-return iterators; ship the XIL2CPP044 diagnostic for sim-path async. Unit tests verify XGCRootSpan registration over captures; verify state-machine MoveNext correctness; verify the async state machine survives a GC cycle mid-await. Estimated: 3-4 weeks.
  10. Phase 6.j — Exception handling emit (try/catch/finally + throw): ship the Tier 1 shim emit for functions that throw / catch; ship the Dev/Test native-exception lowering; ship the Shipping XResult lowering; ship the per-call-site XResult destructor teardown; ship XCSharpException type infrastructure. Unit tests verify cross-config ABI (Dev shim sig = Shipping shim sig); verify exception propagation through Tier 1 boundaries; verify XResult RAII destructor fires correctly. Estimated: 3 weeks. X-IL2CPP-TIER1-ABI acceptance gate.
  11. Phase 6.k — Hot-reload integration (symbol mangling stability + cross-module rebind): ship the OnClassReplaced delegate listener auto-emission at Z_Construct_FClass_*; ship the per-FClass sub-pool rebind cooperation; verify symbol mangling stability across rebuild via SHA-256 comparison; verify container layout-freeze enforcement. Integration tests with XLiveCoding (synthetic patch DLL) verify Tier 1 shim RVA rewrite + Tier 2 module rebuild path. Estimated: 2-3 weeks. X-IL2CPP-MANGLE-DET + criterion (d) + criterion (e) acceptance gates.
  12. Phase 6.l — Foundation Prototype harness for X10, Criterion (c), Criterion (d), Criterion (e), Criterion (g): ship the SyntheticActorCorpus + SyntheticContainerCorpus + SimPathConvergenceTest + HotReloadCascadeTest + CrossArchReplayTest + SymbolStabilityTest; ship the X-* gate validation tests; integrate with XInsights telemetry for transpile-time metrics. Estimated: 3-4 weeks. All XIL2CPP-side Foundation Prototype gates.

Total estimated implementation duration: ~30-40 weeks (7-9 months) at the foundation-tool cadence (~6-8 weeks per major sub-phase). This is the largest single tool in the engine apart from XCoreXObject; the spec is long because the system is large.

Critical path. Phases 6.a → 6.b → 6.c → 6.e are sequential prerequisites; 6.f and 6.g can parallelize after 6.e; 6.h is gated by 6.g (the FStackMapRecord emit informs the write barrier emit site); 6.i + 6.j are independent and parallelize; 6.k is gated by 6.e + 6.f + 6.g; 6.l is the final integration phase.

Sub-doc split decision. Per the XCoreXObject Rev 2 pattern: this Rev 1 ships as one umbrella spec. The structural §-substructure can split at implementation-phase boundaries if the work units crystallize that way (e.g., Phase 6.g could split into a dedicated stack-map spec; Phase 6.i could split into an async-state-machine spec).
