XCore/XObject/ -- XCoreXObject (System 5) runtime types

This sub-folder hosts the runtime C++ types for XCoreXObject (System 5; see Documents/XCoreXObject.html Rev 4), the universal GC-managed gameplay-object substrate the engine builds on. It is the System-5 analog of the Reflection/ sub-folder that hosts the XCore-4b reflection descriptors.

Phase 5.a deliverable (this commit)

Per the XCoreXObject Rev 4 spec, Phase 5.a ships the XObject base type and its immediate ABI-locked companions:

  • XObject.h -- the 56-byte base for every reflected gameplay type. class XObject with NO virtual methods (hot-reload commitment + FakeVTable dispatch pattern). ABI-locked at XPACT_XOBJECT_LAYOUT_TAG.
  • EObjectFlags.h -- 32-bit lifecycle/policy bitmask with bitwise-operator surface + UE-RF_* mapping documentation (per spec §2.3 + §2.3.1).
  • FXObjectArrayEntry.h -- 32-byte per-XObject GC-state entry held in the global FXObjectArray table. ABI-locked at XPACT_XOBJECTARRAY_ENTRY_LAYOUT_TAG. Per Rev 3 FIX-M-R2-3, the rotating reachability flag MOVED from this entry to XObject::ReachabilityFlag (offset 36) to save one cache miss per object marked in the GC inner loop.
  • XPactVerifyXObjectLayout.h -- the build-time XPACT_VERIFY_XOBJECT_LAYOUT() macro per spec §11.3. XHT-emitted .gen.cpp files instantiate the macro to verify the byte-layout contract against the per-DLL compile.

The Phase 5.a private side (Engine/Source/Runtime/XCore/Private/XObject/):

  • XObject.cpp -- non-inline body for SetFlags / ClearFlags (CAS-loop atomic OR/AND), MarkAsGarbage (non-sim-path guarded; delegates to SetFlags), GetFullName (Outer-chain walk with cycle-safety cap), and IsValidLowLevel (defensive validity probe; Phase 5.a ships the no-FXObjectArray subset).

Later-phase contents (NOT in this commit)

The full XCoreXObject runtime accumulates additional types across later phases of System 5:

  • Phase 5.b -- FXObjectAllocator: the size- class-pool allocator layered on FMallocBinnedX with FMemTag:: XObject attribution.
  • Phase 5.c -- FXObjectArray: the global sparse-array table holding FXObjectArrayEntry records indexed by XObject::InternalIndex.
  • Phase 5.d -- FXObjectInitializer, FXObjectLifecycleTable: CDO + per-class lifecycle dispatch (PostInitProperties, BeginDestroy, FinishDestroy, AddReferencedObjects, Serialize, PostLoad, PreSave).
  • Phase 5.e+ -- FXObjectCollector: the mostly-concurrent SATB GC mark/sweep algorithm.
  • Phase 5.f -- XObjectKey, XPtr, XWeakPtr, XSoftPtr, XStrongPtr: the object-handle surface.
  • Phase 5.g' -- FXObjectRefSchema + FXObjectRefSchemaOp: the .rodata-resident packed opcode vector emitted by XHT per FClass for the schema-vector GC walker (UE-MISS-1 / FIX-A-CRIT-8 fast-path).

Each later-phase deliverable extends the XPACT_VERIFY_XOBJECT_LAYOUT() macro with the new type's ABI pins. See the deferred-pins block in XPactVerifyXObjectLayout.h for the documented growth path.

Hot-reload commitment

Per the Prime Directive (engineering_principles.md) + the XCoreXObject spec hot-reload commitment: no virtual methods on any type in this sub-folder. Subclass behaviour is dispatched via the FClass's FXObjectLifecycleTable (FakeVTable pattern, inherited from XCore-4b's FProperty / FScriptStruct dispatch discipline). A patched DLL may change a user-class's lifecycle implementations without rewriting the XObject vtable -- there isn't one to rewrite.

Standard C++ derivation IS permitted -- a user-class may declare its own virtual methods; the GC NEVER consults the user-class vtable. Only changes to XObject's OWN implicit destructor would matter, and XObject has none (the FakeVTable replaces it).
